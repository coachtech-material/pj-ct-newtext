# 量産ループ（複数 Section の一括執筆プロトコル）

`section-write` が複数 Section を含むスコープ（章 Issue・複数章）を扱うときの実行プロトコル。新規の量産にも、既存 Section の一括改稿にも使う。**メインセッション（親）はオーケストレーションに徹し、本文の執筆・参考資料の展開・セルフチェックはすべてサブエージェントの新しいコンテキストで行う**。これにより 1 セッションのコンテキストを圧迫せずに Tutorial 全体の量産を完走できる。

> 設計出自: 執筆フレームワーク curriculum-writer の量産ループ（さらに遡ると spec 駆動開発ツール cc-sdd の自律実装ループ）の本リポジトリ移植。対応: タスクリスト＝章 Issue の節構成 / 仕様書＝章 Issue＋マイルストーンの構成確定版 / implementer＝section-writer / reviewer＝independent-reviewer / 進捗台帳＝git log（コミット済み＝検収済み）＋章 Issue の進捗コメント。

## 原則（コンテキスト経済）

- **親は Section 本文・参考資料の生テキストを Read しない**。扱うのはファイルパス・定型報告・機械検証の出力だけ。各タスク完了後、以後に引き継ぐのは1行サマリ（例: `13-1: 全5節 APPROVED（軽微修正1回）・commit abc1234〜def5678`）のみ
- **サブエージェントへは常にパスで渡す**（ガイド類・章 Issue の節構成・ブリーフ・前後 Section・対象パス・AI臭チェック基準）。ゴール・骨子の内容を親が転記しない
- **1 タスク = 1 章 = 1 執筆サブエージェント**。章の全節を1体の `section-writer` に一括で書かせる（ガイド・ブリーフの読み込みが章1回で済み、章内の用語・題材の一貫性も上がる）。章をまたいで1体にまとめない。章の同時進行は「3. タスクサイクル」末尾のパイプライン規定（最大2章）に従う
- **定型報告は厳密にパースする**: `STATUS:` / `VERDICT:` / `DIAGNOSIS:` 等の定型フィールド行だけを結果として扱い、散文からの推測はしない。フィールドが欠落していたら再要求は1回だけ（それでも欠落なら不合格として扱う）
- **状態はディスク上に置く**: 検収を通った Section をその都度コミットする（コミット済み＝検収済み）。親は累積記憶に依存せず、**各タスク開始時に git log と実ファイルの有無を読み直す**。コンテキスト圧縮・セッション中断が起きても、同じスコープで再実行すれば未完タスクだけが再構成され、そのまま再開になる
- **モデルの分担**: 執筆は `section-writer`（model: opus を定義済み）、検収は `independent-reviewer`・`learner-persona`（セッションのモデルを継承）。書き手と審査員でモデルを分ける

## 0. 事前条件

- `section-write`「1. ゲート検査」を通過している（様式ロック済み・章 Issue に節構成あり）
- 作業ブランチがマイルストーンブランチ（例: `milestone/stage1-design-ai`）であることを確認する

## 1. ランプラン（ユーザー承認は開始時の1回だけ）

1. 章 Issue の節構成からタスクリストを作る（**1 章 = 1 タスク**。章内の節リストをタスクの内訳として持つ）。**完了・未完は git で節単位に判定する**:
   - 節のコミット（メッセージに節番号）が存在する → その節は完了（成果に触れない）。全節コミット済みの章はタスクにしない
   - 実ファイルがあるのに未コミットの節 → **残工程**（執筆をスキップし、「3. タスクサイクル」の機械検証→レビュー→コミットから実施）
   - 実ファイルが無い節 → 新規（章タスクの執筆対象）
   - 完了・残工程・新規の節が混在する章は、コミット済みの節を除いた残りを1つの章タスクとして扱う
   - 既存 Section の一括改稿では全 Section が対象（改稿指示をランプランに明記し、各タスクへ渡す）
2. 章の処理順は章番号順とする（後章は前章の内容を前提にするため）。章をまたぐ同時進行は独立実行ではなく、「3. タスクサイクル」末尾のパイプライン規定（最大2章）に従う
3. **配布物の正準化**: 全タスク共通で渡すパス一式（writing-rules / 種別ガイド / ai-slop-curriculum.md / 章 Issue の節構成 / ブリーフ）と検証コマンド（`python3 .claude/scripts/lint_curriculum.py`）をここで1度だけ確定し、以降の起動テンプレートに使い回す
4. ランプランを提示する: `| 章 | Section | 種別 | タスク種別(新規/改稿/残工程) | quiz要否 |` の表 ＋ ブリーフの単位 ＋ 停止条件
5. 承認を1回得たら、以降は完了報告まで自律で回す（質問しない）。ループを中断するのは診断が STOP を返した場合と、続行不能な環境不備のみ

## 2. ブリーフ（参考資料の整理結果をファイルとして永続化）

参考資料の一括取得・整理を、チャットに揮発させずファイルにする。

- 章ごとに `local/write-briefs/<章ID>.md` へ書く（例: `local/write-briefs/13-1.md`。`local/` は gitignore 済み）
- **作成はランプラン承認後、その章の執筆タスク直前に行う**（JIT）。既存のブリーフがあれば再利用し、再開時に二重生成しない
- **作成はサブエージェントへ委任する**（親が素材を読まないため）。渡すもの: 章 Issue の節構成・マイルストーンの仕様・依頼で指定された参考資料（流用元教材・公式ドキュメント URL 等）・題材にする既習アプリのパス
- 内容: ①Section 横断で統一すべき事実（名前パターン・数値・用語）②Section ごとの使用素材（コード・仕様の verbatim 引用と出典）③教材に書かないこと ④**論点の割り当て表**（下記）
- **④ 論点の割り当て表は必須**。章の節が互いに矛盾する事故（前節が教えたルールと後節の模範解答が食い違う／同じ論点を2節が本説明として持つ／学習目標に対応する成果物が無い／成果物のファイル名が衝突する）は、ここを先に埋めておけば防げる。次の3表を作る:
  - `| 論点・概念 | 本説明を持つ節 | 他節での扱い |` — 本説明は1節だけ。他節は「1文で参照」か「扱わない」
  - `| 節 | 学習目標 | 対応する成果物 |` — 目標に対応する成果物が無い行があれば、その時点で節構成の不備として章 Issue に上げる
  - `| 節 | 作らせる成果物とファイル名 | あえて書かないこと（担当する節） |` — ファイル名の衝突と、後続節のネタバレを同時に潰す
- ブリーフ冒頭に必ず記す: 「このファイルは執筆用の内部資料。**ここに現れる内部用語・記号（出典ラベル・『ブリーフ』等）を本文へ転記しない**」。完了報告には `FORBIDDEN_TERMS:`（本文に出てはいけない内部語の一覧）を含めさせ、親はタスクサイクル手順2の横断 grep の検索語に使う

## 3. タスクサイクル（章 1 件ごとに完結させる）

```text
section-writer（章の全節を一括執筆） → 親の機械検証（節ごと） → independent-reviewer（章1回・節別指摘表）
  →（REJECTED → 修正サブエージェントが一括修正 → 構造級の指摘があればフル再レビュー ×最大2 → なお REJECTED なら診断サブエージェント）
  → コミット（節単位・親が直列） → 1行サマリだけを引き継いで次章へ
```

1. **執筆**: `section-writer` を1体起動し、**章の全節を一括で**書かせる。渡すもの＝正準化したパス一式・章内の節番号と作成先パスの一覧・前後 Section（前章末尾・次章冒頭を含む隣接節）のパス・quiz 要否。節ごとのセルフチェック（lint・節構成整合・コード正確性・種別ガイドのチェックリスト・AI臭＋自己採点）まで**子側で完了**させ、完了報告は**節別に**受ける（FILES_CHANGED・SELF_CHECK・SCORE 等を節ごとに列挙）。種別ガイドが REFERENCES_CONSULTED に無い報告は不合格として差し戻す。残工程の節（実ファイルあり・未コミット）は執筆対象から除き、手順2以降だけを実施する
2. **親の機械検証**（**節ごとに**実施する。自己申告を信用しない。ただし本文は読まない）:
   - `python3 .claude/scripts/lint_curriculum.py <対象ファイル>`（新規ファイルは 🔴🟡 ともゼロでなければ差し戻し）
   - 対象ファイルの存在と規模の確認（`wc -m`。4,000 字を大きく割っていれば CONCERNS と突合）
   - ブリーフ内部語の横断 grep（「ブリーフ」と、ブリーフ子が報告した FORBIDDEN_TERMS が本文へ漏れていないか）
   - quiz の確認（新規 Section の quiz は作成対象外のため、**誤って作られていないこと**を確認する。タスクで quiz 要と指定した改稿の場合のみ存在確認）
3. **独立レビュー**: `independent-reviewer` を**章まとめて1回**起動する（章の全節のパス・章 Issue 番号・種別ガイドのパスを渡し、**節別の指摘表**で返させる）。**1回のレビューで「内容の正誤・構成」「密度（冗長・同一論点の再説明）」「初出スキルの未教授」をまとめて見る**（別々の診断パスに分けると往復が倍になる）。REJECTED の場合は、節別の REMEDIATION を**新しい修正サブエージェント**（section-writer）1体にまとめて渡して**一括修正**させる。再レビューは指摘の級で分ける:
   - **構造級**（説明の運び・節構成レベル）の指摘が1件でもあった場合 → 修正後に**フル再レビュー**する（章1回・節別指摘表。最大2回）。**密度の指摘で大きく削った場合は、再レビューで「削減による指示語の迷子・接続の断絶・理由の消失」を検査させる**
   - **軽微**（文言・表記）のみの場合 → 一括修正後に、lint ＋**変更差分の確認**（修正の FILES_CHANGED・差分と指摘箇所の突合）で通す。フル再レビューは行わない
4. **診断（3回目も REJECTED、または子が BLOCKED / NEEDS_CONTEXT を返したとき）**: **失敗履歴を渡さない**新しい診断サブエージェントを起動し、正準化したパス一式・最新の指摘・対象の節のファイル・章 Issue の該当節を渡して根本原因を分類させる。報告は定型で受ける: `DIAGNOSIS: RETRY | BLOCK | STOP`・`ROOT_CAUSE:`・`FIX_PLAN:`（RETRY のときのみ）
   - `RETRY`（原因が特定でき、修正方針が具体的）→ FIX_PLAN を新しい修正サブエージェントに渡して**1回だけ**再走 → 再レビュー。なお REJECTED なら BLOCK 扱いに落とす
   - `BLOCK`（原因が節単体で解決しない: 節構成の設計不備・参考資料の不足）→ **該当の節を保留**にする（章内の他の節は続行する）。設計不備は章 Issue へのコメントとして残し、完了報告に含める
   - `STOP`（教材横断の問題・ユーザー判断が必要）→ ループを中断してエスカレーション
5. **コミット**: lint クリアと検収通過（レビュー APPROVED、または軽微指摘の一括修正＋差分確認）を親が確認してから、**節単位のまま親が直列に**コミットする（`{節番号}: {要約}`＋`Refs #{章Issue}`。**stage するのは対象 Section・quiz の明示パスのみ**。`git add -A` は使わない。ブリーフ・一時ファイルは含めない）。保留にした節は**書きかけの稿をコミットせず**、未コミットパスとして完了報告に明示する。子が報告した横断的決定（CONCERNS 内の用語・題材の決定）はガイドの該当箇所へ反映するか、章 Issue にコメントする（後続章の子はそこから読む＝学習の伝搬）

**パイプライン**: 章のレビュー・修正待ちの間に、**次章のブリーフ作成・執筆を開始してよい**（同時進行は最大2章）。機械検証・レビュー・コミットは章ごとに独立して完結させ、コミットは親が直列に行う。用語・題材などの横断的決定は、ブリーフと章 Issue コメントで後続章へ伝搬する（先行着手済みの次章に影響する決定が出た場合は、修正タスクとして次章の子に渡す）。保留（BLOCK）の節に依存する後続の節・章は着手せず、依存しないものは続行する。

## 4. 完走処理（章 Issue 単位）

- **学習者通読**: `learner-persona` に章全体を通読させる（既習範囲を指定。例: T13 Ch3 なら「T1〜T12 と 13-1〜13-2 既習」）。「読み進められない」級の指摘は修正サブエージェントで解消してから完了とする
- **章 Issue への記帳**: 進捗コメント（`| Section | 執筆 | レビュー判定 | 修正回数 | commit |` の表 ＋ 保留・設計不備の差し戻し事項 ＋ learner-persona の要約）を残し、本文の完了条件チェックボックスを更新する。**Issue はクローズしない**（最終 PR の Closes で閉じる）
- 完了報告には生成したブリーフのパス・未コミットの書きかけ稿のパスも含める
- **完了主張は証拠の範囲まで**: 「全タスク APPROVED」と言えるのは、親が lint とレビュー判定を実際に確認したタスクだけ。サブエージェントの成功報告そのものは証拠にしない
- **再開**: 中断後に同じスコープで `section-write` を再実行すれば、「1. ランプラン」手順1のタスクリスト構成が git log と実ファイルから未完の章タスク（新規・残工程の節）だけを拾い、続きから回る（コミット済みの節の成果には触れない）
