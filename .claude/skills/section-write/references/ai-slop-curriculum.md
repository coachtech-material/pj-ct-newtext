# AI 臭チェック（教材版）

教材の文章から「AI が書いた感じ」を取り除くためのチェック基準。`section-writer` のセルフチェック最終手順と `independent-reviewer` の文体観点で使う。

> 出典: [stop-ai-slop-jp](https://github.com/iKora128/stop-ai-slop-jp)（Daichi Nagashima, MIT License, hardikpandya/stop-slop 日本語派生）を教材の文体（敬体・断定・再現性重視）に合わせて再構成したサブセット。原典はブログ・note 向けの規範を含むため、そのままでは使わない。
> 追補: [あなたの技術ブログの「AI臭さ」を抜くスキル公開します](https://qiita.com/minorun365/items/699e89544da8b0de300d)（minorun365, Qiita, 2026-07）から、段落頭の接続詞連打・均等な網羅列挙・動詞の演出的な言い換え・動作主の消えた受動態を取り込み。同記事のブログ向け規範（常体化・体言止めの推奨・大胆な比喩・まとめ / 目次の削除・主観の推奨・箇条書きの一律上限）は教材のテンプレート・トーンと衝突するため採らない。

## 適用範囲（先に読む）

**教材本文に適用しないルール**（原典にあるが教材と正面衝突するもの）:

- 中間温度を混ぜる（「まあまあ」「微妙」）→ 教材は判断を明確に示す
- 伝聞を残す（「らしい」「ようだ」）→ 教材は裏取りした事実を断定で書く
- 毒・自虐・皮肉を許す → 教材には持ち込まない
- 一人称「自分は」で書く → 本文は「あなた」「私たち」を用いる
- 文末の意図的なムラ → 本文は敬体で統一する（`guides/writing-rules.md`）

**機械チェックに委譲済み**（ここで重複チェックしない）: ダッシュ記号・壊れる太字・言語なしコードブロック・imgタグの書式・フェーズ定型文の正本一致は `.claude/scripts/lint_curriculum.py` が検出する。

**定型ブロックは適用除外**: ガイドが要求する定型（🎯 学ぶこと・✨/🚀 まとめ・📌 導入・📋 要件・✅ チェックリスト・✏️ タスク・🧠 先輩エンジニアの思考プロセス・📖 模範解答/進行例の冒頭定型文・`> 🔥` フェーズ定型文・quiz の枠）は、「リズムの均一さ」「同じ型の反復」系チェックの指摘対象にしない。定型の**中身**の言い回しが毎回同一文になっている場合のみ指摘する。

## 1. 構造のチェック

- [ ] **命題型見出し**がないか。見出しは名詞句・動詞句（「〇〇は△△だ」型・断定文の見出しは各節を演説にする）
- [ ] **「A ではなく B」の二項対比**を 1 Section に 3 回以上使っていないか。多くは「B です」と直接書ける
- [ ] **機械的な3項目並列**がないか（「3つのポイント」を作るために項目をでっち上げていないか。2つ・4つに崩せるなら崩す）
- [ ] **均等な網羅列挙**になっていないか（漏れなく列挙して長大な箇条書きにしない。本文で実際に使う・つまずくものだけに絞る。手順・✅ チェックリスト等の定型は対象外）
- [ ] **全段落が同じ長さ・同じ型**で着地していないか（「〜が重要です」「〜しましょう」の反復締め）
- [ ] **段落頭の接続詞連打**がないか（「さらに」「加えて」「また」「一方で」で段落を始め続けない。前の文から流れで繋がるなら接続詞ごと削る）
- [ ] **決めつけ→反転の序文**（「〜と思っていませんか？実は…」）を使っていないか
- [ ] **儀式的な締め**がないか。各見出しの末尾に毎回まとめ文・移行アナウンス（「それでは次に見ていきましょう」）を置かない
- [ ] **絵文字の装飾使用**がないか。絵文字は `guides/writing-rules.md` の表が定義する機能マーカー（見出し・コールアウト）限定で、箇条書きのビュレット代用・本文中の散布・✅❌の対比乱用をしない
- [ ] **「ラベル + コロン」の機械的列挙**になっていないか。太字の有無を問わず、すべての箇条書きを「語: 説明」型で並べない（ガイドが定義する定型ラベルは対象外）

## 2. 語彙のチェック

- [ ] **ハイプ表現**: 革命的・劇的に・完全に解決・究極の・魔法のように → 効果は事実と数値で（「！」の連打で勢いを演出しない）
- [ ] **AI 偏愛語の多用**: 本質・解像度・営み・文脈・手触り・示唆 → 1 Section に同じ抽象語を撒かない
- [ ] **翻訳調動詞**: 「〜を物語っている」「〜を示唆している」「〜に収斂する」→ 「〜ということです」「〜を意味します」等の平易な形に
- [ ] **横文字メタファー**: 思考の OS・習慣をインストール・脳内をリファクタリング → 普通の日本語に戻す（比喩は writing-rules の「身近で実用的な比喩」の範囲で）
- [ ] **動詞の演出的な言い換え**: 使う→「活用する」、紹介する→「回る」、学ぶ→「旅する」 → 行為はそのままの動詞で書く（説明する・作る・確認する）
- [ ] **冗長表現**: 〜することができます→〜できます / 〜を行います→〜します / 〜という形になります→〜になります
- [ ] **咳払い前置き**: 「率直に言うと」「結論から言うと」「重要なのは」の乱発 → 削って本題から書く

## 3. 立場のチェック

- [ ] **両論併記で判断を放棄**していないか。「〇〇もあり、△△もあります」で終えず、本教材としての推奨と理由を明示する（選ばせる場合は判断基準を示す）
- [ ] **「ケースバイケース」「場合による」で結論を回避**していないか
- [ ] **過剰ヘッジ**: 「〜かもしれません」「〜と言えるでしょう」の連発 → 裏取りした内容は言い切る
- [ ] **擬人化ドラマ**: 「コードが物語る」「アーキテクチャが呼吸する」のような文学的擬人化 → 技術的な主語の記述（「このメソッドは〜を返します」）は正当なので混同しない
- [ ] **動作主の消えた受動態**で操作を説明していないか。「設定されます」「作成されます」では、学習者が手を動かすのか・ツールが自動でやるのかが分からない → 「あなたが〜します」「○○が自動で〜します」と動作主を書く（結果の観察「画面に〜が表示される」は正当なので混同しない）
- [ ] **根拠の消去**: 「〜と考えられています」「〜とされています」で出典を曖昧にしない。出典があるなら明記、教材としての推奨なら「本教材では〜を推奨します」と引き受ける

## 4. 採点（総合判定に使う）

各軸 1〜10 点。合計 35/50 未満はその Section を書き直す（`section-writer` のセルフチェック手順）。

| 軸 | 質問 |
|---|---|
| 説明の必然性 | Why（これがないと何が困るか）が立っているか。機能紹介の羅列になっていないか |
| リズム | 見出し・段落の配置が単調でないか（全節同型の反復になっていないか。ガイドの定型骨格は除く） |
| 主体の明確さ | 誰が・何が・何をするのかが追えるか（擬人化ドラマ・根拠の消去・動作主の消えた受動態がないか） |
| 具体性 | 抽象語で終わらず、コード・コマンド・実例に降りているか |
| 削減 | 削れる段落・言い換えの重複がないか |

## 修正例（教材文体での対比）

**例1: ハイプ＋対比の乱用**

- ❌「従来の手作業は限界です。マイグレーションは単なるツールではなく、チーム開発を革命的に変える本質的な仕組みです。」
- ✅「マイグレーションを使うと、テーブル定義の変更がコードとして履歴に残り、チーム全員が同じ手順で同じスキーマを再現できます。」

**例2: 命題型見出し＋機械的並列**

- ❌「## マイグレーションが開発を変える」「メリットは3つあります: 再現性、共有性、安全性。」
- ✅「## マイグレーションの仕組み（up / down）」＋ メリットは本文の流れで必要な数だけ述べる

**例3: 儀式的な締め＋判断放棄**

- ❌「いかがでしたか。ORM にも SQL にもそれぞれ良さがあります。状況に応じて使い分けましょう。」
- ✅「本教材では、定型的な CRUD は ORM、集計を伴う参照系は生 SQL と使い分けます。理由は〜」

**例4: 動作主の消えた受動態**

- ❌「マイグレーションが実行され、テーブルが作成されます。」（学習者が打つのか、自動で起きるのか分からない）
- ✅「あなたが `sail artisan migrate` を打つと、Laravel がテーブルを作成します。」
