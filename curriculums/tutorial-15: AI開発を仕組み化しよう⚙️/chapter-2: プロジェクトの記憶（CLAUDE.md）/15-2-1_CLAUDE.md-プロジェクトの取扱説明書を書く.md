# 15-2-1: CLAUDE.md - プロジェクトの取扱説明書を書く

## 🎯 このセクションで学ぶこと

- 毎回打っていた前提を、1枚のファイルに移せるようになる。
- そのファイルに何を書き、何を書かないかを判断できるようになる。
- `/init` で叩き台を作り、中身を読んで自分の手で削れるようになる。

## 毎回説明していたことを、1枚に置く

`CLAUDE.md`（このプロジェクトの前提を書いておく、AIが毎回読むファイル）を、アプリのフォルダに1枚置きます。公式ドキュメントの説明では、Claude Codeは各セッションの開始時にこのファイルを読みます。あなたが「読んでください」と頼まなくても、`@` で指さなくても読まれます。

15-1-1「毎回手でやっていたこと」で、同じ前提を毎回説明しているものの行き先を、このファイルに決めました。やるのは、毎回打っていた数行をここへ移すことだけです。次のセッションからは、打たずに済みます。

新しく入った人に渡す、機械の取扱説明書のようなものだと考えてください。電源の入れ方、押してはいけないボタン、変な音がしたときに見るところ。毎回口で説明する代わりに、機械の横に1枚貼っておきます。

14-2-2「コンテキストは有限」で使った `/compact` とも噛み合います。公式ドキュメントの説明では、`/compact` を打ったあと、Claude Codeはこのファイルをディスクから読み直します。要約のときに前提が薄まっても、このファイルに書いた分は戻ってきます。

## 置き場所は1つだけ

| 気をつけること | 中身 |
|:--|:--|
| 置く場所 | アプリのフォルダのいちばん上です。`app/` や `docs/` の中に置くと、**何も言われないまま効きません** |
| ファイル名 | `CLAUDE.md` です。すべて大文字で、拡張子は `.md` です |
| 起動したフォルダ | 必ずアプリのフォルダに `cd` してから `claude` を起動します（14-1-1でやったのと同じです） |

置き場所を図にすると、こうなります。

```text
post-app-practice/
├── CLAUDE.md      ← ここに置く
├── app/
├── docs/
│   ├── comment.md
│   ├── draft.md
│   └── structure.md
├── routes/
└── tests/
```

いちばん多いのは、`docs/` の中に入れてしまう形です。設計書と同じ仲間に見えるので、つい入れたくなります。この1枚だけは外に出しておいてください。

## 何を書いて、何を書かないか

置き場所が決まったら、次は中身です。分かれ目は2つです。**コードを開けば分かることか**。そして、**来週も本当のままか**です。1つ目は、14-2-2で1回の依頼に何を渡すかを決めたときと同じ物差しです。

| 書くもの | 書かないもの |
|:--|:--|
| コードを読んでも分からないコマンド（`./vendor/bin/sail` を頭に付ける、など） | コードを読めば分かること（フォルダの一覧・テーブルのカラム・モデルの一覧） |
| ふつうと違う書き方の決めごと（画面に出すエラーメッセージは日本語にする、など） | Laravelを知っていれば分かる一般的な作法 |
| テストの回し方と、結果の見せ方 | 設計書に書いてあることの写し（代わりに「`docs/comment.md` を読んで」と1行だけ書く） |
| 触ってほしくないもの | いまだけの話（「移行作業中です」「これから作ります」） |
| このアプリだけの落とし穴（`php artisan` では動かない、など） | 「きれいなコードを書いてください」のような、当たり前のお願い |

右の列を書きたくなる気持ちは分かります。丁寧に書いたほうが伝わりそうに見えるからです。ただ、モデルの一覧は `app/Models/` を開けば書いてあります。書き写した分は、モデルが増えた日から嘘になります。

左の列は逆です。`./vendor/bin/sail` を頭に付けるという決まりは、コードのどこを探しても書いてありません。あなたがTutorial 9で環境を作ったときの事情です。こういうものだけが、ここに書く価値のある行です。

---

## 曖昧な書き方を、確かめられる書き方に直す

書く中身が決まっても、書き方で効き目が変わります。左のように書いていたものを、右のように直します。

| こう書くと伝わらない | こう書けば伝わる |
|:--|:--|
| きれいなコードを書いてください | 入力チェックはコントローラーの `validate()` に書き、設計書の入力チェック表と同じ内容にしてください |
| ちゃんとテストしてください | 変更が終わったら `./vendor/bin/sail artisan test` を実行し、その出力を貼ってください |
| ファイルは整理してください | 機能テストは `tests/Feature/` に置き、テストメソッド名は `test_` で始めてください |
| セキュリティに気をつけてください | `.env` は読まないでください。値が要るときは私に聞いてください |

右の列に共通しているのは1つだけです。**そのとおりにできたかを、後から確かめられる**形になっています。

「きれいなコードを書いてください」と書いた場合、書けたかどうかを誰も判定できません。判定できないなら、守られたかどうかも分かりません。「テストメソッド名は `test_` で始めてください」なら、ファイルを開けば1秒で分かります。

14-2-1「前提を渡し、作り方は任せる」でやったことと同じです。違うのは、あのときは1回の依頼に書いていたものを、今回は毎回効くファイルに書く、という点です。

---

## 書いてあっても、必ず守られるわけではない

公式ドキュメントには、このファイルに書いたことは判断の材料として渡されるだけで、強制的な設定ではない、と明記されています。書けば必ずそのとおりになる保証はありません。書いてあるのに `php artisan` で打とうとすることは、実際に起こります。

そのうえで、公式ドキュメントはこうも書いています。具体的で短い指示ほど、そのとおりに従われやすくなります。さきほどの右の列が、まさにその形です。

とはいえ、上がるのは確率です。ですから、**絶対に起きてほしくないこと**は、このファイルに書くだけで済ませません。`.env` を読ませないことは、お願いではなく、機械の側で止めるものです。14-1-3「モードと権限」で `.claude/settings.json` に書いた `deny` が、その形でした。この使い分けはChapter 4で扱います。ここに書くのは、**そうしてほしい決めごと**です。

## 🏃 /init で叩き台を作る

`CLAUDE.md` はただのテキストファイルなので、1から自分で書けます。ただ、白紙から書き始めると手が止まります。Claude Codeには、いまのコードを読んで叩き台を書く `/init` というコマンドがあるので、まずこれを使います。

出てきたものは、そのままでは使いません。読んで、削って、コミットするところまでが、この実践です。

### Step 1: 打つ前に、手元をきれいにしておく

`/init` は新しいファイルを作ります。気に入らなければ捨てて戻せるように、先にコミットを済ませておきます。

```bash
# アプリのフォルダへ移動して、記録していない変更が無いかを見る
cd ~/laravel-practice/post-app-practice
git status
```

Tutorial 14の最後にすべてコミットしてpushしているので、変更は残っていないはずです。自分が触ったファイルが出てきた場合は、先にコミットしておいてください。

### Step 2: `/init` と打つ

Claude Codeを起動して、入力欄に1行打ちます。

```bash
# アプリのフォルダの中で実行する
claude
```

```text
/init
```

打つのは、この1回だけです。すでに `CLAUDE.md` がある状態で打ち直すと、自分が書いた文も書き換えの対象になります。あとから足したくなったときは、自分の手でファイルを開いて書きます。

`/init` は、いまのコードを読んで回ります。ルート、コントローラー、モデル、テスト、設定ファイルと開いていくので、少し時間がかかります。

### Step 3: 途中で止まったら、1行打って続けさせる

読んで回る途中で、`.env` を開こうとすることがあります。14-1-3で `.claude/settings.json` に書いた `deny` があるので、そこは機械が止めます。

止まったところで `/init` そのものが終わってしまうことがあります。`CLAUDE.md` が作られないまま止まったら、続けて次の1行を打ちます。

```text
.env は読まずに続けてください。
```

> 💡 **TIP**: 毎回止まるわけではありません。止まらずに最後まで進んだときは、この1行は要りません。

それでも `CLAUDE.md` が作られないまま終わったときは、もう一度 `/init` を打って構いません。まだファイルが無いので、書き換えは起きません。

### Step 4: 全文を読んで、3種類だけ削る

できあがった `CLAUDE.md` をVS Codeで開き、上から最後まで読みます。長いので飛ばしたくなりますが、何を削るかを決めるのはあなたです。

`/init` が書くのは、いまのコードを見た結果です。ですから、次の3種類が混ざります。この3つだけを削ります。

| 削るもの | どうするか |
|:--|:--|
| 打ったことのないコマンド | Tutorial 14で一度も打っていないコマンドが並んでいたら、その行を消します |
| 教材で使ってきた形と違うコマンド | テストのコマンドが `./vendor/bin/sail artisan test` になっていなければ、この形に直します |
| いまだけの話 | 「いまここが足りない」「これから直す」のような、その時点の状態が書かれていたら、消します |

3種類とも書かれていないことがあります。無ければ、そのまま次へ進んでください。

最初の2行（`# CLAUDE.md` と、その下の説明文）はそのままで構いません。見出しが英語のままなのが気になるなら、日本語に書き換えても構いません。

削るのはこの3種類だけにしてください。残りをどう整えるかは、15-2-2で刈り方を覚えてから、15-2-3で仕上げます。

### Step 5: コミットする

削り終えたら記録します。

```text
CLAUDE.md をコミットして、main に push してください。
```

この1枚は、コードと同じくプロジェクトの一部です。だから一緒に記録します。効く相手は、次に起動したときの自分と、来月このアプリに戻ってきた自分です。

このコミットは、どの機能イシューにも属していません。だからメッセージにイシューの番号を入れていません。14-5-2で設計のメモを記録したときと同じで、ブランチも切らず `main` のまま進めます。

ここまでで、次の3つを確かめてください。

- [ ] `CLAUDE.md` がアプリのフォルダのいちばん上にある
- [ ] 打ったことのないコマンド・違う形のコマンド・いまだけの話が残っていない
- [ ] GitHubでリポジトリのページを開いて、`CLAUDE.md` が表示されている

## 💡 よくある間違い

**`/init` を何度も打ち直す**

思ったものが出てこないと、もう一度打ちたくなります。ただ、打ち直すと自分が書いた文も書き換えの対象になります。あとから足すときは、ファイルを開いて書きます。

**フォルダの中に置いてしまう**

`app/` や `docs/` の中に置いても、エラーは出ません。**何も言われないまま効きません**。置き場所はアプリのフォルダのいちばん上です。

**生成されたものを読まずに全部残す**

`/init` が書くのは、いまのコードを見た結果です。自分が打ったことのないコマンドや、その時点の状態が混ざります。読まずに残すと、その嘘を毎回読ませることになります。

## ✨ まとめ

- セッションは毎回まっさらなところから始まります。前提を書いた1枚を置いておくと、Claude Codeがセッションの始めに読みます。
- 置き場所はアプリのフォルダのいちばん上、ファイル名は `CLAUDE.md` です。フォルダの中に入れると、起動したときに読まれません。
- 書くのは、コードを読んでも分からないことだけです。フォルダの一覧やモデルの一覧は、コードを開けば書いてあります。
- 書き方は、後から確かめられる形にします。「きれいなコードを書いてください」は、守られたかどうかを誰も判定できません。
- ここに書くのは、そうしてほしい決めごとです。必ず止めたいものは、お願いとは別のやり方で守ります。
