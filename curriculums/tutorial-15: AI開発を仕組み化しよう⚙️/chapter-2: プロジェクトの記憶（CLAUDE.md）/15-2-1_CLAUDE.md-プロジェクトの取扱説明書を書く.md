# 15-2-1: CLAUDE.md - プロジェクトの取扱説明書を書く

## 🎯 このセクションで学ぶこと

- プロジェクトの前提を書いておくファイルが、なぜ要るのかを説明できるようになる。
- そのファイルに何を書き、何を書かないかを判断できるようになる。
- `/init` で叩き台を作り、中身を読んで自分の手で削れるようになる。

---

## 導入：昨日通じた話が、今日は通じない

前の章では、どうなったら何に固めるかを決めました。手元にはまだ何も増えていません。この章で増えるのは、アプリのフォルダに置く1枚のファイルだけです。

14-1-2「Claude Codeのセットアップと基本操作」で、起動してから終えるまでのひとつづきのやり取りをセッションと呼ぶ、と確かめました。そこで一緒に確かめたことが、もう1つあります。セッションを終えると、そのやり取りは残りません。次に起動したときは、また何も知らないところから始まります。

これは、あなたの環境の問題ではありません。Claude Code の作りとしてそうなっています。公式ドキュメントにも、セッションは毎回まっさらなところから始まる、と書かれています。昨日3回説明したことは、今日の1回目には残っていません。

Tutorial 14 で、こんな行を何度も打ちませんでしたか。

```text
テストは ./vendor/bin/sail artisan test で回してください。
php artisan では動きません。Docker の中で動いているアプリです。
マイグレーションも ./vendor/bin/sail artisan migrate の形で実行してください。
```

打った回数を数えると、けっこうな数になるはずです。しかもこれは、考えて書いた文ではありません。毎回同じことを、思い出しながら打ち直していただけです。

## 毎回説明していたことを、1枚に置く

14-5-2「振り返りと設計書の寿命」の最後に、毎回手でやっていたことを4つ挙げました。その1つ目が、このアプリの前提を依頼のたびに説明し直すことでした。15-1-3「使い終える書類と、育てる道具」の対応表でも、同じ間違いを2回された、同じ前提を毎回説明している、の2行が同じ行き先を指していました。その行き先が、ここで作るファイルです。

`CLAUDE.md`（このプロジェクトの前提を書いておく、AIが毎回読むファイル）を、アプリのフォルダに1枚置きます。公式ドキュメントの説明では、Claude Code は各セッションの開始時にこのファイルを読みます。あなたが「読んでください」と頼まなくても、`@` で指さなくても読まれます。

やることは、それだけです。毎回打っていた前提の数行を、このファイルに移しておきます。次のセッションからは、打たなくて済みます。

新しく入った人に渡す、機械の取扱説明書のようなものだと考えてください。電源の入れ方、押してはいけないボタン、変な音がしたときの見るところ。毎回口で説明する代わりに、機械の横に1枚貼っておきます。

14-2-2「コンテキストは資源」で、話を続けたまま机を空ける `/compact` を学びました。公式ドキュメントの説明では、`/compact` を打ったあと、Claude Code はこのファイルをディスクから読み直します。要約のときに前提が薄まっても、このファイルに書いた分は戻ってきます。

## 置き場所は1つだけ

次の3つだけ、正確に押さえてください。

| 気をつけること | 中身 |
|:--|:--|
| 置く場所 | アプリのフォルダのいちばん上です。`app/` や `docs/` の中に置くと、**何も言われないまま効きません** |
| ファイル名 | `CLAUDE.md` です。すべて大文字で、拡張子は `.md` です |
| 起動したフォルダ | 必ずアプリのフォルダに `cd` してから `claude` を起動します（14-1-3 でやったのと同じです） |

置き場所を図にすると、こうなります。

```text
authorization-app-ai/
├── CLAUDE.md      ← ここに置く
├── app/
├── docs/
├── routes/
└── tests/
```

いちばん多いのは、`docs/` の中に置いてしまう形です。設計書と同じ仲間に見えるので、つい入れたくなります。ですが、この1枚だけは外に出しておいてください。

## 何を書いて、何を書かないか

置き場所が決まったら、次は中身です。分かれ目は2つあります。**コードを開けば分かることか**。そして、**来週も本当のままかどうか**です。

| 書くもの | 書かないもの |
|:--|:--|
| コードを読んでも分からないコマンド（`./vendor/bin/sail` を頭に付ける、など） | コードを読めば分かること（フォルダの一覧・テーブルのカラム・モデルの一覧） |
| ふつうと違う書き方の決めごと（画面に出すエラーメッセージは日本語にする、など） | Laravel を知っていれば分かる一般的な作法 |
| テストの回し方と、結果の見せ方 | 設計書に書いてあることの写し（代わりに「`docs/comment/` を読んで」と1行だけ書く） |
| 触ってほしくないもの | いまだけの話（「移行作業中です」「これから作ります」） |
| このアプリだけの落とし穴（`php artisan` では動かない、など） | 「きれいなコードを書いてください」のような、当たり前のお願い |

右の列を書いてしまう気持ちは分かります。丁寧に書いたほうが伝わりそうに見えるからです。ですが、モデルの一覧は `app/Models/` を開けば書いてあります。書き写した分は、モデルが増えた日から嘘になります。

左の列は逆です。`./vendor/bin/sail` を頭に付けるという決まりは、コードのどこを探しても書いてありません。あなたが Tutorial 9 で環境を作ったときの事情です。こういうものだけが、ここに書く価値のある行です。

---

## 曖昧な書き方を、確かめられる書き方に直す

書く中身が決まっても、書き方で効き目が変わります。左のように書いていたものを、右のように直します。

| こう書くと伝わらない | こう書けば伝わる |
|:--|:--|
| きれいなコードを書いてください | 入力チェックはコントローラーの `validate()` に書き、`docs/` の入力チェック表と同じ内容にしてください |
| ちゃんとテストしてください | 変更が終わったら `./vendor/bin/sail artisan test` を実行し、その出力を見せてください |
| ファイルは整理してください | 機能テストは `tests/Feature/` に置き、テストメソッド名は `test_` で始めてください |
| セキュリティに気をつけてください | `.env` は読まないでください。値が要るときは私に聞いてください |

右の列に共通しているのは、1つだけです。**そのとおりにできたかを、後から確かめられる**形になっていることです。

「きれいなコードを書いてください」と書いた場合、書けたかどうかを誰も判定できません。判定できないということは、守られたかどうかも分かりません。一方で「テストメソッド名は `test_` で始めてください」なら、ファイルを開けば1秒で分かります。

これは 14-2-1「指示は仕様書 - 具体的に頼む」でやったことと同じです。違うのは、あのときは1回の依頼に書いていたものを、今回は毎回効くファイルに書く、という点だけです。

---

## 書いてあっても、必ず守られるわけではない

公式ドキュメントには、このファイルに書いたことは判断の材料として渡されるだけで、強制的な設定ではない、と明記されています。書けば必ずそのとおりになる、という保証はありません。書いてあるのに `php artisan` で打とうとすることは、実際に起こります。

そのうえで、公式ドキュメントはこうも書いています。具体的で短い指示ほど、そのとおりに従われやすくなります。さきほどの右の列が、まさにその形です。

とはいえ、確率が上がるだけです。ですから、**絶対に起きてほしくないこと**は、このファイルに書くだけで済ませてはいけません。たとえば `.env` を読ませないことは、お願いではなく、機械の側で止めるべきものです。その止め方は、後の章で扱います。このファイルに書くのは、**そうしてほしい決めごと**です。

## 🏃 /init で叩き台を作る

> 🔥 ここからは、AIに実装を任せて構いません。ただし「任せる」と「丸投げ」は違います。何を作るかは設計書で自分が決め、出てきたものはテスト・動作確認・コードレビューで自分が検証します。品質の責任は、AIではなくあなたが握ります。

`CLAUDE.md` は、テキストファイルなので1から自分で書けます。ですが、白紙から書き始めると手が止まります。Claude Code には、いまのコードを読んで叩き台を書く `/init` というコマンドがあるので、まずこれを使います。

出てきたものをそのまま使うのではありません。読んで、削って、コミットするところまでが、この実践です。

### Step 1: 打つ前に、いまの状態を記録しておく

`/init` は新しいファイルを作ります。気に入らなければ捨てて戻せるように、先に手元をきれいにしておきます。

```bash
# アプリのフォルダの中で実行する
cd ~/laravel-practice/14_hands-on/authorization-app-ai
git status
```

Tutorial 14 の最後にすべてコミットして push しているので、変更は残っていないはずです。ここで見慣れない画像ファイルの名前が出てきても、そのままで構いません。14-2-3 で手元にコピーしたもので、記録していないためです。

ほかに自分が触ったファイルが出てきた場合は、先にコミットしておいてください。

### Step 2: /init と打つ

Claude Code を起動します。

```bash
# アプリのフォルダの中で実行する
claude
```

入力欄に、次の1行を打ちます。

```text
/init
```

打つのは、この1回だけです。すでに `CLAUDE.md` がある状態で打ち直すと、自分が書いた文も書き換えの対象になります。あとから足したくなったときは、自分の手でファイルを開いて書きます。

### Step 3: 承認を読んで進める

`/init` は、いまのコードを読んで回ります。その途中で、承認を何度か求められます。

> ⚠️ **注意**: ここから先の画面の説明は、2026年8月時点のものです。表示が違っても、読んでから許可するという判断は変わりません。

たとえば、こういう画面が出ます。

```text
 Bash command
   ls -a ~/.codex/ ./.codex/ ~/.gemini/ ./.gemini/ 2>/dev/null;
   ls ./GEMINI.md ./.cursorrules ./.cursor ./.github/copilot-instructions.md 2>/dev/null

   Check foreign agent configs

 Do you want to proceed?
 ❯ 1. Yes
   2. Yes, allow reading from .codex/ from this project
   3. No
```

ほかのAI向けの設定ファイルが置かれていないかを見に行っています。無ければ何も起きません。ここは許可して構いません。

このとき、次の2つに気をつけてください。

**1. 「今後は聞かない」にあたる選択肢を選ばない**

承認の選択肢に「今後は聞かない」が混ざる回があります。ここでは選ばず、1回だけの許可を選びます。14-1-4「ガードレール - 機密情報と権限の承認」で決めた作法のままです。押してしまった許可の取り消し方は、後の章で扱います。

**2. `.env` を読む承認は断る**

`/init` の途中で、`.env` を読む承認を求められることがあります。毎回出るわけではありません。求められたときは、承認画面に `.env` という文字が入っていないかを見て、入っていたら「許可しない」を選びます。

断ると、そこで `/init` が止まってしまうことがあります。止まったら、続けて次の1行を打ちます。

```text
.env は読まずに続けてください。
```

14-1-4 で、何を読ませるかは自分が決める、と決めました。`/init` が求めてきても、そこは変わりません。

それでも `CLAUDE.md` が作られないまま終わってしまったときは、もう一度 `/init` を打って構いません。まだファイルが無いので、書き換えは起きません。

### Step 4: 作られる前に、全文を読む

読み終えると、Claude Code は `CLAUDE.md` を作ろうとします。このとき、これから書き込む中身の全文が、行番号つきで画面に出ます。

ここは 14-3-4「差分をレビューする - 承認ゲート」でやったことと同じです。**読んでから**「はい」を選びます。長いので飛ばしたくなりますが、次の Step でどれを削るかを決めるのは、あなたです。

「このセッションの編集をすべて許可する」にあたる選択肢は選ばないでください。

### Step 5: 3種類だけ削る

作られたファイルを VS Code で開きます。`/init` が書くのは、いまのコードを見た結果です。ですから、次の3種類が混ざります。この3つだけを削ります。

| 削るもの | どうするか |
|:--|:--|
| 打ったことのないコマンド | Tutorial 14 で一度も打っていないコマンドが並んでいたら、その行を消します |
| 教材で使ってきた形と違うコマンド | テストのコマンドが `./vendor/bin/sail artisan test` になっていなければ、この形に直します |
| いまだけの話 | 「いまここが足りない」「これから直す」のような、その時点の状態が書かれていたら、消します |

3つとも、書かれていないことがあります。無ければ、そのまま次へ進んでください。

最初の2行（`# CLAUDE.md` と、その下の説明文）は、そのままで構いません。見出しが英語のままなのが気になるなら、日本語に書き換えても構いません。

削るのはこの3種類だけにしてください。残りをどう整えるかは、次の 15-2-2 で刈り方を覚えてから、15-2-3 で仕上げます。

### Step 6: コミットする

削り終えたら、記録します。`/exit` で Claude Code を抜けてから、ターミナルで打ちます（14-3-3 でやったのと同じです）。

```bash
# アプリのフォルダの中で実行する
git add CLAUDE.md
git commit -m "Add CLAUDE.md"
git push origin main
```

この1枚は、コードと同じくらいプロジェクトの一部です。だから一緒に記録します。次に起動したときの自分と、来月このアプリに戻ってきた自分に、そのまま効きます。

このコミットは、どの機能イシューにも属していません。ですからメッセージにイシューの番号を入れていません。14-5-2 で設計のメモを記録したときと同じ形です。ブランチも切らず、`main` のまま進めます。

ここまでで、次の3つを確かめられれば大丈夫です。

- [ ] `CLAUDE.md` がアプリのフォルダのいちばん上にある
- [ ] 打ったことのないコマンド・違う形のコマンド・いまだけの話が残っていない
- [ ] GitHub でリポジトリのページを開いて、`CLAUDE.md` が表示されている

## 💡 よくある間違い

**`/init` を何度も打ち直す**

思ったものが出てこないと、もう一度打ちたくなります。ですが打ち直すと、自分が書いた文も書き換えの対象になります。育てるのは自分の手です。

**フォルダの中に置いてしまう**

`app/` や `docs/` の中に置いても、エラーは出ません。**何も言われないまま効きません**。置き場所はアプリのフォルダのいちばん上です。

**生成されたものを読まずに全部残す**

`/init` が書くのは、いまのコードを見た結果です。自分が打ったことのないコマンドや、その時点の状態が混ざります。読まずに残すと、その嘘を毎回読ませることになります。

## ✨ まとめ

- セッションは毎回まっさらなところから始まります。前提を書いた1枚を置いておくと、Claude Code がセッションの始めに読みます。
- 置き場所はアプリのフォルダのいちばん上、ファイル名は `CLAUDE.md` です。フォルダの中に入れると、起動したときに読まれません。
- 書くのは、コードを読んでも分からないことだけです。フォルダの一覧やモデルの一覧は、コードを開けば書いてあります。
- 書き方は、後から確かめられる形にします。「きれいなコードを書いてください」は、守られたかどうかを誰も判定できません。
- ここに書くのは、そうしてほしい決めごとです。必ず止めたいものは、お願いではない別のやり方で守ります。

`/init` が作った叩き台は、まだ短いはずです。ここから使っていくと、行が足されていきます。そして、増えるほど、大事な1行が守られにくくなっていきます。次の 15-2-2 では、なぜそうなるのかと、増えた行をどう刈るのかを扱います。
