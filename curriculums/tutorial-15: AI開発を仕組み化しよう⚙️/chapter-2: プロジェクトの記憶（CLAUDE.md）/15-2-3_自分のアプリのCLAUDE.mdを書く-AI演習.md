# 15-2-3: 自分のアプリのCLAUDE.mdを書く - AI演習

## 📌 この演習について

自分のアプリの `CLAUDE.md` を、1枚として書き上げます。`/init` が書いた叩き台に、Tutorial 14で毎回口で説明していたことを足して、要らない行を落とします。

書いたら終わりにしません。書いたものが読まれて、そのとおりに答えが返ってくるところまで自分で確かめて、この章を終えます。

## 🎯 演習課題

### 📋 課題

`~/laravel-practice/post-app-practice` の `CLAUDE.md` を、自分のアプリの1枚として書き上げてください。

材料は次のとおりです。

| 材料 | どこにあるか |
|:--|:--|
| いまの `CLAUDE.md` | 15-2-1で `/init` に書かせ、3種類を削ってコミットしたもの |
| 消す・残すの判断 | 15-2-2の4つの問い（消したら間違えるか／いつの話か／コードを開けば分かるか／他の紙にも書いてあるか） |
| 毎回説明していたこと | Tutorial 14で、依頼のたびに打っていた前提の行 |

書く中身は、次の4つに振り分けます。

| 見出し | 何を書くか |
|:--|:--|
| よく使うコマンド | 起動・停止・マイグレーション・テスト（全部を回す形と、1クラスだけ回す形）。`./vendor/bin/sail` を頭に付ける決まりも、ここに書きます |
| 守ってほしい書き方 | 入力チェックの置き場所、認可の判定の置き場所、一覧で関連するデータを出すときの決まり |
| テストの決まり | テストの置き場所とメソッド名、データベースを使うテストに付ける1行、変更のあとにテストを回して出力を貼ってもらうこと |
| 触らないでほしいもの | `.env`、自動で作られるフォルダ、実行済みのマイグレーションファイル |

3つ目の「テストの決まり」は、15-2-2で刈った見本に入っていませんでした。あの紙は刈る練習のために用意したものです。Tutorial 14では、実装を頼むたびに「テストも実装と一緒に書いてください」と依頼文へ書き添え（14-3-1）、`Table 'testing.users' doesn't exist` で落ちるたびに `RefreshDatabase` を足させました（14-4-1）。毎回打っていたぶんが、ここに移ります。

書き上げたら、効いているかどうかを自分で確かめるところまでが課題です。

### ✏️ 進め方タスク

1. 【自分】15-2-1で作った `CLAUDE.md` を開き、Tutorial 14で毎回説明していたことを書き出す
2. 【自分】「よく使うコマンド」「守ってほしい書き方」「テストの決まり」「触らないでほしいもの」の4つに振り分けて書く
3. 【自分⇄AI】書いた1行ずつについて、後から確かめられる形になっているかをAIに判定させる
4. 【自分】1行ずつ「これを消したら、AIは間違えるか」を当てて、間違えない行を消す
5. 【自分】`/clear` を打ってから3問を聞き、返ってきた答えを合格の目安と見比べる
6. 【自分⇄AI】答えられなかった問いがあれば1行足して、もう一度確かめる
7. 【自分】コミットしてGitHubへ送る

### ✅ 完成チェックリスト

- [ ] `CLAUDE.md` がアプリのフォルダのいちばん上にあり、ファイル名がすべて大文字であることを、VS Codeのファイル一覧で確かめた
- [ ] `/clear` を打ってから3問を聞き、(1)(2)(3) の答えが合格の目安と合っていることを確かめた
- [ ] 答えられなかった問いについては、根拠になる行を足し、もう一度 `/clear` してから同じ問いで確かめた
- [ ] 1行ずつ「これを消したら、AIは間違えるか」を当てて、間違えない行が残っていないことを確かめた
- [ ] 行数を数えて、200行より少ないことを確かめた
- [ ] GitHubでリポジトリのページを開いて、`CLAUDE.md` が表示されていることを確かめた

## 💡 ヒント

3問を聞いて思ったとおりの答えが返ってこなかったら、症状で分けて直します。

| 症状 | 直し方 |
|:--|:--|
| 3問のどれかに答えられない | その答えの根拠になる行が `CLAUDE.md` に無いということです。1行足して、もう一度 `/clear` してから同じ問いを聞きます |
| 答えは返るが、書いたのと違う内容が返る | 書き方が曖昧です。15-2-1で見た、後から確かめられる形に直します |
| 「ファイルを読んで答えます」と言われる | 質問文の1行目が抜けています。`ファイルは読まないでください。` から始めます |

書いた行が曖昧かどうかを自分で見つけたいときは、その行を読んで「できたかどうかを、誰がどうやって判定するのか」を言ってみてください。言えなければ曖昧です。

何度直しても同じところで止まるときの型は、14-4-3「直らないときの型」にあります。

## 🏃 実践：一緒に進めてみましょう

### 📝 ステップバイステップ

#### Step 1: 毎回説明していたことを書き出す

Claude Codeはまだ起動しません。先に、VS Codeで `CLAUDE.md` を開きます。

そして、Tutorial 14で毎回打っていた行を思い出して、順不同で書き出します。思い出しにくければ、次の場面をたどってください。

- 設計書を1枚頼むごとに、見出しの並びや受け入れ条件の写し方を指定し直しませんでしたか（14-2-4）
- マイグレーションを実行させたとき、`php artisan` ではなく `./vendor/bin/sail artisan` の形かを毎回確かめませんでしたか（14-3-1）
- 実装を頼むとき、テストも一緒に書いてほしいと毎回書き添えませんでしたか（14-3-1）
- テストが `Table 'testing.users' doesn't exist` で落ちるたびに、`RefreshDatabase` を足させませんでしたか（14-4-1）
- 差分を読むたびに、一覧に `with()` が付いているかを見ませんでしたか（14-3-2）

ここでは形を整えなくて構いません。箇条書きで並べます。

#### Step 2: 4つに振り分けて書く

書き出した行を4つの見出しに振り分けて、`CLAUDE.md` を書き直します。15-2-1で `/init` が書いた行のうち残っているものも、ここに混ぜます。`/init` が付けた見出しは、この4つに置き換えて構いません。

このとき、15-2-2の見本を書き写さないでください。あれは刈る練習のために用意した紙です。あなたのアプリで実際に困ったことだけを書きます。

書き終えたら、いったん保存します。

#### Step 3: 書いた行を、確かめられる形に直す

ここで初めてClaude Codeを起動します。

```bash
# アプリのフォルダへ移動して起動する
cd ~/laravel-practice/post-app-practice
claude
```

自分が書いた行を見てもらいます。

```text
@CLAUDE.md を読んでください。
書いてある1行ずつについて、そのとおりにできたかどうかを後から確かめられるか、を判定してください。
確かめられない行があれば、その行と、なぜ確かめられないかを挙げてください。
ファイルは書き換えないでください。直すのは私がやります。
```

> 💡 このお願いのポイントは、①判定してほしい観点を1つに絞っていること ②ファイルを書き換えないでください、と先に断っていること、の2点です。ここで書き直させると、自分が判断していない行が混ざります。読むのはAI、直すのは自分、という分担にしています。

> 💡 **出力例について**: AIの応答は毎回変わります。以下はあくまで一例です。文言が違っても、チェックリストの項目を満たしていれば問題ありません。

```text
Claude Code: （行ごとに判定を並べる。「テストはちゃんと書いてください」の行について、
              何をもって「ちゃんと」とするかが決まっていない、と指摘してくる）
```

指摘は全部受け入れなくて構いません。自分が意図して短く書いた行なら、そのまま残します。直すと決めた行だけ、VS Codeで書き換えます。

#### Step 4: 消してよい行を落として、数える

15-2-2の問いを、自分のファイルに当てます。この1行を消したら、AIは間違えますか。間違えないなら消します。

終わったら、VS Codeでいちばん下の行の番号を見ます。50行前後になっていれば、ちょうどよい厚みです。200行の目安には、まだ余裕があります。

#### Step 5: `/clear` を打ってから、3問を聞く

Claude Codeの入力欄に `/clear` を打ちます。ここまでのやり取りが消えて、まっさらな状態になります。

消す理由は、このあとの答えの出どころを `CLAUDE.md` だけに絞るためです。Step 3で自分が説明した内容がやり取りに残っていると、それを読んで答えられてしまいます。それでは、ファイルが効いているかどうかを確かめたことになりません。

消えるのは、ここまでのやり取りだけです。ファイルに書いたものは消えません。`CLAUDE.md` の中身は、やり取りを空にしても、そのあとの依頼にそのまま渡ります。

続けて、次の質問をそのまま打ちます。

```text
ファイルは読まないでください。いま渡されている指示だけを根拠に、次の3つに短く答えてください。
(1) テストを1クラスだけ実行するコマンドは何ですか。
(2) コードを変えたあと、テストの結果をどう見せる決まりになっていますか。
(3) 新しく /posts/create というルートを足すとき、投稿詳細のルート（/posts/{post}）との
    前後関係はどう決まっていますか。理由も書いてください。
    投稿詳細のURLが違う形になっている場合は、自分のアプリのURLに読み替えてください。
```

> 💡 このプロンプトのポイントは、①「ファイルは読まないでください」と最初に書いて、答えの出どころを `CLAUDE.md` だけに絞っていること ②(3) で**理由**まで聞いていること、の2点です。ルートの並び順は、コードを見れば「そう書いてある」ことは分かりますが、なぜそうなのかは書き残しておかないと答えられません。

返ってきた答えを、この目安と見比べます。

| # | これが返ってくれば合格 |
|:--|:--|
| (1) | `./vendor/bin/sail artisan test --filter CommentTest`（クラス名は違っていてかまいません） |
| (2) | `./vendor/bin/sail artisan test` を実行して、その出力を貼る |
| (3) | `/posts/create` を `/posts/{post}` **より前**に書く／理由は「`create` が `{post}` に吸われて404になるから」 |

答えられなかった問いがあれば、その根拠になる行を `CLAUDE.md` に足します。足したら、もう一度 `/clear` を打ってから、同じ質問をします。

#### Step 6: コミットしてGitHubへ送る

`/exit` でClaude Codeを抜けてから、ターミナルで打ちます。

```bash
# アプリのフォルダの中で実行する
git add CLAUDE.md
git commit -m "CLAUDE.mdを更新"
git push origin main
```

GitHubでリポジトリのページを開いて、`CLAUDE.md` が表示されていることを確かめたら完了です。

## 📖 進行例

> 💡 **進行例について**: AIとの開発は毎回違う流れになります。ここに示すのは一つの進行例です。あなたの画面と違っていても、チェックリストを満たしていれば正解です。

**1. 書き出す**

Tutorial 14で打っていた行を思い出しながら、10行ほど書き出しました。テストのコマンド、入力チェックの決まり、ポリシー、`with()`、テストを実装と一緒に書いてほしいこと、`RefreshDatabase`。書き出してみると、どれも1回では済んでいませんでした。

**2. 見てもらって、1行を書き換え、1行を消す**

`@CLAUDE.md` を読ませて判定させたところ、3行に指摘が付きました。

```text
Claude Code: （「テストはちゃんと書いてください」「読みやすいコードにしてください」の2行について、
              判定する手段が無いと指摘。「with() を付けてください」については、
              どの一覧かが決まっていないと指摘してくる）
```

1つ目はそのとおりだったので、「テストは `tests/Feature/` に置き、テストメソッド名は `test_` で始める」に書き換えました。2つ目の「読みやすいコードにしてください」は、判定できる形に言い直せなかったので、行ごと消しました。3つ目は、一覧の場所を全部列挙すると長くなるので、そのまま残しました。

**3. `/clear` して、3問を聞く**

`/clear` を打ってから、3つの質問を送りました。

```text
Claude Code: (1) ./vendor/bin/sail artisan test --filter CommentTest
             (2) ./vendor/bin/sail artisan test を実行して、その出力を貼ります
             (3) 指示の中に、ルートの前後関係についての記載が見当たりません
```

(1) と (2) は合格の目安どおりでした。(3) は答えが返りませんでした。書いていないのだから、当然です。

**4. 1行足して、もう一度確かめる**

`CLAUDE.md` の「守ってほしい書き方」に、2行足しました。

```text
- `/posts/create` のように文字が決まっているルートは、`/posts/{post}` より前に書く。
  順番が逆だと `create` が `{post}` に吸われて404になる。
```

もう一度 `/clear` を打ってから、同じ3問を送ります。今度は (3) にも、順番と理由の両方が返ってきました。

**5. 数えて、記録する**

行数は46行でした。200行の目安には遠く、まだ足す余地があります。コミットしてpushし、GitHubのページで表示されることを確かめました。

これは一例です。あなたが書いたものと同じである必要はありません。あなたのアプリで実際に困ったことが書かれていれば、行が違っていても構いません。15-2-2の見本と重なる行があるのは、同じアプリの決めごとだからです。重なっていない行が、自分で足したところです。

````markdown
# CLAUDE.md

投稿管理アプリです。Laravel を Sail（Docker）で動かしています。
投稿の一覧・作成・編集・削除、投稿へのコメント、下書きと公開の切り替えができます。
機能ごとの設計書は `docs/` の中にあります（例: `docs/comment.md`）。

## よく使うコマンド

```bash
./vendor/bin/sail up -d                              # 開発環境を起動する
./vendor/bin/sail down                               # 停止する
./vendor/bin/sail artisan migrate                    # マイグレーションを実行する
./vendor/bin/sail artisan test                       # テストを全部実行する
./vendor/bin/sail artisan test --filter CommentTest  # テストを1クラスだけ実行する
./vendor/bin/sail artisan route:list                 # ルート一覧を見る
```

- PHP と artisan は、必ず `./vendor/bin/sail` を頭に付けて実行してください。
  このアプリは Docker の中で動いているので、`php artisan` では動きません。

## 守ってほしい書き方

- 入力チェックはコントローラーの `validate()` に書き、設計書の入力チェック表と同じ内容にする。
- 画面に出すエラーメッセージは日本語にする。
- 「自分のものだけ編集・削除できる」の判定は `app/Policies/` に書き、
  コントローラーからは `$this->authorize()` で呼ぶ。
  コントローラーや Blade に `if ($post->user_id === auth()->id())` を直接書かない。
- `/posts/create` のように文字が決まっているルートは、`/posts/{post}` より前に書く。
  順番が逆だと `create` が `{post}` に吸われて404になる。
- 一覧で関連するデータを出すときは `with()` を付ける。
- `create()` や `update()` に `$request->all()` を渡さない。

## テストの決まり

- テストは `tests/Feature/` に置き、テストメソッド名は `test_` で始める。
- 実装を書き換えるときは、テストも同じ依頼の中で書く。
- データベースを使うテストには `use RefreshDatabase;` を付ける。
  付けないと、テスト用データベースにテーブルが無いと言われて落ちる。
- 変更が終わったら `./vendor/bin/sail artisan test` を実行し、その出力を貼ってください。

## 触らないでほしいもの

- `.env`: 読む必要も書く必要もありません。値が要るときは私に聞いてください。
- `vendor/`・`node_modules/`・`storage/`: 自動で作られるフォルダです。
- すでに実行済みのマイグレーションファイル: 書き換えず、新しく1つ追加してください。
- `composer.json` に新しい依存を足さない。
````

「その出力を貼ってください」の行は、14-4-1「テストで検証する」で決めたことをそのまま書いています。合否を決めているのは `failed` の有無だけで、それは出力を見れば分かります。毎回口で言う代わりに、ここに1行置いています。

## 🚀 まとめ

- 自分のアプリの `CLAUDE.md` を、4つの見出しに振り分けて書き上げました。書いたのは、コードを開いても分からないことだけです。
- 書いたら終わりにせず、`/clear` を打ってから3問聞いて確かめました。やり取りに残った自分の発言を消すと、答えの出どころが `CLAUDE.md` だけになります。
- 答えられなかった問いは、根拠の行が無いということです。足して、もう一度同じ問いを当てます。
- 完成したファイルは、コードと同じように記録します。効く相手は、次に起動したときの自分と、来月このアプリに戻ってきた自分です。

この1枚で、**同じ説明を二度としない**が1つ実現しました。アプリの前提を毎回書いていたぶんは、これでもう打たずに済みます。

消えたのは前提の説明だけです。レビューのときに見る観点を毎回その場で並べていたぶんは、まだ残っています。あれは前提ではなく、決まった手順です。手順のほうは、Chapter 3で呼び出せる部品にします。
