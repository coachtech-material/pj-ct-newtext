# 15-2-1: CLAUDE.mdの育て方

## 🎯 このセクションで学ぶこと

- `CLAUDE.md` に何を書いて、何を書かないかを行ごとに判断できる。
- 曖昧な決まりを、後から確かめられる書き方に直せる。
- どうなったら1行足すのかを、自分の基準として決められる。

## 何を書いて、何を書かないか

2026年8月時点の公式ドキュメントが、入れるものと入れないものを一覧にしています。分かれ目は、**コードを開けば分かることか**、そして、**来週も本当のままか**です。

| 書くもの | 書かないもの |
|:--|:--|
| Claudeには推測できない打ち方（`./vendor/bin/sail` を頭に付ける、など） | コードを読めば分かること（フォルダの一覧・テーブルのカラム・モデルの一覧） |
| 動かすのに要る環境の癖（必要な環境変数、など） | その言語やフレームワークを知っていれば分かる一般的な作法 |
| 既定と違う書き方の決めごと（画面に出す入力チェックのメッセージは日本語にする、など） | 設計書や仕様書の写し（代わりに「`docs/reply.md` を読んで」と在りかを1行だけ書く） |
| テストの回し方と、使うテストランナー | よく変わること（「移行作業中です」「これから作ります」） |
| リポジトリの作法（ブランチ名の付け方、PRの書き方） | ファイルを1つずつ説明したもの |
| このアプリだけの設計上の判断 | 長い説明や解説 |
| 落とし穴（`php artisan` では動かない、など） | 「きれいなコードを書いてください」のような、当たり前のお願い |

右の列を書きたくなるのは、丁寧に書いたほうが伝わりそうに見えるからです。ただ、モデルの一覧は `app/Models/` を開けば書いてあります。書き写した分は、モデルが1つ増えた日から嘘になります。

左の列は逆です。`./vendor/bin/sail` を頭に付けるという決まりは、コードのどこを探しても書いてありません。9-1-2「Docker環境でLaravelを動かそう（Laravel Sail）」で環境を作ったときの事情です。こういうものだけが、ここに書く価値のある行です。

### 見出しの立て方

公式ドキュメントが書式について言っているのは、見出しと箇条書きでまとまりを作ること、1ファイル200行未満に収めること、食い違う決まりを並べないことの3つだけです。決まった雛形はありません。上の左の列が、そのまま見出しになります。

| 見出し | 入るもの |
|:--|:--|
| よく使うコマンド | 推測できない打ち方、環境の癖、落とし穴 |
| コードの書き方 | 既定と違う書き方の決めごと |
| 設計上の決めごと | このアプリ固有の判断 |
| Gitとプルリクエスト | ブランチ名の付け方、PRの書き方 |
| 触らないでほしいもの | 触らせない先（機械で止める指定のほうは `.claude/settings.json`・15-4-1） |

テストの回し方だけ、この1枚から出して別のファイルに持ちます（15-2-3）。

中身の無い見出しは立てません。`/init` が別の名前で見出しを立てていて、そこに中身が入っているなら、そのままで構いません。

置き場所は2か所あります。アプリのフォルダの `CLAUDE.md` は、このプロジェクトを開いた人全員に効き、コミットすればチームにも渡ります。`~/.claude/CLAUDE.md` は、自分のPCで開くどのプロジェクトでも読まれます。どちらも起動時に読み込まれ、両方あれば両方とも渡ります。この教材で育てるのは、アプリのフォルダのほうです。プロジェクトをまたいで効かせたい自分の好み（返事は日本語で、など）だけ、`~/.claude/CLAUDE.md` に置きます。

> 💡 **TIP**: この教材の外では、`CLAUDE.md` をWHAT・WHY・HOWの3つに分ける型も見かけます（2026年8月時点）。ただし、その型のWHATに入るディレクトリ構成や技術スタックは、上の表では右の列にあるものです。`/doctor` に刈らせても、まっ先に消える側にまわります（15-2-2）。

## 確かめられる書き方

書く中身が決まっても、書き方で効き目が変わります。左のように書いていたものを、右のように直します。

| こう書くと伝わらない | こう書けば伝わる |
|:--|:--|
| きれいなコードを書いてください | 入力チェックはコントローラーの `validate()` に書き、`docs/reply.md` の「入力チェックとメッセージ一覧」と同じ内容にしてください |
| ちゃんとテストしてください | 変更が終わったら `./vendor/bin/sail test` を回し、結果を報告してください |
| ファイルは整理してください | 機能のテストは `tests/Feature/` に置いてください |
| セキュリティに気をつけてください | `.env` は読まないでください。値が要るときは私に聞いてください |

右の列はどれも、**そのとおりにできたかを、後から確かめられる**形になっています。

「きれいなコードを書いてください」の場合、書けたかどうかを誰も判定できません。判定できないなら、守られたかどうかも分かりません。「機能のテストは `tests/Feature/` に置いてください」なら、フォルダを開けば1秒で分かります。14-2-1で受け入れ条件を操作の言葉で書いたときと、同じ物差しです。

ここに書いたことが強制ではないことは、14-1-3で見たとおりです。上がるのは確率で、具体的で短い行ほど従われやすくなります。確かめられる形に直すのは、その確率を上げるためです。確実に止めたいものは、この1枚に書くだけでは足りません。権限の設定で止めます（15-4-1）。

## 足す引き金

思いついた順に足すと、太るのはあっという間です。この教材で書き足す引き金にするのは、次のものだけです。

| 引き金 | 足す1行 |
|:--|:--|
| 同じ間違いを**2回目**にされた | その間違いを防ぐ決めごとを1行 |
| 前のセッションで打った説明を、また打っている | その説明を1行 |
| `/clear` したAIに聞いて、答えが返ってこなかった | 答えの根拠になる決めごとを1行 |

上の2つは、2026年8月時点の公式ドキュメントが挙げているものと同じです。公式はほかに、コードレビューで指摘されたとき・新しく入った人にも同じ説明が要るとき、も挙げています。1人でこのアプリを触っているあいだは出番が無いので、この教材では上の3つを使います。

上の2つでは、1回目では足しません。1回きりのことは、次に起きるとは限らないからです。2回目に起きたことは、3回目も起きます。ここが線です。

3つ目は入り方が違います。間違えられるのを待たずに、書き漏らしのほうを先に見つけます。書いたつもりの決めごとが本当に書いてあるかは、`/clear` を打ってから聞けば分かります（15-2-4）。

足すときに、もう1つ守ることがあります。**古い行を消してから、新しい行を足す**。「日本語にする」と決め直したなら、「英語のままでよい」の行はその場で消します。食い違ったまま2つ並ぶと、どちらが読まれるかは決まりません。

足す操作そのものは、その場で頼むのがいちばん速く済みます。「いま直させたことを `CLAUDE.md` に足して」と言えば、その場で書き足されます。公式ドキュメントもこの頼み方を挙げています（2026年8月時点）。自分で開いて書き換えたいときは、`/memory` と打つと小さなメニューが出るので、`Project instructions`（このアプリの `CLAUDE.md`）を選べば、エディタで開きます。

どちらで足した場合も、書き足された行はその場で読みます。ここに入った1行が効くのは、これから先のセッション全部です（15-1-3）。

## 変えたら、効いているかを見る

書き足したり書き直したりしたら、その場で1回試します。テストの回し方を書き直したなら、次の依頼で書いたとおりのコマンドが打たれるかを見ます。

思ったとおりに動かなかったときに見るのは、次の順です。

1. その行が、後から確かめられる形になっているか
2. その行の前後に、消してよい行が並んでいないか（消せる行が多いほど、大事な1行は効きにくくなります。刈り方は15-2-2で扱います）

効かなかったときに同じことをもう一度書き足すと、ほかの行と一緒に埋もれます。増やす前に、いま書いてある1行を直してください。

> 💡 **TIP**: `/compact` で会話を要約したあとも、いちばん上の `CLAUDE.md` はディスクから読み直されます（2026年8月時点の公式ドキュメント）。会話の中だけで伝えた前提は要約で薄まりますが、この1枚に書いた分は戻ってきます（14-5-2）。

## 💡 Claudeが自分で取るメモ（auto memory）

`CLAUDE.md` に何を書くかを決めるのは、あなたです。これとは別に、何を書き留めるかまでClaude自身が決める仕組みも動いています。auto memory と呼ばれるもので、2026年8月時点では既定で有効です。

|  | `CLAUDE.md` | auto memory |
|:--|:--|:--|
| 何を書くかを決める人 | あなた | Claude |
| 中身 | 指示と決まり | 気づいたことや、やり方の癖 |
| 共有範囲 | リポジトリに入るので、コードと一緒にチームへ渡る | 自分のマシンの中だけ。他のマシンへは渡らない |

置き場は `~/.claude/projects/<プロジェクト>/memory/` です。中身はこうなっています。

```text
~/.claude/projects/<プロジェクト>/memory/
├── MEMORY.md          ← 目次。毎回のセッションで読み込まれる
├── debugging.md       ← 話題ごとのメモ。必要になったときだけ読まれる
└── ...
```

毎回渡るのは `MEMORY.md` だけで、しかも先頭の200行（または25KB）までです。詳しい話は話題ごとのファイルへ追い出され、Claudeが要ると判断したときに読みに行きます。`CLAUDE.md` が長さに関係なく全部読まれるのとは、ここが違います。

作業中に画面へ `Saved 2 memories`・`Recalled 2 memories` と出ることがあります。この仕組みが書いたり読んだりした合図です。

| やりたいこと | やり方 |
|:--|:--|
| 何が書かれているかを読む | `/memory` のメニューで `Open auto-memory folder` を選ぶ。ただのマークダウンなので、自分で直せるし消せる |
| 覚えさせる | 「pnpm を使って、npm ではない」のように頼む。こう言われたものはauto memoryへ入る |
| `CLAUDE.md` のほうに入れる | 「これを `CLAUDE.md` に足して」と、置き場所を名指しする |
| 止める | `/memory` の切り替えで切る。プロジェクト単位で切るなら `.claude/settings.json` に `autoMemoryEnabled` を `false` |

置き場所が `~` の下なので、リポジトリには入りません。同じリポジトリのworktree（15-5-1）は1つのフォルダを共有しますが、別のマシンやクラウドの環境へは渡りません。**チームに渡したい決まりは、こちらに書かせても届きません。** 決める人も渡る範囲も違うので、混ぜて考えないでください。この教材であなたが育てるのは `CLAUDE.md` のほうです。

## 🏃 毎回書いていた前提を、1枚に移す

14-5-4で立てたIssueの5項目のうち、上から2つをこの1枚へ移します。

思いどおりに直らない・壊れたと感じたら14-5-1（直らないときの型）へ。応急は `git restore .`

```bash
# アプリのフォルダへ移動して、記録していない変更が無いかを見る
cd ~/laravel-practice/post-app-practice
git status
```

自分が触ったファイルが出てきた場合は、先にコミットしておいてください。

### Step 1: 移すものを確かめる

14-5-4で立てたIssueを開きます。番号を控えていなければ、`gh issue list` で探せます。

```bash
gh issue view <番号>
```

この節で移すのは、上の2つです。

```markdown
- [ ] 依頼のたびに、このアプリの前提（変えないもの・入力チェックのメッセージは日本語で出すこと）を書き直した
- [ ] 実装を頼むたびに「テストも書いて、./vendor/bin/sail test で回して、通るまで直して、最後に結果を報告して」を書き添えた
```

自分のIssueの文言は、これと違っていて構いません。同じことを指していれば大丈夫です。

### Step 2: 決まりとして書かせる

Claude Codeを起動します。

```bash
# アプリのフォルダで実行する
claude
```

渡すのは、移したいものと、移す先だけです。どの見出しに入れるかまで指定しません。

```text
毎回の依頼文に書き添えていた前提を、CLAUDE.md の決まりに移したい。

- このアプリの前提（タイムラインの今の動き・入力チェックのメッセージは日本語）
- テストも書いて ./vendor/bin/sail test で回し、通るまで直して結果を報告すること
- PRの本文に、テスト結果と受け入れ条件の突き合わせを書くこと

見出しの分け方も決めて、CLAUDE.md に足して。足した行を見せて。
```

3つ目は、14-4-5でPRの本文に書かせた形です。PRを出すたびに依頼文へ書いていたので、こちらへ移せます。

### Step 3: 出てきた行を読んで、言い直す

足された行を、1行ずつ読みます。

当てるのは、**後から確かめられる形になっているか**。上で見た物差しをそのまま使います。

もう1つが、**来週も本当のままでいられるか**。ここに1か所、直すところが残っているはずです。14-3-3の依頼文では「タイムラインの今の動き（一覧・編集・削除）は変えない」と書いていました。あれはリプライ機能を作るあいだの話で、この先タイムラインそのものに機能を足す日は来ます。「変えない」のまま毎回効く1枚に置くと、その日から嘘になります。

渡した言葉をそのまま持ってくるのは、AIの側では正しい振る舞いです。ここは自分で見つけて、言い直します。

```text
タイムラインの行を「今ある動き（一覧・編集・削除）を壊さない」に直して。
```

1回の依頼に書いた行を1枚に移すというのは、この言い直しまで含めた作業です。

## ✨ まとめ

- 書くのは、コードを開いても分からないことと、来週も本当のままでいられることだけ。見出しは、そのまま入るものの名前で立てる。
- 曖昧な決まりは、後から確かめられる形に直してから置く。判定できない行は、守られたかどうかも分からない。
- 足す引き金は、同じ間違いの2回目・前のセッションで打った説明の打ち直し・`/clear` したAIが答えられなかったとき。
- 足す前に、古い行を消す。
- 打ち込みは頼めばよい。自分が決めるのは、何を置くかと、出てきた行をそのまま残すかどうか。
- 1回の依頼に書いていた行を1枚へ移すときは、いつでも本当のままでいられる言い方に直す。
