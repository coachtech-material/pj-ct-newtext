### 📋 課題

`~/laravel-practice/post-app-practice` の `CLAUDE.md` と `.claude/rules/testing.md` を、自分のアプリの決まりとして仕上げてください。

材料は次のとおりです。

| 材料 | どこにあるか |
|:--|:--|
| いまの `CLAUDE.md` | 15-2-1で4行足し、15-2-3でテストの行を移したもの |
| いまの `.claude/rules/testing.md` | 15-2-3で作った4行 |
| 消す・残すの判断 | 15-2-2の4つの問い（消したら間違えるか／いつの話か／コードを開けば分かるか／他の紙にも書いてあるか） |
| 毎回説明していたこと | Tutorial 14で、依頼のたびに打っていた前提の行 |

書く中身は、次のとおりに振り分けます。

| 置き場 | 見出し | 何を書くか |
|:--|:--|:--|
| `CLAUDE.md` | よく使うコマンド | 起動・停止・マイグレーション・テスト（全部を回す形と、1クラスだけ回す形）。`./vendor/bin/sail` を頭に付ける決まりも、ここに書きます |
| `CLAUDE.md` | 守ってほしい書き方 | 入力チェックの置き場所、メッセージを日本語で出すこと、消せる人の判定の揃え先、一覧で関連するデータを出すときの決まり、ポスト本文の文字数の上限をいくつに揃えるか、PRの本文に書くこと |
| `CLAUDE.md` | 触らないでほしいもの | `.env`、自動で作られるフォルダ、実行済みのマイグレーションファイル |
| `.claude/rules/testing.md` | （ファイルごと1つの話題） | テストの置き場所、回し方、結果の見せ方 |

テストの決まりだけ、置き場が `CLAUDE.md` の外です。15-2-3でこちらへ移したので、足りない行が見つかったらルールのファイルのほうに書き足します。

書き上げたら、効いているかどうかを自分で確かめるところまでが課題です。

### ✏️ 進め方タスク

## 💡 ヒント

3問を聞いて思ったとおりにならなかったら、当てはまるものを見て直します。

| 起きたこと | 直し方 |
|:--|:--|
| 3問のどれかに答えられない | その答えの根拠になる行が、どちらのファイルにもありません（直し方はStep 5） |
| 答えは返るが、書いたのと違う内容が返る | 書き方が曖昧です。15-2-1で見た、後から確かめられる形に直します |
| 質問文の1行目を書き忘れた | `ファイルは読まないでください。` から打ち直します。この行が無いと、答えの出どころを絞れません |
| 自分では書いていないことに答えが返る | `/memory` を打って `Open auto-memory folder` を選ぶと、Claudeが自分で書き留めたメモを読めます（15-2-1の 💡） |

書いた行が曖昧かどうかを自分で見つけたいときは、その行を読んで「できたかどうかを、誰がどうやって判定するのか」を言ってみてください。言えなければ曖昧です。

何度直しても同じところで止まるときの型は、14-5-1「直らないときの型」にあります。応急は `git restore .` です。

## 🏃 実践：一緒に進めてみましょう

### 📝 ステップバイステップ

#### Step 1: 毎回説明していたことを書き出す

Claude Codeはまだ起動しません。先に、VS Codeで `CLAUDE.md` と `.claude/rules/testing.md` を開きます。

そして、Tutorial 14で毎回打っていた行を思い出して、順不同で書き出します。思い出しにくければ、次の場面をたどってください。

- 設計書を1枚頼むごとに、見出しの並びを指定し直しませんでしたか（14-3-3）
- マイグレーションのとき、`php artisan` で失敗していないかを毎回見ていませんでしたか（14-3-3）
- 差分を読むたびに、一覧に `with()` が付いているかを見ませんでしたか（14-4-2）
- 編集画面に文字数の上限を足したとき、上限を140字と決めませんでしたか（14-3-2）
- PRの本文に、テストの結果と受け入れ条件の判定を書かせませんでしたか（14-4-5）
- 依頼のたびに、入力チェックのメッセージを日本語で出すことを書き添えませんでしたか（14-5-4）

ここでは形を整えなくて構いません。箇条書きで並べます。

#### Step 2: 振り分けて書く

書き出した行を、3つの見出しとルールのファイルに振り分けます。15-2-1で足した4行のうち、テストの1行は15-2-3で移したので、`CLAUDE.md` 側には戻しません。

「守ってほしい書き方」には、本文の文字数の上限を1行入れてください。14-3-2で編集画面に付けた140字が、このアプリで使っている値です。ほかの画面にも上限を付けるときはその数に揃える、という形で書いておくと、作成画面に上限を付けたかどうかに関係なく本当のままでいられます（Step 5で使います）。

このとき、15-2-2の見本を書き写さないでください。あれは刈る練習のために用意した紙です。あなたのアプリで実際に困ったことだけを書きます。

書き終えたら、いったん保存します。

#### Step 3: 書いた行を、確かめられる形に直す

ここで初めてClaude Codeを起動します。

```bash
# アプリのフォルダへ移動して起動する
cd ~/laravel-practice/post-app-practice
claude
```

自分が書いた行を見てもらいます。

```text
@CLAUDE.md と @.claude/rules/testing.md を読んでください。
書いてある1行ずつについて、そのとおりにできたかどうかを後から確かめられるか、を判定してください。
確かめられない行があれば、その行と、なぜ確かめられないかを挙げてください。
ファイルは書き換えないでください。直すのは私がやります。
```

> 💡 判定してほしい観点を1つに絞り、ファイルを書き換えないでください、と先に断っています。ここで書き直させると、自分が判断していない行が混ざります。読むのはAI、直すのは自分、という分担にしています。

> 💡 **出力例について**: AIの応答は毎回変わります。以下はあくまで一例です。文言が違っても、チェックリストの項目を満たしていれば問題ありません。

```text
Claude Code: （行ごとに判定を並べる。「テストはちゃんと書いてください」の行について、
              何をもって「ちゃんと」とするかが決まっていない、と指摘してくる）
```

指摘は全部受け入れなくて構いません。自分が意図して短く書いた行なら、そのまま残します。直すと決めた行だけ、VS Codeで書き換えます。

#### Step 4: 消してよい行を落として、数える

15-2-2の問いを、自分のファイルに当てます。この1行を消したら、AIは間違えますか。間違えないなら消します。

終わったら、VS Codeでいちばん下の行の番号を見ます。200行の目安には、まだ余裕があるはずです。

#### Step 5: `/clear` を打ってから、3問を聞く

Claude Codeの入力欄に `/clear` を打ちます。ここまでのやり取りが空になります。

消す理由は、このあとの答えの出どころを `CLAUDE.md` とルールのファイルだけに絞るためです。Step 3で自分が説明した内容がやり取りに残っていると、それを読んで答えられてしまいます。それでは、ファイルが効いているかどうかを確かめたことになりません。

消えるのは、ここまでのやり取りだけです。ファイルに書いたものは消えません。空になったあとの依頼にも2枚の中身が渡っているかどうかは、このあとの3問で分かります。

続けて、次の質問をそのまま打ちます。

```text
ファイルは読まないでください。いま渡されている指示だけを根拠に、次の3つに短く答えてください。
(1) このアプリで PHP や artisan のコマンドを打つとき、頭に何を付ける決まりですか。
(2) テストを1クラスだけ実行するコマンドは何ですか。
(3) ポスト本文の文字数の上限は、何字に揃える決まりですか。
```

> 💡 1行目の「ファイルは読まないでください」は、答えの出どころを、いま渡されている指示に絞るための行です。その場でファイルを開いて読んだ結果が返ってきたのでは、起動のたびに渡っているかどうかの確かめになりません。

返ってきた答えを、この目安と見比べます。

| # | 出どころ | これが返ってくれば合格 |
|:--|:--|:--|
| (1) | `CLAUDE.md` の「よく使うコマンド」 | `./vendor/bin/sail` を頭に付ける（`php artisan` では動かない） |
| (2) | `.claude/rules/testing.md` | `./vendor/bin/sail test --filter ReplyTest`（クラス名は違っていてかまいません） |
| (3) | `CLAUDE.md` の「守ってほしい書き方」 | 140字（14-3-2で編集画面に付けた上限に揃える） |

(2) に答えが返ってきたら、15-2-3で別のファイルに分けた決まりも、起動のたびに読まれていることになります。分けても効き方は変わらない、という確かめです。

**`/clear` のあとに3問を聞いたところ**

答えられなかった問いがあれば、その根拠になる行を足します。15-2-1で見た3つ目の引き金です。足したら、もう一度 `/clear` を打ってから、同じ質問をします。

#### Step 6: コミットしてGitHubへ送る

```text
CLAUDE.md と .claude/rules/testing.md をコミットして、main に push して。
```

GitHubでリポジトリのページを開いて、2つのファイルが表示されていることを確かめたら完了です。

## 📖 進行例

> 💡 **進行例について**: AIとの開発は毎回違う流れになります。ここに示すのは一つの進行例です。あなたの画面と違っていても、チェックリストを満たしていれば正解です。

**1. 書き出す**

Tutorial 14で打っていた行を思い出しながら、10行ほど書き出しました。テストのコマンド、入力チェックの決まり、消せる人の判定、`with()`、本文の文字数の上限、PRの本文に書かせていたこと。書き出してみると、どれも1回では済んでいませんでした。

**2. 見てもらって、1行を書き換え、1行を消す**

2枚を読ませて判定させたところ、3行に指摘が付きました。

```text
Claude Code: （「テストはちゃんと書いてください」「読みやすいコードにしてください」の2行について、
              判定する手段が無いと指摘。「with() を付けてください」については、
              どの一覧かが決まっていないと指摘してくる）
```

1つ目は、確かめられる形に言い直すと「機能のテストは `tests/Feature/` に置く」になりました。それは15-2-3で `.claude/rules/testing.md` に書いた1行目そのものだったので、書き換えずに消しました。他の紙にあるものは、そちらに任せます。2つ目の「読みやすいコードにしてください」は、判定できる形に言い直せなかったので、行ごと消しました。3つ目は、一覧の場所を全部列挙すると長くなるので、そのまま残しました。

**3. 消しすぎたことに、あとで気づく**

Step 4で「この1行を消したら、AIは間違えますか」を当てているとき、「ポスト本文に文字数の上限を付けるときは、140字に揃える」の行で迷いました。140という数字は、編集画面の入力チェックにそのまま書いてあります。コードを開けば分かることは書かない、という物差しに当てて、消しました。

**4. `/clear` して、3問を聞く**

`/clear` を打ってから、3つの質問を送りました。

```text
Claude Code: （(1) には ./vendor/bin/sail を頭に付ける、(2) には
              ./vendor/bin/sail test --filter ReplyTest が返る。(3) は
              「指示の中に、文字数の上限についての記載が見当たりません」と返ってくる）
```

(1) と (2) は合格の目安どおりでした。(2) が返ってきたので、ルールのファイルも読まれています。(3) は答えが返りませんでした。さきほど消した行が、ちょうどそれです。

**5. 1行戻して、もう一度確かめる**

消したのが正しかったのかを、考え直しました。140という数字は、たしかにコードを開けば分かります。ただ、ほかの画面にも上限を付けるときはその数字に揃える、というのはコードのどこにも書いていません。数字ではなく、そちらの決めごとのほうが要るので、「守ってほしい書き方」に1行戻しました。

```text
- ポスト本文に文字数の上限を付けるときは、140字に揃える（編集画面で使っている値）。
```

もう一度 `/clear` を打ってから、同じ3問を送ります。今度は (3) にも答えが返ってきました。消すか残すかの判断は、こうして `/clear` のあとの質問で答え合わせができます。

**6. 数えて、記録する**

`CLAUDE.md` の行数は34行でした。200行の目安には遠く、まだ足す余地があります。`.claude/rules/testing.md` は15-2-3で書いた4行のままで、足すものは出ませんでした。コミットしてpushし、GitHubのページで2つとも表示されることを確かめました。

```bash

- タイムラインの今ある動き（一覧・編集・削除）を壊さない。

## 触らないでほしいもの

- `.env`: 読む必要も書く必要もありません。値が要るときは私に聞いてください。
- `vendor/`・`node_modules/`・`storage/`: 自動で作られるフォルダです。
- すでに実行済みのマイグレーションファイル: 書き換えず、新しく1つ追加してください。
````

## 🚀 まとめ

- 自分のアプリの決まりを、`CLAUDE.md` の3つの見出しと `.claude/rules/testing.md` に振り分けて仕上げました。書いたのは、コードを開いても分からないことだけです。
- 書いたら終わりにせず、`/clear` を打ってから3問聞いて確かめました。やり取りに残った自分の発言を消すと、答えの出どころが2枚のファイルだけになり、答えが返らない問いがそのまま書き漏らしの在りかになります。
- 分けたファイルからも答えが返るので、話題ごとに置き場を分けても効き方は変わりません。
- 完成した2枚は、コードと同じように記録します。効く相手は、次に起動したときの自分と、来月このアプリに戻ってきた自分です。

これで、**同じ説明を二度としない**が1つ実現しました。アプリの前提を毎回書いていたぶんは、これでもう打たずに済みます。

消えたのは前提の説明だけです。差分を受け取るときに読む順番を毎回その場で組み立てていたぶんは、まだ残っています。あれは前提ではなく、決まった手順です。手順のほうは、Chapter 3で呼び出せる部品にします。
