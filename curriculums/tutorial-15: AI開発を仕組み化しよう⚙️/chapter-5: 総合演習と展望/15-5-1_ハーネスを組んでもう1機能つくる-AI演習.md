# 15-5-1: ハーネスを組んでもう1機能つくる - AI演習

## 📌 この演習について

Chapter 2からChapter 4までで、前提・手順・担当者・許可と自動実行の4点がそろいました。この章では、新しい道具を増やしません。そろった4点を持ち込んで、もう1つ機能を作りきります。

> 🔥 ここからは、AIに実装を任せて構いません。ただし「任せる」と「丸投げ」は違います。何を作るかは設計書で自分が決め、出てきたものはテスト・動作確認・コードレビューで自分が検証します。品質の責任は、AIではなくあなたが握ります。

## 🎯 演習課題

### 📋 課題

今回の要件は、次のとおりです。

> いまの投稿一覧は、新しい順にすべての投稿が並ぶだけです。投稿が増えると、読みたいものを探せません。投稿に「タグ」を付けられるようにして、一覧をタグで絞り込めるようにします。タグは、あらかじめ用意されたものから選びます。タグを付け替えられるのは、その投稿を書いた本人だけです。

受け入れ条件は、今回は先に決めてあります。次の4行が、最後の判定に使う基準です。

- [ ] 投稿一覧で、それぞれの投稿に付いているタグが表示される（タグが1つも付いていない投稿には、何も表示されない）
- [ ] 自分の投稿の編集画面でタグを選び直して保存すると、投稿一覧の表示がそのとおりに変わる
- [ ] 投稿一覧でタグを1つ選ぶと、そのタグが付いた投稿だけが並ぶ。このとき、他人の下書きは出てこない
- [ ] 他人の投稿の編集画面を直接URLで開こうとすると403になり、他人の投稿のタグは変えられない

あなたが発注者です。決めきれないところは自分で決めます。ただし今回も、判断が同時に増えすぎないよう、いくつかは先に決めてあります。

| 決めてあること | 中身 |
|:--|:--|
| 選べるタグ | あらかじめ用意されたものから選びます。タグを新しく作る画面は作りません |
| タグの用意のしかた | シーダーで数件入れておきます。もとからある投稿4件の行は消しません |
| テーブルの名前 | タグそのものを入れるのが `tags`、投稿とタグをつなぐのが `post_tag` です。9-5-2で見た付け方（2つのテーブル名を単数形にして、アルファベット順につなぐ）そのままです |
| 1つの投稿に付けられる数 | 最大3つまでにします。受け入れ条件ではなく、入力チェックとして扱います |
| 付け替えられる人 | その投稿を書いた本人だけです |
| 付け替える場所 | 10-3-5で作った投稿の編集画面に足します |
| 一覧の絞り込み | 投稿一覧でタグを1つ選ぶ形にします。投稿を書けるようにしたときに決めた「公開済みと、自分の下書き」の範囲は変えません |

今回作らないものも決めておきます。

| 作らないもの | 理由 |
|:--|:--|
| タグを新しく作る画面 | 用意されたものから選ぶ、と決めたためです |
| 一覧のページ送り | 一覧の並べ方や見た目は、今回の対象ではありません |
| 状態遷移図 | タグには状態がありません。作らなかった理由は `docs/tagging/README.md` に書きます |
| 認可のテスト | 403になることは、ブラウザで直接URLを開いて確かめます |

**進め方の骨**

6. ブランチをpushしてプルリクエストを開き、マージする（14-3-5・14-4-3）

**テーブルを作る順**

`tags` と `post_tag` は、この順で作ります。`post_tag` は `posts` と `tags` の両方ができてから作らないと、つながりを書けません。9-5-5「リレーション - ハンズオン演習」でも、同じ理由で作る順が決まっていました。

```bash
# アプリのフォルダの中で実行する
./vendor/bin/sail artisan make:model Tag -m
./vendor/bin/sail artisan make:migration create_post_tag_table
```

**シーダーは足す。もとの行は消さない**

タグのデータは、`DatabaseSeeder.php` に直接書かず、新しいシーダーのクラスを1つ作って、その中に入れます。

```bash
# アプリのフォルダの中で実行する
./vendor/bin/sail artisan make:seeder TagSeeder
```

作ったら、`database/seeders/DatabaseSeeder.php` の `run()` に、そのクラスを呼び出す1行を足します（9-3-5）。もとから書かれている投稿4件の行は書き換えません。書き換えると、10-3-5で確かめた動きが変わります。

クラスを分けておくと、タグだけを入れ直したいときに、そのクラスだけを名指しして流せます。

**投稿の一覧に出す範囲を壊さない**

絞り込みを足すと、一覧の条件が2つ重なります。タグで絞ることと、「公開済みと、自分の下書きだけを出す」ことの両方です。片方だけになっていないかは、`test.md` の観点に1行入れて、テストで確かめてください。

**テストが回らないときは**

Sailが起動しているかを確かめてください。Docker Desktop（またはDocker Engine）を起動してから `./vendor/bin/sail up -d` を実行します。

**詰まったときは**

14-4-5で持った3つの型に戻ってください。まず巻き戻す、頼む単位を分け直す、2回直らなければ区切って分かったことを書き足す、の順です。設計書に書いていないことをAIが聞いてきたら、それは設計の穴です。その場で決めて、設計書を直してから続けます。

### 📝 ステップバイステップ

#### Step 1: ハーネスを持ち込む

ハーネスは、15-1-2で名前を付けた、AIが走れるようにするための道具立てのことです。

```bash

cd ~/laravel-practice/14_hands-on/authorization-app-ai
git switch main
git pull origin main
```

アプリが止まっている場合は、Docker Desktop（またはDocker Engine）を起動してから、Sailを立ち上げます。

```bash
# アプリのフォルダの中で実行する
./vendor/bin/sail up -d
```

持ち込むのは、次の4点です。

| どこにあるか | 何をしてくれるか | 作った場所 |
|:--|:--|:--|
| `CLAUDE.md` | このアプリの前提を、依頼のたびに説明しなくてよくなる | 15-2-3 |

#### Step 2: 機能イシューを立てる

ここは、これまでと変わりません。

GitHubで自分の `authorization-app-practice` のページを開き、「Issues」タブから新しいイシューを立てます。タイトルは動詞で終える形（例: `投稿にタグを付けられるようにする`）、ラベルは `enhancement` です。

本文の枠も同じで、いま埋めるのは `## 概要` だけです。

```markdown
## 概要
（何ができるようになるかを2〜3行で）

## 受け入れ条件
- [ ] 〜すると、〜になる

## 設計書
docs/tagging/

## タスク
- [ ] （設計書を書いてから並べます）
```

立てたら、イシューの番号を控えておいてください。Tutorial 14で、機能イシュー2件とプルリクエスト2本を1番から4番まで使っています。ですから今回のイシューは5番になる見込みです。

このあとの手順には `#5` やブランチ名の `issue-5` が出てきますが、自分の画面に表示されている番号に読み替えて進めてください。

#### Step 3: 設計書を8ファイル書かせる

今回のフォルダを作ります。

```bash
# アプリのフォルダの中で実行する
mkdir docs/tagging
```

Chapter 4で入れた Hooks は、Markdownのファイルを書き換えたときにも動きます。設計書を1ファイル書かせるたびにテストが回るので、返事までに少し間が空きます。止まったように見えても、待ってください。

頼み方は14-2-4と同じです。1つ頼み、読んで、直してから、次を頼みます。ここで変わるのは2つだけです。

1つ目は、渡すものが減ることです。このアプリがLaravelをSailで動かしていること、どの機能が入っているか、設計書がどこにあるか。この3つはChapter 2で `CLAUDE.md` に書いたので、今回は依頼文に書きません。書かずに済んだかどうかは、あとで数えます。

設計書1枚ごとの列名・記号・IDの振り方は、これとは別です。`CLAUDE.md` に書いていない分は、14-2-4の「頼むときに必ず指定すること」の表のとおり、今回も自分で指定します。

2つ目は、下調べを担当に投げられることです。設計書を書く前に、「タグの表示をどこに足すのか」を決める必要があります。これまでは自分のやり取りの中で調べていましたが、今回は `@agent-codebase-explorer` と書いて、担当を名指しします。

```text
@agent-codebase-explorer 投稿一覧と投稿の編集画面が、どのファイルで組み立てられているかを調べてください。
一覧を出しているコントローラーのメソッド、一覧のBladeファイル、編集画面のフォームのBladeファイルの3つを、
ファイル名と、根拠になる行と一緒に教えてください。
```

> 💡 このお願いのポイントは3つです。①調べてほしいものを3つに絞っている ②根拠になる行まで出させている ③設計に要る場所だけを聞いている。②があると、返ってきた答えを自分でファイルを開いて確かめられます。14-1-3でやった裏取りと同じです。文言をそのまま覚える必要はありません。

担当を分けても、確かめるのは自分です。

`usecase.md` を頼むときは、課題に載せた受け入れ条件の4行をそのまま渡して、その4行を書かせてください。言い回しを変えさせると、Step 8で突き合わせる基準が2つになります。

`data.md` を頼むときは、図に出す範囲を自分で切ります。

```text
docs/tagging/data.md を書いてください。
今回足すテーブルは2つです。タグそのものを入れる tags と、投稿とタグをつなぐ post_tag です。

- ER図はMermaidのerDiagramで、posts・tags・post_tag の3つだけを描いてください
- post_tag には post_id と tag_id を置きます
- いまあるほかのテーブルは、今回の図には出さないでください
- 図の下に、テーブル定義とCRUD表を続けてください
```

> 💡 このお願いのポイントは3つです。①足すテーブルを名前で決めている ②図に出す範囲を切っている ③書く順を指定している。②が無いと、アプリ全体のER図が返ってきて、今回どこが増えたのかを読み取れなくなります。文言をそのまま覚える必要はありません。

#### Step 5: 実装タスクに割る

ここも同じです。

設計書を3枚ほど渡して、タスクの案を出させます。返ってきた案は、14-3-2の3つの基準（差分を読み切れるか、終わったことを自分で確かめられるか、設計書の行に対応しているか）で決め直してください。決まったら、タスク名の先頭に設計書のIDを入れて、イシューの `## タスク` に並べます。

#### Step 6: ブランチを切って、実装させる

```bash
# アプリのフォルダの中で実行する
git switch -c feature/issue-5-add-post-tagging
```

あとはタスクごとに、14-3-3と同じ手順を回します。計画を立てさせ、計画を読んで承認するか指摘するかを決め、実装させ、差分を読んで承認し、コミットして、イシューのタスクを `- [x]` にします。

ここでの変わり方は、2つです。

1つ目は、承認を押す回数です。`.claude/settings.json` に書いた形のコマンドは、承認を求めずに動きます。テストの実行のように、内容を読むまでもないと自分で決めたものが対象です。14-1-4で身につけた読む判断は、そのまま残ります。

2つ目は、テストです。ファイルを書き換えるたびに、テストが機械で回ります。落ちたらAIに伝わって、直そうとします。テストを流す分だけ、1回のやり取りに時間がかかります。

減らしてはいけないものが1つあります。差分を読む回数です。14-3-4で、読み切れる量かどうかを決めないまま「今後は聞かない」を押すと、人間の介在点を1つ消したことになる、と確かめました。今回消したのはコマンドの承認であって、差分の承認ではありません。

テーブルが増えるので、データベースへの反映も要ります。打つのは、テーブルを作るタスクが終わった直後です。全部のタスクが終わってからではありません。

```bash
# アプリのフォルダの中で実行する
./vendor/bin/sail artisan migrate
```

続けて、選べるタグのデータを入れます。ここで `./vendor/bin/sail artisan db:seed` とだけ打つと `DatabaseSeeder` が丸ごと動いて、10-3-5で入れたデータに手が入ります。自分が足したシーダーのクラスだけを名指しして流してください。

```bash
# アプリのフォルダの中で実行する
./vendor/bin/sail artisan db:seed --class=TagSeeder
```

クラス名は、自分が作ったものに読み替えます。9-3-5「シーダーの基礎」で使った打ち方です。

#### Step 7: テストを回して、自分の目で見る

```bash
# アプリのフォルダの中で実行する
./vendor/bin/sail artisan test
```

Hooksが回すのは、あなたが打ち忘れたときのためです。最後の1回は自分で打って、自分の目で見てください。

見るのは `failed` の有無です（14-4-1）。`failed` が出たら、その1本の行だけをAIに渡して直させ、もう一度自分で回します。テストのほうを消したり緩めたりはしません。

回し終えたら、`test.md` の観点表と `tests/Feature/` を並べて、テストにすると決めた行がそれぞれ書かれているかを確かめてください。

#### Step 8: 下読みを当ててから、自分で読む

Chapter 3で作った `/review-checklist` を呼びます。

```text
/review-checklist
```

`docs/review-checklist.md` の観点が、上から順に当たります。挙がってくるのは「ここを見てください」という下読みで、直すかどうかの決定ではありません。14-4-2で、毎回すべての観点を当てようとすると流し読みになる、と確かめました。下読みは全部当ててよいのですが、そのあと自分で読む箇所は、自分で絞ります。

挙がった箇所を1つずつ開いて、直す・直さないを決めてください。直さないと決めたものは、その理由を自分の言葉で言えるようにしておきます。読むのは人の側です。

そのあとブラウザで、受け入れ条件を1行ずつ潰します。手順は14-4-3と同じです。下の表は受け入れ条件そのものではなく、確かめるための手立てです。

1つ目の行で下書きにもタグを付けるのは、他人の下書きが出てこないことを、そのタグが付いた下書きが実際にある状態で確かめるためです。ユーザーAの下書きが手元に残っていなければ、投稿を1つ書いて、下書きのままにしておいてください。

| 試すこと | どうなれば合っているか |
|:--|:--|
| ユーザーAで、公開している投稿と下書きの投稿の両方に同じタグを選んで保存し、一覧に戻る | 一覧の表示が、選んだとおりに変わる |
| ユーザーBでログインし直して、そのタグを選ぶ | ユーザーAの公開している投稿だけが並び、下書きは出てこない |
| ユーザーBで、ユーザーAの投稿の編集画面のURLを直接開く | 403になる |

確かめた行から順に、イシューの受け入れ条件に `- [x]` を付けていきます。途中で直したところがあれば、ここでコミットまで済ませておいてください。

#### Step 9: pushして、プルリクエストを開き、マージする

```bash
# アプリのフォルダの中で実行する
git push origin feature/issue-5-add-post-tagging
```

GitHubでリポジトリを開き、プルリクエストを作ります。本文の形はこれまでと同じで、最後の行に `Closes #5` を入れます。

```markdown
## 概要
Issue #5 に対応して、投稿にタグを付けられるようにしました。一覧をタグで絞り込めます。

## 変更内容
- tagsテーブルと、投稿とタグをつなぐpost_tagテーブルを追加
- 投稿の編集画面にタグの選択を追加
- 投稿一覧にタグの表示と、タグでの絞り込みを追加
- test.mdの観点のうち、テストにすると決めた行をtests/Feature/に追加

Closes #5
```

受け入れ条件の全行が `- [x]` になったら、「Files changed」を開いて、Step 8で直したところが入っていることを確かめてからマージします。そのあと、手元も `main` にそろえます。

```bash
# アプリのフォルダの中で実行する
git switch main
git pull origin main
git branch -d feature/issue-5-add-post-tagging
```

`.claude/` と `CLAUDE.md` は、Chapter 2からChapter 4のうちに `main` へ入れてあります。だから、この機能のプルリクエストに道具の差分は出てきません。道具を先に共有できる形にしておく、というのはこういうことです。使いながら `CLAUDE.md` を直したくなることはありますが、その行き先は Step 10 に書きます。

#### Step 10: 効き目を数える

最後に、4点が何をしてくれたのかを数えます。数えるのは、次の4つです。

| 数えるもの | どう数えるか | どこを見るか |
|:--|:--|:--|
| 書かずに済んだ前提 | 依頼のたびに書かなくて済んだものを挙げる | `CLAUDE.md` に書いた行と、今回自分が打った依頼文 |
| 機械が先に知らせたテストの失敗 | 自分で打つ前に知らされた回数 | 実装中のやり取り |
| 押さずに済んだ承認 | 許可リストに書いた形のコマンドが、承認を求めずに動いたか | `.claude/settings.json` の `allow` に書いた行 |
| 言わずに守られた決まり／守られなかった決まり | `CLAUDE.md` の行ごとに、守られたかを見る | 出てきたコードと `CLAUDE.md` |

数えたものは、`docs/tagging/README.md` の末尾に `## ハーネスの効き目` という見出しを作って書きます。設計書一式と同じ寿命の記録なので、ここに置きます。

効かなかったものが、次に直す場所です。うまくいかない場面が出てきたら、毎回の依頼に言葉を足すのではなく、書いてあるほうを直します。守られなかった決まりを見つけて `CLAUDE.md` を直した場合は、その1行もここで一緒に記録します。機能のマージはもう済んでいるので、`main` に直接入れる形になります。

```bash
# アプリのフォルダの中で実行する
git add docs CLAUDE.md
git commit -m "Add harness notes to tagging docs"
git push origin main
```

`CLAUDE.md` を直していなければ、記録されるのは `docs` だけです。

ここまでで、手順は自分の頭の中ではなくリポジトリの中にあります。次にこのフォルダを開いた人が、同じ4点を同じ場所で見つけられる状態です。

## 📖 進行例

> 💡 **進行例について**: AIとの開発は毎回違う流れになります。ここに示すのは一つの進行例です。あなたの画面と違っていても、チェックリストを満たしていれば正解です。

**1. 設計書を頼むときに、アプリの説明を1行も書かなかった**

`feature-list.md` から順に8ファイルを書かせました。渡したのは、思考プロセスの表の1行目に挙げた3つだけです。

このアプリがLaravelをSailで動かしていること、どの機能が入っているか、設計書がどこにあるかは、8回とも1行も書きませんでした。Tutorial 14のあいだ、依頼のたびに説明し直していた分です。

**2. どこに足すかを、担当に調べさせた**

`screen.md` を書く前に、一覧と編集画面がどのファイルでできているかを調べる必要がありました。`@agent-codebase-explorer` で名指しして投げると、3つのファイル名と、根拠になる行が返ってきました。

自分でその3つを開いて、書かれていた行があることを確かめました。調べている途中の読み込みは、自分のやり取りには積まれていません。そのまま `screen.md` の依頼に移れました。

**3. テストが落ちたことを、先に知らされた**

タグでの絞り込みを実装させている最中に、テストが落ちたと知らされました。自分ではまだ打っていない段階です。

落ちたのは、投稿を書けるようにしたときに作った「他人の下書きが一覧に出てこない」テストでした。タグの条件を足したときに、公開済みと自分の下書きに絞る条件のほうが外れていたためです。落ちた1本の行を渡して直させ、そのあと自分でもう一度打って `failed` が0になったことを見ました。

**4. 下読みで2件挙がり、1件は直さないと決めた**

`/review-checklist` を打つと、2件挙がりました。1件は、一覧の絞り込みで投稿ごとにタグを取りに行っている、というものです。これは直しました。

もう1件は、編集画面のBladeでタグの並び順を指定していない、というものでした。設計書に並び順を決めていないので、これは設計の側の話です。今回は直さず、`README.md` に「並び順は決めていない」と1行書いておきました。挙がったから直す、ではなく、直すかどうかを自分で決めています。

**5. 守られた決まりと、守られなかった決まり**

`CLAUDE.md` に書いた決まりのうち、「テストが落ちた状態で作業を終えない」は、一度も口に出さずに守られました。進行例3で直しにいったのが、そのままその実物です。

守られなかったものもあります。タグを4つ選んだときのエラーメッセージが、英語のまま出ていました。`CLAUDE.md` には「画面に出すエラーメッセージは日本語にする。」と書いてあります。

**6. 書いてあるほうを直した**

その場で「日本語にしてください」と頼めば直ります。ただ、それでは次の機能でも同じことを言うことになります。

そこで `CLAUDE.md` のほうを直しました。「画面に出すエラーメッセージは日本語にする。」を、「画面に出すエラーメッセージは、その機能の設計書の `screen.md` に書いたメッセージ一覧の文言をそのまま使う。」に書き換えています。どこを見ればよいかが書かれていなかったのが、守られなかった理由でした。直したのはマージが終わったあとで、Step 10 のメモと一緒に `main` へ記録しました。

## 🚀 まとめ

- 同じ流れをもう一度回しました。変わったのは順番ではなく、毎回手でやっていたことが減ったことです。
- 前提・観点・承認・テストの4つは、置き場所を決めた時点で、次の機能にも効きました。
- Chapter 1で決めた「同じ説明を二度としない」は、ここで形になりました。今回、このアプリの前提もレビューの観点も、一度も言い直していません。
- 機械が先に知らせても、最後の1回は自分で打ちます。下読みが挙げても、直すかどうかは自分が決めます。
- 効かなかった決まりは、数えてみて初めて見つかります。見つかったら、直す先は依頼文ではなく、書いてあるほうです。
- やり方が一人の頭の中にしかない状態を、属人化と呼びます。手順をリポジトリに置いた時点で、来月このアプリを触る自分も、`/clear` した次のやり取りのAIも、同じ手順を使えます。
