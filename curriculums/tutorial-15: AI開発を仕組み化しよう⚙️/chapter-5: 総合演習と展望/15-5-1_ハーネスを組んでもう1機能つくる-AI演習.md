# 15-5-1: ハーネスを組んでもう1機能つくる - AI演習

## 📌 この演習について

3つ目の機能を作ります。新しい道具は増やしません。Chapter 2からChapter 4で置いた4つを持ち込んで、そのまま1機能を通します。

渡すものは14-5-1と同じ3つです。実現したいこと、変えたくないこと、完成の判定基準。手順は並べません。

題材は、投稿へのタグ付けと、タグでの絞り込みです。9-5-5「リレーション - ハンズオン演習」で、同じ形のものを一度作りました。今回は、すでに動いているアプリの上に足します。コメントも下書きも入った状態で、そのどちらも壊さないことが、あのとき無かった条件です。

## 🎯 演習課題

### 📋 課題

**実現したいこと**

> いまの投稿一覧は、新しい順にすべての投稿が並ぶだけです。投稿が増えると、読みたいものを探せません。投稿に「タグ」を付けられるようにして、一覧をタグで絞り込めるようにします。タグは、あらかじめ用意されたものから選びます。付け替えられるのは、その投稿を書いた本人だけです。

**譲れないところ**

ここだけは決まっています。それ以外の作り方は指定しません。

| 決めごと | 中身 |
|:--|:--|
| 選べるタグ | あらかじめ用意されたものから選びます。タグを新しく作る画面は作りません |
| タグの用意のしかた | シーダーで数件入れておきます |
| 1つの投稿に付けられる数 | 最大3つまでです。受け入れ条件には入れず、入力チェックとして扱います |
| 付け替えてよい人 | その投稿を書いた本人だけです |
| 一覧に出す範囲 | 下書き機能で決めた「公開済みの投稿すべてと、自分が書いた下書き」を変えません |

テーブルの名前も、タグを選ぶ画面の作りも決めていません。設計のときに決めます。

**変えたくないこと**

| 変えたくないもの | 確かめ方 |
|:--|:--|
| もとからある4件の投稿 | この機能を入れたあとも、ユーザーA・ユーザーBのどちらの一覧にも出ます |
| 投稿の編集と削除 | 他人の投稿は編集・削除のボタンが出ず、URLを直接開くと403になります |
| コメントと下書き | ここまでに入れたものは、そのまま動きます |

**完成の判定基準**

この4行が、この演習の受け入れ条件になります。

- [ ] 投稿一覧で、それぞれの投稿に付いているタグが表示される（1つも付いていない投稿には、何も出ない）
- [ ] 自分の投稿でタグを選び直して保存すると、一覧の表示がそのとおりに変わる
- [ ] 一覧でタグを1つ選ぶと、そのタグが付いた投稿だけが並ぶ。このとき、他人の下書きは出てこない
- [ ] 他人の投稿の編集画面をURLで直接開くと403になり、他人の投稿のタグは変えられない

**案を出させて選ぶところ**

タグを選ぶ操作をどこに置くかは、決めていません。投稿の編集画面に足す、コメントで作った投稿詳細に足す、一覧から直接付け替える、といった置き方があります。設計のときにAIへ案を出させて、そこから選んでください。比べる軸を一緒に渡すところは、14-5-1と同じです。選んだ理由は `docs/tagging.md` に1行書いておきます。

### ✏️ 進め方タスク

作業する場所は、これまでと同じアプリです。下書き機能がマージされた `main` から始めます。

```bash

cd ~/laravel-practice/post-app-practice
git switch main
git pull origin main

# Sail が止まっていたら起動する
./vendor/bin/sail up -d
```

持ち込む4つが手元にあるかを、ファイルの一覧で見ます。

```bash
# アプリのフォルダの中で実行する
ls CLAUDE.md .claude/settings.json .claude/agents/codebase-explorer.md .claude/skills/review-checklist/SKILL.md
```

```text

.claude/settings.json
.claude/skills/review-checklist/SKILL.md
CLAUDE.md
```

4行そろっていれば、持ち込むものはそろっています。`No such file or directory` と出たものがあれば、作った節へ戻ってください。

| どこにあるか | 何をしてくれるか | 作った節 |
|:--|:--|:--|
| `CLAUDE.md` | このアプリの前提を、依頼のたびに説明しなくてよくなる | 15-2-3 |
| `.claude/agents/codebase-explorer.md` | 調べものを、別のやり取りとして切り離して任せられる | 15-3-2 |
| `.claude/skills/review-checklist/SKILL.md` | 自分のレビュー観点を、毎回同じ順で当てられる | 15-3-3 |
| `.claude/settings.json` | 読まなくてよいと決めた承認が省ける／触らせたくないものが止まる／編集のたびにテストが回る | Chapter 4 |

確かめたら、Claude Codeを起動し直してから始めます。`.claude/` に置いたものは、起動したときに読み取られます（15-3-1）。

4つはChapter 2からChapter 4のうちに `main` へ入れてあるので、これから作る機能のプルリクエストに道具の差分は出てきません。道具を先に共有できる形にしておく、というのはこういうことです。

1. 【AI】機能イシューを `gh issue create` で立てさせる。上の受け入れ条件を本文に入れる
2. 【自分⇄AI】プランモードで設計させ、決まったことを `docs/tagging.md` にまとめさせる。タグを選ぶ操作の置き場所は案を出させて選ぶ
3. 【AI】ブランチを切らせ、実装の計画を出させる
4. 【自分】計画を読んで承認する
5. 【AI】実装させる。テストも一緒に書かせ、コミットして `gh pr create` まで通させる
6. 【自分】`/review-checklist` で下読みを当て、テストを回し、受け入れ条件と突き合わせる
7. 【AI】プルリクエストをマージさせる
8. 【自分】効き目を数えて、`docs/tagging.md` に書き足す

手を止めるのは、4番と6番の2箇所です。ほかは渡して構いません。8番で数える4つは「🏃 効き目を数える」に並べてあるので、始める前に見ておいてください。

イシューの番号は `#3` になる見込みです。画面に出ている番号が違っていたら、そちらに読み替えてください。

**テーブルを作る順**

タグそのものを入れるテーブルと、投稿とタグをつなぐテーブルの2つが増えます。つなぐほうは、両方ができてからでないと作れません。9-5-5でも、同じ理由で作る順が決まっていました。つなぐテーブルの名前の付け方（2つのテーブル名を単数形にして、アルファベット順につなぐ）は9-5-2のとおりです。

テーブルが増えるので、データベースへの反映も要ります。

```bash
# アプリのフォルダの中で実行する
./vendor/bin/sail artisan migrate
```

**もとの4件を消さない**

タグのデータは、`database/seeders/DatabaseSeeder.php` に直接書かせず、シーダーのクラスを1つ作らせて、そこへ入れさせてください。流すときも、そのクラスだけを名指しします。

```bash
# アプリのフォルダの中で実行する
./vendor/bin/sail artisan db:seed --class=TagSeeder
```

クラス名は、自分が作ったものに読み替えます。`./vendor/bin/sail artisan db:seed` とだけ打つと `DatabaseSeeder` が丸ごと動いて、同じユーザーと投稿がもう一度入ります（9-3-5）。

**ER図の範囲を切る**

`docs/tagging.md` にER図を描かせるときは、出す範囲を自分で指定します。指定しないと、アプリ全体の図が返ってきて、今回どこが増えたのかを読み取れません。

```text
ER図はMermaidの erDiagram で、posts と、今回足す2つのテーブルだけを描いてください。
いまあるほかのテーブルは、今回の図に出さないでください。
```

**設計書を書かせているあいだ、返事が遅い**

Chapter 4で仕掛けたフックは、Markdownを書き換えたときにも回ります。1ファイル書かせるたびにテストが流れるので、返事までに間が空きます。止まったように見えても、待ってください。

**AIから質問が返ってきたとき**

まだ決めていないことです。答えを探しにいく前に、自分で決めてください。決めたら `docs/tagging.md` に書き足してから、続きを頼みます。

## 🏃 効き目を数える

マージまで終わったら、持ち込んだ4つが何をしてくれたのかを、数えて書き出します。

| 数えるもの | どこを見るか |
|:--|:--|
| 書かずに済んだ前提 | `CLAUDE.md` に書いた行と、今回自分が打った依頼文 |
| 押さずに済んだ承認 | テストを実行したとき、承認画面が出なかったか（`.claude/settings.json` の `allow` に書いた形です） |
| 機械が先に知らせたテストの失敗 | 自分で打つ前に知らされた回数 |
| 言わずに守られた決まり／守られなかった決まり | `CLAUDE.md` の行ごとに、出てきたコードと見比べる |

書き出す先は `docs/tagging.md` の末尾です。`## ハーネスの効き目` という見出しを作って、そこへ入れます。

効かなかったものが、次に直す場所です。うまくいかなかった場面が出てきたら、毎回の依頼に言葉を足しても、次の機能でまた同じことを言うことになります。直すのは、書いてあるほうです。`CLAUDE.md` を直した場合は、その1行もここで一緒に記録します。

機能のマージはもう済んでいるので、`main` に直接記録します。

```bash
# アプリのフォルダの中で実行する
git add docs CLAUDE.md
git commit -m "タグ機能の設計書にハーネスの効き目を追記"
git push origin main
```

`CLAUDE.md` を直していなければ、記録されるのは `docs` だけです。

## 📖 進行例

> 💡 **進行例について**: AIとの開発は毎回違う流れになります。ここに示すのは一つの進行例です。あなたの画面と違っていても、チェックリストを満たしていれば正解です。

**1. 置き場所の案を出させて、1つ選ぶ**

設計の途中で、タグを選ぶ操作の置き場所を聞きました。返ってきたのは、投稿の編集画面に項目を足す案、投稿詳細に付け替えの操作を置く案、一覧のカードから直接付け替える案の3つです。

選んだのは編集画面です。投稿の中身を直す操作がすでにそこにまとまっていて、項目を1つ足すだけで済むためです。この理由を `docs/tagging.md` に1行足しました。

**2. 設計を頼むとき、アプリの説明を1行も書かなかった**

このアプリがLaravelをSailで動かしていること、いまどの機能が入っているか、設計書をどこへ置くか。Tutorial 14のあいだ、依頼のたびに書き直していた3つです。今回は1度も書きませんでした。

**3. どこに足すかは、担当に調べさせた**

編集画面と一覧がどのファイルでできているかを、名指しして調べさせました。

```text
@agent-codebase-explorer 投稿の編集画面と投稿一覧が、どのファイルで組み立てられているかを調べてください。
一覧を出しているコントローラーのメソッド、一覧のBladeファイル、編集画面のフォームのBladeファイルの3つを、
ファイル名と、根拠になる行と一緒に教えてください。
```

> 💡 このお願いのポイントは2つです。①調べてほしいものを3つに絞っている ②根拠になる行まで出させている。②があると、返ってきた答えを自分でファイルを開いて確かめられます。文言をそのまま覚える必要はありません。

返ってきた3つを自分で開いて、その行があることを確かめました。調べているあいだの読み込みは、こちらのやり取りには積まれていません（15-3-2）。そのまま設計の依頼に移れました。

**4. テストが落ちたことを、先に知らされた**

絞り込みを実装させている最中に、テストが落ちたと伝わってきました。落ちたのは、下書き機能のときに書いた「他人の下書きが一覧に出てこない」テストです。タグの条件を足したときに、公開済みと自分の下書きに絞る条件のほうが外れていました。

自分で打つ前に分かったので、そのまま直させました。`CLAUDE.md` の「テストが落ちた状態で作業を終えないでください。」の行が、ここで効いています。

**5. 下読みで2件挙がった**

`/review-checklist` を打つと、2件挙がりました。1件は、一覧で投稿ごとにタグを取りに行っている、というものです。9-5-3で見たN+1なので、これは直させました。

もう1件は、タグの並び順が決まっていない、というものでした。設計書に並び順を書いていないので、コードの側の話ではありません。`docs/tagging.md` に「並び順は決めていない」と1行足して、コードはそのままにしました。

**6. 書いてあるほうを直す**

`CLAUDE.md` に自分で書いた行のうち、1つが守られていませんでした。タグを4つ選んだときのエラーメッセージが、決めておいた形になっていません。

その場で頼めば直りますが、それでは次の機能でも同じことを言うことになります。そこで `CLAUDE.md` の側を書き直しました。守られなかった理由は、どこを見ればその形になるのかを書いていなかったことです。直した1行は、効き目のメモと一緒に `main` へ記録しました。

## 🚀 まとめ

- 同じ流れをもう一度回しました。変わったのは順番ではありません。毎回手でやっていたことが、手元の外へ移りました。
- 前提・観点・承認・テストの4つは、置き場所を決めた時点で、次の機能にも効きました。Chapter 1で決めた「同じ説明を二度としない」が、ここで形になっています。
- 効かなかった決まりは、数えてみて初めて見つかります。見つかったら、直す先は依頼文ではなく、書いてあるほうです。
- やり方が一人の頭の中にしかない状態を、属人化と呼びます。手順をリポジトリに置いた時点で、来月このアプリを触る自分も、`/clear` した次のやり取りのAIも、同じ手順を使えます。
