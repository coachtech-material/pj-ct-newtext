# 15-5-2: 書く役と受け取る役を分ける

## 🎯 このセクションで学ぶこと

- 書いたセッションに受け取りをさせない理由を理解し、2つのセッションに役を割り振れるようになる。
- 受け取る側で当てるものを、公式のものと自分で作ったものを重ねる形で組み立てられるようになる。
- 判定に落ちたとき、どちらの場所を直すかを判断できるようになる。

---

## 導入

15-5-1で場所を2つに分けた時点で、セッションも2つになっています。あとは、どちらに何をさせるかです。ここを決めずに両方へ同じことを頼むと、書いたセッションが自分の書いたものを見に行くことになり、受け取りの意味が薄くなります。

---

## 書く役と受け取る役

1つの機能を、コードを書くセッションと、受け取って判定するセッションに分ける進め方です。書く役は書く場所（worktree）のセッション、受け取る役は検証する場所のセッションが持ちます。

分ける理由は、コンテキストにあります。実装したセッションには、そのとき決めたことと、そのとき置いた前提が全部積まれています。同じセッションに「合っているか見て」と頼むと、判定の材料もその積み上がった前提から取ります。受け取る役のセッションには、それが無いところから始まります。手元にあるのは、届いたコードと、イシューに書いた受け入れ条件だけです。15-3-3で見た、確かめる仕事は別のコンテキストへ切り出すという線を、セッション1つぶんに広げた形です。同じ考え方は公式の道具にも入っていて、`/code-review` は自分のコンテキストを持つ担当として裏で走ります（14-4-2）。

| 役 | 場所 | すること |
|:--|:--|:--|
| 書く役 | 書く場所（worktree） | コードとテストを書く。テストは書くだけで、実行はしない。コミットしてpushする |
| 受け取る役 | 検証する場所（元のフォルダ） | ブランチを受け取り、テストを回し、レビューとUATを当て、受け入れ条件で判定し、プルリクエストを出してマージする |

自分の位置は1周目と変わりません。何を作るか・どうなったら完成か・受け取るかどうかを決めるのは、どちらのセッションでもなく、あなたです（14-1-1）。増えたのは、その決めごとを渡す相手が2つになったことだけです。

---

## 受け取る側で当てるもの

受け取る役は、次のものを順に当てます。

| 当てるもの | 何を見るか | 出どころ |
|:--|:--|:--|
| テスト | 書かれたテストが全部通るか | AIが書いたもの |
| `/code-review` | 間違いと、整理できるところ | Claude Code同梱 |
| `/review-diff` | このアプリの受け取り手順で差分を読む | 15-3-2で自分が作った |
| `/uat` | 受け入れ条件を1行ずつ画面で確かめる | 15-3-4で自分が作った |
| 自分の目 | 判定が割れた行、条件の書きぶりでは決まらないところ | あなた |

公式のものと自分で作ったものは、どちらかを選ぶものではありません。**役割が違うので重ねて当てます**。`/code-review` が見るのはどのプロジェクトでも同じ間違いと整理で、このアプリの受け入れ条件が何かは知りません。`/review-diff` が持っているのは逆で、突き合わせる相手と読む順番は知っていますが、一般的なバグの探し方は書いていません。

`/code-review` を受け取る側で回すときは、見る範囲を後ろに足します。

```text
/code-review main...worktree-like
```

素の `/code-review` が見るのは、いまいるブランチが上流より先に進んでいるぶんと、まだコミットしていない変更です（14-4-2）。受け取ったブランチはpushされたところと同じ位置にいるので、素のままだと見るものがありません。`main...worktree-like` と足すと、`main` からこのブランチまでの差を見ます。

`/review-diff` にも、同じ範囲を言葉で伝えます。15-3-2で当てたときはマージ済みのプルリクエストの番号を渡しましたが、受け取る役が当てるのはプルリクエストを出すより前なので、番号ではまだ呼べません。突き合わせ先のイシューの番号も、このとき一緒に渡します。

## 判定に落ちたとき

受け入れ条件のどれかが落ちたら、**直すのは書く場所です**。受け取る役はその場で直しません。落ちた行と、画面で何が起きたかを書いて返します。Keepしてある書く場所を開き直して直させ、もう一度pushして、受け取る役がもう一度受け取ります。

書いたものをその場で直すと、直した内容は受け取る役のセッションにしか残りません。書く場所には古いままのコードが残り、次にそこで直させたときに、直したはずのものが戻ります。1周目に「通るまで直して」で閉じていた輪は、2つに分かれても、書く側で閉じます。

同じファイルを2本の作業が触っていて、マージのときにぶつかったら、解消はAIに頼めます。出てきた差分を読むのは、これまでと同じで自分です。

## 🏃 いいね機能を、2つのセッションで通す

作るのは、タイムラインのポストにいいねを付けられる機能です。テーブルが1本増えます。

**受け入れ条件**

- [ ] タイムラインのポストそれぞれに、いいねのボタンと、いまのいいねの数が出ている
- [ ] いいねしていないポストのボタンを押すと、数が1つ増えて、押した状態の見た目に変わる
- [ ] 押した状態のボタンをもう一度押すと、数が1つ減って、押していない見た目に戻る
- [ ] 別のアカウントでログインし直すと、そのアカウントが押していないポストは、押していない見た目のまま、数だけが増えている

**変えないもの**

タイムラインの一覧・編集・削除、リプライ、ポスト作成、編集画面の文字数制限、「編集済み」の目印は、いまの動きのままです。

設計書は作りません。突き合わせる相手はイシューの受け入れ条件です。設計書が無い件では、イシューの受け入れ条件を突き合わせ先にする、という1行を `/review-diff` に足してあります（15-3-2）。ここがその1行の初めての出番です。

思いどおりに直らない・壊れたと感じたら14-5-1（直らないときの型）へ。まだコミットしていない変更は `git restore .`（4-3-5）で戻せます。

### Step 1: 検証する場所でイシューを立てる

イシューは、書く場所を作る前に、検証する場所で立てます。

```bash
# 投稿アプリのフォルダで実行する
git switch main
git pull origin main
./vendor/bin/sail up -d
claude
```

上の受け入れ条件4行を渡して、起票させます（14-3-3）。番号は画面に出たものを覚えておいてください。

### Step 2: 書く場所を作って、実装させる

別のターミナル（またはタブ）を開いて、投稿アプリのフォルダで打ちます。

```bash
# 投稿アプリのフォルダで実行する
claude -w like
```

```text
イシュー #<番号> のいいね機能を作って。

- 受け入れ条件の4行を満たすところまで
- タイムラインの今の動き（一覧・編集・削除）とリプライ、ポスト作成は変えない
- 「編集済み」の目印も変えない

テストは書くだけにして、実行はしないで。実行はこのあと別の場所でやります。
できたらコミットして、このブランチを push して。
```

このアプリの前提も、テストを書くことも、書き添えていません。どちらも `CLAUDE.md` とルールに入っているからです。ここで書き足したのは、この件でしか言えないことだけです。

書き終わったら `/exit` で閉じて、**1 の Keep** を選びます。

### Step 3: 受け取る

最初のターミナルへ戻ります。

```bash
# 投稿アプリのフォルダで実行する
git fetch origin
git switch -c receive-like origin/worktree-like
./vendor/bin/sail artisan migrate
./vendor/bin/sail artisan test
```

テーブルが増えたので、受け取ったあとに `migrate` が要ります。書く場所ではデータベースをさわれないので、この1回がブラウザで動かすための最初の準備になります。

### Step 4: レビューとUATを当てる

検証する場所のセッションで、順に当てます。

```text
/code-review main...worktree-like
```

```text
/review-diff main...worktree-like の差分を、イシュー #<番号> の受け入れ条件と突き合わせて見て
```

```text
/uat 次の4行を確かめて。

- タイムラインのポストそれぞれに、いいねのボタンと、いまのいいねの数が出ている
- いいねしていないポストのボタンを押すと、数が1つ増えて、押した状態の見た目に変わる
- 押した状態のボタンをもう一度押すと、数が1つ減って、押していない見た目に戻る
- 別のアカウントでログインし直すと、そのアカウントが押していないポストは、押していない見た目のまま、数だけが増えている
```

`/uat` に渡すのは、確かめる受け入れ条件そのものか、それが書いてあるファイルの場所です（15-3-4）。この件では設計書を作っていないので、開いて読ませるファイルがありません。イシューに書いた4行を、そのまま渡します。

`/code-review` は裏で走るので、届くまでのあいだに `/review-diff` を頼んで構いません。届いた指摘は、直すものと直さないものに分けます（14-4-2）。直すものがあれば、Step 2の書く場所へ戻します。

### Step 5: 4行目を自分の目で確かめる

`/uat` の判定が返ったら、4行目だけは自分でも触ります。ここは2つのアカウントを行き来しないと確かめられない行で（14-4-3）、片方のアカウントだけを見ていると通ったように見えます。`usera@example.com` でいくつか押してから、`userb@example.com` でログインし直して、数だけが増えていて、ボタンは押していない見た目のままであることを見ます。

### Step 6: プルリクエストを出して、マージして、片づける

```text
worktree-like から main へのプルリクエストを出して。
本文には、テストの結果と、受け入れ条件4行の判定を入れて。
最後に Closes #<イシューの番号> を。
```

本文を読んでからマージし、片づけます（15-5-1）。

```bash

git switch main
git pull origin main
git worktree remove .claude/worktrees/like
git branch -d worktree-like receive-like
```

## ✨ まとめ

- 書く役は書く場所、受け取る役は検証する場所。受け取る役は、届いたコードとイシューの受け入れ条件だけを材料に判定する。
- 受け取る側では、公式のものと自分で作ったものを重ねて当てる。`/code-review` は一般の間違い、`/review-diff` はこのアプリの突き合わせ、`/uat` は受け入れ条件、最後に自分の目。
- 受け取る側では、`/code-review` にも `/review-diff` にも `main...worktree-<名前>` の範囲を渡す。プルリクエストはまだ無く、素の `/code-review` では見るものがない。
- 落ちた行は、書く場所へ戻して直させる。受け取る側で直すと、書く場所に古いコードが残る。
- テーブルが増えた件では、受け取ったあとに `migrate` を打ってからブラウザで確かめる。
