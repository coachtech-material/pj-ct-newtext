# 15-5-4: 広がる道具と、変わらない原則

## 🎯 このセクションで学ぶこと

- 開発フローのどの段に何が付いたのかを、自分の言葉で説明できるようになる。
- この先に広がる道具の名前と、それが何をするものかを知る。
- 使っているものが変わったときに、どこを見に行けばよいかを判断できるようになる。

---

## 導入

Tutorial 14では、1周を回すたびに同じことを手で運んでいました。Tutorial 15では、その運び先を1つずつ決めてきました。ここで一度、どこに何が付いたのかを並べておきます。並べておかないと、この先で新しい道具の名前を聞いたときに、自分に足りないものがどこなのかを言えません。

---

## 1周の各段に付いたもの

Issue化 → 計画 → 実装とテスト → レビュー → UAT → PR の6段と、そのあいだに挟まる承認と回し方です。

| 段 | Tutorial 14で毎回手でやっていたこと | いまの状態 |
|:--|:--|:--|
| Issue化 | 受け入れ条件の書き方と日本語で出すことを、毎回依頼文で指定した | `/issue`（15-5-3） |
| 計画 | 持ち方を選んだ | **仕組み化しない**。なし・planモード・設計書から選ぶのは人（14-3-1） |
| 実装とテスト | テストの句を毎回書き添えた | `CLAUDE.md` とルールの決まり（Chapter 2）＋Hooksが必ず回す（Chapter 4） |
| レビュー | 読む観点をその場で組み立てた | `/code-review`（同梱）＋`/review-diff`（このアプリの物差し・15-3-2） |
| UAT | 受け入れ条件を2回貼り直した | `/uat`（15-3-4） |
| PR | 証拠を本文に入れることを毎回頼んだ | `CLAUDE.md` の決まりに昇格。作るのはAI |
| （承認） | 毎回押した | 許可の指定（15-4-1）。外へ出ていくものは、聞かれたまま残した |
| （回し方） | 1本ずつ直列 | worktreeで書く場所を増やし、受け取りは1か所（15-5-1〜15-5-3） |

計画の行だけ、いまも人の手元に残っています。何を作るかと、それをどの寿命の計画で持つかを選ぶのは、14-1-1で分けた「決める」側の仕事だからです。判断そのものは仕組みへ移しません。

---

## ここから先の道具

いま使えるようになる必要はありません。名前と、何をするものかだけを知っておいてください。

**対話しないで動かす（`-p`）**

`claude -p "依頼"` は、対話の画面を開かずに1回ぶんだけ動かす形です。標準入力と標準出力が普通のコマンドと同じように使えるので、ほかのコマンドとつなげられます。

```bash
git log --oneline -20 | claude -p "最近のコミットを要約して"
```

CIの中で動かす、コミットの前に確認を挟む、たくさんのファイルをまとめて処理する、といった使い道です。

**決まった時刻に回す**

毎朝プルリクエストを見る、毎週依存を点検する、といった繰り返しを自動で回す方法は、どこで動かしたいかで分かれます（2026年8月時点）。

| 選び方 | どこで動くか |
|:--|:--|
| Routines | クラウド。自分のパソコンが止まっていても動いてほしいとき |
| デスクトップアプリの予定実行 | 自分のパソコン。手元のファイルやコミットしていない変更が要るとき |
| GitHub Actions | GitHubの上で自動的に走らせる（CI）。リポジトリで起きたことに合わせたいとき |
| `/loop` | いま開いているセッションの中。開いているあいだだけ様子を見たいとき |

このうちGitHub Actionsは、時刻だけでなく、リポジトリで起きたことにも反応させられます。入れておくと、イシューやプルリクエストのコメントに `@claude` と書くだけで、そこから作業を始めて、同じ場所に結果を返してきます。入口はセッションの中で打つ `/install-github-app` です。Proの契約でも、`claude setup-token` で作ったトークンを登録すれば動きます。使った分は手元で使うのと同じ枠から減り、GitHub Actions側の実行時間も消費します（2026年8月時点）。

**手元の外にあるセッション**

`claude --cloud "依頼"` は、claude.ai の上に新しいセッションを作ります。`claude --teleport` は、そちらで動いているセッションを手元のターミナルに引き取って続けます。

**エージェントチーム**

複数のClaude Codeのセッションをまとめて動かす仕組みです。worktreeが分けるのはファイルで、こちらが合わせるのは仕事の中身のほうです。

このほかに、名前だけ挙げておくものがあります。Agent SDKは、プログラムからClaude Codeを呼ぶための開発キットです。Enterpriseには、組織単位で設定を配る仕組みがあります（2026年8月時点）。どちらも公式ドキュメントに専用のページがあるので、必要になったら名前で引いてください。

**MCPとプラグイン**

どちらも、この教材でもう入れています。MCPは14-4-4で入れたPlaywrightが、外のツールにつなぐ口でした。プラグインは15-3-2で入れたskill-creatorが、Skillをまとめて配る形でした。この2つは、名前を聞いて終わりの道具ではありません。いま手元で動いています。置き場所と管理のしかたは15-3-5にまとめてあります。

## 道具が変わっても、変わらないもの

新しく出てきたものを見たときに、これは何のための道具なのかを判断する基準が要ります。基準になるのは、どれもTutorial 14とTutorial 15で自分の手を動かしたことばかりで、新しく覚えることはありません。

### コンテキストを与える

14-5-2で見たとおり、AIが一度に読み取れる量には限りがあります。この限られた量に何を載せるかが、返ってくるものの質を決めます。

Chapter 2で `CLAUDE.md` に前提を書いたのも、15-3-3で調べものを別の担当に出したのも、この量の使い方を決める作業でした。前者は、毎回必ず載せておきたいものを、セッションの外に置く形です。後者は、載せたくないもの（調べている途中の読み込み）を、別のやり取りへ追い出す形です。向きは逆ですが、決めているのは同じことです。

新しい道具に出会ったときは、まずここを見てください。それを入れると、毎回読み込まれるものが増えるのか、減るのか。増えるほうの道具は、入れる理由がはっきりしているときだけにします。

### 小さく回す

14-3-2では、実装の前に計画を出させ、読んでから承認しました。14-5-1では、頼む単位を分け直す目安を持ち、2回直らなければ仕切り直すと決めました。どちらも、頼む単位を小さくして、確かめる間隔を短くするための決めごとです。

まとめて頼んでまとめて受け取ると、確かめる場所が最後の1回しかありません。そこで落ちると、どこで道を外れたのかを探すところから始まります。

### 検証を組み込んで、輪を閉じる

15-1-3で見たとおり、Tutorial 14では、依頼のたびに書き添えていた1行が、書く・回す・直す・報告するという輪を作っていました。その輪を、依頼文に書かなくても回るようにしたのが、Chapter 4で書いたフックの1行です。15-5-3では、機械が先に知らせてきた回数を数えました。

公式のベストプラクティスも、依頼の最後に、その機能が動くことを示す確認の手順を置くよう書いています。渡すのはテストでも、動かして見せる手順でも、画面の写真でも構いません。

新しい道具を見たときの質問も、ここから出てきます。それを入れると、機械が判定できることが増えるのか。増えないなら、その道具は輪を閉じる側の道具ではありません。

## 一次情報の見に行き方

コマンドも画面も、この教材が書かれたあとに変わります。変わったときに、自分で見に行ける場所を持っておいてください。入口は `https://code.claude.com/docs/` で、使い方の指針は Best practices のページにまとまっています（2026年8月時点）。

もう1つ、手っ取り早い方法があります。Claude Codeは自分のドキュメントを見に行けます。使っているものが新しくても古くても、いまのやり方を聞けば答えられる、と公式に書かれています。試しに1度、自分のClaude Codeで打ってみてください。

```text
いまのバージョンで、Hooksの設定はどこに書きますか。公式ドキュメントの場所も教えてください。
```

「いまのバージョンで」と書いてあるので、手元のもので答えます。場所も一緒に聞いているので、返ってきた答えを自分で開いて確かめられます。場所の書かれていない答えは、そこから先へ進めません。動く例つきで教わりたいときは、`/powerup` でレッスンが開きます。

ドキュメントを引くこと自体を、道具に任せる手もあります。公式ドキュメントを全文検索できるMCPサーバーが配られていて、サインインもトークンも要りません（15-3-5）。足しておくと、上のような質問に、Claude Codeが自分でドキュメントを検索して答えるようになります。

**変わったところを見る**

何がいつ変わったのかは、リリースの記録に日付の順で並んでいます。入口は `https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md` です（2026年8月時点）。手元の版が上がったあとにここを開くと、増えたものと変わったものが分かります。

## 人がどう使っているかを見る

ドキュメントに載るのは、道具に何ができるかまでです。それを実際にどう組み合わせているかは、使っている人の書いたもののほうに早く出てきます。この教材で作ったHooksやSkillも、ほかの人はまったく違うものを入れています。

Xには、Anthropicの公式アカウント（`@AnthropicAI`）と、Claudeの公式アカウント（`@claudeai`）があります。新しいものが出たときは、まずここに出ます。

そこから先の探し方は決まっています。公式が出した機能の名前でXを検索して、それを実際に使って書いている人を見つけ、その人を追います。腰を据えて読むものではありません。手が空いたときに眺めて、「そんな使い方があるのか」を1つ拾えれば十分です。

> ⚠️ **注意**: 実在しないコマンドや設定を、それらしく紹介している記事もあります。見かけたものを打つ前に、`/help` と公式ドキュメントで確かめてください。AIが答えたコマンドについても同じです。

### いちばん効くのは、回した回数

Anthropicが約40万セッションを分析した調査（`https://www.anthropic.com/research/claude-code-expertise`・2026年）では、依頼が検証済みの成功に至った割合は、初心者で15%、中級以上で28〜33%でした。差が付いていたのは、知っている機能の数ではありません。指示の枠の付け方、何を検証させるかの指定、うまくいかないときの直し方の3つです。

どれも、Tutorial 14とTutorial 15で手を動かしたことです。そして、読んで覚えるものではありません。自分の依頼が空振りして、直して、通るところまでを何度か通ったぶんだけ身につきます。だから、新しい道具を追いかけるより先に、自分のプロジェクトで1周多く回すほうが効きます。

## 💡 よくある間違い

**道具から先に増やす**

受け入れ条件を書かずに道具だけ入れても、道具は決めていないことを決めてくれません。

**「同時に動かせば速くなる」と考える**

書く場所を2つに増やしても、読んで確かめる量は変わりません。速く終わる前提で予定を立てるときに、確かめる時間まで一緒に短くしないでください。

**開いたページの場所を、そのまま覚える**

前に開いた場所を開き直して、たどり着けないところで手が止まります。ページが消えたのではなく、移っただけのことがほとんどなので、入口から辿り直してください。

## ✨ まとめ

- フローの各段には、置き場所が決まった道具が付きました。残っているのは計画の行で、そこは人が選び続けます。
- この先に広がるのは、対話しないで動かす形、決まった時刻に回す形、手元の外にあるセッション、複数のセッションをまとめる形です。名前と用途だけ知っておけば足ります。
- 道具が増えても、見る基準は3つに戻ります。コンテキストを与える、小さく回す、検証を組み込んで輪を閉じる。
- 新しい道具を見たときは、毎回読み込まれるものが増えるのか、機械が判定できることが増えるのかを聞いてください。
- 手順は変わります。覚えるのは、どこを見に行けばよいかです。Claude Code自身にも聞けます。
- 変わったところはリリースの記録で、人がどう使っているかはXで拾えます。ただし、いちばん効くのは自分で1周多く回すことです。

これでTutorial 15は終わりです。毎回手でやっていたことに置き場所を決めて、その仕組みごと機能を何本も作り切りました。置いた道具は、次に自分が触るプロジェクトでも、同じ手順で作れます。

次のTutorial 16では、ここまでに身につけたものを持ち寄って、アプリを1本作り上げます。
