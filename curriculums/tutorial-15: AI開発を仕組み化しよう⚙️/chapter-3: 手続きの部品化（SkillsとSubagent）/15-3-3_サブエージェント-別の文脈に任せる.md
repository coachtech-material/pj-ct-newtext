# 15-3-3: サブエージェント - 別の文脈に任せる

## 🎯 このセクションで学ぶこと

- 調べものを別のコンテキストに切り出すと何が変わるのかを、3つに分けて説明できる。
- 読むための道具だけを渡した調査役を作って、名前で呼び出せるようになる。
- Skill・サブエージェント・MCPの違いを見分けられるようになる。

---

## 導入

14-5-2で、`app` フォルダのPHPファイルを全部読ませてから `/context` を打ちました。読ませたファイルの分だけ、使用量が増えていました。

調べものは、いつもこの形をしています。「この決まりはどこで決まっていますか」の答えが3行でも、そこへたどり着くまでに10ファイル開いていることがあります。開かれたファイルの中身は、そのままあなたのコンテキストに積まれます。答えは3行しか要らないのに、10ファイル分が残り、そのあとの実装の依頼は、狭くなったところから始まります。

---

## サブエージェントとは

サブエージェントは、決めた仕事だけを、別のコンテキストで引き受ける担当です。調べものをこの担当に出すと、ファイルを開いて読むのは向こうのコンテキストで、こちらに返ってくるのは報告だけになります。開いた10ファイルの中身は、あなたのコンテキストには積まれません。

実物は、もう見ています。14-4-2で `/code-review` を送ったとき、`Running in the background as @code-review` と出ました。あれが、別の担当が別のコンテキストで動いていた表示です。

返ってくるのが報告だけということは、報告に書かれていないことは、こちらに何も残らないということでもあります。ですから、**何を根拠にそう言えるのか**まで報告に含めさせます。どういう形で返してほしいかは、担当を作るときに書いておきます。

---

## 任せると何が変わるか

| 変わること | 中身 |
|:--|:--|
| コンテキストが減る | 開いたファイルは向こうに積まれ、こちらに返るのは報告だけ |
| 触れる範囲を決められる | 使ってよい道具を指定できる。渡さなかった道具は、頼まれても使えない |
| 同時に動かせる | 別のコンテキストで動くので、担当を何人か立てて並行させられる |

3つ目は、たとえば「テストが落ちている原因」と「同じ書き方をしている場所」を、別々の担当に同時に調べさせる形です。1つのセッションで順番に聞くより早く終わり、どちらが開いたファイルも、こちらには積まれません。

呼び方は、Skillと同じで2つあります（15-3-1）。`@agent-` に名前を続けて指名する道と、`description` を読んだClaudeが自分で回す道です。指名すれば、確実にその担当が動きます。

---

## 渡す道具の指定

サブエージェントには、使ってよい道具を指定できます。これから作る調査担当に渡すのは、次の3つだけです。

| 道具 | できること |
|:--|:--|
| `Read` | ファイルを開いて読む |
| `Grep` | ファイルの中身から文字列を探す |
| `Glob` | ファイル名で探す |

どれも読むための道具です。書き換えるための道具を渡していないので、この担当は、頼まれてもコードを書き換えられません。「読むだけにしてください」とお願いする形ではなく、書き換えられない状態にしてから渡す形です。

> ⚠️ **注意**: 読み取り専用の担当に書き換えを頼んでも、書き換わりません。ただし、あなたが話しているセッション本体は書けます。「代わりにやりましょうか」と言われたら、そこが判断の場所です。

## 定義ファイルの形

担当1人につき、ファイル1枚です。置き場所は `.claude/agents/` で、今回は `codebase-explorer` という名前にするので `.claude/agents/codebase-explorer.md` になります。先頭を `---` で挟む書き方は、`SKILL.md`（15-3-1）と同じです。

```markdown
---
name: codebase-explorer
description: このアプリのコードを読んで、聞かれたことに根拠つきで答える調査担当。どこに何が書いてあるかを知りたいときに使う。コードの書き換えはしない。
tools: Read, Grep, Glob
---
```

| 項目 | 書くもの |
|:--|:--|
| `name` | 担当の名前。小文字とハイフンで付けます。呼ぶときにこの名前を使います |
| `description` | どういうときにこの担当へ回すか |
| `tools` | 使ってよい道具。書かないと、**あなたのセッションが使える道具を全部引き継ぎます** |

置き場所は、Skillと同じ考え方です。`.claude/agents/` に置けばこのリポジトリだけ、`~/.claude/agents/` に置けば自分のPCで開くどのプロジェクトでも呼べます。これから作る調査担当はこのアプリのコードを読む役なので、リポジトリの中に置きます。

`---` から下は、この担当への指示書です。ここに、調べ方と、報告のしかたを書きます。書かせるのは次の内容です。

- 関係のありそうなファイルを探し、実際に開いて、書いてあるとおりに読む
- 書かれていないことは「書かれていません」と答える。推測で埋めない
- 答えを最初に1〜3行、そのあとに根拠を「ファイル名:行番号」とその行の中身で示す
- 確かめられなかったことがあれば、最後に分けて書く

推測で埋めさせないと決めているのは、書かれていないと分かったことも、こちらにとっては情報だからです。場所まで書かせているのは、返ってきた答えを自分で開けるようにするためです。場所の無い報告は、そこから先へ進めません。

## 手順の部品と、担当と、外への接続口

`.claude/` に置くものが増えてきたので、ここで並べます。

| 何を足すか | どこで動くか | 何が返るか |
|:--|:--|:--|
| Skill | いまのコンテキストの中。書いてある手順がそのまま足される | 手順を実行した結果 |
| サブエージェント | 別のコンテキスト。渡す道具を選べる | 報告だけ |
| MCPサーバ | 外にある別のプログラム（14-4-4） | そのプログラムができること |

調べものを任せるときにいちばん効くのが、この道具の絞り込みです。

### 確かめる側のコンテキスト

同じ形で、レビューを担当するサブエージェントも作れます。この教材では作りません。`/code-review` が既にその形で動いていて、汎用の間違い探しは公式に任せる、と15-3-1で線を引いたからです。

書いた側と確かめる側を分ける考え方は、担当だけの話ではありません。セッションそのものを2つに分ける形は、15-5-2で扱います。

## 🏃 調査役を作って、問いを投げる

投げる問いは、答えを自分が知っているものにします。作った担当が定義したとおりに動いたかどうかを、返ってきた報告だけで判定できるからです。

投稿アプリのフォルダでClaude Codeを起動します。

```bash
# 投稿アプリのフォルダで実行する
claude
```

### Step 1: 定義ファイルを作らせる

ファイルは自分で書きません。何が要るかを伝えて、書かせます。

```text
このリポジトリに調査担当のサブエージェントを作って。
.claude/agents/codebase-explorer.md に置いて。

- 使ってよい道具は Read, Grep, Glob の3つだけ
- このアプリのコードを読んで、聞かれた1つの問いに答える
- 書かれていないことは「書かれていません」と答える。推測で埋めない
- 報告は、答えを1〜3行 → 根拠を「ファイル名:行番号」とその行の中身、の順
- 確かめられなかったことは最後に分けて書く
- コードの書き換えはしない
```

以前は `/agents` という対話画面から作る道もありましたが、2026年8月時点では、こうしてClaudeに書かせるか、ファイルを直接置くかの2つになっています。

### Step 2: できたファイルを開いて確かめる

VS Codeで `.claude/agents/codebase-explorer.md` を開きます。見るのは名札の部分で、`tools` の行が `Read, Grep, Glob` の3つだけになっているかを確かめてください。ここに書き換え用の道具が混ざっていたら、その1行を自分で直します。

### Step 3: 起動し直す

`.claude/agents/` は、いまのセッションを始めた時点ではありませんでした。Skillのときと同じ決まりで、フォルダごと新しくできた場合は、そのセッションからは使えません。

```bash
# 投稿アプリのフォルダで実行する
claude
```

### Step 4: 名前を付けて問いを投げる

```text
@agent-codebase-explorer このアプリで「自分のポストだけ編集できる」という決まりは、
どのファイルのどこで判定されていますか。その行のコードも一緒に見せてください。
```

`@agent-` のあとに `name` を続けた形が、指名です。打っている最中はファイル名の候補が出ますが、そのまま送れば担当として届きます。

> 💡 **出力例について**: AIの応答は毎回変わります。以下はあくまで一例です。文言が違っても、チェックリストの項目を満たしていれば問題ありません。

```text
Claude Code: （調査担当が別のコンテキストで動き、終わると報告だけが返ってくる。
              答えが先に数行、そのあとに「ファイル名:行番号」とその行のコード。
              確かめられなかったことがあれば、最後に分けて書かれる）
```

見つからないと返ってきたときは、打った名前・ファイルの中の `name`・ファイルの置き場所の3つを見比べます。合っているなら、まだ起動し直せていません。

### Step 5: 報告を自分で開いて確かめる

報告に書かれたファイルを、VS Codeで開きます。`app/Policies/PostPolicy.php` は配られたときから手元にあるファイルで、10-3-5「認可機能 - ハンズオン演習」で読み方を学んだ形のままです。行番号がずれていても構いません。ファイル名と、その行の中身が合っているかを見ます。

### Step 6: 記録する

```text
.claude/agents をコミットして、main に push してください。
```

15-3-2と同じく、機能を作る作業ではないので、ブランチを切らずに `main` へ送ります。

思いどおりに直らない・壊れたと感じたら、14-5-1（直らないときの型）へ進んでください。まだコミットしていない変更は `git restore .`（4-3-5）で元に戻せます。

このセクションが終わった時点で、次の4つを確かめてください。

- [ ] `.claude/agents/codebase-explorer.md` ができていて、`tools` が `Read, Grep, Glob` の3つだけになっている
- [ ] 起動し直したあと、`@agent-codebase-explorer` を付けた問いに報告が返ってきた
- [ ] 報告が、答え → 根拠（ファイル名:行番号）の順になっている
- [ ] 報告に書かれたファイルを自分で開いて、示された行の中身がその付近にあることを確かめた

## 💡 よくある間違い

**道具の名前を打ち間違える**

道具の名前は英語で、先頭が大文字です。書いた名前が1つも道具として解決できないと、その担当は起動そのものに失敗します。

**何でも別の担当に投げる**

向いているのは、たくさん読むけれど返すのは短い仕事です。何度もやり取りしながら詰めていく仕事は、返ってくるのが報告だけなので、そのまま自分のセッションで進めたほうが速く済みます。

## ✨ まとめ

- サブエージェントは、決めた仕事を別のコンテキストで引き受ける担当。返ってくるのは報告だけなので、たくさん読んで短く返す調べものに向く。
- 任せると3つ変わる。こちらのコンテキストが減る、触れる範囲を道具で決められる、担当を並行させられる。
- 返るのが報告だけということは、根拠を書かせないと何も残らないということ。答え・根拠・確かめられなかったことの順で書かせる。
- 定義ファイルは `.claude/agents/<名前>.md` の1枚。`name`・`description`・`tools` を先頭に書く。`tools` を書かないと道具を全部引き継ぐ。
- 読むための道具だけを渡せば、頼まれても書き換えられない。お願いではなく、渡す道具で決める。
- 作り方は、要る条件を伝えてClaudeに書かせ、できた名札を自分で確かめる。`.claude/agents/` を初めて作ったセッションからは使えないので、起動し直す。
- 呼ぶときは `@agent-<名前>` で指名する。`description` を読んだClaudeが自分で回すこともある。
