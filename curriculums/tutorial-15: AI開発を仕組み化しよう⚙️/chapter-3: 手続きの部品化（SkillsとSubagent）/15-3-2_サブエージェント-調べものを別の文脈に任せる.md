# 15-3-2: サブエージェント - 調べものを別の文脈に任せる

## 🎯 このセクションで学ぶこと

- 調べものを別の担当に出す意味を説明できるようになる。
- 読むための道具だけを渡した担当を作って、名前で呼び出せるようになる。
- 手順を部品にするのと、担当者に任せるのとの違いを説明できるようになる。

---

## 導入：あの4つの問いは、全部あなたの机に積まれていた

14-1-3で、このアプリに4つの問いを投げました。あのとき「1つのセッションのまま、4問を続けて投げてください」と書いてありました。AIは答えるために `routes/web.php` を開き、`PostPolicy.php` を開いています。読んだファイルの中身は、そのままあなたのやり取りに積まれます。14-2-2では、それを作業机に書類を広げていく様子にたとえて、「あの程度なら、まだ机はがら空きです」と書きました。

がら空きでなくなるのは、調べる量が増えたときです。調べものの多くは、たくさん読むのに、返ってくる答えは短い仕事です。「この決まりはどこで決まっていますか」の答えが3行でも、そこへたどり着くまでに10ファイル開いていることがあります。答えは3行しか要らないのに、10ファイル分がやり取りに残ります。そのあとの実装の依頼は、そのぶん狭くなった状態で進みます。

15-1-3で並べた引き金の4行目は「調べものでコンテキストが埋まる」でした。固める先が、このセクションで作るものです。

---

## 別のところで調べて、報告だけを返す

サブエージェント（決めた仕事だけを、別のやり取りとして切り離して任せる担当）を作ると、調べものをその担当に出せます。

担当は、別のやり取りとしてファイルを開いて読みます。読み終えたら、こちらに返すのは報告だけです。開いた10ファイルの中身は、あなたのやり取りには積まれません。14-2-2で見た机の上に、調べものの途中経過まで積まないで済む、ということです。

返ってくるのが報告だけ、ということは、報告に書かれていないことは、こちらのやり取りには残らない、ということでもあります。ですから、**何を根拠にそう言えるのか**まで報告に含めさせます。どういう形で返してほしいかは、担当を作るときに書いておきます。

---

## 渡す道具を選べる

サブエージェントには、使ってよい道具を指定できます。これから作る調査担当に渡すのは、次の3つだけです。

| 道具 | できること |
|:--|:--|
| `Read` | ファイルを開いて読む |
| `Grep` | ファイルの中身から文字列を探す |
| `Glob` | ファイル名で探す |

どれも読むための道具です。書き換えるための道具を渡していないので、この担当は、頼まれてもコードを書き換えられません。「読むだけにしてください」とお願いするのではなく、書き換えられない状態にしてから渡す、という形です。

> ⚠️ **注意**: 読み取り専用の担当者に書き換えを頼んでも、書き換わりません。ただし、あなたが話しているセッション本体は書けます。「代わりにやりましょうか」と言われたら、そこが判断の場所です。

## 定義ファイルの形

担当1人につき、ファイル1枚です。置き場所は `.claude/agents/` で、ファイル名は `name` に付けた名前と同じにします。今回は `codebase-explorer` という名前にするので、ファイルは `.claude/agents/codebase-explorer.md` になります。中身は次のとおりです。

```markdown
---
name: codebase-explorer
description: このアプリのコードを読んで、聞かれたことに根拠つきで答える調査担当。どこに何が書いてあるかを知りたいときに使う。コードの書き換えはしない。
tools: Read, Grep, Glob
---

あなたはこのアプリの調査担当です。頼まれた1つの問いにだけ答えます。

## 調べ方

1. 関係のありそうなファイルを探す
2. 実際に開いて、書いてあるとおりに読む
3. 書かれていないことは「書かれていません」と答える。推測で埋めない

## 報告のしかた

1. **答え**を最初に1〜3行で書く
2. **根拠**を「ファイル名:行番号」と、その行の中身で示す
3. **確かめられなかったこと**があれば、最後に分けて書く

**あなたはファイルを書き換えません。** 調べて報告するところまでが仕事です。
```

先頭を `---` で挟む書き方は、15-3-1で見た `SKILL.md` と同じです。違うのは、`tools` の行が増えていることです。

`---` から下の本文は、この担当への指示書です。上から順に見ていきます。

- **調べ方の3つ目**を入れてあるのは、推測で埋めさせないためです。書かれていないと分かったことも、こちらにとっては情報になります。
- **報告のしかた**は、14-1-3で「どこを見てそう言えるのか」を一緒に出させたのと同じ形です。あのときは依頼のたびに自分で書いていました。ここでは担当の側に書いておくので、毎回書かなくてよくなります。
- **最後の1行**は、道具で止めたうえで、文章にも重ねて書いたものです。

---

## 名前で呼ぶ

作った担当は、依頼の先頭で名指しします。

```text
@agent-codebase-explorer （調べてほしいことを続けて書く）
```

`@agent-` のあとに `name` を続けた形です。調べものを外に出したいときは、毎回この形で指名します。

---

## 手順を部品にするのと、担当者に任せるのと

Skillは手順書です。呼び出すと、書いてある手順がいまのやり取りにそのまま足されます。サブエージェントは担当者です。別のところで作業して、こちらに返ってくるのは報告だけです。そしてサブエージェントには、渡す道具を選べます。読むための道具しか渡さなければ、書き換えは起きません。この「道具を絞れる」ところが、調べものを任せるときにいちばん効きます。

同じ形で、レビューを担当するサブエージェントも作れます。ただしこの教材では、レビューの観点は次のセクションでSkillとして持ちます。

## 🏃 調査役を作って、14-1-3の問いを投げ直す

> 🔥 ここからは、AIに実装を任せて構いません。ただし「任せる」と「丸投げ」は違います。何を作るかは設計書で自分が決め、出てきたものはテスト・動作確認・コードレビューで自分が検証します。品質の責任は、AIではなくあなたが握ります。

14-1-3のStep 2で投げた問いを、今度は調査担当に投げ直します。同じ問いを選ぶのは、答えを自分が知っているからです。14-1-3にも書いたとおり、答えを知っている問いを混ぜておくと、返ってくる説明の正確さを測れます。

### Step 1: 定義ファイルを作る

Claude Codeを起動したままなら、先に `/exit` で終了します。ターミナルに戻ったら、アプリのフォルダで次の2行を打ちます。

```bash
# アプリのフォルダの中で実行する
mkdir -p .claude/agents
touch .claude/agents/codebase-explorer.md
```

VS Codeで `.claude/agents/codebase-explorer.md` を開き、「定義ファイルの形」に載せた全文をそのまま貼り付けて、保存します。

### Step 2: 起動し直す

ファイルを保存したら、もう一度 `claude` と打って起動します。

```bash
# アプリのフォルダの中で実行する
claude
```

### Step 3: 名前を付けて問いを投げる

```text
@agent-codebase-explorer このアプリでは「自分の投稿だけ編集できる」という決まりがあります。
それはどのファイルのどの行で決まっているのか、その行のコードも一緒に見せてください。
```

> 💡 このお願いのポイントは、①答えを自分が知っている問いを選んでいる ②先頭で名前を出して指名している、の2点です。問いの文そのものは14-1-3と同じで構いません。

> 💡 **出力例について**: AIの応答は毎回変わります。以下はあくまで一例です。文言が違っても、チェックリストの項目を満たしていれば問題ありません。

```text
Claude Code: （調査担当が別のやり取りで動き、終わると報告だけが返ってくる。
              答えが先に数行、そのあとに「ファイル名:行番号」とその行のコード。
              確かめられなかったことがあれば、最後に分けて書かれる）
```

指名が届いていないときは、次のように返ります。

```text
⏺ 「codebase-explorer」という名前のエージェントは見つかりませんでした。
```

このときは、打った名前と、ファイル名・`name` の綴りを見比べます。3つとも合っているなら、まだ起動し直していないだけです。

### Step 4: 報告を自分で確かめる

報告に書かれたファイル名の場所を、VS Codeで開きます。10-3-5「認可機能 - ハンズオン演習」で自分の手で書いたコードなので、合っているかどうかは自分で判定できます。行番号がずれていても構いません。ファイル名と中身が合っているかを見ます。

### Step 5: コミットしてpushする

作った担当を記録します。`/exit` で終了して、ターミナルで次を打ちます。

```bash
# アプリのフォルダの中で実行する
git add .claude
git commit -m "Add codebase-explorer agent"
git push origin main
```

これは機能を作る作業ではないので、14-3-3で決めたブランチの単位（機能イシュー1件＝ブランチ1本）には当てはまりません。ブランチを切らずに `main` へ送ります。

このセクションが終わった時点で、次の4つを確かめてください。

- [ ] `.claude/agents/codebase-explorer.md` を作り、いったん終了して起動し直した
- [ ] `@agent-codebase-explorer` を付けて問いを投げ、答え → 根拠（ファイル名:行番号）の順で報告が返ってきたことを確かめた（確かめられなかったことがあれば、最後に分けて書かれます）
- [ ] 報告に書かれたファイルを自分で開いて、10-3-5で書いた `PostPolicy` と合っているかを判定した
- [ ] `.claude/agents/codebase-explorer.md` をコミットして `main` にpushした

## 💡 よくある間違い

**`tools` を書き忘れる**

書かないと、あなたのセッションが使える道具をそのまま引き継ぎます。調べるだけのつもりで作った担当が、コードを書き換えられる状態になります。渡すのは `Read, Grep, Glob` の3つだけ、と決めて書きます。

**道具の名前を打ち間違える**

道具の名前は英語で、先頭が大文字です。3つとも綴りを間違えると、道具が1つも無い状態になるので、起動そのものを断られます。やっかいなのは、1つだけ間違えたときです。断られないまま、間違えた道具だけが抜けた状態で動きます。

**名前を呼ばずに「調べておいて」と頼む**

名前を出さないと、いつもどおり自分のセッションで調べにいくことがあります。`@agent-codebase-explorer` を先頭に付けて指名します。

**何でも別の担当に投げる**

向いているのは、たくさん読むけれど返すのは短い仕事です。何度もやり取りしながら詰めていく仕事は、返ってくるのが報告だけなので、そのまま自分のセッションでやったほうが速く済みます。

> 💡 **TIP**: 定義ファイルをAIに書かせることもできます。その場合も `.claude/` へのファイル作成は承認を求められるので、中身を読んでから承認してください（14-1-4）。

## ✨ まとめ

- 調べものは、たくさん読むのに答えが短い仕事です。別の担当に出すと、読んだファイルの中身が自分のやり取りに積まれずに済みます。
- 担当には、使ってよい道具を指定できます。読むための道具しか渡さなければ、頼まれても書き換えられません。
- 定義ファイルは `.claude/agents/<名前>.md` の1枚です。`name`・`description`・`tools` を先頭に書き、本文に調べ方と報告のしかたを書きます。
- 返ってくるのは報告だけなので、根拠の示し方を担当の側に書いておきます。書かれていないことは「書かれていません」と答えさせるのも、ここに書きます。
- 呼ぶときは `@agent-<名前>` で指名します。

調べものは、別の担当に出せるようになりました。次は、毎回同じ順で当てたい観点表のほうです。14-4-2で作った `docs/review-checklist.md` を、呼び出せる形にします。
