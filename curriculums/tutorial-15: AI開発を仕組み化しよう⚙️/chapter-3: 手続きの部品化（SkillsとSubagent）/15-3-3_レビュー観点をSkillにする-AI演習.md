# 15-3-3: レビュー観点をSkillにする - AI演習

## 📌 この演習について

Chapter 3の締めくくりです。14-3-2で、差分を読む3段目に当てる観点を、表から選んで使いました。次の機能でも、あの表を開いて、選んで、その場で伝えることになります。この演習では、選んだ観点を `SKILL.md` に書いて、`/review-checklist` と打てば同じ順で当たる形にします。

返ってくるのは下読みです。人が読む場所を絞るところまでを部品に渡し、絞られた先を自分で読みます。

---

## 🎯 演習課題

### 📋 課題

**何を実現したいか**

`.claude/skills/review-checklist/SKILL.md` を作り、`/review-checklist <ファイルのパス>` と打つと、自分が選んだ観点で下読みが返ってくる状態にします。

当てる観点は、14-3-2の「中身を読む」に載っている表から選びます。7行すべてを写しません。いま手元にあるコードに当たるものだけを選び、自分の言葉に書き直して構いません。選ぶ材料が自分の中にあるので、この部品はあなた専用になります。

**何は変えたくないか**

アプリのコードです。この部品は読んで報告するところまでで、直しません。`SKILL.md` にその1行を書いて、実際に手が付いていないことをあとで確かめます。

**どうなったら完成か**

下の完成チェックリストが全部埋まった状態です。

**下読みをかける相手**

2つ当てます。1つ目は `app/Http/Controllers/PostController.php` で、配られたときから手元にあるファイルです。2つ目は、Tutorial 14でコメント機能を作ったときに増えた、コメントを扱うコントローラーです。名前はAIが決めたので、自分のリポジトリで確かめてから指定します。

### ✏️ 進め方タスク

1. 【自分】14-3-2の表から、いま手元のコードに当てる観点を選ぶ
2. 【自分】`.claude/skills/review-checklist/` フォルダを作り、その中に `SKILL.md` を書く
3. 【自分】Claude Codeを終了して、起動し直す
4. 【自分⇄AI】`PostController.php` を指定して呼び出し、下読みさせる
5. 【自分⇄AI】コメントを扱うコントローラーにも当てて、同じ形で返ってくることを見る
6. 【自分】挙がった箇所を1つ開いて、書かれているとおりのコードがあるかを確かめる
7. 【自分】`.claude/` をコミットしてpushする

## 💡 ヒント

**呼び出しても `Unknown skill` と返るとき**

終了して起動し直します（15-3-1）。`/` の一覧に名前が出ているかどうかは、判断の材料になりません。

**書いていない観点が混ざるとき**

`SKILL.md` に「ここに書いた観点以外は当てない」という1行を足します。手順の書きぶりで返り方が変わるところが見えます。

**「要確認」が1つも出ないとき**

失敗ではありません。相手は、テストと受け入れ条件を通した2機能分のコードです。ここで確かめたいのは指摘の数ではなく、決めた形で返ってくるかどうかです。

**`---` で挟んだ2行の意味**

15-3-1に戻って確認してください。

## 🏃 実践：一緒に進めてみましょう

### 🧠 先輩エンジニアの思考プロセス

自分で進めてみて詰まったら、ここから先を読んでください。何を渡し、どこで承認し、何で確かめるのかを、場面ごとに並べます。

| 場面 | 何を渡すか | どこで承認するか | 何で確かめるか |
|:--|:--|:--|:--|
| 部品を作る前 | なし（`SKILL.md` は自分で書く） | なし | 選んだ観点が、手元のコードに当たるものになっているか |
| 起動し直したあと | なし | なし | 呼び出して、下読みが返ってくるか |
| 下読みを頼むとき | 対象のファイルのパスを1つ | なし（読むだけなので承認は出ません） | 判定の並びが、決めた形になっているか |

### 📝 ステップバイステップ

#### Step 1: 当てる観点を選ぶ

14-3-2の「中身を読む」の表を開きます。N+1、認可の置き場所、マスアサインメント、XSS、CSRF、入力チェック、書き方の揃いの7行が並んでいます。

このうち、コントローラーを読むときに当たるものだけを選びます。XSSとCSRFは画面のテンプレートに当たる観点なので、コントローラーを相手にすると毎回「対象外」で埋まります。ここでは次の5つにします。自分の判断で増やしても減らしても構いません。

| 観点 | このアプリでの具体形 |
|:--|:--|
| N+1 | 一覧で関連先の名前を出しているのに、`with()` が付いていないか |
| 認可の置き場所 | 編集できる人・消せる人の判定が、どこに書かれているか |
| マスアサインメント | `create($request->all())` の形になっていないか |
| 入力チェック | `validate()` を通しているか。項目が設計書と合っているか |
| 書き方の揃い | いまあるコードと同じ呼び方・同じ書き方になっているか |

#### Step 2: フォルダとファイルを作る

Claude Codeを起動したままなら、先に `/exit` で終了します。ターミナルに戻ったら、次の2行を打ちます。

```bash
# アプリのフォルダの中で実行する
mkdir -p .claude/skills/review-checklist
touch .claude/skills/review-checklist/SKILL.md
```

VS Codeで `.claude/skills/review-checklist/SKILL.md` を開いて、次の内容を書きます。`## 観点` の5行は、Step 1で自分が選んだものに入れ替えてください。`description` の後半も、自分がふだん打ちそうな言い方にしてよいところです。

```markdown
---
name: review-checklist
description: 決めておいたレビュー観点で、指定したファイルの下読みをする。「レビューして」「観点を当てて」「下読みして」と言われたときに使う。
---

# レビュー観点の下読み

指定されたファイルを読み、下に並べた観点を1つずつ当てます。
観点はここに書いたものだけを当ててください。足したり言い換えたりしないでください。

## 観点

- N+1: 一覧で関連先の名前を出しているのに、with() が付いていないか
- 認可の置き場所: 編集できる人・消せる人の判定が、どこに書かれているか
- マスアサインメント: create($request->all()) の形になっていないか
- 入力チェック: validate() を通しているか。項目が設計書と合っているか
- 書き方の揃い: いまあるコードと同じ呼び方・同じ書き方になっているか

## 手順

1. 指定されたファイルを読む（指定が無ければ、変更されたファイルを対象にする）
2. 観点ごとに、当てはまるか・当てはまらないか・判定できないかを決める
3. 判定できないときは、何が足りなくて判定できないのかを書く

## 出力の形式

観点1つにつき1行で、次の順に書いてください。

観点 / 判定（要確認・OK・対象外）/ ファイル名:行番号 / 気づいたこと

最後に、人が自分の目で読むべき箇所を3つまで挙げてください。

コードを直す作業はしないでください。読んで報告するところまでが仕事です。
```

書いてある内容のうち、意図がつかみにくいところを3つ補います。

- **「判定できない」を選択肢に入れている**のは、材料が無いときに「分からない」と言える逃げ道を作るためです。選択肢が2つしか無いと、材料が無くてもどちらかに寄せた答えが返ってきます。
- 手順に**指定が無いときの決め**を書いてあるので、パスを付けずに `/review-checklist` とだけ打っても動きます。
- **最後の2行**が、この部品の範囲を決めています。「人が自分の目で読むべき箇所を3つまで」で読む場所をこちらに戻し、「コードを直す作業はしないでください」で手前に止めます。ここを消すと、AIが書いたコードをAIが直す形になります。

#### Step 3: 起動し直して、呼んでみる

保存したら、もう一度 `claude` と打って起動します。

```bash
# アプリのフォルダの中で実行する
claude
```

読み込まれたかどうかは、次のStepでそのまま呼んで確かめます。

#### Step 4: PostController.php を下読みさせる

```text
/review-checklist app/Http/Controllers/PostController.php
```

> 💡 **出力例について**: AIの応答は毎回変わります。以下はあくまで一例です。文言が違っても、チェックリストの項目を満たしていれば問題ありません。

```text
Claude Code: （Skill(review-checklist) の行が出たあと、指定したファイルを読んで、
              観点ごとに1行ずつ次の形で並べてくる）

N+1 / OK / PostController.php:13 / index() に with(['user', 'category']) が付いている
認可の置き場所 / OK / PostController.php:30 / update() の先頭で authorize() を呼んでいる
マスアサインメント / OK / PostController.php:32 / validate() の結果だけを update() に渡している

（残りの観点が続き、最後に、人が自分の目で読むべき箇所が3つまで挙がる）
```

並んでいるのは、あなたが `SKILL.md` に書いた観点そのものです。この教材の例と同じにはなりません。行の数と文言が、自分の書いたとおりになっているかを見てください。

`Unknown skill: review-checklist` と返ったら、まだ起動し直せていません。`/exit` で終了して、`claude` からやり直します。

#### Step 5: コメントを扱うコントローラーにも当てる

まず、名前を確かめます。

```bash
# アプリのフォルダの中で実行する
ls app/Http/Controllers
```

Tutorial 14でコメント機能を作ったときに増えたファイルが並んでいます。そのパスを、同じように後ろに続けて打ちます。コメント専用のコントローラーが見当たらないときは、コメントの処理が `PostController.php` の中に入っています。その場合はStep 4の結果が2件目を兼ねるので、Step 6へ進んでください。

```text
/review-checklist app/Http/Controllers/（コメントを扱うコントローラー）.php
```

こちらはAIが書いたコードなので、判定の付き方が変わります。`PostController.php` と同じ観点を、同じ順で当てた結果が返ってくるところを見てください。当てる観点を毎回その場で伝える作業が、ここで消えています。

#### Step 6: 挙がった箇所を確かめて、記録する

挙がった箇所から1つ選び、VS Codeでそのファイルを開いて、指されている行を読みます。行番号はずれることがあるので、ファイル名と、その行の中身が合っているかを見ます。

そのあと、`git status` を打ちます。

```bash
# アプリのフォルダの中で実行する
git status
```

差分が出ているのは `.claude/` だけで、`app/` のファイルは変わっていないはずです。`SKILL.md` の最後の1行が効いています。確かめたら、作った部品を記録します。

```text
.claude/skills をコミットして、main に push してください。
```

15-3-2と同じく、機能を作る作業ではないので、ブランチを切らずに `main` へ送ります。GitHubでリポジトリを開き、`.claude/skills/review-checklist/SKILL.md` が見えることを確かめてください。

## 📖 進行例

> 💡 **進行例について**: AIとの開発は毎回違う流れになります。ここに示すのは一つの進行例です。あなたの画面と違っていても、チェックリストを満たしていれば正解です。

**1. 観点を選ぶ**

14-3-2の表から5行を選びました。XSSとCSRFは、コントローラーを読むときには当たらないので外しました。

**2. 作って、起動し直す**

`.claude/skills/review-checklist/SKILL.md` を書いたあと、そのままのセッションで呼んだところ、`Unknown skill: review-checklist` と返りました。`/exit` で終了して起動し直すと、同じ打ち方で下読みが始まりました。

**3. PostController.php に当てる**

判定が5行返ってきました。書いた観点と同じ5行で、余計な観点は混ざっていません。「要確認」が付いたのは入力チェックの1件で、本文の文字数の上限が指定されていない、という内容でした。挙がった行を開いて読み、`validate()` の中身が実物と合っていることを確かめました。

**4. コメントのコントローラーに当てる**

`ls app/Http/Controllers` で名前を確かめてから、同じ形で呼びました。同じ5行の観点が、同じ順で並びました。こちらは「要確認」が1つも出ませんでした。Tutorial 14でテストと受け入れ条件を通したコードなので、そういうこともあります。見たかったのは、1件目と同じ形で返ってくるかどうかです。

**5. 記録する**

`git status` で `app/` に差分が出ていないことを見てから、`.claude` をコミットして `main` へ送りました。GitHubのページで `SKILL.md` の中身が読めることを確かめて、この演習は終わりです。

## 🚀 まとめ

- 繰り返す手順は `SKILL.md` に書いて、`/名前` で呼び出せます。作った直後のセッションからは呼べないので、終了して起動し直します。
- 当てる観点は、14-3-2の表から手元のコードに関係するものだけを選びました。選ぶ作業が、機能のたびから1回に減ります。
- 返ってくるのは下読みです。読む場所が絞られた状態で受け取り、絞られた先は自分で開いて確かめます。
- 部品にコードを触らせない線は、`SKILL.md` の1行と、そのあとの `git status` で確かめられます。
- 15-1-1で置いた「同じ説明を二度としない」が、この章で2つ形になりました。調べ方の指示と、レビューの観点です。

この章で `.claude/` に置いた2つは、どちらも自分が呼ばないと動きません。呼び忘れれば、無いのと同じです。呼ばなくても決まった場面で必ず走る形は、15-4-2で作ります。
