# 15-3-3: レビュー観点をSkillにする - AI演習

## 📌 この演習について

Chapter 3の締めくくりです。15-3-1で、繰り返す手順は名前を付けて呼び出せることを見ました。ここでは実際に1つ作ります。題材は、14-4-2「AIが書いたコードのレビュー観点」で自分が作った観点表です。

14-5-2で並べた「毎回手でやっていたこと」の2つ目、同じレビュー観点を毎回その場で伝えること。これがこの演習で消えます。

> 🔥 ここからは、AIに実装を任せて構いません。ただし「任せる」と「丸投げ」は違います。何を作るかは設計書で自分が決め、出てきたものはテスト・動作確認・コードレビューで自分が検証します。品質の責任は、AIではなくあなたが握ります。

## 🎯 演習課題

### 📋 課題

`.claude/skills/review-checklist/SKILL.md` を作り、`/review-checklist` で呼び出せるようにしてください。呼ぶと、自分の観点表に沿って、指定したファイルの下読みが返ってくる状態がゴールです。

入力になるのは、14-4-2で作った `docs/review-checklist.md` です。あのとき「この表は、後で使い回せる形にしておきます」と書きました。その使い回す形が、これです。

**置き場所は変えません。** 観点表は `docs/` の直下に置いたままにします。14-4-2で書いたとおり、この表はコメント機能だけのものではなく、次の機能でも同じものを使うからです。移動も削除もしないでください。

ここで決めておくことが1つあります。**観点を `SKILL.md` に写さない**、という決め方です。`SKILL.md` には「`docs/review-checklist.md` を読んでから始めること」とだけ書き、観点そのものは書きません。理由は2つあります。

1つ目は、観点表の中身が人によって違うからです。14-4-2では「自分が実際に見た観点だけを、自分の言葉で書いてください」と頼みました。ですから、あなたの表とほかの人の表は、行数も文言も違います。写した瞬間に、その部品はあなた専用になります。

2つ目は、そのほうが後が楽だからです。読んでいるうちに「これも見よう」と思った観点は、`docs/review-checklist.md` に1行足すだけで次から当たります。`SKILL.md` を開く必要はありません。観点を足す場所が1か所に決まっている、という状態を作ります。

`SKILL.md` に書くのは、次の3つです。

- frontmatterの2行（`name` と `description`）
- 手順（観点表を読む、対象のファイルを読む、観点ごとに判定する）
- 出力の形式（どういう形で返してほしいか）

下読みの対象は `app/Http/Controllers/PostController.php` にします。10-3-5「認可機能 - ハンズオン演習」から手元にあるファイルで、自分で `$this->authorize()` を足した場所でもあります。15-3-1で見たとおり、呼び出し名の後ろにファイルのパスを続けると、そのファイルが対象になります。

### ✏️ 進め方タスク

1. 【自分】`docs/review-checklist.md` を開いて、いま何行あるかを見る
2. 【自分】`.claude/skills/review-checklist/` フォルダを作り、その中に `SKILL.md` を置く
3. 【自分】Claude Codeを終了して、起動し直す
4. 【自分⇄AI】`/review-checklist app/Http/Controllers/PostController.php` と打って、下読みさせる
5. 【自分】返ってきた観点が、`docs/review-checklist.md` に書いた行と同じかを確かめる
6. 【自分⇄AI】`docs/review-checklist.md` に観点を1行足して、もう一度呼び出す
7. 【自分】挙がった箇所を1つ選び、自分でそのファイルを開いて、直すか直さないかを決める
8. 【自分】`.claude/` と `docs/` をコミットしてpushする

## 💡 ヒント

**作ったのに `Unknown command` と出たら**

終了して起動し直します。作ったばかりの部品は、起動し直すまで見つけてもらえません（15-3-1）。

**観点表が見つからないと言われたら**

それが正しい動きです。観点は `SKILL.md` に書いていないので、`docs/review-checklist.md` が無いと当てるものがありません。このとき、それらしい表をでっち上げずに止まります。ファイル名の綴りと置き場所を確かめてください。

**直したのに変わらないときは**

一度呼び出したあとに `SKILL.md` を直しても、そのやり取りの中では入れ替わりません。`/clear` するか、終了して起動し直します。

**`---` で挟んだ2行の意味**

15-3-1に戻って確認してください。

**「要確認」が1つも出なかったとき**

失敗ではありません。下読みの相手は、10-3-5の模範解答と、自分でテストと受け入れ条件を通した2機能ぶんのコードです。指摘が0件になることは十分あります。ここで確かめたいのは、指摘の数ではなく、観点ごとに1行ずつ並ぶ形で返ってくるかどうかです。

## 🏃 実践：一緒に進めてみましょう

### 🧠 先輩エンジニアの思考プロセス

自分で進めてみて詰まったら、ここから先を読んでください。何を渡し、どこで承認し、何で確かめるのかを、場面ごとに並べます。

| 場面 | 何を渡すか | どこで承認するか | 何で確かめるか |
|:--|:--|:--|:--|
| 部品を作る前 | なし（`SKILL.md` は自分で書く） | なし | `docs/review-checklist.md` が何行あるか |
| 起動し直したあと | なし | なし | `/` を打って、候補に名前が出るか |
| 下読みを頼むとき | 対象のファイル名を1つ | なし（読むだけなので承認は出ません） | 画面に `Skill(review-checklist)` が出ているか |

### 📝 ステップバイステップ

#### Step 1: いまのやり方を確かめる

`docs/review-checklist.md` を開いて、いま何行あるかを数えておきます。あとで1行足したときに、増えたことが分かるようにするためです。

この表を使うとき、これまではここを開いて、今回当てる観点を選んで、自分の目で読んでいました。これから作るのは、その前半（開いて、当てて、場所を挙げる）を毎回同じ順でやらせる部品です。

#### Step 2: フォルダとファイルを作る

Claude Codeを起動したままなら、先に `/exit` で終了します。ターミナルに戻ったら、次の2行を打ちます。

```bash
# アプリのフォルダの中で実行する
mkdir -p .claude/skills/review-checklist
touch .claude/skills/review-checklist/SKILL.md
```

VS Codeで `.claude/skills/review-checklist/SKILL.md` を開いて、次の内容を書きます。まずはこのまま書いて構いません。`description` の後半だけは、自分がふだん打ちそうな言い方に入れ替えてもよいところです。

```markdown
---
name: review-checklist
description: docs/review-checklist.md に書いた観点で、変更したファイルの下読みをする。「レビューして」「観点を当てて」「下読みして」と言われたときに使う。
---

# レビュー観点の下読み

`docs/review-checklist.md` に書かれた観点で、指定されたファイルを1つずつ読みます。
観点はこのファイルには書きません。毎回 `docs/review-checklist.md` を読んでから始めてください。

## 手順

1. `docs/review-checklist.md` を読み、観点の一覧を取り出す
2. 指定されたファイルを読む（指定が無ければ、変更されたファイルを対象にする）
3. 観点ごとに、当てはまるか・当てはまらないか・判定できないかを決める

## 出力の形式

観点1つにつき1行で、次の順に書いてください。

`観点 / 判定（要確認・OK・対象外）/ ファイル名:行番号 / 気づいたこと`

最後に、**人が自分の目で読むべき箇所**を3つまで挙げてください。

判定が「OK」でも、それは観点に当てはまらなかったという意味だけです。
コードを直す作業はしないでください。直すかどうかは人が決めます。
```

書いてある内容のうち、意図がつかみにくいところを3つ補います。

- **「判定できないか」を選択肢に入れている**のは、判断の材料が無いときに「分からない」と言える逃げ道を作るためです。選択肢が2つしか無いと、材料が無くてもどちらかに寄せた答えが返ってきます。
- 手順に**指定が無いときの決め**を書いてあるので、ファイル名を付けずに `/review-checklist` とだけ打っても動きます。
- **出力の形式の最後にある2つの指示**が、この部品と14-4-2との境目です。「人が自分の目で読むべき箇所を3つまで挙げてください」で読む場所を人に戻し、「コードを直す作業はしないでください」で直す手前で止めています。ここを消すと、AIが書いたコードをAIが直す形になります。

#### Step 3: 起動し直して、名前が出るかを見る

保存したら、もう一度 `claude` と打って起動します。起動したら `/` を打ってみてください。使えるものの一覧に `review-checklist` が並んでいれば、読み込まれています。

#### Step 4: 呼び出して下読みさせる

```text
/review-checklist app/Http/Controllers/PostController.php
```

> 💡 **出力例について**: AIの応答は毎回変わります。以下はあくまで一例です。文言が違っても、チェックリストの項目を満たしていれば問題ありません。

```text
Claude Code: （docs/review-checklist.md を読み、指定したファイルを読んでから、
              観点ごとに1行ずつ次の形で並べてくる）

create() に $request->all() を渡していないか / OK / PostController.php:38 / 個別に指定している
入力フォームに @csrf があるか / 対象外 / - / 画面のテンプレートはこのファイルに無い

（最後に、人が自分の目で読むべき箇所が3つまで挙がる）
```

並んでいる観点は、あなたの `docs/review-checklist.md` に書いた行そのものです。この教材の例と同じにはなりません。行の数も、文言も、自分が書いたとおりになっているかを見てください。

画面に `Skill(review-checklist)` の行が出ていることも、あわせて確かめます。

#### Step 5: 観点を1行足して、もう一度呼ぶ

`docs/review-checklist.md` の末尾に、観点を1行足します。中身は何でも構いません。ここでは例として、次の行を足します。

```markdown
- [ ] 使わなくなった `use` の行が残っていないか
```

保存したら、もう一度 `/review-checklist app/Http/Controllers/PostController.php` と打ちます。足した行が、判定の一覧に出てくるはずです。判定が「対象外」でも構いません。足した行が出てこないときは、`/clear` してからもう一度呼びます。

確かめたいのは、`SKILL.md` を1文字も直していないのに、当てる観点が増えたことです。

#### Step 6: 自分で読んで、決める

挙がった箇所から1つ選びます。そのファイルをVS Codeで開いて、指されている行を自分の目で読んでください。読んだうえで、直すか、直さないかを決めます。直さないと決めるのも判断です。

決めたら、作った部品と、足した観点を記録します。`/exit` で終了して、ターミナルで次を打ちます。

```bash
# アプリのフォルダの中で実行する
git add .claude docs
git commit -m "Add review-checklist skill"
git push origin main
```

GitHubでリポジトリを開き、`.claude/skills/review-checklist/SKILL.md` が見えることを確かめてください。

## 📖 進行例

> 💡 **進行例について**: AIとの開発は毎回違う流れになります。ここに示すのは一つの進行例です。あなたの画面と違っていても、チェックリストを満たしていれば正解です。

**1. 作って、起動し直す**

`.claude/skills/review-checklist/` を作り、`SKILL.md` を書きました。作った直後のセッションで `/review-checklist` と打ったところ、`Unknown command: /review-checklist` と返りました。`/exit` で終了して起動し直すと、`/` の一覧に名前が出ました。

**2. 呼び出す**

対象のファイル名を付けて呼び出しました。画面に `Skill(review-checklist)` の行が出たあと、`docs/review-checklist.md` を読みにいき、そのあとに `PostController.php` を読んで、判定が並びました。観点は9行あり、`docs/review-checklist.md` に書いた9行と同じでした。

**3. 挙がったものを読む**

「要確認」が付いたのは1件でした。人が読むべき箇所として挙がっていた行を開いて、自分で読みました。読んだ結果、いまのままで問題ないと判断したので、直していません。

**4. 観点を1行足す**

`docs/review-checklist.md` に1行足して、もう一度呼び出しました。判定が10行になり、足した観点も並んでいました。`SKILL.md` は開いていません。

**5. 記録する**

`.claude` と `docs` をコミットして、`main` へ送りました。GitHubのページで `SKILL.md` の中身が読めることを確かめて、この演習は終わりです。

## 🚀 まとめ

- 繰り返す手順は、`SKILL.md` に書いて `/名前` で呼び出せます。作ったら、いったん終了して起動し直します。
- 観点は部品に写さず、`docs/review-checklist.md` を読ませます。観点を足す場所が1か所に決まり、足した次の呼び出しから当たります。
- 返ってくるのは下読みです。読む場所を絞るところまでが部品の仕事で、直すかどうかは自分が決めます。
- 15-1-1で置いた「同じ説明を二度としない」が、この章で2つ形になりました。調べ方の指示と、レビューの観点です。

この章では、`.claude/` に道具を2つ置きました。調べものを任せる担当と、観点を当てる部品です。ただし、どちらも自分が呼ばないと動きません。呼び忘れれば、無いのと同じです。承認を1つずつ押しているのも、テストを自分で打っているのも、Tutorial 14のときのままです。次のChapter 4では、こちらが呼ばなくても決まった場面で必ず動く形を作ります。
