# 15-4-3: 品質ゲートを組む - AI演習

## 📌 この演習について

15-4-2 で読んだ1行を、自分のアプリに仕掛けます。ここで組むのは品質ゲート（次へ進む前に、機械が必ず通す確認）です。AIがファイルを書き換えたら、その直後にテストが走り、落ちたらAIがそれを直します。

仕掛けるだけでは、効いているかどうかが分かりません。通ったときは画面に何も出ないからです。**わざと1回落とすところまでが、この演習です。**

---

## 🎯 演習課題

### 📋 課題

**目的**

AIがファイルを書き換えるたびにテストが走り、落ちたらAIが直してから終わる状態にします。

使う材料は、Chapter 2 で作った `.claude/rules/testing.md` と、15-4-1 で書いた `.claude/settings.json` です。どちらもすでに手元にあるので、それぞれに1つずつ足します。

| 足すもの | 何を決めるか |
|:--|:--|
| `.claude/rules/testing.md` に1行 | テストが落ちたまま作業を終えない、という決まり |
| `.claude/settings.json` に `hooks` | ファイルを書き換えた直後に、必ずテストを走らせること |

**順番は決まりが先です。** 設定だけを足すと、機械はテストが落ちたことを知らせますが、AIは落ちたことを報告して止まります。指摘するところまでが設定の仕事で、指摘されたら直す、を決めるのが決まりの1行です。

**変えないもの**

- `.claude/settings.json` の `permissions`（15-4-1 で書いた `deny`・`ask`・`allow`）
- テストのコード。落ちたテストを消したり、条件を緩めたりして通すのは禁じ手です（14-4-1）

**受け入れ条件**

自分の手で落ちる状態を作り、AIに動きを変えない依頼を1つしたときに、編集の直後にゲートが落ち、AIがその原因を直して `failed` が0に戻る状態です。

### ✏️ 進め方タスク

1. 【自分】Sailを起動して、Claude Codeを起動する
2. 【AI】`.claude/rules/testing.md` に、テストが落ちたまま終わらせないための1行を足させる
3. 【自分⇄AI】`.claude/settings.json` に、編集のたびにテストを回す設定を足させ、書かれたものを読む
4. 【自分】`/permissions` を開いて、15-4-1 で書いた指定が消えていないことを確かめる
5. 【自分】リプライ本文の入力チェックを1か所外し、自分でテストを打って `failed` が出ることを確かめる
6. 【自分⇄AI】動きを変えない小さな依頼を1つ出し、ゲートが落ちるところと、AIが直すところを見る
7. 【自分⇄AI】もう一度同じ形の依頼を出し、通ったときは画面に何も出ないことを確かめる
8. 【自分⇄AI】`.claude/rules/testing.md`・`.claude/settings.json`・`app/` の変更をコミットして push させ、棚卸しのイシューにチェックを付ける

### ✅ 完成チェックリスト

- [ ] `/permissions` の一覧に、`deny`・`ask`・`allow` が `hooks` を足したあとも並んでいる
- [ ] `/hooks` の一覧に、`PostToolUse` のフックが1つ並んでいる
- [ ] 入力チェックを外した状態で `./vendor/bin/sail test` を打ち、`failed` が出ることを見た
- [ ] AIに依頼を出したとき、編集の直後にゲートが落ち、その中身がAIに届いたことを画面で見た
- [ ] 外れていた入力チェックが戻ったあと、`./vendor/bin/sail test` で `failed` が0になった
- [ ] `git diff app tests` を打って、テストのコードが書き換わっていないことを確かめた
- [ ] もう一度同じ形の依頼を出し、通ったときは画面に何も出ないことを確かめた
- [ ] GitHubのリポジトリのページに、`.claude/rules/testing.md` と `.claude/settings.json` が表示されている
- [ ] 棚卸しのイシューの2つ目にチェックが付いている

> 🚀 **ここから先は、自分の力で進めてみましょう！**

## 💡 ヒント

詰まったときの粘り方は 14-5-1「直らないときの型」のとおりです。巻き戻す、小さく分ける、2回直らなければ仕切り直す、の3つで足ります。壊れたと感じたら、まだコミットしていない変更は `git restore .` で戻せます。この演習に固有のものだけ足しておきます。

**テストが回らない**

Sailが起動しているかを確かめてください。

```bash
# アプリのフォルダの中で実行する
./vendor/bin/sail up -d
```

**何をしても、ゲートが動いていないように見える**

まず `.claude/settings.json` を開いて、`//` で始まる行（15-4-1）と、閉じ括弧やカンマの過不足が無いかを見てください。どちらも問題が無ければ、いったんClaude Codeを終了して起動し直してから、もう一度試してください。

**入力チェックを外したのに、テストが落ちない**

書かれているテストの中身によっては、この外し方で落ちないことがあります。そのときの手当ては Step 4 の折りたたみにあります。

**AIが、外れた入力チェックを戻さずに聞き返してくる**

戻してよいかを聞かれたら、戻すように答えてください。そのうえで `.claude/rules/testing.md` の1行が効いているかを見たいときは、`/clear` してから同じ手順をもう一度試します。やり取りに残った自分の発言が消えるので、決まりのほうだけが根拠の状態になります。

## 🏃 実践：一緒に進めてみましょう

### 🧠 先輩エンジニアの思考プロセス

自分で進めてみて詰まったら、ここから先を読んでください。何を渡し、どこで手を止め、何で検証するのかを、場面ごとに並べます。

| 場面 | 何を渡すか | どこで手を止めるか | 何で検証するか |
|:--|:--|:--|:--|
| 決まりを足す | `.claude/rules/testing.md` の1行 | 自分で書くところ | ファイルを開いて、テストの決まりの並びに入っているかを読む |
| 仕掛けを足す | `.claude/settings.json` の `hooks` | 自分で書くところ | `/permissions` を開いて、`permissions` が消えていないことを見る |
| 落ちる状態を作る | （渡さない） | 自分で書くところ | 自分でテストを打って `failed` が出ることを見る |
| 仕掛けを試す | 動きを変えない小さな依頼 | auto なので承認画面は出ない。出てきた差分を読むところ | 編集の直後にテストが走り、落ちたことが画面に出る |
| 直ったことを見る | （渡さない） | auto なので承認画面は出ない。戻された差分を読むところ | 自分でテストを打って `failed` が0であることを見る |

### 📝 ステップバイステップ

アプリが止まっている場合は、Docker Desktop（またはDocker Engine）を起動してから、Sailを立ち上げます。

```bash
# アプリのフォルダへ移動して、Sailを起動する
cd ~/laravel-practice/post-app-practice
./vendor/bin/sail up -d
```

進めるモードは auto です。入力欄の下が `⏵⏵ auto mode on` になっていることを見てから始めます。ファイルが1つ書き換わるたびに承認画面が出ることはないので、AIが書き換えた差分は、画面に出たところで読みます。

#### Step 1: 決まりとフックを足させる

2つまとめて頼みます。ファイルを編集するたびにテストが走る仕掛けと、落ちたままにしない決まりです。

```text
2つお願いしたい。

1つ目。.claude/rules/testing.md に「テストが落ちた状態で作業を終えない。
原因が自分の変更以外にあっても直す」を足して。

2つ目。ファイルを編集したあとに必ずテストが走るフックを .claude/settings.json に足して。
落ちたらそのターンを止めて、出力がAIに戻るようにして。
いま入っている permissions は消さないで。

3つ目。allow に ./vendor/bin/sail artisan test と sail artisan test の2つの形も足して。

書いたら、settings.json 全体を見せて。
```

1つ目の後半が肝心です。「原因が自分の変更以外にあっても」が無いと、AIは自分が触っていない場所には手を出しません。この演習で落ちるのは、AIが触っていない場所です。

3つ目は、打ち方のズレです（15-4-1）。`allow` に書いてあるのは `sail test` の形で、これから足すフックが打つのは `sail artisan test` です。別の文字列として扱われるので、フックの外で `sail artisan test` を打つと、そこだけ聞かれます。同じテストを走らせるコマンドの形が2つあるなら、両方を通しておきます。

#### Step 2: 書かれたものを読む

出てきた `.claude/settings.json` を読みます。フックの部分は、この形になっているはずです。

```json
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "./vendor/bin/sail artisan test >&2 || exit 2"
          }
        ]
      }
    ]
  }
```

見るところは3つです。`PostToolUse` の場面になっていること。`matcher` がファイルを書き換える道具（`Edit`・`Write`）に当たっていること。コマンドの終わりが `|| exit 2` になっていること。`exit 2` が、そのターンを止めて出力をAIへ戻す番号です（15-4-2）。違っていたら、その場で直させます。

`permissions` と `hooks` が、いちばん外側の `{ }` の中に並んでいる形になります。`//` で始まる行が1行でも入っていたら、設定は丸ごと読めなくなるので、そこも見ます。

下を開いて、全体の形と見比べてください。`allow` に書いた行やフックのコマンドは、自分のアプリに合わせて違っていて構いません。見るのは、かっことカンマの位置です。

<details>
<summary>📄 書き足したあとの `.claude/settings.json` 全文（クリックで展開）</summary>

```json
{
  "permissions": {
    "deny": [
      "Read(.env)",
      "Read(.env.*)",
      "Edit(.env)",
      "Edit(.env.*)"
    ],
    "ask": [
      "Bash(git push *)"
    ],
    "allow": [
      "Bash(./vendor/bin/sail test *)",
      "Bash(sail test *)",
      "Bash(./vendor/bin/sail artisan test *)",
      "Bash(sail artisan test *)"
    ]
  },
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "./vendor/bin/sail artisan test >&2 || exit 2"
          }
        ]
      }
    ]
  }
}
```

</details>

このファイルは、保存すればそのまま効きます。ふだんは起動し直す必要はありません。

#### Step 3: permissions が生きていることを確かめる

Claude Codeで `/permissions` と打ちます。15-4-1 で書いた `deny`・`ask`・`allow` が、そのまま並んでいれば大丈夫です。

並んでいなければ、JSONの書式が壊れています。カンマの過不足を見てください。片方が壊れると両方が読めなくなるので、`permissions` が生きているかどうかが、そのまま `hooks` が生きているかどうかの目印になります。`/hooks` と打つと、いま登録されたフックのほうも読めます（画面は2026年8月時点）。

#### Step 4: 落ちる状態を、自分の手で作る

先に、リプライの本文のカラム名を確かめます。この名前を決めたのはAIなので、手元では `body` ではないことがあります。`docs/reply.md` の「入力チェックとメッセージ一覧」か、`database/migrations/` にあるリプライ用のマイグレーションを開いて、本文にあたる名前を読んでください。ここから先の `body` は、その名前に読み替えます。

確かめたら、その名前で入力チェックの場所を探します。

```bash
# アプリのフォルダの中で実行する
grep -rn "'body'" app/
```

> 💡 **TIP**: `grep` は、決めた文字を含む行を取り出すコマンドです（14-5-1）。`-r` はフォルダの中のファイルをまとめて探す指定で、`-n` は見つかった行の番号も出す指定です。

`'body' => 'required|string|max:500',` のような行が見つかります。書いたのはAIなので、上限の数字や並び順は手元で違います。この行から `required|` の部分だけを消して、保存します。

```php
// 見つかったファイル（わざと外した状態）
'body' => 'string|max:500',
```

`'body' => ['required', 'string', 'max:500']` のように、角かっこで並べる形で書かれていることもあります。その場合は `'required',` の1つを消してください。

これで、本文が空のままでもリプライが登録できる状態になりました。`docs/reply.md` に書いた受け入れ条件の3行目と食い違っています。

書き換えたら、**自分でテストを打ちます。**

```bash
# アプリのフォルダの中で実行する
./vendor/bin/sail test
```

`failed` が出ることを、ここで確かめてください。落ちるのは、本文が空のときの動きを確かめているテストです。テストの名前も、落ちた理由の文面も、AIが書いたテストによって変わります。見るのは `failed` の有無だけです（14-4-1）。ここを飛ばすと、あとの Step でゲートが落ちません。落ちないのを見て「仕掛けが効いていない」と勘違いすることになります。

<details>
<summary>入力チェックの行が見つからないとき・外しても `failed` が出ないとき（クリックで展開）</summary>

止まり方は2通りありますが、手当ては同じです。

**入力チェックの行が見つからない**

入力チェックが別の書き方で置かれています。コントローラーの `validate()` にも、9-6-4「フォームリクエスト」で学んだ形の `app/Http/Requests/` の中にも見当たらなければ、探す文字列を `required` だけに広げて、リプライに関わるファイルを見てください。それでも見つからなければ、下の手当てに移ります。

**外しても `failed` が出ない**

本文が空のときの動きを確かめるテストが、書かれていません。下の手当てに移ります。

**手当て**

リプライを消せるのが書いた本人だけであることを決めている判定を、代わりに外します。

```bash
# アプリのフォルダの中で実行する
grep -rn "user_id" app/Policies/
```

`return $user->id === $reply->user_id;` のような行が見つかります。この行を `return true;` に置き換えると、他人のリプライも消せる状態になり、それを確かめているテストが落ちます。戻すときも同じ1行です。

</details>

#### Step 5: 依頼を1つ出して、ゲートが落ちるところを見る

Claude Codeで、動きを変えない小さな依頼を1つ出します。

```text
app/Http/Controllers/PostController.php の index() に、何をしている処理なのかを説明する日本語のコメントを1行足してください。
```

> 💡 この依頼が動きを変えないものになっているのは、ゲートが落ちた原因を、いま足したものと取り違えないためです。Step 4 で外した場所とも別のファイルなので、AIは自分が触っていない場所の失敗を受け取ることになります。

AIがファイルを書き換えると、その直後にテストが走ります。Docker越しに動くので、しばらく返事が止まったように見えます。出てきた差分は、その場で読んでください。

テストは落ちます。`PostToolUse:Edit hook returned blocking error` から始まる知らせが画面に出て、落ちたテストの出力が続きます。同じ内容がAIにも届くので、AIはその中身を読みます。

**ゲートが落ちて、テストの出力が出たところ**

<img alt="15-4-3_2.png" src="">

ここから先は毎回変わります。`.claude/rules/testing.md` の1行があるので、AIは自分が書き換えたものではない場所にも手を伸ばします。戻す差分が出たら、何をどう戻したのかを読んでください。直っているべきなのは入力チェックのほうです。戻さずに聞き返してきたときの答え方は、💡ヒントにあります。

通ったあと、自分でもテストを打ちます。

```bash
# アプリのフォルダの中で実行する
./vendor/bin/sail test
```

`failed` が0であることを確かめてください。

#### Step 6: 通ったときは何も出ないことを確かめる

もう一度、動きを変えない小さな依頼を出します。今度は落ちる材料がありません。

```text
app/Http/Controllers/PostController.php の destroy() に、何をしている処理なのかを説明する日本語のコメントを1行足してください。
```

> 💡 Step 5 と同じ形の依頼です。違うのは、落ちる材料がもう残っていないことだけです。同じ形にしておくと、出方の違いだけを見比べられます。

差分が出たあと、しばらく待ちます。**何も表示されなければ、テストが走って通っています。** 無反応が合格の合図です。

**通ったので、差分のあとに何も出ていない画面**

<img alt="15-4-3_3.png" src="">

どちらの Step でも、編集の直後にテストは走っています。違うのは、落ちたかどうかだけです。

#### Step 7: コミットして push する

コミットする前に、取り残しが無いかを見ます。

```bash
# アプリのフォルダの中で実行する
git diff app tests
```

Step 4 で外した入力チェックが戻っていれば、差分に残っているのは、Step 5 と Step 6 で足した日本語のコメントだけになります。外した部分が戻っていなければ、自分で戻してください。`tests/` に差分が出ていたら、テストのほうが書き換えられています。その差分は元に戻して、入力チェックのほうが直っているかをもう一度見てください（14-4-1）。

記録も頼みます。

```text
.claude/rules/testing.md と .claude/settings.json と app/ の変更をコミットして、main に push してください。
そのあと、棚卸しのイシューの2つ目「テストの句を書き添えた」にチェックを付けて。
```

2つ目にチェックを付けるのは、ここです。Chapter 2 では決まりとして書いただけで、書き忘れたら抜けるままでした。依頼文に書かなくても走る形になって、はじめて手から離れます。

15-4-1 と同じく、ブランチは切っていません。機能を作る作業ではないからです。push の手前では承認画面が出ます。`ask` に書いたコマンドなので、auto でも聞かれます。

## 📖 進行例

> 💡 **進行例について**: AIとの開発は毎回違う流れになります。ここに示すのは一つの進行例です。あなたの画面と違っていても、チェックリストを満たしていれば正解です。

Step 5 は、たとえば次のように進みます。

```text
あなた: （PostController の index() にコメントを1行足す依頼を出す）
Claude Code: （コメントを1行足す差分が出る。読む）
Claude Code: （編集の直後にテストが走る。しばらく間があってから、
             PostToolUse:Edit hook returned blocking error の行と、
             落ちたテストの出力が出る）
Claude Code: （その中身を読んで、どこが落ちているのかを報告してくる）
```

落ちたテストの名前も、AIがそこから書く説明も毎回変わりますが、たどり着く先は Step 4 で外した入力チェックです。

読む差分は2つになります。1つ目はコメントを足す差分、2つ目は入力チェックを戻す差分です。仕掛けを足したあとも、差分を読む場所は減っていません。増えたのは、読む前に機械が1度チェックを通していることです。

## 🚀 まとめ

- 機械に守らせるには2つが要ります。設定は指摘するところまで、`.claude/rules/testing.md` の1行が直すところまでを担います。
- 通ったときは何も出ません。効いていることを確かめるには、落ちる状態を自分の手で作ります。
- 落ちたテストを消したり緩めたりして通すのは禁じ手です。テストのファイルが書き換わっていたら、元に戻します。
- Chapter 2 から置いてきた `CLAUDE.md`・`.claude/rules/`・`.claude/skills/`・`.claude/agents/` に、`.claude/settings.json` が並びました。Chapter 1 で言い出した「同じ説明を二度としない」は、この形になりました。

整形の自動化は、Tutorial 16 で Laravel Pint を学んだあとに、同じやり方で足せます。

置いた道具がどれだけ効くのかは、Chapter 5 で数えます。
