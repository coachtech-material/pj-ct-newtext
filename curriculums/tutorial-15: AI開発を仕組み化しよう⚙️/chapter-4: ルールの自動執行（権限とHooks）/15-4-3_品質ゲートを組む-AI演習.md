# 15-4-3: 品質ゲートを組む - AI演習

## 📌 この演習について

15-4-2 で読んだ1行を、自分のアプリに仕掛けます。ここで組むのは品質ゲート（次へ進む前に、機械が必ず通す確認）です。AIがファイルを書き換えたら、その直後にテストが走り、落ちたらそのままでは先へ進めない状態にします。

仕掛けるだけでは、効いているかどうかが分かりません。通ったときは画面に何も出ないからです。**わざと1回落とすところまでが、この演習です。**

---

## 🎯 演習課題

### 📋 課題

**何を実現したいか**

AIがファイルを書き換えるたびにテストが走り、落ちたらAIが直してから終わる状態にします。

使う材料は、Chapter 2 で書いた `CLAUDE.md` と、15-4-1 で書いた `.claude/settings.json` です。どちらもすでに手元にあるので、それぞれに1つずつ足します。

| 足すもの | 何を決めるか |
|:--|:--|
| `CLAUDE.md` に1行 | テストが落ちたまま作業を終えない、という約束 |
| `.claude/settings.json` に `hooks` | ファイルを書き換えた直後に、必ずテストを走らせること |

**順番は `CLAUDE.md` が先です。** 設定だけを足すと、機械はテストが落ちたことを知らせますが、AIは直しません。落ちた原因を正しく突き止めたうえで、「依頼はこれだけだったので、そこには手を付けていません。直してよければ対応します」と聞き返して終わります。指摘するところまでが設定の仕事で、指摘されたら直す、を決めるのが `CLAUDE.md` の1行です。

**何は変えたくないか**

- `.claude/settings.json` の `permissions`（15-4-1 で書いた `deny`・`ask`・`allow`）
- テストのコード。落ちたテストを消したり、条件を緩めたりして通すのは禁じ手です（14-4-1）

**どうなったら完成か**

自分の手で落ちる状態を作り、AIに動きを変えない依頼を1つしたときに、編集の直後にゲートが落ち、AIがその原因を直して `failed` が0に戻る状態です。

### ✏️ 進め方タスク

1. 【自分】Sailを起動して、Claude Codeを起動する
2. 【自分】`CLAUDE.md` に、テストが落ちたまま終わらせないための1行を足す
3. 【自分】`.claude/settings.json` に、編集のたびにテストを回す設定を足す
4. 【自分】`/permissions` を開いて、15-4-1 で書いたルールが消えていないことを確かめる
5. 【自分】コメント本文の入力チェックを1か所外し、自分でテストを打って `failed` が出ることを確かめる
6. 【自分⇄AI】動きを変えない小さな依頼を1つ出し、ゲートが落ちるところと、AIが直すところを見る
7. 【自分⇄AI】もう一度同じ形の依頼を出し、通ったときは画面に何も出ないことを確かめる
8. 【自分⇄AI】`CLAUDE.md`・`.claude/settings.json`・`app/` の変更をコミットして push させる

### ✅ 完成チェックリスト

- [ ] `/permissions` の一覧に、`deny`・`ask`・`allow` が `hooks` を足したあとも並んでいる
- [ ] 入力チェックを外した状態で `./vendor/bin/sail artisan test` を打ち、`failed` が出ることを見た
- [ ] AIに依頼を出したとき、編集の直後にゲートが落ち、その中身がAIに届いたことを画面で見た
- [ ] AIが外れていた入力チェックを戻したあと、`./vendor/bin/sail artisan test` で `failed` が0になった
- [ ] テストのコードを書き換える差分を、1つも承認していない
- [ ] もう一度同じ形の依頼を出し、通ったときは画面に何も出ないことを確かめた
- [ ] GitHubのリポジトリのページに、`CLAUDE.md` と `.claude/settings.json` が表示されている

> 🚀 **ここから先は、自分の力で進めてみましょう！**

## 💡 ヒント

詰まったときの粘り方は 14-4-3「直らないときの型」のとおりです。巻き戻す、小さく分ける、2回直らなければ仕切り直す、の3つで足ります。この演習に固有のものだけ足しておきます。

**テストが回らない**

Sailが起動しているかを確かめてください。

```bash
# アプリのフォルダの中で実行する
./vendor/bin/sail up -d
```

**何をしても、ゲートが動いていないように見える**

まず `.claude/settings.json` を開いて、`//` で始まる行が入っていないかを見てください。1行入っているだけで、`hooks` も `permissions` も丸ごと読めなくなります。閉じ括弧やカンマの過不足も同じです。どちらも問題が無ければ、いったんClaude Codeを終了して起動し直してから、もう一度試してください。

**入力チェックを外したのに、テストが落ちない**

書かれているテストの中身によっては、この外し方で落ちないことがあります。そのときの手当ては Step 4 の折りたたみにあります。

**AIが、外れた入力チェックを戻さずに聞き返してくる**

戻してよいかを聞かれたら、戻すように答えてください。そのうえで `CLAUDE.md` の1行が効いているかを見たいときは、`/clear` してから同じ手順をもう一度試します。やり取りに残った自分の発言が消えるので、`CLAUDE.md` だけが根拠の状態になります。

## 🏃 実践：一緒に進めてみましょう

### 🧠 先輩エンジニアの思考プロセス

自分で進めてみて詰まったら、ここから先を読んでください。何を渡し、どこで承認し、何で検証するのかを、場面ごとに並べます。

| 場面 | 何を渡すか | どこで承認するか | 何で検証するか |
|:--|:--|:--|:--|
| ルールを足す | `CLAUDE.md` の1行 | 自分で書くので承認は無い | ファイルを開いて、守ってほしいことの並びに入っているかを読む |
| 仕掛けを足す | `.claude/settings.json` の `hooks` | 自分で書くので承認は無い | `/permissions` を開いて、`permissions` が消えていないことを見る |
| 落ちる状態を作る | （渡さない） | 承認は無い | 自分でテストを打って `failed` が出ることを見る |
| 仕掛けを試す | 動きを変えない小さな依頼 | AIが出した差分を読んで承認する | 編集の直後にテストが走り、落ちたことが画面に出る |
| 直ったことを見る | （渡さない） | AIが戻す差分を読んで承認する | 自分でテストを打って `failed` が0であることを見る |

### 📝 ステップバイステップ

アプリが止まっている場合は、Docker Desktop（またはDocker Engine）を起動してから、Sailを立ち上げます。

```bash
# アプリのフォルダへ移動して、Sailを起動する
cd ~/laravel-practice/post-app-practice
./vendor/bin/sail up -d
```

#### Step 1: CLAUDE.md に1行足す

`CLAUDE.md` を開いて、守ってほしいことを並べたところの末尾に、次の1行を足します。見出しの名前は人によって違うので、進め方や約束を並べた箇所を探してください。

```markdown
- テストが落ちた状態で作業を終えないでください。原因が自分の変更以外にあっても、直してから終わってください。
```

後半が肝心です。「原因が自分の変更以外にあっても」が無いと、AIは自分が触っていない場所には手を出しません。この演習で落ちるのは、AIが触っていない場所です。

#### Step 2: 設定に hooks を足す

**`.claude/settings.json`** を開きます。いまは `permissions` のまとまりが1つだけ入っているので、その閉じ括弧のうしろにカンマを打ってから、次を続けて書きます。

```json
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "./vendor/bin/sail artisan test >&2 || exit 2"
          }
        ]
      }
    ]
  }
```

`permissions` と `hooks` が、いちばん外側の `{ }` の中に並んでいる形になります。`//` で始まる行は、1行も入れません。

このファイルは、保存すればそのまま効きます。ふだんは起動し直す必要はありません。

#### Step 3: permissions が生きていることを確かめる

Claude Codeで `/permissions` と打ちます。15-4-1 で書いた `deny`・`ask`・`allow` が、そのまま並んでいれば大丈夫です。

並んでいなければ、Step 2 でJSONの書式が壊れています。カンマの過不足を見てください。片方が壊れると両方が読めなくなるので、`permissions` が生きているかどうかが、そのまま `hooks` が生きているかどうかの目印になります。

#### Step 4: 落ちる状態を、自分の手で作る

コメントの本文の入力チェックを探します。

```bash
# アプリのフォルダの中で実行する
grep -rn "'body'" app/
```

`'body' => 'required|string|max:500',` のような行が見つかります。書いたのはAIなので、上限の数字や並び順は手元で違います。この行から `required|` の部分だけを消して、保存します。

```php
// 見つかったファイル（わざと外した状態）
'body' => 'string|max:500',
```

`'body' => ['required', 'string', 'max:500']` のように、角かっこで並べる形で書かれていることもあります。その場合は `'required',` の1つを消してください。

これで、本文が空のままでもコメントが登録できる状態になりました。`docs/comment.md` に書いた受け入れ条件と食い違っています。

書き換えたら、**自分でテストを打ちます。**

```bash
# アプリのフォルダの中で実行する
./vendor/bin/sail artisan test
```

`failed` が出ることを、ここで確かめてください。落ちるのは、本文が空のときの動きを確かめているテストです。テストの名前も、落ちた理由の文面も、AIが書いたテストによって変わります。見るのは `failed` の有無だけです（14-4-1）。ここを飛ばすと、あとの Step でゲートが落ちません。落ちないのを見て「仕掛けが効いていない」と勘違いすることになります。

<details>
<summary>`'body'` の行が見つからないとき・外しても `failed` が出ないとき（クリックで展開）</summary>

コントローラーの `validate()` にも、9-6-4「フォームリクエスト」で学んだ形の `app/Http/Requests/` の中にも見つからない場合は、探す文字列を `body` だけに広げてください。

外しても `failed` が出ないときは、本文が空のときを確かめるテストが書かれていません。代わりに、コメントを消せるのが書いた本人だけであることを決めている判定を外します。

```bash
# アプリのフォルダの中で実行する
grep -rn "user_id" app/Policies/
```

`return $user->id === $comment->user_id;` のような行が見つかります。この行を `return true;` に置き換えると、他人のコメントも消せる状態になり、それを確かめているテストが落ちます。戻すときも同じ1行です。

</details>

#### Step 5: 依頼を1つ出して、ゲートが落ちるところを見る

Claude Codeで、動きを変えない小さな依頼を1つ出します。

```text
app/Http/Controllers/PostController.php の index() に、何をしている処理なのかを説明する日本語のコメントを1行足してください。
```

> 💡 この依頼のポイントは、①動きを変えない依頼にしている（ゲートが落ちた原因を、いま足したものと取り違えないため）②Step 4 で外した場所とは別のファイルを指している、の2点です。②があるので、AIは自分が触っていない場所の失敗を受け取ることになります。

差分を読んで承認すると、その直後にテストが走ります。Docker越しに動くので、しばらく返事が止まったように見えます。

テストは落ちます。落ちたことを知らせる行が画面に出て、同じ内容がAIにも届きます。落ちたテストの名前も、AIがそこから書く説明も毎回変わりますが、たどり着く先は Step 4 で外した入力チェックです。そして `CLAUDE.md` の1行があるので、自分が書き換えたものではない場所を、元に戻そうとします。

戻す差分も承認の対象です。何をどう戻そうとしているのかを読んでから承認してください。直すのは入力チェックのほうです。テストを書き換える差分が出てきたら、そこは承認せずに、入力チェックを戻すように伝えてください（14-4-1）。

通ったあと、自分でもテストを打ちます。

```bash
# アプリのフォルダの中で実行する
./vendor/bin/sail artisan test
```

`failed` が0であることを確かめてください。

#### Step 6: 通ったときは何も出ないことを確かめる

もう一度、動きを変えない小さな依頼を出します。今度は落ちる材料がありません。

```text
app/Http/Controllers/PostController.php の destroy() に、何をしている処理なのかを説明する日本語のコメントを1行足してください。
```

> 💡 Step 5 と同じ形の依頼です。違うのは、落ちる材料がもう残っていないことだけです。同じ形にしておくと、出方の違いだけを見比べられます。

差分を承認したあと、しばらく待ちます。**何も表示されなければ、テストが走って通っています。** 無反応が合格の合図です。

どちらの Step でも、編集の直後にテストは走っています。違うのは、落ちたかどうかだけです。

#### Step 7: コミットして push する

コミットする前に、`app/` に取り残しが無いかを見ます。

```bash
# アプリのフォルダの中で実行する
git diff app
```

Step 4 で外した入力チェックはAIが戻しているはずなので、差分に残っているのは、Step 5 と Step 6 で足した日本語のコメントだけになります。外した部分が戻っていなければ、自分で戻してください。

記録も頼みます。

```text
CLAUDE.md と .claude/settings.json と app/ の変更をコミットして、main に push してください。
```

15-4-1 と同じく、ブランチは切っていません。機能を作る作業ではないからです。push の手前では承認画面が出ます。`ask` に書いたコマンドなので、auto でも聞かれます。

## 📖 進行例

> 💡 **進行例について**: AIとの開発は毎回違う流れになります。ここに示すのは一つの進行例です。あなたの画面と違っていても、チェックリストを満たしていれば正解です。

Step 5 は、たとえば次のように進みます。

```text
あなた: （PostController の index() にコメントを1行足す依頼を出す）
Claude Code: （コメントを1行足す差分を出す。読んで承認する）
Claude Code: （編集の直後にテストが走る。しばらく間があってから、落ちたことを知らせる行が出る）
Claude Code: （落ちた理由を説明する。コメント本文の入力チェックから required が外れていて、
             本文が空でも登録できてしまうと伝えてくる）
Claude Code: （CLAUDE.md のルールに従って、required を戻す差分を出す。読んで承認する）
Claude Code: （もう一度テストが走り、今度は何も出ない）
```

承認したのは2回です。1回目はコメントを足す差分、2回目は入力チェックを戻す差分です。どちらも、読んでから通しています。仕掛けを足したあとも、差分を読む場所は減っていません。増えたのは、読む前に機械が1度チェックを通していることです。

落ちた場所は、依頼したファイルとは別のところでした。それでも戻す差分が出てきたのは、`CLAUDE.md` に「原因が自分の変更以外にあっても」と書いてあるからです。設定だけを足した状態では、ここでAIは「直しますか」と聞いて止まります。

## 🚀 まとめ

- 機械に守らせるには2つが要ります。設定は「テストが落ちた」と指摘するところまでを担い、`CLAUDE.md` の1行が「指摘されたら直す」を担います。片方だけでは、AIは落ちたことを報告して止まります。
- 通ったときは何も出ません。効いていることを確かめるには、落ちる状態を自分の手で作ります。
- 落ちたテストを消したり緩めたりして通すのは禁じ手です。テストを書き換える差分は承認しません。
- Chapter 2 から置いてきたものが、これで4つになりました。`CLAUDE.md`、`.claude/agents/` の1本、`.claude/skills/` の1本、そして `.claude/settings.json` です。Chapter 1 で言い出した「同じ説明を二度としない」は、この4つの形になりました。

整形の自動化は、Tutorial 16 で Laravel Pint を学んだあとに、同じやり方で足せます。

置いた道具がどれだけ効くのかは、Chapter 5 で新しい機能を1つ作りながら自分で数えます。
