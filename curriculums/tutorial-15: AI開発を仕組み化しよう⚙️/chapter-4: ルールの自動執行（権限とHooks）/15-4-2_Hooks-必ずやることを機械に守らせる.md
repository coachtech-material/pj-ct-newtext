# 15-4-2: Hooks - 必ずやることを機械に守らせる

## 🎯 このセクションで学ぶこと

- 決まった場面で必ず走る確認を仕込めることを、説明できるようになる。
- `>&2`・`||`・`exit 2` の3つが何をしているのかを、読めるようになる。
- 自動で回ることと、自分の目で見ることの関係を言えるようになる。

---

## 導入：書いてある約束は、守られないことがある

15-1-3 で並べた表に、「毎回必ず起きてほしい確認がある」という行がありました。その行き先が、このセクションで扱う Hooks です。

`CLAUDE.md` に「コードを変えたら、最後にテストを実行してください」と書いたとします。書けば読まれますが、読んで動くのはAIです。15-2-1 で扱ったとおり、書いたことはお願いであって、必ず守られるわけではありません。長い依頼の途中では、抜けることがあります。

守らせ方は、これで3段目になります。1段目が `CLAUDE.md` で、書いて頼む。2段目が 15-4-1 の `deny` で、させたくないことを機械が止める。3段目がここで、やってほしいことを機械が必ず走らせます。

止めるほうは、AIが手を伸ばした瞬間に効きます。走らせるほうは、AIが動いたあとに効きます。どちらも、覚えている人がいなくても成立するところが同じです。

---

## 決まった場面で、必ず走らせる

Hooks（Claude Code が決まった場面で自動的に実行するコマンド）は、`.claude/settings.json` に書きます。15-4-1 で許可リストを書いたのと同じファイルです。

2-1-4「VSCodeの基本設定と拡張機能」で、ファイルを保存したときに自動で整える設定を入れました。考え方は同じで、決まった場面が来たら、機械が勝手に決まったことをします。違うのは、動く場面と、走らせる中身を自分で決められるところです。

この章で仕掛けるのは1つだけです。**AIがファイルを書き換えた直後に、テストを走らせます。** 落ちたら、落ちたことをAIに知らせます。

---

## どこで走らせるか

「決まった場面」として選べるものは、いくつも用意されています。ここでいう場面は、AIがファイルを読み書きしたり、コマンドを打ったりする操作のことで、Chapter 3 で自分が置いた道具のことではありません。この教材で覚えておくのは2つです。

| 場面 | いつ走るか |
|:--|:--|
| 操作の前 | AIがファイルを書き換えたり、コマンドを実行したりする、その直前 |
| 操作のあと | 書き換えや実行が終わった、その直後 |

いま要るのは下の1つだけです。設定ファイルの中では `PostToolUse` という名前で書きます。前に走るほうは、実行してよいかを判定させる場面で使うもので、この教材では扱いません。

絞り込みは、もう一段あります。AIがした操作の種類です。名前の付け方は 15-4-1 の許可リストと同じで、今回選ぶのは、ファイルを書き換えたとき（`Edit`）と、ファイルを新しく作ったとき（`Write`）の2つです。設定では `Edit|Write` と書きます。

> ⚠️ **注意**: ここでの `|` は「または」という意味の区切りです。14-4-4「AIとデバッグする」で使った、左のコマンドの出力を右へ渡す `|` とは、別の場所の話です。

---

## 1行の中身を読む

書く場所と場面が決まったので、走らせる中身を見ます。次に示すのは **`.claude/settings.json`** に足すことになる部分だけを取り出したものです。書き足すのは次のセクションなので、ここでは読むだけです。

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "./vendor/bin/sail artisan test >&2 || exit 2"
          }
        ]
      }
    ]
  }
}
```

`hooks` の中に場面の名前（`PostToolUse`）、その中に条件（`matcher`）と実行するコマンド、という2段の入れ子です。`hooks` という名前が内側にもう一度出てきますが、内側は「走らせるものの一覧」という意味で、外側とは別のまとまりです。中身のあるのは最後の `command` の1行だけで、あとはその1行をどこに差し込むかを表しています。

その1行は、3つに分かれます。

| 書き方 | 何をしているか |
|:--|:--|
| `./vendor/bin/sail artisan test` | 14-4-1 から使っているテストのコマンドです |
| `>&2` | このコマンドが出した文字を、AIにも届く側へ流します |
| `\|\| exit 2` | 左が失敗したときだけ、`exit 2` を実行します |

`||` は `&&` の反対だと思ってください。`&&` は左がうまくいったときに右へ進み、`||` は左が失敗したときだけ右へ進みます。

`exit 2` の `2` は、終了コード（コマンドが終わるときに返す、うまくいったかどうかを表す数字）です。コマンドは終わるときに数字を1つ返していて、0はうまくいった、0以外は失敗、という決まりになっています。ふだんは目に見えませんが、`exit` と書くと自分で決めて返せます。`>&2` にも `2` が付いていますが、こちらは出し先を表す番号で、`exit 2` の `2` は終わり方を表す番号です。並んでいるだけで、別のものです。

Claude Codeは、この数字を見ています。`2` を受け取ると、それを失敗として扱い、失敗の中身をAIへ送り返します。書き換えたファイルが元に戻るわけではありませんが、AIはそのまま先へ進まずに、落ちた中身を読むことになります。だから `exit 2` は、Claude Codeへの「やり直して」の合図になっています。

### 落ちたときだけ、AIに届く

テストが落ちると、編集の直後に、落ちたことを知らせる行が画面に出ます。同じ内容がAIにも届くので、AIは原因を読んで直そうとします。

ここで、書き方を2か所まちがえると、届き方が変わります。

`2` ではなく `1` を返すと、失敗はあなたには見えますが、AIには届きません。Claude Codeは `1` を「知らせるだけの失敗」として扱い、そのまま先へ進みます。それでは、落ちたことに気づいて直しにいく役は、あなたのままです。

`>&2` を付けないと、AIには「何かが失敗した」ことしか伝わりません。テストの出力は、この書き方を付けないと届かない側へ出るからです。落ちたテストの名前も、落ちた理由も、AIの手元には残りません。

そして、いちばん驚くのはここです。**通ったときは、画面に何も表示されません。** 無反応が合格です。何も出ないので動いていないように見えますが、走ったうえで通っている状態です。

ただし、何も出ないと分かるまでには間があります。テストはDocker越しに動くので、時間がかかります。編集のあとに返事が止まったように見えても、そこで待ってください。

15-1-2 で、AIに検証を回させると輪が閉じる、という話をしました。ここがその実物です。テストを実行するのも、結果を読むのも、直してもう一度回すのも、AIの側で完結します。

## 自動で回っても、最後の1回は自分で打つ

14-4-1「テストで検証する - まず機械に聞く」で、`failed` が消えたことを自分の目で見る、と決めました。機械が先に知らせてくれるようになっても、最後の1回は自分で打ちます。

Hooks が塞ぐのは、押し忘れです。「テストを回すのを忘れた」「回したけれど結果を読まずに次へ行った」という取りこぼしが起きなくなります。塞がないのは、判断のほうです。テストが通っているという事実は、受け入れ条件を満たしているという意味ではありません。14-4-3 でやった受け入れ条件との突き合わせは、これまでどおり自分の手で残ります。

もう1つ、AIの報告と、自分で見た結果は別のものだ、という 14-1-4 の線もそのままです。「テストは通りました」という文章は、AIが自動で回した場合でも、やはり文章です。証拠になるのは、自分の手で回した実行結果です。

## 仕掛ける前に、中身を読む

`.claude/settings.json` に書いたコマンドは、Claude Codeが自動で実行します。誰の権限で実行されるのかを、公式ドキュメント（2026年8月時点）は次のように書いています。

> コマンド フックはユーザー アカウントの完全な権限でシェル コマンドを実行します。ユーザー アカウントがアクセスできるファイルを変更、削除、またはアクセスできます。フック コマンドを設定に追加する前に、すべてのフック コマンドを確認してテストしてください。

自分で書いたものなら、中身は自分が知っています。問題になるのは、他人が書いた設定を持ってきたときです。

15-4-1 で見たとおり、フォルダを信頼するかを聞かれる画面は、そのフォルダで先に許可されている操作を見せてくれます。ただし、この画面は Hooks のことを教えてくれません。知らないリポジトリを手元に持ってきたときは、Claude Codeを起動する前に `.claude/settings.json` を開いて、中を自分の目で見てください。

## 💡 よくある間違い

**通ったのに何も出ないので、動いていないと思う**

いちばん多い勘違いです。通ったときは無反応です。動いているかどうかを確かめたいときは、テストが落ちる状態をわざと作って、知らせが出ることを見ます。手順は次のセクションで組みます。

**落ちたことを、自分だけが見える形にしてしまう**

`>&2` を落としたり、`exit 2` を `exit 1` にしたりすると、この形になります。画面には出るのに、AIは直しにいきません。自動で回している意味が半分なくなります。

**自動で回るから、自分でテストを打たなくていいと思う**

回るのはAIが編集した直後だけです。自分でファイルを直したときには走りません。締めの1回は、これまでどおり自分で打ちます。

**設定のファイルに `//` で説明書きを入れる**

11-1-3「JSONとは」で学んだとおり、この形式にコメントは書けません。1行入れただけで、`hooks` も `permissions` も丸ごと読めなくなります。エラーも警告も出ないので、気づけるのは「動かない」と分かったあとです。

## ✨ まとめ

- Hooks は、決まった場面が来たときにClaude Codeが自動で実行するコマンドです。書く場所は `.claude/settings.json` で、15-4-1 の許可リストと同じファイルです。
- この教材で使うのは、AIが操作をしたあとに走るものです。ファイルを書き換えたとき（`Edit`）と、新しく作ったとき（`Write`）に絞ります。
- 走らせる中身は1行です。`>&2` で出力をAIへ届く側へ流し、`|| exit 2` で、落ちたときだけ「やり直して」を返します。
- 落ちるとAIに中身が届き、AIは原因を読んで直そうとします。通ったときは、画面に何も表示されません。
- 塞げるのは押し忘れだけです。`failed` が0であることを自分の目で見る、という 14-4-1 の作法は、これまでどおり残ります。

形は分かりました。次の 15-4-3 では、これを自分のアプリに仕掛けます。仕掛けたあと、本当に効いているかどうかを、落ちる状態を自分で作って確かめるところまでをやります。
