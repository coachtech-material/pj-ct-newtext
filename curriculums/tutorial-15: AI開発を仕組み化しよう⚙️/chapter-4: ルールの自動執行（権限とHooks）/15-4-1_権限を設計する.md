# 15-4-1: 権限を設計する

## 🎯 このセクションで学ぶこと

- 許可の指定を書く場所の違いを知り、書いたものが誰に効くのかを理解する。
- 触らせたくないファイルを止め、手元の外へ出ていく操作は必ず聞かせる形に組み直せるようになる。
- 毎回の承認が要らないコマンドを選び、どれを聞かれたまま残すのかを判断できるようになる。

---

## 導入

Chapter 2 と Chapter 3 で置いてきたものは、どれもAIが読んで、読んだうえでどう動くかを決めるものでした。ここから置くのは、AIの判断を通らない層です。何に触れてよいかの指定を守らせているのはClaude Code自身で、モデルの側ではありません（公式ドキュメント・2026年8月時点）。

auto で動いているClaude Codeは、実行しようとしている操作が依頼の範囲を超えていないかを検査してから、自分で進みます（14-1-5）。検査役が見ているのはそこまでです。このアプリで `.env` を開いてよいか、いま `git push` してよいかは、依頼の範囲の内側にあるかどうかとは別の話になります。触らせないもの、必ず聞かせるものは、こちらから書いておきます。

## 設定ファイル

似た名前のファイルが3つ出てきます。効く範囲が違うので、先に並べておきます。

| ファイル | 効く範囲 | 中身を決めるのは |
|:--|:--|:--|
| `.claude/settings.json` | このフォルダを開いた人全員 | あなた（リポジトリに入れて共有する） |
| `~/.claude/settings.json` | 自分のPCで開くフォルダ全部 | あなた（自分のPCの中だけ） |
| `.claude/settings.local.json` | 自分のPCの、このフォルダ | Claude Code（押した承認から自動で溜まる） |

上の2つは、何を書くかを決めるのがあなたで、打ち込みはClaude Codeに頼めます（15-1-3）。いちばん下だけ、中身までClaude Codeが決めます。

1つ目が、このセクションで書くファイルです。プロジェクトの設定なので、リポジトリに入れます。次にこのフォルダを開いた人が、同じ許可の状態で始められます。多くの場合、その人は来月の自分です。

2つ目は、プロジェクトをまたぐ自分の好みを書く場所です。下の `defaultMode` はここに書きます。

3つ目は、自分では作りません。承認画面で「今後は聞かない」にあたる選択肢を選ぶと、その内容がこのファイルに自動で書き足されます。自分のPCの中だけに置くものなので、コミットには入れません。Claude Codeがこのファイルを作ったときは、Gitの除外にも自動で足されます。

> 💡 **TIP**: Tutorial 2 で見た VS Code の `settings.json` とは別のファイルです。あちらはエディタの見た目や保存時の動きを決めるもので、名前が同じなだけです。

### defaultMode

`Shift+Tab` で切り替えたモードは、そのセッションのあいだだけ効きます。次に起動したときにどのモードで始まるかを決めているのが `defaultMode` です。2026年8月時点では、Pro・Max・Teamの新しいセッションは auto で始まります。14-1-5 のとおりに `Shift+Tab` で切り替えてきただけなら、既定は変えていません。ここは読み飛ばして構いません。自分で `~/.claude/settings.json` を書いて既定を変えたことがある人だけ、次を書いてください。

**`~/.claude/settings.json`**

```json
{
  "permissions": {
    "defaultMode": "auto"
  }
}
```

このファイルが無ければ、新しく作ります。すでに `{` から始まる中身があるなら、その中に `permissions` を並べます。

書く場所に、1つだけ決まりがあります。`auto` を既定にする指定は、プロジェクトの `.claude/settings.json` に書いても効きません（2026年8月時点）。`.claude/settings.local.json` に書いた場合も同じです。この制限が付いているのは `auto` だけで、たとえば `"defaultMode": "plan"` をプロジェクト設定に書けば、そのフォルダの既定になります。

このあと書く `deny`・`ask`・`allow` のほうは、プロジェクト設定に書いたものがそのまま効きます。ここから先は、`.claude/settings.json` の話です。

## 許可の指定

`permissions` の中に書く `deny`・`ask`・`allow` の3つのまとまりが、**許可の指定**です。それぞれ、止めるもの、必ず聞かせるもの、聞かずに通すものを並べます。このあとの 🏃 で書かせると、**`.claude/settings.json`** はこの形になります。先に全体を読んでおきます。

```json
{
  "permissions": {
    "deny": [
      "Read(.env)",
      "Read(.env.*)",
      "Edit(.env)",
      "Edit(.env.*)"
    ],
    "ask": [
      "Bash(git push *)"
    ],
    "allow": [
      "Bash(./vendor/bin/sail test *)",
      "Bash(sail test *)"
    ]
  }
}
```

Claude Codeは、この3つを `deny` → `ask` → `allow` の順に見て、**最初に一致したものが結果を決めます。** どちらが具体的に書かれているかは関係ありません。`allow` に細かく書いたコマンドでも、`deny` の広い1行に当たれば止まります。同じことが `ask` と `allow` のあいだにも起きるので、`allow` に書いたコマンドが `ask` にも当たれば、聞かれます。

1行ずつの書き方は共通です。かっこの前が操作の種類で、`Bash` はコマンドの実行、`Read` はファイルを読むこと、`Edit` はファイルを書き換えることを指します。かっこの中に、その対象を書きます。

> ⚠️ **注意**: JSONのファイルには `//` で始まる説明書きを入れられません（11-1-3）。1行入れただけで設定として読めなくなり、書いたものが1行も効かなくなります。しかも、エラーも警告も出ません。この教材ではコードブロックの1行目にファイルの場所をコメントで書いてきましたが、この形式ではそれができないので、ファイル名はコードブロックの外に書いています。書かせたものを読むときも、この1行が混じっていないかを見ます。

### deny

`deny` は、AIがそこへ手を伸ばした時点で止めます。承認するかどうかを自分が選ぶ場面にもなりません。

止めているのは `.env` と、`.env.local` のような派生ファイルです。読むほうの指定は 14-1-5 で書いたものをそのまま置き、書き換えるほうの指定をここで足しました。どの道具からも変えさせない形にするためです。

止まる範囲は 14-1-5 の表のとおりです。Claude Codeがファイルを開く経路と、`cat`・`head`・`tail`・`sed` のように中身を読むコマンドは止まります。PHPやPythonのスクリプトが中で開く経路は止まりません。設定は金庫ではないので、秘密の値そのものを依頼の文章に貼らない、という自分の側の線は別に持っておきます。

> ⚠️ **注意**: `Read` と `Edit` の指定は、`.gitignore` と同じパターンの書き方です。`.env.*` は `.env.local` と一緒に `.env.example` も指します。`.env.example` は 14-1-2 で `cp .env.example .env` と打ったファイルで、秘密の値は入っていませんが、これも一緒に止まります。中身を見たいときは、自分の端末で開いてください。

### ask

14-1-5 で、慎重になるのは影響が手元の外へ出ていくものに触るとき、と決めました。物差しは、その作業の結果が自分の手元の中で終わるかどうかです。例として挙げたのが、本番で動いているデータ、秘密の値、外部への公開でした。秘密の値は、外へ出る手前でAIに触らせない形にして、`deny` で止めました。残りのうち、この演習で実際に起きるのが外部への公開で、`git push` がそれにあたります。手元のコミットはいくらでもやり直せますが、GitHubへ送ったものは取り消せません。

`ask` に書いたものは、**auto で動いていても承認画面が出ます**。auto は検査役の判断で自動承認するモードですが、許可の指定に当たった操作は検査役を通らず、その場で決まります。手元の外へ出ていく操作について、人が止まる場所を作り直すのが `ask` の役目です。

`*` は、この後ろに何が続いても、という印です。`git push origin main` のように後ろが続く形も、`git push` とだけ打たれた形も、この1行で当たります（2026年8月時点）。

本番のデータベースを作り替えるコマンドも、同じ考え方でここへ入れます。この演習で使っているのは練習用のデータベースで、消えても `migrate --seed` で作り直せるので、いまは入れていません。

### allow

14-1-5 の最後に、`deny` の反対の「これは毎回聞かなくてよい」という指定もある、と書いてありました。それが `allow` です。

入れたのはテストを回すコマンドだけです。何度も打つうえ、中身を確かめなくても困りません。2行あるのは、同じコマンドの打ち方が2通りあるからです。9-1-2 で `sail` という短縮名を登録しているので、AIがどちらの形で打っても効くように両方書いています。`--filter` を付けた形も、何も付けない形も、それぞれの1行で当たります。

書かないものも決めておきます。`git status` や `ls` のような読むだけのコマンドは、Claude Codeが最初から承認なしで通します。この一覧は設定で変えられないので、書いても動きは変わらず、行数が増えるぶん、本当に許したものが埋もれます。`Bash(./vendor/bin/sail *)` のような広い書き方もしません。1行で承認はほとんど出なくなりますが、`sail` の後ろに何が続いても通るようになります。

イシューを立てさせる操作（14-3-3）のような、外へ通信するコマンドも入れません。承認のたびに確認を押していたのはここです（14-5-4）。ただ、GitHubへ送ったものは取り消せません。`git push` と同じ扱いにして、聞かれたままにしておきます。Chapter 5 でも `gh` の承認画面は出ます。

承認を全部消すのが、この設計の目的ではありません。押す回数は減らして、手元の外へ出ていくものは残します。

auto で動いているあいだは、`allow` に書かなくても止まらないことがほとんどです。それでも書いておきます。検査役の判断を待たずに通り、次にこのフォルダを開いた人が同じ状態で始められ、何を許したのかが1か所に読める形で残ります。

## 書いたのに聞かれるとき

承認画面に出ているコマンドの文字列と、自分が書いた指定を見比べます。

いちばん多いのは打ち方のズレです。`./vendor/bin/sail test` と `sail test` は、別の文字列として扱われます。片方しか書いていなければ、もう片方は聞かれます。

次に多いのが、`&&` でつないだコマンドです。Claude Codeはつないだものを1つずつ別々に見るので、片方でも書いていなければ全体が止まります。

いま何が効いているかは、Claude Codeで `/permissions` と打つと一覧で読めます。指定ごとに、どのファイルから読まれたものかも並びます。押してしまった「今後は聞かない」を消すのも、この画面からです。

## 🏃 設定を書いて、効き方を見る

アプリが止まっている場合は、Docker Desktop（またはDocker Engine）を起動してから、Sailを立ち上げます。

```bash
# アプリのフォルダへ移動して、Sailを起動する
cd ~/laravel-practice/post-app-practice
./vendor/bin/sail up -d
```

思いどおりに直らない・壊れたと感じたら、14-5-1（直らないときの型）へ進んでください。まだコミットしていない変更は `git restore .` で元に戻せます。

### Step 1: 設定を書かせる

Claude Codeを起動します。

```bash
claude
```

設定ファイルも、書かせて構いません（15-1-3）。渡すのは、何をどう扱いたいかです。

```text
.claude/settings.json の permissions を書き足したい。いま入っている deny はそのまま残して。

- git push は、auto で動いていても必ず聞いてほしい
- テストを回すコマンドは、聞かずに通してほしい（sail の短縮名で打つ形も含めて）
- gh は聞かれたままでいい

書いたら、settings.json 全体を見せて。
```

出てきたものを読みます。見るのは、14-1-5 で書いた `deny` が残っているか、`ask` と `allow` が上で決めたとおりに分かれているか、そして `//` で始まる行が1行も入っていないかです。JSONはコメントを許さない書き方なので、`//` が1行あるだけで、この設定は丸ごと読めなくなります。

書き換えた設定は、Claude Codeが見張っていて、保存すると読み直されます。`permissions` と `hooks` は、起動し直さなくてもそのまま効きます（2026年8月時点）。ただし、**ファイルを新しく作ったとき**や、書いたのに効いていないように見えるときは、開き直してから確かめてください。`claude -c` で開き直せば、それまでのやり取りは引き継いだままです（14-5-2）。

## 💡 よくある間違い

**「今後は聞かない」を押して、許可を育てる**

押した分は `.claude/settings.local.json` に溜まっていくので、一見すると同じことに見えます。違うのは、読まずに押した1回もそのまま残ることと、溜まる先が自分のPCの中で共有できないことです。

**広く書いて、承認をゼロにする**

`Bash(./vendor/bin/sail *)` のように短く書けたときほど、何を許したのかを読み直してください。許可の指定は自分用のメモではなく、次にこのフォルダを開いた人への約束です。広く書けば、その広さがそのまま渡ります。

## ✨ まとめ

- 共有する `.claude/settings.json`、自分のPCだけの `~/.claude/settings.json`、Claude Codeが自動で書き足す `.claude/settings.local.json` を、書く前に選ぶ。
- `auto` を既定にする `defaultMode` は、ユーザー設定にだけ書く。`deny`・`ask`・`allow` はプロジェクト設定でそのまま効く。
- 許可の指定は `deny` → `ask` → `allow` の順に見られ、最初に一致したものが結果を決める。具体的に書いたほうが勝つ、という順序ではない。
- `deny` はAIが手を伸ばした時点で止める。`cat` のようなコマンド経由も止まるが、スクリプトが中で開く経路までは止まらない。
- `ask` は auto でも承認画面を出す。手元の外へ出ていく操作は、押す回数を減らす対象にしない。
- `allow` に書いておくと、検査役の判断を待たずに通り、次にこのフォルダを開いた人にも同じ許可が渡る。読むだけのコマンドと、広く当たる書き方は書かない。
