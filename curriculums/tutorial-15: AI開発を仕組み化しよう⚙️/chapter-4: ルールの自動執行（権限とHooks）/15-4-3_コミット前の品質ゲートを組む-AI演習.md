# 15-4-3: コミット前の品質ゲートを組む - AI演習

## 📌 この演習について

15-4-2 で読んだ1行を、自分のアプリに仕掛けます。ここで組むのは品質ゲート（次へ進む前に、機械が必ず通す確認）です。2本立てにします。

1. **必ずテストが回る**。AIがファイルを書き換えたら、その直後にテストが走り、落ちたらそのままでは先へ進めません。
2. **触ってはいけないファイルが守られる**。`.env` を読ませようとしても、機械が止めます。

2つ目は、15-4-1 で書いた `deny` の2行が担います。このセクションで書き足すのは1つ目だけで、2つ目は効き目を確かめるだけです。

タイトルに「コミット前」と書きましたが、コミットするタイミングで何かが動くわけではありません。編集のたびに回るので、コミットするときには通っている状態になっている、という意味です。

> 🔥 ここからは、AIに実装を任せて構いません。ただし「任せる」と「丸投げ」は違います。何を作るかは設計書で自分が決め、出てきたものはテスト・動作確認・コードレビューで自分が検証します。品質の責任は、AIではなくあなたが握ります。

## 🎯 演習課題

### 📋 課題

使う材料は2つです。Chapter 2 で書いた `CLAUDE.md` と、15-4-1 で書いた `.claude/settings.json` です。どちらも、すでに手元にあります。

このセクションでは、この2つに1つずつ足します。**順番は `CLAUDE.md` が先です。**

| 足すもの | 何を決めるか |
|:--|:--|
| `CLAUDE.md` に1行 | テストが落ちたまま作業を終えない、という約束 |
| `.claude/settings.json` に `hooks` | ファイルを書き換えた直後に、必ずテストを走らせること |

順番に意味があります。設定だけを足すと、機械はテストが落ちたことを知らせますが、AIは直しません。落ちた原因を正しく突き止めたうえで、「依頼はこれだけだったので、そこには手を付けていません。直してよければ対応します」と聞き返して終わります。機械が指摘するところまでが設定の仕事で、指摘されたら直す、を決めるのが `CLAUDE.md` の1行です。

`CLAUDE.md` には、テストを実行して出力をそのまま見せてほしい、という行を書いた人も多いはずです。それは報告のしかたを決める行で、今回足すのは、落ちたまま終わらせないことを決める行です。別のことなので、両方あって構いません。

そのうえで、仕掛けが本当に生きているかを自分で確かめます。**わざと1回落とすところまでが、この演習です。**

### ✏️ 進め方タスク

1. 【自分】`./vendor/bin/sail up -d` でSailを起動し、Claude Codeを起動する
2. 【自分】`CLAUDE.md` に、テストが落ちたまま終わらせないための1行を足す
3. 【自分】`.claude/settings.json` に、編集のたびにテストを回す設定を足す
4. 【自分】`.claude/settings.json` を開いて、`hooks` が書かれていることを確かめる
5. 【自分】コメント本文の入力チェックを1文字だけ書き換えて、自分でテストを打って `failed` が出ることを確かめる
6. 【自分⇄AI】動きを変えない小さな変更を1つ頼み、ゲートが落ちるところと、AIが直すところを見る
7. 【自分】自分でテストを打ち直して、`failed` が0であることを確かめる
8. 【自分⇄AI】もう一度、動きを変えない小さな変更を頼み、通ったときは画面に何も出ないことを確かめる
9. 【自分⇄AI】`.env` の値を聞いてみて、止まることを確かめる
10. 【自分】`CLAUDE.md`・`.claude/settings.json`・AIが手を入れた `app/` の変更をコミットして push する

## 💡 ヒント

詰まったときの粘り方は 14-4-5「うまくいかない時の型」のとおりです。巻き戻す、小さく分ける、2回直らなければ仕切り直す、の3つで足ります。この演習に固有のものを4つ足しておきます。

**テストが回らない**

Sailが起動しているかを確認してください。

```bash
# アプリのフォルダの中で実行する
./vendor/bin/sail up -d
```

**何をしても、ゲートが動いていないように見える**

まず `.claude/settings.json` を開いて、`//` で始まる行が入っていないかを見てください。1行入っているだけで、`hooks` も `permissions` も丸ごと読めなくなります。閉じ括弧やカンマの過不足も同じです。どちらも問題が無ければ、いったんClaude Codeを終了して起動し直してから、もう一度 Step 5 を試してください。

**入力チェックを書き換えたのに、テストが落ちない**

入力チェックが別のファイルに書かれていることがあります。そのときの手当ては、このあとの Step 4 の折りたたみに書いてあります。

**AIが、書き換わっていた1行を戻さずに聞き返してくる**

戻してよいかを聞かれたら、戻すように答えます。そのあとの確かめ方は、このあとの「📖 進行例」の最後に書いてあります。

## 🏃 実践：一緒に進めてみましょう

### 🧠 先輩エンジニアの思考プロセス

自分で進めてみて詰まったら、ここから先を読んでください。何を渡し、どこで承認し、何で検証するのかを、場面ごとに並べます。

| 場面 | 何を渡すか | どこで承認するか | 何で検証するか |
|:--|:--|:--|:--|
| ルールを足す | `CLAUDE.md` の1行 | 自分で書くので承認は無い | ファイルを開いて、守ってほしいことの並びに入っているかを読む |
| 仕掛けを足す | `.claude/settings.json` の `hooks` | 自分で書くので承認は無い | ファイルを開いて、`permissions` が消えていないかを読む |
| 仕掛けを試す | 動きを変えない小さな依頼 | AIが出した差分を読んで承認する | 編集の直後にテストが走り、落ちたことが画面に出る |
| 直ったことを見る | （渡さない） | AIが戻す差分を読んで承認する | 自分で `./vendor/bin/sail artisan test` を打って `failed` が0であることを見る |
| 守りを試す | `.env` の値を聞く依頼 | 承認は出ない（止まる） | 値が返ってこないことを見る |

### 📝 ステップバイステップ

アプリが止まっている場合は、Docker Desktop（またはDocker Engine）を起動してから、Sailを立ち上げます。

```bash
# アプリのフォルダの中で実行する
cd ~/laravel-practice/14_hands-on/authorization-app-ai
./vendor/bin/sail up -d
```

#### Step 1: CLAUDE.md に1行足す

`CLAUDE.md` を開いて、守ってほしいことを並べたところの末尾に、次の1行を足します。見出しの名前は人によって違うので、進め方や約束を並べた箇所を探してください。

```markdown
- テストが落ちた状態で作業を終えないでください。原因が自分の変更以外にあっても、直してから終わってください。
```

後半が肝心です。「原因が自分の変更以外にあっても」が無いと、AIは自分が触っていない場所には手を出しません。

#### Step 2: 設定に hooks を足す

**`.claude/settings.json`** を、次の形にします。`permissions` は 15-4-1 で書いたままで、`hooks` を足しただけです。

```json
{
  "permissions": {
    "allow": [
      "Bash(./vendor/bin/sail artisan test *)",
      "Bash(sail artisan test *)",
      "Bash(./vendor/bin/sail artisan route:list *)",
      "Bash(sail artisan route:list *)"
    ],
    "ask": [
      "Bash(./vendor/bin/sail artisan migrate *)",
      "Bash(./vendor/bin/sail artisan migrate:fresh *)",
      "Bash(./vendor/bin/sail artisan db:seed *)",
      "Bash(git push *)"
    ],
    "deny": [
      "Read(./.env)",
      "Edit(./.env)"
    ]
  },
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "./vendor/bin/sail artisan test >&2 || exit 2"
          }
        ]
      }
    ]
  }
}
```

`permissions` と `hooks` の間のカンマを忘れないでください。`//` で始まる行は、1行も入れません。

このファイルは、保存すればそのまま効きます。ふだんは起動し直す必要はありません。ただし、保存したのに Step 5 でゲートが動かないときは、いったんClaude Codeを終了して、起動し直してから試してください。

#### Step 3: 書けたことを、ファイルを開いて確かめる

保存した `.claude/settings.json` を、VS Codeでもう一度開いて読みます。見るのは3つです。

- `hooks` が書かれていること
- `permissions` の `allow`・`ask`・`deny` が、3つとも残っていること
- `//` で始まる行が、1行も入っていないこと

ここは目で読むだけなので、Dockerが起動していなくても確かめられます。効いているかどうかは、このあとの Step 4 と Step 5 で見ます。

#### Step 4: 落ちる状態を、自分の手で作る

14-4-4「AIとデバッグする」でも、1行だけ書き換えてわざと壊しました。あちらは自分でログを追いかけて直しました。ここでは、機械が見つけて、AIが直します。

`app/Http/Controllers/CommentController.php` を開いて、コメントの本文の入力チェックを探します。次のような行があるはずです。

```php
// app/Http/Controllers/CommentController.php
$request->validate([
    'body' => 'required|string|max:500',
]);
```

書き方はAIが書いたものなので、並び順や書式は手元で少し違うかもしれません。探すのは `max:500` の部分です。ここに `0` を1文字足して、上限を5000文字にします。

```php
// app/Http/Controllers/CommentController.php（わざと書き換えた状態）
$request->validate([
    'body' => 'required|string|max:5000',
]);
```

これで、`docs/comment/screen.md` の入力チェック表に書いた「500文字以内」と、コードが食い違った状態になります。

書き換えたら、**自分でテストを打ちます。** `failed` が出ることを、ここで確かめます。

```bash
# アプリのフォルダの中で実行する
./vendor/bin/sail artisan test
```

落ちるのは、本文が501文字だと登録できないことを確かめているテストです。14-2-4「AIと設計書を作る」でテスト観点表に `TC-05` として書いた行が、いまの食い違いを捉えています。

<details>
<summary>`max:500` の行が見つからないとき・書き換えても `failed` が出ないとき（クリックで展開）</summary>

Tutorial 14 では、入力チェックはコントローラーの `validate()` に書きました。ただし、9-6-4「フォームリクエスト」で学んだ形に自分で寄せていた場合は、同じ内容が `app/Http/Requests/` の中のファイルに書かれています。その場合は、そのファイルの同じ行を書き換えてください。戻すときも同じ行です。

それでも `failed` が出ないときは、上限ではなく必須のほうを外します。同じ行から `required|` を消すと、本文が空でも登録できるようになるので、本文が空だとコメントは増えないことを確かめているテストが落ちます。

```php
// app/Http/Controllers/CommentController.php（わざと書き換えた状態）
'body' => 'string|max:500',
```

</details>

この確認を飛ばすと、あとの Step でゲートが落ちません。落ちないのを見て「仕掛けが効いていない」と勘違いすることになるので、ここは必ず自分の目で見てください。

#### Step 5: 普通の依頼を1つして、ゲートが落ちるところを見る

Claude Codeを起動して、動きを変えない小さな依頼を1つします。

```text
app/Http/Controllers/CommentController.php の store() に、何をしている処理なのかを説明する日本語のコメントを1行足してください。
```

> 💡 このプロンプトのポイントは、①動きを変えない依頼にしている（ゲートが落ちた原因を、いま足したものと取り違えないため）②ファイルと場所を名指ししている、の2点です。

差分を読んで承認すると、その直後にテストが走ります。Docker越しに動くので、しばらく返事が止まったように見えます。

テストは落ちます。落ちたことを知らせる行が画面に出て、同じ内容がAIにも届きます。AIは原因を読み、Step 4 で書き換えた入力チェックの1行にたどり着きます。そして `CLAUDE.md` の1行があるので、自分が書き換えたものではない1行を、元に戻そうとします。

戻す差分も承認の対象です。何をどう戻そうとしているのかを読んでから承認してください。直すのは入力チェックのほうで、テストのほうではありません。14-4-1「テストで検証する - まず機械に聞く」で、落ちたテストを消したり緩めたりして通すのは禁じ手だと決めました。テストを書き換える差分が出てきたら、そこは承認せずに、入力チェックを戻すように伝えてください。

通ったあと、最後に自分でテストを打ちます。

```bash
# アプリのフォルダの中で実行する
./vendor/bin/sail artisan test
```

`failed` が0であることを、自分の目で見てください。14-4-1 で決めた作法は、機械が先に回してくれるようになっても変わりません。

#### Step 6: 通ったときは何も出ないことを確かめる

もう一度、動きを変えない小さな依頼をします。今度は落ちる材料がありません。

```text
app/Http/Controllers/PostController.php の index() に、何をしている処理なのかを説明する日本語のコメントを1行足してください。
```

> 💡 Step 5 と同じ形の依頼です。違うのは、落ちる材料がもう残っていないことだけです。同じ形にしておくと、出方の違いだけを見比べられます。

差分を承認したあと、しばらく待ちます。**何も表示されなければ、テストが走って通っています。** 無反応が合格の合図です。

Step 5 との違いは、落ちたかどうかだけです。どちらの場合も、編集の直後にテストは走っています。

#### Step 7: 触ってはいけないファイルが守られることを確かめる

15-4-1 で書いた `deny` の2行を試します。

```text
.env の APP_KEY の値を教えてください。
```

> 💡 これは、値を知るための依頼ではありません。**止まることを確かめるための依頼です。** この演習のアプリの `.env` は練習用のダミーですが、止まる形を先に見ておきます。

承認画面は出ません。読み取りそのものが止まるので、AIは値を答えられません。承認して通すか止めるかを自分が選ぶ、という場面にすらならない、というのが `deny` の効き方です。

#### Step 8: コミットして push する

コミットする前に、`app/` に余計な差分が残っていないかを見ます。Step 4 で書き換えた入力チェックはAIが戻しているはずですが、`max:500` に戻っているかを自分の目で確かめます。戻っていなければ、自分で戻します。

```bash
# アプリのフォルダの中で実行する
git status
git add CLAUDE.md .claude app
git commit -m "Add quality gate for Claude Code"
git push origin main
```

15-4-1 と同じく、ブランチは切っていません。機能を作る作業ではないからです。

## 📖 進行例

> 💡 **進行例について**: AIとの開発は毎回違う流れになります。ここに示すのは一つの進行例です。あなたの画面と違っていても、チェックリストを満たしていれば正解です。

Step 5 のやり取りは、たとえば次のように進みます。

```text
あなた: app/Http/Controllers/CommentController.php の store() に、何をしている処理なのかを
        説明する日本語のコメントを1行足してください。
Claude Code: （コメントを1行足す差分が出る。読んで承認する）
Claude Code: （編集の直後にテストが走る。しばらく間があってから、落ちたことを知らせる行が出る）
Claude Code: （落ちた理由を説明する。本文の入力チェックの上限が max:5000 になっていて、
             501文字が通ってしまうと伝えてくる）
Claude Code: （CLAUDE.md のルールに従って、上限を max:500 に戻す差分を出す。読んで承認する）
Claude Code: （もう一度テストが走り、今度は何も出ない）
あなた: （自分で ./vendor/bin/sail artisan test を打ち、failed が0であることを見る）
```

承認したのは2回です。1回目はコメントを足す差分、2回目は入力チェックを `max:500` に戻す差分です。どちらも、読んでから通しています。仕掛けを足したあとも、差分を読む場所は減っていません。増えたのは、読む前に機械が1度チェックを通していることです。

AIが2回目の差分を出さずに、「戻してよいですか」と聞き返してくることもあります。そのときは戻すように答えてください。そのうえで `CLAUDE.md` の1行が効いているかを見たい場合は、`/clear` してからもう一度同じ手順を試します。やり取りに残った自分の発言が消えるので、`CLAUDE.md` だけが根拠の状態になります。

## 🚀 まとめ

Chapter 2 から置いてきたものが、これで4つになりました。`CLAUDE.md`、`.claude/agents/` の1本、`.claude/skills/` の1本、そして `.claude/settings.json` です。Chapter 1 で言い出した「同じ説明を二度としない」は、この4つの形になりました。

このセクションで分かったのは、機械に守らせるには2つが要る、ということです。設定は「テストが落ちた」と指摘するところまでを担い、`CLAUDE.md` の1行が「指摘されたら直す」を担います。片方だけでは、AIは落ちたことを報告して止まります。

そして、機械が先に知らせてくれるようになっても、締めの1回は自分で打ちます。`failed` が0であることを自分の目で見る、というやり方は、Tutorial 14 から何も変わっていません。

整形の自動化は、Tutorial 16 で Laravel Pint を学んだあとに、同じやり方で足せます。

道具は4つそろいました。次のChapter 5では、この4つを全部持ち込んだ状態で、新しい機能を1つ作ります。設計から実装、検証、マージまでを回して、置いた道具がどれだけ効くのかを自分で数えます。
