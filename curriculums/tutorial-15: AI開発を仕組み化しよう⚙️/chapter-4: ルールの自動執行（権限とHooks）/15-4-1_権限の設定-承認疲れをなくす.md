# 15-4-1: 権限の設定 - 承認疲れをなくす

## 🎯 このセクションで学ぶこと

- 読まなくてよいと自分が決めた承認だけを、設定に書けるようになる。
- 押してしまった「今後は聞かない」がどこに残るのかを知り、取り消せるようになる。
- 触らせたくないファイルを、機械の側で止められるようになる。

## 導入：同じ承認を、何度押しましたか

Chapter 2 で `CLAUDE.md` を書き、Chapter 3 で `.claude/` の中に道具を2つ置きました。残っているのは、15-1-2 で並べた5つのうちの2つ、権限と Hooks です。この2つは、どちらも `.claude/settings.json` に書きます。道具としては別のものですが、置き場所は同じ1つのファイルです。ですからこの章で増えるファイルは1本だけで、そこに書くことが2つある、という形になります。どこまで任せるかを先に決めること（このセクション）と、決まった場面で必ず走らせること（15-4-3）です。

14-1-2「Claude Codeのセットアップと基本操作」で、見慣れない設定のファイルやフォルダが増えても、いまは触らなくてよい、と書いてありました。その中身が、この `.claude/` とその下に置くファイルです。

15-1-3 で並べた表に、「同じ承認を何度も押している」と「絶対に触らせたくないものがある」という2行がありました。どちらの行き先も、この `.claude/settings.json` です。

あわせて、14-1-4「ガードレール - 機密情報と権限の承認」で先送りにした2つを、ここで返します。1つは、あらかじめ設定を書いておいて、機械的に読ませないようにする方法です。もう1つは、押してしまった許可を取り消す方法です。どちらも、この先のTutorialで扱う、と書いたままになっていました。

14-1-4 では、似た確認が続くと、内容を読まずに通すだけのボタンになる、とも書きました。ここでは、読まなくてよいと自分が決めたものを、先に減らします。

> ⚠️ **注意**: ここから先の画面の説明は、2026年8月時点のものです。表示が違っても、読んでから許可するという判断は変わりません。

## 押した「今後は聞かない」は、どこに残るのか

14-1-4 で、承認画面の「今後は聞かない」を選ぶと、コマンドについてはそのプロジェクトでずっと聞かれなくなる、と扱いました。ずっと効くということは、どこかに書き残されているということです。

押した直後、アプリのフォルダに **`.claude/settings.local.json`** というファイルが自動で作られます。次は、`./vendor/bin/sail artisan route:list` を許可したときに書かれた中身です。

```json
{
  "permissions": {
    "allow": [
      "Bash(./vendor/bin/sail artisan route:list *)"
    ]
  }
}
```

中身は、押したコマンドによって変わります。行の最後の `*` は、この後ろに何が続いても、という印です。

このファイルには、性質が2つあります。

- **自分のPCの中にしか残りません。** Claude Codeが、このファイルはGitに載せなくていいと自動で登録してくれるので、`git add .` をしてもコミットには入りません。自分で作る必要はないので、手で作らないでください。
- **読まずに押した1回も、そのまま残ります。** 次に起動したときも効いたままです。

1つ目は、ありがたい仕組みです。自分の手元だけの好みを、他の人に押し付けずに済みます。この先で書く設定のように、リポジトリに入れて共有したいものは、別のファイルに書きます。

困るのは2つ目です。読まずに押した1回は、押した本人にも覚えがありません。だから、消し方を先に知っておきます。

### 押してしまった許可を取り消す

Claude Code で `/permissions` と打つと、いま効いている許可の一覧が開きます。消すのはこの画面からです。JSONを手で書き換える必要はありません。

```text
1. claude を起動する
2. /permissions と打つ
3. ↓キーで、消したいルールに合わせる
4. Enter を押す
5. 消してよいかを聞かれるので Yes を選ぶ
6. Esc で閉じる
```

一覧の1件目は、新しいルールを足すための行です。↓を1回押すとその行、2回押すと最初のルールに合います。

消す前に出る確認画面には、そのルールがどのファイルに書かれていたものかが表示されます。自分のPCだけの設定なのか、リポジトリに入れて共有している設定なのかが、ファイルを開かずに分かります。

> ⚠️ **注意**: 消えたかどうかは、いったんClaude Codeを終了して、起動し直してから確かめてください。同じセッションのまま同じ依頼をすると、AIがそれまでのやり取りを読んで「ルールを消しましたね」と話すだけで、コマンドを試さないことがあります。

この画面からルールを足すこともできますが、この教材では次のとおりファイルに自分で書きます。何を許したのかを、まとめて読める形にしておきたいからです。

## 許可リストを、自分で書く

ここまでは、押してしまったものを消す話でした。ここからは、先に決めておく話です。毎回の承認を省いてよいものを、あらかじめ書いておきます。この一覧を許可リスト（毎回の承認を省いてよいものを、あらかじめ書いておく一覧）と呼びます。

置き場所は `.claude/settings.json` です。15-3-1 で見た `.claude/` の中に、Chapter 3 で置いた道具と並べて置きます。

> 💡 **TIP**: Tutorial 2 で見た VS Code の `settings.json` とは別のファイルです。あちらはエディタの文字の大きさや保存時の動きを決めるもの、こちらはClaude Codeに渡す許可を決めるものです。名前が同じなだけで、置き場所も中身も関係ありません。

書き方は 11-1-3「JSONとは」で学んだJSONです。1つだけ念を押します。この形式のファイルには、`//` で始まる説明書きを入れられません。入れると設定が丸ごと読めなくなり、書いたものが1行も効かなくなります。しかも、エラーも警告も出ません。

この教材ではこれまで、コードブロックの1行目にファイルの場所をコメントで書いてきました。この形式ではそれができないので、ここから先は、ファイルの名前をコードブロックの外に書きます。書き写すときも、その1行は足さないでください。

**`.claude/settings.json`** に、次を書きます。

```json
{
  "permissions": {
    "allow": [
      "Bash(./vendor/bin/sail artisan test *)",
      "Bash(sail artisan test *)",
      "Bash(./vendor/bin/sail artisan route:list *)",
      "Bash(sail artisan route:list *)"
    ],
    "ask": [
      "Bash(./vendor/bin/sail artisan migrate *)",
      "Bash(./vendor/bin/sail artisan migrate:fresh *)",
      "Bash(./vendor/bin/sail artisan db:seed *)",
      "Bash(git push *)"
    ],
    "deny": [
      "Read(./.env)",
      "Edit(./.env)"
    ]
  }
}
```

1行ずつの書き方は、どれも同じ形です。かっこの前が操作の種類で、`Bash` はコマンドの実行、`Read` はファイルを読むこと、`Edit` はファイルを書き換えることを指します。かっこの中には、その対象を書きます。

`.claude/settings.local.json` と違って、こちらはリポジトリに入れて共有します。次にこのフォルダを開く人が、同じ許可の状態で始められます。多くの場合、その人は来月の自分です。

> 💡 **TIP**: 新しいフォルダで初めてClaude Codeを起動したときだけ、このフォルダを信頼してよいかを聞かれます。自分で作ったフォルダなら、信頼する側を選びます。許可リストを書いたフォルダでは、その中身も一緒に表示されます。

つまり許可リストは、自分用のメモではありません。次にこのフォルダを開いた人に読み上げられる、約束事です。広く書けば、その広さがそのまま読み上げられます。

保存すると、Claude Codeを起動したままでも効きます。`.claude/` に作ったほかの道具は、作った直後に起動し直す必要がありましたが、この設定ファイルだけは別です。

### allow・ask・deny の3つ

`permissions` の中は、3つのまとまりに分かれています。

| まとまり | 何をするか | ここに書くもの |
|:--|:--|:--|
| `allow` | 聞かずに通す | 中身を確かめなくても困らない、と自分が決めたもの |
| `ask` | 必ず聞く | 通ってしまうと困るもの |
| `deny` | 止める | させたくないもの |

**`allow` に入れたのは2つだけです。** テストの実行と、ルート一覧の表示です。どちらも、中身を確かめなくても困りません。

同じコマンドを2行ずつ書いているのは、打ち方が2通りあるからです。9-1-2「Docker環境でLaravelを動かそう（Laravel Sail）」で `sail` という短縮名を登録しています。AIがどちらの打ち方をしても効くように、両方書いておきます。

`git status` や `git diff` のような、読むだけのコマンドは書いていません。もともと聞かれないので、書いても何も変わりません。

`Bash(./vendor/bin/sail *)` のような広い書き方もしていません。`sail` を丸ごと許可すると、その後ろに何が続いても通ります。

**`ask` は、うっかり押した許可への保険です。** `ask` に書いたものは、`allow` に入っていても、押してしまった「今後は聞かない」が残っていても、必ず聞き直されます。データベースを作り替えるコマンドと、リモートへ送るコマンドを入れました。

`migrate` と `migrate:fresh` を別々に書いているのは、`migrate *` と書いても `migrate:fresh` が含まれないからです。データベースを全部消すコマンドなので、独立した1行で残します。

`ask` と `deny` は「必ず聞く」「止める」側なので、書き漏らしても事故になりません。書いていないものは、今までどおり聞かれるだけです。

**`deny` が、先送りにしていた約束の片方です。** `.env` を読むことと書き換えることを、2行で止めます。14-1-4 では、`.env` を自動で避ける仕組みはありません、と書きました。この2行を書いたフォルダでは、AIが `.env` を開こうとしたところで機械が止めます。`cat .env` のように、コマンドを経由して読もうとした場合も同じです。

## 書いたのに聞かれるとき

書いたはずのコマンドで承認画面が出たら、見るところは1つです。承認画面に出ているコマンドの文字列と、自分が書いたルールを見比べます。

いちばん多いのは、打ち方のズレです。`./vendor/bin/sail artisan test` と `sail artisan test` は、別の文字列として扱われます。片方しか書いていなければ、もう片方は聞かれます。許可リストが同じコマンドを2行ずつ持っているのは、このためです。

次に多いのが、つないだコマンドです。14-1-4 で、`&&` でつないだコマンドは、行の先頭だけを見て判断せず最後まで読む、と書きました。許可リストのうえでも、つないだコマンドは1つずつ別々に見られます。片方でも書いていなければ、全体が止まります。読みにくいだけでなく、機械的にも損だ、ということです。

---

## 減らすのは、読まなくていい承認だけ

許可リストを書いても、`migrate` と `git push` は今までどおり毎回聞かれます。減らしたのは、読まなくていい承認だけです。

`deny` も、完全な金庫ではありません。止められるのは、Claude Codeが把握している開き方だけです。14-1-4 で学んだ「秘密の値そのものを打ち込まない」は、設定を書いたあとも続けます。

承認をすべて飛ばすモードも存在しますが、Claude Codeの公式ドキュメント（2026年8月時点）は、隔離された環境でのみ使うようにと書いています。手元のPCで使うものではありません。許可リストは、その代わりに置くものです。

14-1-4 で決めた「押す前に、これは何を変えるのか」を自分に聞くやり方は、変わりません。変わるのは、その質問を向ける回数です。

## 🏃 承認の回数を数えて、許可リストを書く

> 🔥 ここからは、AIに実装を任せて構いません。ただし「任せる」と「丸投げ」は違います。何を作るかは設計書で自分が決め、出てきたものはテスト・動作確認・コードレビューで自分が検証します。品質の責任は、AIではなくあなたが握ります。

設定を書く前と後で、承認画面が出た回数を自分で数えます。数字が変わることより、何が減って何が残るのかを見てください。

1. 【自分⇄AI】設定を書く前に、承認画面が何回出るかを数える
2. 【自分】「今後は聞かない」を1回だけ押して、残るファイルを開く
3. 【自分】押した許可を取り消して、承認画面が戻ることを確かめる
4. 【自分】`.claude/settings.json` に許可リストを書く
5. 【自分⇄AI】まったく同じ依頼をして、承認画面の回数を数え直す
6. 【自分】コミットして push する

アプリが止まっている場合は、Docker Desktop（またはDocker Engine）を起動してから、Sailを立ち上げます。

```bash
# アプリのフォルダの中で実行する
cd ~/laravel-practice/14_hands-on/authorization-app-ai
./vendor/bin/sail up -d
```

### Step 1: 承認の回数を数える

Claude Codeを起動して、次のとおり頼みます。

```text
次の3つを順番に実行してください。
1) ./vendor/bin/sail artisan test
2) ./vendor/bin/sail artisan route:list
3) ./vendor/bin/sail artisan test
```

> 💡 このプロンプトのポイントは、①打ってほしいコマンドを名指ししている（AIに選ばせない）②あとでまったく同じ文をもう一度使う、の2点です。同じ文でないと、承認の回数を比べられません。

承認画面が出たら、この1回だけ許可する選択肢を選びます。「今後は聞かない」にあたるものも出ますが、ここでは選ばないでください。選ぶと、あとで数え直したときに、減った理由が設定のおかげなのか、押したせいなのかが分からなくなります。

承認画面が何回出たかを数えて、メモしておきます（___ 回）。

テストの本数や表示は、あなたのアプリで変わります。承認画面の回数も、AIがコマンドをまとめるかどうかで前後します。ここで見たいのは、あとで数える数字との差です。

### Step 2: 「今後は聞かない」を1回だけ押してみる

ここまで、この選択肢は選ばないでくださいと書いてきました。この1回だけ、何が起きるのかを見るために選びます。すぐ取り消します。

```text
./vendor/bin/sail artisan route:list を実行してください。
```

> 💡 このコマンドを選んだのは、ルートの一覧を表示するだけで何も書き換えないからです。このあと許可リストにも入れるコマンドなので、間違って許可が残っても困りません。

承認画面が出たら、押す前に選択肢の文字列を読んでください。これから保存されるルールが、そのまま表示されています。読んだら、「今後は聞かない」にあたるほうを選びます。

VS Codeで `.claude/settings.local.json` を開きます。Tutorial 14 で一度も「今後は聞かない」を選んでいなければ、押す前には無かったファイルです。中身は、このセクションの前半で見た形になっています。

いま押した `route:list` のほかにも行が並んでいることがあります。その場合は、Tutorial 14 のどこかで「今後は聞かない」を押した分が残っています。読まずに押した1回が、こういう形で残り続けるということです。

`git status` を打っても、このファイルは出てきません。

### Step 3: 押した許可を取り消す

`/permissions` と打って、さきほど保存されたルールを消します。手順は前半の6行のとおりです。消したあとに `.claude/settings.local.json` を開くと、さきほど増えた `route:list` の行が消えています。ほかの行が残っている場合は、それは前に押した分なので、同じ手順で消せます。

消えたことを確かめます。いったんClaude Codeを終了して、起動し直してから、Step 2 と同じ依頼をもう一度します。承認画面が戻ってきたら、取り消せています。ここでは、この1回だけ許可する側か、許可しない側を選んでください。もう一度「今後は聞かない」を押すと、いま消したルールがそのまま戻ります。

### Step 4: 許可リストを書く

VS Codeで、`.claude/` の中に `settings.json` という名前のファイルを作ります。中身は「許可リストを、自分で書く」で示したものをそのまま書きます。`//` で始まる行は入れません。

保存したら、書けたことを目で確かめます。`allow` に4行、`ask` に4行、`deny` に2行が入っていれば大丈夫です。

### Step 5: 数え直す

Claude Codeを終了して、起動し直します。設定はセッションの途中でも効きますが、Step 1 と条件をそろえるために、ここでは起動し直します。

Step 1 とまったく同じ文を頼みます。承認画面が何回出たかを数えます（___ 回）。

0回にならなかった場合は、承認画面に出ているコマンドの文字列と、自分が書いたルールを見比べてください。`./vendor/bin/sail` と `sail` の食い違いか、`&&` でつないだ形か、そのどちらかであることがほとんどです。

メモした2つの数字の差が、これから毎回省ける確認の数です。

### Step 6: コミットして push する

```bash
# アプリのフォルダの中で実行する
git add .claude
git commit -m "Add permission settings for Claude Code"
git push origin main
```

ブランチは切っていません。これは機能を作る作業ではないので、14-3-3「計画を立てさせてから実装させる」で決めたブランチの単位（機能イシュー1件につきブランチ1本）には当てはまらないからです。

`git add .claude` と打っても、`.claude/settings.local.json` は入りません。入るのは、共有する `settings.json` だけです。

このセクションが終わった時点で、次の4つを確かめてください。

- [ ] 設定を書く前と後で、承認画面が出た回数をそれぞれ数えてメモした
- [ ] `.claude/settings.local.json` を開いて、押した「今後は聞かない」が書き残される形を自分の目で見た
- [ ] 取り消したあと、起動し直して同じ依頼をして、承認画面が戻ることを確かめた
- [ ] GitHubでリポジトリのページを開いて、`.claude/settings.json` が表示されていることを確かめた

## 💡 よくある間違い

**「今後は聞かない」を押して、許可リストを育てる**

押した分は溜まっていくので、一見すると同じことに見えます。違うのは2つです。読まずに押した分まで溜まること。そして、溜まる先が自分のPCの中で、リポジトリに入れて共有できないことです。

**`sail` を丸ごと許可する**

`Bash(./vendor/bin/sail *)` の1行で、承認画面はほとんど出なくなります。同時に、`sail` の後ろに何が続いても通るようになります。短く書けたときほど、何を許したのかを読み直してください。

**読むだけのコマンドを書き並べる**

`git status` や `ls` を許可リストに並べても、動きは変わりません。もともと聞かれないものです。行数が増えると、本当に許したものが埋もれます。

**設定を書いたから、もう承認画面を読まなくていいと思う**

残った承認は、自分が「読む」と決めたものです。減った分だけ、1件あたりに使える注意は増えています。

## ✨ まとめ

- 「今後は聞かない」を押すと、その内容は `.claude/settings.local.json` に書き残されます。自分のPCの中にだけ残り、Gitには出ません。
- 押してしまった許可は `/permissions` から消せます。消えたかどうかは、起動し直してから確かめます。
- 先に決めておく許可は `.claude/settings.json` に書き、リポジトリに入れて共有します。`allow` は聞かずに通すもの、`ask` は必ず聞くもの、`deny` は止めるものです。
- `deny` に `.env` の2行を書くと、AIが開こうとしたところで機械が止めます。ただし完全な金庫ではないので、秘密の値を自分で打ち込まない、はこのあとも続けます。
- 書いたのに聞かれるときは、承認画面の文字列と自分のルールを見比べます。`./vendor/bin/sail` と `sail` は別物として扱われます。

承認の数は減りました。読むべきものだけが残っている状態です。ただ、必ずやってほしいことのほうは、まだ自分が覚えています。コードを変えたらテストを回す、というのは、いまも自分で思い出して打っている作業です。次の 15-4-2 では、決まった場面で必ず走る確認を、機械の側に持たせます。
