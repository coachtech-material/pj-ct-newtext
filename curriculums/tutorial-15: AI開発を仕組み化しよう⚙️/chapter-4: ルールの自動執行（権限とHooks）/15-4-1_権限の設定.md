# 15-4-1: 権限の設定

## 🎯 このセクションで学ぶこと

- 設定を書く場所が3つあることを知り、書いたものが誰に効くのかを言えるようになる。
- 触らせたくないファイルを止め、取り返しのつかない操作は必ず聞かせられるようになる。
- 毎回の承認が要らないコマンドを書き出して、リポジトリで共有できるようになる。

---

## 導入：頼んだ作業に必要なら、`.env` も `git push` も通ります

auto で動いているClaude Codeは、実行しようとしている操作が依頼の範囲を超えていないかを検査してから、自分で進みます（14-1-3）。検査役が見ているのはそこまでです。このアプリで `.env` を開いてよいか、いま `git push` してよいかは、依頼の範囲の内側にあるかどうかとは別の話になります。

このプロジェクトで何に触らせないかは、こちらから書いておきます。書く先が `.claude/settings.json` の `permissions` です。14-1-3 では `.env` を止める指定だけを書きました。ここでは、その周りを組み直します。

---

## 設定を書く場所は3つ

同じような名前のファイルが3つ出てきます。効く範囲が違うので、先に並べておきます。

| ファイル | 効く範囲 | 中身を作るのは |
|:--|:--|:--|
| `.claude/settings.json` | このフォルダを開いた人全員 | 自分（リポジトリに入れて共有する） |
| `~/.claude/settings.json` | 自分のPCで開くフォルダ全部 | 自分（自分のPCの中だけ） |
| `.claude/settings.local.json` | 自分のPCの、このフォルダ | Claude Code（自動で書き足す） |

1つ目が、このセクションで書くファイルです。プロジェクトの設定なので、リポジトリに入れます。次にこのフォルダを開いた人が、同じ許可の状態で始められます。多くの場合、その人は来月の自分です。

2つ目は、プロジェクトをまたぐ自分の好みを書く場所です。下の `defaultMode` はここに書きます。

3つ目は、自分では作りません。承認画面で「今後は聞かない」にあたる選択肢を選ぶと、その内容がこのファイルに自動で書き足されます。自分のPCの中だけに置くものなので、コミットには入れません。

> 💡 **TIP**: Tutorial 2 で見た VS Code の `settings.json` とは別のファイルです。あちらはエディタの見た目や保存時の動きを決めるもので、名前が同じなだけです。

### auto を既定にしたいとき

`Shift+Tab` で切り替えたモードは、そのセッションのあいだだけ効きます。次に起動したときにどのモードで始まるかを決めているのが `defaultMode` です。2026年8月から、Pro・Max・Teamの新しいセッションは auto で始まります。14-1-3 のとおりに `Shift+Tab` で切り替えてきただけなら、既定は変えていません。ここは読み飛ばして構いません。自分で `~/.claude/settings.json` を書いて既定を変えたことがある人だけ、次を書いてください。

**`~/.claude/settings.json`**

```json
{
  "permissions": {
    "defaultMode": "auto"
  }
}
```

このファイルが無ければ、新しく作ります。すでに `{` から始まる中身があるなら、その中に `permissions` を並べます。

書く場所に、1つだけ決まりがあります。`auto` を既定にする指定は、プロジェクトの `.claude/settings.json` に書いても**無視されます**（2026年8月時点）。リポジトリの側が、それを開いた人に auto を与えられないようにするためです。ほかのモードにこの制限はなく、たとえば `"defaultMode": "plan"` をプロジェクト設定に書けば、そのフォルダの既定になります。`auto` を既定にしたいときだけ、ユーザー設定の `~/.claude/settings.json` に書きます。

このあと書く `deny`・`ask`・`allow` のほうは、プロジェクト設定に書いたものがそのまま効きます。ここから先は、`.claude/settings.json` の話です。

---

## 書く中身

先に全体を出します。**`.claude/settings.json`** を、次の中身にします。

```json
{
  "permissions": {
    "deny": [
      "Read(.env)",
      "Read(.env.*)",
      "Edit(.env)",
      "Edit(.env.*)"
    ],
    "ask": [
      "Bash(git push *)"
    ],
    "allow": [
      "Bash(./vendor/bin/sail artisan test *)",
      "Bash(sail artisan test *)"
    ]
  }
}
```

3つのまとまりは、上から順に見られます。`deny` に当たれば止まり、当たらなければ `ask` を見て、それも当たらなければ `allow` を見ます。最初に当たったものが効くので、`allow` に書いてあるコマンドでも、`ask` にも書いてあれば聞かれます。

1行ずつの書き方は共通です。かっこの前が操作の種類で、`Bash` はコマンドの実行、`Read` はファイルを読むこと、`Edit` はファイルを書き換えることを指します。かっこの中に、その対象を書きます。

> ⚠️ **注意**: JSONのファイルには `//` で始まる説明書きを入れられません（11-1-3）。1行入れただけで設定として読めなくなり、書いたものが1行も効かなくなります。しかも、エラーも警告も出ません。この教材ではコードブロックの1行目にファイルの場所をコメントで書いてきましたが、この形式ではそれができないので、ファイル名はコードブロックの外に書いています。書き写すときも、その1行は足さないでください。

---

## 止める

`deny` は、AIがそこへ手を伸ばした時点で止めます。承認するかどうかを自分が選ぶ場面にもなりません。

止めているのは `.env` と、`.env.local` のような派生ファイルです。読むほうの指定は 14-1-3 で書いたものをそのまま置き、書き換えるほうの指定をここで足しました。

止まる範囲は決まっています。Claude Codeがファイルを開く経路と、`cat`・`head`・`tail`・`sed` のように中身を読むコマンドは止まります。PHPやPythonのスクリプトが中で開く経路は止まりません（14-1-3）。設定は金庫ではないので、秘密の値そのものを依頼の文章に貼らない、という自分の側の線は別に持っておきます。

> ⚠️ **注意**: `.env.*` は `.env.local` と一緒に `.env.example` も止めます。`.env.example` は環境を作り直すときのコピー元で（14-1-1）、秘密の値は入っていません。それでも一緒に止まるのは、`deny` に「ここだけは通す」という例外を書けないからです。中身を見たいときは、自分の端末で開いてください。

---

## 必ず聞かせる

14-1-1 で、慎重になるのは取り返しがつかないものに触るとき、と決めました。物差しは、失敗したときに自分の手で元へ戻せるかどうかです。例として挙げたのが、本番で動いているデータ、秘密の値、外部への公開でした。秘密の値は `deny` で止めました。残りのうち、この演習で実際に起きるのが外部への公開で、`git push` がそれにあたります。手元のコミットはいくらでもやり直せますが、GitHubへ送ったものは取り消せません。

`ask` に書いたものは、**auto で動いていても承認画面が出ます**。auto は検査役の判断で自動承認するモードですが、`ask` はその手前で当たります。取り返しがつかない操作について、人が止まる場所を作り直すのが `ask` の役目です。

`*` は、この後ろに何が続いても、という印です。`git push origin main` のように後ろが続く形も、`git push` とだけ打たれた形も、この1行で当たります（2026年8月時点）。

本番のデータベースを作り替えるコマンドも、同じ考え方でここへ入れます。この演習で使っているのは練習用のデータベースで、消えても `migrate --seed` で作り直せるので、いまは入れていません。

---

## 聞かずに通す

14-1-3 の最後に、`deny` の反対の「これは毎回聞かなくてよい」という指定もある、と書いてありました。それが `allow` です。

入れたのはテストを回すコマンドだけです。何度も打つうえ、中身を確かめなくても困りません。2行あるのは、同じコマンドの打ち方が2通りあるからです。9-1-2 で `sail` という短縮名を登録しているので、AIがどちらの形で打っても効くように両方書いています。`--filter` を付けた形も、何も付けない形も、それぞれの1行で当たります。

書かないものも決めておきます。`git status` や `ls` のような読むだけのコマンドは、Claude Codeが最初から承認なしで通します。書いても動きは変わらず、行数が増えるぶん、本当に許したものが埋もれます。`Bash(./vendor/bin/sail *)` のような広い書き方もしません。1行で承認はほとんど出なくなりますが、`sail` の後ろに何が続いても通るようになります。

`gh issue create` のような、外へ通信するコマンドも入れません。14-2-4 から毎回承認画面が出ているので、いちばん `allow` に書きたくなるものです。ただ、GitHubへ送ったものは取り消せません。`git push` と同じ扱いにして、聞かれたままにしておきます。Chapter 5 でもう1機能作るときにも、`gh` の承認画面はまた出ます。

auto で動いているあいだは、`allow` に書かなくても止まらないことがほとんどです。それでも書いておきます。検査役の判断を待たずに通り、次にこのフォルダを開いた人が同じ状態で始められ、何を許したのかが1か所に読める形で残ります。

保存すると、Claude Codeを起動したままでも効きます。`.claude/` に置いたほかの道具は、作った直後に起動し直す必要がありましたが、この設定ファイルだけは別です。

---

## 書いたのに聞かれるとき

承認画面に出ているコマンドの文字列と、自分が書いたルールを見比べます。

いちばん多いのは打ち方のズレです。`./vendor/bin/sail artisan test` と `sail artisan test` は、別の文字列として扱われます。片方しか書いていなければ、もう片方は聞かれます。

次に多いのが、`&&` でつないだコマンドです。つないだものは1つずつ別々に見られるので、片方でも書いていなければ全体が止まります。

いま何が効いているかは、Claude Codeで `/permissions` と打つと一覧で読めます。ルールごとに、どのファイルから読まれたものかも並びます。押してしまった「今後は聞かない」を消すのも、この画面からです。↓キーで消したいルールに合わせて `Enter` を押し、確認に答えると消えます。

---

## 🏃 設定を書いて、効き方を見る

アプリが止まっている場合は、Docker Desktop（またはDocker Engine）を起動してから、Sailを立ち上げます。

```bash
# アプリのフォルダへ移動して、Sailを起動する
cd ~/laravel-practice/post-app-practice
./vendor/bin/sail up -d
```

### Step 1: 設定を書く

VS Codeで `.claude/settings.json` を開き、「書く中身」で示したものに書き換えます。14-1-3 で書いた `deny` は、この中に入っています。

保存したら、Claude Codeを起動します。

```bash
claude
```

### Step 2: 効いているものを読む

`/permissions` と打ちます。いま書いた `deny`・`ask`・`allow` が一覧に並び、それぞれ `.claude/settings.json` から読まれたことが表示されます。並んでいなければ、JSONの書式が壊れています。カンマの過不足と、`//` で始まる行が入っていないかを見てください。読み終えたら `Esc` で閉じます。

### Step 3: 止まることを確かめる

```text
.env の APP_KEY の値を教えてください。
```

> 💡 これは値を知るための依頼ではありません。**止まることを確かめるための依頼です。** このアプリの `.env` に入っているのは練習用のダミーの値ですが、止まる形を先に見ておきます。

承認画面は出ません。読み取りそのものが止まるので、AIは値を答えられません。通すか止めるかを自分が選ぶ場面にすらならない、というのが `deny` の効き方です。

### Step 4: 聞かれないことを確かめる

`Shift+Tab` を何回か押して、`⏸ manual mode on` に合わせます。承認をいちばん多く求めるモードです（14-1-3）。この状態で頼みます。

```text
./vendor/bin/sail artisan test を実行してください。
```

manual なのに承認画面が出ず、そのままテストが走れば、`allow` が効いています。Docker越しに動くので、結果が出るまでしばらくかかります。

承認画面が出たときは、「書いたのに聞かれるとき」でやったとおりに見比べてください。画面に出ているコマンドの文字列と、自分が書いた2行です。`./vendor/bin/sail` と `sail` は別の文字列として扱われるので、書いていないほうの形で打たれていれば、そこで聞かれます。

確かめ終わったら、`Shift+Tab` を押して `⏵⏵ auto mode on` に戻してください。

### Step 5: 記録して、聞かれることを確かめる

設定をコミットして push するところまで、まとめて頼みます。

```text
.claude/settings.json をコミットして、main に push してください。
```

コミットまでは止まりません。止まるのは push の手前です。`ask` に書いたコマンドなので、auto でも承認画面が出ます。出たら、通してください。

ブランチは切っていません。機能を作る作業ではないので、14-3-1 で決めたブランチの単位（機能イシュー1件につきブランチ1本）に当てはまらないからです。

投げ終えたら、次の4つを確かめてください。

- [ ] `/permissions` の一覧に、`.claude/settings.json` から読まれたルールが並んでいる
- [ ] `.env` の値を聞いて、値が返ってこないことを見た
- [ ] manual にした状態でテストを頼み、承認画面が出ないことを見た
- [ ] push の手前で承認画面が出て、GitHubのリポジトリのページに `.claude/settings.json` が表示されている

## 💡 よくある間違い

**「今後は聞かない」を押して、許可を育てる**

押した分は `.claude/settings.local.json` に溜まっていくので、一見すると同じことに見えます。違うのは、読まずに押した1回もそのまま残ることと、溜まる先が自分のPCの中で共有できないことです。

**読むだけのコマンドを書き並べる**

`git status` や `ls` を並べても動きは変わりません。もともと聞かれないものです。

**広く書いて、承認をゼロにする**

`Bash(./vendor/bin/sail *)` のように短く書けたときほど、何を許したのかを読み直してください。許可リストは自分用のメモではなく、次にこのフォルダを開いた人への約束です。広く書けば、その広さがそのまま渡ります。

## ✨ まとめ

- 設定ファイルは3つあります。共有する `.claude/settings.json`、自分のPCだけの `~/.claude/settings.json`、Claude Codeが自動で書き足す `.claude/settings.local.json` です。
- `auto` を既定にする `defaultMode` は、プロジェクト設定に書いても無視されます。ユーザー設定に書きます。ほかのモードにこの制限はありません。
- ルールは `deny`・`ask`・`allow` の順に見られ、最初に当たったものが効きます。
- `deny` はAIが手を伸ばした時点で止めます。`cat` のようなコマンド経由も止まりますが、スクリプトが中で開く経路までは止まりません。
- `ask` は auto でも承認画面を出します。取り返しがつかない操作について、人が止まる場所を作り直すのがこの指定です。
- `allow` に書いておくと、検査役の判断を待たずに通り、次にこのフォルダを開いた人にも同じ許可が渡ります。
