# 13-1-3: DB設計

## 🎯 このセクションで学ぶこと

- タスク管理アプリのデータベース設計を行う方法を学ぶ
- エンティティの抽出からER図の作成、テーブル設計までの流れを理解する
- 1対多リレーションシップの設計方法を習得する

---

## 🧠 先輩エンジニアの思考プロセス

### 「なぜ機能要件の次にデータベース設計なのか？」

機能要件で「何を作るか」が決まったら、次は「どうやってデータを保存するか」を決めます。

### 理由1: データ構造が決まらないとコードが書けない

```
❌ データ構造を決めずにコードを書く
→ 「このデータはどこに保存する？」と迷う
→ 後からテーブル構造を変更する羽目になる

✅ 先にデータ構造を決める
→ マイグレーション、モデル、コントローラーの設計がスムーズ
→ 一貫性のあるコードが書ける
```

### 理由2: リレーションシップを先に決める

「ユーザーとタスクの関係は？」「カテゴリーとタスクの関係は？」を先に決めておくと、Eloquentのリレーションシップ設計が楽になります。

### 理由3: API設計の前提になる

「どんなデータを返すか」は「どんなデータがあるか」に依存します。データベース設計が先です。

## 導入：なぜデータベース設計が必要なのか

データベース設計（Database Design）とは、**システムで扱うデータの構造を設計する作業**です。

データベース設計を行わずに開発を始めると、以下のような問題が発生します。

| 問題 | 説明 |
|:---|:---|
| データの重複 | 同じデータが複数のテーブルに保存される |
| データの不整合 | データが矛盾する（例: ユーザーが削除されたのに、そのユーザーのタスクが残っている） |
| パフォーマンスの低下 | データの取得に時間がかかる |

データベース設計を行うことで、これらの問題を防ぐことができます。

---

## Step 1: エンティティの抽出

エンティティ（Entity）とは、**システムで扱うデータのまとまり**です。

機能要件から、以下のエンティティを抽出します。

| エンティティ | 説明 |
|:---|:---|
| **User（ユーザー）** | システムを利用するユーザー |
| **Task（タスク）** | 登録されたタスク情報 |
| **Category（カテゴリー）** | タスクを分類するカテゴリー |

---

### エンティティの属性

各エンティティが持つ属性（データ項目）を洗い出します。

**User（ユーザー）**:
- 名前
- メールアドレス
- パスワード

**Task（タスク）**:
- タイトル
- 説明
- 優先度（1:低、2:中、3:高）
- どのユーザーのタスクか
- どのカテゴリーに属するか

**Category（カテゴリー）**:
- カテゴリー名

---

## Step 2: リレーションシップの定義

**リレーションシップ（Relationship）**とは、**エンティティ間の関係**です。

タスク管理アプリでは、以下のリレーションシップがあります。

| リレーションシップ | 種類 | 説明 |
|:---|:---|:---|
| User - Task | 1対多 | 1人のユーザーは複数のタスクを持つ |
| Category - Task | 1対多 | 1つのカテゴリーには複数のタスクが属する |

---

### リレーションシップの方向

リレーションシップには方向があります。

**User → Task（1対多）**:
- 1人のUserは、複数のTaskを持つ
- 1つのTaskは、1人のUserに属する

**Category → Task（1対多）**:
- 1つのCategoryには、複数のTaskが属する
- 1つのTaskは、1つのCategoryに属する

---

### 💡 TIP: 1対多リレーションシップの見分け方

「AはBを複数持つか？」を考えます。

| 質問 | 答え | リレーションシップ |
|:---|:---|:---|
| 1人のユーザーは複数のタスクを持つか？ | はい | User:Task = 1:多 |
| 1つのタスクは複数のユーザーに属するか？ | いいえ | Task:User = 多:1 |
| 1つのカテゴリーには複数のタスクが属するか？ | はい | Category:Task = 1:多 |

---

## Step 3: ER図の作成

**ER図（Entity-Relationship Diagram）**とは、**エンティティとリレーションシップを図で表したもの**です。

ER図を作成することで、**データベースの構造を視覚的に理解できる**ようになります。

---

### ER図

```
[users]                     [categories]
  id (PK)                     id (PK)
  name                        name
  email                       created_at
  password                    updated_at
  created_at                    |
  updated_at                    |
    |                           |
    | 1:多                      | 1:多
    |                           |
    +---------------------------+
                |
                v
            [tasks]
              id (PK)
              user_id (FK) -----> users.id
              category_id (FK) -> categories.id
              title
              description
              priority
              created_at
              updated_at
```

---

### ER図のコードリーディング

| 記号 | 意味 |
|:---|:---|
| `[users]` | usersテーブル |
| `id (PK)` | 主キー（Primary Key） |
| `user_id (FK)` | 外部キー（Foreign Key） |
| `1:多` | 1つのレコードに対して、複数のレコードが紐づく |
| `-----> users.id` | usersテーブルのidを参照 |

---

### リレーションシップの詳細

| 親テーブル | 子テーブル | 外部キー | 関係 |
|:---|:---|:---|:---|
| users | tasks | tasks.user_id | 1人のユーザーが複数のタスクを持つ |
| categories | tasks | tasks.category_id | 1つのカテゴリーに複数のタスクが属する |

---

## Step 4: テーブル設計

ER図を元に、**テーブル設計**を行います。

テーブル設計では、以下の内容を決めます。

| 項目 | 説明 |
|:---|:---|
| テーブル名 | エンティティ名を複数形にする（例: users、tasks） |
| カラム名 | データの項目名（スネークケース） |
| データ型 | データの型（例: BIGINT、VARCHAR、TEXT） |
| 制約 | データの制約（例: NOT NULL、UNIQUE、FOREIGN KEY） |

---

### usersテーブル

| カラム名 | データ型 | 制約 | 説明 |
|:---|:---|:---|:---|
| id | BIGINT | PRIMARY KEY, AUTO_INCREMENT | ユーザーID |
| name | VARCHAR(255) | NOT NULL | ユーザー名 |
| email | VARCHAR(255) | NOT NULL, UNIQUE | メールアドレス |
| password | VARCHAR(255) | NOT NULL | パスワード（ハッシュ化） |
| created_at | TIMESTAMP | NULL | 作成日時 |
| updated_at | TIMESTAMP | NULL | 更新日時 |

> 💡 **ポイント**: usersテーブルはLaravelのデフォルトで用意されているため、カスタマイズは最小限にします。

---

### categoriesテーブル

| カラム名 | データ型 | 制約 | 説明 |
|:---|:---|:---|:---|
| id | BIGINT | PRIMARY KEY, AUTO_INCREMENT | カテゴリーID |
| name | VARCHAR(255) | NOT NULL | カテゴリー名 |
| created_at | TIMESTAMP | NULL | 作成日時 |
| updated_at | TIMESTAMP | NULL | 更新日時 |

> 💡 **ポイント**: カテゴリーはシステム共通のため、user_idは持ちません。

---

### tasksテーブル

| カラム名 | データ型 | 制約 | 説明 |
|:---|:---|:---|:---|
| id | BIGINT | PRIMARY KEY, AUTO_INCREMENT | タスクID |
| user_id | BIGINT | NOT NULL, FOREIGN KEY | ユーザーID（所有者） |
| category_id | BIGINT | NOT NULL, FOREIGN KEY | カテゴリーID |
| title | VARCHAR(255) | NOT NULL | タスクタイトル |
| description | TEXT | NULL | タスクの説明 |
| priority | TINYINT | NOT NULL, DEFAULT 2 | 優先度（1:低、2:中、3:高） |
| created_at | TIMESTAMP | NULL | 作成日時 |
| updated_at | TIMESTAMP | NULL | 更新日時 |

---

### テーブル設計のコードリーディング

| 項目 | 説明 |
|:---|:---|
| `BIGINT` | 大きな整数。IDに使用 |
| `VARCHAR(255)` | 最大255文字の可変長文字列 |
| `TINYINT` | 小さな整数（-128〜127）。優先度1〜3に最適 |
| `TEXT` | 長い文字列。説明文に使用 |
| `PRIMARY KEY` | 主キー。テーブル内で一意 |
| `AUTO_INCREMENT` | 自動採番 |
| `NOT NULL` | NULL禁止 |
| `UNIQUE` | 重複禁止 |
| `FOREIGN KEY` | 外部キー。別テーブルの主キーを参照 |
| `DEFAULT 2` | デフォルト値を2（中）に設定 |

---

### 外部キー制約

**外部キー制約（Foreign Key Constraint）**を設定することで、**データの整合性を保つ**ことができます。

| 外部キー | 参照先 | ON DELETE |
|:---|:---|:---|
| tasks.user_id | users.id | CASCADE（ユーザー削除時にタスクも削除） |
| tasks.category_id | categories.id | RESTRICT（カテゴリー削除を制限） |

---

### 💡 TIP: ON DELETEの種類

| 種類 | 動作 | 使用場面 |
|:---|:---|:---|
| CASCADE | 親が削除されたら子も削除 | ユーザー削除時にタスクも削除 |
| RESTRICT | 子がある場合は親の削除を禁止 | カテゴリー削除時にタスクがあればエラー |
| SET NULL | 親が削除されたら子の外部キーをNULLに | 任意のリレーション |

---

### 🚨 よくある間違い

**間違い1: 外部キー制約を設定しない**

外部キー制約がないと、存在しないユーザーIDを持つタスクが作成できてしまいます。

**対処法**: 必ず外部キー制約を設定し、データの整合性を保ちます。

---

**間違い2: データ型を適切に選ばない**

優先度（1〜3）にBIGINTを使うのは無駄です。

**対処法**: データの範囲に合ったデータ型を選びます。

| データ | 適切なデータ型 |
|:---|:---|
| ID | BIGINT |
| 優先度（1〜3） | TINYINT |
| タイトル | VARCHAR(255) |
| 説明文 | TEXT |

---

**間違い3: テーブル名を単数形にする**

Laravelの規約では、テーブル名は複数形です。

**対処法**: `task`ではなく`tasks`、`category`ではなく`categories`にします。
