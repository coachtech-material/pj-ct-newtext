## 🧠 先輩エンジニアの思考プロセス

### 「なぜDB設計の次にこれらの設計を行うのか？」

DB設計で「どんなデータがあるか」が決まったら、次は「どうやってデータにアクセスするか」を決めます。

### 理由1: 実装前に全体像を把握する

```
❌ 設計なしに実装を始める
→ 「このAPIはどんなレスポンスを返す？」と迷う
→ 「このルートはどんなURLにする？」と迷う

✅ 先に設計を決める
→ 実装時に迷わない
→ チームメンバーとの認識が揃う
```

### 理由2: Issueに分解しやすくなる

設計が明確だと、「このAPIを実装する」「このバリデーションを実装する」とIssueを分解できます。

## API設計

### API設計とは

**API設計**とは、**外部からアクセスできるエンドポイントの仕様を決める作業**です。

タスク管理アプリでは、認証なしでタスク情報を取得できる**公開API**を提供します。

---

### API一覧

| # | メソッド | エンドポイント | 説明 | 認証 |
|:---:|:---|:---|:---|:---:|
| API-1 | GET | /api/tasks | タスク一覧を取得 | 不要 |
| API-2 | GET | /api/tasks/{id} | タスク詳細を取得 | 不要 |

---

### API-1: タスク一覧API

| 項目 | 内容 |
|:---|:---|
| **エンドポイント** | GET /api/tasks |
| **認証** | 不要 |
| **リクエストパラメータ** | なし |
| **レスポンス形式** | JSON |

**レスポンス例**:

```json
{
  "data": [
    {
      "id": 1,
      "title": "企画書を作成する",
      "description": "来週の会議に向けて企画書を作成する",
      "priority": 3,
      "priority_label": "高",
      "category": {
        "id": 1,
        "name": "仕事"
      },
      "user": {
        "id": 1,
        "name": "山田太郎"
      },
      "created_at": "2024-01-15T10:30:00.000000Z"
    }
  ]
}
```

---

### API-2: タスク詳細API

| 項目 | 内容 |
|:---|:---|
| **エンドポイント** | GET /api/tasks/{id} |
| **認証** | 不要 |
| **パスパラメータ** | id: タスクID（整数） |
| **レスポンス形式** | JSON |

**レスポンス例（成功時）**:

```json
{
  "data": {
    "id": 1,
    "title": "企画書を作成する",
    "description": "来週の会議に向けて企画書を作成する",
    "priority": 3,
    "priority_label": "高",
    "category": {
      "id": 1,
      "name": "仕事"
    },
    "user": {
      "id": 1,
      "name": "山田太郎"
    },
    "created_at": "2024-01-15T10:30:00.000000Z",
    "updated_at": "2024-01-15T10:30:00.000000Z"
  }
}
```

**レスポンス例（404エラー時）**:

```json
{
  "message": "Task not found"
}
```

## ルーティング設計

### ルーティング設計とは

**ルーティング設計**とは、**URLとコントローラーの対応を決める作業**です。

---

### Web画面のルーティング

| # | メソッド | URL | コントローラー@メソッド | 説明 | 認証 |
|:---:|:---|:---|:---|:---|:---:|

## バリデーション設計

### バリデーション設計とは

**バリデーション設計**とは、**入力データの検証ルールを決める作業**です。

---

### ユーザー登録のバリデーション

| フィールド | ルール | エラーメッセージ |
|:---|:---|:---|
| name | required, string, max:255 | 名前は必須です / 名前は255文字以内で入力してください |
| email | required, email, unique:users | メールアドレスは必須です / 有効なメールアドレスを入力してください / このメールアドレスは既に登録されています |
| password | required, min:8, confirmed | パスワードは必須です / パスワードは8文字以上で入力してください / パスワードが一致しません |

---

### カテゴリー登録・編集のバリデーション

| フィールド | ルール | エラーメッセージ |
|:---|:---|:---|
| name | required, string, max:255 | カテゴリー名は必須です / カテゴリー名は255文字以内で入力してください |

---

### タスク登録・編集のバリデーション

| フィールド | ルール | エラーメッセージ |
|:---|:---|:---|
| title | required, string, max:255 | タイトルは必須です / タイトルは255文字以内で入力してください |
| description | nullable, string | - |
| priority | required, integer, in:1,2,3 | 優先度は必須です / 優先度は1〜3の値を選択してください |
| category_id | required, exists:categories,id | カテゴリーは必須です / 選択されたカテゴリーは存在しません |

---

### バリデーションルールのコードリーディング

| ルール | 説明 |
|:---|:---|
| `required` | 必須項目 |
| `string` | 文字列であること |
| `max:255` | 最大255文字 |
| `email` | メールアドレス形式 |
| `unique:users` | usersテーブルで重複しないこと |
| `min:8` | 最小8文字 |
| `confirmed` | 確認用フィールドと一致すること |
| `nullable` | 空でもOK |
| `integer` | 整数であること |
| `in:1,2,3` | 1, 2, 3のいずれかであること |
| `exists:categories,id` | categoriesテーブルのidに存在すること |

## 認可設計

### 認可設計とは

**認可設計**とは、**誰がどのリソースにアクセスできるかを決める作業**です。

---

### 認可ルール

| リソース | アクション | 認可ルール |
|:---|:---|:---|
| Category | 一覧表示 | ログインユーザーのみ |
| Category | 登録 | ログインユーザーのみ |
| Category | 編集 | ログインユーザーのみ |
| Category | 削除 | ログインユーザーのみ |
| Task | 一覧表示 | ログインユーザーのみ（自分のタスクのみ表示） |
| Task | 登録 | ログインユーザーのみ |
| Task | 詳細表示 | ログインユーザーのみ（自分のタスクのみ） |
| Task | 編集 | タスクの所有者のみ |
| Task | 削除 | タスクの所有者のみ |

---

### Policyの設計

**TaskPolicy**を作成し、タスクの所有者チェックを行います。

| メソッド | 説明 | 認可条件 |
|:---|:---|:---|
| view | タスク詳細表示 | `$task->user_id === $user->id` |
| update | タスク編集 | `$task->user_id === $user->id` |
| delete | タスク削除 | `$task->user_id === $user->id` |

> 💡 **ポイント**: カテゴリーはシステム共通のため、Policyは作成しません。ログイン済みであれば誰でも操作できます。

---

### 認可の実装方法

| 方法 | 使用場面 |
|:---|:---|
| ミドルウェア（`auth`） | ログイン必須のルートに適用 |
| Policy | リソースの所有者チェック |
| Bladeディレクティブ（`@can`） | 画面での表示制御 |

## テスト要件

### テスト要件とは

**テスト要件**とは、**どのような観点でテストを行うかを決める作業**です。

---

### テスト対象

| カテゴリ | テスト対象 | テスト種別 |
|:---|:---|:---|
| 認証 | ユーザー登録 | Feature |
| 認証 | ログイン | Feature |
| 認証 | ログアウト | Feature |
| CRUD | カテゴリー一覧表示 | Feature |
| CRUD | カテゴリー登録 | Feature |
| CRUD | カテゴリー編集 | Feature |
| CRUD | カテゴリー削除 | Feature |
| CRUD | タスク一覧表示 | Feature |
| CRUD | タスク登録 | Feature |
| CRUD | タスク詳細表示 | Feature |
| CRUD | タスク編集 | Feature |
| CRUD | タスク削除 | Feature |
| 認可 | 他人のタスクにアクセス不可 | Feature |
| API | タスク一覧API | Feature |
| API | タスク詳細API | Feature |

---

### テストケース例

**タスク登録のテストケース**:

| # | テストケース | 期待結果 |
|:---:|:---|:---|
| 1 | 正常な入力でタスクを登録 | タスクがDBに保存される |
| 2 | タイトルが空の場合 | バリデーションエラー |
| 3 | 優先度が範囲外の場合 | バリデーションエラー |
| 4 | 存在しないカテゴリーIDの場合 | バリデーションエラー |
| 5 | 未ログインでアクセス | ログイン画面にリダイレクト |

---

**認可のテストケース**:

| # | テストケース | 期待結果 |
|:---:|:---|:---|
| 1 | 自分のタスクを編集 | 編集成功 |
| 2 | 他人のタスクを編集 | 403 Forbidden |
| 3 | 自分のタスクを削除 | 削除成功 |
| 4 | 他人のタスクを削除 | 403 Forbidden |

---

### 🚨 よくある間違い

**間違い1: テスト要件を後回しにする**

テスト要件を後回しにすると、「何をテストすればいいかわからない」となります。

**対処法**: 設計段階でテスト要件を定義し、実装と並行してテストを書きます。

---

**間違い2: 正常系のテストだけ書く**

正常系だけでなく、異常系（バリデーションエラー、認可エラーなど）もテストします。

**対処法**: 各機能に対して、正常系・異常系の両方のテストケースを定義します。
