# 14-5-1: 直らないときの型

## 🎯 このセクションで学ぶこと

- エラーをAIに渡すときに、何を一緒に渡して何を渡さないかが分かる。
- ログの中から、読むべき1行を取り出せるようになる。
- 巻き戻す・分け直す・仕切り直すの3つを、詰まる前に用意しておけるようになる。

---

## 導入

Chapter 4では、リプライ機能をPRまで通しました。ここまでは、頼んだものが返ってきた前提で進んできました。実際の開発では、テストが落ちる、画面が真っ白になる、エラーの文字だけが並ぶ、という時間のほうが長くなります。

AIに任せると、この時間は短くなります。エラーの文を渡せば、たいてい何か直ってくるからです。困るのはその先で、2回直させても直らないときに、そのまま3回目、4回目と続けてしまいます。1回ごとに何かが変わるので、進んでいるように見えます。そのあいだにコードは触られ続け、最初に動いていたところまで巻き込まれていきます。

先に決めておけば、この時間は数分で終わります。用意するのは、渡し方と、打ち切り方です。

---

## 渡す前にやること

**1. エラーの文を最後まで読む**

10-4-4「エラー画面の読み方とスタックトレース」で見たとおり、読むのはいちばん上のメッセージと、その下に出るファイル名と行番号です。データベースからのエラーなら、実行しようとしたSQLもメッセージの中に入っているので、1行目は画面の中で何度も折り返します。折り返した先に手がかりがあるので、途中で読むのをやめないでください。AIに貼るときも、エラーの塊は区切りのよいところまでまとめて貼ります。

**2. 同じ操作をもう一度やる**

同じエラーが出れば、原因はいまのコードの中にあります。出なければ話が変わります。再現しないものは、AIにも直せません。

**3. 自分の見立てを1つ持つ**

どのファイルが怪しいかを、1つだけ決めます。当たっている必要はありません。見立てを持たずに渡すと、返ってきた説明が合っているかを判定する足場がなくなります。

---

## 渡すもの、渡さないもの

| 渡すもの | なぜ要るか |
|:--|:--|
| エラーの文 | 1行目と、その下に出る発生場所まで |
| 自分がやった操作 | どの画面で、何を入れて、何を押したか |
| どうなるはずだったか | 受け入れ条件に書いてあるので、そのまま引いてこられます |
| 自分の見立て | どのファイルが怪しいか。分からなければ「分からない」と書きます |

3つ目が、受け入れ条件を先に文字にしておくことの効き目です。「本文を入れてリプライを送ると、一覧に増える」と書けるのは、イシューか `docs/reply.md` にその1行があるからです。これが無いと、AIの目標は「エラーを消すこと」だけになります。エラーが出なくなる直し方と、原因を取り除く直し方は別のもので、前者を受け取り続けると、動いてはいるのに何が起きていたのか分からないコードが残ります。

渡さないものも決めておきます。`.env` の中身・パスワード・本物の鍵は渡しません（14-1-5）。ログファイルの丸ごと貼り付けもしません。読むのは1行で、丸ごと渡すと、読ませるだけで渡せる量を使い切ります。

---

## ログから、読むべき1行を取り出す

10-4-3「ログの活用」で、ログが `storage/logs/laravel.log` に追記されることと、`tail -f` で流れを見られることを学びました。すでに起きたエラーの文を読みたいときは、別の取り出し方のほうが速く済みます。

```bash
# 投稿アプリのフォルダの中で実行する
grep "local.ERROR" storage/logs/laravel.log | tail -1
```

`grep` は、決めた文字を含む行だけを取り出すコマンドです。`|`（縦棒）は、左のコマンドが出したものを右のコマンドへ渡す書き方です。この2つで、`local.ERROR` という印が付いた行だけを取り出し、そのうちいちばん新しい1行を表示しています。

1行に絞るのは、**1件のエラーで数十行から百行ほどの記録が残る**からです。エラーの文は最初の1行で、そのあとは処理をたどった記録が延々と続きます。`tail -20` で末尾を見ると、その記録の途中しか見えません。10-4-4で「`vendor/` で始まる行は通常は無視してよい」と学んだ、あの部分です。

まだ1度もエラーが起きていないアプリには `storage/logs/laravel.log` がありません。`No such file or directory` と出たら、記録するものがまだ無いということです。時刻にも気をつけてください。行の先頭に出るのは日本時間ではありません。世界共通の基準時刻で記録されるので、手元の時計より9時間前になります。

## 返ってきた修正案の見方

説明が付いていなければ、「なぜこの変更で直るのですか」と1行送って聞きます。返ってきた理由が自分の見立てと合っていれば、そのまま進めます。違っていたら、どちらが外れているのかを先に決めます。自分の見立てが外れていただけなら、それは収穫です。

もう1つ見るのは、**直す範囲がエラーの原因と釣り合っているか**です。1行の書き忘れが原因なのに3つのファイルを書き換える案が返ってきたら、「いちばん小さい直し方を教えてください」と聞き直します。

そして、直ったことは同じ操作をもう一度やって確かめます。

---

## 巻き戻す

1回目の修正が効かなかったときに、いちばん先にやるのは**壊れた状態を残さないこと**です。効かなかった修正の上に2回目を重ねると、いま動いていないのが1回目のせいなのか2回目のせいなのかが分からなくなります。

戻し方は、戻す単位で選びます。

| 戻す単位 | どの道具の記録か | 手段 | 何が戻るか |
|:--|:--|:--|:--|
| やり取り1回分 | Claude Code | `/rewind` | 会話とコードを、選んだ時点まで |
| コミット1つ分 | Git | `git reset --hard HEAD~1` | そのコミットで記録した変更 |
| ブランチ1本分 | Git | `main` に戻ってブランチを捨て、切り直す | そのブランチでやったことすべて |

1つ目と、あとの2つは別々の記録です。Claude Codeは、依頼を1つ受け取るたびに、そのとき触るファイルの中身を自分で控えています。だから**コミットしていない段階でも戻せます**。Gitのほうは、コミットしてからでないと戻り先がありません。

### /rewind の中身

`/rewind` と打つか、入力欄が空の状態で `Esc` を2回押すと、戻す画面が開きます。入力欄に文字が入っているときは、2回目の `Esc` はその文字を消すほうに使われます。

画面には、このセッションで自分が送った依頼が上から並びます。まず**どの時点に戻るか**を選び、そのあと**何をするか**を選びます（2026年8月時点）。

| 選ぶもの | 何が起きるか |
|:--|:--|
| Restore code and conversation | 会話もコードも、その時点まで戻します |
| Restore conversation | 会話だけ戻します。コードはいまのままです |
| Restore code | コードだけ戻します。会話はいまのままです |
| Summarize from here | その時点から後ろの会話を、要約にまとめます |
| Summarize up to here | その時点より前の会話を、要約にまとめます。後ろはそのまま残ります |
| Never mind | 何もせずに、一覧へ戻ります |

上の3つが巻き戻しです。真ん中の2つは戻すためのものではなく、会話を縮めてコンテキストを空けるためのもので、そちらは14-5-2で扱います。選んだ時点より後ろにファイルの書き換えが1つも無いときは、コードを戻す2つは並びません。

会話を戻すと、その時点で送った依頼が入力欄に戻ってきます。書き直して送り直せます。

> ⚠️ **注意**: 戻せるのは、AIが**ファイルを編集する道具で書き換えたもの**だけです。AIがコマンドを打って作ったファイル（`./vendor/bin/sail artisan make:` で増えるファイルなど）は控えられていないので、`/rewind` では消えません。残っていたら、Gitのほうで片づけます。

表示がここに書いたものと違うときは、`/help` と公式ドキュメントで確かめてください。

コミット1つ分を戻すコマンドは、12-1-3「マージの基礎」で読んだ形です。

```bash
# 投稿アプリのフォルダの中で実行する
git reset --hard HEAD~1
```

コミットが細かいほど、戻る先を細かく選べます。1日分の作業を1回のコミットにまとめていると、途中まで戻る道がありません。GitHubへpushしたあとのコミットには使いません。手元とGitHubで記録が食い違うためです。

ブランチごと捨てるのは、やり直しに見えて、そうでもありません。捨てるのは書かれたコードだけで、そのあいだに分かったこと（どこで詰まったか、何を試したら何が起きたか）は残ります。それを入れて頼み直すぶん、次は速く終わります。

---

## 頼む単位を分け直す

戻したあと、同じ大きさでもう一度頼むと、たいてい同じところで詰まります。次のどれかが出ていたら、その頼み方は大きすぎます。

- **差分を読み切れない量で出てきた**。何がどう変わるのかを自分の言葉で言えないなら、読み切れていません
- **1つ直すたびに、別のところが壊れる**。2往復したら、その頼みに関係のないものが2つ入っています
- **決めていないことが、2つ以上出てきた**。これは大きさの問題ではありません。設計の穴が、AIからの質問という形で表に出ています。分け直す前に、決めていないことのほうを決めます

---

## 2回直らなければ仕切り直す

打ち切りは、数で決めておきます。同じ問題について**2回直させて直らなければ**、そのセッションを終わりにします。

同じセッションには、前のやり取りが全部残っているからです。外れた案が2つ載ったまま3回目を頼むと、AIはそれを引きずります。回数を重ねるほど当たりにくくなる、という向きになります。

区切りには `/clear` を使います。それまでのやり取りを空にして、新しく始めるコマンドです（詳しくは14-5-2）。そして、新しいセッションの最初の依頼に**分かったことを書き足します**。書くのは、何を試したか（どのファイルをどう直させたか）と、そのとき何が起きたか（エラーが変わったか、変わらなかったか）です。これが無いと、新しいセッションのAIは、さきほど外れた案をもう一度出してきます。同じことを2度やらせないための差は、この数行だけです。

ここまでのどれをやっても直らないときは、その機能を離れて、決めごとのほうへ戻ってください。作るものが決まっていないまま作らせている、ということが起きています。

---

## 🏃 使い捨ての変更を作って、巻き戻す

巻き戻しは、詰まってから初めて打つと手が止まります。いまのコードに小さな変更を1つ入れて、戻すところまでを先に通しておきます。

**この変更は記録しません。** ブランチも切りません。14-4-5でマージを終えたので、いまいる場所は `main` です。この演習が終わった時点で、リポジトリは何も変わっていない状態に戻ります。

ターミナルで投稿アプリのフォルダ（14-1-3でCLAUDE.mdを作ったフォルダ）へ移動して、Claude Codeを起動します。

```bash
# 投稿アプリのフォルダで実行する
claude
```

### Step 1: 小さな変更をAIにさせる

タイムラインの見出しを、1語だけ書き換えてもらいます。

```text
resources/views/posts/index.blade.php の中で、
画面本文の見出しとして出ている「ホーム」を「タイムライン」に変えて。
ブラウザのタブに出るタイトルはそのままで。
```

編集が終わると、応答の中に差分が出ます。書き換わった行を見ておいてください。ここが、戻す対象です。

### Step 2: `/rewind` で戻す

入力欄に打ちます。

```text
/rewind
```

一覧から、Step 1で送った依頼を選びます。そのあとに出る選択肢から、`Restore code and conversation` を選びます。

Claude Codeを開いたまま、別のターミナルで確かめます。

```bash
# 投稿アプリのフォルダの中で実行する
git status
```

一覧に `resources/views/posts/index.blade.php` が出てこなければ、書き換える前とまったく同じ状態です。

**戻したあとの `git status`**

まだ出ている場合は、`git restore .`（4-3-5）で戻してください。この演習で作ったのは記録していない変更だけなので、まるごと捨てて構いません。

確かめ終えたら `/exit` で閉じます。閉じる前に、次の3つを確かめてください。

- [ ] 変更をAIにさせたあと、`/rewind` でその変更が消えた
- [ ] `git status` に、変更したファイルが出てこない
- [ ] エラーをAIに渡すときに書くものを、4つ挙げられる（エラーの文・やった操作・どうなるはずだったか・自分の見立て）

## ✨ まとめ

- エラーが出たら、渡す前に、文を最後まで読み、もう一度やって再現し、見立てを1つ持ちます。
- 渡すのは、エラーの文・やった操作・どうなるはずだったか・自分の見立てです。3つ目は受け入れ条件から引いてこられます。
- ログは `grep "local.ERROR" storage/logs/laravel.log | tail -1` で1行に絞ります。時刻は手元の時計より9時間前で記録されます。
- 修正案は、なぜ直るのかと、直す範囲が原因と釣り合っているかを見ます。
- やり取り1回分を戻すなら `/rewind`（Claude Codeの記録。コミット前でも戻せる）、コミット1つ分なら `git reset --hard HEAD~1`、それより広ければブランチを捨てて切り直します。
- `/rewind` は、戻る時点を選んでから、会話とコードのどちらを戻すかを選びます。AIがコマンドで作ったファイルは戻りません。
- 1回目が効かなかったら戻し、頼む単位を分け直し、2回で直らなければセッションを区切って分かったことを書き足します。
