# 14-5-3: もう1機能を自走で - 総合演習

## 📌 この演習について

ここまでは、次に何をするかが本文に書いてありました。実際の仕事で渡されるのは、何を実現したいかだけです。進め方は、受け取った人が組み立てます。

この演習では、手順を並べません。渡すのは、前提だけです。どう作るかは、あなたとAIで決めてください。

回すのは、Issue化 → 計画 → 実装とテスト → レビュー → UAT → PR の1周分です。14-3-1で選び方を決めた計画の持ち方も、ここでは自分で選びます。

---

## 🎯 演習課題

### 📋 課題

**実現したいこと**

> このアプリでできるのは、タイムラインを読むことと、自分のポストを直すこと、消すことだけです。新しいポストを書く手段がありません。ログインした人が自分のポストを書いて、タイムラインに出せるようにします。

**譲れないところ**

ここだけは決まっています。それ以外の作り方は指定しません。

| 決めごと | 中身 |
|:--|:--|
| ポストが持つ項目 | いまの編集画面と同じ、タイトル・トピック・本文の3つです |
| 書ける人 | ログインしている人だけです |
| 投稿者 | 書いた本人です。ほかの人の名前で出せる形にはしません |

**変えないもの**

| 変えないもの | 確かめ方 |
|:--|:--|
| `posts` テーブルの列 | 列を足したり型を変えたりしません。`database/migrations` にファイルが増えていないことで確かめます |
| タイムラインの一覧・編集・削除 | いまの動きのままです。他人のポストには編集・削除の操作が出ず、URLを直接開くと403になります |
| ここまでに足したもの | リプライ機能と、編集画面の文字数制限・残り文字数の表示は、そのまま動きます |

**受け入れ条件**

13-2-2「ユースケース図とユースケース記述」で書いた形と同じ、「〜すると、〜になる」のチェックリストです。この5行が、この演習の受け入れ条件になります。

- [ ] ログインした状態でタイムラインを開くと、ポストを書く場所か、書く画面への入口がある
- [ ] タイトル・トピック・本文を入れて送ると、タイムラインの先頭にそのポストが増える
- [ ] 本文が空のまま送ると、エラーが表示されてポストは増えない
- [ ] 増えたポストには自分の名前が出ていて、編集と削除の操作が出る
- [ ] ログアウトすると、ポストを書く場所にたどり着けない（ログイン画面に飛ばされる）

**決めていないこと**

書く場所をどこに置くかは決めていません。タイムラインの上にフォームを置く、書くための画面を別に作る、タイムラインから開く、といった置き方があります。入力チェックの中身・ルート名・ボタンの文言も決めていません。AIに案を出させて、そこから選んでください。選んだ理由は、あとで自分が読み返せる場所に1行残します。

文字数の上限は、受け入れ条件に入れていません。14-3-2で編集画面に付けた上限に合わせるか、作成側には付けないかは、あなたの判断です。入力チェックのメッセージを日本語で出したいときは、依頼にその1行を書き添えてください。何も言わないと英語で出ます。

### ✏️ 進め方タスク

作業する場所は、これまでと同じ投稿アプリです。リプライ機能がマージされた `main` から始めます。

```bash
# 投稿アプリのフォルダで実行する
git switch main
git pull origin main

# Sail が止まっていたら起動する
./vendor/bin/sail up -d
```

思いどおりに直らない・壊れたと感じたら14-5-1へ。応急は `git restore .`（4-3-5）です。

1. 【自分】計画の持ち方を選ぶ。なし・planモード・設計書のどれかです（14-3-1）。選んだ理由を1行書き残します
2. 【AI】イシューを立てさせる。上の受け入れ条件を本文に入れる
3. 【AI】ブランチを切らせる
4. 【自分⇄AI】決めていないことを聞き返させて、決める
5. 【AI】選んだ持ち方で計画を出させる。planモードなら計画を、設計書なら `docs/post-create.md` を書かせます
6. 【自分】出てきた計画を読む（14-3-2）
7. 【AI】実装させる。テストも同じ依頼に含め、通るまで直させて、結果を報告させる
8. 【自分】報告された結果を読む（14-4-1）
9. 【AI】`/code-review` を回させ、指摘を読んで直させる（14-4-2）
10. 【自分】受け入れ条件をブラウザで1行ずつ潰す（14-4-3）
11. 【AI】受け入れ条件をブラウザ操作で回させる（14-4-4。導入できていれば）
12. 【自分⇄AI】PRを作らせ、本文を読んでからマージする（14-4-5）

手を止めるのは、1・4・6・8・10・12です。ほかは渡して構いません。

### ✅ 完成チェックリスト

- [ ] テストの結果報告を読んで、落ちているテストが無いことを確かめた
- [ ] 受け入れ条件の5行を、ブラウザで1行ずつ確かめた
- [ ] タイムラインの一覧・編集・削除が、前と同じに動く
- [ ] `database/migrations` にファイルが増えていない
- [ ] 編集画面の文字数制限が、前と同じに効いている
- [ ] 計画の持ち方を選んだ理由が、イシューか設計書かPRの本文のどこかに1行残っている
- [ ] PRがマージされ、イシューが `Closed` になっている

## 📖 進行例

> 💡 **進行例について**: AIとの開発は毎回違う流れになります。ここに示すのは一つの進行例です。あなたの画面と違っていても、チェックリストを満たしていれば正解です。

**1. planモードを選んで、理由をイシューに残す**

あとで突き合わせる受け入れ条件の5行は、イシューの本文に残ります。新しいテーブルも増えないので、ER図のように、実装のあとで読み返したくなる中身がほかにありません。ファイルに残す用事が無いので、planモードで通します。

読むときの物差しは、イシューに書いた5行です。リプライ機能で `docs/reply.md` が持っていた役目を、ここではイシューが持ちます。差分を読むときも（14-4-2）、ブラウザで1行ずつ潰すときも（14-4-3）、突き合わせる相手はこの5行です。

イシューの本文の末尾に、この1行を足しました。

```text
計画はplanモードで通す。受け入れ条件はイシューに残っていて、
実装のあとで読み返したい中身がほかに無いため。
```

**2. 書く場所の案を出させて、1つ選ぶ**

決めていないことのうち、いちばん大きいのが書く場所です。

```text
ポストを書く場所の案を3つ出して。
それぞれについて、受け入れ条件の5行を満たせるかと、
いまのタイムライン（一覧・編集・削除）に影響が出るかを書いて。
```

> 💡 このお願いのポイントは、案を出させるときに**比べる軸**を一緒に渡していることです。軸が無いと、3案が並ぶだけで選べません。

返ってきたのは、タイムラインの上にフォームを置く案、書くための画面を別に作る案、タイムラインのボタンからその画面を開く案の3つでした。選んだのは3つ目です。編集画面がすでに別画面なので、書く側もそろえたほうが迷わないと考えました。

**3. 計画にテストが入っていない**

planモードで計画を出させたところ、触るファイルの一覧に `tests/` がありませんでした。承認せずに、テストも一緒に書くよう伝えて、計画を出し直させました。

**4. 受け入れ条件をブラウザで潰す**

実装が終わって、テストの結果報告にも落ちているものはありませんでした。ブラウザを開くと、書く画面はこうなっています。

タイトル・トピック・本文を入れて送ると、タイムラインの先頭に増えました。

上から潰していって、止まったのは5行目です。ログアウトしてから書く画面のURLを開くと、ログイン画面に飛ばずに、そのまま画面が出てしまいました。

`routes/web.php` を開くと、作成のルートが `Route::middleware('auth')->group(...)` の外に置かれていました。ここを名指しで直させて、もう一度ログアウトした状態で開き、ログイン画面に飛ぶことを確かめました。

**5. `/code-review` の指摘を1つ直す**

回してみると、作成と更新で同じ入力チェックの規則が2箇所に書かれている、という指摘が返ってきました。1箇所にまとめるところまで直させて、テストを回し直させました。

**6. PRを出してマージする**

受け入れ条件の5行がそろったので、PRまで頼みました。本文にテストの結果と受け入れ条件の突き合わせが入っていることを読んでから、マージしました。イシューが `Closed` になって、1周が終わりました。

## 🚀 まとめ

- 前提がそろえば、手順を書かなくても機能は作れます。渡すのは、目的・変えないもの・受け入れ条件です。
- 変えないものは、動きで書きます。「一覧・編集・削除が前と同じに動く」と書いておけば、壊れた時点で気づけます。
- 案を出させるときは、比べる軸を一緒に渡します。軸が無い3案は、並ぶだけで選べません。
- 計画に足りないものがあったら、承認せずに出し直させます。ここで足したテストが、そのまま受け取りの判定に使われます。
- 判定するのは、動いたかどうかではありません。書いた条件を満たしたかどうかです。テストが全部通っていても、受け入れ条件が1行落ちていれば、それは未完成です。
