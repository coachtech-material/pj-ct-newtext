# 14-5-4: 振り返りと手で運んだものの棚卸し

## 🎯 このセクションで学ぶこと

- 2つの機能を作るあいだ、何を自分がやり、何をAIがやったのかを振り返れるようになる。
- 実装が終わったあと、書いた設計書をどう扱うのかを決められるようになる。
- 毎回自分の手でやっていたことをAIに整理させ、これから潰していくイシューとして残せるようになる。

---

## 導入

14-5-3で、2つ目の機能をマージしました。手元には、リプライ機能を作ったときの `docs/reply.md` が残っています。計画を設計書で持つことにした方は、ポスト作成の分ももう1枚あります。

どれも、機能を作り終えたあとのまま置いてあります。扱いを決めておかないと、あとで開いた人が、古い記録なのか、いまのアプリを説明した書類なのかが分からないまま読むことになります。

ここで扱いを決めます。あわせて、2周のあいだ自分の手が何をしていたのかを振り返ります。

---

## 何を自分がやり、何をAIがやったか

リプライ機能とポスト作成機能を通して、作業はこう分かれていました。

| 場面 | あなたがやったこと | AIがやったこと |
|:--|:--|:--|
| 要件を決める | 目的・変えないもの・受け入れ条件を決めた | なし |
| イシューを立てる | 要望を渡し、聞き返しに答えた | `gh` でイシューを立てた |
| 設計する | 決めていないことを決め、出てきた案から選んだ | 聞き返し、設計書か計画にまとめた |
| 実装する | 計画を読んで、足りないところを直させた | コードとテストを書き、テストを回し、通るまで直した |
| レビューする | 指摘を読んで、直させる範囲を決めた | `/code-review` を回し、指摘を直した |
| 動かして確かめる | 受け入れ条件を1行ずつブラウザで潰した | 同じ条件をブラウザ操作で回し、結果を報告した |
| 受け取りを判定する | 条件を満たしているかを決めた | なし |
| PRを出して締める | 本文を読んでマージを決めた | PRを作り、証拠を本文に書いた |

14-5-3の進め方で、手を止めると決めたのは、計画の持ち方を選ぶところ、決めていないことを決めるところ、計画を読むところ、テストの結果を読むところ、受け入れ条件を潰すところ、PRの本文を読むところでした。ファイルを1つずつ承認して回る場面はありませんでした。

右の列が「なし」の行が2つあります。要件を決めるところと、受け取りを判定するところ。この2つに、AIの出番がありませんでした。14-1-1で置いた分担（作るもの・完成の条件・変えない範囲・受け取るかどうか）が、そのまま2機能分の実績になっています。

---

## 実装が終わったあと、何が基準になるか

ここで決めるのは1つです。**設計書とコードの両方を、正しい状態に保とうとしない。** 同じことが2か所に書いてあると、片方だけ直した日から、どちらが本当なのかが分からなくなります。

基準に置くのは、コードとテストのほうです。半年後、誰かがリプライの削除を直して、他人のリプライも消せるようにしてしまったとします。Chapter 3で書いたテストは赤くなり、`./vendor/bin/sail test` を回した人にその場で伝わります。`docs/reply.md` は何も言いません。ファイルの中では、いまも「自分のリプライは消せて、他人のリプライは消せない」と書かれたままです。実物とずれたときに気づける側でないと、基準にはなれません。

だから設計書は、実物に合わせて直し続けません。その機能を作ったときの**記録**として、そのまま残します。1機能を1ファイルにまとめてあるので、ファイル名がそのまま、どこまでの記録かの目印になります。

開いた人に伝わるように、1行目に次の1文だけ足しておきます。

```markdown
> この設計書は、この機能を実装した時点の記録です。このあとは更新していません。
```

## コードに残らないもの

コードとテストが基準になる、と言いましたが、全部がそこに残るわけではありません。

コードに書いてあるのは、**何をしているか**です。書いていないのは、**なぜそうしたか**です。2つの機能でも、たとえば次のようなことは実物から読み取れません。

| コードに現れている形 | 読み取れないこと |
|:--|:--|
| リプライを消せる人の判定が `PostPolicy` と同じ形になっている | 画面のボタンを隠すだけではURLを直接開かれたときに止まらないので、既にある判定にそろえたこと |
| ポストを書く場所が、いまの置き場所に決まっている | いくつかの案から選んだ結果であること |
| 作成の入力チェックに文字数の上限が入っている | 編集画面に合わせると決めたこと（合わせないと決めた場合は、その行が無いこと自体が決めごとです） |

決めたことは人によって違うので、あなたが実際に決めたものに置き換えて読んでください。

これが困るのは、半年後です。上限の1行を見た人は、なんとなくそうなっているのだと読みます。そして、良かれと思って数字を変えます。次の日、編集画面と作成画面で通る長さが違う、という状態になります。

決めた理由だけは、コードのそばに移しておきます。

## 🏃 手で運んだものを棚卸しする

2周のあいだ、毎回同じことを自分の手でやっていました。依頼のたびにアプリの前提を書き、テストの句を書き添え、確認を押しました。1回ずつは数十秒でも、機能ごとに何度も繰り返しています。

これを棚卸しして、イシューに1本立てます。置き場所を `docs/` にしないのは、あそこが設計書の置き場だからです。設計書は実装した時点の記録で、もう更新しません。こちらは、これから1つずつ潰していく作業のほうです。機能を作るときと同じ場所に載せておけば、同じ流れで片づけられます。あわせて、設計書の1行目とREADMEも、ここで片づけます。

ターミナルで投稿アプリのフォルダ（14-1-3でCLAUDE.mdを作ったフォルダ）へ移動して、Claude Codeを起動します。

```bash
# 投稿アプリのフォルダで実行する
claude
```

### Step 1: 材料を渡して、整理させる

AIは、あなたが手でやったことを知りません。やり取りは区切るたびに消えていますし、閉じたイシューやマージ済みのPRに残っているのは、作ったもののほうです。ですから、覚えていることを先に渡します。

```text
この2機能（リプライとポスト作成）を作るあいだ、私が毎回手でやっていたことを棚卸ししたい。
gh で「開発の手作業を仕組みに移す」というイシューを立てて、
本文を「## 毎回手でやったこと」の見出しのチェックリストにして。

私が覚えているのはこれ。足りないところは gh で閉じたイシューとマージ済みのPRを読んで補って。
- 依頼のたびに、変えないもの（タイムラインの今の動き）と、入力チェックのメッセージは日本語で出すことを書いた
- 「テストも書いて、./vendor/bin/sail test で回して、通るまで直して、最後に結果を報告して」を毎回書き添えた
- 差分が出てくるたびに、どこから読むかを自分で決めた
- 受け入れ条件を、自分で潰すときとAIに回させるときで2回貼り直した
- gh を実行するたび、計画を承認するたびに、確認を押した

機能の説明は書かないで。私が繰り返した作業だけ。
```

> 💡 **出力例について**: AIの応答は毎回変わります。以下はあくまで一例です。文言が違っても、チェックリストの項目を満たしていれば問題ありません。

```markdown
## 毎回手でやったこと

- [ ] 依頼のたびに、このアプリの前提（変えないもの・入力チェックのメッセージは日本語で出すこと）を書き直した
- [ ] 実装を頼むたびに「テストも書いて、./vendor/bin/sail test で回して、通るまで直して、最後に結果を報告して」を書き添えた
- [ ] 差分が届くたびに、設計書と突き合わせる順番を自分で組み立てた
- [ ] 同じ受け入れ条件を、自分で確かめるときとAIに回させるときの2回、貼り直した
- [ ] `gh` の実行と計画の承認のたびに、確認を押した
```

### Step 2: 読んで直す

出てきたものを、そのまま置きません。見るのは1つだけです。並んでいるのが、自分が繰り返した作業になっているか。機能の説明が混ざっていたら、その行を消させます。

このイシューは、ここでは閉じません。5つとも潰し終えるのはTutorial 15です。番号を控えておいてください。

### Step 3: 設計書とREADMEを片づける

設計書の1行目の1文と、コードに残らない決めごとを、まとめて書かせます。

```text
docs/reply.md の1行目に「> この設計書は、この機能を実装した時点の記録です。このあとは更新していません。」を足して。

そのうえで README.md の末尾に「## 設計のメモ」という見出しを作って、
@docs/reply.md を読んで、リプライ機能をなぜそう作ったのかを箇条書きにして。

書くのは、作らないと決めたもの・選ばなかった作り方・
知らずに変えると壊れる決めごと・設計書のありかの4つだけ。
何ができるかの説明は README.md の「できること」に既にあるので書かないで。
```

ここで読ませているのはリプライ機能の設計書だけです。計画を設計書で持つことにした方は、`docs/post-create.md` も同じように1行目を足して、依頼の中で一緒に読ませてください。planモードで通した方は、イシューに残したのが計画の持ち方を選んだ理由だけなので、どう作るかを選んだ理由はどこにも残っていません。この分は、できあがった `README.md` の「設計のメモ」に、自分で1行ずつ書き足してください。

「書かないもの」を名指ししているのは、これが無いと機能紹介が返ってくるからです。AIから見れば、そちらのほうが自然なREADMEです。

### Step 4: まとめて記録する

今回はコードを変えていないので、ブランチを切らずに `main` へ記録します。

```text
docs と README.md をコミットして、main に push して。
```

このコミットは、どちらのイシューにも属していません。だからメッセージにイシューの番号を入れていません。2件とも、もう閉じています。

書き終えたら、次の5つを確かめてください。

- [ ] GitHubでイシューの一覧を開いて、「開発の手作業を仕組みに移す」が立っている
- [ ] 本文に「毎回手でやったこと」がチェックリストで並び、機能の説明ではなく、自分が繰り返した作業になっている
- [ ] `README.md` の「設計のメモ」に、なぜそう作ったのかが書かれている
- [ ] 自分が作った設計書の1行目に、記録である旨の1文が入っている
- [ ] `main` にコミットされ、GitHubにも上がっている

## ✨ まとめ

- 2機能を通して、要件を決めるところと、受け取りを判定するところには、AIの出番がありませんでした。
- 設計書とコードの両方を正しく保とうとしません。基準はコードとテストです。実物とずれたときに赤くなるのはテストで、設計書は黙ったままだからです。
- 設計書は、その機能を作ったときの記録として残します。更新しないので、1行目にその旨を書き添えます。1機能1ファイルなので、ファイル名がそのまま範囲の目印になります。
- コードに残るのは「何をしているか」だけです。作らないと決めたもの、選ばなかった作り方、知らずに変えると壊れる決めごとは、READMEに書き残します。
- 毎回手でやっていたことは、棚卸ししてイシューに立てます。潰していく作業なので、更新しない設計書とは置き場所を分けます。材料を渡さないと、AIには整理する元がありません。
