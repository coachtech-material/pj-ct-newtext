# 14-5-1: もう1周する - 総合演習

## 📌 この演習について

ここまでは、次に何をするかが本文に書いてありました。実際の仕事で渡されるのは、何を実現したいかだけです。進め方は、受け取った人が組み立てます。

この演習では、手順を並べません。渡すのは、前提だけです。どう作るかは、あなたとAIで決めてください。

題材は、投稿の下書きです。今回の機能は投稿に状態を持たせるので、13-6-2「状態遷移設計 - ステータスの一生を描く」で描いた状態遷移図と遷移表が、そのまま設計の材料になります。

---

## 🎯 演習課題

### 📋 課題

**実現したいこと**

> いまは、一度出した投稿を引っ込められません。書いた本人が、自分の投稿を下書きに戻せるようにします。下書きになった投稿は本人の一覧にだけ残り、ほかの人の一覧からは消えます。あとから公開に戻せます。

**譲れないところ**

ここだけは決まっています。それ以外の作り方は指定しません。

| 決めごと | 中身 |
|:--|:--|
| 状態は2つ | 「下書き」と「公開済み」の2つだけです。公開待ちや削除済みは作りません |
| 切り替えてよい人 | その投稿を書いた本人だけです |
| 一覧に出す範囲 | 公開済みの投稿すべてと、自分が書いた下書きです |

列の名前も、切り替えの操作をどこに置くかも、画面の作りも決めていません。設計のときに決めます。

**変えないもの**

| 変えないもの | 確かめ方 |
|:--|:--|
| いまある4件の投稿 | この機能を入れたあとも、ユーザーA・ユーザーBのどちらの一覧にも4件とも出ます |
| 投稿の編集と削除 | いまの動きのままです。他人の投稿は編集・削除のボタンが出ず、URLを直接開くと403になります |
| コメント機能 | ここまでに入れたものは、そのまま動きます |

**受け入れ条件**

13-2-2「ユースケース図とユースケース記述」で書いた形と同じ、「〜すると、〜になる」のチェックリストです。この5行が、この演習の受け入れ条件になります。

- [ ] ユーザーAが自分の投稿を下書きにすると、ユーザーBの一覧からその投稿が消える
- [ ] ユーザーAの一覧には、その下書きが残っている
- [ ] ユーザーAがその下書きを公開に戻すと、ユーザーBの一覧にまた出る
- [ ] ユーザーBがユーザーAの投稿を開くと、状態を切り替える操作が出ない
- [ ] ユーザーBがユーザーAの投稿の状態を切り替えようとすると、403になる（この1行だけ、ブラウザから操作を送れないのでテストで確かめます）

**案を出させて選ぶところ**

状態を切り替える操作をどこに置くかは、決めていません。投稿一覧のカードに置く、コメント機能で足した投稿詳細に置く、編集画面の項目にする、といった置き方があります。設計のときにAIへ案を出させて、そこから選んでください。選んだ理由も `docs/draft.md` に1行書いておきます。

### ✏️ 進め方タスク

作業する場所は、これまでと同じアプリです。コメント機能がマージされた `main` から始めます。

```bash
# アプリのフォルダへ移動して、最新の main にそろえる
cd ~/laravel-practice/post-app-practice
git switch main
git pull origin main

# Sail が止まっていたら起動する
./vendor/bin/sail up -d
```

1. 【AI】機能イシューを `gh issue create` で立てさせる。上の受け入れ条件を本文に入れる
2. 【自分⇄AI】決めていないことを聞き返させてから、決まったことを `docs/draft.md` にまとめさせる。切り替えの置き場所は案を出させて選ぶ
3. 【AI】ブランチを切らせ、実装の計画を出させる
4. 【自分】計画を読んで承認する
5. 【AI】実装させる。テストも一緒に書かせ、コミットして `gh pr create` まで通させる
6. 【自分】テストを回し、受け入れ条件と突き合わせる
7. 【AI】プルリクエストをマージさせる

手を止めるのは、4番と6番の2箇所だけです。ほかは渡して構いません。

## 📖 進行例

> 💡 **進行例について**: AIとの開発は毎回違う流れになります。ここに示すのは一つの進行例です。あなたの画面と違っていても、チェックリストを満たしていれば正解です。

**1. 置き場所の案を3つ出させて、1つ選ぶ**

設計の途中で、切り替えの操作の置き場所を聞きました。

```text
状態を切り替える操作の置き場所を、案を3つ出してください。
それぞれについて、この機能の受け入れ条件を満たせるかと、
いまある編集・削除の画面に影響が出るかを書いてください。
```

> 💡 このお願いのポイントは、案を出させるときに**比べる軸**を一緒に渡していることです。軸が無いと、3案が並ぶだけで選べません。

返ってきたのは、投稿一覧のカードに置く案、投稿詳細に置く案、編集画面の項目にする案の3つでした。選んだのは投稿詳細です。投稿1件を相手にする操作が1か所にまとまり、一覧のカードに新しいボタンが増えないためです。この理由を `docs/draft.md` に1行足しました。

**2. 計画にテストが入っていない**

ブランチを切らせて計画を出させたところ、触るファイルの一覧に `tests/` がありませんでした。承認せずに、テストも一緒に書くよう伝えて、計画を出し直させました。

**3. 実装したら、一覧から4件とも消えた**

実装が終わってブラウザを開くと、投稿一覧が空になっていました。「変えないもの」の1行目が落ちています。

列を足したときに、既にあった4件へ何が入ったのかを見ると、原因が分かりました。新しい列の初期値が下書きの側になっていて、4件とも下書きとして扱われていたのです。分かったことをそのまま渡して、初期値を直させました。

列を足す変更は、もうデータベースに流したあとです。ファイルを直しただけでは反映されないので、いったん巻き戻してから流し直します。

```bash
# アプリのフォルダで実行する
./vendor/bin/sail artisan migrate:rollback --step=1
./vendor/bin/sail artisan migrate
```

9-3-4「マイグレーションの実行とロールバック」で使ったコマンドです。`--step=1` を付けているので、取り消されるのは直前に流した1つだけです。消えるのは足した列だけで、投稿もコメントも残ります。

**4. 受け入れ条件で1つ落ちる**

テストは全部通りました。ブラウザで受け入れ条件を上から潰していくと、4行目で止まりました。ユーザーBの画面に出ているユーザーAの投稿にも、「下書きに戻す」のボタンが出ています。

押すと403になるので、動きとしては止まっています。それでも受け入れ条件は、操作が出ないことを求めています。ボタンの出し分けだけを名指しで直させて、コミットしました。

**5. マージする**

受け入れ条件の5行がそろったので、マージまで頼みました。

```text
プルリクエストの内容を確認して、問題なければマージしてください。
マージしたら、手元の main も最新にそろえてください。
```

機能イシューが `Closed` になって、もう1周が終わりました。

## 🚀 まとめ

- 前提がそろえば、手順を書かなくても機能は作れます。
- 変えないものは、動きで書きます。「4件が両方の一覧に出たまま」と書いておけば、列の初期値を間違えた時点で気づけます。
- 案を出させるときは、比べる軸を一緒に渡します。軸が無い3案は、並ぶだけで選べません。
- 計画に足りないものがあったら、承認せずに出し直させます。ここで足したテストが、そのまま受け取りの判定に使われます。
- 403で止まっていても、受け入れ条件が「操作が出ない」なら、それは満たしていません。判定するのは動いたかではなく、書いた条件です。
