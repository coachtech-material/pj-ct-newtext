# 14-4-1: 検証をAIに渡す

## 🎯 このセクションで学ぶこと

- 実装の依頼にテストを入れると、確かめる作業のどこまでがAIの側で閉じるのかが分かる。
- テストの実行結果を読んで、受け取ってよいかを判定できるようになる。
- 設計書に書いたテスト観点と、増えたテストを突き合わせられるようになる。

---

## 導入

14-3-3では、`docs/reply.md` を渡してリプライ機能の実装を頼み、依頼の最後にテストの1行を入れました。返ってきたのは、コードとテストと、テストを回した結果の報告です。ここからは、その報告を読んで、受け取ってよいかを決めます。14-1-1で見た開発フローでいうと、いまいるのは「実装とテスト」の結果を受け取るところです。

## 依頼の最後の1行が閉じているもの

14-3-3で送った依頼を、もう一度見てください。

```text
docs/reply.md のとおりにリプライ機能を作って。

- 受け入れ条件の4行を満たすところまで
- タイムラインの今の動き（一覧・編集・削除）は変えない
- 入力チェックのメッセージは日本語で出す
- テストも書いて、./vendor/bin/sail test で回して、通るまで直して、最後に結果を報告して
```

最後の1行に並んでいるのは、書く・回す・直す・報告する、という4つの動きです。テストを書いた本人が回し、落ちたら直し、通ってから報告する。ここまでが1回の依頼の中でつながっているので、人の手番が来るのは最後の報告を読むところです。

テストをあとから頼むと、この順番が崩れます。できあがったコードを見てからテストを書けば、そのコードが通ることだけを確かめるテストになります。何を確かめたいかは `docs/reply.md` のテスト観点に先に書いてあるので、実装と同じ依頼で渡します。

14-2-1では、リプライ機能の検証手段を「ブラウザの操作で確かめる」の一言で渡していました。実装まで頼む段になると、そこにテストが加わります。

> 💡 **進行例について**: AIとの開発は毎回違う流れになります。ここに示すのは一つの進行例です。あなたの画面と違っていても、チェックリストを満たしていれば正解です。

```text
Claude Code: リプライのテストを3本書きました。./vendor/bin/sail test を回したところ、
             Table 'testing.replies' doesn't exist で3本とも落ちました。
             テスト用のデータベースにはテーブルが無いので、テストクラスに
             RefreshDatabase を付けて回し直しました。いまは全部通っています。
```

テスト用のデータベースは空で用意されるので、この進行例のように途中でつまずくこともあれば、最初からその形で書かれて何も起きないこともあります。どちらでも、エラーに当たって直し、回し直すところまではAIの側で終わっています。あなたが受け取るのは、その先です。

## 実行結果の読み方

報告に書いてあることは、自分で回しても見られます。

```bash
# 投稿アプリのフォルダで実行する
./vendor/bin/sail test
```

`sail` に渡した `test` は、中で `artisan test` に橋渡しされます。10-5-3「単体テストの基礎」で打った `sail artisan test` と、動くものは同じです。9-1-2「Docker環境でLaravelを動かそう（Laravel Sail）」で `sail` の短縮名を登録した方は、`sail test` と短く打っても構いません。

1本だけ回し直したいときは、10-5-3で使った `--filter` を付けます。`ReplyTest` のところは、AIが付けたテストクラスの名前に置き換えてください。`tests/Feature/` を開けば分かります。

```bash
# 投稿アプリのフォルダで実行する
./vendor/bin/sail test --filter ReplyTest
```

全部通ると、次のような画面になります。

```text
   PASS  Tests\Unit\ExampleTest
  ✓ that true is true

   DEPR  Tests\Feature\ExampleTest
  ! the application returns a successful response → Constant PDO::MYSQL… 0.08s
PHP Deprecated:  Constant PDO::MYSQL_ATTR_SSL_CA is deprecated since 8.5, use Pdo\Mysql::ATTR_SSL_CA instead in /var/www/html/config/database.php on line 62
PHP Deprecated:  Constant PDO::MYSQL_ATTR_SSL_CA is deprecated since 8.5, use Pdo\Mysql::ATTR_SSL_CA instead in /var/www/html/config/database.php on line 62
PHP Deprecated:  Constant PDO::MYSQL_ATTR_SSL_CA is deprecated since 8.5, use Pdo\Mysql::ATTR_SSL_CA instead in /var/www/html/config/database.php on line 62

   DEPR  Tests\Feature\ReplyTest
  ! replies are listed on post page → Constant PDO::MYSQL_ATTR_SSL_CA i… 0.17s
  ✓ reply body is required                                               0.01s
  ✓ user cannot delete others reply                                      0.01s

  Duration: 0.31s
```

テストの名前も件数も秒数も、AIが書いたテストによって変わります。自分の画面と1文字ずつ見比べる必要はありません。

10-5-3で見た `PASS` と `✓` のほかに、知らない表示が混ざっています。クラス名の左の `DEPR`、テスト名の左の `!` とその右に続く `Constant PDO::MYSQL_ATTR_SSL_CA is deprecated`、`PHP Deprecated:` から始まる行、そしていちばん下の `Tests:` の行に並ぶ `deprecated` です。

`deprecated` は「この書き方は将来なくなります」という予告で、テストの合否とは関係がありません。原因は、コンテナのPHPとLaravelの設定ファイルの組み合わせにあります。あなたのコードにも、AIが書いたコードにも原因はありません。組み合わせによっては1件も出ないので、出ても出なくても、見るところは変わりません。

`Tests:` の行の読み方だけ、10-5-3から変わります。予告が出たテストは `deprecated` のほうに数えられるので、`passed` の数と、書かれたテストの本数が合いません。上の画面では `ReplyTest` の3本はどれも落ちていませんが、1本目に予告が出たので、その1本だけ `deprecated` に入っています。

合否を決めているのは、**`failed` という語が出ているかどうか**だけです。

> ⚠️ **注意**: 10-5-7「テスト - ハンズオン演習」にも、`DEPR` と表示されてもテストは通っている、という注意書きがありました。同じ表示のことです。消そうとして `phpunit.xml` や `config/database.php` を触ると、テストそのものが動かなくなるほうが先に起きます。出たままにしてください。

## 落ちたときの読み方

1本落ちると、画面はこうなります。

```text
   FAIL  Tests\Feature\ReplyTest
  ! replies are listed on post page → Constant PDO::MYSQL_ATTR_SSL_CA i… 0.20s
  ✓ reply body is required                                               0.01s
  ⨯ user cannot delete others reply                                      0.02s
  ────────────────────────────────────────────────────────────────────────────
   FAILED  Tests\Feature\ReplyTest > user cannot delete others reply
  Expected response status code [403] but received 404.
Failed asserting that 404 is identical to 403.

  at tests/Feature/ReplyTest.php:37
     33▕         $user = User::factory()->create();
     34▕
     35▕         $response = $this->actingAs($user)->delete('/replies/1');
     36▕
  ➜  37▕         $response->assertStatus(403);
     38▕     }
     39▕ }

  Tests:    2 deprecated, 1 failed, 2 passed (5 assertions)
```

落ちた印は、テスト名の左の `⨯` です。その下の区切り線から先に、落ちた1本の中身が出ます。中身は3つに分かれています。どのテストが落ちたか（`FAILED` の行）、なぜ落ちたか（`Expected` から始まる行）、どこで落ちたか（`at` の行）。どんな理由で落ちるかはそのつど変わるので、見る場所のほうを覚えてください。

AIに渡すのは、この区切り線から下だけです。通ったテストの行も、`!` の行も、直すのには要りません。

```text
テストを回したら、次の1本が落ちました。原因を調べて直してください。
テストのほうは書き換えないでください。docs/reply.md に書いた観点のとおりです。

（FAILED の行から at tests/... の行までを貼る）
```

2行目を書いておくと、直る相手が実装のほうになります。書かずに渡すと、いま動いているコードに合わせてテストのほうが書き換えられることがあります。

落ちたテストを消したり、条件を緩めたりして通すのは禁じ手です。`failed` は消えますが、設計書に書いた観点と実物の食い違いは残ります。

直させたら、`--filter` を外してもう一度全部回します。1本を直した拍子に、別のテストが落ちることがあります。

## テスト観点と突き合わせる

`failed` が0でも、まだ終わりではありません。通ったテストが、確かめたかったことを確かめているかは別の話だからです。

`docs/reply.md` の「テスト観点」と、`tests/Feature/` に増えたテストを並べて見ます。この「テスト観点」は、13-8-1「テスト設計 - 設計の検証としてのテスト」で学んだテスト観点表を、設計書1ファイルの中に縮めたものです。観点の行がそれぞれテストになっているか。そして、観点に無いテストが増えていないか。

設計書は、実装より先にあなたが書いたものです。テストのほうを正として観点を読み替えるのは順番が逆で、**観点を正としてテストを読みます**。観点に無いテストが増えていたら、そのテストが何を確かめているのかを読んでください。読んで意味のあるものなら設計書に行を足し、意味が分からないものは消させて構いません。

実装とテストを一度に書かせたときには、テストが実装をなぞっているだけ、という形も出ます。「本文が空のままだと、エラーが表示されてリプライは増えない」の観点なら、テストが本当に空の本文を送っているかを、その1本だけ開いて確かめてください。空白を1文字入れて送って通っているだけなら、そのテストは通っても、確かめたかった境目を踏んでいません。

観点が全部、自動テストになるとも限りません。どの観点をどの手段で確かめるかは、人が決めます。

| テスト観点 | 確かめる手段 |
|:--|:--|
| ポストを1件開くと、そのポストとリプライの一覧が見える | テスト |
| 本文を入れてリプライを送ると、一覧に増える | テスト |
| 他人のリプライを消そうとすると、断られる | テスト |
| エラーの文言が、設計書に書いた日本語で出る | ブラウザで確かめる（14-4-3） |

上の3行は受け入れ条件から起こした観点で、4行目は `docs/reply.md` の「入力チェックとメッセージ一覧」から出てきた観点です。

3行目をテストに寄せるのは、他人のリプライには消すための操作が出ず、画面から試す道がないからです。テストなら、消す処理を直接呼んで断られることを見られます。この行のテストが書かれていない場合は、書き足させるか、判定がどこに置かれているかをコードで確かめる（14-4-2）かの、どちらかにします。

4行目が反対にテストへ向かないのは、文言を確かめるテストを書くと、設計書の文言を直すたびにテストも直すことになるからです。画面の前で読んだほうが速く終わります。

テストで確かめる、画面で確かめる、コードを読んで確かめる。どれかを済ませれば残りが要らなくなる、という関係にはありません。

## 🏃 テストを回して、観点と突き合わせる

### Step 1: 起動して、作業ブランチにいることを確かめる

アプリが止まっている場合は、Docker Desktop（またはDocker Engine）を起動してから、投稿アプリのフォルダでSailを立ち上げます。

```bash
# 投稿アプリのフォルダで実行する
./vendor/bin/sail up -d
git branch
```

`git branch` の一覧で、リプライ機能の作業ブランチに `*` が付いていることを確かめてください。付いていなければ、そのブランチへ切り替えます。

手直しはAIに渡すので、Claude Codeも開いておきます。テストを回すものとは別のターミナルで起動してください。

```bash
# 投稿アプリのフォルダで実行する
claude
```

### Step 2: テストを回して、結果を読む

```bash
# 投稿アプリのフォルダで実行する
./vendor/bin/sail test
```

画面をいちばん下までスクロールして、`Tests:` で始まる行を見ます。`failed` という語が無ければ、書かれたテストは全部通っています。

### Step 3: 観点と突き合わせる

`docs/reply.md` の「テスト観点」と、`tests/Feature/` に増えたファイルを両方開きます。

観点の行を上から1つずつたどって、対応するテストがあるかを見てください。無い行が出てきたら、テストで確かめるのか、ブラウザで確かめるのかを、その場で決めます。ブラウザで確かめると決めた行は、14-4-3で潰します。

### Step 4: 落ちていたら直させる

`failed` が出ていたら、区切り線から下をコピーして、上に載せた頼み方で渡します。直ったら、その直しを作業ブランチにコミットするところまで頼みます。

```text
テストが全部通りました。この直しを作業ブランチにコミットしてください。
```

思いどおりに直らない・壊れたと感じたら、14-5-1（直らないときの型）へ進んでください。まだコミットしていない変更は `git restore .`（4-3-5）で元に戻せます。

このセクションが終わった時点で、次の3つを確かめてください。

- [ ] `./vendor/bin/sail test` を回して、`Tests:` の行に `failed` が無いことを見た
- [ ] `docs/reply.md` のテスト観点が、それぞれテストとして書かれていることを確かめた
- [ ] テストにしない観点について、何で確かめるかを決めた

## ✨ まとめ

- テストは実装と同じ依頼に入れて、書く・回す・直す・報告するまでをAIの側で閉じさせます。人の手番は、報告と実行結果を読むところです。
- 実行結果で見るのは `Tests:` の行に `failed` があるかどうかだけです。`DEPR`・`!`・`deprecated` は合否に関係しません。
- 落ちたら、区切り線から下だけを渡し、テストは書き換えないでほしいと添えます。テストを消す・緩めるのは禁じ手です。
- `failed` が0でも、`docs/reply.md` の観点を正としてテストを読み直します。観点に無いテストが増えていたら、中身を読んで足すか消すかを決めます。
- テストにしない観点は、何で確かめるかをその場で決めます。
