# 14-4-2: セルフレビューと差分の受け取り

## 🎯 このセクションで学ぶこと

- Claude Codeに同梱されている `/code-review` で、いまのブランチの変更にレビューをかけられるようになる。
- `git diff main` で差分を受け取り、3段の順に読めるようになる。
- 引っかかったところを、名指しで直させられるようになる。

---

## 導入

リプライ機能で書き換わったファイルは、10近くあります。上から順に全部読もうとすると、後半は文字を追うだけになります。先に機械へ読ませて、そのあと順番を決めて自分で読みます。フローでいうと、いまいるのは「レビュー」です。

---

## /code-reviewとは

`/code-review` は、Claude Codeに最初から入っているレビュー用のコマンドです。いまの変更を、間違いと整理の観点で見て指摘します。何かを追加で入れる必要はありません。セッションの中で、次を送ります。

```text
/code-review
```

素の `/code-review` が見るのは、いまいるブランチで積んだコミットと、まだコミットしていない変更です（2026年8月時点）。リプライ機能の作業ブランチにいれば、そのブランチで増えた分がそのまま対象になります。

打ち始めると、入力欄の右側に、後ろに付けられるものが並んで出ます。

```text
/code-review [low|medium|high|xhigh|max|ultra] [--fix] [--comment] [<pr#>|<branch>|<path>]
```

角括弧は「付けても付けなくてもよい」という意味で、`|` で区切られているのはどれか1つを選ぶという意味です。

| 付けるもの | 何が変わるか |
|:--|:--|
| `low` 〜 `max` | どれくらい広く見るか。`low`・`medium` は確度の高いものに絞り、`high` から上は広く見るかわりに、確かでないものも混ざります。付けないと、前に指定した段階のまま動きます |
| `ultra` | 💰 クラウドで動く、多数のエージェントによる深いレビュー。定額の外なので、この教材では使いません |
| `--fix` | 見つけた指摘を、そのまま直させます |
| `--comment` | 指摘を、プルリクエストの該当行へのコメントとして書き込みます |
| `<pr#>` `<branch>` `<path>` | 見せる相手を変えます。プルリクエストの番号・ブランチ名・ファイルのパスのどれかです |

**この節では、どれも付けずに送ります。** とくに `--fix` を付けないのは、出てきた指摘のどれを直してどれを直さないかを決めるのが、このあとの仕事だからです。

送ると、その場に1行だけ出て、プロンプトはすぐ入力できる状態に戻ります。

```text
❯ /code-review
  ⎿  Running in the background as @code-review
```

**`/code-review` を送った直後の画面**

レビューは裏で動いています。画面の下のほうに、動いている作業として経過秒数つきで並びます。終わると、会話のほうに次の行が届き、続けて指摘が出ます。

```text

```

行の末尾には、かかった時間が付きます。何分になるかは、変更の量で変わります。送ってから画面の前で待つのではなく、届いたら読む、という付き合い方になります。届くまでのあいだ、同じセッションで別のことを頼んでも構いません。

## 届いた指摘を、直すものと直さないものに分ける

出てくるのは、機械が見つけた候補です。全部が直す対象になるとは限りません。読むときの物差しは `docs/reply.md` で、設計書に書いたことと食い違っているものから先に直します。

直させるときは、どこをどう直すかを名指しします。ファイル名とクラス名はAIが決めたものなので、自分の手元にあるものへ置き換えてください。

```text
app/Http/Controllers/ReplyController.php の store で、
Reply::create($request->all()) の形になっています。
docs/reply.md の「入力チェックとメッセージ一覧」のとおりに validate() を通して、
その結果と、ログイン中のユーザーのIDだけを渡す形に直してください。
ほかのファイルは変えないでください。
```

どう直すかを設計書を根拠に書いておくと、直し方をAIが決めずに済みます。直させたら、`./vendor/bin/sail test` をもう一度回してから（14-4-1）、作業ブランチにコミットします。

## 差分を受け取る場所

機械が読んだあとに、自分でも読みます。差分は `git diff` で出せます。比べる相手は `main` です。作業ブランチは `main` から切ったので、`main` との差が、このブランチで増えた分と一致します。

```bash
# 投稿アプリのフォルダで実行する
git diff --name-only main
git diff main
```

`--name-only` を付けると、変わったファイルの名前だけが並びます。全体の量を眺めるのに向いています。付けなければ、変わった行がそのまま出ます。長いので、ターミナルの中で少しずつ送りながら読んでください。

14-1-2で使ったVS Codeのソース管理ビューには、ここでは何も並びません。あちらに出るのは**まだコミットしていない変更**で、リプライ機能の実装はもうコミット済みだからです。いま読みたいのは、このブランチで積んだコミットまで含めた `main` との差なので、`git diff` を使います。ソース管理ビューが役に立つのは、このあと直させたときです。直った内容がコミット前にそこへ並びます。

## 読む順番

### 1. 設計書と突き合わせる

`docs/reply.md` に書いたものが、そのとおりに増えているかを見ます。テーブルとカラム、画面、入力チェックの3か所です。

ここで力を入れるのは、書いたものがあるかどうかの確認より、**書いていないものが増えていないか**のほうです。増えやすいのは、カラムと画面、それからパッケージです。`composer.json` が一覧に出ていたら、頼んでいない依存が足されています。自分で書き換えるつもりのないファイルなので、一覧を眺めるときにいちばん目が滑ります。名前だけ覚えておいて、出ていないかを見てください。

### 2. 触っていないはずの場所を見る

リプライ機能で変える約束をしていない場所です。

| 見る場所 | 前からあるもの |
|:--|:--|
| `routes/web.php` | ポストの4本のルート |
| `app/Http/Controllers/PostController.php` | ポストの一覧・編集・更新・削除 |
| `app/Policies/PostPolicy.php` | ポストを編集・削除できる人の判定 |
| `resources/views/posts/index.blade.php` | タイムラインの画面 |

この4つのうち、`routes/web.php` と `resources/views/posts/index.blade.php` には差分が出ます。リプライのルートが増え、タイムラインからポストの詳細画面へ入るリンクが1本増えるからです。ここで読むのは、増えた行より、前からあった行がそのまま残っているかどうかです。リンク1本と数行で収まるはずのところに10行を超える差分が出ていたら、ついでの書き換えが混ざっています。

とくに見るのは、消えた行です。`git diff main` の出力では、`-` から始まる行がそれにあたります。足された行は頼んだものが出てくるので読みやすく、消えた行は自分が過去に読んだものなので、飛ばしても違和感がありません。たとえば `PostController::update()` の先頭にある `$this->authorize('update', $post)` の1行が整理のついでに消えていても、自分のポストを編集している限り、画面の見た目は何も変わりません。他人のポストを開いたときに初めて表に出ます。

### 3. 中身を読む

1段目と2段目でも差分は読んでいますが、見ていたのは何が増えて何が消えたか、という範囲のほうです。3段目で見るのは、増えた行の中身です。読み始める前に、この機能に当たる観点だけを決めておきます。一覧を上から順に当てていくと、関係のない行で手が止まります。

| 見るところ | このコードでの具体形 | 学んだ場所 |
|:--|:--|:--|
| N+1 | リプライ一覧で書いた人の名前を出しているのに、`with()` が付いていないか | 9-5-1・9-5-3 |
| 認可の置き場所 | 「消せるのは書いた本人だけ」の判定が、どこに書かれているか | 10-3-5 |
| マスアサインメント | `Reply::create($request->all())` の形になっていないか | 9-4-8 |
| XSS | リプライの本文を `{!! !!}` で出していないか | 10-6-3 |
| CSRF | リプライの入力フォームに `@csrf` があるか | 10-6-1 |
| 入力チェック | `validate()` の中身が、設計書の入力チェックと合っているか | 9-6章 |
| 書き方の揃い | いまあるコードと同じ呼び方・同じ書き方になっているか | 12-3-5 |

仕組みは、どれもすでに学んだところです。ここで新しいのは、自分が書いていないコードにこれを当てるという点だけです。差分に `tests/` のファイルが出ていたら、そちらの中身も同じように読みます。読むときの見方は14-4-1にあります。

## 物差しは手元にある

「同じ書き方になっているか」を見るには、比べる相手が要ります。タイムラインを出しているコードが、そのまま物差しになります。

```php
// app/Http/Controllers/PostController.php
public function index()
{
    $posts = Post::with(['user', 'category'])->latest()->get();

    return view('posts.index', compact('posts'));
}
```

タイムラインの画面では、ポストごとに `{{ $post->user->name }}` と `{{ $post->category->name }}` を出しています。そのために `with(['user', 'category'])` が付いています。リプライ一覧でも、リプライごとに書いた人の名前を出すのなら、同じことが要ります。

画面のほうにも物差しがあります。`resources/views/posts/index.blade.php` には、`@can('update', $post)` でボタンを出し分けている箇所と、フォームの中に `@csrf` を置いている箇所があります。リプライの削除ボタンと入力フォームが、この形から外れていないかを見ます。

「AIはこう書きがちだ」と決めつけて探すのではなく、手元にある形と見比べて、外れていたら気づく。これがレビューのやり方です。

> ⚠️ **注意**: このアプリには、データベースへの問い合わせ回数を画面に出す道具は入っていません。9-5-3「Eager Loadingとレイジーローディング」で使ったものを、わざわざ入れなくて構いません。ここで見るのは、コードに `with()` が書かれているかどうかです。

## 判定は1か所に集める

「消せるのは書いた本人だけ」という決まりは、ポリシーに書いても、コントローラーの中に `if` で書いても、画面の上での動きは同じになります。それでも、1か所に集めておくほうが後で困りません。

同じ判定が2か所に書かれていると、片方だけ直したときに食い違います。将来「ポストを書いた人も、そのポストへのリプライを消せる」に変えるとします。判定がポリシーに1つだけあれば、直すのは1か所です。コントローラーと画面の両方に条件が書いてあれば、片方を直し忘れたときに、ボタンは出るのに押すと403になります。

画面から隠すだけでは止められない、という事情もあります。このアプリでも、他人のポストの編集画面を直接URLで開くと403になります。ボタンを消しても、URLを直接打たれたら通ってしまうので、止めるには処理そのものの手前に判定が要ります。

読むときに見るのは、判定の文が同じかどうかよりも、その判定がどこに何回書かれているかです。

---

## 説明と実物が合っているか

AIは、作業のあとに「〜を追加しました」という報告を出します。報告に書かれていることが差分の中にあるか、差分にあることが報告に書かれているかを見ます。食い違ったときに読む相手は、差分のほうです。

## 🏃 セルフレビューを回して、差分を読む

### Step 1: `/code-review` を送る

投稿アプリのフォルダ（14-1-3でCLAUDE.mdを作ったフォルダ）でClaude Codeを起動し、リプライ機能の作業ブランチにいることを確かめてから送ります。

```bash
# 投稿アプリのフォルダで実行する
claude
```

```text
/code-review
```

`Running in the background as @code-review` が出て、入力できる状態に戻れば動いています。

### Step 2: 届くまでに、変わったファイルの一覧を見る

別のターミナルで、名前だけを出します。

```bash
# 投稿アプリのフォルダで実行する
git diff --name-only main
```

`docs/reply.md` に書いていないファイルが混ざっていないかを見てください。上の「触っていないはずの場所」の4つが一覧に出ていたら、`git diff main` でその中身を読みます。

### Step 3: 届いた指摘を読む

`Agent "/code-review" finished` の行が出たら、その下に指摘が並びます。1つずつ、`docs/reply.md` と突き合わせてください。設計書と食い違っているものが、直す対象です。

### Step 4: 直させて、テストを回し直す

上に載せた形で名指しして直させます。直ったら、テストを回して `Tests:` の行に `failed` が無いことを確かめ、作業ブランチにコミットするところまで頼みます。

```bash
# 投稿アプリのフォルダで実行する
./vendor/bin/sail test
```

指摘が1つも無かった場合や、読んだうえで直さないと決めた場合は、コミットするものはありません。そのまま次へ進んでください。

思いどおりに直らない・壊れたと感じたら、14-5-1（直らないときの型）へ進んでください。まだコミットしていない変更は `git restore .`（4-3-5）で元に戻せます。

このセクションが終わった時点で、次の4つを確かめてください。

- [ ] `/code-review` を送り、届いた指摘を最後まで読んだ
- [ ] `git diff --name-only main` の一覧に、設計書に書いていないファイルが無いことを見た
- [ ] 「触っていないはずの場所」の4つについて、差分が出ているかを見た
- [ ] 直させたところがある場合は、テストを回し直して作業ブランチにコミットした

## ✨ まとめ

- レビューの一手目は同梱の `/code-review`。素の形で、いまいるブランチのコミットと未コミットの変更を見ます。
- `/code-review` は裏で動き、結果は後から会話に届きます。送ってから待たず、届いたら読みます。
- 差分は `git diff --name-only main` で一覧、`git diff main` で中身。比べる相手は `main` です。
- 読む順番は、設計書との突き合わせ、触っていないはずの場所、中身の3段です。
- 1段目で探すのは、書いたものの有無よりも、書いていないものが増えていないかです。`composer.json` は名前だけ覚えておきます。
- 2段目で見落とすのは、消えた行です。`-` から始まる行を先に探します。
- 3段目に入る前に、この機能に当たる観点を絞ります。比べる相手は、タイムラインのコードが持っています。
