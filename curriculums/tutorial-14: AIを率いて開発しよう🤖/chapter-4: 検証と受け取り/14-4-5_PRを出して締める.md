# 14-4-5: PRを出して締める

## 🎯 このセクションで学ぶこと

- 検証の証拠を本文に載せたプルリクエストを、AIに作らせられるようになる。
- できた本文と差分を読んで、受け取ってよいかを決められるようになる。
- マージまで済ませて、イシューが閉じるところまで1周を締められるようになる。

---

## 導入

テストも受け入れ条件も潰し終わりましたが、その結果はいまのところ、あなたの手元とAIとのやり取りの中にしかありません。半年後にこのコードを開いた人は、何を確かめて受け取ったのかを知る手立てがありません。残す場所がプルリクエストです。フローでいうと、最後の「PR」です。

---

## 記録の単位

| 単位 | 何に対応するか | 今回の中身 |
|:--|:--|:--|
| ブランチ1本 | 機能イシュー1件 | リプライ機能の作業ブランチ |
| プルリクエスト1本 | 機能イシュー1件 | 本文に `Closes #<自分が立てたイシューの番号>` を入れる |
| コミット | 動くところまで進んだひと区切り | AIが区切ります |

12-2-1「イシュー駆動開発とは」で学んだ形と同じです。違うのは、ブランチを切るのもコミットするのもプルリクエストを出すのも、依頼の中に入れてAIにやらせる点です。`Closes #1` の書き方は12-2-4「ハンズオン - GitHub連携演習」で使ったもので、この1行があると、プルリクエストがマージされたときにイシューが自動で閉じます。番号は、自分が立てたイシューのものに置き換えてください。

---

## 本文に載せるのは、検証の証拠

プルリクエストの本文に書くのは、何を作ったかと、それをどうやって確かめたかです。確かめたことは、この章で全部済んでいます。

- テストの実行結果（14-4-1）
- 受け入れ条件4行の結果（14-4-3・14-4-4）

作成もAIに頼めます。

```text
リプライ機能のプルリクエストを出して。

- 作業ブランチを origin に push してから gh pr create を使って
- 本文に、何を作ったかの要約
- 本文に、sail test の結果（Tests: の行）
- 本文に、受け入れ条件の4行と、それぞれ確かめたかどうか
- 本文の最後に Closes #<自分が立てたイシューの番号>
```

受け入れ条件の4行は `docs/reply.md` にあるので、依頼文の中で書き写しません。ただし、それを画面で確かめたのはあなたなので、出てきた本文の判定が自分の見たとおりかは読んで確かめます。違っていたら、その行を直させます。

---

## いまは、自分が受け取る側

12-2-3「プルリクエストの作成とレビュー」で出したプルリクエストは、他の人が読む前提のものでした。いまは、書いたのがAIで、受け取るかどうかを決めるのがあなたです。読む手順もこの章で決まっています。機械の一手目が `/code-review`、そのあと差分を3段で読み（14-4-2）、画面で受け入れ条件を潰す（14-4-3・14-4-4）。最後にマージするかどうかを決めるところだけが、人の手に残ります。

プルリクエストができると、GitHubの「Files changed」に差分が並びます。14-4-2で `git diff main` に見たものと同じものが、ブラウザで読める形になっているだけです。手元で読み切れなかったところがあれば、ここで読み直せます。

---

## 検証を通してから、マージする

受け入れ条件が全部埋まったら、マージします。これもAIに頼めます。

```text
docs/reply.md の受け入れ条件を全部確かめました。
プルリクエストをマージして、ブランチを消してください。
そのあと、手元も main に切り替えて最新にしてください。
```

AIは `gh pr merge` を実行し、リモートと手元のブランチを片づけて、`main` を最新にします。本文に `Closes #` の行が入っていれば、マージと同時にイシューも閉じます。閉じたかどうかは、自分で見られます。

```bash
# 投稿アプリのフォルダで実行する
gh issue view <自分が立てたイシューの番号>
```

`gh issue view` は、イシュー1件の中身と状態をターミナルに出すコマンドです。`CLOSED` と表示されれば、イシューからブランチ、実装、検証、マージまでが1周しました。

順序には意味があります。この章のあいだ、プルリクエストは作らずに置いてありました。もし確かめる前にマージしていたら、いま見つかった食い違いを直す相手は `main` です。ブランチを切り直し、プルリクエストを出すところからやり直すことになります。ブランチの上で直せば、直した記録も同じプルリクエストの中に残ります。

## 🏃 プルリクエストを出して、マージする

### Step 1: 作業ブランチにいることを確かめる

投稿アプリのフォルダ（14-1-3でCLAUDE.mdを作ったフォルダ）で、リプライ機能の作業ブランチに `*` が付いていることを見てから、Claude Codeを起動します。

```bash
# 投稿アプリのフォルダで実行する
git branch
claude
```

### Step 2: プルリクエストを出させる

上に載せた依頼を送ります。イシューの番号は、14-3-3で自分が立てたものに置き換えてください。番号を忘れていたら、`gh issue list` で一覧を出せます。

終わると、プルリクエストのURLが返ってきます。

### Step 3: 本文と差分を読む

返ってきたURLをブラウザで開き、本文を読みます。

- 何を作ったかの要約が、`docs/reply.md` の中身と合っているか
- `Tests:` の行が入っていて、`failed` が無いか
- 受け入れ条件の4行が並んでいて、判定が自分の見たとおりか
- 最後に `Closes #` の行があり、番号が自分のイシューのものか

違っているところがあれば、その場で直させます。プルリクエストの本文の書き直しも、AIに頼めます。

### Step 4: マージまで頼む

本文を読み終えたら、上に載せたマージの依頼を送ります。終わったら、イシューが閉じたことを確かめます。

```bash
# 投稿アプリのフォルダで実行する
gh issue view <自分が立てたイシューの番号>
```

**マージ済みのプルリクエストと、閉じたイシュー**

思いどおりに直らない・壊れたと感じたら、14-5-1（直らないときの型）へ進んでください。まだコミットしていない変更は `git restore .`（4-3-5）で元に戻せます。

このセクションが終わった時点で、次の4つを確かめてください。

- [ ] プルリクエストの本文に、`Tests:` の行と受け入れ条件4行の判定が載っていることを見た
- [ ] 本文の最後の `Closes #` が、自分が立てたイシューの番号になっていることを見た
- [ ] マージのあと、`main` にリプライ機能と `docs/reply.md` が入っていることを見た
- [ ] `gh issue view` で、イシューが `CLOSED` になっていることを見た

## ✨ まとめ

- プルリクエストは、機能イシュー1件に1本。本文に検証の証拠を書かせて、あとから読める場所に残します。
- 本文に入れるのは、テストの実行結果と、受け入れ条件4行の判定と、`Closes #<自分が立てたイシューの番号>` です。
- 受け入れ条件を画面で潰したのは人なので、本文に書かれた判定は自分で読み直し、食い違っていれば直させます。
- 「Files changed」に出るのは、`git diff main` で読んだものと同じ差分です。
- マージは、検証を全部通してからです。マージもAIに頼め、`Closes #` の行があればイシューも一緒に閉じます。
- `gh issue view` で `CLOSED` を見たら、イシューからマージまでの1周が終わりです。
