# 14-5-2: 振り返りと設計書の寿命

## 🎯 このセクションで学ぶこと

- 2つの機能を作るあいだ、何を自分がやり、何をAIがやったのかを言えるようになる。
- 実装が終わったあと、設計書をどう扱うのかを決められるようになる。
- コードには残らない決めごとを、READMEに書き残せるようになる。

---

## 導入：手元に何が残ったか

アプリには、投稿へのコメント機能と、投稿を自分で書く機能が入りました。Tutorial 14で作ったものを並べると、次のようになります。

| 残ったもの | 中身 |
|:--|:--|
| コードとテスト | `main` にマージ済み。`./vendor/bin/sail artisan test` で回せます |
| 設計書 | `docs/comment/` と `docs/post-create/` に8ファイルずつ。ほかに14-2-3で起こした `docs/mermaid-practice.md` が1枚 |
| レビュー観点表 | `docs/review-checklist.md` |
| 記録 | 閉じた機能イシュー2件と、マージ済みのプルリクエスト2本 |

このセクションでやることは2つです。ここまでの進め方を振り返ることと、**この設計書をこのあとどうするのかを決めること**です。

---

## 何を自分がやり、何をAIがやったか

2つの機能を通して、作業はこう分かれていました。

| 場面 | あなたがやったこと | AIがやったこと |
|:--|:--|:--|
| 要件を決める | 何を作り、何を作らないかを決めた | なし |
| 設計書を書く | 列名・記号・ロール名を指定し、出てきたものを直した | 文章と図を書いた |
| タスクに割る | 区切りの大きさを3つの基準で決めた | 割り方の案を出した |
| 実装する | 計画を承認し、差分を1つずつ読んで承認した | コードとテストを書いた |
| 検証する | テストを回し、コードを読み、受け入れ条件と突き合わせた | 見つかったところを直した |
| 記録する | イシューに印を付け、プルリクエストを出してマージした | なし |

右の列が「なし」の行が2つあります。要件を決めるところと、記録するところです。この2つには、そもそもAIの出番がありませんでした。

残りの4行を見ても、AIがやったのは**書くこと**だけです。設計書の文章を書く、コードを書く、テストを書く、直す。決めることと、確かめることは、最初から最後まであなたの側にありました。14-1-1で「作らせてよいのは、書く作業のほうです」と書いた線が、そのまま2つの機能分の実績になっています。

決めていなかったことは、AIからの質問として表に出ました。コメントの一覧は新しい順と古い順のどちらで並べるのか。14-2-4でこれを聞かれて手が止まったのは、AIが分からなかったからではなく、**設計書のどこにも書いていなかった**からです。質問が来たとき、答えが設計書の中にあるなら読み方の問題で、どこにも無ければ設計の穴でした。

---

## 設計書は、いつまで正しいのか

ここからが、このセクションの本題です。

設計書は、これから作るものを決めた書類でした。決めていないことを渡すとAIが決めてしまうので、先に文字にしておく。そのために書きました。

その役目は、実装が終わった時点でいったん終わります。マージしたあと、このアプリが**いまどうなっているか**を決めているのは、コードとテストです。設計書ではありません。

食い違ったときのことを考えると、はっきりします。`api.md` には `PATCH /posts/{post}/status` と書いてあるのに、実物のルートが違っていたとします。ブラウザで動いているのは実物のほうです。設計書を書き換えても、画面は何も変わりません。直す相手はコードで、設計書はそのあとに付いてくる書類になります。

ですから、`docs/comment/` と `docs/post-create/` を、これから先ずっと実物に合わせて直し続ける必要はありません。**この2つは、使い終えた書類として残します。更新はしません。**

> ⚠️ **注意**: 危ないのは、更新しない設計書を「いまの仕様書」のつもりで置いておくことです。次に読んだ人は、そこに書いてあることが今も生きていると思って読みます。半年後に足された機能が反映されていない設計書は、何も書いていないより始末が悪くなります。機能ごとにフォルダを分けたのは、「これはコメント機能を作ったときの決めごとだ」と、あとから読む人が範囲を絞れるようにするためでもあります。

そうならないように、1つだけ手を打っておきます。`docs/comment/README.md` と `docs/post-create/README.md` の1行目に、次の1文を書き足してください。いつの時点のものかが、開いた人にすぐ伝わります。

```markdown
> この設計書は、この機能を実装した時点の記録です。このあとは更新していません。
```

扱いが違うものが2枚あります。1枚は `docs/review-checklist.md` です。これは特定の機能に属していません。次にどんな機能を作るときも、同じ観点でコードを読みます。14-4-2で「後で使い回せる形にしておきます」と書いたのは、このためです。**これは残します。** もう1枚は `docs/mermaid-practice.md` で、こちらは記法の練習で書いたものなので、消して構いません。

## コードに残らないもの

コードとテストが基準になる、と言いましたが、全部がそこに残るわけではありません。

コードに書いてあるのは、**何をしているか**です。書いていないのは、**なぜそうしたか**です。今回の2つの機能でも、次のことはコードから読み取れません。

| コードに現れている形 | 読み取れないこと |
|:--|:--|
| `status` の既定値が `published` | 既にあった投稿を一覧から消さないために、そう決めたこと |
| 状態が `draft` と `published` の2つ | 公開待ちや削除済みを作らない、と決めた結果であること |
| コメントに編集の処理が無い | 作り忘れではなく、作らないと決めたこと |
| 判定がポリシーに1つだけある | 画面から隠すだけでは止まらないので、1か所に集めたこと |

13-6-2「状態遷移設計 - ステータスの一生を描く」で、引かなかった矢印にも意味がある、と学びました。引かなかった矢印は、コードには跡が残りません。同じように、作らなかった機能も、選ばなかった作り方も、実物を見ただけでは分かりません。

これが困るのは、半年後です。`default('published')` という1行を見た人は、なんとなくそうなっているのだと読みます。そして、良かれと思って `draft` に変えます。次の日、既にあった投稿が一覧から消えます。

決めた理由だけは、コードのそばに移しておきます。

## 設計意図をREADMEに残す

置き場所は、アプリの `README.md` です。14-1-2でClaude Codeに1行足してもらった、あのファイルです。リポジトリを開いた人がいちばん最初に読む場所なので、探さなくても目に入ります。

書くのは、次の4種類です。

| 書くこと | このアプリでの例 |
|:--|:--|
| 作らないと決めたものと、その理由 | コメントの編集は作らない。消して書き直せば足りるため |
| 選べたのに選ばなかった作り方と、その理由 | 状態は2つだけ。公開待ちは作らない |
| 知らずに変えると壊れる決めごと | `status` の既定値は `published`。既にある投稿を一覧から消さないため |
| 設計書のありか | `docs/comment/` と `docs/post-create/` |

書かないものも決めておきます。**何ができるかの説明は書きません。** それはコードを読めば分かりますし、機能が増えるたびに書き足す約束になってしまいます。READMEに残すのは、コードを読んでも分からないことだけです。

### 下書きをAIに作らせる

ここから1つだけ手を動かします。材料は、それぞれの機能フォルダの `README.md` にあります。「作らなかった設計書とその理由」を、あそこに書き残してありました。

```text
README.md の末尾に「## 設計のメモ」という見出しを作り、
次の2つの機能について、なぜそう作ったのかを箇条書きで書いてください。

- 投稿へのコメント機能（docs/comment/）
- 投稿の作成と下書き（docs/post-create/）

書くのは、作らないと決めたもの・選ばなかった作り方・知らずに変えると壊れる決めごと・
設計書のありかの4つだけです。何ができるかの説明は書かないでください。コードを読めば分かることだからです。
@docs/comment/README.md と @docs/post-create/README.md を読んで、下書きにしてください。
```

> 💡 このお願いのポイントは3つです。①書く場所と見出しを指定している ②書く中身を4つに絞っている ③書かないものを名指ししている。③が無いと、返ってくるのは機能紹介になります。AIから見れば、そちらのほうが自然なREADMEだからです。文言をそのまま覚える必要はありません。

> 💡 **出力例について**: AIの応答は毎回変わります。以下はあくまで一例です。文言が違っても、チェックリストの項目を満たしていれば問題ありません。

```markdown
## 設計のメモ

### 投稿へのコメント機能

- コメントの編集は作っていません。消して書き直せば足りるためです。
- 「消せるのは書いた本人だけ」の判定は、ポリシーに1か所だけ置いています。画面のボタンを消すだけでは、URLを直接開かれたときに止まらないためです。
- 設計書は `docs/comment/` にあります。

### 投稿の作成と下書き

- `posts.status` の既定値は `published` です。列を足したときに、既にあった投稿が一覧から消えないようにするためです。新しく作る投稿は、登録の処理で `draft` を入れています。
- 状態は「下書き」と「公開済み」の2つだけです。公開待ちや削除済みは作っていません。
- 設計書は `docs/post-create/` にあります。
```

出てきた下書きは、そのまま置きません。分担はこれまでと同じで、**書くのはAI、直すのは自分**です。読むときに見るのは2つだけです。理由が書かれているか。何ができるかの説明が紛れ込んでいないか。

書けたら、記録します。機能フォルダの `README.md` に足した1行も、ここで一緒に記録します。

```bash
# アプリのフォルダの中で実行する
git add README.md docs
git commit -m "Add design notes to README"
git push origin main
```

この記録は、どちらの機能イシューにも属していません。だからコミットメッセージにイシューの番号を入れていません。2件とも、もう閉じています。

書き終えたら、次の5つを確かめてください。

- [ ] `README.md` に「設計のメモ」があり、2つの機能の分が書かれている
- [ ] 書かれているのが「なぜそうしたか」で、「何ができるか」の説明が入っていない
- [ ] 知らずに変えると壊れる決めごとが、1つ以上書かれている
- [ ] 設計書のありか（`docs/comment/` と `docs/post-create/`）が書かれている
- [ ] GitHubでリポジトリのページを開いて、書いたものが表示されている

## 💡 よくある間違い

**作り終えた設計書を、いまの仕様書のつもりで置いたままにする**

いつの時点のものかを書き足さずに残すと、この形になります。

**READMEに機能の説明を書く**

「投稿にコメントを付けられます」のような行です。書きたくなりますが、READMEはその置き場所ではありません。

**何も残さない**

いちばん多いのがこれです。決めた本人は理由を覚えているので、書き残す必要を感じません。忘れたころに触るのは、たいてい自分です。

## ✨ まとめ

- 2つの機能を通して、AIがやったのは書くことだけでした。決めることと確かめることは、最初から最後まで自分の側にありました。
- 決めていなかったことは、AIからの質問として表に出ます。設計書で答えられない質問が来たら、それが設計の穴です。
- 実装が終わると、いまどうなっているかを決めるのはコードとテストです。機能フォルダの設計書は、使い終えた書類として残します。更新はしないので、いつの時点の記録かを1行書き添えます。
- `docs/review-checklist.md` だけは残します。特定の機能に属さず、次の機能でも同じ観点で読むためです。
- コードには「何をしているか」しか残りません。作らないと決めたもの、選ばなかった作り方、知らずに変えると壊れる決めごとは、READMEに書き残します。

これでTutorial 14は終わりです。設計書を渡してAIに実装させ、テスト・コードレビュー・受け入れ確認の3つで検証し、`main` に入れるところまでを、2つの機能で回し切りました。品質の責任を自分が握る、というのは、この3つを自分の手で通すことでした。

ここまでのあいだ、毎回手でやっていたことがあります。このアプリの前提を依頼のたびに説明し直すこと。同じレビュー観点を毎回その場で伝えること。承認を1つずつ押すこと。テストを自分で回すこと。これらを毎回の作業から取り出して、あらかじめ置いておく方法は、次のTutorial 15で扱います。

そのあとのTutorial 16では、ここまでに身につけたものを持ち寄って、アプリを1本作り上げます。
