# 14-5-2: 振り返りと設計書の寿命

## 🎯 このセクションで学ぶこと

- 2つの機能を作るあいだ、何を自分がやり、何をAIがやったのかを言えるようになる。
- 実装が終わったあと、書いた設計書をどう扱うのかを決められるようになる。
- コードには残らない決めごとを、READMEに書き残せるようになる。

---

## 導入：置きっぱなしの設計書は、いまの仕様書に見える

手元には、2つ分の設計書が残りました。`docs/comment.md` と `docs/draft.md` です。どちらも、機能を作り終えたあとのまま置いてあります。

この2枚を、このあとどう扱うかを決めずに置いておくと、半年後に開いた人は困ります。開いた人には、それが古い記録なのか、いまのアプリを説明した書類なのかが分かりません。書いてあるとおりに動くと思って読み、違うところで足を取られます。

そうならないよう、このセクションで扱いを決めます。あわせて、2機能分の進め方を振り返ります。

---

## 何を自分がやり、何をAIがやったか

コメント機能と下書き機能を通して、作業はこう分かれていました。

| 場面 | あなたがやったこと | AIがやったこと |
|:--|:--|:--|
| 要件を決める | 実現したいこと・変えたくないこと・受け入れ条件を決めた | なし |
| イシューを立てる | なし | `gh` でイシューを作った |
| 設計する | 譲れないところを指定し、出てきた案から選んだ | 案を出し、設計書にまとめた |
| 実装する | 計画を読んで承認した | ブランチを切り、コードとテストを書き、コミットしてプルリクエストを出した |
| 検証する | テストを回し、受け入れ条件と突き合わせた | 指摘された分を直した |
| マージする | なし | `gh` でマージした |

手を止めたのは、計画を承認するところと、受け入れ条件と突き合わせるところの2箇所だけです。ファイルを1つずつ承認して回る場面はありませんでした。

右の列が「なし」の行が2つあります。要件を決めるところと、判定するところ。この2つに、AIの出番がありませんでした。14-1-1で置いた「ゴールを決めることと、できたものを検証すること」が、そのまま2機能分の実績になっています。

---

## 実装が終わったあとの正本

設計書は、これから作るものを決めた書類でした。決めていないことを渡すとAIが決めてしまうので、先に文字にしておく。そのために書きました。

その役目は、マージした時点で終わります。ここから先、このアプリがいまどうなっているかを決めているのは、コードとテストです。

食い違ったときにどうなるかを考えると、はっきりします。半年後、誰かが状態の切り替えを直して、他人の投稿も切り替えられるようにしてしまったとします。このとき、Chapter 5で書いたテストは赤くなります。`./vendor/bin/sail artisan test` を回した人に、その場で「決めたことが変わった」と伝わります。`docs/draft.md` は何も言いません。ファイルの中では、いまも「切り替えてよいのは本人だけ」と書かれたままです。

黙っている書類は、正本になれません。正本になれるのは、実物とずれたときに気づける側です。だからコードとテストを基準に置きます。

もう1枚、いま手元でずれているものがあります。14-2-3でAIに書かせた `docs/structure.md` です。あれを書いた時点でクラスは5つでしたが、Chapter 3でコメント機能を作ったので、いまはコメントを扱うクラスが増えています。図はそのままなので、開いた人はいまのアプリより1つ少ない構造を読むことになります。誰も直せと言ってくれません。

`docs/comment.md` と `docs/draft.md` を、これから先ずっと実物に合わせて直し続ける必要はありません。この2枚は、**その機能を作ったときの記録**として残します。更新はしません。

ファイル名が、範囲の目印になっています。`docs/comment.md` に書いてあるのはコメント機能を作ったときの決めごとで、下書き機能の話は入っていません。あとから読む人は、ファイル名を見て「これはコメントを作ったときの記録だ」と範囲を絞れます。1機能を1ファイルにまとめておくと、この読み方ができます。

そのうえで、1行だけ足しておきます。それぞれの1行目に、次の1文を書いてください。開いた人に、いつの時点のものかがすぐ伝わります。

```markdown
> この設計書は、この機能を実装した時点の記録です。このあとは更新していません。
```

## コードに残らないもの

コードとテストが基準になる、と言いましたが、全部がそこに残るわけではありません。

コードに書いてあるのは、**何をしているか**です。書いていないのは、**なぜそうしたか**です。2つの機能でも、次のことは実物から読み取れません。

| コードに現れている形 | 読み取れないこと |
|:--|:--|
| 状態の列の初期値が公開の側 | もとからあった4件を一覧から消さないために、そう決めたこと |
| 状態が2つだけ | 公開待ちや削除済みを、意図して作らなかったこと |
| 切り替えの操作が1つの画面にある | 3つの案から選んだ結果であること |
| コメントに編集の処理が無い | 作り忘れではなく、消して書き直せば足りると判断したこと |

13-6-2「状態遷移設計 - ステータスの一生を描く」で、引かなかった矢印にも意味がある、と学びました。引かなかった矢印は、コードに跡が残りません。作らなかった機能も、選ばなかった作り方も、実物を見ただけでは分かりません。

これが困るのは、半年後です。列の初期値の1行を見た人は、なんとなくそうなっているのだと読みます。そして、良かれと思って初期値を下書きの側に変えます。次の日、もとからあった投稿が一覧から消えます。14-5-1で自分が一度踏んだのと、同じ穴です。

決めた理由だけは、コードのそばに移しておきます。

## 🏃 設計意図をREADMEに残す

置き場所は、アプリの `README.md` です。リポジトリを開いた人がいちばん最初に読む場所なので、探さなくても目に入ります。

書くのは、次の4種類です。

| 書くこと | このアプリでの例 |
|:--|:--|
| 作らないと決めたものと、その理由 | コメントの編集は作らない。消して書き直せば足りるため |
| 選べたのに選ばなかった作り方と、その理由 | 状態は2つだけ。公開待ちは作らない |
| 知らずに変えると壊れる決めごと | 状態の列の初期値。もとからある投稿を一覧から消さないため |
| 設計書のありか | `docs/comment.md` と `docs/draft.md` |

何ができるかの説明は書きません。`README.md` の「できること」に、もう書いてあります。同じことを書き足すと、機能が増えるたびに2箇所を直す約束になります。

### Step 1: 下書きをAIに作らせる

材料は、2枚の設計書です。作らないと決めたものも、選んだ理由も、あそこに書いてあります。

```text
README.md の末尾に「## 設計のメモ」という見出しを作って、
@docs/comment.md と @docs/draft.md を読んで、
この2つの機能をなぜそう作ったのかを箇条書きにしてください。

書くのは、作らないと決めたもの・選ばなかった作り方・
知らずに変えると壊れる決めごと・設計書のありかの4つだけです。
何ができるかの説明は、README.md の「できること」に既にあるので書かないでください。
```

> 💡 このお願いのポイントは3つです。①書く場所と見出しを指定している ②書く中身を4つに絞っている ③書かないものを名指しし、既にどこに書いてあるかまで伝えている。③が無いと、返ってくるのは機能紹介です。AIから見れば、そちらのほうが自然なREADMEだからです。文言をそのまま覚える必要はありません。

> 💡 **出力例について**: AIの応答は毎回変わります。以下はあくまで一例です。文言が違っても、チェックリストの項目を満たしていれば問題ありません。

```markdown
## 設計のメモ

### 投稿へのコメント

- コメントの編集は作っていません。消して書き直せば足りるためです。
- 「消せるのは書いた本人だけ」の判定は、ポリシーに1か所だけ置いています。画面のボタンを消すだけでは、URL を直接開かれたときに止まらないためです。
- 設計書は `docs/comment.md` にあります。

### 投稿の下書き

- 状態の列の初期値は「公開済み」です。列を足したときに、もとからあった投稿が一覧から消えないようにするためです。
- 状態は「下書き」と「公開済み」の2つだけです。公開待ちや削除済みは作っていません。
- 設計書は `docs/draft.md` にあります。
```

### Step 2: 読んで直す

出てきた下書きは、そのまま置きません。見るのは2つだけです。理由が書かれているか。何ができるかの説明が紛れ込んでいないか。

### Step 3: 記録する

設計書の1行目に足した記録の1文も、ここで一緒にコミットします。今回はコードを変えていないので、ブランチを切らずに `main` へ直接記録します。

```text
README.md と docs をコミットして、main に push してください。
```

このコミットは、どちらの機能イシューにも属していません。だからメッセージにイシューの番号を入れていません。2件とも、もう閉じています。

書き終えたら、次の4つを確かめてください。

- [ ] `README.md` に「設計のメモ」があり、2つの機能の分が書かれている
- [ ] 書かれているのが「なぜそうしたか」で、何ができるかの説明が入っていない
- [ ] 知らずに変えると壊れる決めごとが、1つ以上書かれている
- [ ] `docs/comment.md` と `docs/draft.md` の1行目に、記録である旨の1文が入っている

## ✨ まとめ

- 手を止めたのは、計画を承認するところと、受け入れ条件と突き合わせるところの2箇所だけでした。要件を決めるところと判定するところに、AIの出番はありませんでした。
- 実装が終わると、いまどうなっているかを決めるのはコードとテストです。実物とずれたときに赤くなるのはテストで、設計書は黙ったままだからです。
- 2枚の設計書は、その機能を作ったときの記録として残します。更新しないので、1行目にその旨を書き添えます。
- 1機能を1ファイルにまとめておくと、ファイル名がそのまま範囲の目印になります。
- コードに残るのは「何をしているか」だけです。作らないと決めたもの、選ばなかった作り方、知らずに変えると壊れる決めごとは、READMEに書き残します。

Tutorial 14はここまでです。2つの機能を、イシューを立てるところからマージまで通しました。

このあいだ、毎回同じことを手でやっていました。アプリの前提を依頼のたびに説明し直すこと。承認を押すこと。テストを自分で回すこと。これを毎回の作業から取り出して、あらかじめ置いておく方法は、Tutorial 15で扱います。
