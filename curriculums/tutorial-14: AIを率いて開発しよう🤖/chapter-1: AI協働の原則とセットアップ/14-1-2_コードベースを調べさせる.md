# 14-1-2: コードベースを調べさせる

## 🎯 このセクションで学ぶこと

- 前提としたいことだけを渡して、手段はAIに任せた依頼が書けるようになる。
- 返ってきた説明・提案・質問を、それぞれの役割で受け取れるようになる。
- `@` でファイルを名指しできるようになる。

---

## 導入：いきなり書かせると、書き直しになる

このアプリは Tutorial 13 で設計の題材にしましたが、コードを隅から隅まで読んだわけではありません。ルートの定義もモデルも、配られたときのまま置かれています。

「コメントを書けるようにして」といきなり頼むと、AIはこのアプリの作りを推測しながら書き始めます。当たることもありますが、外れれば書き直しです。先に読ませて、あなたとAIが同じものを見ている状態を作ってから頼むほうが、結局は速くなります。

新しく入った人に仕事を頼むときと同じ順番です。まずコードを読んでもらい、分かったことを説明してもらってから、作業に入ってもらいます。説明を聞けば、その人がどこまで分かっているかも見えます。

---

## 調査の頼み方

Claude Codeは、起動したフォルダの中のファイルを自分で開いて読めます。こちらからコードを貼り付ける必要はありません。

頼み方のコツは、答えだけでなく、**どこを見てそう言えるのか**を一緒に出させることです。

```text
このプロジェクトで、ログインしていない人でも開ける画面がどれかを教えてください。
どのファイルの何行目を見てそう判断したかも書いてください。
```

> 💡 このお願いのポイントは、2行目です。場所が書いてあれば、そのファイルを自分で開いて、合っているかを確かめられます。場所が書かれていない答えは、正しそうに見えても確かめようがありません。

聞くことを1つに絞る必要はありません。まとめて聞いても、答えごとに根拠のファイルが書いてあれば、どれがどれの話なのかを追えます。追えなくなるのは根拠が書かれていないときで、数の問題ではありません。

---

## ファイルを名指しする

Claude Codeの入力欄で `@` を打つと、そのあとにファイルパスの候補が出ます。途中まで打つと候補が絞り込まれるので、目的のファイルを選べばパスが入ります（2026年8月時点）。

`@` で指したファイルは、AIが答える前に読みます。「app フォルダの中の Http の中の Controllers にある PostController.php」と文章で場所を説明する代わりに使うもの、と考えてください。

触る場所がもう決まっているときは、探させずに渡します。探させると、関係のないファイルまで開くので、答えが返るまでに時間がかかります。逆に、どこに何があるかをこちらも知らないときは、`@` を使わずに探させます。このあとの 🏃 がその形です。

---

## 返ってきた説明を確かめる

AIの説明は、もっともらしく読めます。裏取りには次の2つを使います。

1. **示されたファイルを自分で開く**。VS Codeでそのファイルを開き、書かれていた行が本当にあるかを見ます。
2. **答えを知っている問いを混ぜておく**。1問だけ自分が確実に知っていることを聞くと、返ってくる説明の正確さを測れます。

行番号は、しばしばずれます。ファイル名と中身が合っていれば、行番号のずれは気にしなくて構いません。ファイルを開いてもそんなコードが無かったのなら、その説明は捨てます。

---

## 🏃 まとめて1つ、大きく頼む

アプリのフォルダでClaude Codeを起動します。

```bash
# アプリのフォルダへ移動して起動する
cd ~/laravel-practice/post-app-practice
claude
```

### Step 1: 提案を出させる

投げるのは、次の1つだけです。

```text
本アプリケーションは教材学習用に運営から提供されたシンプルな練習用スターターキットをcloneしたもので、現状このアプリケーション自体に特に面白みがありません。
Claude Codeがどこまでできるかを体感するために、まずこのアプリケーションのブラッシュアップ案を提案いただきたいです！
なお、次のChapterで今の状態を使うので、ブランチを切って作業してください！
```

> 💡 このお願いのポイントは2つです。①前提とやりたいことだけを書いて、**何を足すべきかは書いていない**こと。手段まで指定すると、指定した範囲の中からしか返ってきません。②ブランチを切るのも頼んでいること。`git` の操作を自分でやる理由はありません。14-1-1で `gh` を入れたのも、これと同じ理由です。文言をそのまま覚える必要はありません。

> 💡 **出力例について**: AIの応答は毎回変わります。以下はあくまで一例です。文言が違っても、チェックリストの項目を満たしていれば問題ありません。

```text
あなた: （上の依頼を送る）
Claude Code: （routes・コントローラー・モデル・ポリシー・画面を順に読み、
              ブランチを切ってから、改良案を並べて説明してくる。
              決めてほしいことがあれば、そこで聞き返してくる）
```

### Step 2: 返ってきたものを3つに分けて受け取る

提案を出すには、先にコードを読む必要があります。そのため返ってくるものには、3種類が混ざります。役割が違うので、分けて受け取ります。

| 返ってきたもの | どう受け取るか |
|:--|:--|
| アプリの説明 | **裏を取ります。** 示されたファイルを1つか2つ開いて、書いてあるとおりかを見ます |
| 改良案 | **たたき台です。** 正解ではありません。作るかどうかは、こちらが決めます |
| AIからの質問 | **設計の穴の予告です。** Chapter 2で決めることになります |

裏取りには、答えを知っている箇所を使うのが早道です。「自分の投稿だけ編集できる」の判定がどこにあるかは、14-1-1で見ています。`app/Policies/PostPolicy.php` を指していれば、ほかの説明もある程度信用できます。指していなければ、その説明は捨てます。

### Step 3: 案を1つ選んで、まるごと作らせる

出てきた案から、作ってみたいものを1つ選びます。投げるのは、これだけです。

```text
（選んだ案）を作ってください。作り方はそちらで決めてください。
```

マイグレーションもモデルもコントローラーもルートも画面も、まとめて出てきます。**1回の指示でこれだけ出てくる**ということを、ここで一度見ておいてください。14-1-1に書いた「手で書いても間に合う量しか出さないなら、AIを使う意味はほとんどありません」は、この大きさの話です。

`http://localhost` を開いて、動くかどうかだけ見ます。動かなければ、そのまま「動きません」と伝えて直させて構いません。

### Step 4: 元の状態に戻して、コメント機能の下調べをする

Chapter 2は、配られたままの状態から始めます。戻すのも頼みます。

```text
main に戻してください。作ったブランチは残しておいてください。
```

そのうえで、Chapter 2の下調べを1つ投げます。

```text
このアプリに、投稿へコメントを書ける機能を足すとします。
どのファイルが増えて、どのファイルを直すことになりそうか、一覧にしてください。
```

これまでと性質が違います。Step 1の説明は、答えがこのアプリの中にあるので、開けば確かめられます。こちらに確かめられる答えはありません。これから自分が決めることの下調べなので、返ってきた一覧は正解ではありません。たたき台として受け取ってください。

投げ終えたら、次の5つを確かめてください。

- [ ] アプリの説明で示されたファイルを開いて、書いてあるとおりかを見た
- [ ] 「自分の投稿だけ編集できる」の判定が `PostPolicy` にある、と説明されていた
- [ ] 改良案とAIからの質問を、Chapter 2の材料として読んだ（正解として読んでいない）
- [ ] 案を1つ選んで作らせ、1回の指示で出てくる量を見た
- [ ] `git branch` で `main` に戻っていることと、作業したブランチが残っていることを確かめた

**アプリの説明に出てくるはずのもの**

説明の中身は毎回変わりますが、次の3つはどれも押さえてくるはずです。開いて突き合わせられるのも、この3つです。

1つ目は、ログインの要る画面と要らない画面の分かれ目です。

```php
// routes/web.php
// ...
Route::get('/', function () {
    return view('welcome');
});

// 認証が必要なルート
Route::middleware('auth')->group(function () {
    Route::get('/posts', [PostController::class, 'index'])->name('posts.index');
    Route::get('/posts/{post}/edit', [PostController::class, 'edit'])->name('posts.edit');
    Route::put('/posts/{post}', [PostController::class, 'update'])->name('posts.update');
    Route::delete('/posts/{post}', [PostController::class, 'destroy'])->name('posts.destroy');
});
```

このファイルの中で `Route::middleware('auth')->group()` の外にあるのは、`/` の1本だけです。ただし、ログインしていない人が開けるルートがこれだけとは限りません。ログイン・新規登録・パスワード再設定のルートはFortifyが登録していて、このファイルには書かれていないからです。AIが `/forgot-password` のようなルートを挙げてきても、間違いではありません。ただしこのアプリには再設定の画面が用意されていないので、開くとエラーになります。

2つ目は、編集できる人を決めている場所です。

```php
// app/Policies/PostPolicy.php
public function update(User $user, Post $post): bool
{
    return $user->id === $post->user_id;
}
```

いま操作している人のIDと、投稿に記録されている投稿者のIDが同じかどうかを見ています。

3つ目は、投稿とユーザーのつながりです。3か所で表されています。`app/Models/Post.php` の `user()`（`belongsTo`）、`app/Models/User.php` の `posts()`（`hasMany`）、そして `posts` テーブルの `user_id` カラムです。1人のユーザーが複数の投稿を持ち、1件の投稿は1人のユーザーに属します。

**改良案について**

ここに正解はありません。投稿を書く画面が無いこと、投稿1件だけを開く画面が無いこと、検索や並べ替えが無いこと、パスワード再設定の画面が用意されていないことあたりは、コードを読めば見えるので挙がりやすいはずです。挙がった案の大きさがばらばらでも構いません。**どれを作るかを決めるのは、AIではなくこちらです。**

**コメント機能で増えるもの**

返ってきた一覧に、コメントを保存するテーブル、それを扱うモデル、コメントを受け取るルートと処理、コメントを表示する画面あたりが並んでいれば、下調べとしては十分です。

</details>

AIから質問が返ってきた場合も、それは収穫です。13-1-1「設計とは何か」で、答えが設計書のどこにも無い質問が来たらそこが設計の穴だ、という見方を置きました。コードを読ませたときの質問にも、同じ見方が効きます。AIが「この場合はどうしますか」と聞いてきたら、それはまだ決まっていないことです。Chapter 2で決める項目として書き留めておいてください。

## ✨ まとめ

- 作業を頼む前にコードを読ませて説明させると、推測で書き始められずに済みます。
- 調査を頼むときは、答えと一緒に「どのファイルの何行目を見たか」を出させます。場所が書かれていない答えは確かめようがありません。
- 聞くことを1つに絞る必要はありません。根拠が書かれていれば、まとめて聞いても追えます。
- 答えを知っている問いを混ぜておくと、返ってくる説明の正確さを測れます。
- 触る場所が決まっているときは `@` で名指しし、決まっていないときは探させます。
- 1回の指示で、テーブルから画面までまとめて出てきます。小さく刻んで頼む理由はありません。
- ブランチの切り替えも頼みます。`git` の操作を自分の手でやる理由はありません。
