# 14-1-3: 最初の仕事は質問 - コードベースを調査させる

## 🎯 このセクションで学ぶこと

- いきなり書かせず、まず質問から入る理由を説明できるようになる。
- コードの調査を頼むときに、依頼へ何を書けばよいかが分かるようになる。
- 返ってきた説明が合っているかを、自分で確かめられるようになる。

---

## 導入：読ませてから、書かせる

13-8-2「総合演習 - 仕様から設計書一式を作る」では、できあがった設計書をAIに読ませて、質問と食い違いを出させました。今度は逆に、まだ何も設計していないアプリを読ませて、説明させます。相手は14-1-2で手元に戻した、投稿管理のアプリです。

Claude Codeは、起動したフォルダの中のファイルを自分で開いて読めます。こちらからコードを貼り付ける必要はありません。ですから、このアプリに対して最初にやることは、コードを書かせることではなく、いまそこに何があるのかを教えてもらうことです。14-1-2で書き換えさせたのは `README.md` の1行だけで、アプリの中身にはまだ触れていません。

---

## なぜ、いきなり書かせないのか

理由は2つあります。

**あなた自身が、そのアプリの全部を見ていないから**

このアプリは自分で作ったものですが、隅から隅まで書いたわけではありません。10-3-5「認可機能 - ハンズオン演習」で自分の手を入れたのは、`PostPolicy` の作成、コントローラーへの `$this->authorize()` の追加、Bladeへの `@can` の追加の3か所です。それ以外、たとえばルートの定義（`routes/web.php`）やモデル（`app/Models/` の中身）は、スターターキットに入っていたものをそのまま使いました。10-3-5の本文にも載っていません。中身を知らないところへ、いきなり手を入れさせるのは危険です。

**AIも、最初は何も知らないから**

「コメントを書けるようにして」といきなり頼むと、AIはこのアプリの作りを推測しながら書き始めます。当たることもありますが、外れれば書き直しです。先に読ませて、あなたとAIが同じものを見ている状態を作ってから頼むほうが、結局は速くなります。

新しく入った人に仕事を頼むときと同じ順番です。まずコードを読んでもらい、分かったことを説明してもらってから、作業に入ってもらいます。説明を聞けば、その人がどこまで分かっているかも見えます。

---

## 調査の頼み方

頼み方のコツは、答えだけでなく、**どこを見てそう言えるのか**を一緒に出させることです。

```text
このプロジェクトで、ログインしていない人でも開ける画面がどれかを教えてください。
どのファイルの何行目を見てそう判断したかも書いてください。
```

> 💡 このお願いのポイントは、2行目です。場所が書いてあれば、そのファイルを自分で開いて、合っているかを確かめられます。場所が書かれていない答えは、正しそうに見えても確かめようがありません。文言をそのまま覚える必要はありません。

もう1つ、1回の依頼で聞くことは1つに絞ります。5つまとめて聞くと、答えも5つ分まとめて返ってきて、どの答えがどの根拠に対応しているのかを追えなくなります。1つ聞いて、確かめて、次を聞く。この順で進めます。

---

## 🏃 4つの問いを投げてみる

> 🔥 ここからは、AIに実装を任せて構いません。ただし「任せる」と「丸投げ」は違います。何を作るかは設計書で自分が決め、出てきたものはテスト・動作確認・コードレビューで自分が検証します。品質の責任は、AIではなくあなたが握ります。

アプリのフォルダでClaude Codeを起動して、4つの問いを1つずつ投げます。1問ごとに終える必要はありません。1つのセッションのまま、4問を続けて投げてください。

```bash
# アプリのフォルダへ移動して起動する
cd ~/laravel-practice/14_hands-on/authorization-app-ai
claude
```

### Step 1: ログインしていない人が開ける画面を聞く

上の「調査の頼み方」に載せたお願いを、そのまま投げてみてください。

> 💡 **出力例について**: AIの応答は毎回変わります。以下はあくまで一例です。文言が違っても、チェックリストの項目を満たしていれば問題ありません。

```text
あなた: （上のお願いをそのまま送る）
Claude Code: （routes/web.php を読み、ログインが要るルートと要らないルートを、
              ファイル名と行番号を添えて説明してくる）
```

### Step 2: 「自分の投稿だけ編集できる」がどこで決まっているかを聞く

```text
このアプリでは「自分の投稿だけ編集できる」という決まりがあります。
それはどのファイルのどの行で決まっているのか、その行のコードも一緒に見せてください。
```

この問いだけは、答えを完全に知っています。10-3-5で自分の手で書いたコードだからです。**答えを知っている問いを混ぜておく**と、返ってくる説明の正確さを測れます。

### Step 3: 投稿とユーザーのつながりを聞く

```text
このアプリで、投稿とユーザーがどうつながっているのかを教えてください。
モデルとテーブルの両方から説明してください。
```

「モデルとテーブルの両方から」と書いているのは、片方だけの説明だと確かめにくいからです。9-5-1「1対多のリレーションシップ」で学んだリレーションの定義と、8-1-4「主キーと外部キー」で学んだ外部キーは、同じつながりを別の場所から表したものです。両方を出させれば、突き合わせて確かめられます。

### Step 4: コメント機能を足すなら何が増えるかを聞く

```text
このアプリに、投稿へコメントを書ける機能を足すとします。
どのファイルが増えて、どのファイルを直すことになりそうか、一覧にしてください。
```

この4つ目だけ、性質が違います。Step 1からStep 3は、答えがこのアプリの中にあるので、開けば確かめられます。Step 4に確かめられる答えはありません。これから自分が決めることの下調べです。返ってきた一覧は正解ではなく、たたき台として受け取ってください。Chapter 2で設計を始めるときの材料になります。

### Step 5: 分かったことをメモに残す

4つの問いの答えを、短くメモしておきます。

- 合っていたこと（自分でファイルを開いて確かめたもの）
- 違っていたこと、または書かれていなかったこと

このメモは自分用です。ファイルとして残す必要はありませんし、コミットもしません。目的は、AIの説明を自分で検算する習慣をつけることです。

投げ終えたら、次の3つを確かめてください。

- [ ] Step 1からStep 3の答えについて、示されたファイルを自分で開いて中身を見た
- [ ] Step 2の答えが、10-3-5で自分が書いた `PostPolicy` と合っているかを判定した
- [ ] Step 4で返ってきた一覧を、正解ではなくたたき台としてメモに書き留めた

## 返ってきた説明を確かめる

AIの説明は、もっともらしく読めます。1-1-6「AIの活用法」で学んだとおり、裏付けを取ってから信じます。ここでの裏取りは次のとおりです。

1. **示されたファイルを自分で開く**。VS Codeでそのファイルを開き、書かれていた行が本当にあるかを見ます。
2. **自分が書いたコードの記憶と照らす**。Step 2の答えは、10-3-5で自分の手で書いたものです。

行番号は、しばしばずれます。ファイル名と中身が合っていれば、行番号のずれは気にしなくて構いません。逆に、ファイルを開いてもそんなコードが無かったのなら、その説明は捨てます。

<details>
<summary>📖 4つの問いを投げ終えたら開く（答え合わせ）</summary>

**Step 1: ログインしていない人が開ける画面**

`routes/web.php` の該当部分は、次のとおりです。

```php
// routes/web.php
// ...
Route::get('/', function () {
    return view('welcome');
});

// 認証が必要なルート
Route::middleware('auth')->group(function () {
    Route::get('/posts', [PostController::class, 'index'])->name('posts.index');
    Route::get('/posts/{post}/edit', [PostController::class, 'edit'])->name('posts.edit');
    Route::put('/posts/{post}', [PostController::class, 'update'])->name('posts.update');
    Route::delete('/posts/{post}', [PostController::class, 'destroy'])->name('posts.destroy');
});
```

このファイルの中で `Route::middleware('auth')->group()` の外にあるのは、`/` の1本だけです。ただし、ログインしていない人が開けるルートがこれだけとは限りません。ログイン・新規登録・パスワード再設定のルートは、10-3-5のスターターキットに入っていたFortifyが登録していて、このファイルには書かれていないからです。

ですから答えは、トップページと、Fortifyが登録しているこれらのルートです。AIが `/forgot-password` のようなパスワード再設定のルートを挙げてきても、間違いではありません。ただしこのアプリには再設定の画面が用意されていないので、開くとエラーになります。

**Step 2: 編集できる人を決めている場所**

`app/Policies/PostPolicy.php` の `update` メソッドです。

```php
// app/Policies/PostPolicy.php
public function update(User $user, Post $post): bool
{
    return $user->id === $post->user_id;
}
```

いま操作している人のIDと、投稿に記録されている投稿者のIDが同じかどうかを見ています。10-3-5で自分の手で書いた行です。

**Step 3: 投稿とユーザーのつながり**

3か所で表されています。`app/Models/Post.php` の `user()`（`belongsTo`）、`app/Models/User.php` の `posts()`（`hasMany`）、そして `posts` テーブルの `user_id` カラムです。1人のユーザーが複数の投稿を持ち、1件の投稿は1人のユーザーに属します。

**Step 4: コメント機能を足すと増えるもの**

ここに正解はありません。返ってきた一覧に、コメントを保存するテーブル、それを扱うモデル、コメントを受け取るルートと処理、コメントを表示する画面あたりが並んでいれば、下調べとしては十分です。

</details>

質問が返ってきた場合も、それは収穫です。13-1-1「設計とは何か」で、答えが設計書のどこにも無い質問が来たらそこが設計の穴だ、という見方を置きました。コードを読ませたときの質問にも、同じ見方が効きます。AIが「この場合はどうしますか」と聞いてきたら、それはまだ決まっていないことです。Chapter 2で決める項目として、メモに書き足しておいてください。

## ✨ まとめ

- AIに作業を頼む前に、まずコードを読ませて説明させます。あなたも全部を見ていませんし、AIも最初は何も知りません。
- 調査を頼むときは、答えと一緒に「どのファイルの何行目を見たか」を出させます。場所が書かれていない答えは確かめようがありません。
- 1回の依頼で聞くことは1つに絞ります。聞いて、確かめて、次を聞く順で進めます。
- 答えを知っている問いを混ぜておくと、返ってくる説明の正確さを測れます。このアプリでは、10-3-5で自分の手で書いた `PostPolicy` がそれにあたります。
- 確かめ方は、示されたファイルを自分で開くことと、自分が書いたコードの記憶と照らすことの2つです。

次のセクション（14-1-4）では、渡してよいものといけないものの線を引きます。この先はアプリのコードそのものを書かせ、コマンドも実行させます。その前に決めておくことがあります。
