# 14-2-1: 前提を渡し、作り方は任せる

## 🎯 このセクションで学ぶこと

- 依頼に何を書き、何を書かないのかを決められるようになる。
- 変えないものと、手本にしてほしいものを、コードの場所を指して伝えられるようになる。
- 画面の見た目を、画像で渡せるようになる。
- 返ってきた案に、直したいところを1つずつ伝えられるようになる。

---

## 導入：作り方まで書くと、その作り方までしか出てこない

コメント機能を頼むとき、こう書くこともできます。「`app/Models/Comment.php` を作り、`post_id`・`user_id`・`body` を持たせて、`PostController` に `show` を足して、`resources/views/posts/show.blade.php` を新しく作って……」。

この書き方には天井があります。出てくるのは、あなたが思いついた作り方そのものです。もっと短い道や、Laravelに用意されている書き方があっても、指定した以上そちらは出てきません。

そのうえ、この文は最後まで書ききれません。ファイル名まで指定できるのは、その作り方を一度やったことのあるときだけです。初めて作る機能では途中で手が止まり、書けなかったところは結局AIが埋めます。

渡すものを入れ替えます。なぜ要るのか、何ができればよいのか、どこは動かせないのか。ここはあなたにしか書けません。作り方のほうは、AIのほうがたくさん知っています。ただし、このアプリで既に決まっている作り方だけは、あなたのほうが知っています。そこは渡します。

---

## 依頼に書くこと

書き方に決まった型はありません。実物を1本見てください。同じコメント機能を、作り方を書かず、前提のほうを渡して頼むとこうなります。**これは読むためのもので、いま送る必要はありません。** 送るのは、このセクションの 🏃 です。

```text
このアプリに、投稿へのコメント機能を足します。
投稿の一覧からは、誰がどんな投稿をしたかしか分かりません。
読んだ人が、投稿に一言返せるようにしたいです。

いまある投稿の一覧・編集・更新・削除の動きは、変えないでください。
app/Policies/PostPolicy.php の「自分の投稿だけ編集・削除できる」という
判定も、そのままにしてください。
投稿一覧に出ている投稿者名とカテゴリ名の表示も、そのまま残してください。

コメントを消せる人の判定は、この PostPolicy と同じやり方に揃えてください。

次のことができれば完成です。
- ログインした状態で投稿を1件開くと、その投稿とコメントの一覧が表示される
- 本文を入れてコメントを送ると、コメントの一覧に増える
- 本文を空のままコメントを送ると、エラーが表示され、コメントは増えない
- 自分が書いたコメントは自分で消せて、他人のコメントは消せない

どう作るかはそちらで決めて、コードを書く前に提案してください。
```

効いているところを指します。

出てくるファイル名は1つだけです。指しているのは**触ってほしくないもの**と**手本にしてほしいもの**で、「これを作れ」とは書いていません。テーブル名もカラム名もクラス名も、1つも出てきません。書かなかったのは、これから作るものの名前です。

手本の1行は、作り方の指定です。**作り方を全部空けるわけではありません。** 自分が知っている決まりごとは書いて、知らないところを空けます。コメントを消せるのは誰かという判定には `PostPolicy` という前例がこのアプリにあるので、そこは渡します。テーブルの名前には前例が無いので、空けます。

完成の判定は、**操作の言葉**で書いています。「〜すると、〜になる」の形なので、誰が試しても合否が一致します。13-2-2で書いた受け入れ条件と同じ形です。

最後の1行は、2つのことをしています。1つは、**作り方の判断を渡す**と口に出していることです。黙って空けるのと、渡すと書くのとでは、返ってくるものが変わります。書かないだけだと、AIは決めてよいのか確認してくることがあります。もう1つは、**コードを書く前に止めている**ことです。止めておけば、作り方が気に入らないときに、文章のやり取りだけで直せます。

線の引きどころは、13-1-1で置いたものと同じです。設計が抽象で、実装が具体でした。依頼文でも同じところで切れています。**あなたが抽象を持ち、AIが具体を埋めます。** 具体のうち、いまのアプリで既に決まっているものだけが例外で、それが手本の1行です。空けたところは、あとから塞げます。返ってきた作り方を読んで、気に入らないところが1つあれば、そこだけ指定し直せば済みます。

> ⚠️ **注意**: 空けてよいのは作り方だけです。「コメントを消せるのは誰か」を決めないまま渡すと、AIがどちらかに決めて、決めた側で最後まで作ります。とはいえ、決めるべきことを先に全部並べるのは無理です。自分が決めたことを書く、で構いません。書き落としの見つけ方は14-2-4で扱います。

---

## 変えないものは、場所で伝える

「いまの機能を壊さないでください」とだけ書いても、どこを壊してはいけないのかは決まりません。守りたいものが分かっているなら、名前で書きます。

```text
いまある投稿の一覧・編集・更新・削除の動きは、変えないでください。
app/Policies/PostPolicy.php の「自分の投稿だけ編集・削除できる」という判定も、そのままにしてください。
投稿一覧に出ている投稿者名とカテゴリ名の表示も、そのまま残してください。
```

ファイルの名前を書いておくと、AIは作業に入る前にそこを読みます。14-1-2で使った `@` と同じ働きで、文章の中にパスを書くだけでも伝わります。

ここに書いた3つは、どれもいまのアプリを開けば確かめられます。`routes/web.php` には投稿まわりのルートが4本、`app/Policies/PostPolicy.php` には `update` と `delete` の2つ、投稿一覧の画面には投稿者名とカテゴリ名が出ています。**守りたいものは、コードを見て書きます。** 記憶で書くと、無いものを守らせることになります。

## 画像を渡す

画面の見た目は、文章で説明するより見せるほうが速く伝わります。Claude Codeには、画像をそのまま渡せます。

渡し方は、クリップボードからの貼り付けです。画像をコピーした状態で、Claude Codeの入力欄で貼り付けます。Macは `Cmd+V`、Windows（WSL）は `Ctrl+V` です。WSLでは、ターミナル側が `Ctrl+V` を先に受け取ってしまうことがあります。貼り付いた様子が無いときは `Alt+V` を試してください（2026年8月時点）。Windows側でコピーした画像も、WSLの中で動いているClaude Codeにそのまま貼り付けられます。

うまく渡せると、入力欄に `[Image #1]` のような印が入ります。これが、画像を受け取った合図です。印が出たら、続けて依頼の文章を打ちます。何度試しても印が出ないときは、その画像をアプリのフォルダに保存してから `@` で指してください。

画面を撮る操作そのものは、Macでは `Control+Shift+Command+4`、Windowsでは `Windows+Shift+S` です（2026年8月時点）。範囲を選ぶと、その部分がクリップボードに入ります。Macで `Control` を付けずに `Shift+Command+4` を押すと、クリップボードには入らず、デスクトップにファイルとして保存されます。

> ⚠️ **注意**: 14-1-3で引いた線は、画像にも同じように当てはまります。画面を撮るときは、本物のメールアドレスやパスワードが写り込んでいないかを見てください。この演習で画面に出るのは、練習用に用意された `usera@example.com` のアカウントだけです。

## 🏃 前提だけ渡して、作り方を出させる

これから作るのは、投稿へのコメント機能です。Chapter 4まで、この機能を通しで扱います。

投げる依頼は、どれもファイルを書き換えません。承認を求められて止まることもありません。

```bash
# アプリのフォルダへ移動して起動する
cd ~/laravel-practice/post-app-practice
claude
```

### Step 1: 依頼文を送る

送るのは、次の1本で全部です。上に載せたものと同じなので、そのまま貼り付けて送ってください。

```text
このアプリに、投稿へのコメント機能を足します。
投稿の一覧からは、誰がどんな投稿をしたかしか分かりません。
読んだ人が、投稿に一言返せるようにしたいです。

いまある投稿の一覧・編集・更新・削除の動きは、変えないでください。
app/Policies/PostPolicy.php の「自分の投稿だけ編集・削除できる」という
判定も、そのままにしてください。
投稿一覧に出ている投稿者名とカテゴリ名の表示も、そのまま残してください。

コメントを消せる人の判定は、この PostPolicy と同じやり方に揃えてください。

次のことができれば完成です。
- ログインした状態で投稿を1件開くと、その投稿とコメントの一覧が表示される
- 本文を入れてコメントを送ると、コメントの一覧に増える
- 本文を空のままコメントを送ると、エラーが表示され、コメントは増えない
- 自分が書いたコメントは自分で消せて、他人のコメントは消せない

どう作るかはそちらで決めて、コードを書く前に提案してください。
```

受け入れ条件はこの4行です。14-2-4で設計書に写し、Chapter 3で実装させ、Chapter 4で1行ずつ突き合わせる相手になります。

> 💡 **出力例について**: AIの応答は毎回変わります。以下はあくまで一例です。文言が違っても、チェックリストの項目を満たしていれば問題ありません。

```text
あなた: （上の依頼を送る）
Claude Code: （routes/web.php や app/Models/Post.php を読んだうえで、
              増えるテーブル・増える画面・追加するルートを説明してくる）
```

### Step 2: 返ってきた案を、前提と突き合わせる

読むところは決まっています。依頼文に書いた**変えないものと手本**に、返答が触れているかです。

いまある4本のルートを残したまま足す形になっているか。投稿者名とカテゴリ名の表示に手が入っていないか。コメントの削除が `PostPolicy` と同じやり方になっているか。触れていれば、前提が届いています。素通りされていたら、その1つを名指しでもう一度伝えてください。

テーブル名やカラム名が自分の想像と違っていても、直す必要はありません。そこは渡していない部分です。

### Step 3: 画面を渡して、足りない前提を補う

ここで、画面を1枚渡します。アプリが止まっている場合は、Docker Desktop（またはDocker Engine）を起動し、Claude Codeとは別のターミナルで次を実行してください。

```bash
# アプリのフォルダで実行する（Windowsの方はWSL(Ubuntu)のターミナルで）
cd ~/laravel-practice/post-app-practice
./vendor/bin/sail up -d
```

ブラウザで `http://localhost` を開き、`usera@example.com` / `password` でログインして、投稿一覧（`http://localhost/posts`）を表示します。その画面を撮って、Claude Codeの入力欄へ貼り付け、続けて次を打ちます。

```text
いま貼ったのが、このアプリの投稿一覧です。
この画面を見たうえで、コメントの一覧と入力欄をどこに置くことになるかを説明してください。
コードはまだ書かないでください。
```

> 💡 この依頼のポイントは、画面の形を文章で書き起こさずに済ませていることです。何が並んでいるかを言葉で説明すると10行かかりますが、画像なら1枚です。

返ってきた説明に、画面に実際に並んでいるもの（投稿者名、カテゴリ名、編集と削除のボタン）が出てくれば、画像が読まれています。

### Step 4: 気になったところを詰める

返ってきた案を、そのまま受け取る必要はありません。読んで引っかかったところを、そのまま文章で伝えます。

```text
コメントを消すときに確認画面を挟む形になっていますね。
そこは挟まずに、押したらその場で消える形にしてください。
```

一度に何個も伝えると、どれが直ってどれが落ちたのかを追えなくなります。**1つ伝えて、返ってきたものを読んで、また1つ伝えます。** この往復はコードが1行も書かれていない状態で進むので、何度でもやり直せます。文章のやり取りだけで済むのは、Step 1の最後の1行でコードを止めているからです。

引っかかるところが無ければ、この往復は要りません。案がそのまま通ることもあります。

**ここでは実装させません。** 理由は2つです。1つは、いま出ているのが会話の中の案で、ファイルとして残っていないことです。セッションを終えれば消えます。もう1つは、この案がまだ、受け入れ条件と1行ずつ突き合わせられる形になっていないことです。

残る形にするのが14-2-3と14-2-4で、そこで作った設計書をもとに実装させるのがChapter 3です。この節でやったのは、その前段にあたる、**渡し方の練習**です。

投げ終えたら、次の4つを確かめてください。

- [ ] 返ってきた案が、依頼文に書いた「変えないもの」に触れている
- [ ] 画像を渡した依頼への返答が、画面に並んでいるものに触れている
- [ ] 気になったところを伝えて、案が書き直された（無ければ、無かったと言えれば構いません）
- [ ] ここまででファイルが1つも書き換わっていない（承認を1度も求められていない）

## ✨ まとめ

- 依頼文に決まった型はありません。書くのは、なぜ要るのか、触ってほしくないのはどこか、どうなったら完成か。どれも抽象のほうの話です。
- これから作るものの名前（テーブル名・カラム名・クラス名）は空けておきます。空けた分は、AIが知っている定番の形で埋まります。
- 作り方を全部空けるわけではありません。いまのアプリに前例があるものは、そのファイルを手本として名指しで渡します。
- 決まっていないことを空けるのは別の話です。ただし、決めるべきことを先に全部並べるのは無理なので、自分が決めたことを書けば十分です。書き落としは14-2-4で拾います。
- 守りたいものは、ファイル名や画面の項目名で書きます。書くときは、記憶ではなくコードを見て書きます。
- 画像はクリップボードから貼り付けて渡します。入力欄に `[Image #1]` のような印が入れば渡せています。
- 返ってきた案は、そのまま受け取らなくて構いません。引っかかったところを1つずつ伝えて直させます。コードを書かせる前なので、文章のやり取りだけで済みます。
- 実装はここではしません。案を残る形にするのが14-2-3と14-2-4、それをもとに実装させるのがChapter 3です。
