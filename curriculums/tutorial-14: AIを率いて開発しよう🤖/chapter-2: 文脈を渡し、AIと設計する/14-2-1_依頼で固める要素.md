# 14-2-1: 依頼で固める要素

## 🎯 このセクションで学ぶこと

- 目的・制約・スコープ外（変えないもの）・参照・受け入れ条件・検証手段で依頼を組み立て、作り方は渡さずに書けるようになる。
- 変えないものを、コードの場所を指して伝えられるようになる。
- 返ってきた案を渡した前提と突き合わせ、引っかかったところを1つずつ直せるようになる。

---

## 導入

14-1-4では、使い捨てのフォルダでアプリを丸ごと1本作らせました。あれだけの量が出てきても、受け取ってよいのかどうかは判定しようがありませんでした。何が欲しいかを先に言えていなかったからで、この章ではそれをAIに渡せる形にしていきます。14-1-1で見た開発フロー（Issue化 → 計画 → 実装とテスト → レビュー → UAT → PR）でいうと、いまいるのは先頭の、意図と受け入れ条件を固めるところです。

---

## 作り方を書かない理由

リプライ機能を頼むとき、こう書くこともできます。「`app/Models/Reply.php` を作って、`post_id`・`user_id`・`body` を持たせて、コントローラーに `show` を足して、ポストの詳細画面を新しく作って……」。

この書き方には天井があります。出てくるのは、あなたが思いついた作り方そのものです。もっと短い道や、あなたの案よりさらに良い作り方をAIが知っていても、指定した以上そちらは出てきません。そもそも、初めて作る機能ではこの文を最後まで書ききれません。ファイル名まで指定できるのは同じものを一度作ったことがあるときだけで、書けなかったところは結局AIが埋めます。

だから、渡すものを入れ替えます。なぜ要るのか、何ができれば完成か、どこは動かせないのか。ここはあなたにしか書けません。作り方は、AIのほうがたくさん知っています。

---

## 依頼で固める要素

依頼で固めるのは、作り方という手段ではなく、意図のほうです。意図を組み立てる要素は、次のとおりです。

| 要素 | 固める内容 |
|:-----|:-----------|
| 目的 | なぜ要るのか。誰が何に困っていて、どうなってほしいのか |
| 制約 | 作り方に課す条件。既存のやり方に揃える、など |
| スコープ外（変えないもの） | 今回は手を入れない範囲 |
| 参照 | 読んでほしい場所。手本になるファイルや画面 |
| 受け入れ条件 | どうなったら完成か。「〜すると、〜になる」 |
| 検証手段 | 完成をどうやって確かめるか |

固めるのは内容であって、書式ではありません。毎回この見出しを全部立てる必要はなく、文脈に既にあるもの（直前に渡したファイル、前のやり取りで決めたこと）は繰り返しません。

実物を1本見てください。Tsubuにリプライ機能を足す依頼です。これは読むためのもので、送るのはこのセクションの 🏃 です。

```text
Tsubuにリプライ機能を足したい。
ポストを読んだ人が、その場で一言返せるようにする。今は読むだけで、返す手段がない。

- タイムラインの今の動き（一覧・編集・削除）は変えない
- リプライを消せる人の判定は app/Policies/PostPolicy.php のやり方に揃える

完成の条件（ブラウザの操作で確かめる）:
- ポストを1件開くと、そのポストとリプライの一覧が見える
- 本文を入れてリプライを送ると、一覧に増える
- 本文が空のままだと、エラーが表示されてリプライは増えない
- 自分のリプライは消せて、他人のリプライは消せない

作り方はそちらで決めて、コードを書く前に案を見せて。
```

表の要素は、この中に全部入っています。目的は最初の2行、制約と参照は真ん中の2行、受け入れ条件と検証手段は「完成の条件（ブラウザの操作で確かめる）」のまとまりです。

効いているのは、むしろ書いていないもののほうです。これから作るものの名前が、1つも出てきません。テーブル名もクラス名もURLも書いてありません。空けたところは、AIが知っている定番の形で埋まります。唯一出てくるファイル名の `app/Policies/PostPolicy.php` は「これを作れ」という指定ではありません。このアプリで既に決まっているやり方の場所で、あの1行は制約（このやり方に揃える）と参照（このファイルを読む）を兼ねています。要素と行が1対1に対応する必要はありません。

最後の1行は、コードを書く前で案を止めています。止めてあるから、気に入らない作り方が返ってきても、文章の往復だけで直せます。

> ⚠️ **注意**: 空けてよいのは作り方です。「リプライを消せるのは誰か」のような決めごとを、もし書かずに渡すと、AIがどちらかに決めて、決めた側で最後まで進みます。かといって、決めるべきことを送る前に全部洗い出す必要はありません。まだ固まっていないことの整理は、14-2-2でAIと一緒にやります。

### 変えないものの指し方

「今の動きは変えない」とだけ書いても、どこを壊してはいけないのかは決まりません。守りたいものが分かっているなら、名前と場所で書きます。この依頼では、タイムラインの「今の動き」を一覧・編集・削除という機能名まで割り、削除の判定は `app/Policies/PostPolicy.php` とパスで指しました。依頼文の中にパスを書くだけで、AIは作業に入る前にそこを読みに行きます。

どちらも、いまのTsubuを開けば確かめられます。`routes/web.php` にはポストのルートが一覧・編集・更新・削除の4本（依頼文で「編集」と呼んだ動きは、画面を出すルートと更新のルートの2本です）、`app/Policies/PostPolicy.php` には「自分のポストだけ」を判定する `update` と `delete` の2つがあります。**守りたいものは、コードを見て書きます。** 記憶で書くと、無いものを守らせることになります。いまは読むだけで構いません。🏃で使う分は、上の依頼文にもう書いてあります。

### 受け入れ条件と検証手段

完成の条件の4行は、どれも操作の言葉です。ポストを開く、本文を入れて送る、という操作をしたら何がどうなるか、で書いてあります。13-2-2で書いた受け入れ条件（「〜すると、〜になる」）と同じ形なので、誰が試しても合否が一致します。

この4行は、依頼の中でいちばん長く使われます。Chapter 3で実装させた結果を受け取るかどうかも、Chapter 4の検証も、この4行との突き合わせで決まります。検証手段は、その突き合わせをどうやるかです。この依頼では「ブラウザの操作で確かめる」の一言ですが、実装まで頼む段になると、テストを書いて回すところまで含めます（Chapter 4）。

## 🏃 前提だけ渡して、案を出させる

ここから作り始めるのは、Tsubuのリプライ機能です。Chapter 4の終わりまで、この機能を通しで扱います。この演習で送る依頼はコードを書く前で止めてあるので、ファイルは書き換わりません。

ターミナルでTsubuのフォルダ（14-1-3でCLAUDE.mdを作ったフォルダ）へ移動して、Claude Codeを起動します。

```bash
# Tsubuのフォルダで実行する
claude
```

### Step 1: 依頼文を送る

送るのは次の1本で全部です。上で読んだものと同じなので、そのまま貼り付けて送ってください。

```text
Tsubuにリプライ機能を足したい。
ポストを読んだ人が、その場で一言返せるようにする。今は読むだけで、返す手段がない。

- タイムラインの今の動き（一覧・編集・削除）は変えない
- リプライを消せる人の判定は app/Policies/PostPolicy.php のやり方に揃える

完成の条件（ブラウザの操作で確かめる）:
- ポストを1件開くと、そのポストとリプライの一覧が見える
- 本文を入れてリプライを送ると、一覧に増える
- 本文が空のままだと、エラーが表示されてリプライは増えない
- 自分のリプライは消せて、他人のリプライは消せない

作り方はそちらで決めて、コードを書く前に案を見せて。
```

> 💡 **出力例について**: AIの応答は毎回変わります。以下はあくまで一例です。文言が違っても、チェックリストの項目を満たしていれば問題ありません。

```text
あなた: （上の依頼を送る）
Claude Code: （routes/web.php や app/Policies/PostPolicy.php を読んだうえで、
              増えるテーブル・画面・ルートと、リプライ削除の判定のやり方を
              説明してくる）
```

途中で実装まで進み始めたときは、`Esc` で止めて「案だけ見せて。まだ実装しないで」と伝えてください。止めるのが遅れてファイルが書き換わってしまっても、心配は要りません。まだコミットしていない変更なので、`git restore .`（4-3-5）で元に戻せます。

### Step 2: 返ってきた案を、前提と突き合わせる

読むところは決まっています。依頼に書いた変えないものと制約に、案が触れているかです。いまの4本のルートを残したまま足す形になっているか。リプライを消せる人の判定が、`PostPolicy` と同じ「自分のものだけ」になっているか。触れていれば、前提が届いています。触れていないのは不合格ではありません。書いていないだけか、前提が壊れているのかが分からないので、「いまの4本のルートは変えない前提で合ってる？」と聞いて確かめれば済みます。

テーブル名やカラム名が自分の想像と違っても、直す必要はありません。そこは渡していない部分です。

### Step 3: 引っかかったところを1つずつ詰める

案を読んで引っかかったところを、そのまま文章で伝えます。たとえばこうです。

```text
リプライを消すとき確認画面を挟む案になってるけど、
そこは挟まずに、押したらその場で消える形にして。
```

一度に何個も伝えると、どれが直ってどれが落ちたのかを追えなくなります。1つ伝えて、返ってきたものを読んで、また1つ伝えます。引っかかるところが無ければ、この往復は要りません。案がそのまま通ることもあります。

ここでは実装までは進めません。いま出ている案は、どのファイルにも書かれていません。この節の目的は案そのものではなく渡し方の練習なので、案が残らなくても構いません。Issueと設計書という残る形に起こすのは、14-3-3でやります。

閉じる前に、次を確かめてください。確かめ終えたら `/exit` で閉じます。

- [ ] 返ってきた案が、依頼に書いた「変えないもの」に触れている
- [ ] リプライを消せる人の判定が、`PostPolicy` に揃える前提で説明されている
- [ ] 引っかかったところを1つ伝えて、案が書き直された（引っかかりが無ければ、そのままで構いません）
- [ ] ファイルは1つも書き換わっていない（ファイル編集時に出る差分の表示が、応答の中に無い）

---

## ✨ まとめ

- 依頼で固めるのは、目的・制約・スコープ外（変えないもの）・参照・受け入れ条件・検証手段。作り方と、これから作るものの名前は空けておく。
- 固めるのは内容で、書式は毎回同じでなくてよい。文脈に既にあるものは繰り返さない。
- 変えないものは、コードを確かめて、機能名とパスで指す。
- 受け入れ条件は「〜すると、〜になる」の操作の言葉で書く。成果物を受け取るかどうかは、この行との突き合わせで決める。
- 返ってきた案の直しは、1つ伝えて、読んで、また1つ。コードを書かせる前なら、文章の往復だけで済む。
