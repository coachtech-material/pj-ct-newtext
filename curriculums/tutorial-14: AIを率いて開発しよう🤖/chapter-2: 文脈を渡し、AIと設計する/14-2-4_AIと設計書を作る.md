# 14-2-4: AIと設計書を作る

## 🎯 このセクションで学ぶこと

- 設計書を書き始める前に、何を作るのかを固定できるようになる。
- 設計書一式を、AIと分担して作れるようになる。
- 出てきた設計書のどこを見て、どう直すのかが分かるようになる。

---

## 導入：作らせる前に、何を作るかを決める

Chapter 1でアプリを読ませ、14-2-1で渡し方を覚え、14-2-3で図をテキストに直しました。ここで初めて、設計書そのものをAIに書かせます。

Tutorial 13で作ったカフェや経費精算の設計書は、そのまま実装するためのものではありませんでした。あそこで身につけたのは形式です。その形式を使って、いま手元で動いているアプリに、機能を1つ設計します。

13-8-2「総合演習 - 仕様から設計書一式を作る」でやったのは、できあがった設計書をAIに読ませて、質問を出させることでした。今度は書かせる側に回ります。読ませるときは、返ってきた質問を読めば済みました。書かせると、返ってきたもの全部を確かめることになります。確かめる量は増えます。

そして、書かせる前にやることが1つあります。何を作るのかを決めて、動かないところに置いておくことです。

---

## 要件を先に固定する

設計書を書き始めると、細かい判断が次々に出てきます。コメントは編集できるのか。他人のコメントは消せるのか。返信は付けられるのか。何を作るのかが決まっていないと、この判断のたびに作るものが揺れます。AIは、聞かれれば答えを埋めてくれますが、それはあなたが決めていないことを代わりに決めているだけです。

そこで、設計書より先に**機能イシュー**（設計書を書き始める前に立てる、要件を書いたイシュー）を1件立てます。立てる順序は次のとおりです。

1. 概要だけを書いて、イシューを立てる（このセクションの最初）
2. 設計書を書く
3. 受け入れ条件と、設計書の場所を書き足す（このセクションの最後）

イシューの作り方は、12-2-2「GitHubイシューの作成と管理」で学んだ手順そのままです。GitHubで自分の `authorization-app-practice` のページを開き、「Issues」タブから新しいイシューを立ててください。

### 今回作る機能

Chapter 2からChapter 4まで、この機能を通しで扱います。

> 投稿の一覧からは、誰がどんな投稿をしたかしか分かりません。読んだ人が投稿に一言返せるようにします。投稿を1件開く画面を作り、その画面でコメントを書き込めるようにします。自分が書いたコメントは自分で消せますが、他人のコメントは消せません。

この文が、今回の要件です。あなたが発注者であり、実装を任せる側でもあります。決めきれないところは、あなたが決めます。ここでは、作らないものを2つ決めておきました。

| 作らないもの | 理由 |
|:--|:--|
| コメントの編集 | 消して書き直せば足りるため |
| コメントへの返信 | 画面とデータの作りが一段複雑になるため |

もう1つ、コメントの本文は**必須で、500文字以内**と決めておきます。この決めごとは、あとで入力チェック表とテスト観点表に効いてきます。

### イシューに書く形

タイトルは、動詞で終わる形にします（例: `投稿にコメントできるようにする`）。ラベルは、12-2-1で見た `enhancement` を付けてください。本文は次の形です。

```markdown
## 概要
（何ができるようになるかを2〜3行で）

## 受け入れ条件
- [ ] 〜すると、〜になる
- [ ] 〜すると、〜になる

## 設計書
docs/comment/

## タスク
- [ ] （Chapter 3で書き足します）
```

`## 概要` の見出しは、12-2-2で使ったテンプレートと同じです。いまの時点で埋めるのは `## 概要` だけで構いません。`## 受け入れ条件` と `## 設計書` は、設計書を書いたあとに埋めます。

`## 受け入れ条件` に書く文は、あとで**できあがったものを受け取ってよいかを判定する基準**になります。それをChapter 4で使います。

## 設計書をどこに置くか

14-2-3で作った `docs/` の中に、機能ごとのフォルダを切ります。今回のフォルダ名は `comment` です。

```text
docs/
├── mermaid-practice.md   ← 14-2-3で作ったもの
└── comment/              ← これから作る
```

機能ごとに分けるのは、1つの機能の設計書がひとまとまりで見られるようにするためです。Chapter 3で実装を頼むときには、このフォルダを丸ごと渡します。次の機能を作るときは、その名前で新しいフォルダを切ります。

## 何を作り、何を作らないか

作るのは8つのファイルです。**どれも1ページ程度**で足ります。Tutorial 13の章ごとの成果物を、もう一度フルセットで作り直すわけではありません。

| ファイル | 中身 | 作り方を学んだ節 |
|:--|:--|:--|
| `README.md` | このフォルダの案内 | 13-8-2 |
| `feature-list.md` | 機能一覧＋今回作らないものの表 | 13-2-1 |
| `usecase.md` | ユースケース記述1本 | 13-2-2 |
| `screen.md` | 画面一覧＋画面遷移図＋画面項目定義＋入力チェック表＋メッセージ一覧 | 13-3-1／13-3-2／13-3-3 |
| `api.md` | API設計書＋権限マトリクス | 13-4-1／13-4-2 |
| `data.md` | ER図＋テーブル定義書＋CRUD表 | 13-5-2／13-5-3 |
| `behavior.md` | シーケンス図1本＋例外一覧 | 13-6-1／13-6-3 |
| `test.md` | テスト観点表＋テストケース2本 | 13-8-1 |

作らないものも、先に決めておきます。**設計書は、機能に合わせて取捨します。** 全部そろえることが目的ではありません。

| 作らない設計書 | 理由 |
|:--|:--|
| 状態遷移図 | コメントに状態がないため。書いた瞬間から、消されるまでずっと同じです |
| クラス図 | このアプリの構造図は、14-2-3で `docs/mermaid-practice.md` に起こしたものがあるため。新しく足すものは `data.md` と `api.md` で指せます |
| ユースケース図 | この機能を使う登場人物が、ログイン済みユーザーだけのため（訪問者はどの機能も使えません）。機能一覧に出てくる「コメントを書いた本人」は、そのログイン済みユーザーに条件が1つ付いたものです。誰が何をできるかは、機能一覧・ユースケース記述・権限マトリクスで文字にできます |
| ワイヤーフレーム | 足す画面が、投稿1件とコメントの一覧・入力欄だけのため。並べ方を図に描いて決めるほどの中身がありません |
| 確認事項リスト | 今回は自分が発注者で、決めきれないことは自分で決めるため |

13-3-2では、画面項目定義をワイヤーフレームの四角を上からたどって書き出しました。今回はその下絵がないので、`screen.md` の画面項目定義は、いま動いている投稿一覧の画面と、上の要件の文から起こします。

この判断は、`README.md` に理由つきで書き残します。「作らなかった」と「作り忘れた」を、あとから区別できるようにするためです。

> 💡 **API設計書について**: 13-4-1「API設計 - エンドポイントと入出力」で決めたAPI設計書の役割（どのURLに何を送ると、何が返るかを決めた書類）は、画面を返すルートにもそのまま当てはまります。同じ様式を使ってください。ただし、画面のルートには `/api/` を付けません。返すものはJSONではなく、画面（または移動先）になります。

## 型は自分が知っている

ここからが、このセクションの本題です。設計書を作る仕事を、次のように分けます。

| 誰が | 何をするか |
|:--|:--|
| 自分 | どの設計書に何の列があり、どの順で埋めるのかを知っている |
| AI | その型に沿って、実際に書く |
| 自分 | 出てきたものを読んで、直す |

**型を知っている**というのは、Tutorial 13で全部自分の手で書いた、ということです。だから「機能一覧を作って」ではなく、次のように言えます。

- 機能一覧を、ID・機能・主な利用者の3列で作ってください
- IDは `F-01` から振ってください
- そのすぐ下に「今回作らないもの」の表を続けてください

型を知らない人がAIに設計書を頼むと、返ってきたものが良いのか悪いのかを判定できません。列が1つ増えていても、ロール名が言い換えられていても、それらしく読めてしまいます。

### 渡すもの

設計書を書かせるときの材料は、次の3つです。14-2-2で決めたとおり、その依頼に要らないものは渡しません。

1. 要件の文（機能イシューに書いたもの）
2. アプリの実物（`@` でファイルを指す）
3. `@docs/mermaid-practice.md`（このアプリの構造図。`data.md` を頼むときだけ渡します）

3つ目のファイルには、練習で起こしたカフェのER図も入っています。今回の設計に効くのはクラス図のほうなので、渡すときに「使うのはクラス図です」と書き添えてください。

### 1ファイルずつ頼む

8つを1回で頼まないでください。まとめて頼めば、まとめて返ってきます。返ってきたものを全部読んで直せる人はいませんし、読み切れないまま次へ進むと、Chapter 3の実装がその上に積み上がります。

1つ頼み、読んで、直す。そのうえで次を頼みます。

### 頼むときに必ず指定すること

Tutorial 13で決めた列名や記号は、こちらから言わなければ、AIは自分の知っている形で書きます。ファイルごとに、次のことを指定してください。

| ファイル | 指定すること |
|:--|:--|
| `screen.md` | 画面一覧は ID・画面名・役割・主な利用者 の4列（IDは `SC-01` から）／画面遷移図はMermaidの `flowchart`／画面項目定義の「種類」は 表示・入力（1行）・入力（複数行）・選択・ボタン・リンク の6つから選ぶ／入力チェック表は6列で、本文は必須・500文字以内／メッセージ一覧は4列 |
| `api.md` | エンドポイント一覧は ID・メソッド・エンドポイント・何をするか・認証 の5列（IDは `API-01` から）／そのあとに1本ごとの詳細／最後にエラーレスポンス一覧（3列）／権限マトリクスは列が 訪問者・ログイン済みユーザー の2つで、記号は ○・×・△／△の行は、表のすぐ下に条件を書く |
| `data.md` | ER図はMermaidの `erDiagram` で、四角に書くのはテーブル名だけ／テーブル定義書は追加する `comments` だけ、列は カラム名・データ型・制約・説明／CRUD表は行が機能一覧、列が日本語のエンティティ名 |
| `behavior.md` | シーケンス図1本をMermaidの `sequenceDiagram` で／例外一覧は 起きること・どこで気づくか・そのときの処置・利用者への知らせ の4列 |
| `test.md` | テスト観点表は ID・何を確かめるか・区分・元になった設計書 の4列（IDは `TC-01` から）／区分は 正常系・異常系・境界値 の3つだけ／境界値は必ず2行1組／そのあとにテストケースを2本 |
| `README.md` | ①何の機能の設計書一式か ②ファイル一覧と、それぞれが何の設計書か ③この機能で作らなかった設計書と、その理由 |

---

## 出てきた設計書を直す

出てきたものは、そのまま置きません。列名・記号・言葉づかいの3点を見て、自分で直します。次のずれがよく起きます。

| よく起きるずれ | 直し方 |
|:--|:--|
| 列が増える、または減る（「優先度」「担当」などが足される） | Tutorial 13で決めた列だけに戻す |
| **訪問者**・**ログイン済みユーザー**という名前そのものが言い換えられる（「一般ユーザー」「認証済みユーザー」など） | Tutorial 13で決めたこの2つの名前に戻す |
| 受け入れ条件が「〜できること」の形になる | 「〜すると、〜になる」の形に戻す |
| テスト観点表の「元になった設計書」が空になる | 空のままにしない。埋められない行があれば、それは設計の穴なので、設計書のほうを直す |
| 実装の詳細（クラス名・メソッド名）が設計書に入り込む | 設計書からは外す。どう作るかを決めるのはChapter 3です |
| 頼んでいない状態遷移図まで作られる | この機能に状態はありません。`README.md` の「作らなかった設計書」に理由を書きます |

上から4つ目だけ、性質が違います。ほかは書き方のずれですが、これは中身の話です。13-8-1「テスト設計 - 設計の検証としてのテスト」で、この欄が空のまま残る行が出たら、そこが設計の穴だと学びました。AIが埋められなかったということは、どの設計書にも書かれていない、ということです。

## 🏃 コメント機能の設計書を作る

> 🔥 ここからは、AIに実装を任せて構いません。ただし「任せる」と「丸投げ」は違います。何を作るかは設計書で自分が決め、出てきたものはテスト・動作確認・コードレビューで自分が検証します。品質の責任は、AIではなくあなたが握ります。

進め方は次のとおりです。誰がやるのかを、行の先頭に書いてあります。

1. 【自分】機能イシューを立てる（概要だけ書く）
2. 【自分】`docs/comment/` フォルダを作る
3. 【自分⇄AI】要件の文とアプリの実物を渡し、機能一覧とユースケース記述を書かせて、自分で直す
4. 【自分⇄AI】画面・APIと権限・データ・振る舞い・テストの設計書を、1ファイルずつ書かせて、自分で直す
5. 【自分⇄AI】READMEを書かせて、作らなかった設計書と理由が入っているかを確かめる
6. 【自分】機能イシューに、受け入れ条件と設計書の場所を書き足す
7. 【自分】`docs/` をコミットして、GitHubへ送る

このセクションは長くなります。途中で区切って構いません。区切るときは、そこまでに書けた設計書がファイルとして保存されていることを確かめてください。

### Step 1: 機能イシューを立てる

GitHubで `authorization-app-practice` のページを開き、「Issues」タブから新しいイシューを立てます。タイトルは `投稿にコメントできるようにする`、ラベルは `enhancement` です。

本文には、いまは `## 概要` だけを書きます。上に載せた要件の文を、自分の言葉で2〜3行にまとめてください。残りの見出し（`## 受け入れ条件`・`## 設計書`・`## タスク`）は、枠だけ作っておきます。

立てたら、イシューの番号を控えておいてください。最後のコミットで使います。

### Step 2: `docs/comment/` を作る

```bash
# アプリのフォルダの中で実行する
cd ~/laravel-practice/14_hands-on/authorization-app-ai
mkdir docs/comment
```

### Step 3: 機能一覧とユースケース記述を書かせる

14-1-3と14-2-1で、コメント機能を足すと何が増えそうかを下調べしました。ここから設計書が返ってくるたびに、そのときのメモと見比べて、自分の見立てと違うところがないかを見てください。

アプリのフォルダでClaude Codeを起動して、1つ目を頼みます。

```text
このアプリに、投稿へのコメント機能を足します。要件は次のとおりです。

投稿の一覧からは、誰がどんな投稿をしたかしか分かりません。読んだ人が投稿に一言返せるように
します。投稿を1件開く画面を作り、その画面でコメントを書き込めるようにします。自分が書いた
コメントは自分で消せますが、他人のコメントは消せません。

docs/comment/feature-list.md を作り、機能一覧の表を書いてください。
列は ID・機能・主な利用者 の3つで、IDは F-01 から振ります。
機能名は「コメントの投稿」のような名詞の形にしてください。
主な利用者は、ログインしていれば誰でもできることには「ログイン済みユーザー」、
書いた本人だけができることには「コメントを書いた本人」と書いてください。
そのすぐ下に「今回作らないもの」の表（列は 作らないもの・理由）を続けてください。
今回作らないのは、コメントの編集（消して書き直せば足りるため）と、
コメントへの返信（画面とデータの作りが一段複雑になるため）の2つです。
```

> 💡 この依頼のポイントは4つです。①要件の文を丸ごと渡している ②列名・列順・IDの振り方を自分が指定している ③使うロール名を名指ししている ④作らないものは自分が決めて渡している。決まっていることを渡さないと、その分だけAIが決めます。

> 💡 **出力例について**: AIの応答は毎回変わります。以下はあくまで一例です。文言が違っても、チェックリストの項目を満たしていれば問題ありません。

```text
あなた: （上の依頼を送る）
Claude Code: （docs/comment/feature-list.md を作る差分を示して、進めてよいかを尋ねてくる）
あなた: （差分を読んで、列と行が頼んだとおりなら承認する）
```

できあがったら開いて、列が3つのままか、IDが `F-01` から振られているか、「今回作らないもの」の表が続いているかを見てください。違っていたら、その場で直させます。

続けて、ユースケース記述を頼みます。

```text
次に docs/comment/usecase.md を作ります。
@docs/comment/feature-list.md を読んで、「コメントを書く」のユースケース記述を1本だけ
書いてください。IDは UC-01 です。

項目は アクター・事前条件・基本フロー・代替フロー・事後条件・受け入れ条件 の6つです。
基本フローの主語は、アクターかシステムのどちらかにしてください。
受け入れ条件は「〜すると、〜になる」の形のチェックリストにしてください。
テーブル名やクラス名などの実装の話は書かないでください。
```

> 💡 この依頼のポイントは3つです。①前に作ったファイルを `@` で渡して、続きであることを示している ②項目を6つ名指ししている ③受け入れ条件の文の形を指定している。形を指定しないと「コメントを投稿できること」のような、確かめようのない書き方になります。

**ここがこのセクションでいちばん大事なところです。** 受け入れ条件に、次の4つがそろっているかを確かめてください。足りなければ、自分で書き足します。

- [ ] 投稿一覧で「詳細」を押すと、その投稿の本文とコメントの一覧が表示される
- [ ] 本文を入れて「コメントする」を押すと、その投稿のコメント一覧に自分のコメントが増える
- [ ] 本文を空のまま「コメントする」を押すと、エラーが表示され、コメントは増えない
- [ ] 自分が書いたコメントには「削除」が出て、押すと一覧から消える。他人のコメントには「削除」が出ない

4つ目が抜けやすいので気をつけてください。要件の文では「他人のコメントは消せません」と約束しています。ここに書いておかないと、削除が1行も作られていないまま、Chapter 4の確認を通ってしまいます。

### Step 4: 残りの設計書を1ファイルずつ書かせる

ここまでで2枚できました。ここで `/clear` を打って構いません。次の依頼で `@docs/comment/feature-list.md` のようにファイルを指し直せば、続きとして書けます。

残りは `screen.md`・`api.md`・`data.md`・`behavior.md`・`test.md` の5枚です。この順に、1つずつ頼みます。頼み方の形はStep 3と同じで、「どのファイルを作るか」「何の設計書を書くか」「列名と記号」「やらないこと」を書きます。「頼むときに必ず指定すること」の表を横に置いて進めてください。

1枚目の `screen.md` だけ、依頼の見本を載せます。表の指定を、どう文章に組み立てるかを見てください。

```text
docs/comment/screen.md を作ります。@docs/comment/feature-list.md と
@docs/comment/usecase.md を読んで、次の5つをこの順で書いてください。
```

## ✨ まとめ

- 設計書を書かせる前に、機能イシューで要件を固定します。決めていないことは、AIが代わりに決めます。
- 設計書は `docs/` の中に、機能ごとのフォルダを切って置きます。今回は `docs/comment/` に8つのファイルを作りました。

- 分担は、型は自分が知っていて、書くのはAI、直すのは自分です。列名・記号・ロール名は、こちらから指定しなければ言い換えられます。
- 8つを1回で頼まず、1つ頼んで、読んで、直します。読み切れないまま進めた分は、そのまま実装へ写ります。

これでChapter 2は終わりです。何を作るかが決まり、それを書いた設計書がそろいました。次のChapter 3では、この設計書をAIに渡して、実際にコードを書かせます。
