# 14-3-2: 実装タスクに分解する

## 🎯 このセクションで学ぶこと

- 設計書から実装タスクの一覧を作れるようになる。
- タスクの大きさを、自分の基準で決められるようになる。
- タスク名に設計書のIDを入れて、あとから指せるようにできるようになる。

---

## 導入：設計書のままでは、頼めない

`docs/comment/` に8つの設計書がそろいました。では、このフォルダを丸ごと渡して「このとおりに作ってください」と頼めばよいのでしょうか。

頼めば、たぶん作られます。問題は、そのあとに起きることです。テーブルの追加、モデル、コントローラー、ルート、画面、テスト。9つ以上のファイルの差分が、一度に出てきます。それを全部読んでから承認する人はいません。読まずに通すことになり、14-1-4で確かめたとおり、承認が形だけのボタンになります。

設計書は、決めごとを整理した書類です。作る順番には並んでいません。だからこのセクションでは、設計書を作業の順に割り直します。

---

## 実装タスクとは何か

実装タスクは、設計書から起こした1回の作業の単位です。1つのタスクには、次の3つが決まっています。

| 決まっていること | コメント機能での例 |
|:--|:--|
| どの設計書のどこを実装するのか | `api.md` の `API-02` |
| どのファイルを触ることになるのか | コントローラー、ルート、投稿詳細画面のBlade、テスト |
| 終わったと言えるのは何が起きたときか | 本文を入れて送ると、コメントが一覧に増える |

3つ目がいちばん大事です。「コントローラーを作る」で終わるタスクだと、終わったかどうかを自分で確かめられません。ファイルができたことは確かめられますが、それが正しく動くかどうかは、まだ何も分かっていないからです。

---

## タスクの大きさを決める

どこで区切るかに、決まった正解はありません。判断の基準を3つ持っておけば、自分で決められます。

**1. 差分を自分が読み切れる大きさか**

読み切れない量が一度に出てくると、承認が形だけになります。導入で書いたとおりです。逆に言えば、「これなら全部読める」と思える量が、1つのタスクの上限です。

**2. 終わったかどうかを、自分で確かめられるか**

画面が出る、データが増える、テストが書かれている。このどれかで区切ります。手を動かして確かめられない区切り方をすると、次のタスクへ進んでよいのかが判断できません。

**3. 設計書の1行に対応しているか**

今回は `api.md` のエンドポイントが3本あります。この3本が、そのまま3つのタスクになります。設計書の行に対応していると、実装が終わったときに、どの決めごとが満たされたのかをたどれます。

割りすぎにも気をつけてください。1ファイルずつに割ると、2つ目の基準に引っかかります。

---

## タスク名に設計書のIDを入れる

タスクの名前には、もとになった設計書のIDを先頭に入れます。

```text
API-01 の投稿詳細画面を表示する
```

こうしておくと、実装を頼むときに「`api.md` の `API-01` を実装してください」と書けます。どの決めごとに従って作るのかが、タスク名だけで決まります。名前を読めば設計書のどこを開けばよいかが分かるので、日をまたいで再開するときにも探さずに済みます。

Tutorial 13で振ってきた `F-`・`UC-`・`SC-`・`API-`・`TC-` は、この場面のためにあります。IDが無いと「コメント登録の実装」としか書けず、入力チェックの中身も、戻り先の画面も、あとで設計書を読み直して探すことになります。

> 💡 **TIP**: 1つのタスクが複数のIDにまたがることもあります。今回のタスク1は、`API-01` のエンドポイントと `SC-02` の画面の両方を作ります。そのときは、先頭に置くIDを1つ選び、残りは中身の説明に書いてください。名前が長くなるほど、一覧としては読みにくくなります。

## 🏃 コメント機能を実装タスクに割る

> 🔥 ここからは、AIに実装を任せて構いません。ただし「任せる」と「丸投げ」は違います。何を作るかは設計書で自分が決め、出てきたものはテスト・動作確認・コードレビューで自分が検証します。品質の責任は、AIではなくあなたが握ります。

このセクションでは、まだコードを1行も書かせません。作るのはタスクの一覧だけです。

1. 【自分⇄AI】設計書を渡して、タスクの案を出させる
2. 【自分】返ってきた案の大きさを、3つの基準で決め直す
3. 【自分】タスク名の先頭に、もとになった設計書のIDを入れる
4. 【自分】機能イシューの `## タスク` に貼る

### Step 1: 設計書を渡して、タスクの案を出させる

アプリのフォルダでClaude Codeを起動します。

```bash
# アプリのフォルダへ移動して起動する
cd ~/laravel-practice/14_hands-on/authorization-app-ai
claude
```

渡すのは、作業の単位を決めるのに要る3枚だけです。

```text
@docs/comment/api.md と @docs/comment/usecase.md と @docs/comment/data.md を読んで、
この機能を実装するタスクの一覧を作ってください。
1つのタスクは、動かして確かめられるところまでを1つの区切りとしてください。
タスク名の先頭に、もとになった設計書のIDを入れてください。
コードはまだ書かないでください。
```

> 💡 このお願いのポイントは3点です。①どの設計書を読むかを名指ししている ②区切りの決め方を先に渡している ③「コードはまだ書かないでください」で、この場でやらないことを書いている。文言をそのまま覚える必要はありません。

> 💡 **出力例について**: AIの応答は毎回変わります。以下はあくまで一例です。文言が違っても、チェックリストの項目を満たしていれば問題ありません。

```text
あなた: （上のお願いを送る）
Claude Code: （タスクの一覧を返してくる。3つのこともあれば、5つや6つに割られてくることもある）
```

### Step 2: 返ってきた案の大きさを決め直す

ここが、このセクションでいちばん大事なところです。返ってきた一覧は案であって、決定ではありません。3つの基準に当てはめて、自分で決め直します。

- 1つのタスクで触るファイルが多すぎないか（読み切れる量か）
- そのタスクが終わったとき、何を見れば終わったと言えるか
- 設計書のどの行に対応しているか

多く割られてきたときは、まとめます。「マイグレーションを作る」と「モデルを作る」が別々に並んでいたら、この2つは1つにします。

逆に、1つのタスクが大きすぎると感じたら割ります。判断に迷ったら、そのタスクを終えたときに何を確かめるつもりかを、自分の言葉で言ってみてください。言えなければ、区切りの位置が合っていません。

### Step 3: タスク名にIDを入れる

決めた区切りに、名前を付けます。先頭にIDを置き、そのあとに何をするのかを書きます。

```text
API-02 のコメント登録を実装する
```

AIが付けた名前に「コメント機能のバックエンド実装」のような、設計書のどこを指しているのか分からないものがあれば、書き直してください。

決まった一覧は、次のStepでGitHubのイシューに移します。3件程度なら手で打ち直して構いません。打ち直すのが面倒なら、「決めた形で `- [ ] ID 名前` のチェックリストとして出し直してください」とAIに頼めば、そのまま貼れる形で返ってきます。

### Step 4: 機能イシューの `## タスク` に貼る

GitHubで、14-2-4で立てたイシューを開きます。本文を書き直す手順は、14-2-4で受け入れ条件を書き足したときと同じです。空にしてあった `## タスク` を、決めた一覧に差し替えます。

```markdown
## タスク
- [ ] API-01 の投稿詳細画面を表示する
- [ ] API-02 のコメント登録を実装する
- [ ] API-03 のコメント削除を実装する
```

`- [ ]` の書き方は、12-2-2「GitHubイシューの作成と管理」で学んだチェックリストの記法です。

タスクを1つ終えるたびに、この行を `- [x]` に書き換えます。イシューの本文を開いて `[ ]` を `[x]` にしても、GitHubの画面に表示されているチェックボックスを直接クリックしても、どちらでも同じように保存されます（2026年8月時点）。3つとも `- [x]` になった状態が、この機能を作り終えた状態です。

貼り終えたら、次の4つを確かめてください。

- [ ] 機能イシューの `## タスク` に、タスクが並んでいる
- [ ] どのタスクにも、もとになった設計書のIDが入っている
- [ ] `api.md` のエンドポイント3本が、どれかのタスクに現れている
- [ ] 1つのタスクを終えたときに何が確かめられるようになるかを、自分の言葉で言える

## 💡 よくある間違い

**1ファイルずつに割る**

「マイグレーションを作る」「モデルを作る」「コントローラーを作る」と並べると、一覧としてはきれいに見えます。ただし、最初の2つが終わっても画面には何も起きません。終わったかどうかを確かめられないタスクは、進んだかどうかも分かりません。

**設計書に無い作業を足す**

タスクを書いているうちに「ついでにコメントの編集も」と思いつくことがあります。`feature-list.md` の「今回作らないもの」に、コメントの編集を入れたはずです。足したくなったら、まず設計書を直してください。タスクの一覧を、設計書より先に進めないようにします。

**AIが出した一覧を、そのままイシューに貼る**

Step 2を飛ばす形です。AIは設計書を読んで区切りを提案できますが、あなたが差分をどれだけ読めるかは知りません。区切りを決めるのは、読む人の仕事です。

---

## ✨ まとめ

- 設計書は決めごとの順に整理されています。作業の順に割り直したものが実装タスクです。
- タスクの大きさは3つの基準で決めます。差分を読み切れるか、終わったことを自分で確かめられるか、設計書の行に対応しているか。
- 1ファイルずつに割ると、動くところまで進まないタスクが並びます。
- タスク名の先頭に設計書のIDを入れておくと、実装を頼むときに「`api.md` の `API-01` を実装してください」と書けます。
- タスクは機能イシューの `## タスク` にチェックリストで並べ、終えるたびに `- [x]` に書き換えます。

次のセクション（14-3-3）では、ここで作ったタスクの1つ目と2つ目を、実際にAIに実装させます。ブランチを切るところから始めます。
