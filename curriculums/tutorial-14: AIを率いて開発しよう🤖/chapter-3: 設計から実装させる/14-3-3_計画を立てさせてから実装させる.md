# 14-3-3: 計画を立てさせてから実装させる

## 🎯 このセクションで学ぶこと

- 作業の単位とブランチ・コミットの関係を説明できるようになる。
- AIが立てた計画を読んで、承認するか指摘するかを判断できるようになる。
- 設計書のIDで実装を頼み、テストも一緒に書かせられるようになる。

---

## 導入：いきなり書かせない

いよいよ、アプリのコードを書かせます。ここまでで書き換えさせたのは、`README.md` の1行と `docs/` の中の設計書だけでした。

ただし、タスクを渡していきなり書かせることはしません。14-1-3「最初の仕事は質問 - コードベースを調査させる」で、書かせる前に読ませて説明させました。ここでやるのも同じ筋です。書かせる前に、何をするつもりかを言わせます。違うのは、返ってくるものが「このアプリの説明」ではなく「これからやることの計画」だという点だけです。

---

## 作業の単位とブランチ

先に、どこで区切って記録するかを決めておきます。

| 単位 | 何に対応するか |
|:--|:--|
| ブランチ1本 | 機能イシュー1件（＝1つの機能） |
| コミット1つ | 実装タスク1つ |
| プルリクエスト1本 | 機能イシュー1件 |

14-2-4で立てたイシューは1件で、そこに3つのタスクが並んでいます。ブランチもプルリクエストも、このイシューに対して1本ずつです。

コミットのほうは、タスクごとに1つ作ります。タスク1を終えたらコミット、タスク2を終えたらコミット、という進め方です。こうしておくと、あとで「どの作業でこの行が入ったのか」をたどれます。1つのタスクの途中でおかしくなったときに、直前のコミットまで戻すこともできます。

ブランチを切るコマンドは、12-2-4「ハンズオン - GitHub連携演習」で打った形と同じです。実際に打つのはこのあとの実践のStep 1なので、ここでは形だけ見ておいてください。

```bash
# ここでは読むだけ。打つのは実践のStep 1です
git switch -c feature/issue-1-add-comments
```

`issue-1` の `1` は、14-2-4で立てた自分のイシューの番号に置き換えてください。

## プランモードで計画を立てさせる

14-3-1で名前だけ出したプランモードを、ここで使います。入り方は、依頼の先頭に `/plan` を付けるだけです（2026年8月時点）。

```text
/plan @docs/comment/api.md を読んで、API-01 の実装の計画を立ててください。
```

このモードのあいだ、AIはファイルを読み、必要なら調べるためのコマンドを実行しますが、ソースコードは書き換えません。返ってくるのは、どのファイルに何をするかという計画の文章です。

> 💡 **TIP**: `Shift+Tab` を押して、モードのほうを切り替える入り方もあります。依頼のたびに `/plan` を付けるほうが、いま計画を立てさせているのか実装させているのかを取り違えずに済むので、この教材では `/plan` を使います（2026年8月時点）。

計画ができると、AIはそれを画面に出して、どう進めるかを聞いてきます。画面にはもう少し細かく分かれて並びますが、意味は次の3つに分けられます（2026年8月時点）。

| 選ぶもの | そのあと何が起きるか |
|:--|:--|
| そのまま進めさせる | 計画のとおりに実装が始まります。ファイルの書き換えは、いちいち止まりません |
| 1つずつ確かめながら進めさせる | 実装は始まりますが、ファイルを書き換えるたびに承認を求められます |
| 指摘して、計画を直させる | 実装は始まりません。計画を書き直させます |

この教材で選ぶのは、2つ目の**1つずつ確かめながら進めさせる**です。画面では「承認して各編集を手動でレビュー」と書かれたものが、これにあたります。差分を1ファイルずつ読んで判断する練習が、この章の中身だからです。1つ目を選ぶと、書き換えが終わったあとにまとめて読むことになります。

ここではっきりさせておきたいことが1つあります。計画を承認することは、**実装の開始を許可すること**です。承認した瞬間にモードが切り替わり、AIはファイルを書き換え始めます。「とりあえず承認して、まずいところは後で直す」という進め方にはなりません。

計画に納得できないときは、承認せずに指摘してください。指摘の内容を踏まえた計画が、もう一度出てきます。

## 計画のどこを読むか

計画を読むときに見るのは、次の3つです。

**1. 触るファイルの一覧が、思っていたものと合っているか**

`docs/comment/` の設計書から想像していたファイルと、計画に並んでいるファイルを見比べます。知らないファイルが混ざっていたら、そこで止めます。

**2. 設計書に無いものが入っていないか**

頼んでいないテーブルの追加、頼んでいないパッケージの導入、頼んでいない画面。どれも「あったほうが良さそう」という理由で足されることがあります。良さそうかどうかを決めるのは、設計書を書いたあなたです。

**3. 順番が通っているか**

表を作る前に、その表を使う処理を書く計画になっていないか。テストを書く前に、テストが使うモデルができているか。順番が逆でも実装は進みますが、途中でエラーが出て、そこから直す作業が増えます。

止めるときは、どの設計書のどこと食い違っているのかを名指しします。

```text
計画の3番目に、コメントを編集する画面を作ると書かれています。
docs/comment/feature-list.md の「今回作らないもの」にコメントの編集を入れているので、
そこは外して、計画を立て直してください。
```

> 💡 このお願いのポイントは、どの設計書のどこと食い違っているかを名指ししていることです。「そこは要りません」だけだと、次に同じ判断が要るときに、また同じやり取りをすることになります。

## 実装を頼む

計画を頼むときの依頼文には、実装の依頼がそのまま入ります。書くのは、14-2-1で決めた3つ（何を・どこまで・どうなったら終わりか）です。今回はそこに、設計書のIDと、触ってほしくない場所を足します。

タスク1の依頼は、次の形になります。

```text
/plan @docs/comment/data.md と @docs/comment/api.md と @docs/comment/screen.md を読んで、
実装タスク1「API-01 の投稿詳細画面を表示する」の計画を立ててください。

- comments テーブルと Comment モデルを、data.md のテーブル定義書のとおりに作ります
- Post と User に、コメントへのつながりを足します
- API-01 のエンドポイントと、SC-02 の投稿詳細画面を作ります
- 投稿一覧の画面に、詳細画面へのリンクを1つ足します
- いまある投稿のルート4本（一覧・編集・更新・削除）と、投稿の編集・削除の動きは変えないでください
- 投稿一覧から「詳細」を押すと投稿詳細画面が開くところまでを、このタスクの完了とします
```

> 💡 この依頼のポイントは4点です。①`/plan` を頭に付けて、いきなり書き始めさせない ②読ませる設計書を3枚に絞っている ③やることを設計書のIDで指している ④触ってほしくないところと、どうなったら終わりかを書いている。④の前半が抜けると、ついでに直された箇所を、あとから差分の中で探すことになります。後半が抜けると、どこまでで手を止めるかをAIが決めることになります。

### テストは、実装と一緒に書かせる

タスク2の依頼には、テストの作成を入れます。

```text
/plan @docs/comment/api.md と @docs/comment/usecase.md と @docs/comment/screen.md と
@docs/comment/test.md を読んで、実装タスク2「API-02 のコメント登録を実装する」の計画を
立ててください。

- 入力チェックは screen.md の入力チェック表のとおりにしてください
- エラーメッセージは、入力チェック表に書いた文言どおり日本語で出してください
- test.md の TC-01 から TC-05 までのテストを、tests/Feature/ に一緒に書いてください
- テストメソッドの名前は test_ で始めてください
- テストで使う投稿とユーザーは、テストの中で用意してください。
  database/factories/ には UserFactory.php しかないので、足りない分は一緒に作ってください
- TC-06 は今回は書かないでください
- 投稿詳細画面で本文を入れて送ると、コメントが一覧に増えるところまでを、このタスクの完了とします
```

> 💡 この依頼のポイントは、テストを実装と一緒に書かせていることです。あとから「テストも書いておいて」と頼むと、AIはできあがったコードに合わせてテストを書きます。それでは、コードが間違っていても通るテストになります。何を確かめるかは `test.md` に自分が先に書いてあるので、それを先に渡します。

`TC-06` はここでは書かせません。テスト観点表のどの行を、どの手段で確かめるのかは、14-4-1で決めます。

なお、このセクションではテストを回しません。書かれていることを差分で確かめるところまでです。回すのはChapter 4です。

実装の途中で質問が来たときも、14-2-4と同じ扱いです。設計書に書き足してから、続けてもらいます。

## 🏃 タスク1とタスク2を実装させる

> 🔥 ここからは、AIに実装を任せて構いません。ただし「任せる」と「丸投げ」は違います。何を作るかは設計書で自分が決め、出てきたものはテスト・動作確認・コードレビューで自分が検証します。品質の責任は、AIではなくあなたが握ります。

2つ進めるのは、タスク1にはテストを書く対象が無いからです。テストを含めた依頼の形は、タスク2で初めて成立します。

1. 【自分】ブランチを切る
2. 【自分⇄AI】プランモードで、タスク1の計画を立てさせる
3. 【自分】計画を読んで、承認するか指摘するかを決める
4. 【AI】タスク1を実装させる
5. 【自分】差分を読んで承認し、コミットして、イシューのタスクに印を付ける
6. 【自分⇄AI】同じ手順で、タスク2をテストごと進める

アプリが止まっている場合は、Docker Desktop（またはDocker Engine）を起動してから `./vendor/bin/sail up -d` を実行しておいてください。最後にブラウザで確かめます。

このあとは、Claude Codeへ送る依頼と、ターミナルで打つコマンドが交互に出てきます。ターミナルのコマンドをClaude Codeの入力欄に打つと、依頼として送られてしまいます。`/exit` で抜けてから打つか、別のターミナルを開いて打ってください。

### Step 1: ブランチを切る

```bash
# アプリのフォルダの中で実行する
cd ~/laravel-practice/14_hands-on/authorization-app-ai
git switch -c feature/issue-1-add-comments
```

`git branch` を打って、`*` が新しいブランチに付いていることを確かめてください。

### Step 2: タスク1の計画を立てさせる

Claude Codeを起動して、上に載せたタスク1の依頼を送ります。

```bash
claude
```

> 💡 **出力例について**: AIの応答は毎回変わります。以下はあくまで一例です。文言が違っても、チェックリストの項目を満たしていれば問題ありません。

```text
あなた: （タスク1の依頼を送る）
Claude Code: （routes/web.php や app/Models/Post.php を読んだうえで、
              触るファイルの一覧とやることの順番を書いた計画を出し、どう進めるかを尋ねてくる）
```

計画にファイルの一覧が出てこないときは、「触ることになるファイルの一覧も書いてください」と足して頼み直してください。一覧が無いと、次のStepで読むものがありません。

### Step 3: 計画を読んで決める

「計画のどこを読むか」の3つを、順に当てはめます。

- 触るファイルの一覧は、`docs/comment/` から想像したものと合っているか
- 設計書に無いものが入っていないか
- 順番が通っているか

問題が無ければ承認します。1つでも引っかかったら、承認せずに指摘してください。進め方は「1つずつ確かめながら進めさせる」にあたるものを選びます。ここで承認すると、実装が始まります。

### Step 4: 実装させて、差分を承認する

承認すると、AIがファイルを書き換え始めます。2つ目を選んであるので、書き換えのたびに差分が出て、進めてよいかを聞かれます。14-1-2で `README.md` を書き換えさせたときと同じ画面です。

出てきた差分は、読んでから承認してください。どの順で読むかは、次の14-3-4で扱います。ここでは、頼んだ範囲のファイルかどうかだけでも見てください。

新しいテーブルを作ったときは、データベースへの反映が要ります。AIがコマンドの実行を求めてきたら、`./vendor/bin/sail artisan migrate` の形になっているかを見てから許可してください。このアプリはDockerの中で動くので、`php artisan migrate` では動きません。その形でなければ許可せず、Sailを使うように伝えます。実行を求められないまま先に進んだ場合は、自分でこのコマンドを打ちます。

```bash
# アプリのフォルダの中で実行する
./vendor/bin/sail artisan migrate
```

一通り終わったら、ブラウザで `http://localhost/posts` を開きます。投稿の「詳細」を押して、投稿詳細画面が開くところまで確かめてください。「テーブルが見つからない」というエラー画面が出たら、上の反映が抜けています。

### Step 5: コミットして、イシューに印を付ける

```bash
# アプリのフォルダの中で実行する
git status
git add .
git commit -m "Add #1: add post detail page with comments"
```

`git add .` を使うときは、先に `git status` で何が変わったのかを見る習慣を、4-3-2「ファイルの追加」で学びました。頼んでいないファイルが混ざっていないかを、ここでも見てください。`#1` は自分のイシューの番号に置き換えます。

コミットできたら、機能イシューを開いて、タスク1の行を `- [x]` に変えます。

### Step 6: タスク2を、テストごと進める

`/exit` で抜けていた場合は、`claude` で起動し直します。セッションを続けている場合は、タスク1とは決めることが変わるので、`/clear` を打ってから始めて構いません。設計書は `@` で指し直せば渡せます。

あとは同じ流れです。上に載せたタスク2の依頼を送り、計画を読み、承認し、差分を読んで承認します。実装が終わったら、`tests/Feature/` に新しいファイルができているかを開いて確かめてください。`TC-01` から `TC-05` の5つの観点が、5つのテストメソッドとして書かれていれば、頼んだとおりです。

ブラウザで、本文を入れて「コメントする」を押してみます。コメントが一覧に増えたら、コミットします。

```bash
git status
git add .
git commit -m "Add #1: add comment posting with tests"
```

イシューのタスク2の行も `- [x]` に変えてください。

2つのタスクを終えたら、次の5つを確かめてください。

- [ ] `feature/issue-{番号}-add-comments` ブランチで作業している
- [ ] `http://localhost/posts` で投稿の「詳細」を押すと、投稿詳細画面が開く
- [ ] 本文を入れて「コメントする」を押すと、コメントが一覧に増える
- [ ] `tests/Feature/` に、`TC-01` から `TC-05` に対応するテストが書かれている
- [ ] コミットが2つあり、機能イシューのタスク1とタスク2の行に `- [x]` が付いている

## 💡 よくある間違い

**計画を読まずに承認する**

計画は、実装より短くて読みやすい文章です。だからこそ、流し読みで承認してしまいがちです。ここを飛ばすと、あとで差分の山を読むことになります。読む場所を前に持ってくるのが、計画を立てさせる目的そのものです。

**実装が終わってから「テストも書いて」と頼む**

順番を入れ替えるだけで、テストの意味が変わります。先に書かせれば、テストは `test.md` に書いた観点を確かめるものになります。後から頼めば、いまあるコードが通ることを確かめるだけのものになります。

**3つのタスクを1回で頼む**

「どうせ同じ機能なのだから」とまとめて頼むと、14-3-2で割った意味が無くなります。差分は3タスク分がまとめて出てきて、コミットも1つになります。タスクは1つずつ、終わってから次を頼んでください。

## ✨ まとめ

- ブランチは機能イシュー1件につき1本、コミットは実装タスク1つにつき1つ作ります。
- プランモードは、依頼の先頭に `/plan` を付けて使います。計画のあいだ、ソースコードは書き換わりません。
- 計画を承認することは、実装の開始を許可することです。読んでから承認してください。
- 計画で見るのは、触るファイルの一覧・設計書に無いものが入っていないか・順番が通っているかの3つです。
- 実装の依頼には設計書のIDを書き、テストも一緒に書かせます。あとから頼むと、コードに合わせたテストになります。

次のセクション（14-3-4）では、いま流し読みで通した差分を、どの順で読むかを決めます。人が止まる場所を、自分で設計する話です。
