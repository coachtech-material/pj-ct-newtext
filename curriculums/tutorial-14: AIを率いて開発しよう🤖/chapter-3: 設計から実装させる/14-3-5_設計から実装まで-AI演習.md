# 14-3-5: 設計から実装まで - AI演習

## 📌 この演習について

Chapter 3の締めくくりです。14-3-3では、計画を立てさせるところから差分の承認まで、一緒に進めました。ここからは、同じ流れを自分ひとりで回します。

残っているのは、実装タスク3と仕上げです。タスク3を終えてコミットし、ブランチをGitHubへ送って、プルリクエストを開くところまで進みます。

> 🔥 ここからは、AIに実装を任せて構いません。ただし「任せる」と「丸投げ」は違います。何を作るかは設計書で自分が決め、出てきたものはテスト・動作確認・コードレビューで自分が検証します。品質の責任は、AIではなくあなたが握ります。

## 🎯 演習課題

### 📋 課題

実装タスク3「`API-03` のコメント削除を実装する」を、14-3-3と同じ手順で回してください。

作るものは、`docs/comment/` に書いてあります。`api.md` の `API-03` に、削除のエンドポイントと戻り先が書いてあります。同じ `api.md` の後半にある権限マトリクスの `F-03` は、ログイン済みユーザーに `△` が付いていて、条件は「自分が書いたコメントだけ」です。`usecase.md` の受け入れ条件の4つ目に、画面での見え方が書いてあります。

> 自分が書いたコメントには「削除」が出て、押すと一覧から消える。他人のコメントには「削除」が出ない

この受け入れ条件のうち、後半の「他人のコメントには『削除』が出ない」は、別のアカウントでログインし直さないと確かめられません。この演習で自分の目で見るのは前半までにして、他人から見たときの動きはChapter 4で確かめます。

このアプリには、10-3-5「認可機能 - ハンズオン演習」で自分が書いた `PostPolicy` があります。コメントの削除も、同じ形で作れます。どう作るかを決めるのはあなたなので、依頼の文にそこまで書くかどうかも自分で判断してください。

タスク3では、テストは書かせません。削除の観点（`TC-06`）をどの手段で確かめるのかは、14-4-1で決めます。

タスク3が終わったら、仕上げに進みます。

1. 機能イシューの3つのタスクが、すべて `- [x]` になっている状態にする
2. ブランチをGitHubへ送る
3. プルリクエストを開く（本文に `Closes #{イシューの番号}` を入れる）

**プルリクエストはマージしません。** まだ確かめていないからです。確かめるのは、次のChapter 4です。開いたまま置いておいてください。

## 💡 ヒント

- 1つのタスクが終わるまで、次を頼まないでください。今回残っているのは1つだけですが、仕上げの3手も一度にまとめて頼まないほうが読みやすくなります。
- 計画に頼んでいないものが入っていたら、承認せずに指摘して、立て直させてください（14-3-3）。
- 差分が読み切れない量になったら、そこで止めます。頼む単位を小さくして、やり直してください（14-3-2）。
- タスク3の途中で話が噛み合わなくなってきたら、まだ同じ作業の最中なので `/compact` で机を空けます。区切って `/clear` を打つのは、タスクを終えて次に移るときです（14-2-2）。

## 🏃 実践：一緒に進めてみましょう

### 🧠 先輩エンジニアの思考プロセス

自分で進めてみて詰まったら、ここから先を読んでください。何を渡し、どこで承認し、何で確かめるのかを、場面ごとに並べます。

| 場面 | 何を渡すか | どこで承認するか | 何で確かめるか |
|:--|:--|:--|:--|
| タスク3を頼む前 | `api.md`（`API-03` と権限マトリクスの `F-03`）、`usecase.md` の受け入れ条件の4つ目 | 計画を読んでから | 触るファイルの一覧が、自分の想像と合っているか |
| 実装させている間 | 追加で聞かれたことだけ | 差分を読んでから | 消えた行が無いか。頼んでいないファイルが入っていないか |
| コミットする前 | なし | なし | ブラウザで、自分のコメントに「削除」が出るか |
| プルリクエストを出す前 | なし | 自分 | 3つのタスクに `- [x]` が付いているか |

### 📝 ステップバイステップ

#### Step 1: 残っているタスクを確かめる

GitHubで機能イシューを開きます。タスク1とタスク2に `- [x]` が付いていて、タスク3だけが `- [ ]` のままになっているはずです。付いていなければ、ここで直しておいてください。

手元のブランチも確かめます。

```bash
# アプリのフォルダの中で実行する
cd ~/laravel-practice/14_hands-on/authorization-app-ai
git branch
```

`*` が `feature/issue-1-add-comments` に付いていれば、14-3-3の続きから進められます。アプリが止まっている場合は、`./vendor/bin/sail up -d` で起動しておいてください。

#### Step 2: タスク3の計画を立てさせる

Claude Codeを起動して、`/plan` を付けた依頼を送ります。14-3-3のタスク1・タスク2の依頼と同じ形です。書くのは、読ませる設計書・やること・触ってほしくないところ・どうなったら終わりかの4つです。

依頼を自分で組み立ててみてください。組み立てるときの材料は、上の 🧠 の表の1行目にあります。

#### Step 3: 計画を読んで、承認するか決める

3つの観点で読みます（14-3-3）。

- 触るファイルの一覧が、思っていたものと合っているか
- 設計書に無いものが入っていないか
- 順番が通っているか

引っかかったら、どの設計書のどこと食い違っているかを名指しして、立て直させてください。

#### Step 4: 実装させて、差分を読んで承認する

進め方は、14-3-3と同じく「1つずつ確かめながら進めさせる」を選びます。出てくる差分は、14-3-4で決めた4段の順に読んでください。

今回はとくに、消えた行に気をつけてください。投稿詳細画面のBladeには、タスク1とタスク2で作ったコメントの一覧と入力欄があります。削除ボタンを足すついでに、そこが書き換わっていないかを見ます。

一通り終わったら、ブラウザで `http://localhost/posts` を開き、投稿の詳細画面に入ります。自分が書いたコメントに「削除」が出ているか、押すと一覧から消えるかを確かめてください。

#### Step 5: コミットして、イシューに印を付ける

```bash
# アプリのフォルダの中で実行する
git status
git add app routes resources
git commit -m "Add #1: add comment deletion with policy"
```

`#1` は自分のイシューの番号に置き換えます。コミットできたら、機能イシューのタスク3の行を `- [x]` に変えてください。これで3つとも印が付きます。

#### Step 6: pushして、プルリクエストを開く

```bash
# アプリのフォルダの中で実行する
git push origin feature/issue-1-add-comments
```

GitHubでリポジトリを開くと、「Compare & pull request」ボタンが表示されます。クリックして、プルリクエストを作ります（2026年8月時点）。本文の形は、12-2-4「ハンズオン - GitHub連携演習」で書いたものと同じです。

```markdown
## 概要
Issue #1 に対応して、投稿へのコメント機能を追加しました。

## 変更内容
- commentsテーブルとCommentモデルを追加
- 投稿詳細画面（API-01）を追加
- コメントの登録（API-02）と削除（API-03）を追加
- TC-01からTC-05のテストを追加

Closes #1
```

`1` は自分のイシューの番号に置き換えます。

作ったら、「Files changed」を開いてみてください。3つのコミットの差分が、機能ひとまとまりとして並びます。承認しながら1つずつ見てきたものを、通しで見返せる形です。

**マージはしません。** ここまでで、Chapter 3は終わりです。

## 📖 進行例

> 💡 **進行例について**: AIとの開発は毎回違う流れになります。ここに示すのは一つの進行例です。あなたの画面と違っていても、チェックリストを満たしていれば正解です。

**1. 計画を頼む**

```text
/plan @docs/comment/api.md と @docs/comment/usecase.md を読んで、
実装タスク3「API-03 のコメント削除を実装する」の計画を立ててください。

- 消せるのは、そのコメントを書いた本人だけです（権限マトリクスの F-03）
- 投稿の編集・削除で使っている判定のしかたに、書き方をそろえてください
- 画面には、自分が書いたコメントにだけ「削除」を出してください
- 投稿の編集・削除の動きと、コメントの登録は変えないでください
- 自分のコメントの「削除」を押すと一覧から消えるところまでを、このタスクの完了とします
```

> 💡 この依頼では、`CommentPolicy` という名前を出さずに「投稿の編集・削除で使っている判定のしかたにそろえてください」と頼んでいます。どこに置くかはAIに考えさせて、そろっているかどうかを自分が差分で見る形です。

**2. 計画が返ってくる**

```text
Claude Code: （触るファイルの一覧と手順を示す。ポリシーの追加、コントローラーへの削除処理、
              ルートの追加、Bladeへの削除ボタンの追加、が並んでいる。
              そのあとに、どう進めるかを尋ねてくる）
```

**3. 1か所を指摘して、立て直させる**

一覧の中に `resources/views/posts/index.blade.php` が入っていました。投稿一覧の画面です。コメントの削除に、この画面は関係ありません。

```text
計画に resources/views/posts/index.blade.php が入っていますが、
削除ボタンを出すのは投稿詳細画面（SC-02）だけです。
一覧の画面は触らないで、計画を立て直してください。
```

立て直した計画からそのファイルが消えたので、承認しました。

**4. 差分を読んで承認する**

4つのファイルの差分が順に出てきました。変更されたファイルの一覧が計画のとおりであることを見てから、1つずつ読みます。投稿詳細画面のBladeでは、コメント1件ごとの表示の中に削除ボタンが足されているだけで、コメントの一覧と入力欄の行は消えていませんでした。

**5. ブラウザで確かめる**

`usera@example.com` でログインし、自分が書いたコメントに「削除」が出ることと、押すと一覧から消えることを確かめました。見たのは、受け入れ条件の前半までです。他人のコメントでの見え方と、URLを直接開いたときに403が返るかどうかは、Chapter 4で確かめます。

**6. コミットして、プルリクエストを開く**

コミットし、イシューのタスク3に `- [x]` を付け、pushして、プルリクエストを開きました。本文の最後は `Closes #1` です。マージはしていません。

<details>
<summary>📖 参考実装（自分の差分を読み終えてから開いてください）</summary>

判定を書いた1メソッドだけ載せます。あなたのAIが書いたコードは、これとは違う形になっているはずです。同じでなければいけないものではありません。

```php
// app/Policies/CommentPolicy.php
public function delete(User $user, Comment $comment): bool
{
    return $user->id === $comment->user_id;
}
```

いま操作している人のIDと、コメントに記録されている投稿者のIDを見比べています。10-3-5で自分の手で書いた `PostPolicy::update` と、同じ形です。

見比べるときは、行が同じかどうかではなく、**この判定がどこか1か所に書かれているか**を見てください。コントローラーの中に同じ条件が直接書かれていても、画面上の動きは同じになります。どちらが良いかという話は、14-4-2で扱います。

</details>

## 🚀 まとめ

- 設計書から実装タスクを作り、計画を立てさせ、差分を承認し、コミットし、プルリクエストを開くところまでを1周回しました。
- 承認する場所は自分で決めます。計画で1回、差分で数回、プルリクエストで1回です。
- 差分は順番を決めて読みます。とくに、消えた行はあなたが読まなければ誰も気づきません。
- プルリクエストは開いたまま置いておきます。

これでChapter 3は終わりです。コードは書き上がりましたが、正しいかどうかはまだ何も確かめていません。次のChapter 4では、テストを回し、コードを読み、受け入れ条件と突き合わせます。そのうえで、いま開いたプルリクエストをマージします。
