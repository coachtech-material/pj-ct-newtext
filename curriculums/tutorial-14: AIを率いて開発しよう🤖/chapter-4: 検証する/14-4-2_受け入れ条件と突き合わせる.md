# 14-4-2: 受け入れ条件と突き合わせる

## 🎯 このセクションで学ぶこと

- 受け入れ条件を1行ずつ画面で再現して、受け取ってよいかを判定できるようになる。
- 2つのアカウントを行き来して、同じ画面が見る人によって変わることを確かめられるようになる。
- 検証を通してからマージする、という順序で1機能を締められるようになる。

---

## 導入：テストが通っても、頼んだものができたとは限らない

テストが確かめているのは、テストに書いたことだけです。コメントは保存されるのに、投稿詳細のどこにも出ない。エラーは出るのに、文言が英語のまま。どちらもテストは通ります。

受け取ってよいかを決めるのは、いちばん最初に決めたことです。13-2-2「ユースケース図とユースケース記述」で受け入れ条件を「あとから確認するためのチェックリスト」として書き、Chapter 2 でそれを `docs/comment.md` に持ってきました。使うのはここです。

---

## 受け入れ条件は1行ずつ潰す

`docs/comment.md` の `## 受け入れ条件` に、次の4行が並んでいます。イシューに書いたものと同じ文です。

```markdown
- [ ] ログインした状態で投稿を1件開くと、その投稿の本文と、その投稿に付いたコメントの一覧が表示される
- [ ] 本文を入れてコメントを送ると、その投稿のコメント一覧に自分のコメントが増える
- [ ] 本文を空のままコメントを送ると、エラーが表示され、コメントは増えない
- [ ] 自分が書いたコメントは自分で消せて、他人のコメントは消せない
```

どの行にも、何をするとどうなるかが書いてあります。13-2-2の「〜すると、〜になる」の形にしたのは、**画面の前で1行ずつ再現できるようにするため**でした。「コメントを投稿できること」と書いてあったら、何をどう試せば確かめたことになるのかが、人によって変わります。ボタンの名前が入っていないので、AIが付けた呼び名が何であっても、この4行のまま判定できます。

確かめ方も1行ずつです。まとめて触って「だいたい動いた」で通さないでください。まとめて見ると、たいてい上の1行か2行を試したところで終わります。下の2行は、空のまま送る・他人のものに手を出すという、わざとやらないと踏まない道です。

### 設計書に書いた文言まで見る

3行目を確かめるときに、もう1段見るところがあります。**画面に出るメッセージ**です。

Laravelが最初から持っているメッセージは英語です。何も指定しなければ `The body field is required.` のような文が出ます。13-3-4「画面入力設計 - バリデーションとエラーメッセージ」で、入力チェック表にはルール、メッセージ一覧には画面に出す文言、と分けて書きました。突き合わせる相手は、`docs/comment.md` の `## 入力チェックとメッセージ` に書いた日本語のほうです。

エラーが出ること自体は合っていても、文言が違えばその行は満たされていません。直させるときは、こう頼みます。

```text
本文を空のまま送ったときに、英語のメッセージが出ています。
docs/comment.md の「入力チェックとメッセージ」に書いた日本語が出るようにしてください。
入力チェックのルールそのものは変えないでください。
```

> 💡 このお願いのポイントは、①設計書のどこと食い違っているかを名指ししていること ②直してほしくない範囲を書いていること、の2点です。②が無いと、日本語を出すためにルールごと書き換えられることがあります。文言をそのまま覚える必要はありません。

設計書と実物を突き合わせる、というのは、この作業のことです。

---

## 2つのアカウントを行き来する

4行目は、1つのアカウントでは確かめられません。「他人のコメント」を、自分で用意する必要があります。

シードで入れたアカウントが、配られたアプリに用意されています。

| アカウント | パスワード | 持っている投稿 |
|:--|:--|:--|
| `usera@example.com` | `password` | `/posts/1`・`/posts/2` |
| `userb@example.com` | `password` | `/posts/3`・`/posts/4` |

確かめるのは、**同じ画面が、見る人によって違って見えること**です。ユーザーAが書いたコメントは、ユーザーAの画面には消すための操作が付き、ユーザーBの画面には付きません。コメントの中身そのものは、どちらの画面にも出ます。ユーザーBの画面にユーザーAのコメントが出てこないなら、投稿とコメントのつなぎ方が設計書と違っています。

ついでに、**前からあった出し分けも見ておきます**。投稿一覧では、自分の投稿にだけ「編集」「削除」が出ます。ユーザーBでログインしたときにユーザーAの投稿へボタンが出ていたら、コメント機能を足した拍子に、関係のないところが触られています。

> ⚠️ **注意**: ブラウザのタブを変えても、ログインしている人は変わりません。必ずログアウトしてから、もう一方のアカウントでログインし直してください。

---

## 決めたとおりでない道も確かめる

受け入れ条件は、決めたとおりに使ったときの動きです。そうでない使われ方も、URLを直接開けば画面から試せます。

| 試すこと | どうなれば決めたとおりか |
|:--|:--|
| ログアウトした状態で、投稿詳細のURLを直接開く | ログイン画面へ移る |
| ログインした状態で、存在しない番号の投稿詳細を開く | 404の画面になる |
| ユーザーAでログインしたまま `http://localhost/posts/3/edit` を開く | 403の画面になる |

1行目は、受け入れ条件の1つ目に「ログインした状態で」と書いたことの裏側です。ログインしていない人が開いたときにどうなるかは、そちらには書かれていません。

2行目に「ログインした状態で」と付けたのにも理由があります。投稿詳細はログインした人だけが開ける画面なので、ログインしていないと、投稿があるかどうかを調べる前にログイン画面へ移されます。それでは404を確かめられません。シードで入っている投稿は4件なので、`http://localhost/posts/999` のように大きい番号を開けば、Laravelが404を返します。

3行目は、コメント機能とは関係のない確認です。`/posts/3` はユーザーBの投稿なので、ユーザーAが編集画面を開こうとすると `app/Policies/PostPolicy.php` の判定で止まります。14-1-1でアプリを動かしたときと同じ動きが、いまも残っていることを見ています。

他人のコメントを消そうとしたときだけは、画面から試す道がありません。他人のコメントに消すための操作が出ないからです。押せる道が残っていないかどうかは、テスト（14-4-1）と、判定がどこに置かれているかをコードで見ること（14-3-2）で確かめます。ボタンを消しただけで、処理の手前に判定が無ければ、URLを直接叩けば消せてしまいます。

## 検証を通してから、マージする

受け入れ条件が全部埋まったら、プルリクエストをマージします。マージもAIに頼めます。

```text
docs/comment.md の受け入れ条件を全部確かめました。
プルリクエストをマージして、ブランチを消してください。
そのあと、手元も main に切り替えて最新にしてください。
```

AIは `gh pr merge` を実行し、リモートとローカルのブランチを片づけて、`main` を最新にします。プルリクエストの本文に `Closes #1` が入っていれば、マージと同時に機能イシューも閉じます（12-2-1「イシュー駆動開発とは」）。閉じたかどうかは、自分で見られます。

```bash
# アプリのフォルダの中で実行する
gh issue view 1
```

`CLOSED` と表示されれば、イシューからブランチ、実装、検証、マージまでが1周しました。

順序には意味があります。Chapter 3 でプルリクエストを開いたあと、マージせずに置いてありました。もし確かめる前にマージしていたら、いま見つかった食い違いを直す相手は `main` です。ブランチを切り直し、プルリクエストを出すところからやり直すことになります。ブランチの上で直せば、直した記録も同じプルリクエストの中に残ります。

## 🏃 受け入れ条件を潰して、マージする

### Step 1: ユーザーAで開く

```bash
# アプリのフォルダへ移動して、アプリを起動する
cd ~/laravel-practice/post-app-practice
./vendor/bin/sail up -d
```

ブラウザで `http://localhost` を開き、`usera@example.com` / `password` でログインします。`docs/comment.md` も開いておいてください。確かめた行に、その場で `- [x]` を付けていきます。

### Step 2: 1つ目と2つ目を確かめる

投稿一覧から投稿を1件開きます。その投稿の本文と、コメントの一覧が出れば、1つ目は満たされています。

続けて本文を入れて送ります。戻ってきた画面のコメント一覧に、いま書いたものが増えていれば、2つ目も満たされています。並び順も見てください。設計書に「新しい順」と書いたのなら、いま書いたコメントがいちばん上に来ているはずです。

### Step 3: 3つ目を確かめる

本文を空のまま送信して、3つを見ます。

- エラーが表示されること
- コメントが増えていないこと
- 出ているメッセージが、設計書に書いた日本語であること

英語のメッセージが出ていたら、上に載せた頼み方で直させてから、この手順に戻ります。直させたときは、テストをもう一度回してから、コミットとpushもAIに頼んでください。手元にだけ残っている直しは、プルリクエストには入りません。

### Step 4: 4つ目を確かめる

まず、ユーザーAの画面で、自分が書いたコメントに消すための操作が出ていることを見ます。

そのままログアウトして、`userb@example.com` / `password` でログインし直し、同じ投稿をもう一度開きます。

- ユーザーAが書いたコメントの中身は出ていて、消すための操作は出ていないこと
- ユーザーB自身がコメントを書くと、そちらには消すための操作が出ること
- 投稿一覧では、ユーザーBの投稿にだけ「編集」「削除」が出ていること

ここまで見たら、4つ目に `- [x]` を付けられます。ユーザーBで書いたコメントは、消しておいて構いません。自分のコメントを消せることの確認にもなります。

### Step 5: 決めたとおりでない道を確かめる

上の表の3行を、順に試します。ログアウトした状態で試すのは1行目だけで、2行目と3行目はユーザーAでログインし直してから試してください。

### Step 6: マージする

`docs/comment.md` の受け入れ条件が、全部 `- [x]` になっていることを確かめます。`- [ ]` が残っている行は、まだ確かめていない行です。

そろったら、上に載せた依頼でマージまで頼みます。

このセクションが終わった時点で、次の5つを確かめてください。

- [ ] 受け入れ条件の4行を、すべてブラウザで再現して確かめた
- [ ] エラーのメッセージが、設計書に書いた日本語で出ていることを確かめた
- [ ] ユーザーAとユーザーBの両方でログインして、消すための操作の出方が変わることを確かめた
- [ ] 途中で直したところは、マージの前にpushまで済ませた
- [ ] `gh issue view 1` で、機能イシューが `CLOSED` になっていることを確かめた

---

## 💡 よくある間違い

**画面が出たことだけで合格にする**

投稿詳細が開き、コメントが増えた。ここで「動いた」と判断して、残りの行を飛ばす通し方です。飛ばされるのはいつも、決めたとおりに使わなかったときの行です。そこが抜けているアプリは、普通に触っているあいだは何も起きません。

**自分のアカウントだけで確かめる**

ログインし直すのは面倒ですが、権限に関わる決めごとは1人分の画面には現れません。ユーザーAの画面には、ユーザーAが見てよいものしか出ないからです。

**確かめる前にマージする**

プルリクエストが開いたところで、仕事が終わった気持ちになります。マージしたあとに食い違いが見つかると、直す相手は `main` です。順番を守るほうが速く終わります。

---

## ✨ まとめ

- 受け入れ条件は「〜すると、〜になる」の形で書いてあるので、画面の前でそのまま再現できます。まとめて触って通しません。
- エラーが出ることと、設計書に書いた文言が出ることは別です。文言まで見て、違っていれば直させます。
- 他人から見た画面は、他人としてログインしないと出てきません。同じコメントに、消すための操作が付く画面と付かない画面ができます。
- 決めたとおりでない道は、ログインしていない状態・存在しない番号・他人の投稿の3つを画面から試せます。他人のコメントを消す道だけは画面に無いので、テストとコードで確かめます。
- マージは検証を全部通してからです。マージもAIに頼め、`Closes #1` が入っていれば機能イシューも一緒に閉じます。
