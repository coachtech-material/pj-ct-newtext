# 14-4-3: 動かして確かめる - 受け入れ条件との突き合わせ

## 🎯 このセクションで学ぶこと

- 受け入れ条件を1行ずつ潰して、受け取ってよいかを判定できるようになる。
- 2つのアカウントを行き来して、権限が効いていることを確かめられるようになる。
- 検証を全部通してからマージする、という順序を自分の言葉で言えるようになる。

---

## 導入：受け取ってよいかを決める

テストが通り、コードも読みました。残っているのは、いちばん最初に決めたことと突き合わせる作業です。

13-2-2「ユースケース図とユースケース記述」で受け入れ条件を書いたとき、これは「あとから確認するためのチェックリスト」だと書かれていました。14-2-4では、その4行を機能イシューの `## 受け入れ条件` にそのままコピーしました。同じ文が2か所にあることに意味がある、と書いたのは、この場面のためです。

いま、その4行はまだ `- [ ]` のまま残っています。ここで1行ずつ潰します。全部に `- [x]` が付いたら、コメント機能を受け取ってよい、という判定になります。

## 受け入れ条件は1行ずつ潰す

`docs/comment/usecase.md` に書いた受け入れ条件は、次の4件です。

```markdown
- [ ] 投稿一覧で「詳細」を押すと、その投稿の本文とコメントの一覧が表示される
- [ ] 本文を入れて「コメントする」を押すと、その投稿のコメント一覧に自分のコメントが増える
- [ ] 本文を空のまま「コメントする」を押すと、エラーが表示され、コメントは増えない
- [ ] 自分が書いたコメントには「削除」が出て、押すと一覧から消える。他人のコメントには「削除」が出ない
```

どの行も「〜すると、〜になる」の形で書いてあります。この形にしたのは、**画面の前で1行ずつ再現できるようにするため**でした。「コメントを投稿できること」と書いてあったら、何をどう試せば確かめたことになるのかが、人によって変わります。

だから、確かめ方も1行ずつです。4行をまとめて「だいたい動いた」で通さないでください。まとめて見ると、たいてい1つ目と2つ目だけを試して終わります。3つ目と4つ目は、わざとうまくいかない使い方をしないと通らないので、自然に触っているだけでは踏みません。

### 設計書に書いた文言まで見る

3つ目の行を確かめるときに、もう1段見るところがあります。**画面に出るエラーの文言**です。

`docs/comment/screen.md` のメッセージ一覧に、本文が空のときのメッセージを日本語で書きました。14-3-3の依頼にも、エラーメッセージを設計書のとおり日本語で出してほしい、という1行を入れてあります。文言そのものの置き場所はメッセージ一覧です。13-3-3「画面入力設計 - バリデーションとエラーメッセージ」で、入力チェック表は必須や文字数などのルール、メッセージ一覧は画面に出す文言、と分けました。突き合わせる相手はメッセージ一覧のほうです。

ここで英語のメッセージが出ていたら、その1行は満たされていません。エラーが表示されること自体は合っていても、設計書に書いた文言とは違うからです。直させるときは、次のように頼みます。

```text
本文を空のまま送ったときに、英語のメッセージが出ています。
docs/comment/screen.md のメッセージ一覧に書いた日本語が出るように直してください。
入力チェックのルールそのものは変えないでください。
```

> 💡 このお願いのポイントは2点です。①設計書のどこと食い違っているかを名指ししている ②直してほしくない範囲（ルール本体）を書いている。②が無いと、メッセージを出すためにルールごと書き換えられることがあります。文言をそのまま覚える必要はありません。

設計書と実物を突き合わせる、というのは、こういう作業のことです。

## 2つのアカウントを行き来する

4つ目の行は、1つのアカウントでは確かめられません。「他人のコメントには『削除』が出ない」の「他人」を、自分で用意する必要があります。

10-3-5「認可機能 - ハンズオン演習」で、自分の投稿と他人の投稿を行き来して確かめたのと同じやり方です。使うアカウントも同じ2つです。

| アカウント | パスワード | 持っている投稿 |
|:--|:--|:--|
| `usera@example.com` | `password` | `/posts/1`・`/posts/2` |
| `userb@example.com` | `password` | `/posts/3`・`/posts/4` |

この2人は、`./vendor/bin/sail artisan migrate --seed` で入れたシードデータです。どちらの目で見ても、同じ投稿詳細画面を開けます。

確かめるのは、**同じ画面が、見る人によって違って見えること**です。ユーザーAが書いたコメントは、ユーザーAの画面には「削除」が付き、ユーザーBの画面には付きません。14-3-5では前半だけを見て、後半をChapter 4に残してありました。ここで残りを見ます。

> ⚠️ **注意**: ログアウトせずにブラウザのタブだけを変えても、同じ人としてログインしたままです。必ずログアウトしてから、もう一方のアカウントでログインし直してください。

## 決めたとおりでない道も確かめる

受け入れ条件の4行は、決めたとおりに使ったときの動きです。`docs/comment/behavior.md` の例外一覧には、そうでない使い方を書きました。自分の例外一覧を開いて、1行ずつ、ブラウザで試せる行と試せない行に仕分けてください。ここで新しく試すのは、次の2つです。

| 試すこと | どうなれば合っているか |
|:--|:--|
| ログアウトした状態で `http://localhost/posts/1` を開く | ログイン画面へ移る |
| ログインした状態で、存在しない投稿の番号（`http://localhost/posts/999`）を開く | 404の画面になる |

2つ目に「ログインした状態で」と書いたのには理由があります。投稿詳細画面は、ログインした人しか開けないルートです。ログインしていないと、投稿が存在するかどうかを調べる前にログイン画面へ移されるので、404は出ません。

本文が空のときの入力エラーは、受け入れ条件の3つ目ですでに確かめました。画面から試せないのは、他人のコメントを消そうとしたときの403だけです。他人のコメントには「削除」が出ないので、ブラウザから押す道がありません。自分の例外一覧の行数が違っていたら、自分の一覧を基準に読み替えてください。

押せる道が残っていないかどうかは、14-4-2でコードを読んで確かめました。ボタンを消すだけでなく、処理の手前に判定が置かれているかを見た、あのところです。**画面から試せないものは、コードを読んで確かめる。** これが、14-4-1で「どの行をどの手段で確かめるかは人が決める」と書いたことの中身です。テスト観点表の `TC-06` は、判定の置き場所をコードで見たこと（14-4-2）と、「削除」の出方をブラウザで見たこと（このあとのStep 4）の2つで確かめ終わります。

そのうえで、同じ形の確認を投稿のほうでは画面からできます。ユーザーAでログインしたまま `http://localhost/posts/3/edit` を開くと、403になります。10-3-5で確かめたのと同じ動きです。コメント機能を足したあとも、そこが壊れていないことの確認になります。

> 💡 **TIP**: 14-4-1で、`TC-02` はブラウザだと違う結果になる、と書きました。ログインせずにコメントを送ろうとすると、ブラウザでは419になります。10-6-1「CSRF保護」で見た `419 Page Expired` です。コメントを登録する処理までたどり着く前に、CSRFの検査で止まります。テストのほうは302で、ログイン画面へ移されています。どちらもコメントは登録されないので、決めたとおりです。ブラウザで確かめるのは、画面を開くほう（上の表の1行目）にしてください。

## 検証を全部通してから、マージする

3つの検証が終わったら、プルリクエストをマージします。手順は12-3-5「ハンズオン - コードレビュー演習」で通したものと同じです。

順序には意味があります。14-3-5でプルリクエストを開いたとき、マージせずに置いたままにしました。あのとき、テストの回し方も、レビューの観点も、受け入れ条件との突き合わせ方も、まだ扱っていませんでした。確かめる手段を持たないままマージしていたら、直す場所は `main` になっていたはずです。

ブランチの上で直せば、直した記録もそのプルリクエストの中に残ります。14-4-1でテストを直し、14-4-2でレビューの指摘を直し、いま受け入れ条件で見つかったところを直しました。これが全部、1本のプルリクエストの中に収まっています。

マージすると、本文に書いた `Closes #1` が効いて、機能イシューが自動で閉じます（12-2-1「イシュー駆動開発とは」）。閉じたことまで見て、この機能はできあがりです。

## 🏃 受け入れ条件を潰して、マージする

> 🔥 ここからは、AIに実装を任せて構いません。ただし「任せる」と「丸投げ」は違います。何を作るかは設計書で自分が決め、出てきたものはテスト・動作確認・コードレビューで自分が検証します。品質の責任は、AIではなくあなたが握ります。

1. 【自分】アプリを起動して、ユーザーAでログインする
2. 【自分】受け入れ条件の1つ目と2つ目を確かめる
3. 【自分】3つ目を確かめる（文言まで見る）
4. 【自分】ユーザーBでログインし直して、4つ目を確かめる
5. 【自分】決めたとおりでない道を確かめる
6. 【自分】イシューに印を付けて、プルリクエストをマージする

### Step 1: ユーザーAでログインする

```bash
# アプリのフォルダの中で実行する
cd ~/laravel-practice/14_hands-on/authorization-app-ai
./vendor/bin/sail up -d
```

ブラウザで `http://localhost` を開き、`usera@example.com` / `password` でログインします。

手元のイシューも開いておいてください。確かめた行に、その場で `- [x]` を付けていきます。

### Step 2: 1つ目と2つ目を確かめる

投稿一覧で「詳細」を押します。その投稿の本文と、コメントの一覧が出れば、1つ目は満たされています。

続けて、本文を入れて「コメントする」を押します。押したあとに戻ってきた画面のコメント一覧に、いま書いたものが増えていれば、2つ目も満たされています。

並び順も見てください。`docs/comment/screen.md` に「新しい順」と書いたのなら、いま書いたコメントがいちばん上に来ているはずです。

### Step 3: 3つ目を確かめる

本文を空のまま「コメントする」を押します。

- エラーが表示されること
- コメントが増えていないこと
- 出ているメッセージが、`screen.md` のメッセージ一覧に書いた日本語であること

3つ目まで見てください。英語のメッセージが出ていたら、上に載せた頼み方で直させてから、もう一度この手順に戻ります。

直させた場合は、テストをもう一度回してから、コミットしてpushします。

```bash
# アプリのフォルダの中で実行する
./vendor/bin/sail artisan test
git status
git add .
git commit -m "Fix #1: show validation messages in Japanese"
git push origin feature/issue-1-add-comments
```

`#1` は自分のイシューの番号に置き換えます。プルリクエストは開いたままなので、この直しもその中に入ります。Step 4とStep 5で何かを直したときも同じです。マージする前に、直したものが**pushまで終わっている**ことを確かめてください。手元にだけ残っている直しは、プルリクエストには入りません。

### Step 4: ユーザーBでログインし直す

まず、ユーザーAの画面で、自分が書いたコメントに「削除」が出ていることを見ます。ここまでは14-3-5で確かめました。

そのままログアウトして、`userb@example.com` / `password` でログインし直します。同じ投稿の詳細画面をもう一度開いてください。

- ユーザーAが書いたコメントに、「削除」が出ていないこと
- ユーザーB自身がコメントを書くと、そちらには「削除」が出ること

両方を見たら、4つ目に `- [x]` を付けられます。ユーザーBで書いたコメントは、押して消しておいて構いません。

### Step 5: 決めたとおりでない道を確かめる

3つ試します。ログアウトした状態で試すのは、1つ目だけです。

1. ログアウトして、`http://localhost/posts/1` を開く。ログイン画面へ移れば、決めたとおりです
2. ユーザーAでログインし直して、`http://localhost/posts/999` を開く。404の画面になれば、決めたとおりです
3. そのまま `http://localhost/posts/3/edit` を開く。403になれば、10-3-5で作った認可が、いまも効いています

`http://localhost/posts/999` は、投稿が4件しかないので存在しません。番号を大きくして開くと、Laravelが404を返します。

### Step 6: イシューに印を付けて、マージする

GitHubで機能イシューを開き、`## 受け入れ条件` の4行がすべて `- [x]` になっていることを確かめます。まだ `- [ ]` の行が残っていたら、その行はまだ確かめていません。Step 2に戻ってください。

4行そろったら、プルリクエストを開きます。ここまでに直したところがある場合は、「Files changed」にその直しが出ていることを先に確かめてください。出ていなければ、pushがまだ済んでいません。

確かめたら、マージします（2026年8月時点）。

1. 「Conversation」タブをクリックして、プルリクエストのメイン画面に戻る
2. 「Merge pull request」ボタンをクリックする
3. 「Confirm merge」をクリックする
4. 「Delete branch」をクリックして、ブランチを削除する

そのあと、手元も `main` にそろえます。

```bash
# アプリのフォルダの中で実行する
git switch main
git pull origin main
git branch -d feature/issue-1-add-comments
```

最後に、「Issues」タブを開いて、機能イシューが `Closed` になっていることを確かめてください。

このセクションが終わった時点で、次の6つを確かめてください。

- [ ] 受け入れ条件の4行すべてを、ブラウザで実際に触って確かめた
- [ ] ユーザーAとユーザーBの両方でログインして、「削除」の出方が変わることを確かめた
- [ ] ログインしていない状態で投稿詳細画面を開くと、ログイン画面へ移ることを確かめた
- [ ] 途中で直したところがあれば、マージの前にコミットしてpushした
- [ ] 機能イシューの `## 受け入れ条件` が、4行とも `- [x]` になっている
- [ ] プルリクエストがマージされ、機能イシューが `Closed` になっている

## 💡 よくある間違い

**画面が出たことだけで合格にする**

いちばん多い通し方です。投稿詳細画面が開き、コメントが増えた。ここまでで「動いた」と判断して、残りの2行を飛ばしてしまいます。飛ばした2行は、決めたとおりに使わなかったときの動きです。そこが抜けているアプリは、普通に触っているあいだは何も起きません。

**自分のアカウントだけで確かめる**

ログインし直すのは面倒です。ただし、権限に関わる決めごとは、1人分の画面には現れません。ユーザーAの画面には、ユーザーAが見てよいものしか出ないからです。「他人には出ない」ことは、他人としてログインしないと見えません。

**確かめる前にマージする**

プルリクエストを開いたところで、仕事が終わった気持ちになります。マージしてしまうと、次に直すときの相手は `main` です。ブランチを切り直し、もう一度プルリクエストを出すところからやり直すことになります。順番を守るほうが速く終わります。

## ✨ まとめ

- 受け入れ条件は、画面の前で1行ずつ再現して潰します。まとめて「だいたい動いた」で通しません。
- エラーが出ることだけでなく、設計書に書いた文言が出ているかまで見ます。ここが、設計書と実物を突き合わせるということです。
- 権限に関わる決めごとは、2つのアカウントを行き来しないと確かめられません。
- 画面から試せないものは、コードを読んで確かめます。どの行をどの手段で確かめるかは、人が決めます。
- テストを回し、コードを読み、受け入れ条件と突き合わせてから、マージします。確かめる前にマージしていたら、直す場所は `main` になっていました。

これでコメント機能はできあがりました。設計書を書き、実装させ、3つの手段で検証し、`main` に入れるところまで1周しました。

次のセクション（14-4-4）では、うまくいかなかったときの話をします。ここまでは通った前提で進んできましたが、実際にはエラーで止まるほうが普通です。
