# 14-4-1: テストで検証する - まず機械に聞く

## 🎯 このセクションで学ぶこと

- AIに書かせたテストを自分の手で回して、結果を読めるようになる。
- 失敗ではない表示と、本当の失敗を見分けられるようになる。
- テスト観点表のどの行を、どの手段で確かめるのかを自分で決められるようになる。

---

## 導入：書けたものを、まだ何も確かめていない

Chapter 3で、コメント機能のコードが書き上がりました。プルリクエストは開いたまま、マージせずに置いてあります。このChapter 4は、それを確かめる章です。機械に聞き、自分の目で読み、動かして受け入れ条件と突き合わせ、そのうえでプルリクエストをマージします。

14-1-4で、信じてよいのはテスト・コードを読むこと・受け入れ条件との突き合わせを通ったものだけだ、と決めました。ここから、その3つを順に実際にやります。

順番には理由があります。**機械に判定できることから先に済ませます。** テストは、何度回しても同じ精度で同じ判定を返します。人の目はそうはいきません。同じコードを3回読めば、3回目がいちばん雑になります。ですから、機械が合否を出せるものは機械に出させて、人の目は機械に判定できないところ（設計書のとおりに作られているか、権限が効いているか、受け入れ条件を満たしているか）のために取っておきます。

## まず機械に聞く

14-3-3で、タスク2の依頼にこの1行を入れました。

```text
- test.md の TC-01 から TC-05 までのテストを、tests/Feature/ に一緒に書いてください
```

このとき書かれたテストは、まだ1度も回していません。差分を読んで「書かれていること」は確かめましたが、「通ること」は確かめていません。

この2つは別のものです。テストのファイルがあることと、そのテストが通ることのあいだには、何の関係もありません。書かれたテストが最初から落ちている、ということも起こります。

そして、回すのはあなたです。AIに「テストを回しておいてください」と頼んで「全部通りました」という返事を受け取るのは、確かめたことになりません。14-1-4で決めたとおり、証拠になるのは自分の手で回したときの実行結果です。

---

## テストを回す

アプリのフォルダで、次のコマンドを打ちます。10-5-3「単体テストの基礎」で打ったのと同じコマンドです。実際に打つのはこのあとの実践のStep 1なので、ここでは形だけ見ておいてください。

```bash
# ここでは読むだけ。打つのは実践のStep 1です
./vendor/bin/sail artisan test
```

9-1-2で `sail` の短縮名を登録した方は、`sail artisan test` でも同じです。

1本だけ回し直したいときは、10-5-3で使った `--filter` が使えます。

```bash
# ここでは読むだけ。打つのは実践のStep 1です
./vendor/bin/sail artisan test --filter CommentTest
```

`CommentTest` のところは、AIが付けたテストクラスの名前に置き換えてください。`tests/Feature/` を開けば分かります。

> 💡 **TIP**: このアプリでは `phpunit.xml` を触りません。テスト用のデータベースは、Sailを起動した時点で用意されています。

## 実行結果の読み方

10-5-3で、`PASS` と `✓` と `Tests: 1 passed` の読み方を確かめました。今回の結果には、そこには無かったものが混ざります。全部通ったときは、次のような画面になります。

```text
   DEPR  Tests\Feature\CommentTest
  ! user can post comment → Constant PDO::MYSQL_ATTR_SSL_CA is deprecated // config/database.php:62    0.03s
  ! guest cannot post comment → Constant PDO::MYSQL_ATTR_SSL_CA is deprecated // config/database.php:62
  ✓ comment body is required
  ✓ comment body of 500 characters is accepted
  ✓ comment body of 501 characters is rejected

  Tests:    2 deprecated, 3 passed (5 assertions)
  Duration: 0.06s
```

テストの名前も、行数も、秒数も、AIが書いたテストによって変わります。自分の画面と1文字ずつ見比べる必要はありません。見るのは形のほうです。

10-5-3のときと違うのは、3か所です。

- クラス名の左が `PASS` ではなく `DEPR` になっています
- テスト名の左に `✓` ではなく `!` が付いた行があり、その右に `→` で `Constant PDO::MYSQL_ATTR_SSL_CA is deprecated` というメッセージが続いています
- いちばん下の `Tests:` の行に、`passed` と並んで `deprecated` という語が出ています

押さえることは3つです。

**1. `deprecated` は失敗ではありません**

`deprecated` は「この書き方は将来なくなります」という予告です。テストの合否とは関係がありません。行の左に付いた `!` も、その予告が出たことを示す印であって、落ちた印ではありません。出ている原因は、このアプリが動いているPHPの版と、Laravelの設定ファイルの書き方の組み合わせにあります。あなたが書いたコードにも、AIが書いたコードにも原因はありません。PHPの版によっては、`DEPR` も `!` も1件も出ないことがあります。出ても出なくても、見るところは変わりません。

**2. 消す作業はしません**

`phpunit.xml` をどう書き換えても、この表示は消えません。消そうとして設定ファイルを触ると、テストそのものが動かなくなるほうが先に起きます。出たままで構いません。

**3. 見るのは `failed` の有無です**

合否を決めているのは、`failed` という語が出ているかどうかだけです。`failed` が0であれば、書かれたテストは全部通っています。`deprecated` が何件出ていても、そこは見ません。

> ⚠️ **注意**: `!` が並んだ画面を見て、失敗したと思って手を止める方が必ず出ます。`!` は目立ちますが、探すのは `failed` です。10-5-7「テスト - ハンズオン演習」にも、`DEPR` と表示されてもテストは正常に通っている、という注意書きがありました。同じ表示のことです。

## 観点表と突き合わせる

`failed` が0でも、まだ終わりではありません。**通ったテストが、確かめたかったことを確かめているか**は、別の話だからです。

`docs/comment/test.md` を開いて、テスト観点表と `tests/Feature/` の中身を見比べます。見るのは2つです。

- `TC-01` から `TC-05` の5つが、それぞれテストとして書かれているか
- 観点表に無いテストが増えていないか

`test.md` は、実装より先にあなたが書いたものです。だから、テストのほうを正として観点表を読むのではなく、**観点表のほうを正としてテストを読みます**。テストの中身が観点と合っているかどうかの見方は、次の14-4-2で扱います。

### 観点表の行を、どの手段で確かめるか

観点表は、`TC-01` から `TC-06` までの6行になっているはずです。行数が違っていたら、自分の観点表のほうを基準に読み替えてください。テストになっているのは、そのうち5行です。残った `TC-06`（他人のコメントを削除しようとすると403になる）は、14-3-3の依頼で「今回は書かないでください」と外しました。

観点表の行が全部、自動テストになるとは限りません。**どの行をどの手段で確かめるかは、人が決めます。**

`TC-06` を自動テストにしないのは、権限が効いていることをテストで確かめる書き方を、この教材ではまだ扱っていないからです。それはこの先で扱います。代わりに、この行は次の2つで確かめます。

| 確かめ方 | 扱うセクション |
|:--|:--|
| コードを読んで、「消せるのは書いた本人だけ」の判定がどこに書かれているかを見る | 14-4-2 |
| ブラウザで、2つのアカウントを行き来して、「削除」の出方を見る | 14-4-3 |

403そのものは、ブラウザから出す道がありません。他人のコメントには「削除」が出ないからです。押されたときに止まるかどうかは、判定がどこに置かれているかをコードで見て確かめます。

テストで確かめる、読んで確かめる、動かして確かめる。この3つは、どれかがあれば残りが要らなくなるものではありません。観点表の1行ずつに、どの手段を割り当てるのかを決めるのが、あなたの仕事です。

> 💡 **TIP**: `TC-02` が確かめているのは、ログインしていない人がコメントを登録できないことです。同じことをブラウザで試すと、テストとは違う結果になります。ブラウザでの確かめ方は14-4-3で扱います。

## 落ちたときにすること

`failed` が出たときの手当てです。1本落ちると、画面はこうなります。

```text
   FAIL  Tests\Feature\CommentTest
  ! user can post comment → Constant PDO::MYSQL_ATTR_SSL_CA is deprecated // config/database.php:62    0.03s
  ! guest cannot post comment → Constant PDO::MYSQL_ATTR_SSL_CA is deprecated // config/database.php:62
  ✓ comment body is required
  ✓ comment body of 500 characters is accepted
  ⨯ comment body of 501 characters is rejected
  ───────────────────────────────────────────────────────────
   FAILED  Tests\Feature\CommentTest > comment body of 501 characters is rejected
  Failed asserting that actual size 1 matches expected size 0.

  at tests/Feature/CommentTest.php:31

  Tests:    2 deprecated, 1 failed, 2 passed (5 assertions)
  Duration: 0.05s
```

落ちた印は、テスト名の左の `⨯` です。その下に区切り線が引かれて、落ちた1本の中身が続きます。`at` の行の下には、落ちた行のまわりのコードも数行出ますが、ここでは省いています。どのテストが、どんな理由で落ちるかは、そのときどきで変わります。見る場所のほうを覚えてください。

**1. 落ちた行だけを渡す**

AIに渡すのは、`FAILED` の行から `at tests/Feature/...` の行までです。上の画面で言えば、テスト名（`comment body of 501 characters is rejected`）と、落ちた理由（`Failed asserting that actual size 1 matches expected size 0.`）と、落ちた場所（`at tests/Feature/CommentTest.php:31`）の3つが、この数行に入っています。通ったテストの行や `!` の行は、直すのに要りません。

**2. 直させたら、もう一度自分で回す**

「直しました」という返事は結果ではありません。もう一度 `./vendor/bin/sail artisan test` を打って、`failed` が消えたことを自分の目で見てください。

**3. 落ちたテストのほうを消さない**

いちばんやってはいけないのがこれです。テストが落ちているのは、実装かテストのどちらかが `test.md` の観点と食い違っているからです。テストを消せば `failed` は消えますが、食い違いは残ったままになります。緩めるのも同じです。「500文字以内」を「1000文字以内」に書き換えれば `TC-05` は通りますが、それはもう `test.md` に書いた観点ではありません。

直した場合は、コミットしてpushします。プルリクエストには自動で反映されます（12-2-3「プルリクエストの作成とレビュー」）。

## 🏃 テストを回して、観点表と突き合わせる

> 🔥 ここからは、AIに実装を任せて構いません。ただし「任せる」と「丸投げ」は違います。何を作るかは設計書で自分が決め、出てきたものはテスト・動作確認・コードレビューで自分が検証します。品質の責任は、AIではなくあなたが握ります。

1. 【自分】アプリを起動して、テストを回す
2. 【自分】結果を読んで、`failed` があるかどうかを見る
3. 【自分】`tests/Feature/` を開いて、`TC-01` から `TC-05` に対応しているかを見る
4. 【自分⇄AI】落ちていたら直させて、もう一度回す

### Step 1: テストを回す

アプリが止まっている場合は、Docker Desktop（またはDocker Engine）を起動してから、Sailを立ち上げます。

```bash
# アプリのフォルダの中で実行する
cd ~/laravel-practice/14_hands-on/authorization-app-ai
./vendor/bin/sail up -d
./vendor/bin/sail artisan test
```

ブランチは `feature/issue-1-add-comments` のままです。`git branch` を打って、`*` が付いていることを確かめておいてください。

### Step 2: 結果を読む

画面をいちばん下までスクロールして、`Tests:` で始まる行を見ます。`failed` という語が出ていなければ、書かれたテストは全部通っています。

`!` の付いた行と `Constant PDO::MYSQL_ATTR_SSL_CA is deprecated` は、出ていて正常です。1件も出ていなくても構いません。どちらでも、ここで止まらないでください。

### Step 3: 観点表と突き合わせる

`docs/comment/test.md` と、`tests/Feature/` に増えたテストのファイルを、両方開きます。

`TC-01` から `TC-05` の5行が、5つのテストメソッドとして書かれているかを1行ずつ確かめてください。14-3-3の依頼で「テストメソッドの名前は `test_` で始めてください」と書いたので、10-5-3で学んだ形で並んでいるはずです。

観点表に無いテストが増えていた場合は、そのテストが何を確かめているのかを読んでください。読んで意味のあるものなら、`test.md` のほうに行を足します。意味が分からないものは、消させて構いません。

### Step 4: 落ちていたら直させる

`failed` が出ていたら、その行をコピーしてAIに渡します。

```text
テストを回したら、次の1本が落ちました。原因を調べて直してください。
テストのほうは書き換えないでください。test.md に書いた観点のとおりです。

（FAILED の行から at tests/Feature/... の行までを貼る）
```

> 💡 このお願いのポイントは2点です。①落ちた1本の情報だけを渡していること ②テストを書き換えないでほしいことを先に書いていること。②を書かないと、実装ではなくテストのほうを実装に合わせて直されることがあります。文言をそのまま覚える必要はありません。

直させたら、Step 1のコマンドをもう一度打ちます。`failed` が消えたら、コミットしてpushしてください。

```bash
# アプリのフォルダの中で実行する
git status
git add .
git commit -m "Fix #1: fix failing comment tests"
git push origin feature/issue-1-add-comments
```

`#1` は自分のイシューの番号に置き換えます。落ちたテストが1本も無かった場合は、この手順は要りません。

このセクションが終わった時点で、次の3つを確かめてください。

- [ ] `./vendor/bin/sail artisan test` を自分で実行して、`failed` が0であることを自分の目で見た
- [ ] `test.md` の `TC-01` から `TC-05` が、それぞれテストとして書かれていることを確かめた
- [ ] `TC-06` をどの手段で確かめるのかを、自分の言葉で言える

## 💡 よくある間違い

**実行結果を丸ごと貼って、「直して」と頼む**

落ちたのが1本でも、画面に出た数十行をそのまま貼ると、通っているテストまで手を入れられることがあります。渡す量を自分で選ぶ、というのは14-2-2で決めたとおりです。落ちた行を探すのが面倒に感じるかもしれませんが、探すこと自体が、どこが落ちたのかを自分で把握する作業になります。

**テストが通ったので、動かして確かめるのを省く**

テストが確かめているのは、`test.md` に書いた5つの観点だけです。受け入れ条件は別に4件あり、そちらはまだ1つも確かめていません。機械に聞くのは検証の1段目で、全部ではありません。

**`--filter` で1本だけ回して、それで終わりにする**

直したい1本だけを回すのは速いのですが、直した拍子に別のテストが落ちることがあります。1本直したら、最後に必ず `--filter` を外して全部回してください。

## ✨ まとめ

- テストのファイルがあることと、テストが通ることは別です。回すのは自分で、AIの「通りました」は結果ではありません。
- 実行結果には `!` と `Constant PDO::MYSQL_ATTR_SSL_CA is deprecated` が混ざります。失敗ではないので、消す作業もしません。
- 合否を決めるのは `failed` の有無だけです。
- `failed` が0でも終わりではありません。`test.md` の観点表を正として、`TC-01` から `TC-05` が書かれているかを見比べます。
- 観点表の行が全部、自動テストになるとは限りません。どの行をどの手段で確かめるかは、人が決めます。

次のセクション（14-4-2）では、2段目に進みます。テストが通ったコードを、自分の目で読みます。テストが通ったことは、正しいことの証明ではありません。
