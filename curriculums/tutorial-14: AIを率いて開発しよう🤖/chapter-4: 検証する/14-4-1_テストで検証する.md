# 14-4-1: テストで検証する

## 🎯 このセクションで学ぶこと

- 実装と一緒に書かせたテストを回して、実行結果のどこを見ればよいかが分かるようになる。
- テスト用のデータベースが空であることから出るエラーを、自分で直せるようになる。
- 設計書に書いた観点を、テストで確かめるものと、別の手段で確かめるものに仕分けられるようになる。

---

## 導入：目で全部読むやり方は、続かない

コメント機能のコードとテストは書き上がり、プルリクエストは開いたまま置いてあります。ここからは、受け取ってよいかを確かめる作業です。

確かめる手段のうち、テストだけは何度回しても同じ判定を返します。人の目はそうはいきません。同じコードを3回読めば、3回目がいちばん雑になります。機械が合否を出せるところは機械に出させて、読む力のほうは、機械に判定できないところ（設計書のとおりに作られているか、決めた文言が出ているか）に残しておきます。

検証の1手目がテストなのは、この順番のためです。

---

## テストを回す

アプリのフォルダで、10-5-3「単体テストの基礎」で打ったのと同じコマンドを使います。

```bash
# アプリのフォルダへ移動して、テストを回す
cd ~/laravel-practice/post-app-practice
./vendor/bin/sail artisan test
```

9-1-2で `sail` の短縮名を登録した方は、`sail artisan test` でも同じです。

1本だけ回し直したいときは、10-5-3で使った `--filter` を付けます。`CommentTest` のところは、AIが付けたテストクラスの名前に置き換えてください。`tests/Feature/` を開けば分かります。

```bash
# アプリのフォルダの中で実行する
./vendor/bin/sail artisan test --filter CommentTest
```

## テスト用のデータベースには、テーブルがありません

最初の1回で、次のように落ちることがあります。

```text
   FAIL  Tests\Feature\CommentTest
  ⨯ user can post comment                                              0.13s
  ──────────────────────────────────────────────────────────────────────
   FAILED  Tests\Feature\CommentTest > user can post comment  QueryException
  SQLSTATE[42S02]: Base table or view not found: 1146 Table 'testing.users'
  doesn't exist (Connection: mysql, SQL: insert into `users` ...)
```

`testing` は、テスト専用のデータベースの名前です。`phpunit.xml` に接続先を `testing` へ切り替える指定が入っていて、テストのときだけそちらを見にいきます。開発しながら入れたデータを、テストが消してしまわないための作りです。

Sailはこのデータベースを起動時に用意しますが、**中は空**です。`./vendor/bin/sail artisan migrate --seed` で作ったテーブルは開発用のほうに入っているので、`testing` には1枚もありません。それで「`testing.users` というテーブルが無い」と言われています。

直すのは、テストクラスの2行です。10-5-5「データベーステスト」で使った `RefreshDatabase` を付けます。

```php
// tests/Feature/CommentTest.php
use Illuminate\Foundation\Testing\RefreshDatabase;
use Tests\TestCase;

class CommentTest extends TestCase
{
    use RefreshDatabase;

    // ...
}
```

1行目で、Laravelが用意している仕組みを読み込みます。クラスの中に書いた `use RefreshDatabase;` が本体で、これを付けると、テストを回すときにテスト用データベースへテーブルを作り直し、テスト1本が終わるたびに、そのテストが書き込んだ内容を元へ戻します。

ここで気をつけることが1つあります。テーブルは作られますが、シードは動きません。`usera@example.com` も、シードで入れた投稿4件も、テスト用データベースにはいません。テストで使うデータは、テストの中で作ります。

```php
// tests/Feature/CommentTest.php の中
$user = User::factory()->create();
```

配られたアプリに用意されているファクトリ（テスト用のデータを作る型。10-5-2）は `UserFactory` だけです。投稿やコメントをまとめて作りたいときは、そのファクトリもAIに作らせます。

> 💡 **TIP**: このエラーを先に避けるなら、実装を頼むときの依頼に「データベースを使うテストには `RefreshDatabase` を付けてください」の1行を入れておきます。付いていないまま出てきたときは、上の2行を足すよう頼めば済みます。

## 実行結果の読み方

全部通ると、次のような画面になります。テストの名前も件数も秒数も、AIが書いたテストによって変わります。自分の画面と1文字ずつ見比べる必要はありません。

```text
   PASS  Tests\Unit\ExampleTest
  ✓ that true is true                                                   0.01s

   DEPR  Tests\Feature\CommentTest
  ! user can post comment → Constant PDO::MYSQL_ATTR_SSL_CA is depre…   0.23s
  ! comment body is required → Constant PDO::MYSQL_ATTR_SSL_CA is dep…  0.05s
  ! user cannot delete others comment → Constant PDO::MYSQL_ATTR_SSL…   0.04s
PHP Deprecated:  Constant PDO::MYSQL_ATTR_SSL_CA is deprecated since 8.5,
use Pdo\Mysql::ATTR_SSL_CA instead in /var/www/html/config/database.php on line 62

  Tests:    3 deprecated, 1 passed (7 assertions)
  Duration: 0.40s
```

10-5-3で見た `PASS` と `✓` のほかに、知らない表示が3種類混ざっています。クラス名の左の `DEPR`、テスト名の左の `!` とその右に続く `Constant PDO::MYSQL_ATTR_SSL_CA is deprecated`、そしていちばん下の `Tests:` の行に並ぶ `deprecated` です。

`deprecated` は「この書き方は将来なくなります」という予告で、テストの合否とは関係がありません。原因は、コンテナのPHPとLaravelの設定ファイルの組み合わせにあります。あなたのコードにも、AIが書いたコードにも原因はありません。組み合わせによっては1件も出ないので、出ても出なくても、見るところは変わりません。

`Tests:` の行の読み方だけ、10-5-3から変わります。予告が出たテストは `deprecated` のほうに数えられるので、`passed` の数が自分の書いたテストの本数と合いません。上の画面では、`CommentTest` の3本は落ちておらず、予告が出たので `deprecated` に入っています。

合否を決めているのは、**`failed` という語が出ているかどうか**だけです。

> ⚠️ **注意**: `!` が並んだ画面は失敗したように見えますが、探すのは `failed` です。10-5-7「テスト - ハンズオン演習」にも、`DEPR` と表示されてもテストは通っている、という注意書きがありました。同じ表示のことです。消そうとして `phpunit.xml` や `config/database.php` を触ると、テストそのものが動かなくなるほうが先に起きます。出たままにしてください。

## 落ちたときの読み方

1本落ちると、画面はこうなります。

```text
   FAIL  Tests\Feature\CommentTest
  ! user can post comment → Constant PDO::MYSQL_ATTR_SSL_CA is depre…   0.21s
  ⨯ user cannot delete others comment                                   0.01s
  ──────────────────────────────────────────────────────────────────────
   FAILED  Tests\Feature\CommentTest > user cannot delete others comment
  Expected response status code [403] but received 302.
  Failed asserting that 302 is identical to 403.

  at tests/Feature/CommentTest.php:42
     40▕         $response = $this->actingAs($userB)->delete("/comments/{$comment->id}");
     41▕
  ➜  42▕         $response->assertStatus(403);

  Tests:    1 deprecated, 1 failed, 1 passed (4 assertions)
```

落ちた印は、テスト名の左の `⨯` です。その下の区切り線から先に、落ちた1本の中身が出ます。中身は3つに分かれています。どのテストが落ちたか（`FAILED` の行）、なぜ落ちたか（`Expected` から始まる行）、どこで落ちたか（`at` の行）。どんな理由で落ちるかはそのつど変わるので、見る場所のほうを覚えてください。

AIに渡すのは、この区切り線から下だけです。通ったテストの行も、`!` の行も、直すのには要りません。

```text
テストを回したら、次の1本が落ちました。原因を調べて直してください。
テストのほうは書き換えないでください。docs/comment.md に書いた観点のとおりです。

（FAILED の行から at tests/... の行までを貼る）
```

> 💡 このお願いのポイントは、①落ちた1本の情報だけを渡していること ②テストを書き換えないでほしいと先に書いていること、の2点です。②が無いと、実装のほうではなくテストのほうが、いま動いているコードに合わせて書き換えられることがあります。

落ちたテストを消したり、条件を緩めたりして通すのは禁じ手です。`failed` は消えますが、設計書に書いた観点と実物の食い違いは残ります。テスト側の文字数の上限を実装に合わせて書き換えれば通りますが、それはもう設計書に書いた観点ではありません。

直させたら、`--filter` を外してもう一度全部回します。1本を直した拍子に、別のテストが落ちることがあります。

## テスト観点と突き合わせる

`failed` が0でも、まだ終わりではありません。通ったテストが、確かめたかったことを確かめているかは別の話だからです。

`docs/comment.md` に書いたテスト観点と、`tests/Feature/` に増えたテストを並べて見ます。観点の行がそれぞれテストになっているか、そして観点に無いテストが増えていないか。この2つを見ます。

設計書は、実装より先にあなたが書いたものです。テストのほうを正として観点を読み替えるのは順番が逆で、**観点を正としてテストを読みます**。観点に無いテストが増えていたら、そのテストが何を確かめているのかを読んでください。読んで意味のあるものなら設計書に行を足し、意味が分からないものは消させて構いません。

観点が全部、自動テストになるとも限りません。どの観点をどの手段で確かめるかは、人が決めます。

| 確かめたいこと | 手段 |
|:--|:--|
| 本文を入れて送ると、コメントが1件増える | テスト |
| 本文が空だと、コメントは増えない | テスト |
| 他人のコメントを消そうとすると、断られる | テスト |
| エラーの文言が、設計書に書いた日本語で出る | ブラウザで確かめる（14-4-2） |

3行目をテストに寄せるのは、画面から試す道がないからです。他人のコメントには消すための操作が出ないので、押して確かめられません。テストなら、消す処理を直接呼んで断られることを見られます。この行のテストが書かれていない場合は、書き足させるか、判定がどこに置かれているかをコードで確かめるかの、どちらかにします。

4行目が反対にテストへ向かないのは、文言を確かめるテストを書くと、設計書の文言を直すたびにテストも直すことになるからです。画面の前で読んだほうが速く終わります。

テストで確かめる、画面で確かめる、コードを読んで確かめる。どれかを済ませれば残りが要らなくなる、という関係にはありません。

## 🏃 テストを回して、観点と突き合わせる

### Step 1: テストを回す

アプリが止まっている場合は、Docker Desktop（またはDocker Engine）を起動してから、Sailを立ち上げます。

```bash
# アプリのフォルダへ移動して、テストを回す
cd ~/laravel-practice/post-app-practice
./vendor/bin/sail up -d
./vendor/bin/sail artisan test
```

このあとの手直しはAIに渡すので、Claude Codeも開いておきます。テストを回したものとは別のターミナルで起動してください。

```bash
# 別のターミナルで、アプリのフォルダへ移動して起動する
cd ~/laravel-practice/post-app-practice
claude
```

ブランチは `feature/comment` のままです。`git branch` を打って、`*` が付いていることを確かめておいてください。

### Step 2: 結果を読む

画面をいちばん下までスクロールして、`Tests:` で始まる行を見ます。`failed` という語が無ければ、書かれたテストは全部通っています。

`Table 'testing.users' doesn't exist` で落ちていたら、`RefreshDatabase` が付いていません。テストクラスに2行足すよう頼んでから、もう一度回してください。

### Step 3: 観点と突き合わせる

`docs/comment.md` のテスト観点と、`tests/Feature/` に増えたファイルを両方開きます。

観点の行を上から1つずつたどって、対応するテストがあるかを見てください。無い行が出てきたら、テストで確かめるのか、ブラウザで確かめるのかを、その場で決めます。ブラウザで確かめると決めた行は、14-4-2で使うので設計書に印を付けておいてください。

### Step 4: 落ちていたら直させる

`failed` が出ていたら、区切り線から下をコピーして、上に載せた頼み方で渡します。

直ったら、そのままコミットとpushも頼みます。

```text
テストが全部通りました。この直しをコミットして、feature/comment に push してください。
```

プルリクエストは開いたままなので、push した分はそこに足されます（12-2-3「プルリクエストの作成とレビュー」）。

このセクションが終わった時点で、次の3つを確かめてください。

- [ ] `./vendor/bin/sail artisan test` を回して、`Tests:` の行に `failed` が無いことを見た
- [ ] `docs/comment.md` のテスト観点が、それぞれテストとして書かれていることを確かめた
- [ ] テストにしない観点について、何で確かめるかを決めた

## ✨ まとめ

- テスト用のデータベースは名前が `testing` で、中身は空のまま用意されます。テーブルを作るのは `RefreshDatabase` の役目で、シードは動きません。
- 実行結果には `DEPR` と `!` と `Constant PDO::MYSQL_ATTR_SSL_CA is deprecated` が混ざります。合否を決めているのは `failed` の有無だけです。
- 予告が出たテストは `deprecated` に数えられるので、`passed` の数と自分の書いたテストの本数は合いません。
- 落ちたときにAIへ渡すのは、区切り線から下の数行です。テストを消したり緩めたりして通すのは禁じ手です。
- `failed` が0でも、設計書の観点を正としてテストを読み直します。どの観点をどの手段で確かめるかは、人が決めます。
