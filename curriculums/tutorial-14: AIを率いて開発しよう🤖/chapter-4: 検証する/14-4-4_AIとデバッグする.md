# 14-4-4: AIとデバッグする

## 🎯 このセクションで学ぶこと

- エラーをAIに渡すときに、何を一緒に渡して何を渡さないかを言えるようになる。
- ログの中から、読むべき1行を取り出せるようになる。
- 修正案を丸呑みせずに、原因究明の主導権を自分が持てるようになる。

---

## 導入：うまくいかないほうが普通

Chapter 3とChapter 4は、ここまで「通った」前提で進んできました。計画が通り、実装が通り、テストが通り、受け入れ条件も通りました。

実際の開発は、そうはいきません。テストが落ちる、画面が真っ白になる、エラーの文字だけが並ぶ。手が止まる時間のほうが長いのが普通です。

AIに任せると、この時間が短くなるように見えます。エラー文を貼れば、たいてい何か直してくれるからです。ただし、その直し方には2つあります。原因を突き止めて直す直し方と、エラーが出なくなるように書き換える直し方です。後者を受け取り続けると、エラーは消えたのに何が起きていたのか分からないコードが残ります。

このセクションで決めるのは、**何を渡すか**と、**どこまで自分で決めるか**です。

---

## エラーが出たときに、まず自分がやること

AIに渡す前に、3つやることがあります。どれも、10-4「デバッグの重要性」で学んだことの範囲です。

**1. エラーの文を読む**

10-4-4「エラー画面の読み方とスタックトレース」で、エラー画面のどこに何が出るのかを確かめました。読むのは、いちばん上のメッセージと、その下です。1行目だけを読んで分かった気にならないでください。データベースからのエラーであれば、実行しようとしたSQLがその下に出ます。そこに、1行目には書かれていない手がかりがあります。

**2. 同じことをもう一度やって、再現する**

もう一度同じ操作をして、同じエラーが出るかを確かめます。出れば、原因はいまのコードの中にあります。出なければ、話が変わります。再現しないものは、AIにも直せません。

**3. 自分の見立てを1つ持つ**

どのファイルが怪しいか、自分なりに1つ決めます。当たっている必要はありません。分からなければ「分からない」でも構いません。大事なのは、**渡す前に自分の考えを持っておくこと**です。持たずに渡すと、返ってきた説明が合っているかどうかを判定する足場がなくなります。

---

## AIに渡すもの、渡さないもの

渡すのは、次の4つです。

| 渡すもの | なぜ要るか |
|:--|:--|
| エラーの文 | 1行目と、その下の発生場所やSQLまで。これが無いと当て推量になります |
| 自分がやった操作 | どの画面で、何を入れて、何を押したか。再現できないものは直せません |
| どうなるはずだったか | 設計書に書いてあるので、そのまま渡せます |
| 自分の見立て | どのファイルが怪しいか。分からなければ「分からない」と書きます |

3つ目が、設計書を持っていることの効き目です。「本文を入れて『コメントする』を押すと、その投稿のコメント一覧に自分のコメントが増えるはずです」と書けるのは、`docs/comment/usecase.md` にその1行があるからです。これが無いと、AIは「エラーを消すこと」だけを目標にします。

渡さないものも決めておきます。

| 渡さないもの | なぜ渡さないか |
|:--|:--|
| `.env` の中身、パスワード、本物の鍵 | 14-1-4で引いた線のとおりです |
| ログファイルの丸ごと貼り付け | 読むのは1行です。渡す量を選ぶのは14-2-2で決めたとおりです |

## ログから、読むべき1行を取り出す

10-4-3「ログの活用」で、ログが `storage/logs/laravel.log` に追記されることと、`tail -f` で流れを見られることを学びました。

今回のような、すでに起きたエラーの文を1行読みたいときは、別の取り出し方のほうが速く済みます。

```bash
# アプリのフォルダの中で実行する
grep "local.ERROR" storage/logs/laravel.log | tail -1
```

初めて使う書き方が2つ入っています。`grep` は、決めた文字を含む行だけを取り出すコマンドです。`|`（縦棒）は、左のコマンドが出したものを右のコマンドへ渡す書き方です。この2つを合わせて、`local.ERROR` という印が付いた行だけを取り出し、そのうちいちばん新しい1行だけを表示しています。

動かしながら流れを見たいときは10-4-3の `tail -f`、起きたエラーの文を1行で読みたいときはこちら、という使い分けです。

なぜ `tail` だけでは足りないのかというと、**1件のエラーで100行を超える記録が残る**からです。エラーの文は最初の1行で、そのあとに処理をたどった記録が延々と続きます。`tail -20` で末尾20行を見ると、その記録の途中しか見えません。10-4-4で「`vendor/` で始まる行は通常は無視してよい」と学んだ、あの部分です。

つまずきやすいところが2つあります。

**ログファイルが無いことがあります**

まだ1度もエラーが起きていないアプリには、`storage/logs/laravel.log` がありません。`No such file or directory` と出たら、それは異常ではなく、記録するものがまだ無いということです。1度エラーを起こせば作られます。

**時刻が手元の時計と合いません**

行の先頭に出る時刻は、日本時間ではありません。世界共通の基準時刻で記録されるので、手元の時計より9時間前になります。「さっき出したエラーのはずなのに、時刻が合わない」と迷わないでください。

## 修正案を丸呑みしない

返ってきた修正案には、たいてい説明が付いてきます。ここで見るのは2つです。

**1. なぜそれで直るのかが、自分の見立てと合っているか**

説明が無ければ、聞いてください。「なぜこの変更で直るのですか」と1行送るだけです。返ってきた理由が、さきほど持った自分の見立てと合っていれば、そのまま進めます。違っていれば、どちらが間違っているのかを先に決めます。自分の見立てが外れていただけなら、それは学びです。AIの説明のほうが怪しければ、そこで止めます。

**2. 直す範囲が、エラーの原因と釣り合っているか**

1行の消し忘れが原因なのに、3つのファイルを書き換える案が返ってくることがあります。エラーは消えるかもしれませんが、消えた理由が分からなくなります。範囲が広いと感じたら、「いちばん小さい直し方を教えてください」と聞き直してください。

そして、**直ったことは自分で確かめます**。「直しました」という返事は結果ではありません。もう一度同じ操作をして、エラーが出ないことを見てください。14-1-4で決めた線と同じです。

2回直させても直らないときは、粘り方を変えます。その決め方は、次の14-4-5で扱います。

## 🏃 わざと1行壊して、直すまでをやってみる

> 🔥 ここからは、AIに実装を任せて構いません。ただし「任せる」と「丸投げ」は違います。何を作るかは設計書で自分が決め、出てきたものはテスト・動作確認・コードレビューで自分が検証します。品質の責任は、AIではなくあなたが握ります。

うまくいっているアプリには、直す対象がありません。そこで、自分の手で1行だけ壊して、それを直すところまでをやってみます。

**この変更は記録しません。** ブランチも切りません。確かめ終わったら、消した1行を自分で戻します。14-4-3でマージを終えたので、いまいる場所は `main` です。

1. 【自分】`app/Models/Comment.php` から `'body'` を消す
2. 【自分】ブラウザでコメントを投稿して、エラー画面を読む
3. 【自分】ログから、該当の1行を取り出す
4. 【自分⇄AI】見立てを1つ書いてから、AIに渡す
5. 【自分】返ってきた説明を読んで、消した1行を戻す
6. 【自分】直ったことを確かめて、`git status` を見る

アプリが止まっている場合は、Docker Desktop（またはDocker Engine）を起動してから、Sailを立ち上げます。

```bash
# アプリのフォルダの中で実行する
cd ~/laravel-practice/14_hands-on/authorization-app-ai
./vendor/bin/sail up -d
```

### Step 1: 1行だけ壊す

`app/Models/Comment.php` を開きます。次のような行があるはずです。1行に並んでいることも、1つずつ改行して書かれていることもあります。

```php
// app/Models/Comment.php
protected $fillable = ['post_id', 'user_id', 'body'];
```

ここから `'body'` だけを消して、保存します。

```php
// app/Models/Comment.php（わざと壊した状態）
protected $fillable = ['post_id', 'user_id'];
```

<details>
<summary>この行が見つからないとき・壊してもエラーが出ないとき（クリックで展開）</summary>

`$fillable` の行が無く、代わりに `protected $guarded = [];` と書かれていることがあります。その場合は、その行を次の1行に書き換えてください。本文を入れない `$fillable` を置くと、同じ状態になります。Step 5で戻すのも、この1行です（元の `protected $guarded = [];` に戻します）。

```php
// app/Models/Comment.php（わざと壊した状態）
protected $fillable = ['post_id', 'user_id'];
```

もう1つ、消したのにエラーが出ず、コメントが普通に登録されることがあります。そのときは、コメントを登録しているところが `Comment::create(...)` を使っていません。`app/Http/Controllers/CommentController.php` を開いて、`$comment->body = ...` のように1項目ずつ入れてから `save()` する形になっていないかを見てください。`$fillable` はこの形には効かないので、消しても何も起きません。同じエラーを出すには、本文を入れているその1行を消します。戻すときも同じ1行です。

</details>

### Step 2: エラー画面を読む

ブラウザで投稿詳細画面を開き、本文を入れて「コメントする」を押します。エラー画面が出ます。

出ているのは、次の形の文です。

```text
SQLSTATE[HY000]: General error: 1364 Field 'body' doesn't have a default value
(Connection: mysql, SQL: insert into `comments` (`user_id`, `post_id`, `updated_at`, `created_at`) values (1, 1, ...))
```

1行目は「`body` に何も入っていないのに、初期値も決まっていない」と言っています。ここで止めずに、その下のSQLを読んでください。入れようとしている列の中に、**`body` がありません**。本文は入力したのに、データベースへ渡す段階で落ちている、ということです。

このエラーの出方が、大事なところです。本文が空のまま静かに保存されるのではなく、保存そのものが止まります。`comments` の `body` を `NOT NULL` にしておいたからです。設計書のテーブル定義書に書いた制約が、ここで効いています。

> 💡 **TIP**: 10-4-6「デバッグ - ハンズオン演習」で踏んだ `MassAssignmentException` と、原因になっている決めごとは同じ `$fillable` です。ただし出方が違います。あちらは例外の名前でLaravelが教えてくれましたが、今回はデータベースからのエラーとして出ます。`$fillable` に無い項目は黙って捨てられて先へ進むので、止まるのはデータベースに届いたあとになります。

### Step 3: ログから1行取り出す

同じ内容が、ログにも残っています。

```bash
# アプリのフォルダの中で実行する
grep "local.ERROR" storage/logs/laravel.log | tail -1
```

画面に出ていたのと同じメッセージが、1行で表示されます。画面が真っ白になってしまう種類のエラーでは、こちらが唯一の手がかりになります。

### Step 4: 見立てを書いてから渡す

渡す前に、自分の見立てを1つ決めます。SQLに `body` が無いところまで読めているので、「本文がデータベースへ渡る手前で落ちている」までは言えます。

```text
投稿詳細画面で本文を入れて「コメントする」を押したら、エラーになりました。
docs/comment/usecase.md の受け入れ条件では、コメント一覧に自分のコメントが増えるはずです。

SQLSTATE[HY000]: General error: 1364 Field 'body' doesn't have a default value
(Connection: mysql, SQL: insert into `comments` (`user_id`, `post_id`, `updated_at`, `created_at`) values (1, 1, ...))

SQLの列に body が無いので、本文がデータベースへ渡る手前で落ちていると考えています。
どこで落ちているのか、原因を教えてください。まだ直さないでください。
```

> 💡 このお願いのポイントは4点です。①やった操作を書いている ②どうなるはずだったかを設計書から引いている ③エラーの文をSQLごと貼っている ④自分の見立てを書いたうえで「まだ直さないでください」と止めている。④が無いと、原因の説明を読む前に修正が始まり、自分の見立てと突き合わせる機会がなくなります。文言をそのまま覚える必要はありません。

> 💡 **出力例について**: AIの応答は毎回変わります。以下はあくまで一例です。文言が違っても、チェックリストの項目を満たしていれば問題ありません。

```text
あなた: （上の依頼を送る）
Claude Code: （app/Models/Comment.php を読んで、$fillable に body が無いことを指摘し、
              そのために本文が捨てられてからINSERTされている、と説明してくる）
```

### Step 5: 消した1行を、自分で戻す

説明を読んで、自分の見立てと合っているかを確かめます。合っていたら、`app/Models/Comment.php` を開いて、消した `'body'` を手で打ち戻してください。

ここはAIに直させません。原因が分かっているものを自分で直すところまでが、この練習です。

### Step 6: 直ったことを確かめる

もう一度、投稿詳細画面で本文を入れて「コメントする」を押します。コメントが一覧に増えれば、直っています。

最後に、手元が元に戻っていることを確かめます。

```bash
# アプリのフォルダの中で実行する
git status
```

一覧に `app/Models/Comment.php` が出てこなければ、壊す前とまったく同じ状態です。14-2-3でコピーした2枚のPNGと `README.md` は、記録していないので出たままです（14-3-3）。`app/Models/Comment.php` のほうが出ている場合は、中身をもう一度見てください。空白や並び順が変わっているかもしれません。

このセクションが終わった時点で、次の4つを確かめてください。

- [ ] エラー画面のSQL文から、`body` が抜けていることを自分で見つけた
- [ ] `grep` の形で、ログから該当の1行を取り出せた
- [ ] AIに渡す前に、自分の見立てを1つ書いた
- [ ] 消した1行を戻し、`git status` に `app/Models/Comment.php` が出てこないことを確かめた

## 💡 よくある間違い

**エラーの1行目だけを貼る**

いちばん多い渡し方です。1行目は「何が起きたか」しか言いません。今回で言えば、`body` に初期値が無いことは分かっても、`body` がSQLから消えている事実は伝わりません。エラーの塊は、たいてい数行でひとまとまりです。区切りのよいところまで貼ってください。

**ログを丸ごと貼る**

反対の失敗です。100行を超える記録をそのまま渡すと、読ませるだけで渡せる量を使い切ります。しかも、その中の98行は原因と関係のない記録です。取り出した1行と、自分がやった操作のほうが、はるかに役に立ちます。

**直った理由を聞かない**

エラーが消えたら、そこで終わりにしたくなります。ただし、理由を聞かずに進めると、同じ原因のエラーに次も同じだけ時間をかけることになります。「なぜこれで直ったのですか」の1行は、次に同じところで止まらないための投資です。

## ✨ まとめ

- エラーが出たら、渡す前に3つやります。文を読む、再現する、自分の見立てを1つ持つ。
- 渡すのは、エラーの文・やった操作・どうなるはずだったか・自分の見立ての4つです。設計書があるので、3つ目はそのまま引いてこられます。
- ログは `grep "local.ERROR" storage/logs/laravel.log | tail -1` で1行に絞ります。1件のエラーで100行を超える記録が残るためです。
- ログファイルが無いのは異常ではありません。時刻は手元の時計より9時間前で記録されます。
- 修正案は丸呑みしません。なぜ直るのかを自分の見立てと突き合わせ、直ったことは自分で確かめます。

次のセクション（14-4-5）では、2回直させても直らなかったときの話をします。粘るか、いったん戻すか、仕切り直すか。その決め方を先に持っておきます。
