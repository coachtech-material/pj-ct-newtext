# 14-4-3: 直らないときの型

## 🎯 このセクションで学ぶこと

- エラーをAIに渡すときに、何を一緒に渡して何を渡さないかを言えるようになる。
- ログの中から、読むべき1行を取り出せるようになる。
- 巻き戻す・分け直す・仕切り直すの3つを、詰まる前に用意しておけるようになる。

---

## 導入：詰まってから決めると、いちばん高い道を選ぶ

Chapter 3 とここまでは、通った前提で進んできました。実際の開発では、テストが落ちる、画面が真っ白になる、エラーの文字だけが並ぶ、という時間のほうが長くなります。

AIに任せると、この時間は短くなります。エラーの文を渡せば、たいてい何か直ってくるからです。困るのはその先で、2回直させても直らないときに、そのまま3回目、4回目と続けてしまいます。1回ごとに何かが変わるので、進んでいるように見えます。そのあいだにコードは触られ続け、最初に動いていたところまで巻き込まれていきます。

先に決めておけば、この時間は数分で終わります。用意するのは、渡し方と、打ち切り方です。

---

## 渡す前に、自分が3つやる

**1. エラーの文を最後まで読む**

10-4-4「エラー画面の読み方とスタックトレース」で見たとおり、読むのはいちばん上のメッセージと、その下です。データベースからのエラーなら、実行しようとしたSQLがその下に出ます。1行目には書かれていない手がかりが、たいていそこにあります。

**2. 同じ操作をもう一度やる**

同じエラーが出れば、原因はいまのコードの中にあります。出なければ話が変わります。再現しないものは、AIにも直せません。

**3. 自分の見立てを1つ持つ**

どのファイルが怪しいかを、1つだけ決めます。当たっている必要はありません。見立てを持たずに渡すと、返ってきた説明が合っているかを判定する足場がなくなります。

---

## 渡すもの、渡さないもの

| 渡すもの | なぜ要るか |
|:--|:--|
| エラーの文 | 1行目と、その下の発生場所やSQLまで |
| 自分がやった操作 | どの画面で、何を入れて、何を押したか |
| どうなるはずだったか | 設計書に書いてあるので、そのまま引いてこられます |
| 自分の見立て | どのファイルが怪しいか。分からなければ「分からない」と書きます |

3つ目が、設計書を持っていることの効き目です。「本文を入れて送ると、コメント一覧に増えるはずです」と書けるのは、`docs/comment.md` にその1行があるからです。これが無いと、AIの目標は「エラーを消すこと」だけになります。エラーが出なくなる直し方と、原因を取り除く直し方は別のもので、前者を受け取り続けると、動いてはいるのに何が起きていたのか分からないコードが残ります。

渡さないものも決めておきます。`.env` の中身・パスワード・本物の鍵は渡しません（14-1-3）。ログファイルの丸ごと貼り付けもしません。読むのは1行だからです。

---

## ログから、読むべき1行を取り出す

10-4-3「ログの活用」で、ログが `storage/logs/laravel.log` に追記されることと、`tail -f` で流れを見られることを学びました。すでに起きたエラーの文を読みたいときは、別の取り出し方のほうが速く済みます。

```bash
# アプリのフォルダの中で実行する
grep "local.ERROR" storage/logs/laravel.log | tail -1
```

`grep` は、決めた文字を含む行だけを取り出すコマンドです。`|`（縦棒）は、左のコマンドが出したものを右のコマンドへ渡す書き方です。この2つで、`local.ERROR` という印が付いた行だけを取り出し、そのうちいちばん新しい1行を表示しています。

1行に絞るのは、**1件のエラーで100行を超える記録が残る**からです。エラーの文は最初の1行で、そのあとは処理をたどった記録が延々と続きます。`tail -20` で末尾を見ると、その記録の途中しか見えません。10-4-4で「`vendor/` で始まる行は通常は無視してよい」と学んだ、あの部分です。

つまずきやすいところが2つあります。まだ1度もエラーが起きていないアプリには `storage/logs/laravel.log` がありません。`No such file or directory` と出たら、記録するものがまだ無いということです。もう1つは時刻で、行の先頭に出るのは日本時間ではありません。世界共通の基準時刻で記録されるので、手元の時計より9時間前になります。

---

## 返ってきた修正案の見方

説明が付いていなければ、「なぜこの変更で直るのですか」と1行送って聞きます。返ってきた理由が自分の見立てと合っていれば、そのまま進めます。違っていたら、どちらが外れているのかを先に決めます。自分の見立てが外れていただけなら、それは収穫です。

もう1つ見るのは、**直す範囲がエラーの原因と釣り合っているか**です。1行の書き忘れが原因なのに3つのファイルを書き換える案が返ってきたら、「いちばん小さい直し方を教えてください」と聞き直します。範囲が広いまま受け取ると、直ったとしても何が効いたのかが分かりません。

そして、直ったことは同じ操作をもう一度やって確かめます。

---

## 巻き戻す

1回目の修正が効かなかったときに、いちばん先にやるのは**壊れた状態を残さないこと**です。効かなかった修正の上に2回目を重ねると、いま動いていないのが1回目のせいなのか2回目のせいなのかが分からなくなります。

| 戻したい範囲 | 手段 | 気をつけること |
|:--|:--|:--|
| AIが直前に書き換えたファイル | Claude Codeで `/rewind` と打つ | コマンドの実行で変わったものは戻りません |
| 直前のコミット1つ分 | `git reset --hard HEAD~1` | pushしたあとは戻せません |
| そのブランチでやったこと全部 | `main` に戻り、ブランチを捨てて切り直す | 捨てる前に、残したいものが無いかを見ます |

`/rewind` を打つと（入力欄が空の状態で `Esc` を2回押しても同じです）、どこまで戻すかを選ぶ画面が出ます。戻す範囲は、コードだけ・やり取りだけ・その両方から選べます（2026年8月時点）。手軽ですが、戻るのはClaude Codeがファイルを直接書き換えた分だけです。`./vendor/bin/sail artisan migrate` のようにコマンドを実行して起きた変更は戻らず、作られたテーブルはそのまま残ります。あなたがVS Codeで手で直したものも対象になりません。

確実に戻れるのは、コミットしてあるところまでです。12-1-3「マージの基礎」で読んだ形が、直前のコミットを取り消すときにも使えます。

```bash
# アプリのフォルダの中で実行する
git reset --hard HEAD~1
```

コミットが細かいほど、戻る先を細かく選べます。1日分の作業を1回のコミットにまとめていると、途中まで戻る道がありません。

ブランチごと捨てるのは、やり直しに見えて、そうでもありません。捨てるのは書かれたコードだけで、そのあいだに分かったこと（どこで詰まったか、何を試したら何が起きたか）は残ります。それを入れて頼み直すぶん、次は速く終わります。

---

## 頼む単位を分け直す

戻したあと、同じ大きさでもう一度頼むと、たいてい同じところで詰まります。次のどれかが出ていたら、そのタスクは大きすぎます。

- **差分を読み切れない量で出てきた**。何がどう変わるのかを自分の言葉で言えないなら、読み切れていません
- **1つ直すたびに、別のところが壊れる**。2往復したら、そのタスクに関係のないものが2つ入っています
- **決めていないことが、2つ以上出てきた**。これは大きさの問題ではありません。設計の穴が、AIからの質問という形で表に出ています。分け直す前に設計書のほうを直します

---

## 2回直らなければ仕切り直す

打ち切りは、数で決めておきます。同じ問題について**2回直させて直らなければ**、そのセッションを終わりにします。

理由は、14-2-2で見たとおりです。同じセッションには、前のやり取りが全部残っています。外れた案が2つ載ったまま3回目を頼むと、AIはそれを引きずります。回数を重ねるほど当たりにくくなる、という向きになります。

区切りには `/clear` を使います。そして、新しいセッションの最初の依頼に**分かったことを書き足します**。何を試したか（どのファイルをどう直させたか）と、そのとき何が起きたか（エラーが変わったか、変わらなかったか）の2つです。これが無いと、新しいセッションのAIは、さきほど外れた案をもう一度出してきます。同じことを2度やらせないための差は、この数行だけです。

区切る前に、そこまでの成果はファイルに書き出しておきます。やり取りの中にしかないものは、区切ると消えます。

頼み直しても届かないときに、もう1つ動かせるものがあります。考える深さです。`/effort` と打つと `low`・`medium`・`high`・`xhigh`・`max` から選べて、既定は `high` です（2026年8月時点）。上げるほど時間と枠を使いますが、そのぶん奥まで調べてから答えます。ふだんは既定のままで構いません。原因が入り組んでいて、頼み方を直しても届かないときだけ上げます。

**詰まったときの道は1本にしておきます。** 1回目が効かなかったらまず戻す。戻したうえで頼む単位を分け直す。分け直しても2回目が直らなかったら、セッションを区切って、分かったことを入れて頼み直す。ここまで通っても直らないときは、そのタスクを離れて設計書のほうへ戻ってください。作るものが決まっていないまま作らせている、ということが起きています。

## 🏃 わざと1行壊して、直すまでをやってみる

動いているアプリには、直す対象がありません。自分の手で1行だけ壊して、渡し方と取り出し方を通しておきます。

**この変更は記録しません。** ブランチも切りません。14-4-2でマージを終えたので、いまいる場所は `main` です。確かめ終わったら、消した1行を戻します。

```bash
# アプリのフォルダへ移動して、アプリを起動する
cd ~/laravel-practice/post-app-practice
./vendor/bin/sail up -d
```

直すのはAIに渡すので、別のターミナルでClaude Codeも開いておきます。

```bash
# 別のターミナルで、アプリのフォルダへ移動して起動する
cd ~/laravel-practice/post-app-practice
claude
```

### Step 1: 1行だけ壊す

`app/Models/Comment.php` を開きます。次のような行があるはずです。1行に並んでいることも、1つずつ改行して書かれていることもあります。

```php
// app/Models/Comment.php
protected $fillable = ['post_id', 'user_id', 'body'];
```

ここから `'body'` だけを消して、保存します。

```php
// app/Models/Comment.php（わざと壊した状態）
protected $fillable = ['post_id', 'user_id'];
```

<details>
<summary>この行が見つからないとき・壊してもエラーが出ないとき（クリックで展開）</summary>

`$fillable` の行が無く、代わりに `protected $guarded = [];` と書かれていることがあります。その場合は、その行を下の1行に置き換えてください。本文を含まない `$fillable` を置くと、同じ状態になります。Step 5で戻すのも、この1行です（元の `protected $guarded = [];` に戻します）。

```php
// app/Models/Comment.php（わざと壊した状態）
protected $fillable = ['post_id', 'user_id'];
```

消してもエラーが出ず、コメントが普通に登録されることもあります。そのときは、コメントを登録している処理が `create(...)` を使っていません。コントローラーを開いて、`$comment->body = ...` のように1項目ずつ入れてから `save()` する形になっていないかを見てください。`$fillable` はこの形には効きません。同じエラーを出すには、本文を入れているその1行を消します。戻すときも同じ1行です。

</details>

### Step 2: エラー画面を読む

ブラウザで投稿詳細を開き、本文を入れて送ります。次の形のエラーが出ます。

```text
SQLSTATE[HY000]: General error: 1364 Field 'body' doesn't have a default value
(Connection: mysql, SQL: insert into `comments` (`post_id`, `user_id`, `updated_at`,
`created_at`) values (1, 1, 2026-08-12 12:00:10, 2026-08-12 12:00:10))
```

1行目は「`body` に何も入っていないのに、初期値も決まっていない」と言っています。ここで止めずに、その下のSQLを読んでください。入れようとしている列の中に、**`body` がありません**。本文は入力したのに、データベースへ渡す手前で落ちている、ということです。

止まり方も見ておいてください。本文が空のまま静かに保存されるのではなく、保存そのものが止まっています。`docs/comment.md` の「増えるテーブル」で `body` を必須にしたことが、ここで効いています。

> 💡 **TIP**: 10-4-6「デバッグ - ハンズオン演習」で踏んだ `MassAssignmentException` と、原因になっている決めごとは同じ `$fillable` です。あちらは例外の名前でLaravelが教えてくれましたが、今回はデータベースからのエラーとして出ます。`$fillable` に無い項目は黙って捨てられて先へ進むので、止まるのはデータベースに届いたあとになります。

### Step 3: ログから1行取り出す

同じ内容が、ログにも残っています。

```bash
# アプリのフォルダの中で実行する
grep "local.ERROR" storage/logs/laravel.log | tail -1
```

画面に出ていたのと同じメッセージが、1行で表示されます。画面が真っ白になる種類のエラーでは、こちらが唯一の手がかりになります。

### Step 4: 見立てを書いてから渡す

SQLに `body` が無いところまで読めているので、「本文がデータベースへ渡る手前で落ちている」までは言えます。

```text
投稿詳細で本文を入れて送ったら、エラーになりました。
docs/comment.md の受け入れ条件では、コメント一覧に自分のコメントが増えるはずです。

SQLSTATE[HY000]: General error: 1364 Field 'body' doesn't have a default value
(Connection: mysql, SQL: insert into `comments` (`post_id`, `user_id`, ...) values (1, 1, ...))

SQLの列に body が無いので、本文がデータベースへ渡る手前で落ちていると考えています。
どこで落ちているのか、原因を教えてください。まだ直さないでください。
```

> 💡 このお願いのポイントは4点です。①やった操作を書いている ②どうなるはずだったかを設計書から引いている ③エラーの文をSQLごと貼っている ④見立てを書いたうえで「まだ直さないでください」と止めている。④が無いと、原因の説明を読む前に修正が始まり、自分の見立てと突き合わせる機会がなくなります。

> 💡 **出力例について**: AIの応答は毎回変わります。以下はあくまで一例です。文言が違っても、チェックリストの項目を満たしていれば問題ありません。

```text
あなた: （上の依頼を送る）
Claude Code: （app/Models/Comment.php を読んで、$fillable に body が無いことを指摘し、
              そのために本文が捨てられてからINSERTされている、と説明してくる）
```

### Step 5: 消した1行を戻す

返ってきた説明が、自分の見立てと合っているかを確かめます。合っていたら、消した `'body'` を戻します。1行なので、自分で打っても、そのままAIに直させても構いません。

### Step 6: 直ったことを確かめる

もう一度、投稿詳細で本文を入れて送ります。コメントが一覧に増えれば直っています。

最後に、手元が元に戻っていることを見ます。

```bash
# アプリのフォルダの中で実行する
git status
```

一覧に `app/Models/Comment.php` が出てこなければ、壊す前とまったく同じ状態です。出ている場合は、中身をもう一度見てください。空白や並び順が変わっているかもしれません。

このセクションが終わった時点で、次の4つを確かめてください。

- [ ] エラー画面のSQLから、`body` が抜けていることを自分で見つけた
- [ ] `grep` の形で、ログから該当の1行を取り出せた
- [ ] AIに渡す前に、自分の見立てを1つ書いた
- [ ] 消した1行を戻し、`git status` に `app/Models/Comment.php` が出てこないことを確かめた

## 💡 よくある間違い

**エラーの1行目だけを貼る**

1行目は「何が起きたか」しか言いません。今回で言えば、`body` に初期値が無いことは伝わっても、`body` がSQLから消えている事実は伝わりません。エラーの塊は、たいてい数行でひとまとまりです。区切りのよいところまで貼ってください。

**ログを丸ごと貼る**

反対の失敗です。100行を超える記録をそのまま渡すと、読ませるだけで渡せる量を使い切ります。しかも、その中の大半は原因と関係のない記録です。

**巻き戻さずに、上から直す**

戻す手間を惜しんで、壊れたコードの上に修正を重ねる進め方です。直ったとしても、何が効いたのかが分かりません。次に同じところで詰まったとき、また同じだけ時間がかかります。

**仕切り直すときに、何も書き足さない**

`/clear` を打って、最初と同じ依頼をもう一度送る形です。同じ答えが返ってきます。区切ることに意味があるのではなく、区切ったうえで渡すものを変えることに意味があります。

---

## ✨ まとめ

- エラーが出たら、渡す前に3つやります。文を最後まで読む、もう一度やって再現する、見立てを1つ持つ。
- 渡すのは、エラーの文・やった操作・どうなるはずだったか・自分の見立てです。3つ目は設計書から引いてこられます。
- ログは `grep "local.ERROR" storage/logs/laravel.log | tail -1` で1行に絞ります。時刻は手元の時計より9時間前で記録されます。
- 修正案は、なぜ直るのかと、直す範囲が原因と釣り合っているかを見ます。
- 1回目が効かなかったら戻し、頼む単位を分け直し、2回で直らなければセッションを区切って分かったことを書き足します。
