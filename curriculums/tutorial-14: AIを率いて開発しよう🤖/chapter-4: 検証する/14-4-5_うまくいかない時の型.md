# 14-4-5: うまくいかない時の型

## 🎯 このセクションで学ぶこと

- 巻き戻す手段を2つ持ち、どちらを使うかを判断できるようになる。
- 詰まったときに、頼む単位を分け直す合図を言えるようになる。
- どこで打ち切って仕切り直すかを、あらかじめ決めておけるようになる。

---

## 導入：直らないときに、何を決めておくか

14-4-4では、原因が分かっているエラーを直しました。壊した場所を自分が知っていたので、1回で終わりました。

本当に困るのは、そうでないときです。直させたのに直らない。直ったと思ったら別のところが壊れる。3回目のやり取りで、最初に何が起きていたのかを自分でも思い出せなくなる。

このとき効くのは、粘る力ではありません。**先に決めておいた打ち切り方**です。困ってから「どうしようか」と考え始めると、たいていいちばん高くつくやり方（そのまま粘る）を選びます。

このセクションで用意するのは3つです。巻き戻す、小さく分ける、2回直らなければ仕切り直す。どれも短い型なので、詰まる前に読んでおいてください。

---

## 巻き戻す

いちばん先にやることは、**壊れた状態を残さないこと**です。1回目の修正が効かなかったのに、その上に2回目の修正を重ねると、いま動いていないコードが、1回目の失敗のせいなのか2回目のせいなのかが分からなくなります。

道具は2つあります。Claude Codeに付いている仕組みと、Gitです。どこまで戻したいかで選びます。

| 戻したい範囲 | 手段 | 気をつけること |
|:--|:--|:--|
| AIが直前に書き換えたファイルだけ | Claude Codeで `/rewind` と打つ | コマンドの実行で変わったものは戻りません |
| 直前のコミット1つ分 | `git reset --hard HEAD~1` | pushしたあとは戻せません |
| そのブランチでやったこと全部 | `main` に戻り、ブランチを捨てて切り直す | 捨てる前に、残したいものが無いかを見ます |

### 1つ目：直前の編集だけを戻す

Claude Codeには、直前の書き換えを戻す仕組みがあります。`/rewind` と打つと（入力欄が空の状態で `Esc` を2回押しても同じです）、どこまで戻すかを選ぶ画面が出ます。戻す範囲は、コードだけ・やり取りだけ・その両方の3つから選べます（画面には、これ以外の項目も並びます。2026年8月時点）。

速くて手軽ですが、**戻る範囲には限りがあります**。戻るのは、Claude Codeがファイルを直接書き換えた分だけです。

- `./vendor/bin/sail artisan migrate` のように、**コマンドを実行して起きた変更は戻りません**。作られたテーブルは、そのまま残ります
- あなたがVS Codeで手で直したものも、対象になりません

**これはGitの代わりにはなりません。** 直前の1手を取り消す道具だと思ってください。

### 2つ目：Gitで戻す

確実に戻れるのは、コミットしてあるところまでです。だから、こちらが主になります。

12-1-3「マージの基礎」で、マージを取り消すやり方として次の形を読みました。やっているのは、1つ前のコミットの状態まで戻すことなので、直前のコミットを取り消したいときにも同じ形が使えます。

```bash
git reset --hard HEAD~1
```

pushしたあとは取り消せない、という注意も同じです。プルリクエストへ送ったあとの取り消しは、この形ではできません。

そのブランチでやったこと全部を捨てるなら、`main` に戻してブランチごと消します。12-1-2「ブランチの作成と切り替え」で読んだ `-D` の形です。

```bash
git switch main
git branch -D feature/issue-1-add-comments
git switch -c feature/issue-1-add-comments
```

ブランチの名前は、そのとき作業しているものに置き換えてください。

やり直しに見えますが、そうでもありません。捨てるのは書かれたコードだけで、そのあいだに分かったこと（どこで詰まったか、何を試したら何が起きたか）は残ります。それを入れて頼み直すぶん、次は速く終わります。

ここで、14-3-3で決めたことが効いてきます。**タスク1つにつきコミット1つ**にしておいたので、戻る先が必ずタスクの区切りになります。3つのタスクを1回のコミットにまとめていたら、タスク1まで戻すことができません。

> 💡 **TIP**: このセクションは読むだけで構いません。ただし `/rewind` は、打ってみないと画面が分かりません。試すなら、`README.md` に1行足させてから `/rewind` を打って、選択肢の並びを見てみてください。戻したあとに `README.md` を開いて、足された1行が消えていれば、戻せたということです。

## 小さく分ける

戻したあと、同じ大きさでもう一度頼むと、たいてい同じところで詰まります。頼む単位を分け直します。

大きさの決め方は、14-3-2で3つ持ちました。差分を自分が読み切れるか、終わったかどうかを自分で確かめられるか、設計書の1行に対応しているか。この3つに戻ります。

このセクションで足すのは、**どうなったら分け直すのか**という合図のほうです。次のどれかが出たら、そのタスクは大きすぎます。

**1. 差分が読み切れない量で出てきた**

14-3-4で決めた判断です。押す前に、この変更で何がどう変わるのかを自分の言葉で言えなければ、読み切れていません。

**2. 1つ直すたびに、別のところが壊れる**

直しては壊れ、を2往復したら、そのタスクの中に関係のないものが2つ入っています。片方を先に終わらせてから、もう片方に移ります。

**3. 決めていないことが、2つ以上出てきた**

これは大きさの問題ではありません。設計の穴です。AIから質問が返ってくる形で表に出ます。分け直す前に、設計書のほうを直してください。

---

## 2回直らなければ仕切り直す

打ち切りの規則は、数で決めておきます。同じ問題について**2回直させて直らなければ**、そのセッションは終わりにします。

理由は、14-2-2で書いたとおりです。前の作業で1回失敗したやり方が残っていると、AIはそれを引きずります。同じセッションで3回目を頼むと、失敗した案が2つ載った机の上で考えることになります。回数を重ねるほど、当たる確率は下がっていきます。

区切り方そのものは、14-2-2で覚えた `/clear` です。あそこでは作業の切れ目で区切るために使いましたが、ここでは打ち切りの合図として使います。

そして、仕切り直すときに1つだけ書き足します。**分かったこと**です。

- 何を試したか（どのファイルをどう直させたか）
- そのとき何が起きたか（エラーが変わったか、変わらなかったか）

これを最初の依頼に入れます。入れないと、新しいセッションのAIは、さきほど外れた案をもう一度出してきます。**同じことを2度やらせないための差は、この数行だけ**です。

区切る前に、そこまでの成果をファイルに書き出しておくのも忘れないでください。頭の中とやり取りの中にしかないものは、区切ると消えます。

---

## 3つを、どの順で試すか

詰まったときの道は、1本にしておきます。

1. 1回目の修正が効かなかったら、**まず戻す**。壊れた上に重ねない
2. 戻したうえで、**頼む単位を分け直す**。合図の3つに当てはまっていないかを見る
3. 分け直しても2回目が直らなかったら、**セッションを区切って、分かったことを入れて新しく頼む**

3を通っても直らないときは、そのタスクではなく設計書のほうに戻ってください。作るものが決まっていないまま作らせている、ということが起きています。

---

## 💡 よくある間違い

**粘り続ける**

同じセッションで5回、6回と直させ続ける進め方です。1回ごとに少しずつ変わるので、進んでいるように感じます。ところが、そのあいだにコードは触られ続け、最初に動いていたところまで巻き込まれていきます。回数を決めておくのは、この感覚を信じないためです。

**巻き戻さずに、上から直す**

戻す手間を惜しんで、壊れたコードの上に修正を重ねる進め方です。直ったとしても、何が効いたのかが分かりません。次に同じところで詰まったとき、また同じ回数だけかかります。

**仕切り直すときに、何も書き足さない**

`/clear` を打って、最初と同じ依頼をもう一度送る形です。これでは、さきほどと同じ答えが返ってきます。区切ることに意味があるのではなく、**区切ったうえで渡すものを変える**ことに意味があります。

---

## ✨ まとめ

- 詰まったときは、まず巻き戻します。壊れた状態の上に修正を重ねると、原因が分からなくなります。
- 戻す手段は2つです。Claude Codeの `/rewind` は直前の編集だけを戻す道具で、コマンドで起きた変更は戻りません。確実に戻れるのはコミットしたところまでなので、Gitのほうが主になります。
- タスク1つにつきコミット1つにしておくと、戻る先が必ずタスクの区切りになります。
- 分け直す合図は3つです。差分が読み切れない、直すたびに別のところが壊れる、決めていないことが2つ以上出てくる。3つ目は設計の穴なので、設計書へ戻ります。
- 同じ問題を2回直させて直らなければ、セッションを区切ります。そのとき、何を試して何が起きたかを書き足します。

これでChapter 4は終わりです。設計書からコードを作らせ、テスト・レビュー・受け入れ確認の3つで検証し、`main` に入れるところまで通しました。詰まったときの手当ても持ちました。

次のChapter 5では、もう一度、別の機能で同じ流れを回します。今度は最初から最後まで自分で進めます。
