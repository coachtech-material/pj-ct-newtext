# 14-4-2: AIが書いたコードのレビュー観点

## 🎯 このセクションで学ぶこと

- 「動く」ことと「正しい」ことの違いを説明できるようになる。
- Tutorial 12で学んだレビューのチェックリストを、AIが書いたコードへ向けられるようになる。
- 自分のレビュー観点表を1枚持てるようになる。

---

## 導入：テストが通っても、まだ分からないことがある

14-4-1で `failed` が0になりました。では、コメント機能はもう正しいのでしょうか。

テストが確かめたのは、`docs/comment/test.md` に自分で書いた5行だけです。5行に書かなかったことについて、テストは何も言いません。黙っているのであって、大丈夫だと言っているのではありません。

ここからが検証の2段目です。機械が判定できなかったところを、自分の目で読みます。

---

## 「動く」と「正しい」は違う

画面にコメントが増えれば、その機能は動いています。動いていても直したほうがよいものは、大きく3種類あります。

**1. 通っていない道が残っている**

テストが通したのは、決めた入力に対する決めた結果だけです。他人のコメントを消そうとしたとき、存在しない投稿を開いたとき、ログインしていない人が直接URLを打ったときの動きは、まだ1度も通っていません。

**2. 同じ結果になる作り方が、いくつもある**

「消せるのは書いた本人だけ」という決まりは、ポリシーに書いても、コントローラーの中に `if` で書いても、画面上の動きは同じになります。動きが同じなら、どちらでもよいわけではありません。

**3. いまは困らないが、あとで困る作りになっている**

コメントが3件のあいだは、投稿者の名前を出すのに何回データベースへ問い合わせても、体感は変わりません。9-5-1「1対多のリレーションシップ（hasMany、belongsTo）」で見たとおり、件数が増えたときに初めて表に出ます。

この3つは、どれもテストでは拾えません。拾えるのは、コードを開いて読む人だけです。

## Tutorial 12のチェックリストを、AIのコードへ向ける

レビューの観点は、すでに持っています。12-3-5「ハンズオン - コードレビュー演習」の最後に、セキュリティ・パフォーマンス・可読性・ベストプラクティスの4つに分けたチェックリストが並んでいました。あれを、今度はAIが書いたコードへ向けます。

読み始める前に、**この機能に実際に当たる行だけ**を決めておきます。一覧を上から順に当てていくと、関係のない行で手が止まります。コメント機能で当たるのは、次の7つです。

| 見るところ | このコードでの具体形 | 学んだ場所 |
|:--|:--|:--|
| N+1 | コメント一覧で `$comment->user->name` を出しているのに、`with('user')` が付いていないか | 9-5-1・9-5-3 |
| 認可の置き場所 | 「消せるのは書いた本人だけ」の判定が、どこに書かれているか | 10-3（章）・10-3-5 |
| マスアサインメント | `Comment::create($request->all())` の形になっていないか | 9-4-8・10-4-6 |
| XSS | コメントの本文を `{!! !!}` で出していないか | 10-6-3 |
| CSRF | コメントの入力フォームに `@csrf` があるか | 10-6-1 |
| 入力チェック | `screen.md` の入力チェック表と、`validate()` の中身が合っているか | 9-6（章）・13-3-3 |
| 名前と書き方の揃い | いまあるコードと同じ呼び方・同じ書き方になっているか | 12-3-5・10-3-1 |

仕組みは、どの行もすでに学んだところです。ここで新しいのは、**自分が書いていないコードに対して、これを当てる**という点だけです。

### 投稿一覧のコードと見比べる

N+1と書き方の揃いについては、物差しが手元にあります。投稿一覧を出しているコードです。まず `app/Http/Controllers/PostController.php` を開いて、`index()` を見てください。10-3-5のスターターキットに最初から入っていたもので、次の形になっているはずです。

```php
// app/Http/Controllers/PostController.php
public function index()
{
    $posts = Post::with('user')->latest()->get();
    return view('posts.index', compact('posts'));
}
```

投稿一覧の画面では、投稿ごとに `{{ $post->user->name }}` で投稿者の名前を出しています。そのために `with('user')` が付いています。もし手元のコードが違う形になっていたら、実物であるそちらが物差しです。コメント一覧でも、コメントごとに書いた人の名前を出すのなら、同じことが要ります。

自分のコードを開いて、**そうなっているかどうかを確かめてください。** 付いていれば、そのまま進みます。付いていなければ、直させます。「AIはこう書きがちだ」と決めつけて探すのではなく、手元にある形と見比べて、外れていたら気づく。これがレビューのやり方です。

> ⚠️ **注意**: このアプリには、クエリの回数を画面に出してくれる道具は入っていません。9-5-3「Eager Loadingとレイジーローディング」で使ったものを入れる必要はありません。ここで見るのは、コードに `with()` が書かれているかどうかです。

### 判定は1か所に集める

14-3-5で、`CommentPolicy::delete()` の参考実装を見たときに、宿題を1つ残しました。「消せるのは書いた本人だけ」の判定がコントローラーの中に直接書かれていても画面上の動きは同じなのに、どちらが良いのか、という話です。

答えは、**1か所に集めるほうが良い**、です。理由は2つあります。

1つ目は、同じ判定が2か所に書かれると、片方だけ直したときに食い違うからです。コメントの削除を将来「投稿を書いた人も消せる」に変えるとします。判定がポリシーに1つだけあれば、直すのは1か所です。コントローラーとBladeの両方に条件が書いてあれば、両方を直さなければなりません。片方を直し忘れると、ボタンは出るのに押すと403になる、という食い違いが起きます。

2つ目は、画面から隠すだけでは止められないからです。10-3-5「認可機能 - ハンズオン演習」で、他人の投稿の編集画面を直接URLで開くと403になることまで確かめました。Bladeの `@can` でボタンを消しても、URLを直接打たれたら通ってしまいます。止めるには、処理そのものの手前に判定が要ります。

読むときに見るのは、判定の文が同じかどうかではなく、**その判定がどこに何回書かれているか**です。

> 💡 **TIP**: ここは読むだけで構いません。直すところはありません。`app/Models/Post.php` の `$fillable` にも `user_id` が入っています。いまの `PostController::update()` は `validate()` を通した値だけを渡しているので、投稿者が入れ替わることはありません。ただし、ここに `$request->all()` を渡す作りに変われば、コメントと同じ危うさが出ます。9-4-8「マスアサインメントと$fillable」で学んだのは、この形のことでした。

## AIが書いたコードで、特に見るところ

上の7つは、人が書いたコードでも見るところです。ここからの3つは、指示を受けて一気に書き上げるという作り方から出てくるものです。12-3で見たチェックリストにも、14-3-4で決めた読む順番にも入っていません。

| 見るところ | なぜ出るのか | 確かめ方 |
|:--|:--|:--|
| 設計書に無いものが増えていないか | 「あったほうが良さそう」なものが足されることがある。計画と差分の承認を1つずつ通ってしまっても、通しで読むと見つかる | `docs/comment/` の8ファイルに書いていないカラム・画面・処理が無いか |
| テストが実装に合わせて書かれていないか | 実装とテストを同時に書くと、テストが実装をなぞるだけになることがある | `test.md` の `TC-` の文と、テストの中身が合っているか |
| 頼んでいない依存が足されていないか | 便利なパッケージが提案されることがある | `composer.json` が変わっていないか |

2つ目は、14-4-1の「落ちたテストのほうを消さない」と同じ話を、逆から見たものです。テストは通っているのに、確かめている中身がずれている、という形で出ます。`TC-05` は「本文が501文字だと、コメントが登録できない」でした。テストが実際に501文字を送っているかどうかを、その1本だけ開いて確かめてください。500文字を送っていれば、そのテストは通っても意味がありません。

3つ目は、差分の中でいちばん見落としやすいところです。`composer.json` は、自分が書き換えるつもりのないファイルなので、変更されたファイルの一覧を眺めるときに目が滑ります。名前を覚えておいて、一覧の中に出ていないかだけを見てください。

> 💡 **TIP**: 14-3-4で決めた読む順番（ファイルの一覧、消えた行、設計書との突き合わせ、説明と実物の突き合わせ）は、まとめて読み返すときにもそのまま使えます。順番はあのままで、見る中身がこのセクションの観点に変わります。

## 🏃 コメント機能のコードを読む

> 🔥 ここからは、AIに実装を任せて構いません。ただし「任せる」と「丸投げ」は違います。何を作るかは設計書で自分が決め、出てきたものはテスト・動作確認・コードレビューで自分が検証します。品質の責任は、AIではなくあなたが握ります。

1. 【自分】プルリクエストの「Files changed」を開いて、通しで読む
2. 【自分】コントローラーとモデルを開いて、N+1・マスアサインメント・認可の置き場所を見る
3. 【自分】Bladeを開いて、`{!! !!}` と `@csrf` を見る
4. 【自分⇄AI】見つかったところを直させて、コミットしてpushする
5. 【自分】`docs/review-checklist.md` を作る

### Step 1: 通しで読む

GitHubでプルリクエストを開き、「Files changed」を見ます。14-3-5で開いたままにしてあるものです。

承認しながら1ファイルずつ見てきたものが、ここでは機能ひとまとまりとして並びます。まず、変更されたファイルの一覧だけを見てください。`composer.json` が混ざっていないか、設計書に無いファイルが増えていないかは、この時点で分かります。

### Step 2: コントローラーとモデルを読む

ここからは手元のVS Codeで読みます。ファイルを行き来するので、そのほうが速く済みます。

`app/Http/Controllers/CommentController.php` を開いて、次の3つを見てください。ファイル名はAIが付けたものなので、違う名前になっていても構いません。

- コメントの登録で、`$request->all()` を渡していないか
- コメントの削除で、書いた本人かどうかの判定がどこにあるか
- `validate()` のルールが、`screen.md` の入力チェック表と同じか

そのあと、投稿詳細画面にコメントを渡しているところを開いて、`with('user')` が付いているかを見ます。`app/Http/Controllers/PostController.php` の `index()` を並べて開くと、比べやすくなります。

### Step 3: Bladeを読む

投稿詳細画面のBlade（`resources/views/posts/show.blade.php` など、AIが作ったファイル）を開きます。Step 2と同じで、名前が違っていても構いません。投稿の本文とコメントの一覧が書かれているファイルです。

- コメントの本文が `{{ }}` で出ているか（`{!! !!}` になっていないか）
- コメントの入力フォームに `@csrf` があるか
- 削除ボタンの出し分けが、画面を隠すだけになっていないか（Step 2で見た判定と対になっているか）

### Step 4: 見つかったところを直させる

引っかかったところがあれば、名指しで直させます。

```text
app/Http/Controllers/CommentController.php の store で、
Comment::create($request->all()) の形になっています。
docs/comment/screen.md の入力チェック表のとおりに validate() を通して、
その結果と、ログイン中のユーザーのIDだけを渡す形に直してください。
ほかのファイルは変えないでください。
```

> 💡 このお願いのポイントは3点です。①どのファイルのどのメソッドかを名指ししている ②どう直すかを設計書を根拠に書いている ③触ってほしくない範囲を書いている。②が無いと、直し方をAIが決めることになります。文言をそのまま覚える必要はありません。

直させたら、差分を読んで承認し、テストをもう一度回してからコミットします。

```bash
# アプリのフォルダの中で実行する
./vendor/bin/sail artisan test
git status
git add .
git commit -m "Fix #1: apply review comments to comment feature"
git push origin feature/issue-1-add-comments
```

`#1` は自分のイシューの番号に置き換えます。引っかかったところが1つも無ければ、この手順は要りません。

### Step 5: 自分のレビュー観点表を作る

最後に、自分が見ると決めた観点を1枚のファイルにします。

```bash
# アプリのフォルダの中で実行する
touch docs/review-checklist.md
```

置き場所は `docs/` の直下です。機能ごとのフォルダの中には入れません。この表はコメント機能だけのものではないので、次の機能でも同じものを使います。

中身は箇条書きで構いません。このセクションで出てきた10個を全部写す必要はありません。**自分が実際に見た観点だけ**を、自分の言葉で書いてください。

```markdown
# レビュー観点

- [ ] 一覧で関連するデータの名前を出しているところに、`with()` が付いているか
- [ ] 「本人だけができること」の判定が、1か所に書かれているか
- [ ] `create()` に `$request->all()` を渡していないか
- [ ] ユーザーが入力した文字を `{!! !!}` で出していないか
- [ ] 入力フォームに `@csrf` があるか
- [ ] 入力チェックの中身が、設計書の入力チェック表と同じか
- [ ] 設計書に無いファイル・カラム・処理が増えていないか
- [ ] テストが、テスト観点表の文のとおりに確かめているか
- [ ] `composer.json` が変わっていないか
```

この表は、後で使い回せる形にしておきます。書けたらコミットしてpushしてください。

```bash
# アプリのフォルダの中で実行する
git add docs/review-checklist.md
git commit -m "Add #1: add review checklist"
git push origin feature/issue-1-add-comments
```

このセクションが終わった時点で、次の5つを確かめてください。

- [ ] コメント一覧で書いた人の名前を出しているところに、`with()` が付いていることを確かめた
- [ ] 「消せるのは書いた本人だけ」の判定が、どこに書かれているかを自分の目で見た
- [ ] コメントの本文が `{!! !!}` で出されていないことを確かめた
- [ ] `composer.json` が変わっていないことを確かめた
- [ ] `docs/review-checklist.md` に、自分が見ると決めた観点が書かれている

## 💡 よくある間違い

**動いたので、読まない**

14-3-5でブラウザを開いて、コメントが増えるところまで見ました。テストも通りました。ここで読むのをやめたくなるのが自然です。ただし、そこまでで確かめたのは「決めたとおりに使ったときに動くこと」だけです。読まなかったコードは、数週間後に自分が直すことになります。

**毎回、全部の観点を当てようとする**

12-3のチェックリストには10項目あり、このセクションの表と合わせれば、もっと増えます。1つの機能に全部を当てようとすると、時間が足りずに、結局どれも流し読みになります。先に「この機能で当たるのはこれ」と絞ってから読むのは、そのためです。絞る作業は、設計書を書いた自分がいちばん速くできます。

**AIに「レビューして」と丸投げする**

12-3-1「コードレビューの目的と効果」では、コードレビューを「他の開発者が書いたコードを確認する」ことだと説明していました。AIが書いたコードをAIに読ませると、書いた側と読む側が同じになります。ここは人が読む場所です。読める量に区切って渡すために、14-3-2でタスクを割りました。

## ✨ まとめ

- テストが確かめたのは、`test.md` に書いた観点だけです。書かなかったことについて、テストは何も言いません。
- 動いていても直したほうがよいものは3種類あります。通っていない道、作り方の選び方、あとで困る作りです。
- 12-3で見たチェックリストを、AIが書いたコードへ向けます。この機能に当たる行だけを、先に絞ってから読みます。
- 「本人だけができること」の判定は1か所に集めます。2か所にあると片方だけ直したときに食い違い、画面から隠すだけではURLを直接打たれたときに止まりません。
- AIのコードで特に見るのは、設計書に無いものが増えていないか、テストが実装をなぞっていないか、頼んでいない依存が足されていないかの3つです。

次のセクション（14-4-3）では、3段目に進みます。ブラウザで実際に触って、受け入れ条件と1行ずつ突き合わせます。そこまで通れば、プルリクエストをマージします。
