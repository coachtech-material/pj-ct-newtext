# 14-3-3: 設計書から作る

## 🎯 このセクションで学ぶこと

- 要望を渡してイシューを立てさせ、返ってきた聞き返しに答えて中身を固められるようになる。
- 1ファイル・7見出しの設計書をAIに書かせ、読んで足りないところを直させられるようになる。
- 設計書を渡して実装を走らせ、テストが通るところまで持っていけるようになる。

---

## 導入

14-3-1で並べた3番、リプライ機能をここから作ります。持ち方は設計書です。開発フロー（Issue化 → 計画 → 実装とテスト → レビュー → UAT → PR）でいうと、この節はIssue化から始めて、実装とテストまで進みます。

画面のやり取りの中にしか無い計画にしてしまうと、実装が終わったあとに「頼んだとおりにできているか」を突き合わせる相手が、プロジェクトの側に1つも残りません。ここでは計画をファイルに書いて、Chapter 4まで持ち越します。

---

## 設計書は1ファイル

`docs/reply.md` の1枚に、最後は次の7つがそろっていれば足ります。

```text
## 概要
## 受け入れ条件
## 変えないもの
## 増えるテーブル
## 増える画面
## 入力チェックとメッセージ一覧
## テスト観点
```

Tutorial 13では、機能一覧・ユースケース記述・画面設計と、種類ごとにファイルを分けて書きました。この7つは、そのとき1冊ずつ書いた設計書を、1ファイルの7見出しまで縮めたものです。「増えるテーブル」は8-1-5で読んだER図、「入力チェックとメッセージ一覧」は13-3-4で書いた入力チェック表とメッセージ一覧に当たります。ここで1ファイルに寄せるのは、この機能が小さいためです。分けたところで、どのファイルにも数行ずつしか入りません。**設計書の粒度は、機能の大きさに合わせます。**

見出しの並びは、依頼のときに渡します。どこに何が書いてあるかが決まっていれば、Chapter 4で受け入れ条件を探すところから始めずに済みます。中身の書き方までは渡しません。

---

## 🏃 リプライ機能を、設計書から作る

作るのは、14-2-1で読んだ依頼と同じリプライ機能です。あのとき出した案はどのファイルにも残っていないので、要望と、変えないものと、完成の条件は、ここで改めて渡します。この機能はChapter 4の終わりまで通しで扱います。

思いどおりに直らない・壊れたと感じたら14-5-1（直らないときの型）へ。応急は `git restore .`（4-3-5）

テストを回すので、アプリを動かしておきます。止まっている場合は、Docker Desktop（またはDocker Engine）を起動してから、このあと起動するClaude Codeとは別のターミナルで次を実行してください。

```bash
# 投稿アプリのフォルダで実行する
./vendor/bin/sail up -d
```

ターミナルで投稿アプリのフォルダ（14-1-3でCLAUDE.mdを作ったフォルダ）へ移動して、Claude Codeを起動します。

```bash
# 投稿アプリのフォルダで実行する
claude
```

### Step 1: 要望を渡して、イシューを立てさせる

```text
以下の要望で、GitHub Issue を立てて。
決めないといけないことがあれば、先にこちらへ質問して。

このアプリにリプライ機能を足したい。
ポストを読んだ人が、その場で一言返せるようにする。今は読むだけで、返す手段がない。

- タイムラインの今の動き（一覧・編集・削除）は変えない
- リプライを消せる人の判定は app/Policies/PostPolicy.php のやり方に揃える

完成の条件:
- ポストを1件開くと、そのポストとリプライの一覧が見える
- 本文を入れてリプライを送ると、一覧に増える
- 本文が空のままだと、エラーが表示されてリプライは増えない
- 自分のリプライは消せて、他人のリプライは消せない
```

> 💡 **出力例について**: AIの応答は毎回変わります。以下はあくまで一例です。文言が違っても、チェックリストの項目を満たしていれば問題ありません。

```text
あなた: （上の依頼を送る）
Claude Code: （いまのルートや PostPolicy を読んだうえで、リプライは編集できるのか、
              リプライにリプライを付けられるのか、本文の長さに上限を置くか、
              といった問いを並べてくる）
```

問いには1つずつ答えます。14-2-2でやったのと同じで、答えを選ぶのはあなたです。答え終えるとイシューが立ちます。

**立ったイシュー**

<img alt="14-3-3_1.png" src="">

返ってきたURLをブラウザで開いてください。URLの末尾の数字がイシューの番号です。以降は、自分の番号に読み替えて進めます。

受け入れ条件のところだけ見ておきます。上の4行が、そのままの文で入っているかを見てください。抜けていたり書き換わっていたりしたら、元の文に直させてから次へ進みます。この4行は、このあと設計書にも動作確認にも同じ文で出てくるので、ここで揃えておきます。

頼んでいないことまで返ってくることがあります。Tutorial 13で `docs/` に置いた設計書があると、AIはそれも読むので、機能の番号を前の続きから振ってきたり、受け入れ条件がこちらの4行より多く並んだりします。多い分には構いません。読んで、要らないものを消させれば済みます。

> 💡 **TIP**: `gh` は、いまいるフォルダのGitの送り先を見て、どのリポジトリに立てるかを決めます。うまくいかないときは、Claude Codeとは別のターミナルで `gh repo view` を実行し、自分のリポジトリが表示されるかを確かめてください。

### Step 2: ブランチを切る

```text
このイシューの作業用にブランチを切って。
```

設計書も、このブランチの上に置きます。Chapter 4の最後で、設計書と実装をひとまとめにしてプルリクエストを出すためです（14-4-5）。mainには、この節では何も入れません。

### Step 3: 設計書を書かせる

図は、Tutorial 13で使ったdraw.ioでは描かせません。8-1-5のER図と同じMermaid（文字で書くと図になる書き方）で書かせて、こちらは表示された図を読んで確かめます。

```text
Issue #（自分の番号）の内容をもとに、設計を docs/reply.md にまとめて。
見出しは 概要 / 受け入れ条件 / 変えないもの / 増えるテーブル / 増える画面 /
入力チェックとメッセージ一覧 / テスト観点 の7つにして。
増えるテーブルは Mermaid の erDiagram で図も入れて。
実装のコードはまだ書かないで。
```

イシューには、要望も、答えた内容も、受け入れ条件も、もう書いてあります。渡したものの中身を、依頼文でもう一度書く必要はありません（14-2-1）。

### Step 4: 設計書を読んで、直させる

VS Codeで `docs/reply.md` を開きます。プレビュー（`Ctrl+Shift+V`、Macは `Cmd+Shift+V`。13-2-1で表を確かめたときと同じものです）も開いて、ER図が図として表示されるところまで見てください。Mermaidを図にする機能は新しめのVS Codeに最初から入っているので、拡張機能を入れる必要はありません（2026年8月時点）。図の代わりにエラーの文言が出たときは、その文言をそのまま貼って渡し、直させます。図にもエラーにもならず、書いた文字がそのまま並んでいるときは、VS Codeが古い可能性があります。更新してから開き直してください。

**`docs/reply.md` のプレビュー**

<img alt="14-3-3_2.png" src="">

図として出ることと、書いてあることが合っていることは別です。表示されたら、中身を読みます。

| よく起きるずれ | 直し方 |
|:--|:--|
| 受け入れ条件が「リプライを投稿できること」の形に書き直されている | 「〜すると、〜になる」に戻す。イシューの文をそのまま写させる |
| 増えるテーブルが表だけで、図が無い | ER図を足させる |
| テスト観点が、うまくいく場合だけになっている | 本文が空のまま送った場合と、他人のリプライを消そうとした場合を足させる |
| 実装のコードが設計書の中に書かれている | 外させる。コードを書くのは次のStepです |
| 「変えないもの」が、イシューに書いた2行と食い違っている | イシューの文に戻させる |

3つ目は書き方のずれではなく、中身の抜けです。13-8-1で見た「決めたとおりでない使われ方」の観点は、設計書からたどらないと出てきません。

見つかったずれは、1つずつ伝えて直させます。

```text
テスト観点に、他人のリプライを消そうとしたときの行がありません。
「自分のリプライは消せて、他人のリプライは消せない」から起こして、1行足してください。
```

読み終えたら、コミットさせます。

```text
docs/reply.md をコミットして。
```

ここまでで、計画がファイルとして残りました。この先でセッションが切れても、新しいセッションを起動して `docs/reply.md` を渡せば、同じ計画から続けられます。

### Step 5: 設計書を渡して、実装させる

計画は `docs/reply.md` が持っているので、planモードは使いません（14-3-1）。

```text
docs/reply.md のとおりにリプライ機能を作って。
テストも書いて、./vendor/bin/sail test で回して、通るまで直して、最後に結果を報告して。
```

Step 3と同じで、渡したファイルに書いてあることは繰り返しません（14-2-1）。受け入れ条件も、変えないものも、入力チェックのメッセージも、`docs/reply.md` の中にあります。ここで足しているのは、**設計書に書いていない1つ**だけです。どうやって確かめるか、です。

2行目が、この依頼のいちばん効くところです。テストを書いたところで止めず、回して、落ちたら直すところまでをAIの側に閉じさせています。詳しくは次章で扱います。

> 💡 **進行例について**: AIとの開発は毎回違う流れになります。ここに示すのは一つの進行例です。あなたの画面と違っていても、チェックリストを満たしていれば正解です。

```text
あなた: （上の依頼を送る）
Claude Code: （マイグレーションとモデルを作り、コントローラーとルートと画面を書き、
              テストを書いて ./vendor/bin/sail test を回し、落ちたところを直して、
              最後にテストの結果を報告する）
```

途中で質問が来たら答えます。答えが `docs/reply.md` のどこにも無い質問なら、そこが設計の穴です。13-1-1で置いた見方が、実装の最中にも効きます。設計書に書き足してから、続けてもらいます。

> ⚠️ **注意**: このアプリはDockerの中で動くので、`php artisan` では動きません。AIが `php artisan migrate` を実行して失敗していたら、`./vendor/bin/sail artisan migrate` を使うように伝えて続けさせてください。

### Step 6: 実装とテストをコミットする

テストが通ったら、Step 4と同じように記録させます。

```text
ここまでの実装とテストをコミットして。
```

最後に、次を確かめてください。確かめ終えたら `/exit` で閉じます。

- [ ] イシューが立っていて、受け入れ条件に上の4行の内容が入っている
- [ ] `docs/reply.md` に7つの見出しがそろっていて、増えるテーブルがプレビューで図として表示される
- [ ] テスト観点に、他人のリプライを消そうとしたときの行がある
- [ ] テストを回した結果が報告されていて、通っている
- [ ] ここまでの変更が作業ブランチにコミットされていて、mainは変わっていない

---

## 設計書のこの先

`docs/reply.md` は、実装のための一時的な材料です。実装が終わったあとは、動いているコードと、通っているテストのほうが、この機能の姿を正しく持ちます。設計書とコードの両方を書き換え続けようとすると、同じことを2か所で管理することになります。

この設計書を使うのは、Chapter 4で、できあがったものを受け取るところまでです。使い終わった設計書を `docs/` にどう置いておくかは、14-5-4で決めます。

---

## ✨ まとめ

- 残す側の計画は、イシューを立ててから設計書に起こす。要望の文だけを渡して、決め落としは問いとして返させる。
- 設計書は1ファイル7見出し。Tutorial 13で種類ごとに分けて書いたものを、機能の大きさに合わせて縮める。
- 見出しの並びは依頼で渡す。中身の書き方は渡さず、書かれたものを読んで足りないところを足させる。
- 図が表示されることと、書いてあることが合っていることは別。表示を確かめてから、中身を読む。
- 抜けやすいのはテスト観点。決めたとおりでない使われ方の行があるかを見る。
- 実装の依頼で足すのは、設計書に書いていないことだけ。この節では検証手段の1行。設計書を作った機能に、planモードは重ねない。
- 設計書は使い捨て。実装が終われば、コードとテストのほうが正しい姿を持つ。
