# 14-3-2: 差分の受け取り方

## 🎯 このセクションで学ぶこと

- 走り終わったものを、どの順で見るのかを言えるようになる。
- コメント機能で当てるレビューの観点を、自分で絞れるようになる。
- 引っかかったところを、名指しで直させられるようになる。

## 導入：まとめて出てくるものを上から順に読むと、途中で目が滑る

計画を承認したあとは止まらないので、こちらの番が回ってくるのは、コミットとプルリクエストまで終わったあとです。書き換わったファイルは10近くあります。上から順に全部読もうとすると、後半は文字を追うだけになります。

順番を決めておくと、外れているものが先に出てきます。

## 受け取る場所

差分（変更した箇所だけを、前とあとで見比べられる形にしたもの）は、プルリクエストができた時点で `gh` から読めます。

```bash
# 変わったファイルの名前だけを出す
gh pr diff --name-only

# 差分の中身をまとめて出す
gh pr diff

# ブラウザで開く
gh pr diff --web
```

`gh pr diff` は、いまいるブランチのプルリクエストを自分で探して、その差分を出します。`--name-only` を付けると名前だけになるので、一覧を眺めるのに向いています。`--web` はGitHubの「Files changed」を開きます。ファイルごとに増えた行数と減った行数が並ぶので、量から見当を付けるならこちらが速いです。

12-2-3「プルリクエストの作成とレビュー」で見た「Files changed」と、出ているものは同じです。

## 読む順番

### 1. 設計書と突き合わせる

`docs/comment.md` に書いたものが、そのとおりに増えているかを見ます。テーブルとカラム、画面、入力チェックの3か所です。

ここで力を入れるのは、書いたものがあるかどうかの確認より、**書いていないものが増えていないか**のほうです。増えやすいのは、カラムと画面、それからパッケージです。`composer.json` が一覧に出ていたら、頼んでいない依存が足されています。自分で書き換えるつもりのないファイルなので、一覧を眺めるときにいちばん目が滑ります。名前だけ覚えておいて、出ていないかを見てください。

### 2. 触っていないはずの場所を見る

コメント機能で変える約束をしていない場所です。

| 見る場所 | 何のファイルか |
|:--|:--|
| `routes/web.php` | いまある4本のルート |
| `app/Http/Controllers/PostController.php` | 投稿の一覧・編集・更新・削除 |
| `app/Policies/PostPolicy.php` | 投稿を編集・削除できる人の判定 |
| `resources/views/posts/index.blade.php` | 投稿一覧の画面 |

この4つに差分が出ていたら、中身を読みます。投稿一覧に詳細画面へのリンクを1本足すだけなら、差分は数行です。そこに10行を超える差分が出ていたら、ついでの書き換えが混ざっています。設計書に「何をどこまで」を書いておくと、1行ずつ読む前に、量だけで見当が付きます。

とくに見るのは、消えた行です。`gh pr diff` の出力では、`-` から始まる行がそれにあたります。足された行は頼んだものが出てくるので読みやすく、消えた行は自分が過去に読んだものなので、飛ばしても違和感がありません。たとえば `PostController::update()` の先頭にある `$this->authorize('update', $post)` の1行が整理のついでに消えていても、自分の投稿を編集している限り、画面の見た目は何も変わりません。他人の投稿を開いたときに初めて表に出ます。

### 3. 中身を読む

ここで初めて、コードそのものを読みます。読み始める前に、この機能に当たる観点だけを決めておきます。一覧を上から順に当てていくと、関係のない行で手が止まります。

| 見るところ | このコードでの具体形 | 学んだ場所 |
|:--|:--|:--|
| N+1 | コメント一覧で書いた人の名前を出しているのに、`with()` が付いていないか | 9-5-1・9-5-3 |
| 認可の置き場所 | 「消せるのは書いた本人だけ」の判定が、どこに書かれているか | 10-3-5 |
| マスアサインメント | `Comment::create($request->all())` の形になっていないか | 9-4-8 |
| XSS | コメントの本文を `{!! !!}` で出していないか | 10-6-3 |
| CSRF | コメントの入力フォームに `@csrf` があるか | 10-6-1 |
| 入力チェック | `validate()` の中身が、設計書の入力チェックと合っているか | 9-6章 |
| 書き方の揃い | いまあるコードと同じ呼び方・同じ書き方になっているか | 12-3-5 |

仕組みは、どれもすでに学んだところです。ここで新しいのは、自分が書いていないコードにこれを当てるという点だけです。

## 物差しは手元にある

「同じ書き方になっているか」を見るには、比べる相手が要ります。投稿一覧を出しているコードが、そのまま物差しになります。

```php
// app/Http/Controllers/PostController.php
public function index()
{
    $posts = Post::with(['user', 'category'])->latest()->get();

    return view('posts.index', compact('posts'));
}
```

投稿一覧の画面では、投稿ごとに `{{ $post->user->name }}` と `{{ $post->category->name }}` を出しています。そのために `with(['user', 'category'])` が付いています。コメント一覧でも、コメントごとに書いた人の名前を出すのなら、同じことが要ります。

画面のほうにも物差しがあります。`resources/views/posts/index.blade.php` には、`@can('update', $post)` でボタンを出し分けている箇所と、フォームの中に `@csrf` を置いている箇所があります。コメントの削除ボタンと入力フォームが、この形から外れていないかを見ます。

「AIはこう書きがちだ」と決めつけて探すのではなく、手元にある形と見比べて、外れていたら気づく。これがレビューのやり方です。

> ⚠️ **注意**: このアプリには、データベースへの問い合わせ回数を画面に出す道具は入っていません。9-5-3「Eager Loadingとレイジーローディング」で使ったものを、わざわざ入れなくて構いません。ここで見るのは、コードに `with()` が書かれているかどうかです。

---

## 判定は1か所に集める

「消せるのは書いた本人だけ」という決まりは、ポリシーに書いても、コントローラーの中に `if` で書いても、画面の上での動きは同じになります。それでも、1か所に集めておくほうが後で困りません。

同じ判定が2か所に書かれていると、片方だけ直したときに食い違います。将来「投稿を書いた人も、その投稿へのコメントを消せる」に変えるとします。判定がポリシーに1つだけあれば、直すのは1か所です。コントローラーと画面の両方に条件が書いてあれば、片方を直し忘れたときに、ボタンは出るのに押すと403になります。

画面から隠すだけでは止められない、という事情もあります。このアプリでも、他人の投稿の編集画面を直接URLで開くと403になります。ボタンを消しても、URLを直接打たれたら通ってしまうので、止めるには処理そのものの手前に判定が要ります。

読むときに見るのは、判定の文が同じかどうかよりも、その判定がどこに何回書かれているかです。

## AIが書いたコードで、特に見るところ

上の観点は、人が書いたコードでも見るところです。ここからの2つは、指示を受けて一気に書き上げるという作り方から出てきます。

**テストが、実装をなぞっていないか**

実装とテストを同時に書かせると、できあがったコードが通ることだけを確かめるテストになることがあります。設計書に本文の文字数の上限を書いたなら、テストが上限を1文字超えた本文を送っているかを、その1本だけ開いて確かめてください。上限ちょうどの本文を送っていれば、そのテストは通っても意味がありません。

**説明と実物が合っているか**

AIは、作業のあとに「〜を追加しました」という報告を出します。報告に書かれていることが差分の中にあるか、差分にあることが報告に書かれているかを見ます。食い違ったときに信じるのは、差分のほうです。

## 引っかかったところを直させる

見つかったら、名指しで直させます。

```text
app/Http/Controllers/CommentController.php の store で、
Comment::create($request->all()) の形になっています。
docs/comment.md の入力チェックのとおりに validate() を通して、
その結果と、ログイン中のユーザーのIDだけを渡す形に直してください。
ほかのファイルは変えないでください。
```

> 💡 このお願いのポイントは、①どのファイルのどのメソッドかを名指ししている ②どう直すかを設計書を根拠に書いている ③触ってほしくない範囲を書いている、の3点です。②が抜けると、直し方をAIが決めることになります。

直させると、また差分が出てきます。読み方は同じ3段です。

---

## 🏃 物差しを先に開いておく

差分が出てきてから比べる相手を探すと、そこで手が止まります。先に開いて、形だけ見ておきます。

### Step 1: 投稿一覧のコントローラーを開く

VS Codeで `app/Http/Controllers/PostController.php` を開き、`index()` を見てください。上に載せたとおりの形になっているはずです。手元のものが違っていたら、実物であるそちらが物差しです。

### Step 2: 投稿一覧の画面を開く

`resources/views/posts/index.blade.php` を開き、次の2か所を探してください。

- `@can('update', $post)` と `@can('delete', $post)` で、編集・削除のボタンを出し分けている箇所
- ログアウトのフォームの中にある `@csrf`

開き終えたら、次の3つを確かめてください。

- [ ] `PostController::index()` に `with(['user', 'category'])` が付いていることを見た
- [ ] `posts/index.blade.php` の `@can` と `@csrf` の書き方を見た
- [ ] コメント機能で当てる観点を、上の表から選んだ

## ✨ まとめ

- 差分は、プルリクエストができた時点で `gh pr diff` から読めます。名前だけなら `--name-only`、ブラウザで読むなら `--web` です。
- 読む順番は、設計書との突き合わせ、触っていないはずの場所、中身の3段です。
- 1段目で探すのは、書いたものの有無よりも、書いていないものが増えていないかです。`composer.json` は名前だけ覚えておきます。
- 2段目で見落とすのは、消えた行です。飛ばしても違和感が出ないので、`-` の行を先に探します。
- 3段目に入る前に、この機能に当たる観点を絞ります。比べる相手は、投稿一覧のコードが持っています。
