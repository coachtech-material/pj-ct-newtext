## 仕様駆動開発とは

**仕様駆動開発**（Spec-Driven Development。頭文字を取って **SDD** とも呼びます）は、作るものの仕様を先に文章として固め、それをAIに渡して実装させる進め方です。段は次の順に並びます。

```mermaid
flowchart LR
    A[要件] --> B[設計] --> C[タスク] --> D[実装]
```

14-3-3でたどったのは、この並びの要件・設計・実装にあたります。イシューに書いた要望と受け入れ条件が要件、`docs/reply.md` が設計、それを渡して走らせたところが実装です。タスクの段（設計を作業の単位に割る）だけ通りませんでした。リプライ機能は1回のやり取りで終わる大きさで、割る相手が無かったためです。

公式ドキュメントのベストプラクティスにも同じ形が載っています。AIに質問させて仕様を1つのファイルに書き起こさせ、書き終えたら新しいセッションを起動してそれを実行させる、という手順です（2026年8月時点）。

## 仕様駆動開発のツール

この流れを決まった手順として用意したツールが、いくつか公開されています（2026年8月時点）。

| 名前 | 何か | 入口 |
|:--|:--|:--|
| **Spec Kit** | GitHubが公開しているオープンソースのツール。Claude Code以外の同じような道具とも使えます | `https://github.com/github/spec-kit` |
| **Kiro** | AWSが作って運用しているもの。VS Codeのようなコードを書く画面・ターミナル・ウェブから使えます | `https://kiro.dev/` |
| **cc-sdd** | Claude Codeにこの流れを足すもの。コマンド1本で入ります | `https://github.com/gotalab/cc-sdd` |

3つとも、やっていることはほぼ同じです。1つだけ中身を見ておきます。

<details>
<summary>⚙️ cc-sddで何が入り、何ができるようになるのか（クリックで展開）</summary>

投稿アプリのフォルダで、次の1行を打つと入ります。日本語で書かせたいので `--lang ja` を付けています（2026年8月時点）。

```bash
npx cc-sdd@latest --lang ja
```

`npx` は、パッケージを入れずにその場で1回だけ実行するコマンドです（14-1-2で入れたNode.jsに付いてきます）。

打ち終わると、フォルダはこうなります（2026年8月時点）。

```text
（アプリのフォルダ）
├── CLAUDE.md                    ← 無ければ作られる（14-1-3で作ったものがあれば、そのまま）
├── .claude/
│   └── skills/                  ← /kiro- で呼び出すものが17本
│       ├── kiro-steering/
│       ├── kiro-spec-requirements/
│       └── ...
└── .kiro/
    └── settings/
        └── templates/           ← 書かせる文書のひな形
            ├── steering/        ← product.md・tech.md・structure.md
            └── specs/           ← requirements.md・design.md・tasks.md
```

入るのはこれだけです。ひな形と呼び出しが置かれただけで、中身のある文書はまだ1つもありません。

足された `/kiro-` の呼び出しのうち、主なものはこれです。

| 呼び出すもの | 何をするか |
|:--|:--|
| `/kiro-steering` | プロダクト全体の前提を書き出させる。既にあるコードから起こすこともできる |
| `/kiro-discovery` | やりたいことを渡すと、整理して、次にどれを打てばよいかを教えてくれる |
| `/kiro-spec-init` | その機能ぶんの置き場所を作る |
| `/kiro-spec-requirements` | 要件と受け入れ条件を書かせる |
| `/kiro-spec-design` | 設計を書かせる。Mermaidの図と、どのファイルを触るかの一覧が付く |
| `/kiro-spec-tasks` | 設計を実装の作業単位に割る |
| `/kiro-impl` | 割った作業を、1つずつ実装させる |

上から順に打っていくと、書かれたものが `.kiro/` の下に貯まっていきます。**置き場所は2つに分かれます。**

```text
.kiro/
├── steering/                    ← プロダクト全体の前提（/kiro-steering が書く）
│   ├── product.md               ← 何を作っているのか
│   ├── tech.md                  ← 何で作っているのか
│   └── structure.md             ← どこに何を置くのか
└── specs/                       ← 機能1つにつき1フォルダ
    └── reply/                   ← 例: リプライ機能
        ├── requirements.md      ← 要件と受け入れ条件
        ├── design.md            ← 設計
        └── tasks.md             ← 実装の作業単位
```

`steering/` は1組だけで、`specs/` の下は機能を作るたびに増えていきます。

14-3-3では、この並びを自分で依頼文に書いて進めました。それが呼び出しとして用意されていて、書いたものの置き場所まで決まっている形です。

新しく始めるプロジェクトでも、途中まで作ってあるプロジェクトでも使えます。後者の場合は `/kiro-steering` が既にあるコードを読んで、プロダクト全体の前提のほうを起こします。

**この教材では入れません。** 理由は次に書きます。ただ、読んで気になったなら、自分の投稿アプリとは別のフォルダを作って、1機能ぶん通してみるのは勧められます。同じことを14-3-3では自分の依頼文でやっているので、決まった手順に乗せると何が楽になって、何が増えるのかを、比べられる状態にあります。

</details>

## 仕様書は2種類ある

ここからが、この教材がツールを使わなかった理由です。ただし、使わなかったのは**片方だけ**です。

さきほど `.kiro/` の下が2つに分かれていたとおり、仕様駆動開発が持つ仕様書は2種類あります。寿命が違います。

| 種類 | 何が書いてあるか | いつまで要るか |
|:--|:--|:--|
| プロダクト全体のもの（steering） | 何を作っているのか、何で作っているのか、どこに何を置くのか | プロジェクトが続くあいだずっと |
| 機能1つぶんのもの（spec） | その機能の要件・設計・タスク | その機能を作り終えるまで |

上は、コードを1行変えても古くなりません。「Laravelで作っている」「コントローラーは `app/Http/Controllers/` に置く」は、機能を1つ足したくらいでは変わらないためです。**これは持ち続ける側です。** 14-1-3で作った `CLAUDE.md` が、同じ役割の1枚でした。それを話題ごとのファイルに分けて、もっと具体的に書いたものだと考えてください。分けて持つやり方は、Tutorial 15で扱います。

## 機能ぶんの仕様書が古くなる

機能1つぶんの仕様書には、テーブルの列も、画面に並ぶものも、入力チェックのメッセージも書いてあります。**どれもコードに書いてあることです。** 同じことが2か所にある状態から始まります。

実装が進めば、変わるのはコードのほうが先です。実装の途中で列の名前を変えれば、コードは変わり、仕様書は前のままになります。14-3-1で「設計書もずっとは持たない」と書いたのは、これが理由でした。

古くなった仕様書が置いてあるだけなら、人にとっては実害がありません。読まなくなるだけです。効いてくるのは、AIに渡すときです。

**古い仕様書は、AIにとっては現在の指示です。** もう使っていない画面や、消したはずの項目が書いてあれば、そのとおりに作り直します。人が読めば「これは前の話だ」と分かるところで、AIは気づきません。人が2つを見比べて気づくよりも先に、AIは書かれたとおりに手を動かします。

避ける道は2つです。コードを変えるたびに仕様書も直し続けるか、機能を作り終えた時点で捨てるか。前者は、機能が増えるだけ手入れが増えます。**この教材は後者を採りました。** `docs/reply.md` は、Chapter 4で受け取りを終えるまでの材料です。

捨てるのは、書いたファイルのほうだけです。仕様を考える工程は残ります。何を作るのか、どうなったら完成かを決める作業は、実装をAIに任せる量が増えるほど重くなります。14-3-3で設計書を読んで直させた時間が、そのまま出来上がりの質になっていました。

## 実装が終わったあとに残るもの

機能ぶんの仕様書を捨てても、プロジェクトが何も持たない状態にはなりません。

| 残るもの | どこにあるか | 扱った節 |
|:--|:--|:--|
| 何を作ったか | コードとテスト | 14-3-3 |
| なぜそう作ったか | コミットメッセージ、プルリクエストの本文 | 12-2-3・14-4-5 |
| 何を作っているのか、どう開発するのか | `CLAUDE.md` | 14-1-3 |

いちばん上はコードの側が持ち、下の2つは人が書いて残します。**何を作ったか**はコードに任せ、**なぜそう作ったか**と**どう開発するのか**を人が持つ。捨てたあとに手元へ残るのは、この分け方です。

いちばん下は、先ほどの表の上の行（プロダクト全体のもの）にあたります。この1枚を育てて、話題ごとに分けて持っていく作業が、Tutorial 15の中身です。

## ✨ まとめ

- 要件 → 設計 → タスク → 実装 の順に進める作り方を、仕様駆動開発（SDD）と呼ぶ。14-3-3で通したのはこの並び。
- この流れをコマンドにしたツールがある（Spec Kit・Kiro・cc-sdd）。要件から実装までを1段ずつ進める形は、14-3-3で自分の依頼文でやったことと同じ。
- 仕様駆動開発の仕様書は2種類。プロダクト全体のものは持ち続け、機能1つぶんのものは作り終えたら捨てる。
- 機能ぶんの仕様書は、書いてあることがコードと重なる。実装が進むとコードのほうが先に変わり、仕様書は古くなる。
- 古い仕様書はAIには現在の指示に見えるので、要らないものを作り直させる。人が気づくより先に手が動く。
- 捨てるのはファイルで、仕様を考える工程ではない。
- 実装のあとに人が残すのは、なぜそう作ったか（コミットとプルリクエスト）と、プロダクト全体の前提（`CLAUDE.md`）。何を作ったかはコードとテストが持つ。
