# 13-6-3: 例外設計 - 外れた時を先に決める

## 🎯 このセクションで学ぶこと

- うまくいかない場合を、3つの問いを使って設計書から洗い出せるようになる。
- 洗い出した1つずつに、システムが何をするのかまで決めて例外一覧にできるようになる。
- まとめて成功・まとめて失敗させる範囲をどこまでにするかを決め、その外に出すものを言えるようになる。

---

## 導入：決めておかないと、気づいた人しか書かない

13-6-1 のシーケンス図も、13-6-2 の状態遷移図も、うまくいったときの絵でした。頼んだ相手は必ず答え、書き込みは必ず成功し、押されたボタンはいつも受け付けられます。実際には、そのどれもが外れます。

外れたときにどうするかは、決めなくても実装は進みます。進んでしまうところが問題で、その場で気づいた人が、気づいたぶんだけ処理を書きます。気づかなかったぶんは、何も起きないまま公開されます。同じ「見つからなかったとき」が、ある画面では丁寧に案内され、別の画面では真っ白になります。

10-4-2「エラーハンドリング」では、起きてしまったエラーをどう処理するかを学びました。このセクションで扱うのは、その手前です。🔑 **起きうることを、起きる前に洗い出す**ところだけを学びます。作るのは、**例外一覧**（うまくいかなかった場合を先に洗い出し、そのときどうするかを決めた表）です。

「うまくいかないとき」を扱う設計書は、これで3つ目になります。すでに2つ作ってあるので、書く場所を先に切り分けておきます。

| 設計書 | 決めること | 書かないこと |
|:-------|:-----------|:-------------|
| メッセージ一覧（13-3-4） | どの画面の、どんな場面で、どんな文言を出すか | なぜそれが起きるのか。システム側の処置 |
| エラーレスポンス一覧（13-4-1） | 自分が作るAPIが返すステータスコードと、その中身 | 外の仕組みで起きたこと。画面の文言そのもの |
| 例外一覧（このセクション） | どんな異常がありうるか。どこで気づくか。システムが何をするか。誰に何を伝えるか | 文言そのもの。返すステータスコードの形 |

だから例外一覧には、文言もステータスコードも書きません。同じことを3か所に書くと、直すときに3か所とも直す必要が出て、たいてい1か所が取り残されます。

> ⚠️ **注意**: サーバーが落ちたときや、回線が切れたときにどう耐えるかは、13-1-2 で挙げたとおりこの教材では扱いません。ここで洗い出すのは、仕組みが動いている中で起こりうる外れ方だけです。

## 例外一覧の読み方

題材は、13-6-1・13-6-2 と同じ宅配便の再配達受付です。あのシーケンス図の矢印と、あの状態遷移図から洗い出したのが、次の表です。

| 起きること | どこで気づくか | そのときの処置 | 利用者への知らせ |
|:-----------|:---------------|:---------------|:-----------------|
| 入力された不在票の番号が見つからない | 番号を確かめるとき | やめて元に戻す | 番号が見つからないことと、もう一度お確かめいただきたいこと |
| 選ばれた日時が、すでに埋まっている | 日時を押さえるとき | やめて元に戻す | その日時が埋まったことと、選び直していただきたいこと |
| 依頼を書き込む途中で失敗した | 依頼を登録するとき | やめて元に戻す（押さえた日時も戻す） | 受け付けられなかったことと、もう一度お試しいただきたいこと |
| すでに取り消された依頼を、もう一度取り消そうとした | 依頼の状態を見るとき | やめて元に戻す | すでに取り消されていること |
| 配達員の端末へ、受け付けた依頼を知らせられなかった | 知らせを送るとき | 待って、3回までやり直す。それでも送れなければ、人が電話で伝える | 知らせない（受け付けは済んでいるため） |

5行目だけは、13-6-1 のシーケンス図に描かなかったやり取りから拾っています。あの図は受け付けが終わるまでの1本で、受け付けたあとに配達員の端末へ知らせる流れは、そこには出てきません。1枚の図に描いた範囲だけが材料ではない、ということです。

いちばん左の欄が、日本語の1文になっているところから見てください。13-4-1 でエラーレスポンス一覧を作ったときと同じ形です。「404」のようなステータスコードや、プログラムの例外の名前を書いても、実装する人には「どういうときの話なのか」が伝わりません。

**3行目が、この表でいちばん大事な行です**。2行目で日時を押さえてから、依頼を書き込むまでの間に失敗すると、押さえたままの日時が残ります。誰の依頼でもない日時が埋まったままになり、他の方がその枠を選べなくなります。処置の欄に「押さえた日時も戻す」と書いてあるのは、**どこまで戻すか**を決めたということです。

**5行目だけ、処置が違います**。知らせが送れなくても、再配達の受け付け自体は成立しています。ここで受け付けごと無かったことにすると、無事に申し込めた方の依頼まで消えます。そこで、書き込んだものは戻さずに、時間を置いて送り直す形にしました。送り直せば届く見込みがあるからです。送り直す回数と、それでも送れなかったときにどうするかまで、この欄に書いてあります。

**5行目の「利用者への知らせ」も見てください**。空欄にせず、「知らせない」と書いてあります。これは、伝えないと決めたということです。13-2-2 で、無いものには「なし」と書くと学んだのと同じで、決めたのか書き忘れたのかを読む人が区別できます。

## 例外一覧の書き方

思いついた順に並べると、必ず抜けます。材料はすでに手元にあるので、そこから機械的に拾います。

**書く手順**

1. シーケンス図の矢印を1本ずつ、下の3つの問いにかけて洗い出します。
2. 洗い出した1つずつに、下の3つの型から処置を決めます。
3. 「やめて元に戻す」を選んだ行があれば、まとめて失敗させる範囲を決めます。
4. 4つの列に書き出します。

**洗い出しの3つの問い**

| # | 問い | 見る場所 |
|:--|:-----|:---------|
| 1 | この矢印は、返ってこないことがあるか | 13-6-1 のシーケンス図の矢印を、1本ずつ |
| 2 | この矢印は、頼んだとおりにならないことがあるか | 同じ矢印を、見つからない・すでに埋まっている・許されていない、という目で見る |
| 3 | この矢印が届いたとき、相手が違う状態になっていることがあるか | 13-6-2 の状態遷移図と突き合わせる |

問い3が、いちばん見つけにくいものを拾います。人は、画面を見てからボタンを押します。その間に時間が流れているので、押した時点では、見たときと違うことになっている場合があります。宅配便の表の4行目がそれで、シーケンス図だけを見ていても出てきません。

**処置の3つの型**

洗い出したら、1つずつに処置を決めます。この教材では、次のどれかを書きます。

| 型 | 何をするか | どんなときに選ぶか |
|:---|:-----------|:-------------------|
| やめて元に戻す | そこまでにデータへ書き込んだことを、無かったことにする | そのまま続けても、意味のある結果にならないとき |
| そのまま進める | 失敗したことは記録に残し、本筋は止めずに先へ進める | あとで集計に使う記録を残せなかったときのように、失敗が本筋の結果に関わらないとき |
| 待って、決められた回数だけやり直す | 時間を置いて、もう一度同じことを頼む | 相手が答えないだけで、頼み直せば通る見込みがあるとき |

1つ目は、まだ何も書き込んでいない場面でも選びます。「そこから先へは進めず、書き込んだものがあれば無かったことにする」という意味で使ってください。番号が見つからない、パスワードが合わない、といった入り口で止まる場合も、この型になります。

2つ目は、上の表には出てきません。宅配便でいえば、受け付けた件数を数えるための記録を残せなかった場面が、これにあたります。数が1件ずれても、再配達の受け付け自体は成立しているので、そこでは止めません。

3つ目を選んだときは、何回まで頼み直すのかと、それでも駄目だったときにどうするのかも決めます。ここを決めずに書くと、いつまでも頼み続ける処理ができあがります。

処置の欄に「エラーを出す」と書きたくなりますが、それは処置になっていません。エラーを出したあと、書きかけたデータをどうするのかが決まっていないからです。3つのどれにも当てはまらないものが出てきたら、処置がまだ決まっていない、ということです。13-2-1 で学んだとおり、想定を添えて確認事項リストへ送ります。

**まとめて成功、まとめて失敗させる範囲を決める**

「やめて元に戻す」を選んだら、🔑 **どこからどこまでを1かたまりにするか**を決めます。宅配便の3行目なら、日時を押さえたところから依頼を書き込むところまでが1かたまりで、途中で失敗したら両方とも無かったことにする、という決定でした。9-3-7「トランザクション処理」で読んだ、まとめて成功・まとめて失敗させる仕組みが、これにあたります。書き方は 9-3-7 が持っているので、設計として決めるのは範囲だけです。

書き込む先が1か所しかない流れでは、この範囲を決める場面がありません。範囲が問題になるのは、2か所以上へ書き込む流れです。

範囲を決めるときの目安が1つあります。**戻せるのは、自分たちのデータベースの中だけ**です。外の仕組みへ出してしまった依頼は、こちらから無かったことにできません。相手の中でもう進んでいるからです。だから、外の仕組みへの依頼は、かたまりの中に入れずに外へ出します。

外へ出すと決めたら、外へ出したあとに失敗したときの行が、例外一覧に1行増えます。

**列と、埋めるときの決めごと**

列は `起きること`・`どこで気づくか`・`そのときの処置`・`利用者への知らせ` の4つで固定します。

- 「起きること」は日本語の1文で書きます。ステータスコードや、プログラムの例外の名前は書きません。
- 「どこで気づくか」には、その異常に最初に気づける場所を書きます。「番号を確かめるとき」「支払いの結果を受け取るとき」のように、シーケンス図の矢印を指せる書き方にします。
- 「そのときの処置」には、3つの型のどれかを書きます。戻す範囲が特別なときや、型の名前だけでは伝わらない動き（どこへ送るか、どれくらいの間その操作を受け付けないか）があるときは、括弧で書き添えます。
- 「利用者への知らせ」には、何を伝えるかを日本語で書きます。文言そのものは書きません。伝えないと決めた行には「知らせない」と書きます。

## 🏃 書いてみよう

宅配便の再配達受付は、読む練習でした。今度は、手元の投稿アプリで書きます。材料は2つあります。13-6-1 で描いたシーケンス図と 13-6-2 で描いた状態遷移図、それにアプリのコードです。

コードには、外れたときの決まりが3か所に書いてあります。1か所目は、ログインが必要なルートの囲みと、ログインしていない人の行き先です。

```php
// routes/web.php
// 認証が必要なルート
Route::middleware('auth')->group(function () {
    Route::get('/posts', [PostController::class, 'index'])->name('posts.index');
    Route::get('/posts/{post}/edit', [PostController::class, 'edit'])->name('posts.edit');
    Route::put('/posts/{post}', [PostController::class, 'update'])->name('posts.update');
    Route::delete('/posts/{post}', [PostController::class, 'destroy'])->name('posts.destroy');
});
```

```php
// app/Http/Middleware/Authenticate.php
    protected function redirectTo(Request $request): ?string
    {
        return $request->expectsJson() ? null : route('login');
    }
```

2か所目は、誰が編集してよいかの判定と、送られてきた入力の確かめ方です。

```php
// app/Policies/PostPolicy.php
    public function update(User $user, Post $post): bool
    {
        return $user->id === $post->user_id;
    }
```

```php
// app/Http/Controllers/PostController.php（update の一部）
        $validated = $request->validate([
            'title' => 'required|string|max:255',
            'content' => 'required|string',
            'category_id' => 'required|exists:categories,id',
        ]);
```

3か所目は、ログインを何度も試されたときの制限です。

```php
// app/Providers/FortifyServiceProvider.php
        RateLimiter::for('login', function (Request $request) {
            $throttleKey = Str::transliterate(Str::lower($request->input(Fortify::username())).'|'.$request->ip());

            return Limit::perMinute(5)->by($throttleKey);
        });
```

### Step 1: コードが決めている外れ方を、表に写す

上の3か所から、外れたときの決まりを読み取って、例外一覧の行にします。1つの行につき、4つの欄が埋まるかを確かめてください。

埋まらない欄が出てきます。コードは「どうするか」までは決めていても、「利用者に何を伝えるか」を決めていないことが多いからです。空欄のままにせず、自分の想定を1つ書き入れてください。想定でよいのか迷うものは、Step 3 と同じように確認事項リストへ送ります。

### Step 2: 書かれていない外れ方を、3つの問いで見つける

13-6-1 で描いたシーケンス図を開いて、矢印を1本ずつたどります。問い1と問い2を当ててください。ブラウザから送られる矢印、`Post` からデータベースへ向かう矢印、それぞれで外れ方が違います。

そのあと、13-6-2 で描いた状態遷移図と突き合わせて、問い3を当てます。投稿一覧を開いてから「編集」を押すまでの間に、その投稿がどうなっている可能性があるかを考えてください。時間が流れているあいだに起きうることが、この問いで拾えます。

ログインしている状態にも同じ問いを当てます。ログインが「続いている」と「切れている」の2つの間を動くと考えてください。画面を開いたまま席を外して、しばらくしてから操作したときが、その場面です。

### Step 3: 「1分間に5回まで」の根拠を確認事項リストへ送る

上のコードには `perMinute(5)` と書いてあります。この数字を例外一覧に書き残すとき、なぜ5回なのかを自分が説明できるかどうかを試してください。

説明できないなら、13-3-4 で入力の決まりの数字に理由を残したときと同じ場面です。想定を添えて確認事項リストへ送る形にしてください。

### Step 4: リポジトリに保存する

`docs/13-6/` に保存します。ファイル名の先頭は、13-6-1・13-6-2 と同じ `post-` です。

VS Codeで `docs/13-6/post-exceptions.md` を新しく作り、4列の表を書きます。Step 3 で作った1行は、13-2-1 で作った確認事項リスト（`docs/13-2/post-questions.md`）の続きの番号に足してください。13-2-1 の解答例は `Q-05` まで埋まっているので、続きは `Q-06` になります。新しいファイルは作りません。

確認事項リストは `docs/13-2/` にあるので、コミットには両方のフォルダを含めます。

```bash
# アプリのフォルダの中で実行する
git add docs/13-2 docs/13-6
git commit -m "13-6: 投稿アプリの例外一覧を追加"
git push origin main
```

**迷いやすいところ**

- **まとめて失敗させる範囲を決めなかった理由**: この流れで書き込むのは `posts` の1行だけです。1か所への書き込みは、それ自体が成功か失敗のどちらかにしかならないので、範囲を決める場面がありません。カフェのモバイルオーダーアプリでは、注文と注文明細の2か所へ書き込みます。範囲を実際に決めるのは 13-6-4 です。
- **「カテゴリが無くなっていた」を残した理由**: いまのアプリに、カテゴリを消す機能はありません。だから、この行の異常は起きません。それでも表に残したのは、`exists:categories,id` という確かめがコードに書かれているからです。確かめが書かれているということは、外れる場合があると誰かが考えたということです。カテゴリを管理する機能を足した日に、この行が生きてきます。反対に、落とすと決めるなら「起きないと判断した」ことを1行残します。
- **編集の可否と入力の確かめを、別の行にした理由**: 気づく場所が違います。編集してよいかの判定は `PostPolicy` が受け持ち、入力の中身は `PostController` が確かめます。処置は同じ「やめて元に戻す」ですが、どこで止まるかが違えば、伝える内容も変わります。13-4-2 で権限マトリクスを作ったときに決めたことが、ここでは外れ方として現れます。

## 💡 よくある間違いと現場での使われ方

**間違い1: 処置の欄に、画面に出す文言を書く**

画面に何を出すかは、13-3-4 のメッセージ一覧が持っています。この欄に書くのは、3つの型のどれかです。

**間違い2: 洗い出しを、画面の入力チェックで済ませる**

入力欄の決まりごとは 13-3-4 で決めました。この表が拾うのは、入力が正しくても外れる場合です。投稿のIDは正しい形なのに、そのIDの投稿がもう無い。カテゴリは選べる形なのに、押した時点では消えている。どちらも入力チェックでは止まりません。

**間違い3: 起きにくいものを、起きないものとして落とす**

「ほとんど起きないから」と落とすと、起きたときに何も決まっていない状態になります。落とすなら、落とすと決めたことを1行残します。起きたときにどうなるかを、その場で誰かが決められるからです。

現場では、例外一覧は実装が終わったあとの確認にも使われます。「この行の場合を試したら、どうなるか」を上から順に確かめれば、決めたとおりに動いているかを見られるからです。反対に、この表が無い状態で外れた場合を試すと、確かめる人が「これは正しい動きなのか、不具合なのか」を判断できません。

## ✨ まとめ

- うまくいかない場合は、起きてから処理を書くのではなく、起きる前に洗い出して処置まで決めます。10-4-2 で学んだ処理の書き方は、決めたあとの話です。
- 洗い出しは、3つの問いで進めます。返ってこないことはあるか、頼んだとおりにならないことはあるか、届いたときに相手が違う状態になっていることはあるか。材料は 13-6-1 と 13-6-2 で描いた図です。
- 処置は「やめて元に戻す」「そのまま進める」「待って、決められた回数だけやり直す」の3つから選びます。「エラーを出す」は処置になりません。どれにも当てはまらないものは、確認事項リストへ送ります。
- 「やめて元に戻す」を選んだら、まとめて成功・まとめて失敗させる範囲を決めます。この範囲は1枚の紙になる成果物ではなく、処置の欄の書き方として現れます。書き込む先が2か所以上ある流れで、はじめて決める場面が来ます。
- 例外一覧は `起きること`・`どこで気づくか`・`そのときの処置`・`利用者への知らせ` の4列です。文言もステータスコードも書きません。それぞれ 13-3-4 と 13-4-1 が持っています。
