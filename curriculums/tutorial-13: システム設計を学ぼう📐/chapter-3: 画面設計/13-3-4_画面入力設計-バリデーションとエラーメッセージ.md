# 13-3-4: 画面入力設計 - バリデーションとエラーメッセージ

## 🎯 このセクションで学ぶこと

- 入力欄ごとに、どこまでの値を受け付けるのかを、実装より先に決めて表にできるようになる。
- 決めた数字に、そう決めた理由を残せるようになる。
- 画面に出す文言を、実装より先に決めて一覧にできるようになる。

---

## 導入：受け付ける範囲は、コードを書きながら決まってしまう

「お名前は必須」と決まっても、100文字のお名前を受け付けるかは決まっていません。電話番号にハイフンが入っていたとき、エラーにするのか、ハイフンを取って受け付けるのかも決まっていません。

こうした決めごとは、決めなくても実装が進みます。進んでしまうのが問題です。手を動かしている人が、その場で「50文字くらいでいいか」と決めて書き、そのままリリースされます。半年後に「名前が入りきらない」と問い合わせが来て、なぜ50文字なのかを聞かれても、誰も答えられません。

入力の決まりごとをコードでどう書くかは、9-6「入力の制約」の章でバリデーションとして学びました。このセクションで扱うのは、その手前です。🔑 **書く前に決めて、書き残す**ところだけを学びます。作るのは、入力チェック表とメッセージ一覧です。

- **入力チェック表**（入力欄ごとに、どんな値まで受け付けるかを決めた表）
- **メッセージ一覧**（画面に出す知らせの文言をまとめた表）

---

## 入力チェック表の読み方

13-3-3で画面項目定義を作った、歯科医院の予約アプリの連絡先入力画面から起こした表です。

| 画面 | 項目 | 必須 | 文字数・桁数 | 形式・値の範囲 | ほかの項目との関係 |
|:-----|:-----|:-----|:-------------|:---------------|:-------------------|
| 連絡先入力画面 | お名前 | 必須 | 30文字以内 | - | - |
| 連絡先入力画面 | 電話番号 | 必須 | 10桁または11桁 | 半角数字のみ | - |
| 連絡先入力画面 | メールアドレス | 任意 | - | メールアドレスの形 | ご希望の連絡方法が「メール」のときは必須 |
| 連絡先入力画面 | ご希望の連絡方法 | 必須 | - | 「電話」「メール」のどちらか1つ | - |

画面項目定義には7行ありましたが、この表は4行で終わっています。引き継ぐのは🔑 **入力と選択の行だけ**だからです。見出しやボタンには、利用者が値を入れないので、受け付ける範囲もありません。

「必須」の欄は、画面項目定義に書いたものと同じ値です。同じことを2か所に書いているように見えますが、この表だけを見て実装できるようにするための重複です。

いちばん右の欄を見てください。メールアドレスは「任意」なのに、条件によっては必須になると書かれています。ひとつの欄だけを見ていては決まらない決めごとが、ここに現れます。この行が無いと、実装した人は「任意」だけを読んで、連絡方法にメールを選んだ患者からメールアドレスを聞かずに予約を受け付けてしまいます。

決めることが無い欄には `-` を書きます。この `-` は「検討したうえで、決めることが無かった」という意味です。「まだ決めていない」ものを `-` で埋めてはいけません。それは13-2-1で学んだとおり、確認事項リストへ回します。

## 入力チェック表の書き方

画面項目定義の入力と選択の行を上から順にたどり、1行ずつ次の問いかけをします。

1. 空のままでもよいか。
2. どのくらいの長さ・桁数まで受け付けるか。
3. どんな形の値なら受け付けるか。数なら、どこからどこまでか。
4. すでに登録されているものと、同じ値が入ってよいか。
5. ほかの項目の入り方によって、答えが変わることはあるか。

1つ目が「必須」の欄、2つ目が「文字数・桁数」の欄、3つ目が「形式・値の範囲」の欄になります。4つ目と5つ目は、どちらもその欄だけを見ていては決まらない話なので、まとめて「ほかの項目との関係」の欄に書きます。

逆に、その欄だけを見ても決まりごとが1つも決まらず、ほかの項目との関係だけが決まる入力欄もあります。同じ値をもう一度入れてもらって、打ち間違いを防ぐための欄が代表です。こうした欄は独立した行にせず、相手の行の「ほかの項目との関係」に書きます。入力欄の数と表の行数が一致しないことがあるのは、このためです。

**実装の言葉で書かない**

問いかけを日本語のまま並べたのには理由があります。設計書は依頼者にも読んでもらうものなので、`max:50` のようなルール名で書くと、決めた内容を確認してもらえません。「30文字以内」と書いてあれば、受付の方が「お名前が30文字を超える患者さんはいませんね」と判断できます。

> 💡 **TIP**: ここで決めた内容は、実装のときに9-6-2「バリデーションルール」で学んだルールへ置き換わります。設計書はその手前の、日本語で合意する段階です。

**決めた理由を残す**

表の下に、数字を決めた理由を1〜2行添えます。歯科医院の予約アプリなら、次のように書きます。

> お名前の30文字は、診察券に印字できる長さに合わせました。電話番号の10桁または11桁は、固定電話と携帯電話の両方を受け付けるためです。

理由が残っていれば、「もっと長くできませんか」と聞かれたときに、何と何がぶつかるのかをその場で答えられます。理由が残っていないと、決め直しのたびに同じ議論を最初からやることになります。

**決めきれない数字は、自分で決めない**

電話番号を「半角数字のみ」と決めたとき、ハイフン付きで入力されたらどうするのかで手が止まります。ここで「エラーにしよう」と自分で決めてしまうと、その判断は自分の頭の中にしか残りません。13-2-1で学んだとおり、想定を添えて確認事項リストへ1行足します。「電話番号はハイフンを入れずに入力していただく想定です。ハイフン付きで入力された場合も受け付ける必要はありますか」と書いておけば、返事を待つあいだも、想定の上で先へ進めます。

> 💡 **TIP**: 5-1-6「フォームの基礎」で学んだ `required` 属性を付けると、空のまま送信ボタンを押してもブラウザが送信を止めてくれますが、受け取る側に同じ値が届く保証にはなりません。9-6で学んだ入力チェックは、受け取る側にも置きます。設計書に書くのは、どちらの側の話でもなく「どこまで受け付けるか」だけです。

## メッセージ一覧の読み方

受け付けられなかったとき、画面には何が出るのか。それを先に決めたのが、メッセージ一覧です。同じ連絡先入力画面の分を見てください。

| 画面 | 出る場面 | 区分 | メッセージ |
|:-----|:---------|:-----|:-----------|
| 連絡先入力画面 | お名前が空のまま「入力内容を確認する」を押した | エラー | お名前を入力してください |
| 連絡先入力画面 | お名前が30文字を超えている | エラー | お名前は30文字以内で入力してください |
| 連絡先入力画面 | 電話番号が空のまま「入力内容を確認する」を押した | エラー | 電話番号を入力してください |
| 連絡先入力画面 | 電話番号が10桁でも11桁でもない | エラー | 電話番号は10桁または11桁で入力してください |
| 連絡先入力画面 | 電話番号に数字以外が入っている | エラー | 電話番号は、ハイフンを入れずに半角数字で入力してください |
| 連絡先入力画面 | メールアドレスの形になっていない | エラー | メールアドレスは、@を含む形で入力してください |
| 連絡先入力画面 | ご希望の連絡方法を選ばずに「入力内容を確認する」を押した | エラー | ご希望の連絡方法を選んでください |
| 連絡先入力画面 | ご希望の連絡方法に「メール」を選んだのに、メールアドレスが空 | エラー | ご希望の連絡方法が「メール」のときは、メールアドレスを入力してください |
| 予約完了画面 | 予約が確定した | 完了 | ご予約を承りました |

エラーの8行は、入力チェック表の決めごとと1つずつつながっています。「30文字以内」と決めたから、超えたときの文言が要る、という順です。表の欄を1つ埋めるたびに、この一覧に行が増えていくと考えてください。

ただし、決めごとがそのまま行になるとは限りません。「ご希望の連絡方法」には、必須という決めごとに対応する行はありますが、「『電話』『メール』のどちらか1つ」という決めごとに対応する行はありません。候補を2つ並べて選んでもらう作りにすれば、それ以外の値は入りようがないからです。🔑 **画面の作りだけで守られる決めごと**には、出す文言が要りません。

最後の1行だけ、区分が「完了」になっています。画面に出る文言は、うまくいかなかったときのものだけではありません。うまくいったときの知らせも、同じ一覧にまとめます。分けて管理すると、片方だけ文言を直して、言い回しがちぐはぐになります。

## メッセージ一覧の書き方

列は `画面`・`出る場面`・`区分`・`メッセージ` の4つです。区分に書くのは「エラー」と「完了」の2つだけにします。

「出る場面」の欄には、どんな操作の結果として出るのかを書きます。「入力エラー」とだけ書くと、どの欄の話なのかが分からず、実装する人が入力チェック表と突き合わせられません。

メッセージそのものには、IDを振りません。文言は変わりやすいので、番号で呼び合うより、画面と場面で指すほうが行き違いが起きにくいためです。

**文言の型を1つ決めて、全画面に通す**

文言は、書く人によって長さも語調もばらつきます。この教材では、次の順で1文にまとめる型を使います。

🔑 **どの項目が → どうなっているか → どうすればよいか**

「お名前は30文字以内で入力してください」なら、「お名前が」「30文字を超えている」「30文字以内で入力すればよい」の3つが1文に入っています。読んだ利用者は、次に何をすればよいのかで迷いません。

型を決めておくと、画面が増えても文言がそろいます。逆に、実装のときに思いついた言葉で書いていくと、同じ意味の知らせが画面ごとに違う言い回しになります。「入力してください」「ご入力ください」「未入力です」が同じアプリの中に並ぶのは、たいていこれが原因です。

> ⚠️ **注意**: システムの側でうまくいかなかった場合（保存に失敗した、外部の仕組みから返事が来ない、など）の洗い出しは、Chapter 6で扱います。ここで決めるのは、画面の入力に関する文言だけです。

## 🏃 書いてみよう

13-3-3で画面仕様を作った投稿アプリの投稿編集画面について、入力チェック表とメッセージ一覧を作ります。

材料は3か所にあります。1つ目は、受け取る側の入力チェックです。

```php
// app/Http/Controllers/PostController.php（update の抜粋）
    public function update(Request $request, Post $post)
    {
        $this->authorize('update', $post);

        $validated = $request->validate([
            'title' => 'required|string|max:255',
            'content' => 'required|string',
            'category_id' => 'required|exists:categories,id',
        ]);

        $post->update($validated);

        return redirect()->route('posts.index');
    }
```

2つ目は、`posts` テーブルの列の作り方です。

```php
// database/migrations/2024_01_01_000001_create_posts_table.php（抜粋）
            $table->string('title');
            $table->text('content');
```

`string` はMySQLの `VARCHAR(255)` になる型で、`text` はもっと長い文章を入れられる型です。8-1-3「テーブル、カラム、レコードの理解」で見た型の使い分けが、ここに出てきています。

3つ目は、画面に出る文言です。13-3-3で読んだ `edit.blade.php` には、こう書かれていました。

```blade
                @error('title')
                    <p class="error">{{ $message }}</p>
                @enderror
```

`{{ $message }}` に入る文言は、このリポジトリのどこにも書かれていません。Laravelが用意している既定の文言がそのまま出ます。しかも、このアプリには日本語の文言ファイルが置かれていないので、画面に出るのは英語のままです。🔑 **文言はまだ決まっていない**、という状態です。

### Step 1: 入力チェック表を作る

`画面`・`項目`・`必須`・`文字数・桁数`・`形式・値の範囲`・`ほかの項目との関係` の6列で表を作ります。画面名は「投稿編集画面」です。

写すのではなく、🔑 **組み替える**のがこのStepです。`max:255` や `exists:categories,id` といったルール名は書かず、この章の列に日本語で振り分けてください。

### Step 2: 決めた理由を書き足す

表の下に、文字数について書いた内容の理由を添えます。ここで一度立ち止まってください。`max:255` の255は、誰かが「投稿のタイトルは255文字まで」と決めた数字なのか、それとも別のところから出てきた数字なのか。上のマイグレーションと見比べると、答えが出ます。

理由を思いつけない数字は、自分で決めてよい数字ではありません。想定を添えて確認事項リストへ回す、という書き方で構いません。

### Step 3: メッセージ一覧を作る

`画面`・`出る場面`・`区分`・`メッセージ` の4列で作ります。文言は、書き方で決めた型に沿って、自分で日本語を考えてください。写す元がありません。

行を作る前に、入力チェック表の決めごとを1つずつ見て、その決めごとを破ったときに画面へ何かを出す必要があるかを考えます。読み方で見たとおり、画面の作りだけで守られる決めごとには文言が要りません。

もう1つ確かめてほしいことがあります。更新が終わったあと、投稿一覧画面に何かが出るのか。`resources/views/posts/index.blade.php` を開いて、うまくいったことを知らせている箇所を探してください。

### Step 4: 保存してコミットする

`docs/13-3/` に、入力チェック表を `post-input-check.md`、メッセージ一覧を `post-messages.md` として保存します。

```bash
# アプリのフォルダで実行する
git add docs/13-3
git commit -m "13-3: 投稿編集画面の入力チェック表とメッセージ一覧を追加"
git push origin main
```

**決めた理由（解答例）**

> タイトルの255文字は、決めて選んだ数字ではありません。`title` の列を `string` 型で作ったことで決まった長さが、そのまま入力チェックにも出てきたものです。投稿一覧に並べたときに読みやすい長さを考えると、50文字や100文字にする案もあります。本文の上限なしも同じで、`text` 型なら長い文章が入る、という以外の根拠がありません。どちらも「この長さで問題ないですか」と確認事項リストへ回します。

| 画面 | 出る場面 | 区分 | メッセージ |
|:-----|:---------|:-----|:-----------|
| 投稿編集画面 | タイトルが空のまま「更新」を押した | エラー | タイトルを入力してください |

次の観点で、自分の成果物と見比べてください。

- [ ] 入力チェック表に、`max:255` のようなルール名が1つも書かれていない
- [ ] 決めることが無い欄に `-` が書かれていて、空欄になっていない
- [ ] 255文字について、それが決めて選んだ数字ではないことに気づけている
- [ ] メッセージの文言が、「どの項目が・どうなっているか・どうすればよいか」の型に沿っている
- [ ] どの行を読んでも、どの画面のどんな場面で出るのかが分かる
- [ ] 文言が要らなかった決めごとについて、要らない理由を言える

**迷いやすいところ**

- **権限が無いときの文言を、この一覧に入れなかった理由**: 13-2-2のUC-05では、他人の投稿の編集画面のURLを直接開いた場合を代替フロー1aとして書きました。これは利用者が入力した値の話ではないので、入力に関する文言だけを並べるこの一覧には入りません。権限が無いことを伝える文言は、13-4-1で作るエラーレスポンス一覧の403の行として決めます。
- **カテゴリに文言を1行も作らなかった理由**: この画面のカテゴリは、登録されているものが候補として並び、開いた時点で今のカテゴリが選ばれています。空のまま送られることも、候補以外の値が送られることもありません。読み方で見た、画面の作りだけで守られる決めごとに当たります。ただし、あとからカテゴリを削除できる機能が付くと、画面を開いたあとに候補が消える場面が生まれます。そのときは「選んだカテゴリが見つかりません」の1行が要ります。
- **完了の行が1つも無い理由**: 更新が終わると投稿一覧画面へ移りますが、その画面には、うまくいったことを知らせる箇所がありません。これは書き忘れではなく、このアプリに完了の知らせが用意されていないという事実です。自分で設計するなら、ここで「更新できたことを投稿一覧画面で知らせるかどうか」を決めます。知らせると決めたなら、`完了` の行を1つ足します。
- **カテゴリの「形式・値の範囲」を日本語に置き換えた理由**: `exists:categories,id` は「`categories` テーブルの `id` に、その値が存在すること」という指定です。ルール名のまま書くと、依頼者には読めません。「登録されているカテゴリのどれか1つ」と書けば、依頼者でも「カテゴリを増やしたら、そのぶん選べるのですね」と確かめられます。

## 💡 現場での使われ方

入力チェック表は実装する人の作業指示になり、そのままChapter 8で学ぶ「何を確かめれば正しいと言えるか」の元にもなります。255文字以内と決めてあれば、255文字と256文字を試せばよい、という具合です。

メッセージ一覧のほうは、文言を直したいときの唯一の置き場所になります。コードの中に文言が散らばっていると、直す作業が、どこに書いてあるかを探すところから始まります。投稿アプリのように文言をLaravelの既定に任せていると、そもそも直す場所がありません。

## ✨ まとめ

- 入力の決まりごとは、コードを書きながらでも決まってしまいます。だからこそ、書く前に決めて表に残します。
- 入力チェック表は、画面項目定義の入力と選択の行だけを引き継ぎ、`画面`・`項目`・`必須`・`文字数・桁数`・`形式・値の範囲`・`ほかの項目との関係` の6列で作ります。
- 埋めるときは、空でよいか・長さ・形と範囲・すでにあるものと重なってよいか・ほかの項目との関係、の順に問いかけます。ルール名は書かず、日本語で書きます。
- 決めた数字には理由を添えます。コードに書かれている数字が、必ず誰かの判断で決まったものとは限りません。
- メッセージ一覧は、`画面`・`出る場面`・`区分`・`メッセージ` の4列で作ります。区分はエラーと完了の2つで、文言は「どの項目が・どうなっているか・どうすればよいか」の型でそろえます。
