# 13-3-1: 画面一覧

## 🎯 このセクションで学ぶこと

- ユースケースの流れをたどって、画面が何枚必要かを数えられるようになる。
- 画面に名前を付け、役割と主な利用者を添えて表に並べられるようになる。
- 利用者が最初に開く画面を決められるようになる。

---

## 導入：枚数が決まらないと、いつ終わるかも答えられない

機能一覧に「投稿の編集」と書いてあっても、それが画面1枚で済むのか、一覧と編集で2枚要るのかは分かりません。Web開発では、画面1枚ごとに表示用のファイルと、それを返す処理が要ります。5枚なのか8枚なのかで、かかる日数は変わります。数えられないものは、いつ終わるかも答えられません。

もう1つ困るのが、名前です。同じ画面を1人が「投稿画面」、もう1人が「記事一覧」と呼びながら作ると、打ち合わせの時間が名前をそろえる作業に消えていきます。

画面一覧（そのシステムに何という画面があるかを並べた表）は、この2つをまとめて片付ける設計書です。

---

## 画面一覧の読み方

題材は、歯科医院の予約アプリです。次の相談を受けたとします。

> 歯科医院で受付をしています。予約のお電話が診療中にも鳴ってしまい、お待たせすることが多いので、患者さんがスマートフォンからご自分で予約を取れるようにしたいです。
>
> 受けたい診療（定期健診、むし歯の治療など）を選んでいただき、空いている日時から1つ選んで、お名前と連絡先を入れて予約が終わる、という流れを考えています。日時は1週間ぶんずつお見せして、その週に空きがなければ次の週も見られるようにしてください。予約が終わったら、その場で予約した日時をご確認いただけると安心だと思います。

この相談から起こした画面一覧が、次の表です。

| ID | 画面名 | 役割 | 主な利用者 |
|:---|:-------|:-----|:-----------|
| SC-01 | 診療選択画面 | 受けたい診療を一覧で見せ、1つ選ぶ（最初に開く画面） | 患者 |
| SC-02 | 日時選択画面 | 空いている日時を1週間ぶん見せ、1つ選ぶ | 患者 |
| SC-03 | 連絡先入力画面 | お名前と連絡先を入力する | 患者 |
| SC-04 | 予約内容確認画面 | 選んだ診療・日時・連絡先を並べて見せ、予約を確定する | 患者 |
| SC-05 | 予約完了画面 | 予約できたことと、予約した日時を知らせる | 患者 |

この表を読むと、作る画面が5枚だと🔑 **数えられます**。機能一覧で作るものの数を数えたのと同じで、画面一覧は表示する側の作業がいくつあるかを数えられる形にした表です。

どの行にも役割が書かれているので、名前だけでは分からない中身も伝わります。「日時選択画面」という名前だけでは、1週間ぶんなのか1か月ぶんなのかが分かりません。役割の欄まで読めば、そこが決まっていると確かめられます。

SC-01の役割には「最初に開く画面」と書き添えてあります。患者がこのアプリを開いたとき、最初に見えるのがこの画面です。ここが決まっていないと、13-3-2で描く画面遷移図の出発点も決まりません。

> 💡 **TIP**: 表の列は `ID`・`画面名`・`役割`・`主な利用者` の4列で固定します。「この画面はどの機能に対応するのか」を書き足したくなりますが、列は増やしません。機能一覧との突き合わせは、演習のセルフチェックの観点で行います。

## 画面一覧の書き方

**手順1: ユースケースをたどって、切れ目を探す**

画面は、思いついた順に数えません。13-2-2で書いたユースケース記述の基本フローを、1行ずつ上からたどります。そして「システムが〜を表示する」と書かれている行で、**画面に並んでいるものが別のものに置き換わるか**を見ます。置き換わるなら別の画面、並んでいるものはそのままで中に入る値だけが変わるなら同じ画面です。

記述を書いていないユースケースもあります。記述は条件や分岐が絡むものから書くので、全部はそろっていません。記述が無いものは、頭の中で操作の流れを通してみてください。

歯科医院の予約アプリなら、診療を選んだあとに映るのは日時の一覧です。診療名の並びが消えて、日付と時刻の並びに変わります。並んでいるものが置き換わるので、別の画面です。日時選択画面で「次の週を見る」を押したときは、日付と時刻という同じものが並んだまま、その値が別の週のものに変わるだけです。並んでいるものは置き換わっていないので、同じ画面のままです。

**手順2: 画面に名前を付ける**

名前は🔑 **「〜画面」で終える**形にそろえます。そして、仕様書とユースケース記述に出てくる言葉をそのまま使います。相談の文章が「診療」と呼んでいるものを「メニュー」と言い換えると、あとで表を突き合わせるときに、同じものかどうかの確認が1往復増えます。

避けたいのは「トップ」「ホーム」のような、何が映るのか分からない名前です。機能名をそのまま持ってくるのもやめます。「予約する画面」では、日時を選ぶところなのか、連絡先を入れるところなのかが分かりません。🔑 **その画面に何が映るか**で名前を付けます。

**手順3: IDを振り、役割と主な利用者を書く**

上から `SC-01`、`SC-02` と番号を振ります。SCはscreen（画面）の頭文字で、番号は2桁のゼロ埋めです。機能一覧の `F-01` と同じで、あとから画面が増えたときは末尾に足し、番号を振り直しません。

役割の欄には、その画面が何のためにあるかを1文で書きます。ここが書けない画面は、まだ役割が決まっていないか、隣の画面と役割が重なっています。

主な利用者の欄は、機能一覧と同じ言葉づかいで書きます。歯科医院の予約アプリは患者だけが使うので、5行すべてが「患者」になります。利用者が1種類しかいない一覧も、正しい一覧です。

**手順4: 最初に開く画面を決める**

利用者がアプリを開いたときに最初に見える画面を1つ選び、役割の欄に「最初に開く画面」と書き添えます。利用者の種類が複数いる場合は、それぞれに1つずつ決めます。これを決めておくと、13-3-2で画面遷移図を描くときの起点になります。

仕様書がログインに触れていないうちは、ログイン画面を置かずに進めます。誰がどこまで使えるかは、13-4-2で権限マトリクスとして表にします。

> ⚠️ **注意**: 画面ごとのURLやHTTPメソッドは、ここでは決めません。それはChapter 4「APIと権限の設計」で扱います。ここで決めるのは、画面の名前と役割、そして誰が使うかだけです。

## 🏃 数えてみよう

歯科医院の予約アプリは「読む」練習でした。今度は、13-1-3で自分のリポジトリに用意した投稿アプリ（`post-app-practice`）を数えます。

このアプリで利用者の目に映るものは、`resources/views` の中のBladeファイルです。VS Codeで開いてください。

```text
resources/views/
├── auth/
│   ├── login.blade.php
│   └── register.blade.php
├── posts/
│   ├── edit.blade.php
│   └── index.blade.php
└── welcome.blade.php
```

どのURLで開くのかは、`routes/web.php` で確かめられます。

```php
// routes/web.php
Route::get('/', function () {
    return view('welcome');
});

// 認証が必要なルート
Route::middleware('auth')->group(function () {
    Route::get('/posts', [PostController::class, 'index'])->name('posts.index');
    Route::get('/posts/{post}/edit', [PostController::class, 'edit'])->name('posts.edit');
    Route::put('/posts/{post}', [PostController::class, 'update'])->name('posts.update');
    Route::delete('/posts/{post}', [PostController::class, 'destroy'])->name('posts.destroy');
});
```

`auth/login.blade.php` と `auth/register.blade.php` を開くURLが、このファイルに見当たりません。ログインと新規登録のルートは、Laravel Fortify（ログイン周りの処理をまとめて受け持つ追加部品）が登録していて、`routes/web.php` には書かれていないためです。画面ファイルはあるので、画面としては数えます。

### Step 1: 1つずつ開いて、何が映るかを確かめる

5つのBladeファイルを順に開き、`<h1>` の文字と、その下に並んでいるものを読み取ります。役割の欄に書く1文の材料になります。

`welcome.blade.php` だけは、`@auth` と `@else` で中身が2つに分かれています。ログインしている人に映るものと、していない人に映るものが、1つのファイルの中に両方書かれています。この画面は1行として数えます。開くURLも画面ファイルも1つで、利用者から見れば同じ画面の中身が入れ替わっているだけだからです。役割の欄には、両方の中身を書きます。

### Step 2: 画面一覧を作る

`ID`・`画面名`・`役割`・`主な利用者` の4列で表を作り、`SC-01` から順にIDを振ります。書き方の手順2のとおり、画面名は「〜画面」で終える形にそろえます。

最初に開く画面も1つ決めて、役割の欄に書き添えてください。

### Step 3: 保存してコミットする

成果物は、アプリのリポジトリの `docs/` の下に、章ごとのフォルダを切って置きます。

```bash
# アプリのフォルダへ移動して、Chapter 3用のフォルダを作る
cd ~/laravel-practice/post-app-practice
mkdir -p docs/13-3
```

このフォルダには、この先のセクションの成果物も一緒に入ります。あとで章末演習のカフェの成果物も同じフォルダに入るので、ファイル名の先頭に、どの題材のものか分かる短い言葉を付けます。投稿アプリのものは `post-` です。

VS Codeで `docs/13-3/post-screen-list.md` を新しく作り、Step 2の表を書いて保存します。

```bash
# アプリのフォルダで実行する
git add docs/13-3
git commit -m "13-3: 投稿アプリの画面一覧を追加"
git push origin main
```

次の観点で、自分の成果物と見比べてください。

- [ ] 画面が5枚になっている
- [ ] 画面名がすべて「〜画面」で終わっている
- [ ] どの行にも役割が1文で書かれている
- [ ] IDが `SC-01` から順に振られている
- [ ] 最初に開く画面が1つ決まっていて、役割の欄に書き添えられている

**迷いやすいところ**

- **「トップ画面」という名前にした理由**: 書き方の手順2では「トップ」「ホーム」のような名前を避けると書きました。この画面は `@auth` で映るものが入れ替わるので、何が映るかを一語で言い表せません。そこだけ例外として「トップ画面」としています。`welcome.blade.php` の `<h1>` にある「認可スターター」は、このスターターキットの呼び名であって画面に映るものを表していないので、名前には採りません。
- **2行に分ける設計との違い**: トップ画面を、ログイン前とログイン後の2行に分ける設計もあり得ます。その場合は、どちらを最初に開く画面にするかを決め直すことになります。この教材では、Step 1のとおり1行で通します。
- **主な利用者を全部「利用者」にした理由**: ログインしているかどうかは、その画面を開ける条件であって、別の種類の利用者ではありません。このアプリを使う人は1種類です。誰がどの画面を開けるかは、13-4-2で権限マトリクスとして表にします。
- **パスワード再設定の画面を入れなかった理由**: Fortifyの設定でパスワード再設定の機能が有効になっているので、`/forgot-password` のようなURLは登録されています。ところが、そこで映すBladeファイルがこのアプリには置かれていないため、開くとエラーになります。画面一覧に並べるのは、いま映るものだけです。

## 💡 現場での使われ方

画面一覧は、見積もりの土台になります。画面1枚あたりの作業量をおおまかに置いてしまえば、枚数をかけるだけで日数の目安が出ます。表の行が増えたら、その日数がどれだけ動くのかも、その場で答えられます。

## ✨ まとめ

- 画面一覧は、作る画面を数えられる形に並べた表です。`ID`・`画面名`・`役割`・`主な利用者` の4列で作り、IDは `SC-01` から順に振ります。
- 画面の切れ目は、ユースケース記述の基本フローを1行ずつたどって探します。並ぶものが入れ替われば別の画面、値だけが変わるなら同じ画面です。
- 名前は「〜画面」で終え、その画面に何が映るかで付けます。仕様書の言葉を言い換えると、突き合わせのたびに確認が増えます。
- 最初に開く画面を決めて、役割の欄に書き添えます。利用者の種類が複数いるときは、それぞれに1つずつ決めます。
- URLやHTTPメソッド、誰がどこまで使えるかは、この表では決めません。
