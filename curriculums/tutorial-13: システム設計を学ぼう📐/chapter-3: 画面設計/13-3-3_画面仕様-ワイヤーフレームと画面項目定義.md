# 13-3-3: 画面仕様 - ワイヤーフレームと画面項目定義

## 🎯 このセクションで学ぶこと

- 1枚の画面に何をどの順で並べるのかを、線と枠だけの下書きに起こせるようになる。
- その画面に置く項目を、名前・種類・必須かどうかまで表に書き出せるようになる。
- 画面設計で決めることと、決めないことを区別できるようになる。

---

## 導入：役割の1文だけでは、まだ作れない

「お名前と連絡先を入力する」という役割だけを渡されても、画面は作れません。連絡先が電話番号なのか、メールアドレスなのか、その両方なのかが決まっていません。両方だとして、どちらも必ず入れてもらうのかも決まっていません。前の画面で選んだ診療と日時を、この画面にもう一度映すのかどうかも決まっていません。

画面一覧の四角の中身は、まだ空っぽです。埋めるために作るのが、ワイヤーフレームと画面項目定義です。

- **ワイヤーフレーム**（画面のどこに何を置くかを、線と枠だけで表した下書き）: 1枚の画面の並びを、目で見て確かめるもの。
- **画面項目定義**（その画面に置く項目を、名前・種類・必須かどうかまで書き出した表）: 図では表せない決めごとを、言葉で固定するもの。

2つで1組です。ワイヤーフレームだけでは「この欄は空のままでもよいのか」が分からず、表だけでは「どれが上でどれが下か」が分かりません。

---

## ワイヤーフレームの読み方

歯科医院の予約アプリから、SC-03「連絡先入力画面」のワイヤーフレームを見てください。

**歯科医院の予約アプリ 連絡先入力画面のワイヤーフレーム**

<img alt="13-3-3_1.png" src="">

線と四角と文字しかありませんが、この画面で何が起きるのかは読み取れます。

いちばん上に画面の見出しがあり、その下に前の画面で選んだ診療と日時が映ります。その下からは、「お名前」のような項目名の四角と、患者に入れてもらう空の四角が、横に2つで1組になって並びます。上から下へ読んでいけば、患者が何をすればよいのかが順にたどれます。

「電話」「メール」と書かれた2つの四角は、押して次へ進むところではありません。ご希望の連絡方法を、どちらか1つ選んでもらうための候補です。ワイヤーフレームでは、選ぶ候補も押すところも同じ四角で表すので、図の上では見分けが付きません。どちらなのかは、このあと作る画面項目定義で書き分けます。

つまり、この画面で押して次へ進むところは、いちばん下の1つだけです。13-3-2の画面遷移図でも、連絡先入力画面から出ていく矢印は1本だけでした。図と下書きが食い違っていれば、どちらかが間違っています。

この下書きからは🔑 **決めていないこと**も読み取れます。文字の大きさ、色、枠の丸み、余白の広さ、押すところの見た目。どれも決まっていません。ここで決めるのは、🔑 **何を、どの順で、いくつ置くか**だけです。

## ワイヤーフレームの描き方

使う記号は次のとおりです。

| 記号 | 表すもの |
|:-----|:---------|
| 外枠の大きな四角 | 画面1枚ぶんの範囲 |
| 中の四角 | 項目の置き場所（見出し・表示する値・項目名・入力欄・選ぶ候補・押すところ・一覧の1行） |
| 横線 | まとまりの区切り |
| 文字 | 項目名・押すところの文字・仮の値 |

四角1つが項目1つとは限りません。項目名の四角と、その値が入る四角は、🔑 **2つで1組**です。選んでもらう項目なら、項目名の四角と、候補を並べた四角がまとめて1組になります。

**描く手順**

1. 画面一覧の「役割」の欄を読み直し、その画面に映るものと、入力してもらうものを書き出します。
2. 外枠を1つ置き、書き出したものを上から順に四角で並べます。並べる順は、利用者が読んでいく順です。
3. 押せるところ（ボタン・リンク）を置きます。押した先が、13-3-2で描いた画面遷移図の矢印と合っているかを確かめます。
4. 項目名や押すところの文字を、四角の中に書きます。値が入る欄は空のままにします。

一覧のように同じ形の行が並ぶところは、🔑 **2〜3行だけ描いて「以下同じ」と書きます**。実際に並ぶのが20行でも、20個の四角を描く意味はありません。決めたいのは1行の中に何が入るかであって、行の数ではないからです。

> ⚠️ **注意**: 実物そっくりに描こうとしないでください。時間がかかるだけではなく、色を塗って角を丸めた下書きを見せられた依頼者は、見た目のほうに気を取られて、いちばん見てほしい項目の抜けを指摘してくれなくなります。四角の大きさがそろっていなくても、並びが少しずれていても、そのままにしてください。

**draw.ioでの操作**

この図で新しく覚える操作はありません。13-1-3で学んだ四角・直線と、ダブルクリックでの文字入力だけで描けます。一覧の1行のように、1つの四角の中に文字と別の四角の両方を入れるときは、文字が枠の中央に来て中の四角と重なります。そのときは13-1-3で使った「テキスト」タブで、文字の位置を枠の上に寄せてください。

## 画面項目定義の読み方

同じ連絡先入力画面の画面項目定義が、次の表です。

| 項目名 | 種類 | 必須 | 内容 |
|:-------|:-----|:-----|:-----|
| 画面見出し | 表示 | - | 「連絡先の入力」 |
| 選んだ診療と日時 | 表示 | - | 前の2画面で選んだ診療名と日時 |
| お名前 | 入力（1行） | 必須 | 予約する方のお名前 |
| 電話番号 | 入力（1行） | 必須 | 当日つながる電話番号 |
| メールアドレス | 入力（1行） | 任意 | 予約内容をお送りする先 |
| ご希望の連絡方法 | 選択 | 必須 | 「電話」「メール」のどちらか1つ |
| 入力内容を確認するボタン | ボタン | - | 押すと予約内容確認画面へ移る |

ワイヤーフレームでは似たような枠が並んでいるだけでしたが、この表では1つずつ違うものになっています。必須（空のままでは先に進めない項目）の欄を見ると、お名前と電話番号は必ず入れてもらい、メールアドレスは空でもよいと決まっています。ご希望の連絡方法は、自由に書いてもらう欄ではなく、2つから選んでもらう欄です。ここまで決まって、はじめて実装する人は迷わずに画面を作れます。

いちばん下の行には、押した先が書かれています。13-3-2で描いた矢印と同じ内容です。図と表のどちらにも書いておくと、片方だけを見た人でも行き先が分かります。

## 画面項目定義の書き方

列は `項目名`・`種類`・`必須`・`内容` の4つで固定します。ワイヤーフレームに置いた四角を、上から順にたどって書き出すと漏れません。このとき、項目名の四角とその値が入る四角は、描いたときと同じく1組で1行にまとめます。連絡先入力画面の表が7行で足りているのは、そうやってまとめているからです。逆に、一覧の1行のように、1つの四角の中に複数のものを並べたところは、中に入っているものを1つずつ行にします。どちらの場合も、四角の数と表の行数は一致しません。

**「種類」に書く言葉**

| 種類 | どんな項目か |
|:-----|:-------------|
| 表示 | 見せるだけで、利用者が変えられないもの |
| 入力（1行） | 1行ぶんの文字を入れてもらうもの |
| 入力（複数行） | 何行にもわたる文章を入れてもらうもの |
| 選択 | 決まった候補から選んでもらうもの |
| ボタン | 押すと何かが起きるもの |
| リンク | 押すと別の画面へ移るもの |

この6つ以外の言葉は使いません。5-1-6「フォームの基礎」で学んだ `<input>` や `<textarea>` のようなタグの名前も書きません。画面項目定義は依頼者にも読んでもらう書類なので、作り方の言葉は持ち込まず、上の言葉で表します。

見た目がボタンでも、押して別の画面へ移るだけのものは「リンク」です。押した結果で分けます。

**「必須」の欄の書き方**

必須かどうかを書くのは、入力と選択の行だけです。「必須」か「任意」のどちらかを書きます。表示・ボタン・リンクの行には `-` を書きます。空欄にしないのは、13-2-2で無い項目を空欄にせず「なし」と書いたのと同じ理由で、決めた結果と書き忘れを区別するためです。

必須かどうかは、思いつきでは決められません。「お名前が無いと、当日どなたの予約か分からない」「メールアドレスは、電話がつながれば無くても困らない」というように、その項目が無いと誰が何に困るのかで決めます。決められないときは、13-2-1で学んだとおり、想定を添えて確認事項リストへ回します。

**「内容」の欄の書き方**

表示の行には何を映すのか、入力の行には何を入れてもらうのか、ボタンとリンクの行には押した先を書きます。「どこまでの値なら受け付けるか」は、まだ書きません。それは13-3-4で入力チェック表として作ります。

## 🏃 描いてみよう

13-3-1で数えた投稿アプリの5枚のうち、**SC-05 投稿編集画面**の1枚を取り出して、ワイヤーフレームと画面項目定義を作ります。

材料は `resources/views/posts/edit.blade.php` です。CSSを省いた本体が、次のコードです。

```blade
<!-- resources/views/posts/edit.blade.php（body 部分。style は省略） -->
<body>
    <div class="container">
        <h1>投稿編集</h1>

        <form action="{{ route('posts.update', $post) }}" method="POST">
            @csrf
            @method('PUT')

            <div class="form-group">
                <label for="title">タイトル</label>
                <input type="text" id="title" name="title" value="{{ old('title', $post->title) }}" required>
                @error('title')
                    <p class="error">{{ $message }}</p>
                @enderror
            </div>

            <div class="form-group">
                <label for="category_id">カテゴリ</label>
                <select id="category_id" name="category_id" required>
                    @foreach ($categories as $category)
                        <option value="{{ $category->id }}" @selected(old('category_id', $post->category_id) == $category->id)>{{ $category->name }}</option>
                    @endforeach
                </select>
                @error('category_id')
                    <p class="error">{{ $message }}</p>
                @enderror
            </div>

            <div class="form-group">
                <label for="content">本文</label>
                <textarea id="content" name="content" required>{{ old('content', $post->content) }}</textarea>
                @error('content')
                    <p class="error">{{ $message }}</p>
                @enderror
            </div>

            <div class="actions">
                <button type="submit" class="btn btn-primary">更新</button>
                <a href="{{ route('posts.index') }}" class="btn btn-secondary">キャンセル</a>
            </div>
        </form>
    </div>
</body>
```

`<select>` の中の `@foreach` は、カテゴリの候補を並べています。候補になるのは `categories` テーブルに登録されているものです。配られた状態では、「お知らせ」「技術メモ」「雑記」の3つが入っています。

### Step 1: ワイヤーフレームを描く

draw.ioで外枠の四角を1つ置き、上のコードのうち**画面に文字や欄として映るものだけ**を、上から順に並べます。`@csrf` や `<div class="form-group">` のように目に見えないものは置きません。文字は、実物に書かれているものをそのまま使ってください。

`@error` のブロックも、いまは置かなくて構いません。入力を受け付けられなかったときに何と出すのかは、13-3-4で決めます。

### Step 2: 画面項目定義を作る

列は `項目名`・`種類`・`必須`・`内容` の4つです。ワイヤーフレームに置いた四角を、書き方のとおりに上からたどって書き出します。

「キャンセル」の行で、種類をどれにするか迷うはずです。見た目はボタンですが、押した結果で分けます。

「必須」の欄は、3つの入力欄すべてに `required` が付いているところが手がかりになります。ただし本来は逆で、🔑 **どれを必須にするかを先に決めて、この表に書いてから**コードを書きます。表に書いてあれば、実装する人が迷いませんし、あとから「本文は空でもよかったんでしたっけ」と聞かれても、表を指させます。

### Step 3: 保存してコミットする

`docs/13-3/` に、ワイヤーフレームを `post-wireframe.drawio` と `post-wireframe.png`、画面項目定義を `post-screen-items.md` として保存します。`.drawio` と書き出したPNGはダウンロードフォルダに入るので、13-1-3のとおりに `docs/13-3/` へ移してからコミットしてください。

```bash
# アプリのフォルダで実行する
git add docs/13-3
git commit -m "13-3: 投稿編集画面の画面仕様を追加"
git push origin main
```

- [ ] ワイヤーフレームに、見出し・入力欄3つ・押すところ2つがすべて置かれている

**迷いやすいところ**

- **「キャンセル」を「リンク」にした理由**: 押しても何も保存されず、投稿一覧画面へ移るだけだからです。6つの言葉では、これはリンクにあたります。実物のコードも `<a>` タグでした。見た目をボタンに寄せてあるのは、押しやすくするためのデザインの都合で、種類を決める材料にはなりません。
- **画面項目定義の内容欄に、3つの名前を直接書かなかった理由**: 候補は `categories` テーブルに登録されているものが並ぶので、カテゴリを1つ足せば候補が4つになります。「『お知らせ』『技術メモ』『雑記』のどれか1つ」と書くと、テーブルを触ったときに表が古くなります。数が変わらない候補（歯科医院の予約アプリの「電話」「メール」など）は直接書き、増える候補は「〜から1つ」と書きます。ワイヤーフレームの候補の欄に3つの名前が入っているのは、記号の表のとおり、図には仮の値を書いてよいからです。
- **開いたときに値が入っていることを、内容の欄に書いた理由**: 編集の画面は、空の欄から始まりません。`old('title', $post->title)` は、いま保存されている値を初めから入れておく書き方です。ここを書いておかないと、実装する人が空の欄から始める画面を作ってしまいます。

## 💡 現場での使われ方

ワイヤーフレームと画面項目定義は、渡す相手が違います。ワイヤーフレームは依頼者に見せて、「この画面でこれだけのことができれば足りますか」を合意するために使います。画面項目定義は実装する人と、画面の見た目を作るデザイナーに渡します。

デザイナーがいる現場では、ワイヤーフレームを渡してそこから仕上げてもらいます。この下書きが、仕上げの出発点になります。

## ✨ まとめ

- ワイヤーフレームは、外枠の四角・中の四角・横線・文字だけで描く画面の下書きです。決めるのは、何を、どの順で、いくつ置くかで、色や書体は決めません。
- 一覧のように同じ形の行が並ぶところは、2〜3行だけ描いて「以下同じ」と書きます。
- 画面項目定義は、`項目名`・`種類`・`必須`・`内容` の4列の表です。項目名と入力欄の四角は1組で1行なので、四角の数と行数は一致しません。
- 種類に書くのは、表示・入力（1行）・入力（複数行）・選択・ボタン・リンクの6つだけです。ボタンとリンクの区別は、見た目ではつきません。押した結果で分けます。
- 必須かどうかは入力と選択の行だけに書き、それ以外は `-` を書きます。決められないときは、想定を添えて確認事項リストへ回します。
