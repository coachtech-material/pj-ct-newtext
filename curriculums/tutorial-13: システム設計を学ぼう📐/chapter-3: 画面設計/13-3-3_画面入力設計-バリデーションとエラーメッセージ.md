# 13-3-3: 画面入力設計 - バリデーションとエラーメッセージ

## 🎯 このセクションで学ぶこと

- 入力欄ごとに、どこまでの値を受け付けるのかを、実装より先に決めて表にできるようになる。
- 決めた数字や決まりごとに、そう決めた理由を残せるようになる。
- 画面に出す文言を、実装より先に決めて一覧にできるようになる。

---

## 導入：受け付ける範囲は、コードを書きながら決まってしまう

13-3-2で作った画面項目定義には、「お名前 / 入力（1行）/ 必須」という行がありました。必須だと決まったので、空のままでは先へ進めません。では、100文字のお名前は受け付けるのでしょうか。電話番号にハイフンが入っていたら、どうなるのでしょうか。

こうした決めごとは、決めなくても実装は進みます。進んでしまうのが問題です。手を動かしている人が、その場で「50文字くらいでいいか」と決めて書き、そのままリリースされます。半年後に「名前が入りきらない」と問い合わせが来て、なぜ50文字なのかを聞かれても、誰も答えられません。

入力の決まりごとをコードでどう書くかは、9-6「入力の制約」の章でバリデーションとして学びました。このセクションで扱うのは、その手前です。🔑 **書く前に決めて、書き残す**ところだけを学びます。作るのは次の2つです。

- **入力チェック表**（入力欄ごとに、どんな値まで受け付けるかを決めた表）
- **メッセージ一覧**（画面に出す知らせの文言をまとめた表）

---

## 入力チェック表の読み方

13-3-2で画面項目定義を作った、歯科医院の予約アプリの連絡先入力画面から起こした表です。

| 画面 | 項目 | 必須 | 文字数・桁数 | 形式・値の範囲 | ほかの項目との関係 |
|:-----|:-----|:-----|:-------------|:---------------|:-------------------|
| 連絡先入力画面 | お名前 | 必須 | 30文字以内 | - | - |
| 連絡先入力画面 | 電話番号 | 必須 | 10桁または11桁 | 半角数字のみ | - |
| 連絡先入力画面 | メールアドレス | 任意 | - | メールアドレスの形 | ご希望の連絡方法が「メール」のときは必須 |
| 連絡先入力画面 | ご希望の連絡方法 | 必須 | - | 「電話」「メール」のどちらか1つ | - |

行が4つしかないことに気づいたでしょうか。画面項目定義には7行ありましたが、この表に引き継ぐのは🔑 **入力と選択の行だけ**です。見出しやボタンには、利用者が値を入れないので、受け付ける範囲もありません。

「必須」の欄は、画面項目定義に書いたものと同じ値です。同じことを2か所に書いているように見えますが、この表だけを見て実装できるようにするための重複です。

いちばん右の欄を見てください。メールアドレスは「任意」なのに、条件によっては必須になると書かれています。ひとつの欄だけを見ていては決まらない決めごとが、ここに現れます。この行が無いと、実装した人は「任意」だけを読んで、連絡方法にメールを選んだ患者からメールアドレスを聞かずに予約を受け付けてしまいます。

決めることが無い欄には `-` を書きます。この `-` は「検討したうえで、決めることが無かった」という意味です。「まだ決めていない」ものを `-` で埋めてはいけません。それは13-2-1で学んだとおり、確認事項リストへ回します。

## 入力チェック表の書き方

画面項目定義の入力と選択の行を上から順にたどり、1行ずつ次の5つを自分に問いかけます。

1. 空のままでもよいか。
2. どのくらいの長さ・桁数まで受け付けるか。
3. どんな形の値なら受け付けるか。数なら、どこからどこまでか。
4. すでに登録されているものと、同じ値が入ってよいか。
5. ほかの項目の入り方によって、答えが変わることはあるか。

1つ目が「必須」の欄、2つ目が「文字数・桁数」の欄、3つ目が「形式・値の範囲」の欄になります。4つ目と5つ目は、どちらもその欄だけを見ていては決まらない話なので、まとめて「ほかの項目との関係」の欄に書きます。

逆に、その欄だけを見ても決まりごとが1つも決まらず、ほかの項目との関係だけが決まる入力欄もあります。同じ値をもう一度入れてもらって、打ち間違いを防ぐための欄が代表です。こうした欄は独立した行にせず、相手の行の「ほかの項目との関係」に書きます。入力欄の数と表の行数が一致しないことがあるのは、このためです。連絡先入力画面には当てはまる欄が無いので、上の表は入力と選択の4つが、そのまま4行になっています。

**実装の言葉で書かない**

問いかけを日本語のまま並べたのには理由があります。設計書は依頼者にも読んでもらうものなので、`max:50` のようなルール名で書くと、決めた内容を確認してもらえません。「30文字以内」と書いてあれば、受付の方が「お名前が30文字を超える患者さんはいませんね」と判断できます。

> 💡 **TIP**: ここで決めた内容は、実装のときに9-6-2「バリデーションルール」で学んだルールへ置き換わります。設計書はその手前の、日本語で合意する段階です。

**決めた理由を残す**

表の下に、数字を決めた理由を1〜2行添えます。歯科医院の予約アプリなら、次のように書きます。

> お名前の30文字は、診察券に印字できる長さに合わせました。電話番号の10桁または11桁は、固定電話と携帯電話の両方を受け付けるためです。

理由が残っていれば、「もっと長くできませんか」と聞かれたときに、何と何がぶつかるのかをその場で答えられます。理由が残っていないと、決め直しのたびに同じ議論を最初からやることになります。

**決めきれない数字は、自分で決めない**

電話番号を「半角数字のみ」と決めたとき、「ハイフン付きで入力されたらどうするのか」で手が止まります。ここで「エラーにしよう」と自分で決めてしまうと、その判断は自分の頭の中にしか残りません。13-2-1で学んだとおり、想定を添えて確認事項リストへ1行足します。「電話番号はハイフンを入れずに入力していただく想定です。ハイフン付きで入力された場合も受け付ける必要はありますか」と書いておけば、返事を待つあいだも、想定の上で先へ進めます。

> 💡 **TIP**: 5-1-6「フォームの基礎」で学んだ `required` 属性を付けると、空のまま送信ボタンを押してもブラウザが送信を止めてくれますが、受け取る側に同じ値が届く保証にはなりません。9-6で学んだ入力チェックは、受け取る側にも置きます。設計書に書くのは、どちらの側の話でもなく「どこまで受け付けるか」だけです。

## メッセージ一覧の読み方

受け付けられなかったとき、画面には何が出るのでしょうか。それを先に決めたのが、メッセージ一覧です。同じ連絡先入力画面の分を見てください。

| 画面 | 出る場面 | 区分 | メッセージ |
|:-----|:---------|:-----|:-----------|
| 連絡先入力画面 | お名前が空のまま「入力内容を確認する」を押した | エラー | お名前を入力してください |
| 連絡先入力画面 | お名前が30文字を超えている | エラー | お名前は30文字以内で入力してください |
| 連絡先入力画面 | 電話番号が空のまま「入力内容を確認する」を押した | エラー | 電話番号を入力してください |
| 連絡先入力画面 | 電話番号が10桁でも11桁でもない | エラー | 電話番号は10桁または11桁で入力してください |
| 連絡先入力画面 | 電話番号に数字以外が入っている | エラー | 電話番号は、ハイフンを入れずに半角数字で入力してください |
| 連絡先入力画面 | メールアドレスの形になっていない | エラー | メールアドレスは、@を含む形で入力してください |
| 連絡先入力画面 | ご希望の連絡方法を選ばずに「入力内容を確認する」を押した | エラー | ご希望の連絡方法を選んでください |
| 連絡先入力画面 | ご希望の連絡方法に「メール」を選んだのに、メールアドレスが空 | エラー | ご希望の連絡方法が「メール」のときは、メールアドレスを入力してください |
| 予約完了画面 | 予約が確定した | 完了 | ご予約を承りました |

エラーの8行は、入力チェック表の決めごとと1つずつつながっています。「30文字以内」と決めたから、超えたときの文言が要る、という順です。表の欄を1つ埋めるたびに、この一覧に行が増えていくと考えてください。

ただし、決めごとがそのまま行になるとは限りません。「ご希望の連絡方法」には、必須という決めごとに対応する行はありますが、「『電話』『メール』のどちらか1つ」という決めごとに対応する行はありません。候補を2つ並べて選んでもらう作りにすれば、それ以外の値は入りようがないからです。🔑 **画面の作りだけで守られる決めごと**には、出す文言が要りません。

最後の1行だけ、区分が「完了」になっています。画面に出る文言は、うまくいかなかったときのものだけではありません。うまくいったときの知らせも、同じ一覧にまとめます。分けて管理すると、片方だけ文言を直して、言い回しがちぐはぐになります。

## メッセージ一覧の書き方

列は `画面`・`出る場面`・`区分`・`メッセージ` の4つです。区分に書くのは「エラー」と「完了」の2つだけにします。

「出る場面」の欄には、どんな操作の結果として出るのかを書きます。「入力エラー」とだけ書くと、どの欄の話なのかが分からず、実装する人が入力チェック表と突き合わせられません。

メッセージそのものには、IDを振りません。文言は変わりやすいので、番号で呼び合うより、画面と場面で指すほうが行き違いが起きにくいためです。

**文言の型を1つ決めて、全画面に通す**

文言は、書く人によって長さも語調もばらつきます。この教材では、次の順で1文にまとめる型を使います。

🔑 **どの項目が → どうなっているか → どうすればよいか**

「お名前は30文字以内で入力してください」なら、「お名前が」「30文字を超えている」「30文字以内で入力すればよい」の3つが1文に入っています。読んだ利用者は、次に何をすればよいのかで迷いません。

型を決めておくと、画面が増えても文言がそろいます。逆に、実装のときに思いついた言葉で書いていくと、同じ意味の知らせが画面ごとに違う言い回しになります。「入力してください」「ご入力ください」「未入力です」が同じアプリの中に並ぶのは、たいていこれが原因です。

> ⚠️ **注意**: システムの側でうまくいかなかった場合（保存に失敗した、外部の仕組みから返事が来ない、など）の洗い出しは、Chapter 6で扱います。ここで決めるのは、画面の入力に関する文言だけです。

## 🏃 書いてみよう

> 🔥 この演習では、設計書をAIに作らせずに、自分の手で書きましょう。記法や考え方についてAIに質問するのは構いませんが、成果物を生成させるのはTutorial 14までお預けです。まず自分の手と頭で書けるようになった人だけが、AIの作った設計を正しく評価できるようになります。

今回の題材は、9-6-5「バリデーション - ハンズオン演習」で作ったユーザー登録フォーム（`validation-app-practice`）です。13-3-1と13-3-2で使ったブログシステムには、受け取る側の入力チェックがありません。13-3-2で見た `required` はブラウザ側だけの指定で、文字数や形の決まりごとはどこにもありません。9-6「入力の制約」で学んだ受け取る側の入力チェックが入っているのはこちらのアプリなので、ここだけアプリを替えます。

自分が書いたフォームリクエストが、そのまま材料になります。

```php
// app/Http/Requests/StoreUserRequest.php（9-6-5 の rules と messages）
    public function rules()
    {
        return [
            'name' => 'required|max:50',
            'email' => 'required|email|unique:users',
            'password' => 'required|min:8|confirmed',
        ];
    }

    public function messages()
    {
        return [
            'name.required' => '名前は必須です',
            'name.max' => '名前は50文字以内で入力してください',
            'email.required' => 'メールアドレスは必須です',
            'email.email' => 'メールアドレスの形式が正しくありません',
            'email.unique' => 'このメールアドレスは既に使用されています',
            'password.required' => 'パスワードは必須です',
            'password.min' => 'パスワードは8文字以上で入力してください',
            'password.confirmed' => 'パスワードが一致しません',
        ];
    }
```

画面のほうには、入力欄が4つありました。

        <div class="form-group">
            <label>名前</label>
            <input type="text" name="name" value="{{ old('name') }}" class="@error('name') error @enderror">

    <div class="success-box">

### Step 1: 入力チェック表を作る

上のコードから、`画面`・`項目`・`必須`・`文字数・桁数`・`形式・値の範囲`・`ほかの項目との関係` の6列の表を作ります。画面名は「ユーザー登録画面」とします。

写すのではなく、🔑 **組み替える**のがこのStepです。`max:50` や `unique:users` といったルール名は書かず、この章の列に日本語で振り分けてください。

もう1つ考えてほしいことがあります。画面の入力欄は4つですが、この表は4行にはなりません。書き方で見た、ほかの項目との関係しか決まらない欄が1つあるからです。どの欄がそれに当たるのかを見つけて、何行になるかを決めてから表を作ってください。

### Step 2: 決めた理由を書き足す

表の下に、「50文字」と「8文字」をそう決めた理由を書きます。9-6-5の要件にはこの2つの数字が書かれていましたが、なぜその数字なのかは書かれていませんでした。あなたが設計者なら、どんな理由でこの数字にしますか。理由を思いつけないなら、それは自分で決めてよい数字ではありません。想定を添えて確認事項リストへ回す、という書き方でも構いません。

### Step 3: メッセージ一覧を作る

`画面`・`出る場面`・`区分`・`メッセージ` の4列で作ります。文言は、9-6-5の `messages()` に書いた8つをそのまま使ってください。ここでは、書き方で決めた型に直さずに写します。型に合っていない文言がどれかは、このあとの「よくある間違いと現場での使われ方」で見比べます。

8行で終わりにしないでください。9-6-5で `messages()` に書かなかった文言が、もう1つ画面に出ていました。登録が終わったあとの画面の見出しです。この画面の名前は「登録完了画面」とします。上のコードから、その見出しの1文を、画面に出ていたとおりの文字で9行目に足してください（添え書きの1文は入れません）。これを足すと、区分の欄が要る理由が分かります。

### Step 4: design-practiceに保存する

`13-3/` フォルダに、入力チェック表を `signup-input-check.md`、メッセージ一覧を `signup-messages.md` として保存します。ファイル名の先頭が `blog-` ではなく `signup-` なのは、別のアプリの成果物だからです。

```bash
# design-practice フォルダの中で実行する
git add 13-3
git commit -m "13-3: ユーザー登録フォームの入力チェック表とメッセージ一覧を追加"
git push origin main
```

次の観点で、自分の成果物と見比べてください。

- [ ] 入力チェック表に、`max:50` のようなルール名が1つも書かれていない
- [ ] 決めることが無い欄に `-` が書かれていて、空欄になっていない
- [ ] 「50文字」「8文字」について、そう決めた理由が書かれている
- [ ] メッセージ一覧に、エラーではない知らせが1行入っている
- [ ] どの行を読んでも、どの画面のどんな場面で出るのかが分かる
- [ ] メッセージの文言が、9-6-5で画面に出していたものと一致している

設計に唯一の正解はありません。文言の並び順や理由の書き方が解答例と違っていても、上の観点を満たしていれば合格です。そのうえで、判断が分かれやすい3点を補足します。

- **3行になった欄の選び方**: パスワード（確認）が、書き方で見た「同じ値をもう一度入れてもらう欄」に当たります。この欄そのものには長さも形の決まりもないので、独立した行にはせず、パスワードの行の「ほかの項目との関係」に書きました。
- **数字の理由を書き残す理由**: 9-6-5の要件には「最大50文字」「最小8文字」という数字だけが書かれていて、変えてよい数字なのかが分かりませんでした。理由が思いつかず、確認事項リストへ回したなら、それも正解です。
- **完了のメッセージを一覧に入れた理由**: 読み方で見たとおり、うまくいったときの知らせも同じ一覧にまとめるためです。

</details>

## 💡 よくある間違いと現場での使われ方

**よくある間違い: 文言を実装のときに考える**

9-6-5で自分が書いた文言を見返してみてください。「名前は必須です」は今の状態だけを伝えていて、「名前は50文字以内で入力してください」は次にどうすればよいかまで伝えています。同じ画面の中でも、型がそろっていないことがあります。実装より先に一覧を作れば、この違いに気づいたところで直せます。

現場では、入力チェック表は実装する人の作業指示になり、そのままChapter 8で学ぶ「何を確かめれば正しいと言えるか」の元にもなります。30文字以内と決めてあれば、30文字と31文字を試せばよい、という具合です。メッセージ一覧のほうは、文言を直したいときの唯一の置き場所になります。コードの中に文言が散らばっていると、どこを直せばよいのかを探すところから始まります。

## ✨ まとめ

- 入力の決まりごとは、コードを書きながらでも決まってしまいます。だからこそ、書く前に決めて表に残します。
- 入力チェック表は、画面項目定義の入力と選択の行だけを引き継ぎ、`画面`・`項目`・`必須`・`文字数・桁数`・`形式・値の範囲`・`ほかの項目との関係` の6列で作ります。
- 埋めるときは、空でよいか・長さ・形と範囲・すでにあるものと重なってよいか・ほかの項目との関係、の5つを順に問いかけます。ルール名は書かず、日本語で書きます。
- 決めた数字には理由を添えます。理由を思いつけない数字は、自分で決めずに確認事項リストへ回します。
- メッセージ一覧は、`画面`・`出る場面`・`区分`・`メッセージ` の4列で作ります。区分はエラーと完了の2つで、文言は「どの項目が・どうなっているか・どうすればよいか」の型でそろえます。

これで、画面設計で作る設計書がひととおりそろいました。次のセクション（13-3-4）は、Chapter 3の設計演習です。13-2-3で受け取ったカフェのモバイルオーダーアプリの続きとして、画面一覧から文言まで、白紙から作ります。
