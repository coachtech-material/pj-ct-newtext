# 13-2-1: 仕様書の読み方と機能一覧

## 🎯 このセクションで学ぶこと

- 仕様書の文章から、誰が使うのか・何をしてほしいのか・何は作らないのかを読み取れるようになる。
- 読み取った内容を、機能一覧という表にまとめられるようになる。
- 仕様書に書かれていない決めごとを見つけ、自分の想定を添えた確認事項リストに書き出せるようになる。

---

## 導入：文章のままでは、作るものを数えられない

仕様は、整理された箇条書きでは届きません。「こういうことに困っていて、こうなると助かる」という、依頼した人が書いたふつうの文章で届きます。これを仕様書と呼びます。

その文章を読んだだけでコードを書き始めると、2つのことが起きます。

1つ目は、作るものを数え間違えることです。作ってほしい機能は文章のあちこちに散らばっているので、読んだだけでは全部でいくつ作るのかが分かりません。3つ作ったところで終わったつもりになり、4つ目があったと気づくのは、依頼した人に見せた日です。

2つ目は、文章に書かれていないことを、自分で埋めてしまうことです。仕様書を書いた人にとって当たり前のことは、わざわざ書かれません。書かれていないと手が動かないので、作る側は「たぶんこうだろう」と決めて進みます。その想定が違っていたときに起きるのが、13-1-1で学んだ手戻りです。

この2つを防ぐために、Chapter 2の最初に2つの表を作ります。作るものを数えられる形に並べた**機能一覧**と、仕様書に書かれていない決めごとを依頼した人に確認するための**確認事項リスト**です。

---

## 仕様書の読み方

題材は、図書館の本を検索したり予約したりできる「図書館アプリ」です。市立図書館の司書の方から、次の相談が届いたとします。作ってほしい機能がいくつあるかを数えながら読んでみてください。

> **図書館アプリのご相談**
>
> 市立図書館で司書をしています。今は本を探すのも予約するのも、窓口まで来ていただくか電話をいただくしかなく、お互いに手間がかかっています。利用者の方がご自宅のスマートフォンから使える、図書館アプリを作ってもらえないでしょうか。
>
> 利用者の方には、まず読みたい本を探せるようにしてあげたいです。タイトルや著者名などから、図書館にある本を探せると助かります。読みたい本が見つかったら、そのまま予約できるようにしてください。予約したあとで都合が変わることもありますので、予約の取り消しもできるとよいと思います。
>
> 私たち司書の側の話もさせてください。カウンターで本をお貸ししたときに、どの本を誰にお貸ししたのかをアプリに記録できるようにしてほしいです。今は紙の台帳に書いていて、月末の集計に時間がかかっています。新しく入った本をアプリに登録するのも、私たちの仕事になります。
>
> なお、本の発注や購入は今までどおり別の仕組みで行いますので、今回のアプリには含めなくて大丈夫です。

この文章から拾うのは、使う人・してほしいこと・作らないものです。

**誰が使うのかを拾う**

まず、文章に出てくる人を探します。「市立図書館で司書をしています」「利用者の方がご自宅のスマートフォンから」とあるので、このアプリを使うのは利用者と司書の2種類です。

使う人が先に分かっていると、残りを読むときに「これは誰の操作だろう」と見分けながら読めます。

**してほしいことを拾う**

次に、動詞を探します。「探せる」「予約できる」「取り消しもできる」「記録できる」「登録する」の5つが見つかります。「〜できるようにしてほしい」「〜もできるとよい」と書かれている部分が、作る機能の候補です。

読みながら書き出さないと、必ず落とします。

**何は作らないのかを拾う**

最後の段落に「本の発注や購入は……今回のアプリには含めなくて大丈夫です」とあります。

どこまで作るかの線引きは、時間が経つと関わった全員があやふやになります。「発注機能はどうなっていましたか」と後で聞かれたときに「今回は作らないと最初に決まっています」と示せるよう、作らないと決まったものも書き残します。

> 💡 **TIP**: 作らないものが仕様書に書かれていないほうが、むしろふつうです。書かれていない場合の扱いは、このあとの「一覧の下に、作らないものを残す」で説明します。

## 機能一覧の書き方

拾い出した内容を、Markdownの表にまとめます。

<details>
<summary>💡 Markdownで表を書く方法（初めて書く人向け）</summary>

12-2-2でイシューを書いたときの、見出しやリストと同じ記法の続きです。表は縦棒（`|`）とハイフンだけで作れます。次のように書くと、

```markdown
| ID | 機能 | 主な利用者 |
|:---|:-----|:-----------|
| F-01 | 本の検索 | 利用者 |
```

このように表示されます。

| ID | 機能 | 主な利用者 |
|:---|:-----|:-----------|
| F-01 | 本の検索 | 利用者 |

1行目が見出しの行です。2行目の `|:---|` は「ここから下がデータの行」という区切りで、この行を書かないと表として表示されません。ハイフンの前の `:` は、その列の文字を左に寄せる指定です。

行を増やしたいときは、同じ形の行を下に足すだけです。縦棒の位置は揃っていなくても構いません。`|ID|機能|主な利用者|` と詰めて書いても表示される表は同じなので、桁を揃えることに時間をかけなくて大丈夫です。

自分の書いた表がこのとおりに表示されるかは、VS Codeで確かめられます。`.md` ファイルを開いた状態で `Ctrl+Shift+V`（Macは `Cmd+Shift+V`）を押すか、エディタ右上のプレビューのボタンを押すと、表示された姿が出ます。区切り行を書き忘れていれば表にならないので、その場で気づけます。

</details>

まず、できあがった図書館アプリの機能一覧を見てください。

| ID | 機能 | 主な利用者 |
|:---|:-----|:-----------|
| F-01 | 本の検索 | 利用者 |
| F-02 | 本の予約 | 利用者 |
| F-03 | 予約の取り消し | 利用者 |
| F-04 | 貸出の記録 | 司書 |
| F-05 | 蔵書の登録 | 司書 |

先ほどの相談の文章と見比べてください。作るものが5つだと🔑 **数えられる**ようになり、名前とIDが付いたので「F-02はできましたか」と一言で指せます。誰の機能なのかも、縦に並べて見比べられます。

この表は、次の手順で作ります。

**手順1: 動詞を拾って、そのまま書き出す**

「仕様書の読み方」で拾った動詞を、思いついた順に書き出します。この時点では並び順もIDも気にしません。図書館アプリなら、先ほど拾った5つがそのまま並びます。

**手順2: 粒度を揃える**

粒度とは、1行をどこまで細かく分けるかということです。🔑 **1つの目的で1行**が目安になります。

大きすぎる例が「本の管理」です。この1行では、検索なのか登録なのか貸出なのか分かりません。逆に小さすぎる例が「検索ボタンを押す」「検索結果を表示する」です。どちらも「本を探す」という1つの目的の途中経過なので、分けても行が増えるだけです。

図書館アプリでは、「予約する」と「予約を取り消す」を別の行にしました。操作する場面も目的も違うからです。一方、「タイトルで探す」と「著者名で探す」は分けません。どちらも「本を探す」という1つの目的の中の、探し方の違いです。

**手順3: 名前を付けて、IDを振る**

行の名前を決めます。**名詞の形に揃える**のがコツです。「本を検索する」と書かずに「本の検索」と書きます。形が揃っていると、表を縦に読んだときに違いが見つけやすくなります。

名前が決まったら、上から `F-01`、`F-02` とIDを振ります。Fはfunction（機能）の頭文字で、番号は2桁のゼロ埋めです。

> ⚠️ **注意**: あとから機能が増えたときは、末尾に足します。順番を整えたくなっても、IDを振り直してはいけません。すでに「F-03の件ですが」と会話やメモに書かれた番号が、全部ずれます。

**手順4: 主な利用者を決める**

各行に誰が使うのかを、仕様書に戻って確かめながら書きます。書くのは「利用者」「司書」のような人の種類ですが、ログインの前と後でできることが変わるアプリでは、「ログイン済み利用者」のようにログインの有無で分けて書くこともあります。

列名を「主な利用者」としたのは、1つの機能を複数の人が使うことがあるからです。「予約の取り消しは、司書も代わりにできるのだろうか」と迷ったら、それは仕様書に決めごとが書かれていないというサインです。自分で決めずに、次に説明する確認事項リストへ回します。

> 💡 **TIP**: 現場では、この表に優先度（高・中・低）や担当者の列を足すこともあります。どれから作るか、どこまで進んだかを管理するためです。この教材では、3列のままで進めます。

**一覧の下に、作らないものを残す**

「仕様書の読み方」で拾った作らないものは、機能一覧のすぐ下に小さな表として付けます。図書館アプリなら、次の1行です。

**今回作らないもの**

| 作らないもの | 理由 |
|:-------------|:-----|
| 本の発注・購入 | 今までどおり別の仕組みで扱うため、依頼の時点で対象外と決まっている |

理由の列を空けないのがコツです。名前だけでは、決まったことなのか、まだ決めていないだけなのかが区別できません。

この表に並べるのは、🔑 **作らないと決まったもの**だけです。「あってもよさそうだが、仕様書に書かれていない」ものは、まだ決まっていないので、確認事項リストのほうに書きます。確認が取れて「作りません」と決まったら、そこでこの表に移します。作る範囲を図で表す方法は、13-2-2で扱います。

## 確認事項リストの書き方

機能一覧を作っていると、必ず「これはどっちだろう」という場所にぶつかります。そこを書き留めておくのが確認事項リストです。

### 曖昧な点の見つけ方

曖昧な点を探そうとしなくても、表を作る作業そのものが見つけてくれます。**手が止まった場所**と、**「たぶんこうだろう」と埋めた場所**が、そのまま曖昧な点です。

図書館アプリでは、たとえば次のところで手が止まります。

- 「タイトルや著者名など」の「など」には、何が入るのか。出版社でも探せるのか。
- 予約を取り消せるのは、予約した本人だけなのか。司書も代われるのか。
- 蔵書の登録は、司書だけの操作でよいのか。
- 貸出の記録には、いつ貸したかだけを残せばよいのか。

どれも、決めなければ画面もテーブルも決まりません。そして、どれも仕様書には書かれていません。

### 想定を添えた聞き方

見つけた曖昧な点は、依頼した人に確認します。このとき、🔑 **自分の想定を先に示してから聞きます**。「予約の取り消しは、どうしますか」と丸ごと投げずに、「利用者本人だけが取り消せるという設計を想定していますが、問題ないですか」と書きます。想定が示してあれば、相手は「はい」か「いいえ、司書も取り消せるようにしてください」と答えるだけで済み、確認が1往復で終わります。こちらが仕様書をどう受け取ったかも同時に伝わるので、読み違いがあればその場で正してもらえます。

### 表にまとめる

確認事項リストも、機能一覧と同じくMarkdownの表で作ります。図書館アプリなら次のようになります。

| ID | 確認したいこと（こちらの想定つき） | 関係する機能 | 状態 |
|:---|:-----------------------------------|:-------------|:-----|
| Q-01 | タイトルと著者名で検索できる想定ですが、出版社や分類での検索も必要ですか | F-01 | 未確認 |
| Q-02 | 利用者本人だけが予約を取り消せる想定ですが、司書が代わりに取り消すことはありますか | F-03 | 未確認 |
| Q-03 | 蔵書の登録は司書だけが扱う想定で問題ないですか | F-05 | 未確認 |
| Q-04 | 貸出の記録には貸した日だけを残す想定ですが、返却期限や返却の記録も必要ですか | F-04 | 未確認 |

IDは機能一覧と同じ振り方で、`Q-01` から順に付けます。「関係する機能」の列で機能一覧のIDと結び付けておくと、回答が返ってきたときに、どの行を直せばよいかがすぐ分かります。複数の機能にまたがる場合は `F-01・F-02` のように並べ、結び付く機能がまだ無い場合は「なし」と書きます。

「状態」の列は、書いた直後は全部「未確認」で、回答が返ってきたら「回答済み」に変え、答えをその行に書き足します。**答えが返ってきた行を消してはいけません**。「なぜこの仕様になったのか」を後から追える記録になるからです。

### 確認が取れたあとにすること

確認が取れたら、その内容を機能一覧に反映します。「司書も予約を取り消せます」という答えならF-03の主な利用者に司書を書き足し、「返却の記録も残してください」という答えなら新しい行を足します。「それは今回作りません」という答えなら、その行を確認事項リストから作らないものの表へ移します。

この先の章で設計を細かくしていくと、機能一覧から漏れていたものが後から見つかります。そのときも勝手に足さずに「〜も必要という理解で合っていますか」と確認事項リストに書き出し、確認が取れてから一覧に足します。

設計書のゴールは「**それを見たら、人でもAIでもすぐ実装に入れる状態**」でした。未確認の行が残っているうちは、その先の設計を確定させられません。

## 🏃 作ってみよう

図書館アプリは「読む」練習でした。今度は、13-1-3で手元に用意した投稿アプリ（`post-app-practice`）で、機能一覧と確認事項リストを作ります。この先の章の実践も、すべてこの1本を題材に進めます。

このアプリは、すでに動くコードが入った状態で配られています。設計書だけが無い状態です。現場でも、動いているシステムに機能を足すときに、まず今あるものを設計書に起こす作業から始めることがあります。今回はその練習でもあります。

> ⚠️ **注意**: 今回表にするのは、「使う人から見て、このアプリで何ができるか」だけです。ルートの書き方やPolicyの実装といったコードの中身には踏み込みません。

### Step 1: READMEを仕様書として読み、コードで裏を取る

`post-app-practice` をVS Codeで開き、`README.md` の「できること」を読みます。次の4行が書かれています。

```text
## できること

- ユーザー登録・ログイン・ログアウト
- 投稿の一覧表示（投稿者の名前とカテゴリつき）
- 投稿の編集（タイトル・カテゴリ・本文）と削除
- 自分の投稿だけを編集・削除（他人の投稿は編集・削除ボタンが出ず、URL を直接開くと 403 になります）
```

この4行を、仕様書として受け取ったつもりで読んでください。使う人・してほしいこと・作らないもの、の順に拾います。

読んだら、`routes/web.php` を開いて裏を取ります。

```php
// routes/web.php
Route::get('/', function () {
    return view('welcome');
});

// 認証が必要なルート
Route::middleware('auth')->group(function () {
    Route::get('/posts', [PostController::class, 'index'])->name('posts.index');
    Route::get('/posts/{post}/edit', [PostController::class, 'edit'])->name('posts.edit');
    Route::put('/posts/{post}', [PostController::class, 'update'])->name('posts.update');
    Route::delete('/posts/{post}', [PostController::class, 'destroy'])->name('posts.destroy');
});
```

`Route::middleware('auth')->group()` の中にある4本は、ログインしていないと使えません。外にあるのはトップページの1本だけです。ログイン・新規登録のルートはこのファイルに書かれていませんが、10-1-1で学んだFortifyが登録しているので、`resources/views/auth/` にログイン画面と新規登録画面のファイルがあることで確かめられます。

ここで、READMEの4行には書かれていない事実が1つ見つかります。**投稿を新しく書くルートがありません**。編集（`edit`・`update`）と削除（`destroy`）はありますが、作成に当たるものが無く、`resources/views/posts/` にも `index.blade.php` と `edit.blade.php` の2枚しかありません。この事実は、Step 3で使います。

### Step 2: 機能一覧を作る

「機能一覧の書き方」の手順1から4のとおりに進めます。列は `ID`・`機能`・`主な利用者` の3列です。Markdownで表を書く手が止まったら、「機能一覧の書き方」冒頭の折りたたみを見返してください。

**READMEの行数と、機能の数は一致しません**。手が止まったら、その行が「使う人にとっての1つの目的」になっているかを考えてみてください。

主な利用者の欄では、ログインの前と後を区別します。トップページとログイン画面はログインしていない人が開き、投稿の一覧・編集・削除はログインした人が使うからです。

一覧ができたら、その下に「今回作らないもの」の表も作ります。READMEには作らないと決まったものが書かれていないので、この表は見出しと区切り行だけの空の表になります。空欄のまま放置したのと区別できるよう、表の下に「READMEには、作らないと決まったものは書かれていませんでした」と1行添えましょう。「無くてもよさそうだが気になる」ものを思いついたら、Step 3の確認事項リストのほうへ書きます。

### Step 3: 確認事項リストを作る

READMEの4行に書かれていない決めごとを探し、3行以上の確認事項リストを作ります。列は `ID`・`確認したいこと（こちらの想定つき）`・`関係する機能`・`状態` の4列です。

Step 1で見つけた「投稿を新しく書く機能が無い」は、そのまま1行目になります。書かれていないだけなのか、作らないと決まっているのかが、READMEからは判断できないからです。ほかにも、投稿1件だけを開く画面、カテゴリを増やす操作、パスワードを忘れたときの再設定など、無いものを探すと見つかります。必ず自分の想定を先に添えて書いてください。

### Step 4: docs/13-2/ に保存する

`post-app-practice` の中に、Chapter 2用の `docs/13-2/` フォルダを作ります。このフォルダは、この先のセクションでも使います。

```bash
# アプリのフォルダへ移動する
cd ~/laravel-practice/post-app-practice

# Chapter 2用のフォルダを作る
mkdir -p docs/13-2
```

このフォルダには、この先のセクションの成果物や、章末演習で作る別の題材の設計書も一緒に入ります。どちらのものか分かるように、ファイル名の先頭にアプリを表す短い言葉を付けます。今回は投稿アプリなので、機能一覧と作らないものの表を `post-feature-list.md` に、確認事項リストを `post-questions.md` にまとめます。

ファイルは、VS Codeの左側のエクスプローラーで `docs` の中の `13-2` フォルダを右クリックし、「新しいファイル...」を選んでファイル名を入力すると作れます。2-1-5でHTMLファイルを作ったときと同じ手順です。中身は、見出しを置いてから表を書きます。`post-feature-list.md` では、機能一覧の表の下に「今回作らないもの」の見出しと表を続けます。ファイルの形は、このあとの答え合わせに「コピー用」として載せてあります。

保存できたら、コミットとpushまで済ませます。

```bash
# post-app-practice フォルダの中で実行する
git add docs/13-2
git commit -m "13-2: 投稿アプリの機能一覧と確認事項リストを追加"
git push
```

## 💡 よくある間違いと現場での使われ方

**間違い1: 画面やテーブルの名前を書いてしまう**

「投稿一覧画面」「postsテーブル」のように、作り方の側の言葉を機能一覧に書いてしまう間違いです。名詞の形に揃えようとすると、かえって起きやすくなります。この表に並べるのは、使う人から見てできることの名前だけです。それを何枚の画面で見せるかはChapter 3、どんなテーブルに保存するかはChapter 5と、別のところで決めます。

**間違い2: 曖昧な点に気づいたのに、自分で決めて先へ進む**

「たぶん司書も取り消せるだろう」と決めて、そのまま作ってしまう間違いです。決めたこと自体が悪いのではなく、それが自分の頭の中にしか残らないのが問題です。確認事項リストに1行書き足せば、その決めごとは全員が見られる場所に残ります。

機能一覧は、現場では依頼した人と「作るものの範囲と数」を先に合意するための1枚です。数が合っていないと、どこまでできたら終わりなのかを判定できません。作らないものの表まで添えれば、範囲の線がどこにあるかも同時に合意できます。

確認事項リストは、回答を書き足して残しておけば、半年後に「なぜこの仕様なのか」と聞かれたときの根拠になります。

## ✨ まとめ

- 仕様書はふつうの文章で届きます。読むときは、誰が使うのか・何をしてほしいのか・何は作らないのかを探しながら読みます。
- 機能一覧は、作るものを数えられる形に並べた表です。動詞を拾い、1つの目的で1行になるよう粒度を揃え、名詞の形の名前と `F-01` からのIDを振り、主な利用者を決めます。IDは他の設計書と突き合わせる目印なので、増えた機能は末尾に足し、振り直しません。
- 作らないと決まったものは、一覧の下に理由を添えて残します。まだ決まっていないものは、この表に入れません。
- 仕様書に書かれていない決めごとは、手が止まった場所と「たぶんこうだろう」と埋めた場所に現れます。見つけたら、自分の想定を添えて確認事項リストに書き出します。相手は「はい」か「いいえ」で答えられ、確認が1往復で終わります。
- 確認が取れたら、その内容を機能一覧か、作らないものの表に反映します。あとから見つかった漏れも、同じ流れで足します。
