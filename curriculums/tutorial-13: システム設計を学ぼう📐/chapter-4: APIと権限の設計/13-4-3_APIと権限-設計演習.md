# 13-4-3: APIと権限 - 設計演習

## 📌 この演習について

カフェのモバイルオーダーアプリの続きとして、画面の裏側を白紙から設計します。ここで決めるのは、それぞれの画面が何をどこから受け取り、どこへ送るのか、そして誰がどの操作をしてよいのかです。

Chapter 3までの成果物が手元にない方は、`answers/13-3/` の中身を `docs/13-3/` にコピーしてから始めてください。

---

## 🎯 演習課題

### 📋 与えられる仕様

新しい仕様は渡されません。使うのは次の3つです。

1. 13-2-3で受け取ったカフェのモバイルオーダーアプリの仕様書。
2. 13-2-3で作った機能一覧・確認事項リスト・ユースケース図・ユースケース記述。
3. 13-3-5で作った画面一覧・画面遷移図・入力チェック表・メッセージ一覧。

手元に無い方は、13-2-3と13-3-5の模範解答を土台にして構いません。ただし、自分の解答と模範解答のどちらを土台にするかを最初に決めて、最後までそちらで通してください。途中で混ぜると、機能・画面・エンドポイントの数が合わなくなります。

支払いについては、13-3-5で置いた前提をそのまま引き継ぎます。支払いそのものは外部の決済サービスに任せ、皆さんが設計するのは、支払いを依頼して、その結果を受け取るところまでです。どのサービスを使うか、どうつなぐかは、この教材では扱いません。

店員側について、仕様書からもう一度引いておきます。認証が必要かどうかを決めるときに、何度も戻ることになる箇所です。

> 私たち店員の側の話もさせてください。カウンターの中にタブレットを1台置いて、入った注文をそこで見られるようにしたいです。商品ができてお客さまにお渡ししたら、その場で「渡しました」と記録できると助かります。今は紙の伝票を手で仕分けていて、渡し忘れが起きることがあります。

お客さま側については、商品の名前・値段・短い説明が並べば十分だと書かれていた段落を、返すものを決めるときに読み返してください。

13-2-3と13-3-5で書き出した確認事項は、**未確認のまま**です。返事を待たずに、そこに書いた自分の想定の上で設計を進めてください。新しく決めきれない点が出てきたら、自分のリストの最後の番号の続きから書き足します（模範解答を土台にした方は `Q-10` からです）。新しいファイルは作らず、13-2-3で作った確認事項リストに行を足してください。

### ✏️ 作成する成果物

保存先は、13-4-1で作った `docs/13-4/` フォルダです。ファイル名の先頭は `cafe-` を付けます。

1. API設計書。`cafe-api.md` の1ファイルに、エンドポイント一覧・1本ごとの詳細・エラーレスポンス一覧を、この順でまとめます。エンドポイント一覧は `ID`・`メソッド`・`エンドポイント`・`何をするか`・`認証` の5列で、IDは `API-01` から振ります。

1. お客さまが使うもののうち、注文を受け付けるもの。
2. 店員が使うもののうち、受け渡しを記録するもの。

1本目について、先に断っておきます。支払いそのもののエンドポイントは作りません。外の仕組みへ引き渡すのは注文を受け付けたあとです。13-2-3で書いたUC-02の基本フローとの食い違いに気づいたら、その扱いは書き終えたあとに模範解答で確かめてください。

## 🏃 実践

### 🧠 先輩エンジニアの思考プロセス

先輩エンジニアは、画面設計の成果物を次の順でAPIと権限に落とし込みます：

| Step | やること | 説明 |
|:-----|:---------|:-----|
| 1 | 画面遷移図を1画面ずつたどり、取りに行くものと送るものに印を付ける | エンドポイントは思いつきで数えない。画面が必要とするものが、そのまま入口になる |
| 2 | 印を付けたものを、扱うものごとにまとめてURLを決める | URLに動きを表す言葉は入れない。何をするかはメソッドで表す |
| 3 | メソッドを決めて、エンドポイント一覧に並べる | 取るならGET、増やすならPOST、書き換えるならPUT、消すならDELETE |
| 4 | 条件や分岐が絡むものから、詳細を書く | 全部は書かない。送るものと返るものは「なし」も含めて埋める |
| 5 | うまくいかなかったときを洗い出して、一覧にする | 自分が作るこのAPIが返すぶんだけ。原因の細かい分類は先の章 |
| 6 | 機能一覧を縦に置いて、ロールごとに ○×△ を埋める | 埋まらないマスが、決まっていない場所 |

### 📝 ステップバイステップで作る

#### Step 1: 画面をたどって、取りに行くものと送るものに印を付ける

13-3-5で描いた画面遷移図を開き、四角を1つずつたどります。それぞれの画面について、「この画面を映すために取りに行くものはあるか」「この画面から送るものはあるか」の2つを問います。

模範解答を土台にしている方なら、画面は7枚あります。全部の画面に印が付くわけではありません。カート画面のように、前の画面で選んだものを映すだけで、サーバー側へ取りに行かない画面もあります。印が1つも付かなかった画面が出てきたら、なぜ付かないのかを説明できるかを確かめてください。

#### Step 2: 扱うものごとにまとめて、URLを決める

印を付けたものを見比べると、大きく2種類に分かれるはずです。商品にまつわるものと、注文にまつわるものです。それぞれにURLを1つずつ決めます。

1件を指すときの `{ }` の中身も、ここで決めます。13-4-1で書いた投稿アプリのAPIでは `{id}` でしたが、カフェには、注文1件を指すために13-2-3のユースケース記述で決めた言葉があります。13-3-5の入力チェック表で桁数まで決めた、あの言葉です。

#### Step 3: メソッドを決めて、エンドポイント一覧に並べる

同じURLでも、メソッドが違えばすることが変わります。注文のURLは、登録・状況の確認・取り消し・一覧の取得・受け渡しの5つの場面で使うことになるはずです。店員が受け取り前の注文を一覧で見る場面（UC-05の基本フロー2）を数え落としやすいので、気をつけてください。

店員が注文を1件選んだあとに見る商品と個数は、この一覧が返すものに含めます。13-4-1の手順3のとおり、入口は増やしません。

「認証」の欄は、お客さま側と店員側で答えが変わります。お客さま側は、13-2-3で会員登録について立てた想定で決まります。店員側は、仕様書の「カウンターの中にタブレットを1台置いて」という記述から考えます。ここで決まらないと感じたら、想定を1つ置いて、確認事項リストへ送ってください。

#### Step 4: 指定された2本の詳細を書く

お客さまが使うもののうち注文を受け付けるもの1本と、店員が受け渡しを記録するもの1本です。

注文を受け付けるほうを書くと、必ず手が止まります。止まった理由をそのまま言葉にして、確認事項リストへ送ってください。なお、外の仕組みへ引き渡すときは、「どこへ送ればよいか」を返すことになります。呼び方や形は決まらなくてよいので、返すものの1つとして日本語で書いておきます。

店員が使うほうでは、13-2-3で書いたUC-05の基本フロー5と6が手がかりになります。店員が何を押し、その結果システムが何を記録するのかが、そのまま送るものと返るものになります。

#### Step 5: うまくいかなかったときを洗い出して、一覧にする

`起きること`・`ステータスコード`・`返すもの` の3列で作ります。手がかりは、13-2-3で書いた代替フローと、13-3-5で作ったメッセージ一覧です。UC-02の代替フローとUC-05の代替フローが、それぞれどのエンドポイントの話なのかを確かめてください。

画面に出す文言は13-3-5のメッセージ一覧で決めたものなので、ここで決め直しません。そこに書いた言い回しを、そのまま「返すもの」の欄に写します。

売り切れの商品を注文されたときにどうするかも、この表で決めます。13-3-5のメッセージ一覧に、その文言はすでにあるはずです。使う数字は、11-1-1と11-2-7で見たものの中から選んでください。

#### Step 6: 権限マトリクスを作り、保存する

13-2-3の機能一覧の5行を、そのまま権限マトリクスの行に写します。列は、機能一覧の「主な利用者」列から起こします。ログインしていない相手をどう扱うかは、13-4-2の手順1のとおりに考えてください。ここでも、会員登録について13-2-3で自分が立てた想定が効いてきます。お客さまがそもそもログインしない前提なら、その列を別に立てるかどうかも、その想定から決まります。

マスを埋めていくと、13-2-3のユースケース図で線を引くかどうか迷った場所が、そのまま迷うマスとして出てきます。図に戻って確かめてください。

API設計書と権限マトリクスがそろったら、13-4-2の手順5のとおりに突き合わせます。×と書いたのに「認証：不要」のままになっている組み合わせが出てきても、それだけでは間違いではありません。それが何を意味するのかは、模範解答で確かめてください。

書き終えたら、`docs/13-4/` フォルダに2つのファイルを保存します。

```text
docs/13-4/
├── cafe-api.md                  # API設計書
└── cafe-permission-matrix.md    # 権限マトリクス
```

確認事項リストは `docs/13-2/cafe-questions.md` に書き足すので、コミットには両方のフォルダを含めます。

```bash
# アプリのフォルダの中で実行する
git add docs/13-2 docs/13-4
git commit -m "13-4: カフェのモバイルオーダーアプリのAPI設計書と権限マトリクスを追加"
git push
```

<summary>📖 作り終えたら開く（模範解答）</summary>

**エンドポイント一覧（解答例）**

| ID | メソッド | エンドポイント | 何をするか | 認証 |
|:---|:---------|:---------------|:-----------|:-----|
| API-01 | GET | /api/products | その日の商品の一覧を取得する | 不要 |
| API-02 | POST | /api/orders | 注文を登録する | 不要 |
| API-03 | GET | /api/orders/{注文番号} | 注文1件の状況を取得する | 不要 |
| API-04 | DELETE | /api/orders/{注文番号} | 注文を取り消す | 不要 |
| API-05 | GET | /api/orders | 受け取り前の注文を、商品と個数とともに一覧で取得する | 必要 |
| API-06 | PUT | /api/orders/{注文番号} | 注文を受け渡し済みにする | 必要 |

6本のうち、SC-02 カート画面に対応するエンドポイントはありません。カートに入れた商品と個数は、支払いに進むまでは画面の中だけの話だからです。SC-03 支払いの画面は外の仕組みの中で進み、SC-04 注文完了画面はAPI-02が返した注文番号を映すだけなので、こちらも新しい入口は増えません。SC-07 注文詳細画面が見せる商品と個数も、API-05が一覧で返しているので、そこから選んだ1件を映すだけです。API-04のDELETEは「この注文を無かったことにしてください」という依頼で、注文の行を消すという意味ではありません。データをどう残すかはChapter 5とChapter 6で決めます。

**API-02の詳細（解答例）**

```markdown
#### API-02: 注文を登録する

- **メソッドとエンドポイント**: POST /api/orders
- **認証**: 不要
- **送るもの**: 本文で、注文する商品と個数の組（1組以上。個数は1つの商品あたり10個まで）
- **返すもの（うまくいったとき）**: 201。注文番号と、合計金額と、支払いの手続きに進むための行き先
- **返すもの（うまくいかなかったとき）**: 422（送ったものに不備があるとき、または選んだ商品が売り切れているとき）
```

「支払いの手続きに進むための行き先」は、外の決済の仕組みのどこへお客さまを送ればよいのかを表すURLのことです。実際にどんな形で返すのかは、つなぎ方が決まってから決めます。

**API-06の詳細（解答例）**

```markdown
#### API-06: 注文を受け渡し済みにする

- **メソッドとエンドポイント**: PUT /api/orders/{注文番号}
- **認証**: 必要
- **送るもの**: URLに注文番号。本文で、受け渡し済みにすること
- **返すもの（うまくいったとき）**: 200。書き換えたあとの注文1件（注文番号・商品と個数・合計金額・受け渡し済みであること）
- **返すもの（うまくいかなかったとき）**: 401（ログインしていないとき）／404（その注文番号の注文が無いとき）
```

「受け渡し済み」は、機能設計の演習で決めた言葉をそのまま使っています。「受け取り前」と合わせて2つありますが、この2つで足りるのか、どんな順で移り変わるのかは、Chapter 6で決めます。

**エラーレスポンス一覧（解答例）**

| 起きること | ステータスコード | 返すもの |
|:-----------|:-----------------|:---------|
| 送ったものに不備がある（注文の登録） | 422 | 不備のあった項目と、その理由の文言 |
| 売り切れの商品が注文された（注文の登録） | 422 | 「この商品は売り切れです」という文言 |
| 指定した注文番号の注文が見つからない（お客さまの状況の確認・取り消し） | 404 | 「ご入力の注文番号の注文が見つかりません」という文言 |
| 指定した注文番号の注文が見つからない（店員の受け渡し） | 404 | 「該当する注文がありません」という文言 |
| ログインしていない（店員が使うもの） | 401 | ログインが必要である旨の文言 |

文言は、どれも画面設計の演習でメッセージ一覧に決めたものです。ここで決め直さず、返す場所だけを移しました。売り切れの文言はメニュー画面のものでしたが、「カートに入れる」を押した時点ではサーバーへ問い合わせないので、サーバーが返す場面は注文の登録のときだけになります。

3行目と4行目は、どちらも404です。それでも行を分けたのは、返す文言が違うからです。同じ数字でも、出す画面が違えば言い回しが変わります。一覧を開いてから「受け渡し済みにする」を押すまでの間に、お客さまがその注文を取り消していることがあるので、受け渡しの時点でも見つからない場合を決めておきます。

代替フロー5a「支払いが完了しなかった場合」は、この表に入っていません。支払いの手続きは外の仕組みの中で進むので、うまくいかなかったことも、まず外の仕組みの側で起きるからです。

**権限マトリクス（解答例）**

| 機能 | お客さま | 店員 |
|:-----|:---------|:-----|
| F-01 メニューの閲覧 | ○ | × |
| F-02 商品の注文 | ○ | × |
| F-03 注文状況の確認 | △ | × |
| F-04 注文の取り消し | △ | × |
| F-05 注文の受け渡し | × | ○ |

△の条件

- F-03 注文状況の確認（お客さま）: 自分が出した注文だけ（注文番号を知っている方だけ）
- F-04 注文の取り消し（お客さま）: 自分が出した注文だけ（注文番号を知っている方だけ）

列は「お客さま」「店員」の2つだけです。会員登録をしない想定なので、お客さまの列が、ログインしていない相手の列を兼ねます。店長とアルバイトの区別が要ることになれば、列が1つ増えます。

**迷いやすいところ**

**お客さま側を「認証：不要」にした理由と、その穴**

会員登録をしない想定なので、そのお客さまが誰なのかをアプリは知りません。ログインの仕組みが無いので、お客さま側の入口は「不要」になります。

ここで穴が1つ生まれます。注文番号さえ知っていれば、誰でもその注文の状況を見られて、取り消せてしまうのです。注文番号は6桁の数字なので、順に試せば他人の注文に当たることもあります。だからこそ、△の条件を「自分が出した注文だけ」で終わらせず、「注文番号を知っている方だけ」と書き足しました。この2つは、実装するとまったく違うものになります。前者は本人かどうかを確かめる作りで、後者は確かめない作りです。

設計書に書いてあるのは後者です。それでよいかどうかは自分たちでは決められないので、Q-11として送りました。「決まっていないから書かない」でも「よさそうだから決めてしまう」でもありません。**想定を書いたうえで、その想定を確認に出す**のが、この演習でいちばん設計らしい判断です。

店員の列に×が4つ並んでいるのに、それに当たるAPI-01からAPI-04までの認証が「不要」なのも、同じ話です。この×は「店員の業務としてはやらない」という決定で、仕組みとして止めるには、呼んできた相手を確かめる必要があります。突き合わせて食い違いに気づいたら、そこまでを設計書に残しておけば十分です。

## 🚀 まとめ

- エンドポイントは、画面遷移図を1画面ずつたどって洗い出します。画面の数とエンドポイントの数は一致しません。
- 「認証」の欄は、仕様書のどこかに答えの手がかりがあります。カフェでは、会員登録についての想定と、店員がカウンターの中のタブレット1台を使うという記述が、そのまま答えを決めました。
- 権限マトリクスの×は、ユースケース図で線を引かなかったことと同じ決定です。Chapter 2で保留にした判断が、章をまたいでここに現れます。
- 2枚の設計書は、書き終えたら突き合わせます。「認証：不要」の入口では、×と書いただけでは止まらないので、そこは決め直すか、確認に出すかのどちらかになります。
- 決めきれない点は、Chapter 2・Chapter 3と同じように想定を添えて確認事項リストへ送ります。想定を書いたうえで確認に出しておけば、返事が来たときに、設計書のどの行を直すかがすぐ分かります。

ここまでで、画面の裏側にどんな入口があり、誰がそれを使ってよいのかが決まりました。ただ、返すと決めた項目をこのアプリがどんな形で覚えておくのかは、まだ決めていません。それはChapter 5で決めます。
