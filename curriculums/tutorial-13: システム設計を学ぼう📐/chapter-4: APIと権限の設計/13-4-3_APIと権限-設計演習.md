# 13-4-3: APIと権限 - 設計演習

## 📌 この演習について

Chapter 4では、API設計書の作り方（13-4-1）と、権限マトリクスの作り方（13-4-2）を学びました。題材は、教材が用意した学習塾の出欠管理アプリと、自分で作ったことのあるアプリでした。今回は、13-2-3で受け取ったカフェのモバイルオーダーアプリの続きとして、画面の裏側を白紙から設計します。

Chapter 3までで、お客さまと店員が何を見て、何を押し、何を入力するのかは決まりました。ここで決めるのは、その画面が何をどこから受け取り、どこへ送るのか、そして誰がどの操作をしてよいのかです。

> 🔥 この演習では、設計書をAIに作らせずに、自分の手で書きましょう。記法や考え方についてAIに質問するのは構いませんが、成果物を生成させるのはTutorial 14までお預けです。まず自分の手と頭で書けるようになった人だけが、AIの作った設計を正しく評価できるようになります。

## 🎯 演習課題

### 📋 与えられる仕様

新しい仕様は渡されません。使うのは次の3つです。

1. 13-2-3で受け取ったカフェのモバイルオーダーアプリの仕様書。
2. 13-2-3で作った機能一覧・確認事項リスト・ユースケース図・ユースケース記述。
3. 13-3-4で作った画面一覧・画面遷移図・入力チェック表・メッセージ一覧。

手元に無い方は、13-2-3と13-3-4の模範解答を土台にして構いません。ただし、自分の解答と模範解答のどちらを土台にするかを最初に決めて、最後までそちらで通してください。途中で混ぜると、機能・画面・エンドポイントの数が合わなくなります。

支払いについては、13-3-4で置いた前提をそのまま引き継ぎます。支払いそのものは外部の決済サービスに任せ、皆さんが設計するのは、支払いを依頼して、その結果を受け取るところまでです。どのサービスを使うか、どうつなぐかは、この教材では扱いません。

店員側について、仕様書からもう一度引いておきます。認証が必要かどうかを決めるときに、何度も戻ることになる箇所です。

> 私たち店員の側の話もさせてください。カウンターの中にタブレットを1台置いて、入った注文をそこで見られるようにしたいです。商品ができてお客さまにお渡ししたら、その場で「渡しました」と記録できると助かります。今は紙の伝票を手で仕分けていて、渡し忘れが起きることがあります。

お客さま側については、商品の名前・値段・短い説明が並べば十分だと書かれていた段落を、返すものを決めるときに読み返してください。

13-2-3と13-3-4で書き出した確認事項は、**未確認のまま**です。返事を待たずに、そこに書いた自分の想定の上で設計を進めてください。新しく決めきれない点が出てきたら、自分のリストの最後の番号の続きから書き足します（模範解答を土台にした方は `Q-10` からです）。新しいファイルは作らず、13-2-3で作った確認事項リストに行を足してください。

### ✏️ 作成する成果物

次の3つを作ります。保存先は、13-4-1で作った `13-4/` フォルダです。ファイル名の先頭は `cafe-` を付けます。

1. API設計書。`cafe-api.md` の1ファイルに、エンドポイント一覧・1本ごとの詳細・エラーレスポンス一覧を、この順でまとめます。エンドポイント一覧は `ID`・`メソッド`・`エンドポイント`・`何をするか`・`認証` の5列で、IDは `API-01` から振ります。
2. 権限マトリクス。`cafe-permission-matrix.md` に、行を13-2-3の機能一覧、列をロールにした表を作ります。△を書いた行には、表のすぐ下に条件を添えます。
3. 確認事項リストへの追記（`13-2/cafe-questions.md`）。

詳細を書くのは、次の2本だけです。

1. お客さまが使うもののうち、注文を受け付けるもの。
2. 店員が使うもののうち、受け渡しを記録するもの。

1本目について、先に断っておきます。支払いそのもののエンドポイントは作りません。外の仕組みへ引き渡すのは注文を受け付けたあとです。13-2-3で書いたUC-02の基本フローとの食い違いに気づいたら、その扱いは書き終えたあとに模範解答で確かめてください。

2本目は、店員がこのアプリでやりたいことの中心で、13-2-3で書いたUC-05の基本フローの終わりに当たります。13-2-3でユースケース記述を2本書いたときと同じ理由で、主となる使い手が違うものを並べると、送るものと返るものの違いが見えてきます。

## 🏃 実践

### 🧠 先輩エンジニアの思考プロセス

先輩エンジニアは、画面設計の成果物を次の順でAPIと権限に落とし込みます：

| Step | やること | 説明 |
|:-----|:---------|:-----|
| 1 | 画面遷移図を1画面ずつたどり、取りに行くものと送るものに印を付ける | エンドポイントは思いつきで数えない。画面が必要とするものが、そのまま入口になる |
| 2 | 印を付けたものを、扱うものごとにまとめてURLを決める | URLに動きを表す言葉は入れない。何をするかはメソッドで表す |
| 3 | メソッドを決めて、エンドポイント一覧に並べる | 取るならGET、増やすならPOST、書き換えるならPUT、消すならDELETE |
| 4 | 条件や分岐が絡むものから、詳細を書く | 全部は書かない。送るものと返るものは「なし」も含めて埋める |
| 5 | うまくいかなかったときを洗い出して、一覧にする | 自分が作るこのAPIが返すぶんだけ。原因の細かい分類は先の章 |
| 6 | 機能一覧を縦に置いて、ロールごとに ○×△ を埋める | 埋まらないマスが、決まっていない場所 |

### 📝 ステップバイステップで作る

#### Step 1: 画面をたどって、取りに行くものと送るものに印を付ける

13-3-4で描いた画面遷移図を開き、四角を1つずつたどります。それぞれの画面について、「この画面を映すために取りに行くものはあるか」「この画面から送るものはあるか」の2つを問います。

模範解答を土台にしている方なら、画面は7枚あります。全部の画面に印が付くわけではありません。カート画面のように、前の画面で選んだものを映すだけで、サーバー側へ取りに行かない画面もあります。印が1つも付かなかった画面が出てきたら、なぜ付かないのかを説明できるかを確かめてください。

#### Step 2: 扱うものごとにまとめて、URLを決める

印を付けたものを見比べると、大きく2種類に分かれるはずです。商品にまつわるものと、注文にまつわるものです。それぞれにURLを1つずつ決めます。

1件を指すときの `{ }` の中身も、ここで決めます。タスク管理APIでは `{id}` でしたが、カフェには、注文1件を指すために13-2-3のユースケース記述で決めた言葉があります。13-3-4の入力チェック表で桁数まで決めた、あの言葉です。

#### Step 3: メソッドを決めて、エンドポイント一覧に並べる

同じURLでも、メソッドが違えばすることが変わります。注文のURLは、登録・状況の確認・取り消し・一覧の取得・受け渡しの5つの場面で使うことになるはずです。店員が受け取り前の注文を一覧で見る場面（UC-05の基本フロー2）を数え落としやすいので、気をつけてください。

店員が注文を1件選んだあとに見る商品と個数は、この一覧が返すものに含めます。13-4-1の手順3のとおり、入口は増やしません。

「認証」の欄は、お客さま側と店員側で答えが変わります。お客さま側は、13-2-3で会員登録について立てた想定で決まります。店員側は、仕様書の「カウンターの中にタブレットを1台置いて」という記述から考えます。ここで決まらないと感じたら、想定を1つ置いて、確認事項リストへ送ってください。

#### Step 4: 指定された2本の詳細を書く

お客さまが使うもののうち注文を受け付けるもの1本と、店員が受け渡しを記録するもの1本です。

注文を受け付けるほうを書くと、必ず手が止まります。止まった理由をそのまま言葉にして、確認事項リストへ送ってください。なお、外の仕組みへ引き渡すときは、「どこへ送ればよいか」を返すことになります。呼び方や形は決まらなくてよいので、返すものの1つとして日本語で書いておきます。

店員が使うほうでは、13-2-3で書いたUC-05の基本フロー5と6が手がかりになります。店員が何を押し、その結果システムが何を記録するのかが、そのまま送るものと返るものになります。

#### Step 5: うまくいかなかったときを洗い出して、一覧にする

`起きること`・`ステータスコード`・`返すもの` の3列で作ります。手がかりは、13-2-3で書いた代替フローと、13-3-4で作ったメッセージ一覧です。UC-02の代替フローとUC-05の代替フローが、それぞれどのエンドポイントの話なのかを確かめてください。

画面に出す文言は13-3-4のメッセージ一覧で決めたものなので、ここで決め直しません。そこに書いた言い回しを、そのまま「返すもの」の欄に写します。

売り切れの商品を注文されたときにどうするかも、この表で決めます。13-3-4のメッセージ一覧に、その文言はすでにあるはずです。使う数字は、11-1-1と11-2-7で見たものの中から選んでください。

#### Step 6: 権限マトリクスを作り、保存する

13-2-3の機能一覧の5行を、そのまま権限マトリクスの行に写します。列は、機能一覧の「主な利用者」列から起こします。ログインしていない相手をどう扱うかは、13-4-2の手順1のとおりに考えてください。ここでも、会員登録について13-2-3で自分が立てた想定が効いてきます。お客さまがそもそもログインしない前提なら、列を別に立てるかどうかも、その想定から決まります。

マスを埋めていくと、13-2-3のユースケース図で線を引くかどうか迷った場所が、そのまま迷うマスとして出てきます。図に戻って確かめてください。

API設計書と権限マトリクスがそろったら、13-4-2の手順5のとおりに突き合わせます。×と書いたのに「認証：不要」のままになっている組み合わせが出てきても、それだけでは間違いではありません。それが何を意味するのかは、模範解答で確かめてください。

書き終えたら、`13-4/` フォルダに2つのファイルを保存します。

```text
13-4/
├── cafe-api.md                  # API設計書
└── cafe-permission-matrix.md    # 権限マトリクス
```

確認事項リストは `13-2/cafe-questions.md` に書き足すので、コミットには両方のフォルダを含めます。

```bash
# design-practice フォルダの中で実行する
git add 13-2 13-4
git commit -m "13-4: カフェのモバイルオーダーアプリのAPI設計書と権限マトリクスを追加"
git push origin main
```

## 📖 模範解答

> 💡 **模範解答について**: 設計に「唯一の正解」はありません。ここに示すのは一つの妥当な解です。自分の設計と見比べて、「違い」ではなく「その違いが問題を起こすか」を考えてみましょう。

<details>
<summary>📖 作り終えたら開く（模範解答）</summary>

**エンドポイント一覧（解答例）**

| ID | メソッド | エンドポイント | 何をするか | 認証 |
|:---|:---------|:---------------|:-----------|:-----|
| API-01 | GET | /api/products | その日の商品の一覧を取得する | 不要 |
| API-02 | POST | /api/orders | 注文を登録する | 不要 |
| API-03 | GET | /api/orders/{注文番号} | 注文1件の状況を取得する | 不要 |
| API-04 | DELETE | /api/orders/{注文番号} | 注文を取り消す | 不要 |
| API-05 | GET | /api/orders | 受け取り前の注文を、商品と個数とともに一覧で取得する | 必要 |
| API-06 | PUT | /api/orders/{注文番号} | 注文を受け渡し済みにする | 必要 |

6本のうち、SC-02 カート画面に対応するエンドポイントはありません。カートに入れた商品と個数は、支払いに進むまでは画面の中だけの話だからです。カートをデータとして残すかどうかは、Chapter 5のデータ設計で決めます。SC-03 支払いの画面は外の仕組みの中で進み、SC-04 注文完了画面はAPI-02が返した注文番号を映すだけなので、こちらも新しい入口は増えません。SC-07 注文詳細画面が見せる商品と個数も、API-05が一覧で返しているので、そこから選んだ1件を映すだけです。

**API-02の詳細（解答例）**

```markdown
#### API-02: 注文を登録する

- **メソッドとエンドポイント**: POST /api/orders
- **認証**: 不要
- **送るもの**: 本文で、注文する商品と個数の組（1組以上。個数は1つの商品あたり10個まで）
- **返すもの（うまくいったとき）**: 201。注文番号と、合計金額と、支払いの手続きに進むための行き先
- **返すもの（うまくいかなかったとき）**: 422（送ったものに不備があるとき、または選んだ商品が売り切れているとき）
```

「支払いの手続きに進むための行き先」は、外の決済の仕組みのどこへお客さまを送ればよいのかを表すURLのことです。実際にどんな形で返すのかは、つなぎ方が決まってから決めます。

**API-06の詳細（解答例）**

```markdown
#### API-06: 注文を受け渡し済みにする

- **メソッドとエンドポイント**: PUT /api/orders/{注文番号}
- **認証**: 必要
- **送るもの**: URLに注文番号。本文で、受け渡し済みにすること
- **返すもの（うまくいったとき）**: 200。書き換えたあとの注文1件（注文番号・商品と個数・合計金額・受け渡し済みであること）
- **返すもの（うまくいかなかったとき）**: 401（ログインしていないとき）／404（その注文番号の注文が無いとき）
```

送るものに使った「受け渡し済み」は、13-2-3で決まっている言葉です。「受け取り前」と合わせて2つありますが、この2つで足りるのか、どんな順で移り変わるのかは、Chapter 6で決めます。

**エラーレスポンス一覧（解答例）**

| 起きること | ステータスコード | 返すもの |
|:-----------|:-----------------|:---------|
| 送ったものに不備がある（注文の登録） | 422 | 不備のあった項目と、その理由の文言 |
| 売り切れの商品が注文された（注文の登録） | 422 | 「この商品は売り切れです」という文言 |
| 指定した注文番号の注文が見つからない（お客さまの状況の確認・取り消し） | 404 | 「ご入力の注文番号の注文が見つかりません」という文言 |
| 指定した注文番号の注文が見つからない（店員の受け渡し） | 404 | 「該当する注文がありません」という文言 |
| ログインしていない（店員が使うもの） | 401 | ログインが必要である旨の文言 |

2行目の「この商品は売り切れです」は、13-3-4のメッセージ一覧ではメニュー画面の文言として決めたものです。ただ、「カートに入れる」を押した時点ではサーバーへ問い合わせないので、この文言をサーバーが返す場面は注文の登録のときだけになります。決めた文言はそのままに、返す場所を注文の登録に移した形です。数字を422にしたのは、送られてきた形は正しくても、そのままでは注文として受けられない点を、送ったものの不備と同じ扱いにそろえたからです。11-1-1で見た400を選んでも、全エンドポイントでそろえてあれば誤りではありません。

3行目と4行目は、どちらも404です。それでも行を分けたのは、返す文言が違うからです。13-3-4のメッセージ一覧では、注文状況画面と注文一覧画面に別々の文言を決めていました。同じ数字でも、出す画面が違えば言い回しが変わります。4行目は注文一覧画面の文言ですが、番号で注文を探す問い合わせがサーバーへ届くのは受け渡しのときなので、売り切れの行と同じく、返す場所だけを移しています。一覧を開いてから「受け渡し済みにする」を押すまでの間に、お客さまがその注文を取り消していることがあるので、受け渡しの時点でも見つからない場合を決めておきます。

UC-02の代替フロー5a「支払いが完了しなかった場合」は、この表に入っていません。支払いの手続きは外の仕組みの中で進むので、うまくいかなかったことも、まず外の仕組みの側で起きるからです。

課題で断った、13-2-3のUC-02との食い違いも、ここで引き取ります。基本フローは5「お客さまが支払いの手続きを行う」、6「システムが注文を登録し、注文番号を表示する」の順でした。この設計では、支払いに進むための行き先を返す前に注文を登録するので、5と6が入れ替わります。そうなると、代替フロー5aの「注文を登録しない」も、そのままでは成り立ちません。支払いが済まないまま終わった注文を取り消し扱いにする、という想定をQ-10として送ったのは、このためです。返事が来たら、API設計書だけでなく、UC-02の記述も書き直す対象になります。

**権限マトリクス（解答例）**

| 機能 | お客さま | 店員 |
|:-----|:---------|:-----|
| F-01 メニューの閲覧 | ○ | × |
| F-02 商品の注文 | ○ | × |
| F-03 注文状況の確認 | △ | × |
| F-04 注文の取り消し | △ | × |
| F-05 注文の受け渡し | × | ○ |

△の条件

- F-03 注文状況の確認（お客さま）: 自分が出した注文だけ（注文番号を知っている方だけ）
- F-04 注文の取り消し（お客さま）: 自分が出した注文だけ（注文番号を知っている方だけ）

**判断が分かれるポイント**

模範と違っていても、セルフチェックの観点を満たしていれば合格です。そのうえで、迷いやすい6点を補足します。

**支払いを外の仕組みに任せ、そこまでを設計書に書いた理由**

13-4-1で学んだ線引きを、カフェに当てはめました。支払いが済んだことをどう受け取るかは、つなぎ方が決まらないと決められないので、Q-10として送りました。13-3-4でQ-07として送った支払いの入力欄の話も、この返事とセットで決まります。

**注文の取り消しをDELETEにした理由**

取り消しは「この注文を無かったことにしてください」という依頼なので、消すメソッドで表しました。ただし、このDELETEは依頼であって、記録として注文を残すかどうかは別の決めごとです。売上の集計に使うなら、取り消した注文も残すことになります。「消す」と書いたからデータが無くなる、と読まないでください。ここはChapter 5とChapter 6で決めます。

**お客さま側を「認証：不要」にした理由と、その穴**

13-2-3のQ-04で、「お客さまは会員登録をせずに注文でき、注文のあとに表示される注文番号で状況を確認する」という想定を立てました。会員登録が無いということは、そのお客さまが誰なのかをアプリは知らないということです。ログインの仕組みが無いので、お客さま側のエンドポイントは「不要」になります。

ここで穴が1つ生まれます。注文番号さえ知っていれば、誰でもその注文の状況を見られて、取り消せてしまうのです。注文番号は6桁の数字だと13-3-4で決めたので、順に試せば他人の注文に当たることもあります。だからこそ、権限マトリクスの△の条件を「自分が出した注文だけ」で終わらせず、「注文番号を知っている方だけ」と書き足しました。この2つは、実装するとまったく違うものになります。前者は本人かどうかを確かめる作りで、後者は確かめない作りです。

設計書に書いてあるのは後者です。それでよいかどうかは自分たちでは決められないので、Q-11として送りました。これが、この演習でいちばん設計らしい判断です。「決まっていないから書かない」でも「よさそうだから決めてしまう」でもなく、**想定を書いたうえで、その想定を確認に出す**という形になっています。

**店員側だけ「認証：必要」にした理由**

店員が使うのは、カウンターの中のタブレット1台です。誰でも注文の一覧を見られてよいはずがないので、認証は必要にしました。ただし、店員お一人ずつにログインしていただくのか、店内の1台として共通のアカウントでログインするのかは、仕様書に書かれていません。共通のアカウントという想定を置いたうえで、Q-12として送りました。13-2-3のQ-02（店長とアルバイトの区別）の返事しだいでは、お一人ずつのログインが必要になり、権限マトリクスの列も増えます。

**店員の列に×が4つ並ぶ理由**

13-2-3のユースケース図で、店員から線が伸びていたのはUC-05「注文を受け渡す」の1本だけでした。13-2-2で学んだとおり、図で線を引かないことは「使えない」という決定です。表の×も同じ意味を持つので、店員の列はF-05だけが○になります。

F-01「メニューの閲覧」を店員も○にしたくなった方は多いはずです。店員が商品の一覧を見てはいけない理由は、確かにありません。ただ、仕様書は店員がメニューを見ることに触れていませんし、13-2-3でも線を引きませんでした。ここで○にすると、表だけがユースケース図と食い違います。店員にもメニューを見せると決めるのなら、この表を直すだけでなく、13-2-3のユースケース図に線を1本足し、確認事項リストにも1行出します。設計書は、どれか1枚だけを動かさないのが決まりです。F-03「注文状況の確認」も同じで、店員が注文を一覧で見るのはF-05「注文の受け渡し」の中の操作なので、F-03の店員は×になります。

F-04「注文の取り消し」の×は、Q-01の返事で「店員も取り消せます」となれば○に変わり、店員が使うエンドポイントが1本増えます。なお、いつまで取り消せるのかという期限のほうは、Chapter 6で状態の移り変わりを設計するときに決めます。

**店員の×と、「認証：不要」の関係**

店員の×が4つ並んでいるのに、それに当たるAPI-01からAPI-04までの「認証」は「不要」です。誰が呼んできても止まらない入口だ、ということです。13-4-2の手順5で見たとおり、この×は「店員の業務としてはやらない」という決定で、仕組みとして止めるには呼んできた相手を確かめる必要があります。止めるかどうかは、お客さま側に本人確認を入れるかどうかと同じ話なので、Q-11の返事とセットで決まります。突き合わせて食い違いに気づいたら、そこまでを設計書に残しておけば十分です。

## 🚀 まとめ

- エンドポイントは、画面遷移図を1画面ずつたどって洗い出します。画面の数とエンドポイントの数は一致しません。
- 「認証」の欄は、仕様書のどこかに答えの手がかりがあります。カフェでは、会員登録についての想定と、店員がカウンターの中のタブレット1台を使うという記述が、そのまま答えを決めました。
- 権限マトリクスの×は、ユースケース図で線を引かなかったことと同じ決定です。Chapter 2で保留にした判断が、章をまたいでここに現れます。
- 2枚の設計書は、書き終えたら突き合わせます。「認証：不要」の入口では、×と書いただけでは止まらないので、そこは決め直すか、確認に出すかのどちらかになります。
- 決めきれない点は、Chapter 2・Chapter 3と同じように想定を添えて確認事項リストへ送ります。想定を書いたうえで確認に出しておけば、返事が来たときに、設計書のどの行を直すかがすぐ分かります。

これでChapter 4は終わりです。ここまでで、画面の裏側にどんな入口があり、誰がそれを使ってよいのかが決まりました。ただ、返すと決めた項目を、このアプリがどんな形で覚えておくのかは、まだ決めていません。次のChapter 5では、データを設計します。商品と注文と個数を、どんなまとまりで持ち、互いにどうつなぐのかを決めていきます。
