# 13-4-2: 認証・認可と権限設計

## 🎯 このセクションで学ぶこと

- そのシステムに何種類の利用者がいるのかを、仕様書から洗い出せるようになる。
- 誰がどの機能を使ってよいのかを、権限マトリクスに ○×△ で書き表せるようになる。
- 条件つきでできることに、その条件を添えて書き残せるようになる。

---

## 導入：「本人だけ」と書いた文章は、本人以外について何も言っていない

「投稿は本人だけが編集できます」という1文を渡されたとします。本人が編集できることは分かりますが、事務の担当者はどうなのか、管理者はどうなのかについては、何も書かれていません。読んだ人は、書かれていない部分を自分で埋めることになります。

埋めるのは、たいてい実装する人です。10-3で学んだとおり、`PostPolicy` に `$user->id === $post->user_id` と1行書けば、他人の投稿は編集できなくなります。この1行を書く前に「誰が編集してよいのか」がどこにも書かれていなければ、その場の判断で書かれます。あとから「事務の人も直せるはずでは」と言われれば、権限に触れている経路をすべて洗い直すことになります。

先に決めておくために作るのが、**権限マトリクス**です。行に機能、列にロール（利用者の役割）を並べ、そのマスに使ってよいかどうかを書いた表です。表という形にすると、🔑 **全部のマスを埋めるまで終われません**。

なお、ここで決めるのは10-3-1「認可とポリシーの基礎」で学んだ認可（あなたはそれをしてよいか）のほうです。認証（あなたは誰か）は済んでいる前提で進めます。どうやってログインしてもらうのかという方式は、この教材では決めません。

---

## 権限マトリクスの読み方

13-4-1と同じ、学習塾の出欠管理アプリです。13-4-1では機能一覧を作らずにエンドポイントを並べたので、13-2-1の付け方に従って、相談とエンドポイント一覧の両方から機能一覧を起こしました。

| ID | 機能 | 主な利用者 |
|:---|:-----|:-----------|
| F-01 | 授業一覧の閲覧 | 講師 |
| F-02 | 出欠の登録 | 講師 |
| F-03 | 出欠の訂正 | 講師 |
| F-04 | 出欠記録の閲覧 | 事務・保護者 |

F-03は、相談の文章には出てきません。13-4-1でAPI-04「登録した出欠を訂正する」という入口を並べたので、それに対応する行として起こしました。この一覧から起こした権限マトリクスが、次の表です。

| 機能 | 講師 | 事務 | 保護者 | ログインしていない相手 |
|:-----|:-----|:-----|:-------|:-----------------------|
| F-01 授業一覧の閲覧 | ○ | ○ | × | × |
| F-02 出欠の登録 | ○ | × | × | × |
| F-03 出欠の訂正 | ○ | △ | × | × |
| F-04 出欠記録の閲覧 | ○ | ○ | △ | × |

△の条件

- F-03 出欠の訂正（事務）: その日のうちに登録されたものだけ
- F-04 出欠記録の閲覧（保護者）: 自分のお子さんの記録だけ

まず、横に読みます。1行を左から右へたどると、その機能について誰ができて誰ができないのかが、一度に分かります。F-02の行なら、出欠を登録できるのは講師だけです。事務と保護者のマスに×が書いてあるので、「事務の人も代わりに登録できるのでは」という疑問は、この表を見た時点で消えます。

次に、縦に読みます。1列を上から下へたどると、そのロールが何をできるのかが分かります。保護者の列は×が3つと△が1つで、このアプリで保護者ができることは1つだけです。機能一覧の「主な利用者」列を見ただけでは、ここまでは分かりませんでした。

いちばん右の列は、上から下まで×が並んでいます。13-4-1のエンドポイント一覧で5本とも「認証：必要」と決めたことが、この列に現れています。

最後に、△の付いたマスを見ます。どちらの△にも、表のすぐ下に条件が書かれています。F-04の保護者のマスに○とだけ書いてあったら、実装する人は「保護者は出欠記録を見られる」と読むので、他の家庭のお子さんの記録まで見える作りになりえます。🔑 **△の条件が、そのまま実装するときの分かれ目**になります。

F-01の事務の○、F-03の事務の△、F-04の講師の○は、相談の文章には書かれていません。「事務は集計のために授業も見る」「登録した直後の打ち間違いは事務が直す」「講師は自分が付けた記録を見返す」という想定を置いて埋めたマスです。想定で埋めたときは、同じ内容を確認事項リストにも出します。表を埋める作業と、確認に出す作業はセットです。

### API設計書と2枚で1組

この表のF-04の行が、13-4-1で見たAPI-05「出欠の記録を取得する」に当たります。あのURLは、講師も事務も保護者も同じように呼びますが、返るものは相手によって変わります。事務には全員の記録、保護者にはご自分のお子さんの記録です。同じ入口でも人によって返るものが違う、という決定は、API設計書の「認証」の欄では表せません。

13-4-1のエラーレスポンス一覧に置いた403の行が、どんなときに返るのかも、これで決まります。保護者が他の家庭のお子さんの記録を取りに来たときと、事務が、その日のうちに登録されたものではない記録を訂正しようとしたときです。

## 権限マトリクスの書き方

**手順1: ロールを洗い出す**

機能一覧の「主な利用者」列を縦に見ます。そこに出てくる人が、そのままロールの候補です。学習塾なら、講師・事務・保護者の3つでした。

もう1つ、機能一覧には出てこないのに必ず数えるロールがあります。ログインしていない相手です。仕様書がその人たちに触れていなくても、システムはその人たちからも呼ばれます。13-2-2で、ログイン機能を足すとアクターが「訪問者」と「ログイン済み利用者」に分かれる、と確認したとおりです。この列は立てて、マスを全部埋めます。

ただし、仕様書に出てくる利用者が、そもそもログインしない前提のこともあります。その場合は、その人の列がログインしていない相手の列を兼ねるので、列を足しません。同じ人たちに2つの列を立てても、同じ記号が並ぶだけです。兼ねたときは、どちらの列が兼ねているのかを表の下に1行残します。読んだ人が、列の立て忘れと見分けられるようにするためです。

列にできるのは、ここまでの2種類です。🔑 **仕様書に出てくる人と、ログインしていない相手**。これ以外は増やしません。「常勤の講師と非常勤の講師では、できることが違うのでは」と思いついても、仕様書がその区別に触れていないなら、そこはまだ決まっていない場所です。13-2-1で学んだとおり、想定を添えて確認事項リストへ送ります。

仕様書に出てくる人の側に区別が無いなら、そちらの列は1つのままで構いません。13-2-2で、アクターが1人しかいない図はおかしな図ではない、と確認しました。ロールも同じです。

**手順2: 行に機能を並べる**

行には、機能一覧の機能名をIDごとそのまま写します（`F-01 授業一覧の閲覧` の形）。動詞に直しません。「授業一覧を見る」と書き換えると、それはユースケース名になってしまい、機能一覧と突き合わせるときに「同じものか」を確かめる手間が増えます。

行を機能、列をロールにするのは、機能がこの先も増えていくのに対して、ロールはめったに増えないからです。増える側を縦にしておくと、表が横に伸びずに済みます。

**手順3: マスを埋める**

使う記号は ○（できる）・×（できない）・△（条件つきでできる）の3つです。

🔑 **×は「この役割の人にはさせない」という決定**です。実際にその操作が止まる作りになっているかどうかは、この表では問いません。止める作りを入れるのは、10-3で学んだポリシーを書く仕事で、この表を書き終えたあとの話です。

空欄は作りません。「できない」は空欄ではなく × と書きます。13-2-2で、ユースケース図で線を引かないことが「使えない」という決定を表す、と学びました。×も同じで、書いた瞬間に決定になります。空欄は決定になりません。あとから見たときに、「できないと決めた」のか「まだ決めていない」のかを見分けられなくなります。

埋められないマスが出てきたら、そこが決まっていない場所です。無理に○か×を選ばず、想定を添えて確認事項リストへ送ります。

**手順4: △の行に条件を書く**

△は、マスの中だけでは意味が伝わりません。表のすぐ下に、どの機能の、どのロールについての条件なのかが分かる形で書きます。

- F-04 出欠記録の閲覧（保護者）: 自分のお子さんの記録だけ

条件の書かれていない△は、実装する人にとっては○と変わりません。△を書いたら、必ず下に1行足してください。

**手順5: API設計書の「認証」の欄と突き合わせる**

表が埋まったら、13-4-1で作ったAPI設計書を横に並べます。見るのは2か所です。

1か所目は、行を横に見て、どのロールも×になっている機能です。誰も使わないと決めた機能なのに、そのためのエンドポイントがAPI設計書に並んでいたら、どちらかが間違っています。マスの埋め方を間違えたか、要らない入口を開いたかのどちらかです。

2か所目は、「認証：不要」と書いたエンドポイントです。この入口は、ログインしていない相手からも呼び出せます。呼んできたのが誰なのかを、システムが知らないまま応じるということです。そのエンドポイントに当たる機能の行で、ログインしていない相手のマスに×を書いても、その×のとおりに止める手立てがありません。手順3で見たとおり、×は決定であって、作りがその決定に追いついているかどうかは別の話です。ここは食い違ったまま残ることがあります。作りを決定にそろえたいなら、そのエンドポイントの「認証」を「必要」にするところから決め直すことになります。そこまで決められないなら、想定を添えて確認事項リストへ送ります。

### 画面で隠すことと、してよいかどうかは別

10-3-4「ポリシーの適用」で学んだ `@can` を使うと、他人の投稿の編集ボタンを画面から消せます。それでも直接URLを打たれれば、止めるのはポリシーのほうです。権限マトリクスに書くのは、この「他人の投稿は編集させない」という決定です。

ボタンを出すかどうかは、Chapter 3で決めた画面の話です。表のマスに「ボタンを出さない」と書きたくなっても、書きません。ボタンを隠しただけでURLを直接打たれたときに止まらないなら、×という決定に作りが追いついていない状態だからです。

## 🏃 書いてみよう

学習塾の出欠管理アプリは「読む」練習でした。今度は、投稿アプリ（`post-app-practice`）で書きます。13-4-1と同じく、コードを読むだけなのでDockerは起動しなくて構いません。

### Step 1: ロールを洗い出す

13-2-1で作った機能一覧の「主な利用者」列に並んでいるのは、「訪問者」と「ログイン済み利用者」の2つです。この2つが、そのまま列になります。

ログインしている人の側に、それ以上の区別はありません。`users` テーブルにも `app/Models/User.php` にも、役割を表す列は1つもないからです。手順1のとおり、そちらの列は1つのままにします。

訪問者の列は、`routes/web.php` を開いて確かめます。投稿に関する4本が `Route::middleware('auth')->group()` の中にあるので、訪問者はこの4本のどれも呼び出せません。それでも列は立てて、マスを埋めます。

### Step 2: 行に機能を並べる

行には、13-2-1で作った機能一覧の機能名をIDごとそのまま写します。ただし、写すのは投稿に関する3行だけです。ユーザー登録・ログイン・ログアウトの3行は、権限マトリクスには載せません。導入で書いたとおり、ログインの方式をこの教材では決めないからです。

`routes/web.php` にはルートが4本ありますが、行は3つです。`posts.edit` と `posts.update` は、編集画面を出す操作と書き換える操作の2本ですが、機能一覧では「投稿の編集」の1行にまとまっています。

### Step 3: マスを埋める

ログイン済み利用者の列から埋めます。一覧を見ることについては、`app/Http/Controllers/PostController.php` の `index()` を見てください。編集と削除については、`app/Policies/PostPolicy.php` を開きます。

```php
// app/Policies/PostPolicy.php
public function update(User $user, Post $post): bool
{
    return $user->id === $post->user_id;
}

public function delete(User $user, Post $post): bool
{
    return $user->id === $post->user_id;
}
```

`$user->id` はいま操作している人の番号、`$post->user_id` はその投稿を書いた人の番号です。この2つが同じときだけ `true` が返ります。○か△かは、この `return` の行から決まります。

訪問者の列は、Step 1で確かめたとおりです。3つとも同じ記号になります。

### Step 4: API設計書と突き合わせる

13-4-1で書いた `docs/13-4/post-api.md` を横に並べて、手順5の2か所を見ます。13-4-1で書いたのは「APIとして作り直すなら」という想定の設計書ですが、決めている中身は同じアプリのものなので、そのまま突き合わせられます。

見るところを1つ足します。13-4-1のエラーレスポンス一覧に書いた403の行と、この表の△の条件が、同じことを言っているかどうかです。片方だけを直すと、2枚が食い違います。

### Step 5: 保存する

13-4-1で作った `docs/13-4/` フォルダに、`post-permission-matrix.md` の名前で保存します。

```bash
# アプリのフォルダの中で実行する
git add docs/13-4
git commit -m "13-4: 投稿アプリの権限マトリクスを追加"
git push
```

IDと機能名は、13-2-1で自分が振ったものに合わせてください。

F-04がログイン済み利用者で○なのは、`PostController` の `index()` に `$this->authorize()` が無いからです。ログインしていれば、誰が書いた投稿でも一覧で読めます。F-05とF-06が△なのは、`PostPolicy` の `update()` と `delete()` が、投稿を書いた本人かどうかを見ているからです。13-2-1の機能一覧では、この2行の「主な利用者」に「（自分の投稿のみ）」と書き添えていました。そこに書いた制約が、ここで△という記号になります。

訪問者の列が3つとも×なのは、4本のルートが `auth` のグループの中にあるためです。

次の観点で、自分の成果物と見比べてください。

- [ ] 列が2つで、ログインしていない人の列がある
- [ ] 行が3つで、機能名が名詞の形になっている（「投稿を編集する」になっていない）
- [ ] ユーザー登録・ログイン・ログアウトの行を作っていない
- [ ] すべてのマスが埋まっている（空欄が1つもない）
- [ ] 編集と削除のマスが △ になっている
- [ ] △の条件が、表のすぐ下に書かれている
- [ ] 「編集ボタンを隠す」が、表の中に書かれていない

設計に唯一の正解はありません。ロールの呼び方や行の並び順が解答例と違っていても、上の観点を満たしていれば合格です。そのうえで、判断が分かれやすい点を補足します。

- **ログインしている人を1つのロールにまとめた理由**: Step 1で確かめたとおり、このアプリには役割の区別が無いためです。役割で分かれる例は、10-2-4「ミドルウェア - ハンズオン演習」の管理者専用ページが当たります。あちらは `is_admin` という列で管理者かどうかを見分け、管理者以外は403で止める作りでした。
- **編集と削除を△にした理由**: ログインしていれば誰でも編集できるわけではなく、自分の投稿だけだからです。`PostPolicy::update()` が返している `$user->id === $post->user_id` という1行が、条件そのものです。ここを○にすると、他人の投稿も編集できる設計になります。
- **`edit` と `update` を1行にまとめた理由**: 権限の上では、どちらも「その投稿を編集してよいか」という同じ判断だからです。コードのほうでも、`PostController` は `edit()` と `update()` の両方で `$this->authorize('update', $post)` を呼んでいます。2行に分けると、同じ決定が2か所に書かれて、片方を直し忘れます。

**突き合わせの結果**

13-4-1のAPI設計書は、4本とも「認証：必要」でした。この表の訪問者の列は3つとも×なので、2枚の言っていることは一致しています。「認証：不要」の行が1つもないので、手順5の2か所目に当たる食い違いは起きません。

403の行と△の条件も、同じことを言っています。API設計書には「自分が書いた投稿ではない（取得・書き換え・削除）」、この表には「自分が書いた投稿だけ」。片方を「事務の人も直せる」に変えたら、もう片方も直す対象になります。

## 💡 よくある間違いと現場での使われ方

いちばん多い間違いは、行を画面の名前で並べることです。「投稿一覧画面」「投稿編集画面」を行にすると、1つの機能が複数の画面に散らばったときに、同じ権限を2か所に書くことになり、片方を直し忘れます。行は機能一覧から写します。

現場では、この表は依頼者との確認にそのまま使えます。「事務の方は、講師が付けた出欠を直せるようにしますか」と、1マスずつ指さして聞けるからです。文章で説明するより速く、聞き漏らしもありません。実装が終わったあとは、Chapter 8で学ぶ「何を確かめれば正しいと言えるか」の元にもなります。×と書いたマスは、そのとおり止まることを確かめる対象になります。

## ✨ まとめ

- 権限マトリクスは、行に機能、列にロールを並べ、誰が何をしてよいかを1枚で表す設計書です。API設計書の「認証」の欄が答えていない部分を引き受けるので、書き終えたらその欄と突き合わせます。「不要」と書いた入口は誰からでも呼び出せるので、表に×と書いただけでは止まりません。
- ロールは、機能一覧の「主な利用者」列と、ログインしていない相手から洗い出します。この2種類のほかは足さず、思いついた区別は確認事項リストへ送ります。ロールが1つしかないアプリもあります。
- 行には、機能一覧の機能名をIDごとそのまま写します。機能は増え、ロールはめったに増えないので、増える側を縦にします。
- マスは ○・×・△ の3つで埋め、空欄を作りません。×は「この役割の人にはさせない」という決定で、空欄は決定になりません。△には、表のすぐ下に条件を書きます。
- 権限マトリクスは「してよいかどうか」の表です。ボタンを出すかどうかは画面設計の話なので、この表には書きません。
