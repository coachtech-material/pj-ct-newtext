# 13-4-2: 認証・認可と権限設計

## 🎯 このセクションで学ぶこと

- そのシステムに何種類の利用者がいるのかを、仕様書から洗い出せるようになる。
- 誰がどの機能を使ってよいのかを、権限マトリクスに ○×△ で書き表せるようになる。
- 条件つきでできることに、その条件を添えて書き残せるようになる。

---

## 導入：ログインさせただけでは、まだ何も決まっていない

13-4-1で作ったAPI設計書の「認証」の欄には、「必要」か「不要」だけを書きました。ログインしていない相手には入口を開かない、というところまでは決まっています。ただ、ログインしたその人が何をしてよいのかは、まだどこにも書かれていません。

学習塾の出欠管理アプリのAPI-05「出欠の記録を取得する」を思い出してください。このURLは、講師も事務も保護者も同じように呼びます。全員に同じ記録を返してよいのでしょうか。それとも、人によって返すものを変えるのでしょうか。API設計書の「認証」の欄は、この問いに答えていません。

10-3-1「認可とポリシーの基礎」で学んだとおり、認証は「あなたは誰か」を確かめる仕組みで、認可は「あなたはそれをしてよいか」を判断する仕組みです。ここで決めるのは後者で、認証は済んでいる前提で進めます。どうやってログインしてもらうのかという方式は、この教材では決めません。

10-3で学んだのは、決まっている権限をどう実装するかでした。`PostPolicy` に `$user->id === $post->user_id` と書けば、他人の投稿は編集できなくなります。困るのは、この1行を書く前に「誰が編集してよいのか」がどこにも書かれていない場合です。実装する人はその場で判断して書きます。あとから「事務の人も直せるはずでは」と言われれば、権限に触れている経路をすべて洗い直すことになります。13-1-1で見たとおり、誰が何をしてよいかという決めごとは1か所には収まらないので、直す範囲が広がります。

これを先に決めておくために作るのが、**権限マトリクス**です。行に機能、列にロール（利用者の役割）を並べ、そのマスに使ってよいかどうかを書いた表です。

表という形にする理由は、はっきりしています。「投稿は本人だけが編集できます」という文章は、本人以外のロールについて何も言っていません。読んだ人は、書かれていない部分を自分で埋めることになります。表なら、🔑 **全部のマスを埋めるまで終われません**。

## 権限マトリクスの読み方

13-4-1と同じ、学習塾の出欠管理アプリです。13-4-1では機能一覧を作らずにエンドポイントを並べたので、13-2-1の付け方に従って、相談とエンドポイント一覧の両方から機能一覧を起こしました。次の4つになります。

| ID | 機能 | 主な利用者 |
|:---|:-----|:-----------|
| F-01 | 授業一覧の閲覧 | 講師 |
| F-02 | 出欠の登録 | 講師 |
| F-03 | 出欠の訂正 | 講師 |
| F-04 | 出欠記録の閲覧 | 事務・保護者 |

このうちF-03は、相談の文章には出てきません。13-4-1でAPI-04「登録した出欠を訂正する」という入口を並べたので、それに対応する行として起こしました。

この一覧から起こした権限マトリクスが、次の表です。

| 機能 | 講師 | 事務 | 保護者 |
|:-----|:-----|:-----|:-------|
| F-01 授業一覧の閲覧 | ○ | ○ | × |
| F-02 出欠の登録 | ○ | × | × |
| F-03 出欠の訂正 | ○ | △ | × |
| F-04 出欠記録の閲覧 | ○ | ○ | △ |

△の条件

- F-03 出欠の訂正（事務）: その日のうちに登録されたものだけ
- F-04 出欠記録の閲覧（保護者）: 自分のお子さんの記録だけ

落とした列

- ログインしていない相手: まず立てて埋めたところ、5本とも「認証：必要」でマスが全部×になり、その決定はAPI設計書の「認証」の欄が持っているので落とした

F-01の事務の○、F-03の事務の△、F-04の講師の○は、相談の文章には書かれていません。「事務は集計のために授業も見る」「登録した直後の打ち間違いは事務が直す」「講師は自分が付けた記録を見返す」という想定を置いて埋めたマスです。想定で埋めたときは、同じ内容を確認事項リストにも出します。表を埋める作業と、確認に出す作業はセットです。

まず、横に読みます。1行を左から右へたどると、その機能について誰ができて誰ができないのかが、一度に分かります。F-02の行なら、出欠を登録できるのは講師だけです。事務と保護者のマスに×が書いてあるので、「事務の人も代わりに登録できるのでは」という疑問は、この表を見た時点で消えます。

次に、縦に読みます。1列を上から下へたどると、そのロールが何をできるのかが分かります。保護者の列は×が3つと△が1つで、このアプリで保護者ができることは1つしかありません。機能一覧の「主な利用者」列を見ただけでは、ここまでは分かりませんでした。

最後に、△の付いたマスを見ます。どちらの△にも、表のすぐ下に条件が書かれています。もしF-04の保護者のマスに○とだけ書いてあったら、どうなるでしょうか。実装する人は「保護者は出欠記録を見られる」と読むので、他の家庭のお子さんの記録まで見える作りになりえます。🔑 **△の条件が、そのまま実装するときの分かれ目**になります。

この表のF-04の行が、13-4-1で見たAPI-05「出欠の記録を取得する」に当たります。あの表では「誰が使えるかは決まらない」と書いて先送りにしていました。同じURLを呼んでも人によって返るものが違う、という決定が、ここでようやく形になりました。13-4-1のエラーレスポンス一覧に置いた403の行が、どんなときに返るのかも、これで決まります。保護者が他の家庭のお子さんの記録を取りに来たときと、事務が、その日のうちに登録されたものではない記録を訂正しようとしたときです。API設計書の「認証」の欄と権限マトリクスは、2枚で1組の設計書です。

## 権限マトリクスの書き方

手順は5つです。

**手順1: ロールを洗い出す**

機能一覧の「主な利用者」列を縦に見ます。そこに出てくる人が、そのままロールの候補です。学習塾なら、講師・事務・保護者の3つでした。

もう1つ、機能一覧には出てこないのに必ず数えるロールがあります。ログインしていない相手です。仕様書がその人たちに触れていなくても、システムはその人たちからも呼ばれます。13-2-2で、ログイン機能を足すとアクターが「訪問者」と「ログイン済みユーザー」に分かれる、と確認したとおりです。

この列は、まず立てて、全部のマスを埋めます。そのうえで、埋めた結果が全部×で、しかも同じ決定をほかの設計書が持っているときだけ、列を落とせます。落とすなら、落とした理由を表の下に1行残します。学習塾の出欠管理アプリがこの形です。13-4-1で見たとおり5本とも「認証：必要」なので、マスは全部×になり、その決定はAPI設計書の「認証」の欄が持っています。

API設計書を作らないアプリでは、落とせません。ログインしていない相手について決めた内容を持てる設計書が、権限マトリクスのほかに無いからです。

ただし、仕様書に出てくる利用者が、そもそもログインしない前提のこともあります。その場合は、その人の列がログインしていない相手の列を兼ねるので、列を足しません。同じ人たちに2つの列を立てても、同じ記号が並ぶだけです。

列にできるのは、ここまでの2種類です。🔑 **仕様書に出てくる人と、ログインしていない相手**。これ以外は増やしません。「常勤の講師と非常勤の講師では、できることが違うのでは」と思いついても、仕様書がその区別に触れていないなら、そこはまだ決まっていない場所です。13-2-1で学んだとおり、想定を添えて確認事項リストへ送ります。

仕様書に出てくる人の側に区別が無いなら、そちらの列は1つのままで構いません（ログインしていない相手の列は、これとは別に立てます）。13-2-2で、アクターが1人しかいない図はおかしな図ではない、と確認しました。ロールも同じです。

**手順2: 行に機能を並べる**

行には、機能一覧の機能名をIDごとそのまま写します（`F-01 授業一覧の閲覧` の形）。動詞に直しません。「授業一覧を見る」と書き換えると、それはユースケース名になってしまい、機能一覧と突き合わせるときに「同じものか」を確かめる手間が増えます。

機能一覧を作っていないアプリを題材にするときは、13-2-1の付け方に従って、名詞の形で機能名を起こします。

行を機能、列をロールにするのは、機能がこの先も増えていくのに対して、ロールはめったに増えないからです。増える側を縦にしておくと、表が横に伸びずに済みます。

**手順3: マスを埋める**

使う記号は3つだけです。

| 記号 | 意味 |
|:-----|:-----|
| ○ | できる |
| × | できない |
| △ | 条件つきでできる |

🔑 **×は「この役割の人にはさせない」という決定**です。実際にその操作が止まる作りになっているかどうかは、この表では問いません。止める作りを入れるのは、10-3で学んだポリシーを書く仕事で、この表を書き終えたあとの話です。

空欄は作りません。「できない」は空欄ではなく × と書きます。13-2-2で、ユースケース図で線を引かないことが「使えない」という決定を表す、と学びました。×も同じで、書いた瞬間に決定になります。空欄は決定になりません。あとから見たときに、「できないと決めた」のか「まだ決めていない」のかを見分けられなくなります。

埋められないマスが出てきたら、そこが決まっていない場所です。無理に○か×を選ばず、想定を添えて確認事項リストへ送ります。

**手順4: △の行に条件を書く**

△は、マスの中だけでは意味が伝わりません。表のすぐ下に、どの機能の、どのロールについての条件なのかが分かる形で書きます。

- F-04 出欠記録の閲覧（保護者）: 自分のお子さんの記録だけ

条件の書かれていない△は、実装する人にとっては○と変わりません。△を書いたら、必ず下に1行足してください。

**手順5: API設計書の「認証」の欄と突き合わせる**

表が埋まったら、13-4-1で作ったAPI設計書を横に並べます。見るのは2か所です。

1か所目は、行を横に見て、どのロールも×になっている機能です。誰も使わないと決めた機能なのに、そのためのエンドポイントがAPI設計書に並んでいたら、どちらかが間違っています。マスの埋め方を間違えたか、要らない入口を開いたかのどちらかです。

2か所目は、「認証：不要」と書いたエンドポイントです。この入口は、ログインしていない相手からも呼び出せます。呼んできたのが誰なのかを、システムが知らないまま応じるということです。そのエンドポイントに当たる機能の行に×を書いても、その×のとおりに止める手立てがありません。手順3で見たとおり、×は決定であって、作りがその決定に追いついているかどうかは別の話です。ここは食い違ったまま残ることがあります。作りを決定にそろえたいなら、そのエンドポイントの「認証」を「必要」にするところから決め直すことになります。そこまで決められないなら、想定を添えて確認事項リストへ送ります。

### 画面で隠すことと、してよいかどうかは別

10-3-5「認可機能 - ハンズオン演習」では、`@can` を使って他人の投稿の編集ボタンを隠しました。それでも直接URLを打つと403になることまで、完成チェックリストで確かめています。権限マトリクスに書くのは、この「他人の投稿は編集させない」という決定のほうです。

ボタンを出すかどうかは、Chapter 3で決めた画面の話です。表のマスに「ボタンを出さない」と書きたくなっても、書きません。ボタンを隠しただけで、URLを直接打たれたときに止まらないなら、×という決定に作りが追いついていない状態だからです。

## 🏃 書いてみよう

> 🔥 この演習では、設計書をAIに作らせずに、自分の手で書きましょう。記法や考え方についてAIに質問するのは構いませんが、成果物を生成させるのはTutorial 14までお預けです。まず自分の手と頭で書けるようになった人だけが、AIの作った設計を正しく評価できるようになります。

今度は、自分が作ったアプリで権限マトリクスを書きます。題材は、10-3-5「認可機能 - ハンズオン演習」で作った投稿管理の機能（`authorization-app-practice`）です。

要件は次の4行でした。

```text
- 自分の投稿のみ編集できる
- 自分の投稿のみ削除できる
- 他人の投稿には編集・削除ボタンが表示されない
- 他人の投稿を直接URL指定で編集・削除しようとすると403エラーになる
```

### Step 1: ロールを洗い出す

このアプリでは機能一覧を作っていないので、スターターキットの表と要件から起こします。スターターキットのシーダーは「2ユーザー（usera, userb）・各2投稿（計4投稿）」でした。管理者と一般の利用者のような役割の区別は、どこにもありません。

では、ロールは1種類でしょうか。ここで、ログインしていない人がこのアプリをどう見るのかを考えてください。要件の4行はどれもログインしている人の話ですが、ログインしていない人がこのアプリを開けないとは、どこにも書かれていません。

### Step 2: 行に機能を並べる

要件の4行から、名詞の形で機能名を起こします。このとき、要件の3行目と4行目は、1行目・2行目と同じ機能について「どう見せるか」「止まるか」を言っているだけなので、新しい行にはなりません。要件から起きるのは2つです。

これに加えて、一覧を見ることも行に入れてください。要件には書かれていませんが、スターターキットの `PostController` に `index` があり、`posts/index` のBladeもあります。作った機能である以上、誰が使ってよいのかを決める必要があります。これで行は3つになります。

### Step 3: マスを埋める

ログインしている人の列から埋めます。編集と削除は、自分が書いた `PostPolicy` を見れば決まります。`update()` と `delete()` に書いた1行が、そのまま○か△かを決めます。一覧は、`PostController` の `index` に `$this->authorize()` を足していません。ログインしていれば誰でも開けるので、○です。

ログインしていない人の列は、教材の本文だけでは決められません。ルートの定義がスターターキット側にあり、10-3-5の本文には載っていないからです。自分のリポジトリ（`~/laravel-practice/10-3-5_hands-on/authorization-app-practice/`）をVS Codeで開き、`routes/web.php` を見てください。パソコンに残っていない方は、10-3-5でpushした `authorization-app-practice` リポジトリをGitHubのページで開けば、同じファイルを読めます。ここもコードを読むだけなので、Dockerは起動しなくて構いません。

探すのは、10-1-5「認証済みユーザーの取得とミドルウェア」で見た `auth` です。`posts` と書かれた行に `->middleware('auth')` が付いているか、`Route::middleware('auth')->group(function () {` で囲まれたまとまりの中に入っていれば、ログインしていない人はその画面を開けません。どちらも見当たらなければ、誰でも開けます。これで、この列の1行目が決まります。

同じ列の残りの2行は、`routes/web.php` を見なくても決まります。`PostPolicy` の `update()` と `delete()` が見ているのは、その投稿を作った人かどうかです。ログインしていない人は投稿を1つも持っていないので、どの投稿にも当てはまりません。編集と削除は×です。これで6つのマスが全部埋まります。

手順5の突き合わせは、ここでは行いません。このアプリはブラウザで開く画面だけで、API設計書を作っていないからです。突き合わせは、13-4-3の演習で、自分が書いた2枚の設計書どうしで行います。

### Step 4: design-practiceに保存する

13-4-1で作った `13-4/` フォルダに、`authz-permission-matrix.md` の名前で保存します。接頭辞の `authz-` は、認可のハンズオンで作ったアプリという意味です。

```bash
# design-practice フォルダの中で実行する
git add 13-4
git commit -m "13-4: 投稿管理と認可の権限マトリクスを追加"
git push origin main
```

## 💡 よくある間違いと現場での使われ方

**間違い1: ロールを思いつきで増やす**

「管理者もいるはずだ」と考えて列を足してしまう間違いです。列を1つ足すと、行の数だけマスが増えます。仕様書に答えが無いのですから、増えたマスは埋められません。決まったことは1つも増えないまま、埋まらないマスだけが並びます。手順1で見たログインしていない相手は別で、ログインしなくても使える機能があるなら、書かれていなくても列を置きます。

**間違い2: 行を画面の名前で並べる**

「投稿一覧画面」「投稿編集画面」を行にしてしまう間違いです。1つの機能が複数の画面に散らばると、同じ権限を2か所に書くことになり、片方を直し忘れます。行は機能一覧から写します。

**間違い3: 迷ったマスを、とりあえず○で埋める**

○は「してよい」という決定です。迷ったまま○を書くと、決めていないことが決まったこととして設計書に残ります。

現場では、この表は依頼者との確認にそのまま使えます。「事務の方は、講師が付けた出欠を直せるようにしますか」と、1マスずつ指さして聞けるからです。文章で説明するより速く、聞き漏らしもありません。実装が終わったあとは、Chapter 8で学ぶ「何を確かめれば正しいと言えるか」の元にもなります。×と書いたマスは、そのとおり止まることを確かめる対象になります。

## ✨ まとめ

- 権限マトリクスは、行に機能、列にロールを並べ、誰が何をしてよいかを1枚で表す設計書です。API設計書の「認証」の欄が答えていない部分を引き受けるので、書き終えたらその欄と突き合わせます。「不要」と書いた入口は誰からでも呼び出せるので、表に×と書いただけでは止まりません。
- ロールは、機能一覧の「主な利用者」列と、ログインしていない相手から洗い出します。この2種類のほかは足さず、思いついた区別は確認事項リストへ送ります。ロールが1つしかないアプリもあります。
- 行には、機能一覧の機能名をIDごとそのまま写します。機能は増え、ロールはめったに増えないので、増える側を縦にします。
- マスは ○・×・△ の3つで埋め、空欄を作りません。×は「この役割の人にはさせない」という決定で、空欄は決定になりません。△には、表のすぐ下に条件を書きます。埋められないマスは、確認事項リストへ送ります。
- 権限マトリクスは「してよいかどうか」の表です。ボタンを出すかどうかは画面設計の話なので、この表には書きません。

次のセクション（13-4-3）は、Chapter 4の設計演習です。カフェのモバイルオーダーアプリの続きとして、API設計書と権限マトリクスを白紙から作ります。Chapter 3で決めた画面が、そのまま入口の洗い出しの出発点になります。
