# 13-5-5: データ設計 - 設計演習

## 📌 この演習について

カフェのモバイルオーダーアプリの続きです。Chapter 4までで、どんな画面があり、その裏側にどんな入口があり、誰がそれを使ってよいのかが決まりました。ここで決めるのは、やり取りする中身そのものを、どんなまとまりで、どんな形で残しておくのかです。白紙から、データ設計の設計書一式を作ります。

Chapter 4までの成果物が手元にない方は、`answers/13-4/` の中身を `docs/13-4/` にコピーしてから始めてください。

## 🎯 演習課題

### 📋 与えられる仕様

新しい仕様は渡されません。使うのは次の4つです。

1. 13-2-3で受け取ったカフェのモバイルオーダーアプリの仕様書。
2. 13-2-3で作った機能一覧・確認事項リスト・ユースケース図・ユースケース記述。
3. 13-3-5で作った画面一覧・画面項目定義・入力チェック表。
4. 13-4-3で作ったAPI設計書・権限マトリクス。

手元に無い方は、それぞれの模範解答を土台にして構いません。ただし、自分の解答と模範解答のどちらを土台にするかを最初に決めて、最後までそちらで通してください。途中で混ぜると、機能とテーブルの数が合わなくなります。

何を覚えておくかを決めるときに何度も戻ることになる箇所だけ、仕様書から引いておきます。

> お客さまには、まずその日のドリンクとフードの一覧を見ていただきたいです。商品の名前と値段と、短い説明が並んでいれば十分です。飲みたいものが決まったら、商品と個数を選んで、そのままアプリの中で支払いまで済ませられるようにしてください。

13-2-3から13-4-3までで書き出した確認事項は、**未確認のまま**です。返事を待たずに、そこに書いた自分の想定の上で設計を進めてください。新しく決めきれない点が出てきたら、自分のリストの最後の番号の続きから書き足します。新しいファイルは作らず、13-2-3で作った確認事項リストに行を足してください。

このあとに出てくる桁数や個数などの数値は、13-2-3から13-4-3の模範解答のものです。自分の解答で進める方は、自分の入力チェック表や機能一覧に書いた値へ読み替えてください。

注文の状態については、13-2-3で「受け取り前」「受け渡し済み」の2つが決まっています。テーブル定義書の「説明」の欄でこの2つに触れて構いませんが、**取りうる値の一覧はここでは作らないでください**。状態がいくつあって、どんな順で移り変わるのかは、Chapter 6で決めます。型も、13-5-3の手順4のとおり、値が出そろっていないうちは `VARCHAR` にしておきます。

## 🏃 実践

### 🧠 先輩エンジニアの思考プロセス

先輩エンジニアは、ここまでの設計書を次の順でデータに落とし込みます。

| Step | やること | 説明 |
|:-----|:---------|:-----|
| 1 | 仕様書とユースケース記述から名詞を拾い、3つのふるいにかける | エンティティは思いつきで数えない。覚えておく必要があるものだけを残す |
| 2 | 残ったものを、エンティティと属性に仕分けて一覧にする | 1つのエンティティにくっついてしか意味を持たないものは属性 |
| 3 | エンティティどうしの関係を、1対多・多対多の言葉で一覧にする | 図を描く前に、言葉で決めておく |
| 4 | ER図を描いて、3つの問いで点検する | 点検で落ちたら、エンティティの分け方に戻る |
| 5 | 英語のテーブル名とカラム名を決めて、型・制約・説明を表にする | ここからが詳細設計側。決めた名前と日本語の対応を残す |
| 6 | 機能一覧を縦に置いて、CRUD表を埋め、空を探す | データ側だけで作った設計を、機能と突き合わせるのは最後 |

### 📝 ステップバイステップで作る

#### Step 1: 名詞を拾って、3つのふるいにかける

13-2-3の仕様書と、そこで書いたユースケース記述を上から読み、名詞に印を付けます。商品、名前、値段、短い説明、ドリンク、フード、個数、カート、合計金額、注文、注文番号といったところです。仕様書に出てこない言葉でも、残しておきたいものに気づいたら足して構いません。いつ注文を受けたのかが、その一例です。注文状況の確認にも、どの順で作って渡すかにも効いてきます。

拾ったものを、1つずつふるいにかけます。ここでいちばん迷うのがカートです。カートにためる話は13-2-3の確認事項に書きましたが、残すかどうかの手がかりは、会員登録について書いた行のほうにあります。会員登録をしない想定のとき、そのカートが誰のものかをアプリは言えません。そこを確かめてから、3つ目のふるいをかけてください。

売り切れについても、ここで行き先を決めます。13-3-5の画面項目定義で「売り切れ」と出すことは決めましたが、それを覚えておくのかどうかは決めていません。商品の属性として持つのか、別に覚えておくものにするのかまでが、このStep 1の範囲です。どんな型で持つかはStep 5で決めます。仕様書に在庫を数える話が出てこないことが手がかりになります。

#### Step 2: エンティティと属性に仕分けて、一覧にする

`エンティティ`・`何を覚えておくものか`・`主な属性` の3列で表を作ります。名前は日本語の単数形で、仕様書の言葉をそのまま使います。

1回の注文の中に商品が複数入ることを、どう表すかがここでの山場です。13-2-3で「1回の注文で複数の商品をまとめて選べる」という想定を立てました。注文1件の中に、商品と個数の組がいくつも入るということです。これを注文の属性として持とうとすると、1つのマスに複数の値を入れることになります。13-5-2の1つ目の問いに引っかかるので、別のエンティティとして立てます。

エンティティにしないと決めたものは、表の下に理由を書き添えてください。Step 1で3つ目のふるいにかけたものが、ここに来ます。

#### Step 3: 関係の一覧を作る

`エンティティA`・`関係`・`エンティティB`・`読み方` の4列です。エンティティを2つずつ組にして総当たりで問い、つながっている組だけ行にします。

「読み方」の欄は、13-5-1の手順3のとおりに書きます。0件があり得るかどうかで書き分けるところが、この表の中に1行あります。

#### Step 4: ER図を描いて、点検する

draw.ioで、四角と線で描きます。四角の中に書くのはテーブル名だけです。英語のテーブル名は、この時点で決めてしまって構いません。線の両端の記号は、Step 3で書き分けた「0件があり得るか」に合わせて選びます。

描けたら、13-5-2の3つの問いをかけます。3つ目の問いでは、商品が持っている項目を、ほかのテーブルにも持たせていないかを確かめます。ただし、この設計にはあえて重複を持たせるところが出てきます。持たせると決めたら、その理由を書き添えてください。

#### Step 5: テーブル定義書を作る

テーブルの数だけ表を作ります。見出しに英語名と日本語名を併記し、`id` の行から書き始めます。

13-3-5の入力チェック表では、注文番号は6桁の半角数字、1商品あたりの個数は10個までと決めました。この2つのうち、片方はテーブル定義書に書けて、もう片方は書けません。書けないほうは、どの設計書が持っているのかを1行添えてください。

まだ決まっていないことに行き当たったら、「説明」の欄に決める場所を書くか、確認事項リストへ送ります。空欄にはしません。

#### Step 6: CRUD表を作って、空を探す

13-2-3の機能一覧の行を、そのまま行に写します。列は、Step 2で作ったエンティティ一覧の日本語名です。

埋め終えたら、13-5-4の手順4のとおりに縦へ読みます。ここが、**この演習でいちばん大事なところ**です。Cが1つも無い列が見つかったら、そのデータを誰が入れるのかを考えてください。

書き終えたら、`docs/13-5/` に5つのファイルを保存します。

```text
docs/13-5/
├── cafe-concept.md  # 概念モデル
├── cafe-er.drawio   # ER図（編集用）
├── cafe-er.png      # ER図（表示用）
├── cafe-table.md    # テーブル定義書
└── cafe-crud.md     # CRUD表
```

13-5-1から13-5-4で保存した `post-` のファイルは、同じフォルダにそのまま置いておきます（上のツリーでは省きました）。

確認事項リストは `docs/13-2/cafe-questions.md` に書き足すので、コミットには両方のフォルダを含めます。

```bash

git commit -m "13-5: カフェのモバイルオーダーアプリのデータ設計を追加"
```

| 商品 | その日に出すドリンクとフード | 名前・値段・短い説明・区分（ドリンクかフードか）・その日売れるかどうか |
| 注文 | お客さまが1回で出した注文 | 注文番号・合計金額・受け取りの状態・注文を受けた日時 |
| 注文明細 | 1回の注文の中の、商品1種類ぶん | 個数・注文したときの値段 |

エンティティにしなかったもの

- カート: 支払いに進むまでの間、画面の中だけで持つものとしました。会員登録をしない想定なので誰のカートかを区別できず、次に開いたときに残っていてほしいものでもないからです

**関係の一覧（解答例）**

| エンティティA | 関係 | エンティティB | 読み方 |
|:--------------|:-----|:--------------|:-------|
| 注文 | 1対多 | 注文明細 | 1件の注文は、1つ以上の注文明細を持つ |
| 商品 | 1対多 | 注文明細 | 1つの商品は、複数の注文明細に現れることがある |

1行目は「1つ以上」、2行目は「複数」と書き分けています。明細が0件の注文はありませんが、まだ一度も注文されていない商品はあり得るからです。

**テーブル定義書（解答例）**

**products（商品）**

| カラム名 | データ型 | 制約 | 説明 |
|:---------|:---------|:-----|:-----|
| id | BIGINT | PRIMARY KEY, AUTO_INCREMENT | 商品を1件ずつ区別する番号 |
| name | VARCHAR(50) | NOT NULL | 商品の名前 |
| price | INT | NOT NULL | 値段（円） |
| description | VARCHAR(100) | - | 短い説明 |
| category | ENUM('drink', 'food') | NOT NULL | ドリンクかフードかの区分 |
| is_available | BOOLEAN | NOT NULL, DEFAULT true | その日に売れるかどうか。売り切れたら false にする |
| created_at | TIMESTAMP | - | 登録した日時 |
| updated_at | TIMESTAMP | - | 最後に書き換えた日時 |

**orders（注文）**

| カラム名 | データ型 | 制約 | 説明 |
|:---------|:---------|:-----|:-----|
| id | BIGINT | PRIMARY KEY, AUTO_INCREMENT | 注文を1件ずつ区別する番号 |
| order_number | VARCHAR(6) | NOT NULL, UNIQUE | お客さまにお伝えする6桁の注文番号 |
| total_amount | INT | NOT NULL | 合計金額（円） |
| status | VARCHAR(20) | NOT NULL | 受け取りの状態。取りうる値はChapter 6で決めます |
| ordered_at | DATETIME | NOT NULL | 注文を受けた日時 |
| created_at | TIMESTAMP | - | 登録した日時 |
| updated_at | TIMESTAMP | - | 最後に書き換えた日時 |

**order_items（注文明細）**

| カラム名 | データ型 | 制約 | 説明 |
|:---------|:---------|:-----|:-----|
| id | BIGINT | PRIMARY KEY, AUTO_INCREMENT | 注文明細を1件ずつ区別する番号 |
| order_id | BIGINT | NOT NULL, FOREIGN KEY | どの注文の明細か |
| product_id | BIGINT | NOT NULL, FOREIGN KEY | どの商品か |
| quantity | INT | NOT NULL | 個数 |
| unit_price | INT | NOT NULL | 注文したときの、その商品1つぶんの値段 |
| created_at | TIMESTAMP | - | 登録した日時 |
| updated_at | TIMESTAMP | - | 最後に書き換えた日時 |

`orders` の `ordered_at` と `created_at` には、今のところ同じ値が入ります。`created_at` はLaravelが行を登録した日時を自動で入れる列で、`ordered_at` のほうは「注文を受け付けた時刻」として自分たちで意識して持つ列です。分けておくと、前もって注文を受け付ける決めごとが入ったときに、受け付けた時刻と登録した時刻を別々に扱えます。`ordered_at` を置かずに `created_at` で代えても間違いではありません。

注文番号を `id` とは別に持ち、型を `VARCHAR(6)` にしたのは、先頭が0になる番号があり得るからです。数値の型で持つと `004512` が `4512` になってしまいます。一方、入力チェック表で決めたもう1つの「1商品あたり10個まで」は、`INT` という型では表せません。この決めごとは入力チェック表が持っているので、テーブル定義書には現れません。設計書は1枚で全部を持つものではない、という一例です。

**CRUD表（解答例）**

| 機能 | 商品 | 注文 | 注文明細 |
|:-----|:-----|:-----|:---------|
| F-01 メニューの閲覧 | R | - | - |
| F-02 商品の注文 | R | C | C |
| F-03 注文状況の確認 | R | R | R |
| F-04 注文の取り消し | - | U | - |
| F-05 注文の受け渡し | R | R・U | R |

F-05で商品と注文明細をRにしているのは、店員のタブレットに「どの商品を何個」と出すためです。注文の行だけを読んでも、何を渡せばよいのかは分かりません。同じ行の注文が `R・U` なのも、注文番号と受け取りの状態を一覧に出したうえで、渡し終えたら状態を書き換えるからです。一方でF-04の注文が `U` だけなのは、取り消す相手を探すためだけの読みをRに数えないからです。

この表を縦に読むと、**「商品」の列にC・U・Dが1つも付いていません**。その日のドリンクとフードを登録する機能も、売り切れに切り替える機能も、機能一覧のどこにも無いということです。

画面設計では「売り切れの商品には『売り切れ』と出す」と見せ方まで決め、API設計では、売り切れの商品を注文されたときに何を返すかまで決めました。それでも、**誰がその商品を売り切れにするのかは、一度も決めていません**。Chapter 2からここまで設計書を作ってきて、ここで初めて見えます。CRUD表が、機能とデータを突き合わせる唯一の表だからです。

処置は、機能を足すことではありません。想定を添えて、確認事項リストへ送ります。

「注文明細」の列にUとDが無いことも、縦に読めば見つかります。こちらは決め忘れではありません。一度入った明細は、注文が取り消されても書き換えずに残します。取り消したことは、注文の側の状態で表します。

**確認事項リストへの追記（解答例）**

番号は、自分のリストの最後の続きです。ここでは `Q-13` としています。

| ID | 確認したいこと（こちらの想定つき） | 関係する機能 | 状態 |

| Q-13 | その日に出す商品の登録と、売り切れの切り替えは、こちらでデータをお預かりして行う想定です。店員の方がタブレットの画面からご自身で操作できる必要はありますか | F-01・F-02 | 未確認 |

**迷いやすいところ**

**合計金額を注文に持った理由**

明細に「注文したときの値段」と「個数」があるので、合計金額は計算すれば出ます。それでも列として持つのは、注文した時点の金額を、動かないものとして残しておくためです。同じ理由で、明細にも `unit_price` を持たせています。商品の値段は `products` にありますが、そちらを見に行く作りにすると、値段を変えた瞬間に過去の注文の金額が変わってしまいます。

合計金額のほうは、明細から足し直せば同じ値が出るので、持たない設計にした方も間違いではありません。「数えれば出るものは覚えておかない」という原則との分かれ目は、そのときお預かりした金額を**記録として残す**必要があるかどうかです。残す必要があるなら、計算で出せるものでも持ちます。

## 🚀 まとめ

- エンティティは、画面から数えません。仕様書とユースケース記述から名詞を拾い、3つのふるいにかけて数えます。カート画面があってもカートを持たない、という判断がその実例です。
- 覚えておかないと決めたものは、理由を書き添えて残します。確認事項の返事しだいで変わる判断なので、何を根拠に落としたのかが分かる形にしておきます。
- 正規形の点検を通したうえで、あえて重複を持たせる場所が2か所出てきます。注文の合計金額と、明細の `unit_price` です。崩した理由を書き添えるところまでが1組です。
- CRUD表は、Chapter 2からここまでの設計書を突き合わせて初めて見えるものを見せてくれます。商品を登録する機能も、売り切れに切り替える機能も、どこにも無いことが、縦に読んだ瞬間に分かります。
- 見つかった穴は、機能を足して埋めません。Chapter 2からChapter 4までと同じように、想定を添えて確認事項リストへ送ります。

注文の状態が、いくつあって、どんな順で移り変わるのかは、まだ決めていません。`status` の取りうる値はChapter 6で決めます。
