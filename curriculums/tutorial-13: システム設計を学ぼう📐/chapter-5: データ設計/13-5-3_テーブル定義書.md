# 13-5-3: テーブル定義書

## 🎯 このセクションで学ぶこと

- テーブルごとに、列の名前・型・決まりごとを決めて、1枚の表に書けるようになる。
- 日本語のエンティティ名と属性を、英語のテーブル名とカラム名に置き換えられるようになる。
- 決まっていないことを空欄にせず、どこで決めるかを書き残せるようになる。

---

## 導入：桁数は、書いた人の手癖で決まってしまう

ER図まで描けば、どんなテーブルがあって、互いにどうつながるかは決まります。ただ、四角の中身は空のままです。`lessons` に何という列を持たせるのか、題名は何文字まで受け付けるのか、空のままでよい列はどれか。ここが決まっていないうちにマイグレーションを書き始めると、その場の判断で `string('title', 200)` と書かれます。あとから「なぜ200文字ですか」と聞かれても、答えられる人が誰もいません。

9-3の章で学んだのは、決まったテーブルをマイグレーションでどう作るかでした。ここで決めるのは、その手前です。🔑 **コードを書く前に、列の名前・型・決まりごとを決めます**。決めた内容を書き残したものが**テーブル定義書**（テーブルごとに、列の名前・型・決まりごとを書き出した書類）です。

日本語の「レッスン」を `lessons` と英語で書き始めるここから先が、13-1-2の地図でいう詳細設計側にあたります。

---

## テーブル定義書の読み方

13-5-1・13-5-2と同じ、料理教室の受講管理アプリです。4つのテーブルのうち、`lessons` の1枚を読みます。

**lessons（レッスン）**

| カラム名 | データ型 | 制約 | 説明 |
|:---------|:---------|:-----|:-----|
| id | BIGINT | PRIMARY KEY, AUTO_INCREMENT | レッスンを1件ずつ区別する番号 |
| teacher_id | BIGINT | NOT NULL, FOREIGN KEY | 担当する講師 |
| title | VARCHAR(100) | NOT NULL | レッスンの題名 |
| held_at | DATETIME | NOT NULL | 開催する日時 |
| capacity | INT | NOT NULL | 定員 |
| created_at | TIMESTAMP | - | 登録した日時 |
| updated_at | TIMESTAMP | - | 最後に書き換えた日時 |

まず、表の見出しを見てください。`lessons` という英語のテーブル名と、「レッスン」という日本語の名前が並んでいます。🔑 **この1行が、日本語と英語の名前の対応表を兼ねます**。別に対応表を作らなくても、定義書を開けばどちらの名前でも探せます。

次に、上から3行目までを見ます。`title` は13-5-1で「題名」と書いた属性ですが、`id` と `teacher_id` は概念モデルにありませんでした。`id` は1件ずつを区別するための列で、`teacher_id` は13-5-2のER図で `lessons` が「多」の側だったことから来ています。線の「多」の側が相手を指す列を持つ、というあの読み取りが、ここで実際の行になりました。

いちばん下の2行も、概念モデルにありませんでした。`created_at` と `updated_at` は、Laravelがマイグレーションの `timestamps()` で自動的に作る列です。概念モデルの段階では意識して決めるものではありませんが、テーブルとしては実在するので、定義書には書きます。

最後に、「説明」の欄を縦に見てください。**空いている行が1つもありません**。ここが空いていると、実装する人は列の名前から中身を推測することになります。`capacity` を「これまでに受け付けた人数」と読み違えて実装されると、定員のチェックが逆になります。「制約」の欄に決まりごとが無い行も、空けずに `-` と書きます。13-4-2の権限マトリクスで、できないことを空欄にせず × と書いたのと同じ理由です。

## テーブル定義書の書き方

テーブル1つにつき、表を1つ作ります。

**手順1: 英語のテーブル名を決める**

13-5-2のER図に置いた四角を、1つずつ表にします。テーブル名は、**英語の小文字で、複数形**にします。投稿アプリの `users`・`categories`・`posts` も、11-2-8「ハンズオン - タスク管理APIのCRUD実装」で使った `tasks` も、この形です。単語が2つ以上になるときは、アンダースコアでつなぎます。

例外は、多対多のつなぎ役として置いた四角です。9-5-2「多対多のリレーションシップ」で学んだとおり、こちらは2つのテーブル名を単数形にして、アルファベット順につないだ名前（`post_tag`）にします。

表の見出しには、英語のテーブル名と日本語の名前を必ず併記してください。ここを省くと、定義書を読む人と依頼者の会話が続かなくなります。

**手順2: 主キーと外部キーの行を置く**

どのテーブルにも、いちばん上に `id` の行を置きます。データ型は `BIGINT`、制約は `PRIMARY KEY, AUTO_INCREMENT` です。1件ずつを区別する番号を、データベースが自動で振る、という意味になります。8-2-2「データベースとテーブルの作成」では `id BIGINT UNSIGNED` と書きましたが、設計書では `BIGINT` とだけ書けば足ります。符号を扱うかどうかまでは、実装のときにLaravelの書き方へ合わせる部分です。

外部キーは、ER図で「多」の側になったテーブルに置きます。列の名前は、相手のテーブル名を単数形にして `_id` を付けた形です（`teacher_id`・`post_id`）。制約の欄に `FOREIGN KEY` と書きます。

**手順3: 属性を、カラム名に置き換える**

13-5-1で日本語で書いた属性を、1つずつ英語のカラム名にします。**小文字とアンダースコア**だけを使います（`held_at`・`unit_price`）。名前の付け方をこれ以上細かく決めることはしません。この教材で守るのは、テーブル名は複数形、カラム名は小文字とアンダースコア、の2つだけです。

**手順4: データ型を決める**

型は、8-1-3「テーブル、カラム、レコードの理解」で学んだ `INT`・`VARCHAR(n)`・`TEXT`・`DATE`・`DATETIME`・`BOOLEAN` を土台にします。この章では、このほかに次の3つも使います。

| 型 | どんな値を入れるものか | これまでに出てきた場所 |
|:---|:-----------------------|:-----------------------|
| `BIGINT` | とても大きな整数 | 8-2-2「データベースとテーブルの作成」の `id BIGINT UNSIGNED` |
| `ENUM` | 決められた選択肢のうちの1つ | 8-2-7「MySQL基本操作 - ハンズオン演習」の `status ENUM('未着手', '進行中', '完了')` |
| `TIMESTAMP` | 日付と時刻 | 9-3の章のマイグレーションが作る `created_at`・`updated_at` |

そのうえで、迷いやすいところを挙げておきます。

- 文字は、上限の見当が付くものは `VARCHAR(100)` のように桁数を決め、本文のように長くなるものは `TEXT` にします。桁数は自分で決めるので、決めた理由を表の下か「説明」の欄に残してください。
- 日付だけでよいものは `DATE`、時刻まで要るものは `DATETIME` です。
- はい・いいえで答えられるものは `BOOLEAN` です。選ぶ言葉の一覧がすでに決まっているなら `ENUM`、まだ出そろっていないなら `VARCHAR` にしておき、決まってから直します。迷うのは、選ぶものが2つしかないときです。分かれ目は、**片方を「そうでない状態」として自然に言えるか**どうかです。支払いが済んでいるかどうかは片方が「済んでいない」で足りるので `BOOLEAN`、レッスンが「対面」か「オンライン」かはどちらにも名前が要るので `ENUM` にします。
- 数を数えるものは `INT` です。`id` と外部キーは `BIGINT` にそろえます。件数が増えても番号が足りなくならないようにするためで、外部キーは指す先の `id` と型が同じでないとつなげません。

**手順5: 制約と説明を書く**

制約の欄には、`PRIMARY KEY`・`FOREIGN KEY`・`NOT NULL`・`UNIQUE`・`DEFAULT` を書きます。空のままにできない列に `NOT NULL`、同じ値が2件あってはいけない列に `UNIQUE`、何も入れなかったときの値が決まっている列に `DEFAULT` を書きます。当てはまるものが無ければ `-` です。

説明の欄は、日本語の1行で埋めます。まだ決まっていないことがあれば、そこも空けません。「取りうる値は次の章で決めます」のように決める場所を書くか、13-2-1で学んだとおり想定を添えて確認事項リストへ送ります。

## 🏃 書いてみよう

投稿アプリの `posts` テーブルについて、定義書を1枚作ります。

### Step 1: マイグレーションを読む

13-5-2で開いた `database/migrations/2024_01_01_000001_create_posts_table.php` を、もう一度開きます。

```php
// database/migrations/2024_01_01_000001_create_posts_table.php
Schema::create('posts', function (Blueprint $table) {
    $table->id();
    $table->foreignId('user_id')->constrained()->cascadeOnDelete();
    $table->foreignId('category_id')->constrained();
    $table->string('title');
    $table->text('content');
    $table->timestamps();
});
```

書かれているのは6行ですが、最後の `timestamps()` が2列ぶんを作るので、定義書の行は7行になります。

### Step 2: 桁数の手がかりを探す

`string('title')` には、桁数が書かれていません。Laravelの `string()` は、桁数を省くと255文字の列を作ります。同じ255という数字が、もう1か所に出てきます。

```php
// app/Http/Controllers/PostController.php の update() から抜粋
$validated = $request->validate([
    'title' => 'required|string|max:255',
    'content' => 'required|string',
    'category_id' => 'required|exists:categories,id',
]);
```

`max:255` です。入口で弾く上限と、テーブルが受け付ける上限がそろっています。この3行には、制約の手がかりも入っています。`required` は「空では受け付けない」という決めごとなので、`NOT NULL` を書く根拠になります。

### Step 3: 定義書を1枚作る

VS Codeで `docs/13-5/post-table.md` を新しく作り、`posts` の表を1つ書きます。列は `カラム名`・`データ型`・`制約`・`説明` の4列で、見出しには英語のテーブル名と日本語の名前を併記します。

**「説明」の欄は、自分の言葉で埋めてください**。その列が何のためにあるのかを、1行で書きます。

### Step 4: 成果物を保存する

```bash
# アプリのフォルダの中で実行する
git add docs/13-5
git commit -m "13-5: 投稿アプリのテーブル定義書を追加"
git push origin main
```

- [ ] 行が7行で、`created_at` と `updated_at` の2行がある
- [ ] 主キーの列名が `id` で、データ型が `BIGINT` になっている
- [ ] 外部キーが2本あり、どちらも制約の欄に `FOREIGN KEY` と書かれている
- [ ] すべての行に、データ型・制約・説明が書かれている（当てはまる制約が無い行は `-`。空欄が1つもない）
- [ ] 「説明」の欄が、自分の言葉で書かれている

**迷いやすいところ**

- **タイトルの桁数を255にした理由**: `string()` が桁数を省いたときに作る長さと、`max:255` の上限が一致しているからです。設計書として書くなら、この255を「タイトルの上限」として自分で決めた数字にします。100文字と決めて、バリデーションも `max:100` にそろえるのも、正しい設計です。
- **`content` を `TEXT` にした理由**: 本文には上限の見当が付かないためです。マイグレーションでも `text()` が使われています。
- **外部キーを `BIGINT` にした理由**: 指す先の `users.id`・`categories.id` が `BIGINT` だからです。型がそろっていないと、外部キーとしてつなげません。
- **日時の2列の制約を `-` にした理由**: `created_at` と `updated_at` はLaravelが値を入れる列で、こちらから決める制約が無いためです。空欄にせず `-` と書くところまでが1組です。

## 💡 よくある間違いと現場での使われ方

**間違い1: 「説明」の欄を空ける**

カラム名を見れば分かる、と考えて空けてしまう間違いです。`status` や `flag` のような列こそ、いつ・誰が・何のためにその値を入れるのかを1行書きます。

**間違い2: 概念モデルに無い列を、断りなく足す**

書きながら「この列もあったほうがよさそうだ」と思いついて足してしまう間違いです。`id` と外部キー、Laravelが作る `created_at`・`updated_at` は、13-5-1の段階で表に出さないと決めたものなので、そのまま足して構いません。それ以外を足すときは、13-5-1のエンティティ一覧にも属性を足します。

現場では、テーブル定義書は実装だけでなく、あとからデータを調べるときにも開かれます。「この列に入っている数字は何ですか」と聞かれたときに答えられるのが、この1枚です。

## ✨ まとめ

- テーブル定義書は、テーブル1つにつき1つの表で、`カラム名`・`データ型`・`制約`・`説明` の4列で作ります。見出しに英語のテーブル名と日本語の名前を併記すると、名前の対応表を兼ねられます。
- どのテーブルにも `id` を置き、外部キーはER図で「多」の側になったテーブルに `{相手の単数形}_id` の形で置きます。テーブル名は複数形、カラム名は小文字とアンダースコアです。
- 型は8-1-3で学んだものに `BIGINT`・`ENUM`・`TIMESTAMP` を足して使います。選択肢が2つのとき、片方を「そうでない状態」と言えるなら `BOOLEAN`、どちらにも名前が要るなら `ENUM` です。
- 「制約」も「説明」も空欄にしません。当てはまるものが無い制約は `-`、まだ決まっていないことは、決める場所を書くか確認事項リストへ送ります。
