# 13-5-1: 概念データ設計 - エンティティの見つけ方

## 🎯 このセクションで学ぶこと

- 仕様書とユースケース記述から、システムが覚えておく情報のまとまりを見つけて、一覧に並べられるようになる。
- 見つけたものどうしのつながりを、1対多・多対多の言葉で一覧にできるようになる。
- 覚えておかないと決めたものについて、その理由を書き残せるようになる。

---

## 導入：アプリを閉じたら、全部消えてしまう

注文を受け付ける入口をいくら丁寧に設計しても、受け取った中身をどこかに残しておかなければ、お客さまがアプリを閉じた瞬間に消えます。次に開いたときには、注文番号を伝えることも、注文の状況を見せることもできません。

残す場所を決めないまま実装を始めると、コードを書きながら「この項目も要る」と気づくたびに、テーブルの形が変わります。データが入ったあとで列を足す直しは、画面の直しよりずっと重くなります。何を、どんなまとまりで残しておくのかは、先に決めます。

## エンティティ一覧の読み方

最初に作るのが**概念モデル**（システムが覚えておく情報の種類と、その関係だけを整理したもの）です。中身は2つの表に分かれます。覚えておく情報のまとまりを並べた**エンティティ一覧**と、そのまとまりどうしがどうつながっているかを並べた**関係の一覧**です。

**エンティティ**（システムが覚えておく情報のまとまり）は、8-1-5「データベース設計の基礎」でER図の四角として出てきたものです。エンティティが持つ項目は**属性**と呼びます。8-1-5でアトリビュートと呼んでいたもので、この教材では「属性」で通します。

言葉が新しく見えますが、**中身はテーブルです**。この章で作るものが、最後にどうなるかを先に並べておきます。

| いま決めるもの | 実装での姿 | 決めるのはどこか |
|:---------------|:-----------|:-----------------|
| エンティティ1つ | テーブル1つ | この節 |
| 属性1つ | カラム1つ | この節（名前と型は13-5-3） |
| エンティティどうしの関係 | 外部キー | この節（どちらが持つかは13-5-2） |

例外は多対多の関係だけで、そのときはどちらにも無かったテーブルが1つ増えます（13-5-2で扱います）。

それでもテーブルと呼ばずにエンティティと呼ぶのは、この段階では**カラム名も型も決めないから**です。「講師」と日本語で書いておいて、`teachers` にするか `instructors` にするかは13-5-3で決めます。名前や型を決めながら「そもそもこれを覚えておく必要があるのか」を考えると、どちらも中途半端になります。ここで決めるのは、覚えておくものの**種類**だけです。

題材は、料理教室の受講管理アプリです。次の相談を受けたとします。

> 料理教室を開いています。月ごとにレッスンの予定を組んで、受講者の方に申し込んでいただく形です。今は紙の申込書を教室ごとにまとめていて、定員を超えて受け付けてしまうことがあります。
>
> レッスンは1回ごとに、題名と、開催する日時と、定員が決まっています。担当する講師は1回につき1人です。講師については、名前のほかに得意な料理も載せて、受講者の方が選ぶときの手がかりにしたいです。
>
> 受講者の方には、お名前と連絡先をご登録いただいたうえで、受けたいレッスンを選んで申し込んでいただきます。受講料は申し込みのときにお支払いいただくので、支払いが済んでいるかどうかも分かるようにしてください。

この相談から起こしたエンティティ一覧が、次の表です。

| エンティティ | 何を覚えておくものか | 主な属性 |
|:-------------|:---------------------|:---------|
| 講師 | レッスンを担当する人 | 名前・得意な料理 |
| レッスン | 1回ぶんの教室 | 題名・開催する日時・定員 |
| 受講者 | 申し込む人 | 名前・連絡先 |
| 申し込み | 誰がどのレッスンに申し込んだか | 申し込んだ日時・支払いが済んでいるか |

この表を上から読むと、🔑 **このシステムが覚えておくものが4種類だ**と分かります。画面一覧が人から見える入口の一覧、エンドポイント一覧がプログラムから見える入口の一覧だとすると、エンティティ一覧は「残しておくものの一覧」です。

4行目の「申し込み」に注目してください。これは、レッスンと受講者をつないでいるだけのように見えます。それでも独立した行になっているのは、**申し込んだ日時**と**支払いが済んでいるか**を覚えておく必要があるからです。つなぐだけなら、誰がどのレッスンを選んだかという組み合わせを覚えれば足ります。その組み合わせに加えて、それ自身の属性を持つものは、1つのエンティティとして立ちます。

もう1つ、この表に**無い**ものを見てください。「定員に達したかどうか」がどこにもありません。定員はレッスンの属性としてあり、今いくつ申し込みが入っているかは、申し込みを数えれば分かります。🔑 **数えれば出るものは、覚えておかない**というのが、ここでの決定です。覚えてしまうと、申し込みが入るたびに数を書き換える処理が要り、書き換えそこねたときに、数えた結果と食い違ったまま残ります。

## エンティティ一覧の書き方

**手順1: 名詞を拾う**

仕様書と、13-2-2のテンプレートで書いたユースケース記述を、上から読みます。そして、出てくる名詞に印を付けます。料理教室の相談なら、レッスン、予定、受講者、申込書、申し込み、教室、定員、題名、日時、講師、名前、得意な料理、連絡先、受講料、支払いです。「定員を超えて受け付けてしまう」のように名詞の形になっていない言い回しから読み取れるもの（定員に達したかどうか）も、ここで拾っておきます。

この段階では選り分けません。多すぎても構いません。

**手順2: 3つのふるいにかける**

拾った名詞を、1つずつ問います。エンティティの候補になるか属性の候補になるかを分けるのが1つ目と2つ目で、🔑 **覚えておくかどうかを決めるのは、いつも3つ目**です。1つ目が「はい」なら、2つ目は飛ばして3つ目へ進みます。

| ふるい | 問い | 「はい」のとき | 「いいえ」のとき |
|:-------|:-----|:---------------|:-----------------|
| 1つ目 | それは何件も並ぶか。1件ずつ区別して数えられるか | エンティティの候補にして、3つ目のふるいへ | 2つ目のふるいへ進む |
| 2つ目 | それは1つのエンティティにくっついてしか意味を持たないか | 属性の候補にして、3つ目のふるいへ | どちらにもしない |
| 3つ目 | それは次に開いたときにも残っていてほしいか。数えたり計算したりすれば出るものは「いいえ」です | 候補のとおり、エンティティか属性にする | 覚えておかない |

🔑 **1つ目が「はい」だっただけでは、エンティティになりません**。3つ目のふるいまでかけてください。

料理教室の名詞を、実際に流してみます。

- **レッスン**: 4月10日の回と4月17日の回を1件ずつ区別して数えられるので、1つ目は「はい」です。3つ目に進むと、申し込みを受けたあとも残っていないと困るので「はい」。エンティティになります。
- **題名**: 1件ずつ数えるものではないので1つ目は「いいえ」、2つ目に進みます。レッスンから切り離すと何のことか分からなくなるので「はい」。3つ目も、題名が残っていないと何の回なのか分からないので「はい」。レッスンの属性になります。
- **教室**: 1つ目は「はい」です（教室ごとに申込書をまとめているので、数えられます）。ところが3つ目に進むと、この相談には教室そのものをシステムに残す話が出てきません。「いいえ」なので、覚えておかないものになります。
- **受講料**: 1つ目は「いいえ」、2つ目はレッスンから切り離すと何の受講料か分からないので「はい」です。ところが3つ目では、この相談に出てくるのが「支払いが済んでいるか」だけで、金額そのものを残してほしいとは書かれていません。「いいえ」なので、覚えておかないものになります。
- **定員に達したかどうか**: 1つ目は「いいえ」、2つ目はレッスンにくっついてしか意味を持たないので「はい」です。3つ目は、申し込みを数えればいつでも出るので「いいえ」。覚えておかないものになります。

残りも同じように流すと、拾った名詞の行き先が全部決まります。

| 行き先 | 拾った名詞 |
|:-------|:-----------|
| エンティティ | レッスン・講師・受講者・申し込み |
| レッスンの属性 | 題名・日時・定員 |
| 講師の属性 | 名前・得意な料理 |
| 受講者の属性 | 名前・連絡先 |
| 申し込みの属性 | 支払い（支払いが済んでいるか） |
| 覚えておかない | 予定・申込書・教室・受講料・定員に達したかどうか |

予定はレッスンを並べたもの、申込書は紙で受け付けていたときの呼び名で、どちらもレッスンと申し込みで言い換えられます。

逆に、拾った名詞に無かったものが1つあります。読み方で見たエンティティ一覧に並んでいた「申し込んだ日時」です。先に申し込んだ方から順に受け付けるには、いつ申し込まれたのかが要ります。名詞を拾うのは出発点なので、足りないものに気づいたら足して構いません。足したものは、なぜ要るのかを言えるようにしておきます。

**手順3: 表に並べる**

`エンティティ`・`何を覚えておくものか`・`主な属性` の3列で表を作ります。

- エンティティの名前は、🔑 **日本語の名詞で、単数形**にします。仕様書が「レッスン」と呼んでいるものを「講座」と言い換えないでください。13-2-2で決めた、仕様書の言葉に設計書を揃えるという約束は、ここでも同じです。まだテーブルではないので、複数形にもしません。
- 「何を覚えておくものか」の欄は、日本語の1文で書きます。ここが書けないエンティティは、まだ何を残すのかが決まっていません。
- 「主な属性」の欄は、日本語の項目名を中黒（`・`）で並べます。**型も桁数も書きません**。それを決めるのは13-5-3です。

**手順4: 覚えておかないと決めたものを、書き残す**

3つ目のふるいで落としたものの中には、「なぜ無いのか」を聞かれるものがあります。料理教室の「定員に達したかどうか」がそれです。表に行が無いだけでは、検討して落としたのか、忘れたのかを、読んだ人が区別できません。落とした理由は、表の下に1行書き添えます。

13-2-2では、ユースケース図で線を引かないことが「使えない」という決定を表すと学びました。13-4-2では、できないことを空欄にせず × と書きました。ここも同じで、🔑 **持たないという決定にも、書き残す場所が要ります**。

拾った名詞のうち、エンティティなのか属性なのかを自分では決めきれないものが出てきたら、そこで止まりません。13-2-1で学んだとおり、想定を添えて確認事項リストへ送り、その想定の上で先へ進みます。

## 関係の一覧の読み方

エンティティ一覧は、覚えておくものを縦に並べただけの表です。どれとどれがつながっているかは、まだどこにも書かれていません。それを並べたのが、次の表です。

| エンティティA | 関係 | エンティティB | 読み方 |
|:--------------|:-----|:--------------|:-------|
| 講師 | 1対多 | レッスン | 1人の講師は、複数のレッスンを担当する |
| レッスン | 1対多 | 申し込み | 1回のレッスンには、複数の申し込みが入る |
| 受講者 | 1対多 | 申し込み | 1人の受講者は、複数の申し込みをする |

いちばん右の「読み方」の欄が、この表の要です。「1対多」という言葉だけでは、どちらが1でどちらが多いのかを読み違えます。日本語の1文にしておけば、依頼者にそのまま読み上げて「これで合っていますか」と確かめられます。料理教室の店主に「1人の講師は、複数のレッスンを担当します」と読み上げたところ、「いえ、2人で担当する回もあります」という返事が返ってきたとします。そうなれば、この行は多対多に変わります。

行が3本しかないことにも注目してください。エンティティは4つあるので、組み合わせは6通りありますが、そのうち3組には行がありません。たとえば講師と受講者の間に行が無いのは、この2つが直接つながっていないからです。講師が受講者を知るのは、レッスンと申し込みをたどった先です。🔑 **つながっていない組は、行を作りません**。

「関係」の欄に書く言葉は、**1対多・多対多・1対1** の3つだけです。8-3-1「リレーションシップの実装準備」で見た3つのパターンと同じもので、新しく覚えることはありません。

## 関係の一覧の書き方

**手順1: エンティティを2つずつ組にして問う**

エンティティ一覧の行を、上から2つずつ組にして、「この2つは直接つながっているか」を問います。4つなら6組です。総当たりで問うのは、思いついた組だけを書くと、つながりを1つ書き落としても気づけないからです。

**手順2: つながっている組に、3つの言葉のどれかを当てる**

「Aの1件に対して、Bは何件あるか」と「Bの1件に対して、Aは何件あるか」の両方を問います。片方が1件で片方が複数なら1対多、両方が複数なら多対多、両方が1件なら1対1です。

このとき、**Aの側に1が来るように並べます**。表の左に1、右に多を置いておくと、一覧を縦に読んだときに向きが揃います。

**手順3: 読み方の文を書く**

「1件の〜は、〜を持つ」「1人の〜は、複数の〜を〜する」の形で、日本語の1文にします。数を表す言葉（1人の、1回の、複数の）を必ず入れてください。「講師はレッスンを担当する」とだけ書くと、何件なのかが消えます。

0件があり得るかどうかも、この1文で書き分けておくと親切です。読み方で見た「1回のレッスンには、複数の申し込みが入る」は、申し込みが1件も入っていないレッスンもあり得る、という書き方です。「申し込みが1件も無いレッスンは登録しない」という決めごとであれば、「1回のレッスンには、1つ以上の申し込みが入る」と書き分けます。どちらなのかは、実装するときに「空でも登録してよいか」という形で必ず問われます。

多対多の組は、1文に両方の向きを入れます。1回のレッスンを2人で担当することがあるなら、講師とレッスンの行は多対多に変わるのでした。そのときは「1人の講師は複数のレッスンを担当し、1回のレッスンは複数の講師が担当する」と書きます。片方だけ書くと、読んだ人がもう片方を自分で埋めることになります。

## 🏃 書いてみよう

料理教室は読む練習でした。ここからは、Tutorial 13で使っている投稿アプリを題材にします。VS Codeで `~/laravel-practice/post-app-practice` を開いてください。

このアプリでできるのは、ログインした人が投稿の一覧を見て、自分が書いた投稿だけを編集・削除することです。投稿にはカテゴリが1つ付いています。

### Step 1: 画面に出ているものを書き出す

次の3つのファイルを開いて、画面に出ている項目と、入力できる項目を書き出します。

| ファイル | 見るところ |
|:---------|:-----------|
| `resources/views/posts/index.blade.php` | 投稿一覧に何が並んでいるか |
| `resources/views/posts/edit.blade.php` | 編集画面で何を入力し、何を選ぶか |
| `resources/views/auth/register.blade.php` | 新規登録で何を入力するか |

> ⚠️ **注意**: `database/migrations/` は、まだ開かないでください。そこには答えがそのまま書かれています。日本語の画面から情報のまとまりを見つけるのがこの演習で、開くのは13-5-2からです。

### Step 2: エンティティ一覧を作る

「エンティティ一覧の書き方」の手順1から4のとおりに進めます。列は `エンティティ`・`何を覚えておくものか`・`主な属性` の3列です。

属性は**日本語で**書いてください。Bladeの中に `title` と書かれていても、ここでは「タイトル」です。英語の名前に置き換えるのは13-5-3です。

3つ目のふるいで落としたものがあれば、表の下に理由を1行書き添えます。このアプリには、落ちるものが1つあります。

### Step 3: 関係の一覧を作る

「関係の一覧の書き方」の手順1から3のとおりに進めます。列は `エンティティA`・`関係`・`エンティティB`・`読み方` の4列です。

エンティティが3つなら、総当たりで問う組は3組です。そのうち行になるのが何組かは、自分で数えてください。

### Step 4: 成果物を保存する

13-1-3で作った `docs/` の中に、Chapter 5用のフォルダを作ります。

```bash
# アプリのフォルダへ移動する
cd ~/laravel-practice/post-app-practice

# Chapter 5用のフォルダを作る
mkdir docs/13-5
```

13-2からと同じく、ファイル名の先頭には、どの題材のものか分かる短い言葉を付けます。投稿アプリのものは `post-` です。

VS Codeで `docs/13-5/post-concept.md` を新しく作り、Step 2とStep 3の表を、この順で1つのファイルにまとめます。

```bash
# アプリのフォルダの中で実行する
git add docs/13-5
git commit -m "13-5: 投稿アプリの概念モデルを追加"
git push origin main
```

```blade
{{-- resources/views/posts/index.blade.php --}}
<p class="meta">投稿者: {{ $post->user->name }}／カテゴリ: {{ $post->category->name }}</p>
```

`$post->user->name` と書かれているとおり、この名前は投稿からユーザーをたどった先にあるものです。同じ人が投稿を10件書けば、同じ名前が画面に10回出ます。投稿の側に名前そのものを持たせると、その人が名前を変えたときに10か所を書き換えることになります。投稿が持つのは「誰が書いたか」というつながりだけです。カテゴリの名前も同じ形です。

**カテゴリをエンティティにした理由**

編集画面のカテゴリは、自由入力ではなく選択肢です。

```blade
{{-- resources/views/posts/edit.blade.php --}}
<select id="category_id" name="category_id" required>
    @foreach ($categories as $category)
        <option value="{{ $category->id }}" @selected(old('category_id', $post->category_id) == $category->id)>{{ $category->name }}</option>
    @endforeach
</select>
```

`$categories` を繰り返して選択肢を並べているので、選べる区分の一覧をアプリが覚えているということです。1件ずつ区別して数えられて、次に開いたときにも残っている必要があるので、3つのふるいをすべて通ります。

## 💡 よくある間違い

**間違い: 画面に出るものを、そのままエンティティにする**

カフェのモバイルオーダーアプリなら、カートがこれにあたります。カート画面があるので、カートというエンティティが要るように見えます。画面があることと、覚えておくことは別です。3つ目のふるいで、次に開いたときにも残っていてほしいかを問い直してください。

## ✨ まとめ

- 概念モデルは、エンティティ一覧と関係の一覧の2つの表で作ります。日本語のまま、覚えておく情報の種類とそのつながりだけを決めます。
- エンティティは、名詞を拾って3つのふるいにかけて見つけます。1つ目と2つ目で候補が分かれ、覚えておくかどうかは3つ目の「次に開いたときにも残っていてほしいか」で決まります。
- 落としたものは、表に行が無いだけでは伝わりません。理由を1行書き添えます。
- 関係の一覧は総当たりで問い、1対多・多対多・1対1のどれかを当てます。つながっていない組には行を作りません。
- 「読み方」の欄には数を表す言葉を入れます。依頼者にそのまま読み上げて確かめられる文にしておくと、思い違いがその場で見つかります。
