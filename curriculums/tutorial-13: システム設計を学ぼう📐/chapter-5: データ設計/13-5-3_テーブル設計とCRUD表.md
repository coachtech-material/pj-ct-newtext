# 13-5-3: テーブル設計とCRUD表

## 🎯 このセクションで学ぶこと

- テーブルごとに、列の名前・型・決まりごとを決めて、テーブル定義書に書けるようになる。
- 日本語のエンティティ名と属性を、英語のテーブル名とカラム名に置き換えられるようになる。
- 機能とデータを突き合わせたCRUD表を作り、空いているところから漏れを見つけられるようになる。

---

## 導入：桁数は、書いた人の手癖で決まってしまう

13-5-2でER図まで描けたので、どんなテーブルがあって、互いにどうつながるかは決まりました。ただ、四角の中身はまだ空です。`lessons` に何という列を持たせるのか、題名は何文字まで受け付けるのか、空のままでよい列はどれか。ここが決まっていないままマイグレーションを書き始めると、その場の判断で `string('title', 200)` と書かれます。あとから「なぜ200文字なのですか」と聞かれても、答えられる人が誰もいません。13-3-3で入力の決めごとについて書いたのと、同じ筋の話です。

9-3の章で学んだのは、決まったテーブルをマイグレーションでどう作るかでした。ここで学ぶのは、その手前です。🔑 **コードを書く前に、列の名前・型・決まりごとを決めます**。決めた内容は、表の形で書き残します。

このセクションから、扱うものが日本語の名前から英語の名前に変わります。13-5-1で「レッスン」「題名」と書いていたものを、`lessons`・`title` と決めていく作業です。13-5-1の導入で確認したとおり、ここからが詳細設計側です。

作るのは2つです。1つ目が**テーブル定義書**（テーブルごとに、列の名前・型・決まりごとを書き出した書類）で、2つ目が**CRUD表**（どの機能が、どのデータを作り・読み・書き換え・消すかを表にしたもの）です。

CRUD表を作るのは、ここまでの設計書が**データ側だけを見て作られている**からです。ER図もテーブル定義書も、Chapter 2で作った機能一覧を1度も見ずに書けてしまいます。この2つを突き合わせると、片方にしか無いものが見つかります。

## テーブル定義書の読み方

13-5-1・13-5-2と同じ、料理教室の受講管理アプリです。4つのテーブルのうち、`lessons` の1枚を読みます。

**lessons（レッスン）**

| カラム名 | データ型 | 制約 | 説明 |
|:---------|:---------|:-----|:-----|
| id | BIGINT | PRIMARY KEY, AUTO_INCREMENT | レッスンを1件ずつ区別する番号 |
| teacher_id | BIGINT | NOT NULL, FOREIGN KEY | 担当する講師 |
| title | VARCHAR(100) | NOT NULL | レッスンの題名 |
| held_at | DATETIME | NOT NULL | 開催する日時 |
| capacity | INT | NOT NULL | 定員 |
| created_at | TIMESTAMP | - | 登録した日時 |
| updated_at | TIMESTAMP | - | 最後に書き換えた日時 |

まず、表の見出しを見てください。`lessons` という英語のテーブル名と、「レッスン」という日本語の名前が並んでいます。🔑 **この1行が、日本語と英語の名前の対応表を兼ねます**。別に対応表を作らなくても、定義書を開けばどちらの名前でも探せます。

次に、上から3行目までを見ます。`title` は13-5-1で「題名」と書いた属性ですが、`id` と `teacher_id` は概念モデルにありませんでした。`id` は1件ずつを区別するための列で、`teacher_id` は13-5-2のER図で `lessons` が「多」の側だったことから来ています。線の「多」の側が相手を指す列を持つ、というあの読み取りが、ここで実際の行になりました。

いちばん下の2行も、概念モデルにありませんでした。`created_at` と `updated_at` は、Laravelがマイグレーションの `timestamps()` で自動的に作る列です。9-5-5の要件の表にも並んでいました。概念モデルの段階では意識して決めるものではありませんが、テーブルとしては実在するので、定義書には書きます。

最後に、「説明」の欄を縦に見てください。**空いている行が1つもありません**。ここが空いていると、実装する人は列の名前から中身を推測することになります。`capacity` を「これまでに受け付けた人数」と読み違えて実装されると、定員のチェックが逆になります。「制約」の欄に決まりごとが無い行は、空けずに `-` と書きます。13-4-2の権限マトリクスで、できないことを空欄にせず × と書いたのと同じ理由です。

## テーブル定義書の書き方

テーブル1つにつき表を1つ作ります。手順は5つです。

**手順1: 英語のテーブル名を決める**

13-5-2のER図に置いた四角を、1つずつ表にします。テーブル名は、**英語の小文字で、複数形**にします。9-5-5の `posts`・`comments`・`tags` も、11-2-8「ハンズオン - タスク管理APIのCRUD実装」で使った `tasks` も、この形でした。単語が2つ以上になるときは、アンダースコアでつなぎます。

例外は、多対多のつなぎ役として置いた四角です。9-5-2「多対多のリレーションシップ」で学んだとおり、こちらは2つのテーブル名を単数形にして、アルファベット順につないだ名前（`post_tag`）にします。

表の見出しには、英語のテーブル名と日本語の名前を必ず併記してください。ここを省くと、定義書を読む人と依頼者の会話が続かなくなります。

**手順2: 主キーと外部キーの行を置く**

どのテーブルにも、いちばん上に `id` の行を置きます。データ型は `BIGINT`、制約は `PRIMARY KEY, AUTO_INCREMENT` です。1件ずつを区別する番号を、データベースが自動で振る、という意味になります。8-2-2「データベースとテーブルの作成」では `id BIGINT UNSIGNED` と書きましたが、設計書では `BIGINT` とだけ書けば足ります。符号を扱うかどうかまでは、実装のときにLaravelの書き方へ合わせる部分です。

外部キーは、ER図で「多」の側になったテーブルに置きます。列の名前は、相手のテーブル名を単数形にして `_id` を付けた形です（`teacher_id`・`post_id`）。制約の欄に `FOREIGN KEY` と書きます。

**手順3: 属性を、カラム名に置き換える**

13-5-1で日本語で書いた属性を、1つずつ英語のカラム名にします。**小文字とアンダースコア**だけを使います（`held_at`・`unit_price`）。名前の付け方をこれ以上細かく決めることはしません。この教材で守るのは、テーブル名は複数形、カラム名は小文字とアンダースコア、の2つだけです。

**手順4: データ型を決める**

型は、8-1-3「テーブル、カラム、レコードの理解」で学んだ `INT`・`VARCHAR(n)`・`TEXT`・`DATE`・`DATETIME`・`BOOLEAN` を土台にします。この章では、このほかに `BIGINT`・`ENUM`・`TIMESTAMP` も使います。8-1-3の代表的なデータ型の表には並んでいないので、先に挙げておきます。

| 型 | どんな値を入れるものか | これまでに出てきた場所 |
|:---|:-----------------------|:-----------------------|
| `BIGINT` | とても大きな整数 | 8-2-2「データベースとテーブルの作成」の `id BIGINT UNSIGNED` |
| `ENUM` | 決められた選択肢のうちの1つ | 8-1-3の本文で名前だけ、8-2-7「MySQL基本操作 - ハンズオン演習」で `status ENUM('未着手', '進行中', '完了')` |
| `TIMESTAMP` | 日付と時刻 | 9-5-5の要件の表の `created_at`・`updated_at` |

そのうえで、迷いやすいところだけ挙げておきます。

- 文字は、上限の見当が付くものは `VARCHAR(100)` のように桁数を決め、本文のように長くなるものは `TEXT` にします。桁数は自分で決めるので、決めた理由を表の下か「説明」の欄に残してください。
- 日付だけでよいものは `DATE`、時刻まで要るものは `DATETIME` です。
- はい・いいえで答えられるものは `BOOLEAN` です。選ぶ言葉の一覧がすでに決まっているなら `ENUM`、まだ出そろっていないなら `VARCHAR` にしておき、決まってから直します。迷うのは、選ぶものが2つしかないときです。分かれ目は、**片方を「そうでない状態」として自然に言えるか**どうかです。支払いが済んでいるかどうかは片方が「済んでいない」で足りるので `BOOLEAN`、レッスンが「対面」か「オンライン」かはどちらにも名前が要るので `ENUM` にします。
- 数を数えるものは `INT` です。`id` と外部キーは `BIGINT` にそろえます。件数が増えても番号が足りなくならないようにするためで、外部キーは指す先の `id` と型が同じでないとつなげません。

**手順5: 制約と説明を書く**

制約の欄には、`PRIMARY KEY`・`FOREIGN KEY`・`NOT NULL`・`UNIQUE`・`DEFAULT` を書きます。空のままにできない列に `NOT NULL`、同じ値が2件あってはいけない列に `UNIQUE`、何も入れなかったときの値が決まっている列に `DEFAULT` を書きます。当てはまるものが無ければ `-` です。

説明の欄は、日本語の1行で埋めます。まだ決まっていないことがあれば、そこも空けません。「取りうる値は次の章で決めます」のように、決める場所を書くか、13-2-1で学んだとおり想定を添えて確認事項リストへ送ります。

## CRUD表の読み方

料理教室の受講管理アプリの機能一覧は、次の6行だとします。

| ID | 機能 | 主な利用者 |
|:---|:-----|:-----------|
| F-01 | レッスンの閲覧 | 受講者 |
| F-02 | レッスンの申し込み | 受講者 |
| F-03 | 申し込みの取り消し | 受講者 |
| F-04 | レッスンの登録 | 講師 |
| F-05 | 受講者の登録 | 受講者 |
| F-06 | 講師の登録 | 講師 |

この6行と、13-5-1で作ったエンティティ一覧の4行を突き合わせたのが、CRUD表です。

| 機能 | 講師 | レッスン | 受講者 | 申し込み |
|:-----|:-----|:---------|:-------|:---------|
| F-01 レッスンの閲覧 | R | R | - | - |
| F-02 レッスンの申し込み | - | R | R | C |
| F-03 申し込みの取り消し | - | - | - | D |
| F-04 レッスンの登録 | R | C | - | - |
| F-05 受講者の登録 | - | - | C | - |
| F-06 講師の登録 | C | - | - | - |

マスに書いてある4つの文字は、そのデータを**作る**のがC、**読む**のがR、**書き換える**のがU、**消す**のがDです。1つのマスに2つ以上入るときは、`R・U` のように中黒で並べます。触らないところは空けずに `-` と書きます。

Rをどこまで数えるかだけ、先に決めておきます。書き換えるにも消すにも、そのデータの1件を先に探す読みが必ず入ります。🔑 **相手を探すためだけの読みは、Rに数えません**。UやDと書いた時点で、その読みも含まれているものとして扱います。Rを書くのは、それ以外の読みです。画面に出すため、受け付けてよいかを判断するため、作るデータに結び付ける相手を確かめるため、といった読みが当てはまります。F-03の「申し込み」がDだけなのは、消す1件を探しているだけだからで、F-02の「受講者」がRなのは、どなたの申し込みかを確かめて、作る申し込みに結び付けるからです。

横に読むと、その機能がどのデータに触るのかが分かります。F-01の行なら、レッスンを読むだけでなく講師も読んでいます。一覧に担当する講師の名前を出すからです。この1行が読めれば、実装する人は「この画面を出すために、どのテーブルを見ればよいか」を迷いません。

縦に読むと、そのデータが誰にどう扱われるのかが分かります。🔑 **CRUD表の値打ちは、こちらの向きにあります**。見るのは、空いているところです。

| 空き方 | 疑うこと |
|:-------|:---------|
| Cが1つも無い列 | そのデータを作る機能が、どこにも無い |
| Rが1つも無い列で、Cも無い | 覚えておく必要が、本当にあるのか |
| Rが1つも無い列で、Cはある | 書き込む前に中身を確かめる機能が、抜けていないか |
| UもDも無い列 | 一度入れたら、二度と直せないデータになる |
| 行のマスが全部 `-` | その機能はデータを触らない。おかしくはないが、本当かを確かめる |

この見方を、上の表に当てはめます。「講師」「レッスン」「受講者」の3つの列には、UもDもありません。講師の名前を書き間違えても直せず、開かなくなったレッスンも残り続けます。どうするつもりなのかを、依頼者に確かめる場所です。

見つけにくいのは、「申し込み」の列のほうです。F-02にC、F-03にDはありますが、Rが1つもありません。Cはあるのに、同じ列にRが無い形です。申し込みを受け付けるとき、定員に達しているかどうかを確かめるには、**すでに入っている申し込みを読む必要がある**のに、それが表に出ていません。この相談は「定員を超えて受け付けてしまう」ことから始まっていました。いちばん困っていた場所が、表の1マスとして抜けていたことになります。

## CRUD表の書き方

手順は4つです。

**手順1: 行に機能を並べる**

Chapter 2で作った機能一覧の機能名を、IDごとそのまま写します（`F-01 レッスンの閲覧` の形）。動詞に直しません。13-4-2で権限マトリクスを作ったときと同じ書き方です。

**手順2: 列にデータを並べる**

13-5-1のエンティティ一覧の行を、**日本語のまま**列にします。英語のテーブル名にしません。行に並ぶ機能名が日本語なので、突き合わせる相手も日本語にそろえます。

13-5-2でつなぎ役として置いた四角も、列にします。「投稿とタグの組」のような呼び方で構いません。この列を作らないと、タグを付け外しする機能があるのかどうかを確かめられません。**つなぎ役のテーブルも、作る・消すの対象になるデータです**。

**手順3: マスを埋める**

機能を1つずつ頭の中で動かして、触るデータにC・R・U・Dを書きます。読み方で決めたとおり、相手を探すためだけの読みはRに数えません。ユースケース記述を書いてあるものは、基本フローを上からたどると数え落としが減ります。

**手順4: 縦に読んで、空を探す**

読み方で見た空き方の表を、列ごとに当てはめます。ここで見つかったものは、**勝手に機能を足して埋めません**。13-2-1で学んだとおり、想定を添えて確認事項リストへ送ります。CRUD表は、間違いを見つける表ではなく、決めていないことを見つける表です。

## 🏃 書いてみよう

> 🔥 この演習では、設計書をAIに作らせずに、自分の手で書きましょう。記法や考え方についてAIに質問するのは構いませんが、成果物を生成させるのはTutorial 14までお預けです。まず自分の手と頭で書けるようになった人だけが、AIの作った設計を正しく評価できるようになります。

13-5-1と13-5-2に続いて、9-5-5「リレーション - ハンズオン演習」で作ったブログシステム（`relation-app-practice`）が題材です。今回は、テーブル定義書とCRUD表を作ります。

### Step 1: 機能一覧を作る

このアプリでは機能一覧を作っていないので、要件の3行から起こします。13-2-1の付け方に従って、名詞の形で機能名を書き、`F-01` から順にIDを振ってください。要件の3行が、そのまま3つの機能になります。13-2-1で機能一覧とセットにした「今回作らないもの」の表は、Step 3のCRUD表を縦に読んでから気づくところなので、ここでは作りません。

### Step 2: `comments` のテーブル定義書を1枚作る

13-5-1では伏せてもらった、9-5-5の要件のテーブル構成の表を、ここからは開いて構いません。4枚全部は作りません。`comments` の行を写しながら、この章の4列（`カラム名`・`データ型`・`制約`・`説明`）に組み替えます。

9-5-5の表は `カラム名`・`型`・`備考` の3列でした。「備考」の行を1つずつ見て、行き先を分けます。「主キー、自動採番」「外部キー（postsテーブル）」のような決まりごとは制約の欄へ、「コメント本文」「作成日時」のような中身の説明は「説明」の欄の手がかりにします。

空にできない列かどうかは、9-5-5の表のどこにも書かれていません。ここは自分で決めるところです。本文の入っていないコメントを登録させるかどうかを考えれば、`body` に `NOT NULL` が要ることが決まります。

**「説明」の欄は、写さずに自分の言葉で埋めてください**。その列が何のためにあるのかを、1行で書きます。

### Step 3: CRUD表を作る

13-5-1で作ったエンティティ一覧の3行に、13-5-2の図でつなぎ役として置いたものを足して、列にします。

埋め終えたら、手順4のとおり縦に読んでください。どの列も、同じ文字ばかりが並ぶはずです。それがどういう状態を表しているのかを、**表の下に1〜2文で書いてください**。これが今回いちばん考えてほしいところです。

### Step 4: design-practiceに保存する

`13-5/` フォルダに、`blogtag-table.md`（テーブル定義書）と `blogtag-crud.md`（CRUD表）の2つを作ります。機能一覧は、CRUD表と同じファイルの先頭に置いて構いません。

```bash
# design-practice フォルダの中で実行する
git add 13-5
git commit -m "13-5: ブログシステムのテーブル定義書とCRUD表を追加"
git push origin main
```

- [ ] CRUD表に空のマスがない（触らないところは `-` と書かれている）
- [ ] 縦に読んで気づいたことが、表の下に書かれている

設計に唯一の正解はありません。言い回しや行の並び順が解答例と違っていても、上の観点を満たしていれば合格です。そのうえで、判断が分かれやすい3点を補足します。

- **C・U・Dが1つも無いのに、間違いではない理由**: 9-5-5は、リレーションの書き方に集中するために、作る機能を省くと最初から決まっていたハンズオンだからです。CRUD表は間違い探しの表ではありません。この表を実際の仕事で作れば、「投稿を書く画面はどこですか」という質問が、実装が始まる前に1回で出てきます。それが目的です。
- **つなぎ役のテーブルを列に入れた理由**: 書き方の手順2のとおりです。エンティティ一覧に行が無くても、テーブルとして実在するなら列にします。
- **F-03のコメントを `-` にした理由**: タグで絞り込んだ一覧にもコメント数は出ますが、F-01と同じ一覧なので、F-01の行で数えています。同じ処理を2行に書かない、という数え方の問題です。ここに `R` を書いても間違いではありません。

## 💡 よくある間違いと現場での使われ方

**間違い1: 「説明」の欄を空ける**

カラム名を見れば分かる、と考えて空けてしまう間違いです。`status` や `flag` のような列は、いつ・誰が・何のためにその値を入れるのかを1行書きます。

**間違い2: CRUD表の行を、画面の名前で並べる**

「投稿一覧画面」「投稿詳細画面」を行にしてしまう間違いです。13-4-2で権限マトリクスについて学んだのと同じで、行は機能一覧から写します。画面を行にすると、1つの機能が複数の画面に散らばったときに、同じ内容を2か所に書くことになります。

**間違い3: CRUD表で見つけた穴を、その場で埋める**

Cが無い列を見つけて、機能一覧に「投稿の作成」を足してしまう間違いです。足した瞬間に、作る量が増え、画面もエンドポイントも要ることになります。依頼者に確かめずに増やしてよいものではありません。

現場では、テーブル定義書は実装だけでなく、あとからデータを調べるときにも使われます。「この列に入っている数字は何ですか」と聞かれたときに開くのがこの1枚です。CRUD表のほうは、設計が一通りそろった時点の点検に使われます。

## ✨ まとめ

- テーブル定義書は、テーブル1つにつき1つの表で、`カラム名`・`データ型`・`制約`・`説明` の4列で作ります。見出しに英語のテーブル名と日本語の名前を併記すると、名前の対応表を兼ねられます。
- どのテーブルにも `id` を置き、外部キーはER図で「多」の側になったテーブルに `{相手の単数形}_id` の形で置きます。テーブル名は複数形、カラム名は小文字とアンダースコアです。
- 「制約」も「説明」も空欄にしません。当てはまるものが無い制約は `-`、まだ決まっていないことは、決める場所を書くか確認事項リストへ送ります。
- CRUD表は、行に機能一覧、列に日本語のエンティティ名を並べ、C・R・U・Dと `-` で埋めます。つなぎ役のテーブルも列にします。
- 縦に読んで空を探すのが、CRUD表の使い方です。Cが無い列、Rが無い列、UもDも無い列が見つかったら、機能を足さずに確認事項リストへ送ります。
