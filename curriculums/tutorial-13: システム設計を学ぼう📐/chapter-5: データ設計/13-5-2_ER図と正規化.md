# 13-5-2: ER図と正規化

## 🎯 このセクションで学ぶこと

- 概念モデルをER図に起こし、線の端の記号までdraw.ioで描けるようになる。
- 描いた設計が第3正規形になっているかを、3つの問いで点検できるようになる。
- あえて重複を持たせる判断があることを知り、その理由を書き残せるようになる。

## 導入：表を上下に往復しないと、つながりが追えない

関係の一覧は、つながりを1行ずつ言葉にした表です。行が3本のうちは読めますが、エンティティが増えて行が8本、10本になると、「レッスンにつながっているのはどれとどれか」を知るために、表を上から下まで何度も往復することになります。

同じ内容を1枚に置き直して、目で追えるようにしたのがER図です。実装が始まったあとも開かれ続ける設計書で、新しく入った人が「このシステムはどんなデータを持っているのか」を知るのに、いちばん早いのがこの1枚です。

## ER図の読み方

13-5-1で読んだ料理教室の受講管理アプリの続きです。あの2つの表を、そのままER図にすると次のようになります。

**料理教室の受講管理アプリのER図**

<img alt="13-5-2_1.png" src="">

四角が1つのテーブルで、中に英語のテーブル名が入っています。四角は4つあり、13-5-1のエンティティ一覧の4行と1対1で対応しています。🔑 **エンティティ一覧の行は、すべて四角として図に現れます**。図に出ていない行があれば、どちらかを書いたあとに、もう片方を直し忘れています。

線は、テーブルどうしの関係です。線に添えた文は、13-5-1の関係の一覧の「読み方」の欄に書いたものと同じで、表の3行がそのまま3本の線になっています。

大事なのは、線の**両端に付いた記号**のほうです。端の形が、その端が何件なのかを表しています。この教材で使う形は4つで、次のとおりです。

**線の端に付ける4つの記号**

<img alt="13-5-2_3.png" src="">

上の図の `teachers` と `lessons` を結ぶ線を、この4つと見比べてください。`teachers` の側は1つ目の形、`lessons` の側は2つ目の形です。つまり「1回のレッスンには講師がちょうど1人」で、「1人の講師にレッスンは0件以上」という意味になります。読み方の文を消しても、どちらが1でどちらが多いかは、この記号だけで読み取れます。

図の記号は、線の**端に近いほうから**読みます。丸と三又が並んでいる端なら、丸が「0件でもよい」、三又が「複数あり得る」を表していて、2つ合わせて「0件以上」になります。

線に**向きが無い**ことにも気づいてください。13-3-2で描く画面遷移図では、矢印の根元が移る前の画面、先端が移った後の画面という意味を持ちます。ER図の線は、そういう向きを持ちません。両端の件数を表しているだけです。

もう1つ、この図から読み取れることがあります。**外部キーをどちらのテーブルに持たせるか**です。`lessons` は `teachers` に対して「多」の側なので、どのレッスンがどの講師のものかを覚えておくのは `lessons` の側です。線の「多」の側が、相手を指す列を持ちます。実際にその列を書き出すのは13-5-3です。

> 💡 **TIP**: 8-1-5では、顧客・注文・注文明細・商品の4つからなるER図を読みました。あの図は四角の中にカラムまで並んでいましたが、この章の図にはテーブル名しかありません。なお、1件の注文の中に複数の商品が入るというあの形は、買い物を扱うシステムでくり返し出てきます。この先の演習でよく似た図になっても、写したわけではありません。

## ER図の描き方

使う記号は次のとおりです。

| 記号 | 表すもの |
|:-----|:---------|
| 四角 | テーブル1つ。中に英語のテーブル名を書く |
| 線 | テーブルどうしの関係 |
| 線の端の形 | その端が何件か。読み方で見た4つから選ぶ |
| 線に添えた文 | 両端が何件ずつなのかを、日本語の1文で言い直したもの |

四角の中に書くのは、テーブル名だけです。カラム名も型も書きません。13-3-2で画面遷移図の四角にIDを書かないのと同じで、図に情報を詰めるほど、見たいものが見えなくなります。この図はつながり方を見るためのもので、カラムを書き出すのはテーブル定義書の役目です。

**描く手順**

1. エンティティ一覧の行数ぶん、四角を置きます。中には英語のテーブル名を入れます。日本語のエンティティ名を英語にして複数形にしたものですが、付け方は13-5-3で決めるので、ここでは手を止めずに置いてください。
2. 関係の一覧の行数ぶん、線を引きます。**「1」の側の四角を左（または上）に置く**と、図と表の並びが揃って読みやすくなります。
3. 引いた線の両端に、上の4つから記号を選んで付けます。13-5-1の手順3で「複数の」と「1つ以上の」を書き分けたのが、そのまま丸と縦線の選び分けになります。
4. 線に、13-5-1の関係の一覧の「読み方」の欄の1文を書き入れます。文が長くて図が読みにくいときは、「1回のレッスンに、複数の申し込み」のように短くしても構いません。ただし、`1対多` とだけ書くのは避けてください。
5. 多対多の行があれば、その2つの四角の間につなぎ役の四角を1つ置き、両側へ1対多の線を2本引き直します。8-3-3で学んだとおり、多対多の関係は2つの1対多に分けて表します。線に書く文も、「1人の講師は、複数のレッスンとの組を持つ」のように、つなぎ役を相手にした形に書き直します。この四角は13-5-1のエンティティ一覧に行がありませんが、テーブル1つとして数えます。

手順3の記号と手順4の文は、どちらか片方だけでは足りません。記号だけだと、どちらの四角が講師でどちらがレッスンかを図の外から補って読むことになり、文だけだと、線を1本増やしたときに書き忘れても図が成立してしまいます。

### draw.ioで線端の記号を選ぶ

四角を置いて文字を入れるのと、四角どうしを線でつなぐのは13-1-3、線に文字を入れるのは13-3-2で学んだとおりです。ER図で新しく覚えるのは、線の端の記号を選ぶ操作だけです。

**線を選ぶ**

引いた線を1回クリックします。右の書式パネルの中身が、線のためのものに変わります。

**「スタイル」タブで、線の端のボタンを見つける**

線の太さや種類を選ぶ欄の下に、線の両端の形を選ぶボタンが2つ並んでいます。左が線を引き始めた側、右が引き終わった側です。

**線を選んだときの書式パネル**

<img alt="13-5-2_s1.png" src="">

**記号の一覧から選ぶ**

ボタンを押すと、端の形の一覧が開きます。長い一覧で、矢印や丸が上のほうに並び、ER図用の記号は下のほうにあります。この教材で使うのは、読み方で見た4つだけです。

> 💡 **TIP**: 一覧には、縦線が1本だけのものや、丸だけのものも並んでいます。使うのは上の4つだけです。線を引いた向きと記号を付けたい側が食い違ったときは、左右のボタンを入れ替えて選び直してください。

## 並べた属性を点検する

点検にかけるのは、図ではなく、13-5-1で並べた属性です。エンティティごとに、属性を上から見ていきます。図を描き終えたあとで構いませんが、エンティティを分けている最中に気づいたときは、その場でかけてください。

点検の前に、主キーについて1つ決めておきます。この教材では、どのテーブルにも1件ずつ区別するための `id` を1本だけ置きます（表に書き出すのは13-5-3です）。主キーが1列だけなら、下の2つ目の問いに引っかかることはありません。2つ目が効いてくるのは、注文IDと商品IDの組のように、2つの列の組で1件を区別しているときだけです。

| 問い | 通らなかったときの直し方 |
|:-----|:-------------------------|
| 1つのマスに2つ以上の値を入れようとしていないか | 値の数だけ行が増えるように、エンティティを分ける |
| 主キーの一部だけで決まる属性が混ざっていないか | その一部で決まるものを、別のエンティティへ出す |
| 主キー以外の属性で決まる属性が混ざっていないか | 決めているほうの属性ごと、別のエンティティへ出す |

3つの問いは、8-1-5で学んだ第1正規形・第2正規形・第3正規形に、上から順に対応しています。正規形の中身は8-1-5のとおりなので、ここでは点検の道具として使うだけです。

料理教室の「申し込み」を、次のように書いていたとします。

| エンティティ | 主な属性 |
|:-------------|:---------|
| 申し込み | 申し込んだ日時・支払いが済んでいるか・レッスンの題名・講師の名前 |

3つ目の問いで落ちます。「レッスンの題名」は、その申し込みがどのレッスンのものかが決まれば決まります。「講師の名前」も、レッスンをたどればその先で決まります。どちらも、申し込みそのものが決めている属性ではありません。8-1-5で見た、社員から所属部署をたどって部署名にたどり着く形と同じです。

そのまま作ると、レッスンの題名を書き換えたときに、そのレッスンへの申し込み全部を書き換えることになります。1件でも直し忘れれば、同じレッスンの題名が2通り残ります。直し方は、この2つの属性を申し込みから外すことです。外しても、`applications` から `lessons` へ線がつながっているので、題名も講師の名前もたどれます。

### あえて重複を持たせる判断

正規化は目的ではなく、道具です。あえて崩したほうがよい場面があります。

料理教室の相談には出てきませんでしたが、あとから「申し込みの一覧に、そのときお支払いいただいた金額も出したい」と言われたとします。レッスンに受講料の属性を足せば、金額はたどれます。ところが、来月から受講料を上げると、**先月ぶんの申し込みの金額まで変わってしまいます**。過去にいくら受け取ったのかが、記録として残りません。

そこで、申し込みのほうにも「支払った金額」を持たせます。レッスンと申し込みの2か所に同じ数字が並ぶので、重複をなくすという正規化の考え方からは外れる形です。それでもこちらを選ぶのは、🔑 **申し込んだ時点の金額を、動かないものとして残す**ためです。

この判断をしたときは、必ず理由を書き残してください。理由が書かれていないと、あとから設計書を読んだ人が「正規化のし忘れだ」と考えて、親切心で外してしまいます。外された瞬間に、過去の金額は動き始めます。

## 🏃 描いてみよう

13-5-1で作った投稿アプリの概念モデルを、ER図に起こします。

### Step 1: 英語のテーブル名を確かめる

13-5-1では開かなかった `database/migrations/` を、ここで開きます。並んでいるファイルのうち、次の3つを見てください。

| ファイル | 見るところ |
|:---------|:-----------|
| `2014_10_12_000000_create_users_table.php` | `Schema::create()` の1つ目の引数 |
| `2024_01_01_000000_create_categories_table.php` | `Schema::create()` の1つ目の引数 |
| `2024_01_01_000001_create_posts_table.php` | `Schema::create()` の1つ目の引数と、`foreignId()` の行 |

`Schema::create()` の1つ目の引数が、そのテーブルの英語の名前です。`foreignId()` は、どのテーブルが、どのテーブルを指す列を持っているかを教えてくれます。

### Step 2: ER図を描く

「ER図の描き方」の手順1から4のとおりに進めます。13-5-1で作った関係の一覧に多対多の行が無いので、手順5は使いません。

線端の記号は、両端とも必ず付けてください。「多」の側を丸と三又にするか、丸の付いていない三又にするかは、投稿を1件も書いていないユーザーがあり得るかどうかで決まります。新規登録の直後を思い浮かべると、どちらかが決まります。

### Step 3: 3つの問いで点検する

「並べた属性を点検する」の3つの問いを、13-5-1で書いた属性にかけます。2つ目の問いは、主キーを `id` の1列にするので当てはまりません。1つ目と3つ目を確かめてください。このアプリでは、直すところは見つからないはずです。**直すところが無いことを確かめるのも点検です**。

### Step 4: 成果物を保存する

draw.ioで `post-er.drawio` の名前で保存し、PNGも `post-er.png` の名前で書き出します。書き出した2つのファイルは、13-1-3のとおりに `docs/13-5/` へ移します。

```bash
# アプリのフォルダの中で実行する
git add docs/13-5
git commit -m "13-5: 投稿アプリのER図を追加"
git push origin main
```

テーブル名とつながりの根拠は、マイグレーションにあります。

```php
// database/migrations/2024_01_01_000001_create_posts_table.php
Schema::create('posts', function (Blueprint $table) {
    $table->id();
    $table->foreignId('user_id')->constrained()->cascadeOnDelete();
    $table->foreignId('category_id')->constrained();
    $table->string('title');
    $table->text('content');
    $table->timestamps();
});
```

1行目の `'posts'` がテーブル名です。`foreignId('user_id')` と `foreignId('category_id')` の2行から、`posts` が `users` と `categories` の両方を指す列を持っていると読めます。相手を指す列を持つのが「多」の側なので、`posts` は2本の線のどちらでも「多」の側です。

関係の向きは、モデルにも書いてあります。

```php
// app/Models/User.php から抜粋
public function posts(): HasMany
{
    return $this->hasMany(Post::class);
}
```

```php
// app/Models/Post.php から抜粋
public function user(): BelongsTo
{
    return $this->belongsTo(User::class);
}

public function category(): BelongsTo
{
    return $this->belongsTo(Category::class);
}
```

`hasMany` が「複数を持つ」側、`belongsTo` が「1つに属する」側です。9-5-1で学んだこの2つが、図の記号の二重線と三又に対応しています。

次の観点で、自分の成果物と見比べてください。

- [ ] 四角が3つで、テーブル名が `users`・`categories`・`posts` になっている
- [ ] 線が2本で、`users` と `categories` の間に線が引かれていない
- [ ] どちらの線も、`posts` の側が「多」になっている
- [ ] 両方の線の両端に、記号が付いている（縦の二重線と、丸と三又）
- [ ] どの線にも、日本語の1文が添えてある
- [ ] 四角の中に、テーブル名以外のもの（カラム名や型）を書いていない
- [ ] 点検の問い（このアプリでは1つ目と3つ目）をかけて、直すところが無いことを確かめた
- [ ] `docs/13-5/` に `.drawio` とPNGの2つがあり、GitHub上でPNGが表示される

**迷いやすいところ**

- **「多」の側を、丸と三又にした理由**: 新規登録したばかりのユーザーは、投稿を1件も持っていません。カテゴリも、投稿が1件も付いていないものがあり得ます（このアプリの「雑記」がそうです）。0件があり得るので、丸の付いた記号を選びます。丸の付いていない三又は「1件以上」という意味になり、投稿を持たないユーザーを登録できない設計になります。
- **主キーと外部キーを図に書かなかった理由**: どちらのテーブルが外部キーを持つかは、線の「多」の側という形で、すでに図に出ているからです。
- **主キーを `id` にそろえる理由**: 8-1-6で紙にER図を描いたときは、`customer_id`・`order_id` のように、テーブル名を含んだ名前を主キーにしました。どちらの書き方も現場にありますが、この教材では、Laravelのアプリに合わせて `id` で通します。8-1-6の形で描いていた方も、間違いではありません。

## 💡 よくある間違いと現場での使われ方

**間違い1: 線に文だけ書いて、記号を付けない**

線の真ん中に「1対多」や日本語の1文だけを置いて終える間違いです。文は読む人のための補助で、ER図としてどちらが何件かを表しているのは記号のほうです。Tutorial 14でAIに図を描かせたときにも、返ってくるのはこの記号なので、読めるようにしておきます。

**間違い2: エンティティ一覧に無いテーブルを、図で増やす**

描きながら「このテーブルもあったほうがよさそうだ」と思いついて足してしまう間違いです。足すのなら、13-5-1のエンティティ一覧にも行を足します。図と表のどちらか片方だけを動かすと、次に開いたときにどちらが新しいのか分からなくなります。

**間違い3: 点検を飛ばす**

図が描けた時点で終わりにしてしまう間違いです。ここで見つかる直しは、エンティティの分け方に戻る大きめの直しになりますが、テーブルを作ってデータを入れたあとで直すよりは、はるかに軽く済みます。

現場では、テーブルが増えたら図も直す、という運用が守られているかどうかで、その設計書が生きているかどうかが分かります。

## ✨ まとめ

- ER図は、関係の一覧を1枚に置き直した図です。四角の数はエンティティ一覧の行数と、線の数は関係の一覧の行数と一致します。
- 四角の中に書くのはテーブル名だけです。線は向きを持たず、両端の記号で件数を表します。縦の二重線がちょうど1件、丸の付いた三又が0件以上、丸の付いていない三又が1件以上、縦線と丸が0件または1件です。
- draw.ioでは、線を選んで「スタイル」タブの端のボタンを押すと、ER図用の記号を選べます。記号と、日本語の1文の両方を付けます。
- 多対多は、つなぎ役の四角を1つ置いて、2本の1対多に分けて描きます。この四角は、エンティティ一覧に行がなくてもテーブルとしては必要です。
- 属性は3つの問いで点検します。通らなかったところは、エンティティの分け方に戻って直します。この観点は、13-5-5のセルフチェックでもう一度使います。
- 申し込んだ時点の金額のように、あとから動いてほしくないものは、正規化の考え方を崩してでも持ちます。崩したときは、崩した理由を必ず書き残します。
