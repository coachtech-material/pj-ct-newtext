# 13-5-4: CRUD表

## 🎯 このセクションで学ぶこと

- 機能一覧とエンティティ一覧を突き合わせて、CRUD表を作れるようになる。
- 表を縦に読んで、決めていないことを見つけられるようになる。
- 見つけた穴を、自分で埋めずに確認事項リストへ送れるようになる。

---

## 導入：データ側だけを見て、設計が仕上がってしまう

ER図もテーブル定義書も、Chapter 2で作った機能一覧を1度も開かずに書き上げられます。仕様書から名詞を拾い、つながりを決めて、型を決める。この道筋のどこにも、「その機能はどのデータに触るのか」を確かめる場面がありません。

そのため、覚えておく場所はあるのに、そこへ書き込む機能がどこにも無い、という設計ができあがります。気づくのは、実装が始まって「この商品を登録する画面はどこですか」と聞かれたときです。

**CRUD表**（どの機能が、どのデータを作り・読み・書き換え・消すかを表にしたもの）は、その質問を実装の前に出させるための表です。

---

## CRUD表の読み方

料理教室の受講管理アプリの機能一覧が、次の6行だとします。

| ID | 機能 | 主な利用者 |
|:---|:-----|:-----------|
| F-01 | レッスンの閲覧 | 受講者 |
| F-02 | レッスンの申し込み | 受講者 |
| F-03 | 申し込みの取り消し | 受講者 |
| F-04 | レッスンの登録 | 講師 |
| F-05 | 受講者の登録 | 受講者 |
| F-06 | 講師の登録 | 講師 |

この6行と、13-5-1で作ったエンティティ一覧の4行を突き合わせたのが、CRUD表です。

| 機能 | 講師 | レッスン | 受講者 | 申し込み |
|:-----|:-----|:---------|:-------|:---------|
| F-01 レッスンの閲覧 | R | R | - | - |
| F-02 レッスンの申し込み | - | R | R | C |
| F-03 申し込みの取り消し | - | - | - | D |
| F-04 レッスンの登録 | R | C | - | - |
| F-05 受講者の登録 | - | - | C | - |
| F-06 講師の登録 | C | - | - | - |

マスに書いてある4つの文字は、そのデータを**作る**のがC、**読む**のがR、**書き換える**のがU、**消す**のがDです。1つのマスに2つ以上入るときは、`R・U` のように中黒で並べます。触らないところは空けずに `-` と書きます。

Rをどこまで数えるかだけ、先に決めておきます。書き換えるにも消すにも、そのデータの1件を先に探す読みが必ず入ります。🔑 **相手を探すためだけの読みは、Rに数えません**。UやDと書いた時点で、その読みも含まれているものとして扱います。Rを書くのは、画面に出すため、受け付けてよいかを判断するため、作るデータに結び付ける相手を確かめるため、といった読みです。F-03の「申し込み」がDだけなのは、消す1件を探しているだけだからで、F-02の「受講者」がRなのは、どなたの申し込みかを確かめて、作る申し込みに結び付けるからです。

横に読むと、その機能がどのデータに触るのかが分かります。F-01の行なら、レッスンを読むだけでなく講師も読んでいます。一覧に担当する講師の名前を出すからです。この1行が読めれば、実装する人は「この画面を出すために、どのテーブルを見ればよいか」を迷いません。

縦に読むと、そのデータが誰にどう扱われるのかが分かります。🔑 **CRUD表の値打ちは、こちらの向きにあります**。見るのは、空いているところです。

| 空き方 | 疑うこと |
|:-------|:---------|
| Cが1つも無い列 | そのデータを作る機能が、どこにも無い |
| Rが1つも無い列で、Cも無い | 覚えておく必要が、本当にあるのか |
| Rが1つも無い列で、Cはある | 書き込む前に中身を確かめる機能が、抜けていないか |
| UもDも無い列 | 一度入れたら、二度と直せないデータになる |
| 行のマスが全部 `-` | その機能はデータを触らない。おかしくはないが、本当かを確かめる |

この見方を、上の表に当てはめます。「講師」「レッスン」「受講者」の3つの列には、UもDもありません。講師の名前を書き間違えても直せず、開かなくなったレッスンも残り続けます。どうするつもりなのかを、依頼者に確かめる場所です。

見つけにくいのは、「申し込み」の列のほうです。F-02にC、F-03にDはありますが、Rが1つもありません。Cはあるのに、同じ列にRが無い形です。申し込みを受け付けるとき、定員に達しているかどうかを確かめるには、**すでに入っている申し込みを読む必要がある**のに、それが表に出ていません。この相談は「定員を超えて受け付けてしまう」ことから始まっていました。いちばん困っていた場所が、表の1マスとして抜けていたことになります。

## CRUD表の書き方

**手順1: 行に機能を並べる**

Chapter 2で作った機能一覧の機能名を、IDごとそのまま写します（`F-01 レッスンの閲覧` の形）。動詞に直しません。13-4-2で権限マトリクスを作ったときと同じ書き方です。

**手順2: 列にデータを並べる**

13-5-1のエンティティ一覧の行を、**日本語のまま**列にします。英語のテーブル名にしません。行に並ぶ機能名が日本語なので、突き合わせる相手も日本語にそろえます。

13-5-2でつなぎ役として置いた四角があれば、それも列にします。「投稿とタグの組」のような呼び方で構いません。つなぎ役のテーブルも、作る・消すの対象になるデータです。

**手順3: マスを埋める**

機能を1つずつ頭の中で動かして、触るデータにC・R・U・Dを書きます。読み方で決めたとおり、相手を探すためだけの読みはRに数えません。ユースケース記述を書いてあるものは、基本フローを上からたどると数え落としが減ります。

**手順4: 縦に読んで、空を探す**

読み方で見た空き方の表を、列ごとに当てはめます。ここで見つかったものは、**勝手に機能を足して埋めません**。13-2-1で学んだとおり、想定を添えて確認事項リストへ送ります。CRUD表は、間違いを見つける表ではなく、決めていないことを見つける表です。

## 🏃 書いてみよう

投稿アプリのCRUD表を作ります。ここまでの3つの節で作った概念モデル・ER図・テーブル定義書に、初めて機能一覧を突き合わせます。

### Step 1: 機能一覧を用意する

13-2-1で、このアプリの機能一覧を作りました。`docs/13-2/` にあるファイルを開いて、その行をそのまま使ってください。手元に無い方は、13-2-1の解答例と同じ次の6行を使って構いません。

| ID | 機能 | 主な利用者 |
|:---|:-----|:-----------|
| F-01 | ユーザー登録 | 訪問者 |
| F-02 | ログイン | 訪問者 |
| F-03 | ログアウト | ログイン済み利用者 |
| F-04 | 投稿の一覧表示 | ログイン済み利用者 |
| F-05 | 投稿の編集 | ログイン済み利用者（自分の投稿のみ） |
| F-06 | 投稿の削除 | ログイン済み利用者（自分の投稿のみ） |

### Step 2: CRUD表を作る

列は、13-5-1で作ったエンティティ一覧の3行（ユーザー・カテゴリ・投稿）です。日本語のままにします。

マスを埋めるときの手がかりは、コントローラーにあります。`app/Http/Controllers/PostController.php` の4つのメソッドを開いて、どのモデルを呼び、どのモデルを画面へ渡しているかを見てください。ユーザー登録・ログイン・ログアウトの処理はこのファイルにありませんが、それぞれ何と照合し、何を作るのかを考えれば、触るデータは決まります。

### Step 3: 縦に読んで、空を探す

「読み方」の空き方の表を、3つの列に当てはめます。このアプリでは、2つの列に目立つ空き方が出て、もう1つ、マスが全部 `-` になる行も出ます。それがどういう状態を表しているのかを、**表の下に2〜3文で書いてください**。これが今回いちばん考えてほしいところです。

### Step 4: 成果物を保存する

VS Codeで `docs/13-5/post-crud.md` を新しく作り、Step 1の機能一覧を先頭に、Step 2の表とStep 3の文を続けます。

```bash
# アプリのフォルダの中で実行する
git add docs/13-5
git commit -m "13-5: 投稿アプリのCRUD表を追加"
git push origin main
```

**CRUD表（解答例）**

F-04でユーザーとカテゴリをRにしている根拠は、一覧を組み立てているこの1行です。

```php
// app/Http/Controllers/PostController.php の index() から抜粋
$posts = Post::with(['user', 'category'])->latest()->get();
```

`with(['user', 'category'])` と書かれているとおり、投稿と一緒にユーザーとカテゴリも読んでいます。画面には投稿者の名前とカテゴリの名前が出るので、9-5-3「Eager Loadingとレイジーローディング」で学んだこの書き方で、まとめて取ってきています。

F-05で投稿とカテゴリの両方をRにしている根拠は、編集画面を出す `edit()` です。

```php
// app/Http/Controllers/PostController.php の edit() から抜粋
public function edit(Post $post)
{
    // ...
    $categories = Category::orderBy('id')->get();

    return view('posts.edit', compact('post', 'categories'));
}
```

カテゴリを全件読んでいるのは、プルダウンに選択肢を並べるためです。投稿のほうも、いま入っているタイトルと本文を編集画面に映すために、`view()` へ渡しています。どちらも画面に出すための読みなので、Rに数えます。書き換える相手を探すためだけの読みではありません。

**表の下に書く2〜3文（解答例）**

> 「投稿」の列にはR・U・Dがそろっているのに、Cがありません。投稿を書く機能が、このアプリには無いということです。「カテゴリ」の列はRだけで、カテゴリを登録する機能も、名前を直す機能もありません。どちらも、あらかじめ入れておいたデータを読むだけになっています。F-03の行は、マスが全部 `-` です。ログアウトは、覚えておくデータに触らない機能ということになります。

- [ ] 機能一覧の行が、すべてCRUD表の行になっている
- [ ] 列が3つで、列名が日本語（ユーザー・カテゴリ・投稿）になっている
- [ ] 空のマスがない（触らないところは `-` と書かれている）
- [ ] 投稿の列にCが無いことに気づいている
- [ ] カテゴリの列にRしか無いことに気づいている

- [ ] 気づいた穴を埋めるために、機能一覧に行を足していない

**迷いやすいところ**

**投稿にCが無いのが、間違いではない理由**

`routes/web.php` の投稿に関するルートは、一覧・編集画面・更新・削除の4本だけです。投稿を作るルートがありません。表示されている4件は、`database/seeders/DatabaseSeeder.php` があらかじめ入れたものです。このアプリは認可（Policy）の練習のために配られたもので、作る機能を省くと最初から決まっていました。CRUD表は間違い探しの表ではないので、Cが無いこと自体は問題になりません。実際の仕事でこの表を作れば、「投稿を書く画面はどこですか」という質問が、実装が始まる前に1回で出てきます。それが目的です。

**カテゴリにRしか無い理由**

カテゴリを入れているのもシーダーです。

```php
// database/seeders/DatabaseSeeder.php から抜粋
$notice = Category::create(['name' => 'お知らせ']);
$techNote = Category::create(['name' => '技術メモ']);
Category::create(['name' => '雑記']);
```

3件を用意して、あとは選ばせるだけの作りです。13-2-1の🏃では、これを「カテゴリはあらかじめ用意されたものから選ぶ想定」として確認事項リストに送りました。CRUD表の空き方が、そこで書いた想定と一致しています。縦に読んだ結果が前の章で送った確認事項と合っているかを見るのも、この表の**使い方の1つ**です。

**F-05のユーザーを `-` にした理由**

編集してよい人かどうかは、`PostPolicy` が決めています。

```php
// app/Policies/PostPolicy.php から抜粋
public function update(User $user, Post $post): bool
{
    return $user->id === $post->user_id;
}
```

比べているのは、ログイン中の人のIDと、投稿が持っている `user_id` です。ユーザーの表を読み直してはいないので、`-` にしました。ログイン中の人の情報を読んでいる、と考えてRを書いても間違いではありません。どちらで数えたかを表の下に1行書いておけば、読む人が迷いません。

**ログアウトの行が、全部 `-` になる理由**

ログアウトは、ログインしている状態を終わらせる操作です。10-1-4「ログイン・ログアウト機能を理解する」で学んだとおり、その状態はセッションが持っていて、`users` や `posts` の中身は動きません。読み方の空き方の表では、いちばん下の「行のマスが全部 `-`」に当たります。おかしくはありませんが、本当に何も残さなくてよいかは確かめる場所です。誰がいつログアウトしたのかを記録する要求があれば、行が動きます。

機能一覧にログインとログアウトを入れていなければ、CRUD表の行は4行になります。そのときは、ユーザーの列にRが1つも付かず、「Cはあるのに、同じ列にRが無い」という別の空き方に見えます。機能一覧の作り方が、CRUD表の読み取りに効いてくる例です。

## 💡 よくある間違いと現場での使われ方

**間違い1: 行を、画面の名前で並べる**

「投稿一覧画面」「投稿編集画面」を行にしてしまう間違いです。13-4-2で権限マトリクスについて学んだのと同じで、行は機能一覧から写します。画面を行にすると、1つの機能が複数の画面に散らばったときに、同じ内容を2か所に書くことになります。

**間違い2: 見つけた穴を、その場で埋める**

Cが無い列を見つけて、機能一覧に「投稿の作成」を足してしまう間違いです。足した瞬間に、作る量が増え、画面もエンドポイントも要ることになります。依頼者に確かめずに増やしてよいものではありません。

現場では、CRUD表は設計が一通りそろった時点の点検に使われます。図と表が増えてきたところで、いちど機能の側から見直すための1枚です。

## ✨ まとめ

- CRUD表は、行に機能一覧、列に日本語のエンティティ名を並べ、C・R・U・Dと `-` で埋めます。つなぎ役のテーブルも列にします。
- 相手を探すためだけの読みは、Rに数えません。UやDを書いた時点で、その読みは含まれています。
- 横に読むと、その機能が触るテーブルが分かります。実装する人が最初に見る向きです。
- 縦に読むと、決めていないことが出てきます。Cが無い列、Rが無い列、UもDも無い列を探します。
- 見つかった穴は、機能を足して埋めません。想定を添えて確認事項リストへ送ります。
