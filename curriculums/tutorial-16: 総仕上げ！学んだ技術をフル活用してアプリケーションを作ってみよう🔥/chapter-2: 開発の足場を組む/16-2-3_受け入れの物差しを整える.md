# 16-2-3: 受け入れの物差しを整える

## 🎯 このセクションで学ぶこと

- 命名・重複・読みやすさを、届いた差分を受け取るときの観点として、このアプリの言葉で言えるようになる。
- その観点を `/review-diff` と `CLAUDE.md` に置いて、毎回の受け取りで効くようにできるようになる。
- Laravel Pintで整形を機械に任せ、フックに組み込めるようになる。

---

## 導入

これから7本ぶんのコードが、自分が書いていない形で届きます。テストが通っていて、受け入れ条件も満たしている差分を前にして、それでも直させるかどうかを決める場面が必ず来ます。そのときの物差しを、コードが1行も無いいまのうちに決めておきます。

---

## 受け取るときに見るもの

命名・可読性・DRY（同じことを2か所に書かない）は、12-3-4と12-3-5のレビューのチェックリストに、確かめる項目として並んでいました。ここから先は、この項目を7本ぶんの差分に当てていくことになります。項目の名前のままでは判定が割れるので、このアプリで何を見るかまで落とします。

名前の慣例は、13-7-2で「Tutorial 16」と送りにしていたところです。Laravelの場合は次のとおりで、この形から外れていると、フレームワークが自動でつないでくれる部分が効かなくなります。

| 何 | 付け方 | 例 |
|:--|:--|:--|
| モデル | 単数 | `Channel` |
| テーブル | 複数 | `channels` |
| 中間テーブル | 2つのテーブル名を単数にして、アルファベット順につなぐ | `channel_user` |
| コントローラ | `<モデル名>Controller` | `ChannelController` |
| ポリシー | `<モデル名>Policy` | `ChannelPolicy` |

重複の観点で最初に見るのは、権限の判定です。このアプリの「そのチャンネルを見てよい人か」という条件は、画面では1件を開いてよいかの判定として、検索では結果を絞り込む条件として使われます。形は違っても、中身は同じ条件です。それがポリシーとコントローラの両方に書かれていたら、片方だけ直したときに穴が開きます。

読みやすさは好みの話に見えますが、判定できる形に落とせます。当てはまらない場合を先に返してから本筋を書く形になっていれば、条件が深く入れ子にならず、あとから読む人が分岐を追えます。

最後の1つは、このアプリだから要る観点です。画面・テーブル・エンドポイントの呼び名が、`docs/design/` と揃っているかを見ます。実装だけで名前が変わると、受け入れ条件も設計書も、どれのことを言っているのかが読み取れなくなります。

## 🏃 観点を道具に持たせる

思いどおりに直らない・壊れたと感じたら、14-5-1（直らないときの型）へ。応急は `git restore .` です。

### Step 1: `/review-diff` に観点を足す

16-2-2で移した `/review-diff` は、読む順番と、危ないところを見る観点（N+1・認可の置き場所・入力チェックなど）を持っています。足りないのは、このアプリの決めごとに沿って受け取ってよいかを判定する物差しです。`.claude/skills/review-diff/SKILL.md` に節を1つ足します。

```markdown
## 受け取ってよいかを決める観点

3段目で中身を読むときは、次の4つも見ます。直すのではなく、直したほうがよい場所として報告します。

- **名前**: Laravelの慣例どおりか（モデルは単数 `Channel`、テーブルは複数 `channels`、中間テーブルは単数のアルファベット順 `channel_user`、コントローラは `ChannelController`、ポリシーは `ChannelPolicy`）。変数やメソッドの名前が中身と合っているか（読んで何のことか分からない名前が無いか）
- **重複**: 同じ判断や同じ問い合わせが2か所以上に写っていないか（権限の判定はポリシーに1か所、共通の見た目は1か所）。**逆に、似ているだけのものを無理にまとめていないか**も見る
- **読みやすさ**: ネストが深くないか（当てはまらない場合を先に返す形になっているか）、1つのメソッドが長すぎないか、コレクションのメソッドで書ける繰り返しが手書きのループになっていないか
- **設計書の言葉**: 画面・テーブル・エンドポイントの呼び名が `docs/design/` と一致しているか（設計書と実物で名前が割れていないか）

**整形の揺れとテストの合否は見ません。** そこは編集のたびにフックが機械で片づけます。人が見るのは、この観点と上の3段です。
```

最後の1行が、この節でいちばん効きます。書いてあるものを見に行くのがSkillなので、機械が片づけるものまで書くと、その報告を毎回人が読むことになります。

### Step 2: `CLAUDE.md` に「守ってほしい書き方」を足す

`/review-diff` は差分が届いてから走ります。書く前から効かせたいものは `CLAUDE.md` に置きます。

```markdown
## 守ってほしい書き方

- 名前は Laravel の慣例に合わせる（モデルは単数・テーブルは複数・中間テーブルは単数のアルファベット順・コントローラは `<モデル名>Controller`）。
- 同じ判断を2か所に書かない。権限の判定はポリシーに1か所だけ置く。
- ネストを深くしない。当てはまらない場合を先に返してから、本筋を書く。
- 整形は Laravel Pint に任せる（`./vendor/bin/sail pint`）。見た目を手で揃えない。
- **JavaScript は使わない**（`docs/design/questions.md` の決めごと）。文字数の表示・その場編集・削除の確認は、画面を開き直す形で作る。
```

最後の1行は、16-1-3で決めたことです。決めごとの中身は設計書にあるので、ここには在りかだけを書いて、理由は写しません。それでもこの1行を置くのは、AIが放っておくと真っ先に破る決めだからです。画面に少し動きを付けたいだけで、JavaScriptの数行が混ざります。

## Laravel Pint

Pintは、PHPのコードの見た目を決まった形に揃える道具です。インデントの幅、`array()` と `[]` のどちらを使うか、クラスの `{` を同じ行に置くか次の行に置くか。こうしたものを、打つだけで全部揃えます。

見た目の揺れは、AIに書かせると必ず出ます。同じセッションの中でも、依頼を分けるたびに少しずつ違う書き方が返ってきます。人が指摘して直させると、そのやり取りに時間を使ったうえに、次の差分でまた揺れます。**機械で揃うものは、機械に揃えさせます。**

このリポジトリでは、導入は要りません。Laravelの `composer.json` の `require-dev`（開発中だけ使う道具の欄）に最初から入っています（2026年8月時点）。設定ファイルも置いていないので、判定に使われるのはPintの既定です。

### Step 3: 打ってみる

```bash
# 自分のリポジトリのフォルダで実行する
./vendor/bin/sail pint --test
```

`--test` を付けると、直さずに「直すところがあるか」だけを見ます。いまの状態では、直すところは出てきません。素のLaravelは、はじめから既定の形で書かれているからです。

`--test` を外して打つと、直すところがあれば実際に書き換わり、直したファイルと直した項目が結果に出ます。

### Step 4: フックに整形を足す

15-4-3の最後に、整形の自動化はTutorial 16で同じやり方で足せる、と書いてありました。同じ `hooks` の中に、コマンドをもう1本並べます。**`.claude/settings.json`** のフックの部分は、こうなります。

```json
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "./vendor/bin/sail pint >&2"
          },
          {
            "type": "command",
            "command": "./vendor/bin/sail artisan test >&2 || exit 2"
          }
        ]
      }
    ]
  }
```

テストの行は1文字も触りません。並べた2本には、役割の違いがあります。整形の行に `|| exit 2` を付けていないのは、Pintが直したあと正常に終わるからです。門はテストの行が持ち、整形は黙って直すだけ、という分担です。

`allow` にも2行足しておきます。AIが自分で `sail pint` を打つ場面があるためです。フックはこの指定を通らないので、門の効き方は変わりません。

```json
      "Bash(./vendor/bin/sail pint *)",
      "Bash(sail pint *)"
```

書き換えたのは `.claude/settings.json` なので、ここでも `/exit` で一度閉じて、起動し直します。設定が読まれるのは起動のときです（15-4-1）。

```bash
claude
```

開き直したら、崩れたコードを1つ用意して確かめます。`array( 1,2,3 )` のように空白と書き方をわざと崩したPHPのファイルを1枚置き、Claude Codeにコメントを1行だけ足させてください。編集の直後に整形が走り、`array( 1,2,3 )` が `[1, 2, 3]` に変わります。確かめ終わったら、そのファイルは消します。

> 💡 **TIP**: 「それ以外は何も変えないで」と頼んだのに整形が入ると、AIが「私が意図的に行ったものではありません」と断りを入れてくることがあります。フックが機械でやったことなので、そのまま進めて構いません。

> 💡 **TIP**: 整形の機械は融通が利きません。日本語で書いたテストの名前の中に英単語が混ざっていると、単語の途中で区切りを入れて `GET` を `ge_t` のように割ることがあります。テストの名前が読みにくく変わっていたら、これです。

### Step 5: コミットする

```text
.claude/ と CLAUDE.md の変更をコミットしてください。
```

ここも `main` に直接記録します。観点も整形の仕掛けも、どのイシューにも属さない共有物だからです（16-2-2と同じ理由）。

- [ ] `/review-diff` のSKILL.mdに、受け取ってよいかを決める観点の節がある

## 機械が決めるもの、人が決めるもの

物差しの置き場所が分かれました。

| 誰が判定するか | 何を | どこで効くか |
|:--|:--|:--|
| 機械 | 整形の揺れ、テストの合否 | 編集のたびにフックが走る |
| 人 | 設計書との一致、名前、重複、読みやすさ | 差分が届いたときに `/review-diff` と自分の目で読む |

左の列は、判定が揺れません。同じコードなら誰が打っても同じ結果になり、直し方も決まっています。右の列は、このアプリの決めごとを知っている人にしか判定できません。だから、左は仕掛けに任せ切り、右に自分の時間を使います。

---

## ✨ まとめ

- 命名・重複・読みやすさは、届いた差分を受け取るときの観点です。項目の名前で置いておかず、このアプリで何を見るかまで落とします。
- 観点は2か所に置きます。届いた差分に当てるものは `/review-diff`、書かせる前に渡すものは `CLAUDE.md` です。
- Pintは同梱されているので、導入は要りません。打てば既定の形に揃います。
- フックには整形とテストを並べます。門を持つのはテストの行だけで、整形は黙って直します。
- 機械が判定できるものは機械に渡し切ります。人が読むのは、このアプリの決めごとを知らないと判定できないところだけです。
