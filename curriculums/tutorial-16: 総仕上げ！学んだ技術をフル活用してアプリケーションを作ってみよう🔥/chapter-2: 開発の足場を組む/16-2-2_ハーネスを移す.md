# 16-2-2: ハーネスを移す

## 🎯 このセクションで学ぶこと

- 前のアプリで組んだハーネスのうち、運ぶものと作り直すものを分けられるようになる。
- コピーした部品から、前のアプリでしか通じない言葉を自分で見つけて書き換えられるようになる。
- 許可の指定とフックを新しいリポジトリに置いて、効いていることを確かめられるようになる。

---

## 導入

いまのリポジトリでClaude Codeを起動すると、読まれるのは `CLAUDE.md` の1枚だけです。テストの決まりも、差分の読み方も、UATの手順も、前のアプリのフォルダの中に置いたままです。このまま7本の機能を回すと、Tutorial 15を始める前と同じで、毎回同じことを打ち直すことになります。

この一式が、15-1-2でハーネスと呼んだ棚です。16-1-1でChapter 2の作るものに挙げた「開発の足場」が、これに当たります。

15-5-4の「置いた道具は、次に自分が触るプロジェクトでも、同じ手順で作れます」を、ここで実際にやります。ただし、ゼロから作り直すのは半分だけです。

---

## 運ぶものと、作り直すもの

ハーネスの部品は、中身がプロジェクトにどれだけ縛られているかで扱いが変わります。

| 部品 | このアプリでどうするか |
|:--|:--|
| `CLAUDE.md` | 作り直す（16-2-1で済み）。書いてあるのはこのリポジトリの前提そのもので、運べる行はごくわずか |
| 許可の指定（`.claude/settings.json` の `permissions`） | 書き起こす。止めたいものがこのアプリで増える |
| フック（同じファイルの `hooks`） | 逐語で運ぶ。テストを回す仕掛けはアプリが変わっても同じ |
| ルール（`.claude/rules/testing.md`） | 運んで、1行だけ差し替える |
| Skill 3本（`/review-diff`・`/uat`・`/issue`） | 運んで、固有の物差しを差し替える |
| Playwright MCP | 作業なし。手元のClaude Codeに入っているので、リポジトリには何も増えない（14-4-4） |

差し替えるのは、**そのアプリの固有の決めごとを指している部分だけ**です。読む順番も、報告のしかたも、聞き返す作法も触りません。公式が持つのは汎用の部分、自作が持つのは固有の決めごと、という15-3-1の線が、持ち運ぶ場面で形になります。

> 💡 **TIP**: この教材では `/review-diff`・`/uat`・`/issue` の名前で書きます。15-3-1のとおり名前を決めるのは自分なので、別の名前を付けていた人は、以降そちらに読み替えてください。

---

## 🏃 コピーしてから、差し替える

2段に分けます。先に中身を変えずにコピーして、そのあとで差し替えます。一度に済ませると、何が前のアプリの言葉だったのかが残りません。

思いどおりに直らない・壊れたと感じたら、14-5-1（直らないときの型）へ。応急は `git restore .` です。

### Step 1: そのままコピーする

先に、運ぶ元に何が入っているかを見ておきます。`rules` と `skills` の2つのフォルダが並んでいれば、そのままコピーできます。

```bash
ls ~/laravel-practice/post-app-practice/.claude/
```

```bash
# 自分のリポジトリのフォルダで実行する
mkdir -p .claude
cp -r ~/laravel-practice/post-app-practice/.claude/rules .claude/rules
cp -r ~/laravel-practice/post-app-practice/.claude/skills .claude/skills
```

運ぶのはこの2つです。`.claude/` の中にほかにも自分で作ったものがあれば、それは要るようになってから運びます。許可の指定とフックは Step 4 で書き起こすので、`settings.json` はコピーしません。

### Step 2: 素で読んで、前のアプリの言葉を見つける

コピーした4枚を上から読んで、**前のアプリのことしか指していない言葉**に印を付けてください。差し替えるのは自分なので、まず自分で見つけます。

- `.claude/rules/testing.md`
- `.claude/skills/review-diff/SKILL.md`
- `.claude/skills/uat/SKILL.md`
- `.claude/skills/issue/SKILL.md`

探し方の当たりは、固有名詞です。ファイルのパス、クラスの名前、メールアドレス、テストの名前。どれも、このリポジトリには存在しません。

見つけたら、下の表と突き合わせてください。

| ファイル | 前のアプリを指している言葉 | このアプリでは |
|:--|:--|:--|
| `rules/testing.md` | `--filter ReplyTest` | `--filter ChannelTest` |
| `review-diff` | 突き合わせ先の `docs/reply.md` | `docs/design/` の設計書一式 |
| `review-diff` | 触っていないはずの場所の `PostController.php`・`PostPolicy.php`・`posts/index.blade.php` | このアプリで全機能が共有する場所 |
| `uat` | ログイン情報の `usera@example.com`・`userb@example.com` | 仕様書が決めている3つのアカウント |
| `issue` | 設計書を探す先の `docs/` | `docs/design/` |

`ChannelTest` は、これから作るテストの名前の見本です。このリポジトリにはまだテストが1本もないので、いま実在しなくて構いません。1クラスだけ回すときの書き方を示す行です。

**印を付けたのに、差し替えないものが1つあります。** `/issue` の中の受け入れ条件の見本4行（ポストとリプライの4行）です。16-1-6で判定に使った粒度の見本と同じ4行なので、このアプリでもそのまま残します。代わりに、設計書に受け入れ条件があるならそこから写す、という1行を Step 3 で足します。

### Step 3: 固有の物差しを差し替える

書き換えは自分で打っても、Claude Codeに頼んでも構いません。差し替えたあとの差分は、次のようになります。

> 💡 **進行例について**: AIとの開発は毎回違う流れになります。ここに示すのは一つの進行例です。あなたの画面と違っていても、チェックリストを満たしていれば正解です。

```diff
--- a/.claude/rules/testing.md
-- テストを1クラスだけ回すときは `./vendor/bin/sail test --filter ReplyTest` の形で回す。
+- テストを1クラスだけ回すときは `./vendor/bin/sail test --filter ChannelTest` の形で回す。
```

```diff
--- a/.claude/skills/review-diff/SKILL.md
-1. `docs/` にあるその機能の設計書（リプライ機能なら `docs/reply.md`）と突き合わせる。書いていないものが増えていないか（`composer.json` に注意）
-   - 設計書が無い機能のときは、そのイシューに書いた受け入れ条件を突き合わせ先にする。
-2. 触っていないはずの場所を見る。`routes/web.php`・`app/Http/Controllers/PostController.php`・`app/Policies/PostPolicy.php`・`resources/views/posts/index.blade.php` の4つ。消えた行から先に
+1. `docs/design/` の設計書一式と突き合わせる。そのイシューの受け入れ条件は `docs/design/acceptance.md`、画面は `screens.md`、テーブルは `data.md`、権限とAPIは `permissions-api.md` にある。書いていないものが増えていないか（`composer.json` に注意）
+   - 設計書に書いていないことが実装されていたら、コードと設計書のどちらが正かを人に聞き返す。勝手にどちらかへ寄せない。
+2. 触っていないはずの場所を見る。`routes/web.php`・`routes/api.php`・`app/Policies/`・`database/migrations/`・`config/` の5つ。消えた行から先に
```

```diff
--- a/.claude/skills/uat/SKILL.md
+このアプリの受け入れ条件は `docs/design/acceptance.md` にあります。イシューの番号や
+機能の名前（認証・チャンネル・メンバー管理・メッセージ・スレッド・検索・公開API）だけを
+渡されたときは、このファイルからその機能の行を読んで対象にします。
+試す前に、同じファイルの「1. 試す前の準備」も読んでください。

-- `usera@example.com` / `password`
-- `userb@example.com` / `password`
+- `sato@example.com` / `password`（佐藤 太郎。「開発」と「採用プロジェクト」を作った人）
+- `suzuki@example.com` / `password`（鈴木 花子。「採用プロジェクト」のメンバー）
+- `takahashi@example.com` / `password`（高橋 健。**「採用プロジェクト」のメンバーではない人**）

-他人のものは触れない、という条件を確かめるときは、2つのアカウントを行き来します。
+他人のものは触れない・見られないはずのものが見えない、という条件を確かめるときは、
+アカウントを行き来します。プライベートチャンネルの確認には高橋を使います。
```

```diff
--- a/.claude/skills/issue/SKILL.md
-1. 渡された要望を読み、いまのコード（`routes/`・`app/` と、`docs/` にある設計書）を見て、決めないといけないことが残っていないかを確かめます。
+1. 渡された要望を読み、いまのコード（`routes/`・`app/`）と `docs/design/` の設計書一式を見て、決めないといけないことが残っていないかを確かめます。
+   - その機能の受け入れ条件が `docs/design/acceptance.md` にすでにあるときは、**そこにある文言をそのまま写します**（言い換えない。設計書とイシューで文言を揃えるため）。
```

言い回しが違っても、指している先が同じなら構いません。差し替えのうち、値を入れ替えただけでないものを見ておきます。

`/review-diff` の2段目は、前のアプリでは実在するファイルを4つ名指ししていました。このリポジトリにはアプリのコードがまだ1行も無いので、同じ書き方ができません。代わりに、**これから必ずできて、しかも7本の機能が共有する場所**を挙げています。ここが荒れると、どのイシューにも影響します。

`/uat` のアカウントは、2人から3人に増えました。前のアプリで見ていたのは「他人のものは触れない」だけでしたが、このアプリにはプライベートチャンネルがあるので、**そもそも見えてはいけない人**という第3の立場が要ります。仕様書が決めた3人のうち、その役は高橋です。

`/issue` に足した1行は、設計書とイシューで受け入れ条件の文言を揃えるためのものです（理由は16-2-4）。

### Step 4: 許可の指定を書き起こす

`deny`・`ask`・`allow` の中身は15-4-1で設計したとおりですが、このアプリでは止めたいものが増えます。**`.claude/settings.json`** を新しく書きます。

```json
{
  "permissions": {
    "deny": [
      "Read(.env)",
      "Read(.env.*)",
      "Edit(.env)",
      "Edit(.env.*)",
      "Edit(docs/spec.md)",
      "Edit(mockup/**)"
    ],
    "ask": [
      "Bash(git push *)"
    ],
    "allow": [
      "Bash(./vendor/bin/sail test *)",
      "Bash(sail test *)",
      "Bash(./vendor/bin/sail artisan test *)",
      "Bash(sail artisan test *)"
    ]
  },
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "./vendor/bin/sail artisan test >&2 || exit 2"
          }
        ]
      }
    ]
  }
}
```

前のアプリから変えたところを見ておきます。

`deny` に `Edit(docs/spec.md)` と `Edit(mockup/**)` を足しました。仕様書と画面の見本は与えられたもので、こちらが書き換える対象ではありません。`CLAUDE.md` にも「変えない」と書いてありますが、あの1枚は判断の材料として渡されるだけです（14-1-3）。確実に止めたいものは、許可の指定で止めます。

`allow` には `sail artisan test` の形を足して、4行にしました。テストを打つコマンドは、決まり・フック・`CLAUDE.md` の3か所に出てきて、`sail test` と `sail artisan test` の2つの形に割れています。どちらで打っても止まらないように、両方を通します。

フックは前のアプリの1行をそのまま運びます。`matcher` が絞るのは操作の種類（`Edit`・`Write`）だけで（15-4-2）、書き換えたファイルの種類では絞られません。`README.md` を1枚直しただけでも、テストは全部回ります（15-5-3）。

> ⚠️ **注意**: JSONにコメントは書けません。`//` で始まる行が1行あるだけで、許可の指定もフックも丸ごと読まれなくなります（15-4-1）。

書けたら、`/exit` で一度閉じて、起動し直します。設定は起動のときに読まれるので（15-4-1）、開いたままのセッションでは、いま書いた指定もフックもまだ効いていません。

```bash
claude
```

### Step 5: 効いていることを確かめる

置いただけでは効いているか分かりません。止まるほうから確かめます。Claude Codeに、あえて止まる操作を頼みます。

```text
あえて Read ツールで .env を読もうとしてみて。
そのあと、あえて Edit ツールで docs/spec.md の1行目を書き換えようとしてみて。
```

どちらも同じ文面で止まります。

```text
File is in a directory that is denied by your permission settings.
```

ファイル1枚を名指しした指定でも `directory` と出ます。`mockup/**` のようなまとめての指定でも、返ってくる文面は同じです。`mockup/index.html` でも1回試して、そのあと `git status` で何も変わっていないことを見てください。

**`deny` に当たって止まったところ**

<img alt="16-2-2_1.png" src="">

フックのほうは、`/hooks` を開くと `PostToolUse` が1つ並んでいるかで見えます（15-4-3）。走っていることを画面で見たいなら、テキストファイルを1つ作らせてください。`.txt` を1枚作っただけでも、テストが全部回ります。通ったときは何も出ません（15-4-3）。確かめ終わったらそのファイルは消します。

`allow` に書いたものが聞かれずに通ることは、15-4-1で確かめました。ここは書き足すところまでです。

Playwright MCPは手元のClaude Codeに入っているので、このリポジトリでも打てば見えます。

```bash
claude mcp list
```

`playwright` の行が `✔ Connected` になっていれば、UATの道具はそのまま使えます（2026年8月時点）。14-4-4で `-s user` を付けて入れたので、リポジトリが変わっても入れ直しは要りません。

最後に、Skillが載っているかを見ます。`.claude/skills/` は、このリポジトリではいま初めてできたフォルダです。フォルダが無い状態で始めたセッションからは呼べませんが（15-3-1）、Step 4 の最後で開き直しているので、`/` を打てば3本が候補に並びます。

Skillを実際に当てるのは16-3-1からです。いまは差分も機能もないので、呼んでも見るものがありません。

### Step 6: コミットする

```text
.claude/ の中身をコミットしてください。
```

ここまでも `main` に直接記録します。ハーネスは、どのイシューにも属さない共有物です。

- [ ] `.claude/rules/testing.md` の `--filter` が `ChannelTest` になっている
- [ ] Skill 3本の中に、前のアプリのファイル名・メールアドレスが残っていない
- [ ] `.env`・`docs/spec.md`・`mockup/index.html` の3つで、`deny` の文面が出て止まった
- [ ] `/hooks` に `PostToolUse` が1つ並んでいる
- [ ] `claude mcp list` で `playwright` が `✔ Connected` になっている
- [ ] `/` を打つと、Skill 3本が候補に出る

## 💡 育ち切ったハーネスの実例

実務のリポジトリでは、この棚がもっと増えます。差分の読み手を観点ごとに分ける、リリースの手順を1本にまとめる、不具合の再現手順を型にする、環境を作り直す段取りを置く。どれも、その現場で何度も繰り返した作業に名前が付いたものです。

数が増えても、線の引き方は変わりません。汎用の作業は公式が同梱しているものを使い、自作の棚に置くのは、その現場でしか通じない固有の物差しだけです。

## ✨ まとめ

- 移すのは半分です。`CLAUDE.md` と許可の指定はプロジェクトごとに書き起こし、ルール・フック・Skillはコピーしてから固有の物差しだけを書き換えます。
- コピーと差し替えを2段に分けると、どこが前のアプリの言葉だったかが差分として残ります。
- 差し替えるのは、そのアプリの決めごとを指している部分だけです。読む順番・報告のしかた・受け入れ条件の粒度の見本は、そのまま使えます。
- `deny` は、`CLAUDE.md` に書くだけでは止まらないものを止めます。与えられた仕様書と画面の見本は、この指定で守ります。
- 効きの確認は、止まるほうから見ます。通っているときは、画面に何も出ません。
