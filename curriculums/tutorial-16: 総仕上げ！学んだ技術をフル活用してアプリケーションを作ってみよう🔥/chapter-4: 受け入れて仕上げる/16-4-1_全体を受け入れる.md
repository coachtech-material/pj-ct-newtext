# 16-4-1: 全体を受け入れる

## 🎯 このセクションで学ぶこと

- 機能ごとの受け取りでは見えないものが何かを、自分の言葉で言えるようになる。
- 設計書一式と実物を突き合わせ、見つかったズレをどちらに合わせるか件ごとに決められるようになる。
- 受け入れの結果を、リポジトリに残る記録の形にできるようになる。

---

## 導入

イシューは7本とも閉じ、1本ずつ受け入れ条件を潰し、差分も読み直してあります。それでも、まだ受け取っていないものが残っています。機能と機能の継ぎ目、端から端までの導線、前に作ったものが後の機能で壊れていないか。どれも、イシュー1本の中を見ているときには視界に入りません。

## 全体の受け入れ

全機能がそろったあとで、設計書一式と実物をもう一度、端から突き合わせる作業です。1本ずつの受け取りとは、見ている範囲が違います。

イシュー1本の受け取りでは、そのイシューの受け入れ条件と、そのイシューが触った差分だけを見ていました。この形では原理的に見えないものがあります。

| 何が見えないか | なぜ見えないか |
|:--|:--|
| 受け入れ条件を、上から順に続けて通したときにだけ出るもの | 1行ずつ試すときは、毎回きれいな初期データから始めています。続けて通すのは、全部そろってからしかできません |
| どのプルリクエストの差分にも出てこないファイル | 差分を読む受け取りは、変わった行だけを見ます。誰も触らなかったファイルは、視野に入りません |
| 最初から混ざっていたもの | 1本目からずっと同じ数の中に混ざっています。混ざったまま数えているので、数字を見ても気づきません |

### 差分を読む物差しが見られないもの

`/review-diff`（15-3-2）は、プルリクエストの番号を渡すと `gh pr diff` で差分を出し、そこを決めた順番で読みます。物差しとしては効きますが、**差分に出てこないファイルは、何回当てても出てきません。**

この形で最後まで作り切ったとき、実際に古いまま残っていた例です。

- `docs/design/README.md`。設計書一式の入口にあたる1枚が、出発点のリポジトリのまま「このフォルダに、あなたが作る設計書を置きます。いまは空です」と書いてありました。中には設計書が7つ入っています
- `CLAUDE.md`。このリポジトリが何なのかを説明する行が「アプリの機能のコードはまだ1行も無い」のまま残っていました。これは**AIに毎回渡している1枚**なので、7本目を作っているあいだじゅう、AIはこれから作るつもりで読んでいたことになります

どちらのファイルも、ここまでのプルリクエストのどれも触っていません。だから差分には1行も出ず、`/review-diff` を何回当てても出てきません。捕まえる手は1つだけで、**全部できあがったあとに、リポジトリを入口から読み直す**ことです。この段を、下の Step 4 に置いてあります。

## 🏃 全体を突き合わせる

思いどおりに直らない・壊れたと感じたら、14-5-1（直らないときの型）へ。応急は `git restore .` です。

始める前に、いまのリポジトリを引き渡しの状態に戻しておきます。

```bash
# 自分のリポジトリのフォルダで実行する
claude
```

```text
全体の受け入れに入ります。main を最新にしてから chore/handover というブランチを切って、
コンテナを起動して、初期データを入れ直してください（migrate:fresh --seed）。
```

この節は、7本ぶんの実物を横に並べて食い違いを探す作業です。判断が重い側なので、`/model` で選択画面を開いて `opus` を `s` キーで選んでおきます（16-1-1）。名前も付けます。

```text
/rename 16-4 全体の受け入れ
```

ブランチを1本切ってから始めます。ここから先で直すのは設計書と `CLAUDE.md` とREADMEで、どれもイシューに紐づきません。16-3-1で `CLAUDE.md` に書いた決まりでは、そういう直しは `chore/` のブランチに載せてプルリクエストで受け取る形でした。最後の1回だけ自分の決まりを外す理由はないので、そのとおりにします。Chapter 4の直しは全部このブランチに載せ、プルリクエストは16-4-2の Step 3 で1本だけ出します。

### Step 1: 作ると言ったものが、全部あるか

設計書一式の機能一覧とCRUD表を、実物と突き合わせます。読む量が多いので、集めるところはAIに回して、出てきた表を自分が読みます。

```text
docs/design/ の機能一覧とCRUD表が、いまの実物と合っているかを突き合わせてほしい。
「ここには何も無い」と書いてあるところと、「今回作らないもの」に挙げたものも含めて、
食い違いを表で出して。この段では、まだ直さないで。
```

渡すのは、何を突き合わせてほしいかだけです。どのコマンドを打ち、どのファイルを開けば分かるかは、向こうが決めます（16-2-3・16-3-3）。ここで手順まで書き添えると、書いた道しか通らなくなります。

CRUD表は、埋まっているところを総当たりしても時間が溶けるだけです。**表が「ここには何も無い」と主張しているところ**を確かめると速く終わります。メッセージの削除が更新（U）であって削除（D）ではないこと、ユーザーのテーブルの列に更新も削除も一度も現れないこと。ここが合っていれば、表は生きています。

「今回作らないもの」を言葉の一覧として書いてあると、その一覧がそのまま最後の検査になります。画面のファイルを横断して、通知・リアクション・未読・添付といった言葉が1つも出てこないことを確かめれば済みます。

### Step 2: 受け入れ条件を、全数で通す

受け入れ条件は、人が上から順に全部試すために書いたものでした（16-1-6）。ここで、初めてそのとおりに通します。

先に、人の導線で端から端まで一巡します。**アドレス欄に打つのは最初の1回だけ**にして、あとは画面の中のリンクとボタンだけで進んでください。ログインして、チャンネルを作り、書き込み、返信し、検索し、検索結果から該当のメッセージへ飛び、ログアウトするところまでです。受け入れ条件は初期データの上で試す形になっているので、**自分でその場で作ったチャンネル**で一巡すると、条件では確かめていない継ぎ目に手が届きます。

**端から端までの一巡**

<img alt="16-4-1_1.png" src="https://s3.ap-northeast-1.amazonaws.com/coachtech-lms-bucket-dev/curriculums/images/16-4-1_1.png">

そのうえで、受け入れ条件を1行ずつ潰します。ここで、1行ずつ試していたときには出なかったことが起きます。行が互いの前提を壊すのです。チャンネルを削除する行を通すと、そのチャンネルを開くところから始まる後ろの行が成り立ちません。メンバーを追加する行を通すと、「その人には見えない」を確かめる行が成り立ちません。

対処は2つで足ります。**順番を入れ替える**ことと、**途中で初期データを入れ直す**ことです。壊す行のあとに `migrate:fresh --seed`（10-5-2）を打ち、どこで入れ直したかを記録に残します。

人が通し終えたら、初期データを入れ直してから、同じ受け入れ条件を `/uat`（15-3-4）にも回させて、報告を読みます。渡すのは受け入れ条件そのものか、それが書いてあるファイルの場所です。

### Step 3: テストと整形を通す

```bash
# 自分のリポジトリのフォルダで実行する
./vendor/bin/sail artisan test
./vendor/bin/sail pint --test
```

`failed` が0で、整形も通ることを確かめます。`--test` は16-2-3で使った、書き換えずに見るだけの形です。機能ごとにテストが何件あるかを数えておくと、このあとの記録に書けます。数えるときに、自分が書いた覚えのないテストが混ざっていないかも見ます。素のLaravelに最初から入っている見本のテストが、1本そのまま残っていることがあります。

### Step 4: リポジトリを入口から読み直す

最後に、**誰も触らなかったファイル**を見に行きます。

初めてこのリポジトリを開いた人が読む順で開いてください。`README.md`、`CLAUDE.md`、そして設計書一式の入口にあたる `docs/design/README.md` です。どれも、書いてあることと実物が合っているかだけを見ます。

`README.md` は次の16-4-2で丸ごと書き直すので、ここでは残り2つを直します。

> 💡 **進行例について**: AIとの開発は毎回違う流れになります。ここに示すのは一つの進行例です。あなたの画面と違っていても、チェックリストを満たしていれば正解です。

実際にこの突き合わせで出たズレは6件でした。内訳は、上の3つの見えない形に、そのまま分かれています。右の列は、どの段で捕まえられるかです。

| # | 見つかったズレ | どの段で捕まえるか |
|:--|:--|:--|
| 1 | メンバーを外したあとの人数が、設計書では「1人」。上から順に通すと、その前の行で1人足しているので「2人」 | Step 2 |
| 2 | 「試す前の準備」に、途中で初期データを入れ直す話が無い | Step 2 |
| 3 | 「公開チャンネルにはそれぞれ編集済みが1件以上」と読めるが、実物はあるチャンネルに集まっていて、どちらも無いチャンネルもある | Step 2 |
| 4 | `docs/design/README.md` が「いまは空です」のまま | Step 4 |
| 5 | `CLAUDE.md` が「機能のコードはまだ1行も無い」のまま | Step 4 |
| 6 | 素のLaravelに入っていた見本のテストが1本、テストの数に混ざったままだった | Step 3（件数を数え直したとき） |

6番だけは、この進行例で実際に気づいたのは次の16-4-2で、提出前に残り物を見たときでした。Step 3 で件数を数え直しておけば、その前に捕まります。

## ズレを、どちらに合わせるか

ズレが出たら、**実物を直すのか、書いたものを直すのか**を件ごとに決めます。決めたら両方を最新の状態にして、次へ進みます。放っておくと、提出したあとに読む人が、どちらを信じればよいのか判断できません。

上の6件のうち5件は、書いたものを直しました。**実物が正しく、書いたものが古い**という形だったからです。アプリのコードは1行も変わっていません。設計を先に決めてから作り、実装中にズレたら設計書側を直してきたので（16-3-2）、最後に残るのは**誰も触らなかった書きもの**のほうだった、ということです。

6番（素のLaravelに入っていた見本のテスト1本）だけは、実物のほうを消します。使っていないテストを消す作業ですが、これは消して終わりではありませんでした。テストのファイルを消し、空になった `tests/Unit/` フォルダごと消したところで、テストが1本も走らなくなります。

```text
Test directory "/var/www/html/tests/Unit" not found
```

`phpunit.xml` に、消したフォルダを指す設定が残っていたためです。不要なファイルを消す作業は、**そのファイルを指していた設定が無いか** まで見て、もう一度テストを回すところまでを含みます。

この1件は `tests/` と `phpunit.xml` に手が入るので、16-3-1で `CLAUDE.md` に書いた `chore/` の説明（`.claude/` の物差し・設計書だけの修正）からははみ出します。どのイシューにも紐づかない直しなので、同じ `chore/handover` に載せます。

## 受け入れの記録

突き合わせた結果は、リポジトリに残る形にします。置き場は `docs/acceptance-report.md` です。

設計書一式の中には入れません。あそこは `docs/design/README.md` が「置くファイルはこれ」と名指ししている一式で、8本目を足すとその表と実物が食い違います。この記録は、これから作るための決めではなく、**作り終えた時点で実際に確かめた結果**です。同じ性質のもの、つまりクライアントから受け取った仕様書と同じ階層に置くのがいちばん近い場所になります。

ファイル名に日付は入れません。受け入れは1回きりのものではなく、直したらやり直すものだからです。日付を入れると同じ内容のファイルが並ぶので、同じファイルを書き換えて、最新が常に1つだけ残る形にします。実施日は中の1行目に書きます。

中身は、プルリクエストの本文の全体版です。書く項目はこうなります。

- 何を突き合わせたか（3本の結果を1つの表に）
- 突き合わせ1: 機能一覧とCRUD表
- 突き合わせ2: 受け入れ条件の全数の判定と、端から端までの一巡
- 見つかったズレと、どちらに合わせたか
- 突き合わせ3: テストと整形
- 引き渡しの状態（どのブランチが最新で、どうやって動かせる状態か）

プルリクエストの本文と違うのは、計画の持ち方と、作らなかったものと、`Closes` が無く、代わりに「何を突き合わせたか」と「引き渡しの状態」が入るところです。受け取る相手が、この1件を見る人から、**このリポジトリを受け取る人**に変わるためです。

```text
docs/acceptance-report.md を作って。
今日確かめた3本の突き合わせの結果と、見つかったズレとどちらに合わせたか、
テストと整形の結果、引き渡しの状態を書いて。
判定は、実際に確かめた値をそのまま載せて。
1行目に実施日を入れて。
```

書けたら全文を読み、自分が画面で見たものと合っているかを確かめてから、直した設計書と `CLAUDE.md`、消した見本のテストの分と一緒に `chore/handover` へコミットします。プルリクエストはまだ出しません。READMEを整えるところまでを、この1本にまとめます。

## ✨ まとめ

- 全部できあがったあとに、リポジトリを入口から読み直します。差分に映らないものは、この段でしか捕まりません。
- 受け入れ条件を上から順に通すと、行が互いの前提を壊します。順番の入れ替えと、途中の入れ直しで通します。
- ズレは件ごとに、実物と書いたもののどちらへ寄せるかを決めて、両方を最新にします。
- 記録は `docs/acceptance-report.md` に、実際に確かめた値をそのまま残します。

設計書一式の役目は、ここまでです。機能ごとの設計書が「その機能を受け取るまで」だったのと同じ線で（14-3-1）、一式は全体の受け入れまで持ちます。これから先、このアプリの姿を正しく持っているのは、動いているコードとテストのほうです。一式は実物と一致した状態で、提出物として締めます。
