# 16-4-2: 提出の形に整える

## 🎯 このセクションで学ぶこと

- 初めてこのリポジトリを開いた人が、READMEだけで動かしてログインし、ひととおり触れる状態に整えられるようになる。
- 書いた手順をAIに頭から通させて、書いただけでは分からない抜けを見つけられるようになる。
- 提出前のリポジトリの掃除を、見た目ではなく確かめてから済ませられるようになる。

## 導入

受け入れの記録まで済んで、リポジトリの中身は最新になりました。1枚だけ、まだ手を付けていないファイルがあります。トップの `README.md` です。作業は16-4-1で切った `chore/handover` の上で続けます（`git branch` を打つと、`*` が付いているのがいまのブランチです。12-1-2）。

いま書いてあるのは、出発点のリポジトリのままの文章です。「`docs/design/` は設計書一式の置き場。いまは空です」「アプリの機能のコードは、1行も入っていません」「あなたが一本のアプリを作り切るための出発点です」。設計書はそろい、画面もルートもあり、テストも走ります。どの1行も、いまの中身と合っていません。読む相手が、これから作る自分から、できあがったものを受け取る人に変わったので、書き直します。

## READMEが引き受けるもの

提出したリポジトリを開いた人が、いちばん最初に読む1枚です。ここが足りないと、その人の手元では動かないという結果だけが残り、中身を見てもらう前に終わります。

引き受けてもらう範囲は、**動かす・ログインする・ひととおり触る**の3つです。これができれば、あとは中身を自分で読めます。見出しは次の並びで置きます。

| 見出し | 書くこと |
|:--|:--|
| 何のアプリか | 1段落の説明と、使っているもの（Laravel・MySQL・Sail）。JavaScriptを1行も使っていないことも、ここに書きます |
| できること | 設計書の機能一覧から、画面で触れるものを一覧にします |
| 動かす | cloneから初期画面までのコマンドを、順番どおりに |
| ログインする | 3つのアカウントと、それぞれの立場（誰がどのチャンネルのメンバーか） |
| ひととおり触ってみる | 数分で一周できる道順。プライベートチャンネルのメンバーでない人で入り直す段を入れます |
| 公開API | 2本のエンドポイントの表と、`curl` の1行 |
| テストと整形 | 打つコマンドと、通ったときに出る行 |
| 中身の地図 | どこに何があるか。なぜそう作ったかは `docs/design/` を見てもらう |

> ⚠️ **注意**: 「動かす」は、clone するところから書きます。出発点のリポジトリのREADMEでは、clone は「使いはじめる」に、そのあとが「初回起動（5手）」に分かれていました。受け取る人は clone から一続きで進むので、1本の手順にまとめます。中身で変えるのは1か所で、最後のマイグレーションに **`--seed` を付けます**。16-2-1で付けなかったのは、初期データをこれから機能ごとに積むところだったからです。いまは3つのアカウントもチャンネルも入っているので、付けないと開いた人はログインできる資格を1つも持てません。

## 🏃 READMEを書き直して、通して確かめる

思いどおりに直らない・壊れたと感じたら、14-5-1（直らないときの型）へ。応急は `git restore .` です。

### Step 1: 起こさせる

READMEを書き起こすのは、16-4-1とは別の作業です。新しいセッションで始めて、`/rename 16-4-2 README` のように名前を付けてください。16-4-1で `s` で選んだ `opus` はそのセッション限りだったので、開き直せば `sonnet` に戻っています（14-1-6）。ここは手順どおりに書き起こす作業なので、そのままで構いません。

書く材料は全部リポジトリの中にあるので、集めるところから任せます。

```text
README.md を、このアプリを初めて受け取る人向けに書き直して。
いまのものは出発点のリポジトリのままで、中身と合っていない。
見出しは 何のアプリか / できること / 動かす / ログインする /
ひととおり触ってみる / 公開API / テストと整形 / 中身の地図 の順で。
機能一覧は docs/design/ から、ログイン情報は初期データから拾って。
動かす手順は clone から始めて、マイグレーションには --seed を付けて。
```

返ってきたら全文を読みます。見るのは、書いてあることが自分の知っている実物と合っているかどうかです。ここではまだ、手順が通るかどうかは分かりません。

### Step 2: 書いた手順を、頭から通させる

READMEの手順は、書いた本人の手元では**すでに動いている状態**で書かれます。`vendor/` があり、`.env` があり、データベースが立ち上がっているところで読み返しても、抜けは見つかりません。

そこで、clone するところから通します。いまのアプリが80番と3306番のポートを掴んでいるので、先に止めます。

```bash
# 自分のリポジトリのフォルダで実行する
./vendor/bin/sail stop
```

clone は GitHub から取ってきます。手元にしかない書き直しは clone した先に出てこないので、先に `chore/handover` を上げます。16-4-1で直した設計書の入口と `CLAUDE.md` も、ここで一緒に上がります。

```text
ここまでの変更をコミットして、chore/handover を origin へ push して。
```

```text
~/laravel-practice/ の下の別のフォルダへ、このリポジトリの chore/handover ブランチを
GitHub から clone して（git clone -b chore/handover）。
そのうえで README.md の「動かす」を上から1行ずつ、そのとおりに実行して。
READMEの clone の行だけは、いまの -b 付きで済ませたものとして飛ばして。
それ以外のコマンドは、足したり変えたりしないで。
詰まったところと、書いていないのに必要だった手順を挙げて。
そのあと「ひととおり触ってみる」の道順も、書いてあるとおりに辿れるか確かめて。
```

ブランチを指定して clone しているのは、書き直したREADMEがまだ `main` に入っていないからです。`git clone -b <ブランチ名>` は、その枝を取り出した状態で持ってきます。READMEに書いた clone の行との違いはここだけなので、読み替えてよいのもこの1行だけです。

Claude Codeは `teamchat-app` のフォルダで起動しています。この依頼はその外側に新しいフォルダを作って触るので、途中で許可を聞かれます。聞かれたら中身を読んで許可してください。

> 💡 **進行例について**: AIとの開発は毎回違う流れになります。ここに示すのは一つの進行例です。あなたの画面と違っていても、チェックリストを満たしていれば正解です。

**書いただけでは分からなかったこと**が、ここで出ます。実際に出た例を挙げます。

- 起動してすぐ次を打つと落ちます。コンテナが `Up` になっても、データベースは中でまだ立ち上がっている途中で、`SQLSTATE[HY000] [2002] Connection refused` が返ります。出発点のリポジトリのREADMEが30秒待たせていたのと同じ理由です。書き直したREADMEにも、`sail ps` の `mysql` が `Up (healthy)` に変わるのを待つことと、**この文言そのもの** を載せます。初見の人が検索するのは、まさにこの1行だからです
- ポートがぶつかる場所を、**1手ずれて書いていました**。書き直しのときに手順を組み替えたのに、但し書きの中の手数が古いまま残っていたためです。文言のほうも、見たことのないものを書いていたので、実際に出る `Bind for 0.0.0.0:80 failed: port is already allocated` に揃えました
- 止め方が1行も書いてありませんでした。冒頭で「別のアプリを止めてください」と読み手に頼んでいるのに、このアプリの止め方がどこにもありません。`sail stop` と `sail down -v` を足し、`down -v` のあとはどこからやり直せばよいかも書きます

抜けが出たら、直すのは**元のフォルダの `README.md`** です。clone した先は読むだけで、そちらには手を入れません。順番はこうなります。

1. clone したフォルダで `./vendor/bin/sail down -v` を打ち、そのフォルダごと削除する
2. 元のフォルダで `./vendor/bin/sail up -d` を打ち、`./vendor/bin/sail ps` の `mysql` が `Up (healthy)` になるまで待つ
3. 元のフォルダで `README.md` を直し、`chore/handover` へコミットして push する
4. 元のフォルダで `./vendor/bin/sail stop` を打って、また止める
5. 上と同じ依頼をもう一度出して、clone するところから通し直す

clone した側を先に落とすのは、80番と3306番をそちらが掴んでいるからです。元のフォルダを起こしてから直すのは、フックが編集のたびに整形とテストを回すからです。16-3-4で足した1句は `vendor/bin/sail` というファイルがあるかどうかだけを見るので、コンテナが止まっていても飛ばしてはくれません。止まったまま直させると、テストが必ず落ちて編集が止まります。4で止め直すのは、通し直しの clone がまた同じポートを使うためです。

通し直しを飛ばすと、clone のやり直しが直す前のREADMEをまた読みます。コミットを分けておくと、READMEを書いたぶんと、通して確かめて直したぶんが、履歴の上で分かれます。

抜けが出なくなったら、1と2の手順で clone を片づけて、元のフォルダを起こし直します。

### Step 3: 最後のプルリクエストを出す

`chore/handover` に載っているのは、Chapter 4で直したもの全部です。受け入れの記録、古くなっていた設計書の入口と `CLAUDE.md`、消した見本のテストと `phpunit.xml` の直し、書き直したREADME。最後のプルリクエストを出して、自分でマージします。

```text
chore/handover のプルリクエストを出して。
本文には、全体の受け入れで見つかったズレとどちらに合わせたか、
READMEを通して確かめて直した抜けを書いて。イシューには紐づかない。
```

16-3-1で出した物差しの1本と同じで、`Closes` は入りません。違うのは、報告する対象です。あちらが「物差しの穴を塞いだ」だったのに対して、これは**全体が引き渡せる状態になった**ことを報告します。

マージしたら `main` に戻して、手元を最新にします。

```text
main に切り替えて、origin から最新を取ってきて。
```

### Step 4: リポジトリを掃除する

受け取る人が最初に見るのは、GitHubのリポジトリのトップです。ここも読まれるものとして整えます。

```bash
# 自分のリポジトリのフォルダで実行する
gh issue list --state all
gh pr list --state merged
git status
```

`--state all` を付けると、閉じたイシューも一覧に出ます。そのうえで、次を確かめます。

- イシューが全部 `CLOSED` になっている
- プルリクエストの並びが、そのまま作った順の物語になっている（本文に判定と証拠が残っている）
- 検証のときに作ったファイルや、素のLaravelの残り物が置きっぱなしになっていない（16-4-1で片づけた分を含めて、もう一度見ます）
- `git status` が空

ブランチは、手元にもリモートにも `main` だけを残します。機能ごとの `feature/...`、Chapter 3で切った `chore/...`（`chore/harness-gaps` など）、そしていま使った `chore/handover` が対象です。マージのときにGitHub側を消していても、**手元の写しは残っています**。ここは見た目で判断すると1回引っかかるので、確かめてから消してください。

<details><summary>ブランチの掃除でつまずくところ（クリックで展開）</summary>

**消したはずのリモートのブランチが、まだ見える**

`git branch -a`（12-1-2）に `remotes/origin/feature/...` が並んで見えても、リモートに残っているとは限りません。あれは**手元に残っている写し**で、リモートで消えたことは自動では伝わってきません。リモートを直接見ると分かります。

```bash
git ls-remote --heads origin
```

`main` の1行だけが返るなら、リモートは片づいています。手元の写しは次で消えます。

```bash
git fetch --prune
```

**`git branch -d` が断ってくる**

「マージされていない」と言われて消せないことがあります。プルリクエストを積み直す形（rebase）で受け取っていると、`main` に載っているのは積み直された別のコミットになるので、手元のブランチが指しているコミットそのものは `main` に見つかりません。`-D` はその安全装置を外すコマンド（12-1-2）なので、外す前に中身が入っているかを確かめます。

```bash
git cherry main feature/issue-1-auth
```

行の先頭が `-` なら、同じ中身が `main` に入っています。`+` なら、まだ入っていません。`-` を確かめてから `git branch -D` で消します。

</details>

## ✨ まとめ
