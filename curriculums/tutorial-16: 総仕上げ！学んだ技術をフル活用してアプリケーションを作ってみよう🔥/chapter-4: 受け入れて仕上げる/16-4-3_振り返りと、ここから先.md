# 16-4-3: 振り返りと、ここから先

## 🎯 このセクションで学ぶこと

- 総仕上げで確かめる5つの行動を、自分のリポジトリの実物で指せるようになる。
- ハーネスがこの1本のあいだにどう育ったのかを、自分の `.claude/` で辿れるようになる。

## 導入

提出まで済みました。手元に残っているのは、動くアプリと、実物と一致した設計書一式と、`.claude/` の中身です。

ここでやるのは、読み直す作業です。16-1-1で並べた5つの行動を自分のリポジトリの実物で指し、`.claude/` がこの1本のあいだにどう変わったのかを見て、そのうえで次に何が変わるのかを確かめます。イシューを立てることも、コードを書くこともしません。

## 5つを、自分の1本で指す

このTutorialのゴールは、これでした。

```text
与えられた仕様を、AIと対話しながら設計に落とし、AIを率いて実装・検証・PRまで一人で回し切れる。
繰り返しは仕組みに落とし、複数の作業を並行で回せる。
```

観測できる形にすると、5つの行動になります。1つずつ、自分のリポジトリのどこを開けば指せるかを見てください。

| 行動 | どこを開くと指せるか |
|:--|:--|
| 作るものをイシューにして、受け入れ条件を書ける | イシュー7本。受け入れ条件は設計書の文言をそのまま写してあるので、16-4-1の全数の判定が、そのままイシューの確かめ直しになりました |
| 計画の持ち方を選び、その理由を言える | 件ごとに、イシューかプルリクエストの本文に残した1行。計画を立てた件と、立てなかった件の両方に理由があります |
| 検証をAIに渡し、受け入れを自分で判定できる | テストの実行結果、`/uat` の報告、人の手で通した一巡、そして `docs/acceptance-report.md` |
| コンテキストを自分で区切って渡せる | `CLAUDE.md` が在りかの表だけを持ち、中身を写していないこと。設計書が種類ごとに分かれていること。イシュー1本ごとに区切ったセッション |
| 繰り返しを仕組みにして、複数の作業を並行で回せる | `.claude/` のフック・許可の指定・Skill・ルール・実装役のサブエージェント。アプリのコードを1行も含まないプルリクエスト。worktreeで同時に進めた2本 |

指せるかどうかは、あとから思い出せるかどうかでは決まっていません。**その場で何が残ったか**で決まっています。計画を立てなかった理由は、プルリクエストの本文に毎回1行書く型があったから残りました。検証は、測った値を出力ごと本文に貼っていたから残りました。コンテキストの区切りだけは、書いたものではありません。設計書が種類ごとに分かれていること自体が、形として残っています。

## この1本で育ったハーネス

5つ目の行に `.claude/` と書きました。そこと `CLAUDE.md` に入っているものは、Chapter 2で置いたときと、いまとで違います。

Chapter 2を終えた時点で入っていたのは、これだけです。

| 置いたもの | どうやって |
|:--|:--|
| `CLAUDE.md` | 作り直して、「守ってほしい書き方」を足した（16-2-1・16-2-3） |
| 許可の指定 | 書き起こした（16-2-2） |
| フック | 書き起こして、整形をもう1本足した（16-2-2・16-2-3） |
| ルール（`testing.md`） | 運んで、固有の物差しを差し替えた（16-2-2） |
| Skill 3本（`/review-diff`・`/uat`・`/issue`） | 運んで差し替え、`/review-diff` に受け取りの観点を足した（16-2-2・16-2-3） |

Chapter 3では、ここに足していきました。

| 足したもの | いつ | 何があって足したか |
|:--|:--|:--|
| ブランチの決まり（`CLAUDE.md`） | 16-3-1 | 決まりが無かったので、AIがその場で名前を決めた |
| Skill（着手・`/start`） | 16-3-1 | 同じ手順を、残り6本ぶん繰り返すと分かった |
| Skill（プルリクエスト） | 16-3-1 | 同じ本文の型を、残り6本ぶん毎回書くと分かった |
| サブエージェント（`agents/implementer.md`） | 16-3-2 | 受け取りの判断に空けておきたいところが、実装のやり取りで埋まった |
| ルール3枚（`http.md`・`eloquent.md`・`blade.md`） | 16-3-3 | 同じ判断を、2つのイシューで2回説明した |
| フックのガード句 | 16-3-4 | 書く場所を増やすと、`vendor/` の無い場所でフックが編集を止めてしまう |

一度置いたものも、そのままでは終わっていません。

| 育った部品 | いつ | どう育てたか |
|:--|:--|:--|
| Skill（着手・`/start`） | 16-3-2 | 計画を承認したあと、実装を担当に渡すところまで持たせた |
| Skill（`/uat`） | 16-3-4 | 書く場所で回す道と、画面の無い件の道を足した |
| ブランチの決まり（`CLAUDE.md`） | 16-3-4 | worktreeが作る枝の名前を含む形に広げた |
| フック | 16-3-4 | `sail` の無い場所では素通りするように直した |

道具はどれも、7本を回している最中に足しています。繰り返すと分かってから、あるいは、それが無くて困ってからです。育てたほうも同じで、`/start` も `/uat` も、使っているうちに足りないところが出たので書き足しました。ハーネスは、作って終わるものではなく、使うほど形が変わります。

## 🏃 育ちを、履歴で見る

上の3つの表は、この教材が並べたものです。同じことを、自分のリポジトリの履歴でも見られます。

```bash
# 自分のリポジトリのフォルダで実行する
git log --oneline -- .claude/ CLAUDE.md
```

物差しをいつ・なぜ変えたのかが履歴に残る、と16-3-1に書きました。ここに出てくるのがそれです。アプリのコードを1行も含まないプルリクエストが、何本か並んでいるはずです。

そして、この一式は次のリポジトリへ持っていけます。16-2-2でやったのは、前のアプリで組んだものを運んで、固有の物差しを差し替えることでした。新しいプロジェクトを始めるときの最初の一手は、そのときと同じです。運ぶのはルール・Skill・サブエージェント、書き起こすのは `CLAUDE.md` と許可の指定とフックです（フックはコマンドの形をそのまま使えます）。線の引き方は変わりません。**中身がプロジェクトにどれだけ縛られているか**で分かれます。

いま手元にある `.claude/` が、そのとき運ぶ側になります。

## Tutorial 13から16まで

4つのTutorialで変わったのは、AIとの距離ではなく、**自分が受け持つ範囲**のほうです。

| Tutorial | やったこと |
|:--|:--|
| 13 | 設計図を、自分の手で描いた。AIには描かせなかった |
| 14 | 1つの機能を、イシューから受け取りまでAIと通した。決めるのは自分、作るのはAI、という分け方を1周ぶん体験した |
| 15 | 毎回手でやっていたことを、置き場所を決めて仕組みに移した。書く場所を増やして、受け取りは1か所に保った |
| 16 | 仕様書とデザインだけを受け取り、設計から提出まで一人で通した。機能は7つ。仕組みは持ち込んで、回しながら育てた |

1-1-6で、SEとプログラマーの分業が「AIを率いる一人のエンジニア」に統合されていく、という話をしました。あそこに出てきた3行を、いまの自分のリポジトリで指せます。設計を決めたのは自分で、それは `docs/design/` に残っています。コードを書いたのはAIで、マージしたプルリクエストに残っています。正しいかどうかを確かめて責任を持ったのも自分で、`docs/acceptance-report.md` に残っています。

## Tutorial 1から16まで

Tutorial 16は、このカリキュラムの最後の1本でもあります。ここまでの道のりを畳むと、こうなります。

| どこ | 何をしていたか |
|:--|:--|
| Tutorial 1〜5 | 画面とコードを自分の手で書き、書いたものを記録に残す道具を覚えた |
| Tutorial 6〜12 | 動かす土台と、言語と、データベースと、フレームワークを積み、チームで作る形まで通した |
| Tutorial 13 | 作る前に決めることを、図と表に落とした |
| Tutorial 14〜16 | 決めたものをAIに作らせ、繰り返しを仕組みに移して、アプリを1本仕上げた |

順番には意味があります。AIが書いたものを受け取れるのは、出てきたコードを読めるからです。読めるのは、Tutorial 1から12で自分の手で書いたからです。何を作らせるかを決められるのは、Tutorial 13で設計を描いたからです。AIに任せられる範囲は、**自分が判定できる範囲より先には広がりません**。14-1-1で分けた「決める側」が最後まで自分に残っていたのは、そのためです。

## ここから先

### 確認テスト

教材学習を終えると、確認テストに進みます。要件はコーチから要件シートという形で渡され、そこからアプリを作って提出します。

渡され方が1つ変わります。**要件が、リポジトリの中に入っていません。** 今回は `docs/spec.md` と `mockup/` がリポジトリの中にあり、指せばAIが読みに行きました（16-1-2）。渡された要件シートを同じように読ませるなら、自分でリポジトリの中に置くところから始まります。

進め方のルールも、その要件シートに書いてあります。確認テストの最中はコーチへの相談とSlackの質問解決が使えないので、**始める前に、その紙を最後まで読んでください**。使ってよい道具も、提出の形も、そこで確かめます。

### 模擬案件

確認テストのあとは、模擬案件に取り組みます。ここでもう1つ変わります。模擬案件では、Tailwind CSSが適用された **Bladeテンプレートが提供され**、あなたはバックエンドの開発に集中します（5-4-1）。今回渡されたのは画面の見本で、CSSはその見本のものをそのまま持ち込み、Bladeは自分の采配でAIに書かせました。渡されるものが増えるので、あなたが受け持つ範囲は狭くなります。

### 変わらないもの

狭くなるのは範囲だけで、受け取りの物差しは変わりません。仕様を読んで設計に落とし、作業の票に割り、1件ずつ回して受け入れ条件で判定し、最後に全体を突き合わせる。今回1周した外側の流れは、規模が変わってもそのまま使えます。

自分のリポジトリは残しておいてください。次に詰まったとき、いちばん近い手本は、自分が通した1本です。`.claude/` も、そこに一緒に残っています。

## ✨ まとめ

- 5つの行動は、イシュー・プルリクエストの本文・設計書・受け入れの記録という実物で指せます。
- 指せるのは、その場で理由と測った値を残していたからです。残していなければ、やったという記憶しか残りません。
- ハーネスは、7本を回している最中に、困ってから足し、使いながら書き換えてきました。作って終わるものではありません。
- 新しいプロジェクトの最初の一手は、16-2-2と同じです。いまの `.claude/` が、そのとき運ぶ側になります。
- Tutorial 13から16で変わったのは、自分が受け持つ範囲です。設計と検証は最後まで自分の側に残りました。
- AIに任せられる範囲は、自分が判定できる範囲より先には広がりません。
- 確認テストでは要件が紙で渡され、模擬案件ではBladeテンプレートが渡されます。渡されるものは変わりますが、回し方の型はそのままです。

Tutorial 1からここまでで、手で書く段階、設計を描く段階、AIと1機能を回す段階、仕組みに移す段階、そして一人でプロダクトを1本作り切る段階を通りました。ここでひと区切りです。次は、同じ型のまま、別のお題で回してください。
