# 16-3-3: メンバー管理とスレッドを作る

## 🎯 このセクションで学ぶこと

- 2回目に出た判断をルールに残し、ファイルの分け方と当たる範囲を自分で決められるようになる。
- 断り方が分かれる機能を、見る順番まで決めて実装させられるようになる。
- 前のイシューで決めたことが、あとのイシューで効いてくる形を確かめられるようになる。

2. 【自分】提案された計画の持ち方を承認する。選んだ理由を1行、イシューかプルリクエストの本文に残す

4. 【自分】返ってきた報告を読む。「決めきれなかったこと」が書かれていたら、そこで決めて出し直させる
5. 【自分】フックが回したテストと整形の結果を読む

8. 【自分⇄AI】`/pr` でプルリクエストを出し、本文と「Files changed」を読んでからマージさせる（16-3-1）
9. 【自分】セッションを区切ってから、スレッドへ移る

## メンバー管理: 断り方が3つに分かれる

この件の要は、**断り方と、見る順番**です。

| 誰が、何をしようとしたか | 返すもの |
|:--|:--|
| 公開チャンネルの番号でメンバー管理を開かれた（作った人でも） | 404 |
| そのチャンネルを見られない社員が開いた | 404 |
| メンバーだが、作った人ではない社員が開いた | 403 |
| 作成者を「外す」で送られた | 403「作成者は外せません」 |

1つ目を先に見るのが**要**です。「そのチャンネルを見られるか」を先に見ると、公開チャンネルは社員全員が見られるので判定を通ってしまい、**作った人にメンバー管理の画面が出ます**。メンバー管理はプライベートチャンネルだけの機能なので、公開かどうかを先に見ます。

「作成者は外せない」も、同じポリシーの中に置きます。外す操作は、操作する人・チャンネル・外される人の3つを見ることになりますが、**判定は1か所**という決まり（16-2-3で `CLAUDE.md` に書いたもの）は、引数が増えても保てます。

### テストが緑でも、見つからないものがある

この件では、テストが全部緑になったあとのUATで1つ出ました。**メンバーの並び順**です。

初期データは、チャンネルを作った人をあとから足すので、加わった順に並べると**作成者が真ん中に来ます**。モックアップの見本では先頭にいます。それでもテストは緑のままでした。設計書に並び順が書かれていないので、**確かめるテストを書く理由が無かった**からです。

見つけたら、直すのは設計書のほうからです（16-3-2の型）。並び順を「作成者を先頭に、そのあとは加わった順」と決めて `docs/design/screens.md` に足し、受け入れ条件を揃えてから、実装に戻ります。

テストは、**設計書が決めていないことを確かめてくれません**。緑は「決めたことが守られている」の証拠であって、「決め忘れが無い」の証拠ではありません。人がブラウザで触る時間が要るのは、ここです。

## スレッド: 前に決めたことが、ここで効く

スレッドで新しく決めることは、ほとんどありません。**返信元が返信でないこと**（返信は1段まで。Q-16）の1つだけです。

代わりに、前に決めたことが3つまとめて効きます。

| もとの決め | この件でどう効くか |
|:--|:--|
| 返信も `messages` に入れる（16-1-4） | 返信の編集・削除・「編集済み」・「削除されました」が、メッセージ側の実装のまま動く。ポリシーもフォームリクエストもそのまま使える |
| 論理削除の既定に任せない（同） | 返信件数を数える1行が、**削除済みの返信も数に入れた件数**を返す（Q-18） |
| 削除は行を残す更新（同） | 削除済みのメッセージが**スレッドの器として残る**ので、「消えたメッセージにも返信できる」（Q-17）が、器を作り直さずに成り立つ |

2つ目が分かりやすいところです。もし既定の論理削除に任せていたら、件数を数える1行が黙って「削除済みを抜いた件数」に変わります。16-3-2では、その決めを**外して測って**6本落ちるのを見ました。この件では、**外していなかったおかげで、測る必要すらありません**。

16-1-4でデータの持ち方に時間をかけた見返りが、2本あとのイシューで返ってきた形です。

## 触っていないテストが落ちる

スレッドを実装すると、**自分が触っていないテストが落ちます**。

```text
   FAIL  Tests\Feature\Message\MessageDestroyTest
  ⨯ 削除済みの行にも編集と削除のボタンは出ない
   FAIL  Tests\Feature\Message\MessageUpdateTest
  ⨯ 他人のメッセージには編集と削除のボタンが出ない
```

どちらも、メッセージのイシューで書いたものです。落ちた行は同じ形をしています。

```php
$response->assertDontSee(route('messages.destroy', $message));
```

削除のURLが画面に出ていないことを、ボタンが無いことの証拠にしていました。スレッドで足した「返信を開く」のURLは `GET /messages/13`、削除は `DELETE /messages/13` です。**文字列としては同じ**で、違うのは送り方だけ。返信を開くリンクを出した瞬間に、この根拠は成り立たなくなりました。

アプリは壊れていません。**テストの根拠のほうが古くなった**のです。直すのはテストで、ボタンそのものを探す形に書き換えます。

この種の落ち方は、AIに直させる前に自分で読んでください。「落ちたので直しました」で通すと、**根拠の弱いテストが、根拠の弱いまま別の形で残ります**。

## 同じ判断が2回目に出たら、ルールにする


15-2-1で、決めごとを足す引き金を3つ見ました。1つ目が「同じ間違いの2回目」です。ここで当てはまるものが出ます。

16-3-2のチャンネルで決めたのは、**判定の順番**でした。

1. そのチャンネルが見えるか。見えなければ404
2. 触ろうとしている行が、そのチャンネルのものか。違えば404
3. 作った人か、書いた本人か。違えば403

順番が結果を変えます。3を先に見ると、メンバーでないプライベートチャンネルに403が返り、**そのIDのチャンネルが存在することが漏れます**。名前も存在も出さない、と決めた確認事項（Q-05）が、断り方1つで破れます。入力チェックも同じで、判定より先に走らせると、エラーの文面が存在を教えます。

そして、いま回したメンバー管理でも、まったく同じ判断が出てきました。断り方が3つに分かれるぶん、順番はもっと効きます。2回目です。ここが引き金になります。

## どう分けて置くか

ルールは1ファイル1トピックで置きます。ファイル名で中身が分かるようにして、`paths` を付けると、当てはまるファイルをAIが読んだときだけ読み込まれます（15-2-3）。`paths` を書かなければ起動のたびに読まれ、`CLAUDE.md` と同じ扱いになります。

| 置き場所 | いつ読まれるか |
|:--|:--|
| `CLAUDE.md` | 起動のたび、毎回 |
| `.claude/rules/` で `paths` を付けたもの | 当てはまるファイルをAIが読んだとき |

分け方は、こちらで決めずに提案させます。

```text
.claude/rules/ にルールを追加したいです。
Laravelの標準的な構成と、本プロジェクトの app/ 配下のコードを調査してもらい、
ルールをどう構造化すべきか（例えばファイル名とpathsの切り方）とその内容について提案してほしい。
```

> 💡 **進行例について**: AIとの開発は毎回違う流れになります。ここに示すのは一つの進行例です。あなたの画面と違っていても、チェックリストを満たしていれば正解です。

返ってきた分け方は、Laravelの置き場所にそのまま乗ります。`app/Http/` に効くもの、`app/Models/` に効くもの、`tests/` に効くもの。ファイル名と `paths` が対応していれば、あとから読む人も探せます。

中身は、全部受け取りません。残すのは、**このプロジェクトの決めに根拠があるもの**だけです。判定の順番のように実際に踏んだもの、設計書で決めたもの、実装を読めば確かめられるもの。一般論として正しいだけの行は落とします。守られたかどうかを確かめられないからです。

**設計書にある規則そのものは写しません**（15-2-1）。入力チェックの規則は `docs/design/screens.md` にあります。ルールに書くのは、そこを見るように、までです。

このときは、4枚に分かれました。

| ファイル | `paths` | 何の決めか |
|:--|:--|:--|
| `http.md` | `app/Http/**`・`app/Policies/**`・`routes/*.php` | 判定の順番、断り方、URLを自分で決めない |
| `eloquent.md` | `app/Models/**`・`database/**` | 論理削除の既定に任せない、返信を別テーブルにしない |
| `blade.md` | `resources/views/**`・`public/css/**`・`public/js/**` | 文言を自分で考えない、色を直値で書かない |
| `testing.md` | なし（毎回読まれる） | 16-2-2で運んだもの |

**`.claude/rules/http.md`**

````markdown
---
paths:
  - "app/Http/**/*.php"
  - "app/Policies/**/*.php"

# HTTP層の書き方

コントローラ・フォームリクエスト・ポリシー・ルートの決まり。**理由まで書いてあるのは、理由を知らないと直したくなる形をしているから。**正本は `docs/design/permissions-api.md` と `docs/design/behavior.md`。

## 判定は必ずこの順で行う

1. **そのチャンネルが見えるか** → 見えなければ **404**（`abort_unless($channel->isVisibleTo(auth()->user()), 404)`）
2. **その子リソースがそのチャンネルのものか** → 違えば **404**
3. **作成者か・投稿者本人か・まだ削除されていないか** → 違えば **403**（`$this->authorize(...)`）

順序を逆にすると、自分がメンバーでないプライベートチャンネルに403が返り、**そのIDのチャンネルが存在することが漏れる**。2 を落とすと、見えるチャンネルのURLの下に別チャンネルのメッセージIDを差し込むだけで手が届く。

`behavior.md` 3章「判定の順序」。

## フォームリクエストの `authorize()` は常に `true` にする

権限判定を書かない。`authorize()` はコントローラ本体より**先に**走るので、ここに作成者チェックや本人チェックを置くと上の順序が崩れ、404 より先に 403 が返る。フォームリクエストは入力チェックだけを受け持つ。

`true` を返す行には、なぜ空なのかのコメントを必ず添える。理由が無いと「書き忘れ」に見えて、次の人が埋めてしまう。

## 入力チェックもコントローラの判定より後に走らせる

フォームリクエストを型引数に取ると入力チェックが先に走る。**エラー文の有無で判断が変わる**。

- エラー文を出さない欄（メッセージ本文など）→ フォームリクエストでよい。はじかれても元の画面に戻るだけで、何も漏れない
- **エラー文を出す欄**（メンバー追加の検索キーなど）→ フォームリクエストに置かず、**コントローラの中で 404/403 判定のあとに `$request->validate(...)` を呼ぶ**。先に走らせると、見えないチャンネルへのPOSTに「該当する社員が見つかりません」が返り、チャンネルの存在が漏れる

## 判定用の private メソッドは、コントローラごとに持たせる

`ensureVisible()` は3つのコントローラに、`ensureBelongsTo()` は2つに同じ内容で置いてある。**この重複は意図的なので、共通の親クラスやトレイトに抽出しない。**

安全に直結する判定は、各アクションを読んだその場で「何を確かめているか」が見えている必要がある。基底クラスに移すと、アクションの本体からは判定が消え、次に足すアクションで**呼び忘れても気づけない**。抽出して得られるのは数行の削減で、失うのは見落としの検知しやすさ。

`MemberController` の `ensureManageable()` のように、そのコントローラでいつも2つ揃って呼ぶ判定を1本に束ねるのはよい。束ねる先がそのクラスの中にあるかぎり、読めば分かる。

## URL・HTTPメソッド・遷移先を自分で決めない

一覧が `permissions-api.md` 2章にある。`PATCH` / `DELETE` は素のHTMLフォームでは送れないので、`POST` + `@method('PATCH')` / `@method('DELETE')` のメソッド偽装で送る。

リダイレクトは `route()` 名前付きルートで書く。パスの直書きをしない。

## チャンネルの作成者に特権を持たせない

**チャンネルを作った人であっても、他人が書いたメッセージは編集・削除できない。**「作成者かどうか」と「投稿者本人かどうか」は別の判定で、ポリシーの中で混ぜない。

`permissions-api.md` 1章 注記[2]。

## UIで隠したことを、判定の代わりにしない

ボタンを出していない・`disabled` にしている、はサーバ側の判定の理由にならない。作成者チェック・投稿者本人チェック・削除確認入力の一致・作成者を外せない制御は、**すべてサーバ側で再検証する**。

## 見えないものへの応答は404で揃える

存在しないID・自分がメンバーでないプライベートチャンネル・チャンネルとメッセージの組み合わせ違い・返信を親に指すURLは、**すべて同じ404**。区別できる応答を返すと、その差から存在が分かってしまう。

「権限が無い操作」だけが403。
````

**`.claude/rules/eloquent.md`**

````markdown
---
paths:
  - "app/Models/**/*.php"
  - "database/**/*.php"
---

# モデルとデータベースの書き方

正本は `docs/design/data.md`。ここは**Laravel の既定に素直に従うと壊れるところ**を挙げる。

## `SoftDeletes` トレイトを使わない

`messages` の `deleted_at` は Laravel の論理削除とは**意味が違う**。

- 削除しても **`body` はクリアしない**。削除済みメッセージは「このメッセージは削除されました」の枠として画面に残り、投稿者名・日時・返信件数も残る。返信も続けられる
- そのためチャンネル表示（F-06）とスレッド表示（F-16）は **`deleted_at` を問わず全件取得**する。`SoftDeletes` のグローバルスコープはこれを既定で弾くので、トレイトを付けると画面から枠ごと消える
- トレイトが無いので **`$message->delete()` は物理削除になる**。論理削除は `markAsDeleted()` だけを通す

逆に**検索（F-17）と公開API（F-19）は `deleted_at IS NULL` を明示的に条件へ入れる**。ここを落とすと削除済みの本文が外に漏れる。

**チャンネルの削除は物理削除**で、`channel_user` と `messages` を `ON DELETE CASCADE` で道連れにする。メッセージの論理削除とは別物。

## 「編集済み」を `updated_at` で判定しない

`edited_at` が入っているかどうかで判定する。`updated_at` は削除（`deleted_at` の更新）でも動くので、編集以外でも印が付いてしまう。`edited_at` はこの判定のためだけに用意した列。

## 返信を別テーブルにしない

`messages` の自己参照（`parent_message_id`）。NULL なら本流、値が入っていれば返信。

- **返信は1段まで**（ネスト禁止）だが、これは**DB制約ではなくアプリ側でチェックする**
- `channel_id` は返信も持つ。親と常に一致する**意図的な冗長化**で、チャンネル単位の取得を WHERE 句1本で書けるようにするためのもの。冗長だからと消さない

## 返信件数の列を持たない

都度 `COUNT(*)` で数える。キャッシュ列を持つと整合性の維持コストが要るが、この規模では見合わない。

## `channel_user` に `updated_at` とサロゲートIDを足さない

`(channel_id, user_id)` の複合主キーで、`created_at` だけを持つ。メンバー行は「参加している／いない」のどちらかで、更新という状態が無い。

そのため次の3つを守る。既定に任せると `updated_at` が生える。

- マイグレーション: `$table->timestamps()` を**使わず** `$table->timestamp('created_at')` を手書きする
- リレーション: `belongsToMany(...)->withTimestamps()` を**使わず** `withPivot('created_at')` で読む
- 行の追加: `attach($id, ['created_at' => now()])` と `created_at` を明示する

複合主キーなので、二重 `attach()` はDBレベルで一意制約違反になる。「すでにメンバーです」の判定はアプリ側で先に行う。

## 表示用の取得はモデルの名前付きメソッドに寄せる

`messagesForDisplay()` / `repliesForDisplay()` のように、**どの条件で絞るかをモデル側に置く**。コントローラやビューに `whereNull('parent_message_id')` を散らさない。削除済みを外すか外さないかの判断が要る箇所なので、1か所に集めて名前で意図を示す。

可視範囲の絞り込みも同じで、`Channel::visibleTo()` の1本に通す。ビューで隠す形にしない。

## ファクトリは列の上限に合わせる

`users.name` は30文字（spec §5-1）。`fake()->name()` はこれを超える値を返すことがあり、当たった回だけ `SQLSTATE[22001] 1406 Data too long` で落ちる。**列に上限があるファクトリは、faker の出力を切って渡す。**

## シーダーは仕様書の内容から動かさない
````
