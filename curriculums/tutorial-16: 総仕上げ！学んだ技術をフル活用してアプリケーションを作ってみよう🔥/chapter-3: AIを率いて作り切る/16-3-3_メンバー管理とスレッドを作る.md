## 同じ判断が2回目に出たら、ルールにする

15-2-1で、決めごとを足す引き金を3つ見ました。1つ目が「同じ間違いの2回目」です。ここで当てはまるものが出ます。

16-3-2のチャンネルで、こう決めました。立場の確認は、**入力チェックより先に済ませる**。編集と削除は `FormRequest` の `authorize()`（9-6-4）で判定し、コントローラの中では判定しません。

理由は、順番が結果を変えるからです。コントローラで判定すると、入力チェックのほうが先に走ります。すると、見られないはずのプライベートチャンネルにも、**「チャンネル名を入力してください」が返ります**。エラーの文面そのものが、そのチャンネルが存在することを教えてしまう。名前も存在も出さない、と決めた確認事項（Q-05）が、入力エラー1つで破れます。

メンバー管理でも、まったく同じ判断が出てきます。2回目です。

## ルールに置くか、`CLAUDE.md` に置くか

置き場所は2つあります（15-2-3）。

| 置き場所 | いつ読まれるか |
|:--|:--|
| `CLAUDE.md` | 起動のたび、毎回 |
| `.claude/rules/` で `paths` を付けたもの | 当てはまるファイルをAIが読んだとき |

いま足そうとしているのは、**HTTPの入口を触るときだけ効けばよい決め**です。モデルを直すときも、Bladeを直すときも、テストを書くときも読まれる必要はありません。`paths` を付けたルールに置きます。

```text
app/Http/ の下を触るときだけ効くルールを .claude/rules/ に足して。paths で範囲を絞って。
チャンネルで決めた次の3つを書いて。

- 立場の確認は FormRequest の authorize() に置く。コントローラの中で判定しない。
  入力チェックが先に走ると、見られないはずのものの存在がエラー文で分かってしまう
- 断り方は2つ。見られない人には404、見られるが立場にない人には403。どちらもポリシーの中だけで決める
- 入力チェックの規則は docs/design/screens.md にあるので、そこを見る。ここには写さない
```

> 💡 **進行例について**: AIとの開発は毎回違う流れになります。ここに示すのは一つの進行例です。あなたの画面と違っていても、チェックリストを満たしていれば正解です。

3つ目は、書かないことを書いています。入力チェックの規則そのものを写すと、設計書と2か所になります（15-2-1）。ルールが持つのは**どこを見るか**までです。

置いたら、効いているかを次の実装の差分で確かめます。メンバー管理のコントローラに立場の判定が書かれていたら、届いていません。

## メンバー管理: 断り方が3つに分かれる

この件の要は、**断り方と、見る順番**です。

| 誰が、何をしようとしたか | 返すもの |
|:--|:--|
| 公開チャンネルの番号でメンバー管理を開かれた（作った人でも） | 404 |
| そのチャンネルを見られない社員が開いた | 404 |
| メンバーだが、作った人ではない社員が開いた | 403 |
| 作成者を「外す」で送られた | 403「作成者は外せません」 |

1つ目を先に見るのが**要**です。「そのチャンネルを見られるか」を先に見ると、公開チャンネルは社員全員が見られるので判定を通ってしまい、**作った人にメンバー管理の画面が出ます**。メンバー管理はプライベートチャンネルだけの機能なので、公開かどうかを先に見ます。

「作成者は外せない」も、同じポリシーの中に置きます。外す操作は、操作する人・チャンネル・外される人の3つを見ることになりますが、**判定は1か所**という決まり（16-2-3で `CLAUDE.md` に書いたもの）は、引数が増えても保てます。

### テストが緑でも、見つからないものがある

この件では、テストが全部緑になったあとのUATで1つ出ました。**メンバーの並び順**です。

初期データは、チャンネルを作った人をあとから足すので、加わった順に並べると**作成者が真ん中に来ます**。モックアップの見本では先頭にいます。それでもテストは緑のままでした。設計書に並び順が書かれていないので、**確かめるテストを書く理由が無かった**からです。

見つけたら、直すのは設計書のほうからです（16-3-2の型）。並び順を「作成者を先頭に、そのあとは加わった順」と決めて `docs/design/screens.md` に足し、受け入れ条件を揃えてから、実装に戻ります。

テストは、**設計書が決めていないことを確かめてくれません**。緑は「決めたことが守られている」の証拠であって、「決め忘れが無い」の証拠ではありません。人がブラウザで触る時間が要るのは、ここです。

## スレッド: 前に決めたことが、ここで効く

スレッドで新しく決めることは、ほとんどありません。**返信元が返信でないこと**（返信は1段まで。Q-16）の1つだけです。

代わりに、前に決めたことが3つまとめて効きます。

| もとの決め | この件でどう効くか |
|:--|:--|
| 返信も `messages` に入れる（16-1-4） | 返信の編集・削除・「編集済み」・「削除されました」が、メッセージ側の実装のまま動く。ポリシーもフォームリクエストもそのまま使える |
| 論理削除の既定に任せない（同） | 返信件数を数える1行が、**削除済みの返信も数に入れた件数**を返す（Q-18） |
| 削除は行を残す更新（同） | 削除済みのメッセージが**スレッドの器として残る**ので、「消えたメッセージにも返信できる」（Q-17）が、器を作り直さずに成り立つ |

2つ目が分かりやすいところです。もし既定の論理削除に任せていたら、件数を数える1行が黙って「削除済みを抜いた件数」に変わります。16-3-2では、その決めを**外して測って**6本落ちるのを見ました。この件では、**外していなかったおかげで、測る必要すらありません**。

16-1-4でデータの持ち方に時間をかけた見返りが、2本あとのイシューで返ってきた形です。

## 触っていないテストが落ちる

スレッドを実装すると、**自分が触っていないテストが落ちます**。

```text
   FAIL  Tests\Feature\Message\MessageDestroyTest
  ⨯ 削除済みの行にも編集と削除のボタンは出ない
   FAIL  Tests\Feature\Message\MessageUpdateTest
  ⨯ 他人のメッセージには編集と削除のボタンが出ない
```

どちらも、メッセージのイシューで書いたものです。落ちた行は同じ形をしています。

```php
$response->assertDontSee(route('messages.destroy', $message));
```

削除のURLが画面に出ていないことを、ボタンが無いことの証拠にしていました。スレッドで足した「返信を開く」のURLは `GET /messages/13`、削除は `DELETE /messages/13` です。**文字列としては同じ**で、違うのは送り方だけ。返信を開くリンクを出した瞬間に、この根拠は成り立たなくなりました。

アプリは壊れていません。**テストの根拠のほうが古くなった**のです。直すのはテストで、ボタンそのものを探す形に書き換えます。

この種の落ち方は、AIに直させる前に自分で読んでください。「落ちたので直しました」で通すと、**根拠の弱いテストが、根拠の弱いまま別の形で残ります**。

## ✨ まとめ

- 同じ判断が2回目に出たら、決めごとにします。当たる範囲が限られているものは、`paths` を付けたルールに置きます。
- ルールが持つのは、どこを見るかまでです。設計書にある規則そのものは写しません。
- 立場の確認は入力チェックより先に走らせます。順番を間違えると、エラーの文面が、見えてはいけないものの存在を教えます。
- テストが緑でも、設計書が決めていないことは確かめられません。決め忘れは、人が触って初めて出ます。
- 前のイシューで決めたことは、あとのイシューで効いてきます。データの持ち方に時間をかけた見返りは、そこで返ってきます。
- 触っていないテストが落ちたら、アプリではなくテストの根拠が古くなったことがあります。直させる前に、自分で読みます。
