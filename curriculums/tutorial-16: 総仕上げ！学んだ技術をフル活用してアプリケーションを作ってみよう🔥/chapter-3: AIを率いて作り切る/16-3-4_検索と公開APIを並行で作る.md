# 16-3-4: 検索と公開APIを並行で作る

## 🎯 このセクションで学ぶこと

- `claude -w` で書く場所を増やし、決まりのほうを道具に合わせて直せるようになる。
- 書く場所ごとに動く環境を持たせて、そこで測れるようになる。
- 1組しかない資源の取り合いを、進め方で避けられるようになる。

---

## 導入

残っているのは検索と公開APIの2本です。この2本は互いを必要としないので、**書く時間を重ねられます**（16-2-4）。

回し方は16-3-1から16-3-3で通したものと同じです。新しく増えるのは、書く場所を2つに分けることと、そこで動かせるようにする手だけです。

## 書く場所を増やす前に、フックを直す

書く場所には `vendor/` が来ません（15-5-1）。いまのフックはそこに `sail` があることを前提にしているので、このまま書く場所を開くと、**編集のたびに失敗して全部の編集が止まります**。

この直しはどのイシューにも属さないので、`chore/` のブランチを1本切って進めます（16-3-1）。ブランチを切るところから頼みます。

```text
chore/hook-guard というブランチで進めたい。main を最新にしてから切って。

このあと worktree で書く場所を増やす。そこには vendor/ が来ないので、いまのフックは
編集のたびに失敗して全部の編集を止めてしまう。sail が無い場所では素通りする形に直して。
```

> 💡 **進行例について**: AIとの開発は毎回違う流れになります。ここに示すのは一つの進行例です。あなたの画面と違っていても、チェックリストを満たしていれば正解です。

**`.claude/settings.json`** のフックの2本が、このような形になります。

```json
      {
        "type": "command",
        "command": "test -x vendor/bin/sail || exit 0; ./vendor/bin/sail pint >&2"
      },
      {
        "type": "command",
        "command": "test -x vendor/bin/sail || exit 0; ./vendor/bin/sail artisan test >&2 || exit 2"
      }
```

`test -x vendor/bin/sail || exit 0;` は、`sail` というファイルが実行できる形で無ければ、そこで何もせずに正常終了する、という意味です。書く場所ではこの先が走らず、元のフォルダではこれまでどおり走ります。**両方に足す**のを忘れないでください。整形の側だけ直すと、テストの側で止まります。

書き換えた設定はその場で読み直されます（15-4-1）。効きを確かめたらプルリクエストを出し、**書く場所を作る前に** `main` へマージしておいてください。書く場所は `main` から枝分かれするので、あとから入れると2つの書く場所のどちらにも届きません。

## 書く場所は `claude -w` で作る

15-5-1で使った形です。書く場所ごとに名前を付けます。

```bash
# 自分のリポジトリのフォルダで実行する
claude -w search
```

`.claude/worktrees/search/` ができて、そのフォルダでセッションが開きます。公開APIのほうは、別のターミナルで `claude -w api` です。開いたら、16-1-1の構えを整えます。`/model` と `/effort` を確かめて、`/rename` に番号を入れて名前を付けます。

**書く場所を2つ開いて、構えを整えたところ**

<img alt="16-3-4_1.png" src="../../../image/16-3-4_1.png">

`claude -w` が最初に作る枝の名前は `worktree-<名前>` です（15-5-1）。これは入れ物で、プルリクエストに載る枝は、**このあと `/start` が切るほう**です。`CLAUDE.md` に書いた決まり（`feature/issue-<番号>-<英字の短い名前>`）が効くのは、そちらです。

切られた名前は、毎回見てください。**決まりから外れることがあります**。上の画面のあと `/start` が切ったのは `feat/search` で、決まりの形になっていませんでした。見つけたら、名前を付け替えさせます。決まりが守られているかを確かめるのは、書いた自分の仕事です。

`.env` は、15-5-1で作った `.worktreeinclude` に書いてあれば運ばれます。`claude -w` は既定で `origin` のデフォルトブランチから枝を切るので、`main` を最新にする手間は要りません（2026年8月時点）。

## 書く場所でも動かせるようにする

worktreeで書いた行は、置いただけでは1行も動きません。理由は2つあります。

Sailのコンテナは、`sail up -d` を打ったフォルダを中へ映しています。コンテナの中で動くPHPが読むのは、いつでもそのフォルダのファイルです。加えて、worktreeにはGitが管理しているファイルしか来ないので、`vendor/` と `.env` がありません（15-5-1）。

そこで、書く場所ごとに**動く環境を1つずつ持たせます**。3つ用意すれば動きます。

### `.env` を運ぶ仕掛けを、このリポジトリにも置く

15-5-1で前のアプリに作った `.worktreeinclude` は、このリポジトリにはありません。書く場所を作る前に置きます。

```text
worktree を作ったときに .env が運ばれるようにしたい。
リポジトリのいちばん上に .worktreeinclude を置いて、.env の1行を書いて。
これはコミットして共有するファイル。
```

置き忘れると、書く場所に `.env` が来ません。そこでAIに `cp .env.example .env` をやらせようとしても、**許可の指定で止まります**（16-2-2で `.env` を `deny` にしました）。止まるのが正しい動きです。先に置いてください。

### ポートをずらす

`compose.yaml` は `APP_PORT`・`FORWARD_DB_PORT`・`VITE_PORT` を見ます（16-2-1）。`COMPOSE_PROJECT_NAME` と併せて、書く場所ごとに違う値にします。運ばれてきた `.env` に、次の4行を足します。検索の場所なら、こうです。

```text
APP_PORT=8001
FORWARD_DB_PORT=33061
VITE_PORT=5181
COMPOSE_PROJECT_NAME=teamchat-search
```

公開APIの場所は `8002`・`33062`・`5182`・`teamchat-api` のように、また別の値にします。`APP_URL` も、そのポートに合わせて直します。

**この4行は、自分の手で書きます。**`.env` はAIが触れないようにしてあるからです（16-2-2）。VS Codeで開いて足してください。頼んで止まるのを見てから自分で打つより、先に自分でやるほうが早いところです。

### ライブラリを取ってくる

`vendor/` は運べません。大きすぎるので `.worktreeinclude` には書きません（15-5-1）。書く場所ごとに取ってきます。

```text
このフォルダでライブラリを取ってきて、コンテナを起動して、テーブルと初期データを入れて。
```

16-2-1でやったのと同じ並びです（`composer install` → `sail up -d` → `key:generate` → `migrate --seed`）。ここは `.env` を触らないので、AIに任せられます。

これで、書く場所が**それぞれ独立して動きます**。ブラウザで開くのは `http://localhost:8001` と `http://localhost:8002`、データベースも別々です。

> ⚠️ **注意**: 設定のキャッシュ（`config:cache`）が残っていると、`phpunit.xml` の指定より強く効いて、テストが開発用のデータベースを触りに行きます。書く場所で見当のつかない落ち方をしたら、`sail artisan config:clear` を試してください。

### 環境を2つ作らない道もあります

`composer install` は書く場所ごとに時間と容量を使い、コンテナも2つぶん動きます。手元が重いと感じたら、**書く場所では書くだけにして、元のフォルダに持ち込んで測る**形に戻せます。その場合は、プルリクエストを出してから `gh pr checkout <番号> --detach` で取り出します。測る場所が1か所になるので、次の節の取り合いに気をつけることになります。

## 環境を分けないと、資源を取り合う

コードの衝突は、gitが教えてくれます。教えてくれないのは、**1組しかないもの**のほうです。

| 1組しかないもの | 何に使うか |
|:--|:--|
| Sailのコンテナ | アプリを動かす |
| 開発用のデータベース | 初期データを入れて画面で確かめる |
| ブラウザと、スクリーンショットの置き場 | UATの証拠を残す |

2本ぶんの検証を同じフォルダで行き来させると、片方の `migrate:fresh --seed` が、もう片方の確認の最中に走ります。テーブルが落ちている一瞬に当たった要求は500を返し、サイドバーが空の画面が出ます。**症状がアプリの不具合とそっくり**なので、原因にたどり着くまでに時間を取られます。2本を並行させたとき、実際にこれで1時間ほど失った落とし穴です。

書く場所ごとに環境を持たせれば、この取り合いは起きません。上でポートとプロジェクト名をずらしたのは、そのためです。**環境を2つ作らない道を選んだときだけ**、次の3つを決めておきます。

- 元のフォルダの向きを変えるのは、確かめているあいだだけにする。終わったら `main` に戻す
- `migrate:fresh --seed` を打つ前に、もう1本の確認が途中でないかを見る
- スクリーンショットの名前を、イシューごとに分ける（片づけるときも自分の分だけ消す）

## 🏃 2本を回す

思いどおりに直らない・壊れたと感じたら、14-5-1（直らないときの型）へ。応急は `git restore .` です。

書く時間は重ね、受け取りは1件ずつ通します。

1. 【自分】書く場所を2つ作る（`claude -w search`・`claude -w api`）。ターミナルは、検証する場所のぶんと合わせて3枚になる
2. 【自分】書く場所ごとに `/rename` で名前を付ける。番号を入れておくと `/resume` から選べる（14-5-2）
3. 【自分】それぞれで `/start` を打って着手する。計画を承認すると、実装が `@agent-implement` に渡る
4. 【AI】実装させる。フックが編集のたびに整形とテストを回すので、落ちればその場で戻ります
5. 【自分⇄AI】`/code-review`・`/review-diff`・`/security-review` を当てる。差分は自分でも読み、直させるものを決める
6. 【自分⇄AI】ブラウザで確かめ、`/uat` を回す。開くのは、その書く場所のポート
7. 【AI】コミットさせ、pushして `/pr` でプルリクエストを出させる
8. 【自分】プルリクエストの本文と「Files changed」を読んでマージする
9. 【自分】もう1本は、**書く場所で** `main` の最新を取り込んでから（`rebase`）、そこでテストをもう一度回す。コンフリクトはそこで解消させ、出てきた差分は自分が読む（15-5-3）
10. 【自分】2本とも閉じたら、書く場所とブランチを片づける

手を止めるのは、5・6・8・9・10です。

書く場所が独立して動くので、**測るところも書く場所です**。持ち込む手が要りません。ただし、書いたセッションが自分の差分を測る形になります。15-5-2で分けたのは、書いた本人に受け取りを判定させないためでした。**判定するのは、報告を読む自分**です。そこは変わりません。

3の `/start` は、枝を切ったあとplanモードに入り、調べてから計画を書きます。設計書側と現状のコード側を、別々のサブエージェントに同時に投げることもあります（15-3-3の「同時に動かせる」）。2つの書く場所で同じことが起きるので、走っている担当は4体になります。

**2つの書く場所で、調査を並行させているところ**

<img alt="16-3-4_3.png" src="../../../image/16-3-4_3.png">

見るのは、**何を根拠に調べているか**です。左は設計書を原文で、右は現状のコードとテストの書き方を読んでいます。ここで読まれたものが計画の材料になるので、見当違いのところを見ていたら、承認する前に気づけます。

6で開くURLを間違えないでください。書く場所ごとにポートが違います。`http://localhost` のままだと、**元のフォルダのアプリか、もう1本の書く場所**を見ていることになります。`/uat` にも、そのポートを渡します。

7でプルリクエストを出すのは、測り終えたあとです。順番を逆にすると、本文に書いたテストの結果が、そのあとの直しで古くなります。

9で `main` の最新を取り込むのは、1本目がマージされたぶんを自分のコミットの下に積むためです。**ここで初めて2本ぶんが同じところで回ります**。取り込んだあとは push が要りますが、書き換わった履歴を送ることになるので、そのままでは通りません（12-1-4）。AIに任せると `--force-with-lease` を付けて送ります。**同じ枝を他の誰も触っていないことが前提**の操作なので、1人で回しているあいだだけの手だと覚えておいてください。

10で片づけるとき、書く場所のセッションを `/exit` で閉じると**2択が出ます**（15-5-1）。自分が付けた名前と、積んだコミットの数が出て、書く場所を残すか消すかを聞かれます。

選ぶのは、**そのときどこまで進んでいるか**で変わります。

| いつ閉じるか | 選ぶもの |
|:--|:--|
| まだ測っている途中・直しが残っている | 残す（Keep）。`claude -w <名前>` で開き直せます |
| プルリクエストがマージ済みで、片づけに来た | 消すほう |

消すほうを選ぶと、`All changes and commits will be lost` と出ます。この文だけ読むと、**怖い書き方**です。消えるのは手元の写しだけで、pushしてあるぶんはリモートに残っています（15-5-1）。マージまで済んでいれば、中身は `main` に入っているので、なくなるものはありません。

逆に、pushしていないコミットがあるときに消すと、**本当に消えます**。数が出ているので、閉じる前にそこを見てください。

そのうえで、`main` を最新にしてから書く場所とブランチを消します。ブランチを消すときに「まだHEADに入っていない」という警告が出ることがあります。プルリクエストを積み直す形やまとめる形で受け取ると、`main` に載るのは別のコミットになるので、gitからはそう見えます。中身は同じなので、消して構いません。

## 検索: 権限をポリシーに置けない1本

> 💡 **進行例について**: AIとの開発は毎回違う流れになります。ここに示すのは一つの進行例です。あなたの画面と違っていても、チェックリストを満たしていれば正解です。

検索が権限マトリクスの形に入らないことは、16-1-5で見たとおりです。実装でも判定をポリシーに置けず、その帰結が取り出すときの絞り込み2行になって出てきます。**見られるチャンネルに限ること**と、**削除済みを外すこと**です。チャンネルを見てよいかの判定は16-3-2で1か所に置いてあるので、それを呼ぶだけで済みます。

この2つを書き忘れても、**テストは緑のまま通ります**。書かなかったことを知らせてくれるものが無いからです。16-1-6で、検索と公開APIに「プライベートチャンネルの内容が漏れない」の行を独立して置かせたのは、この形の穴を人が確かめる窓口を作るためでした。

もう1つ、キーワードの記号をどう扱うかが、16-1-6の穴出しで挙がっていました。そこで決めたエスケープが効いているかは、16-3-2と同じやり方で測れます。テストが全部緑になったところでエスケープを外して回すと、`%` の1文字だけで当たる件数が増えます。ここでは1件が6件になりました。初期データの入ったデータベースで数えると、削除済みを除いた全部が並びます。外すのは、`git checkout --detach` で持ち込んだ元のフォルダです。書く場所には `vendor/` が来ないので、そちらでは測れません。外すのも戻すのも自分の手でやり、`./vendor/bin/sail artisan test` も自分で打ってください。理由は16-3-2と同じで、AIに頼むとフックのテストが落ちて、AIが直しに入ります。測ったらその場で戻し、`git status` を空にしてから次へ進みます（この直しはコミットしません）。

## もう1つの目で、同じ差分を見る

この2本が作っているのは、**見えてはいけないものが外に出る口**です。検索は、メンバーでない人のプライベートチャンネルを引っかけてはいけません。公開APIは、ログインしていない相手に応えます。16-1-4で決めた出口3つ（画面・検索・公開API）のうち、2つがここで揃います。

受け取りに、道具をもう1本足します。`/security-review` は最初から入っていて、**いまのブランチの変更を、セキュリティの目だけで**通します（2026年8月時点）。

```text
/security-review
```

`/code-review` との違いは、見る幅です。`/code-review` は一般的な間違いを広く探します。`/security-review` は狭いところを深く見ます。同じ差分に、別の目を当てる形です。毎回の受け取りは `/code-review` と `/review-diff` で足りますが、**外に出る口を作った回**には、これを足します。

報告は、そのまま受け取りません。ここでも判定は自分です。出てきたものを、設計書の決めと突き合わせてください。「削除済みは検索と公開APIから外す」も「メンバーでない人にプライベートチャンネルの存在を出さない」も、こちらが先に決めたことです（16-1-4・16-1-5）。決めと合っていない指摘が出たら、直す前に**どちらが正か**を考えます。

## 公開API: 画面が無い機能の受け取り

`/uat` のSKILL.mdには、ブラウザを動かす道具・開くURL・ログイン情報・スクリーンショットの置き場が書いてあります。**この4つとも、公開APIには当てはまりません**。画面が無く、ログインしないのが正で、撮るものがありません。

残るのは「受け入れ条件を1行ずつ、満たしているかと、そう判断した理由を証拠つきで報告する」という芯だけです。証拠の作り方は、自分で決めることになります。

| 確かめたいこと | 証拠の作り方 |
|:--|:--|
| 求めた形で返っているか | `curl`（11-1-4）で叩く。ブラウザのアドレス欄と同じ経路になる |
| 見えてはいけないものが出ていないか | 応答の中にその言葉が1回も出てこないことを数える（`grep -c` が0） |
| 存在しない番号と、見えない番号の見分けが付かないか | 2つの応答を突き合わせて、差が無いことを見る（`diff`） |

コマンドを自分で組み立てる必要はありません。何を確かめたいかを渡してAIに叩かせ、返ってきた応答を自分が読みます。

画面のときは「ページの中にその文字が出ていない」で確かめていました。APIでは応答そのものが手に入るので、**1バイトも違わないところまで見られます**。

この件では、素直に書くと受け入れ条件を満たせない場所が1つあります。見つからなかったときに `abort(404, '…')` で返すと、Laravelは**HTMLのエラー画面**を返します。

```text
$ curl -i http://localhost/api/channels/4/messages
HTTP/1.1 404 Not Found
Content-Type: text/html; charset=UTF-8
...
<!DOCTYPE html>
```

LaravelがJSONを返すのは、JSONを期待している要求のときだけです。ブラウザのアドレス欄も `curl` も、そうは名乗りません。受け入れ条件は「アドレス欄にURLを入れて確かめる」と書いてあるので、この経路で文言が入っていないと合格しません。**返す形をコントローラで組み立てる**ようにすると、求めた文言がそのまま返ります。

削除済みを外す1行は、ここでも要ります。書き忘れると、消したはずの本文が**ログインしていない相手にも**出ます。同じデータで、画面側には「このメッセージは削除されました」が残り、APIには何も出ないのが正しい形です。取り出す向きを経路ごとに書く、という16-1-4の決めが、いちばん外側の出口で効いています。

### 呼ぶときに、どこで測るかを渡す

`/uat` のSKILL.mdは、元のフォルダで動かす前提で書いてあります。書く場所で測るなら、そのポートを渡します。環境を2つ作らない道を選んだなら、取り出すところから頼みます。

```text
/uat PR #7 はワークツリーで扱ったものなので、gh pr checkout <番号> --detach でPRを取り出してもらってから、uatを回したいです
```

画面が無い件は、そこも相談します。

```text
/uat 公開APIについてはブラウザ上で確認できないと思うので、進め方を提案いただきたいです
```

2回目からは、これを毎回打つことになります。**繰り返すと分かったら、道具の側に入れます**（15-1-2）。

```text
/skill-creator 加えて、いまの2つを /uat に足してほしい。
```

## コンフリクトの解消

並行させた2本を積み直すと、ぶつかるのは**2本が同じ1行を書き換えたところ**だけです。片方が足した行と、もう片方が足した行が別の場所にあれば、gitが自動でつなぎます。

実際にぶつかったのは2か所で、どちらも意外な場所でした。1つは、ルートを並べたファイルの先頭に置いた**説明のコメント1行**です。ルートの定義そのものは自動でつながり、「このファイルには何の分が入っているか」を書いた1行だけが残りました。解消は、どちらかを選ぶのではなく**両方を足す**ことです。

もう1つは、2本が同じ回に、同じ場所へ、それぞれ別の共通処理を切り出していた例です。どちらも `/review-diff` の重複の観点から出てきた直しで、置き場所まで一致していました。ここでも取るのは両方です。あわせて、**使われなくなった取り込みの行は、両方消すのが正解**になります。整形の道具は消してくれないので、印だけ外して通すと、使っていない行が残ります。

解消はAIにさせて構いません。出てきた差分は自分が読みます（15-5-3）。

## ✨ まとめ

- 書く場所は `claude -w` で作ります。ブランチ名は道具が決めるので、合わないときは決まりのほうを直します。
- 並行で困るのはコードの衝突ではありません。1組しかないコンテナとデータベースを、2本ぶんの検証で取り合うほうです。書く時間は重ね、受け取りは1件ずつ通します。
- 書く場所は、`.env` とライブラリとポートをそろえれば独立して動きます。測るところも書く場所になり、持ち込む手が消えます。
- 環境を分けないなら、1組しかないコンテナとデータベースを取り合います。そのときは受け取りを1件ずつ通し、プルリクエストを `gh pr checkout` で取り出して測ります。
- 検索の権限は、取り出すときの絞り込みに乗ります。ポリシーには置けません。書き忘れてもテストは緑のままなので、受け入れ条件の側に確かめる行を置いてあります。
- 画面が無い機能では、証拠の作り方を自分で決めます。応答そのものを数える・突き合わせるところまでできます。
- コンフリクトは、2本が同じ1行を書き換えたところにだけ出ます。片方を選ぶとは限らず、両方残すことも、両方消すこともあります。
