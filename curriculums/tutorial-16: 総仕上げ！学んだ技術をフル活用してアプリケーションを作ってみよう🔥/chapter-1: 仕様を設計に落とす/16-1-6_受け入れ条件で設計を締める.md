# 16-1-6: 受け入れ条件で設計を締める

## 🎯 このセクションで学ぶこと

- 受け入れ条件とテスト観点をAIに起こさせ、人の側で判定して確定できるようになる。
- 受け入れ条件を、実装単位ごとに2〜4行の量に保てるようになる。
- 設計の穴を、聞き方を変えて自分で出せるようになる。

---

## 導入

16-1-5までで、何を作るか・どう見えるか・どう持つか・誰が何をしてよいかが揃いました。残っているのは、**できあがったかどうかを判定する紙**です。実装が返ってきたときに受け取ってよいかどうかは、この紙で決めます。

## 起こすのはAI、判定は人

受け入れ条件を手で書き起こす節ではありません。14-2-2では、やりたいことを渡して問いに答え、受け入れ条件の形にまとめさせました。今回はそれを7つの実装単位ぶん、一度にやります。まとめて起こせるのは、根拠になる設計書がもう揃っているからです。

実装単位は7つです。認証・チャンネル・メンバー管理・メッセージ・スレッド・検索・公開API。この線を引いたのは仕様書のほうです。機能要件が、アカウント（この教材では認証と呼びます）・チャンネル・メンバー管理・メッセージ・スレッド・検索・公開APIの7つの見出しに分かれていて、機能一覧の番号もその並びのとおりに振ってあります。16-1-2の進行例で作った21本なら、`F-01`〜`F-03` が認証、`F-04`〜`F-07` がチャンネル、`F-08`〜`F-10` がメンバー管理、`F-11`〜`F-14` がメッセージ、`F-15`〜`F-17` がスレッド、`F-18` が検索、`F-19`・`F-20` が公開APIと、範囲がそのまま切れます。

残るのは初期データの1本で、これはどの単位にも入りません。3つのアカウントは認証、4つのチャンネルはチャンネルというように、その機能を作った単位が自分のぶんを一緒に用意します。機能の本数はあなたの一覧と違って構いません。束ねる線は仕様書の側にあるので、本数が何本でも7つに落ちます。この単位を作業の票に割るのはChapter 2でやります。

人の側の仕事は、返ってきたものへの判定です。

**判定1: 型になっているか**

操作すれば合否が決まる文になっているかを見ます。粒度の見本は、Tutorial 14でリプライ機能に書いた4行です。

```text
- ポストを1件開くと、そのポストとリプライの一覧が見える
- 本文を入れてリプライを送ると、一覧に増える
- 本文が空のままだと、エラーが表示されてリプライは増えない
- 自分のリプライは消せて、他人のリプライは消せない
```

「使いやすいこと」「正しく動くこと」のような、人によって合否が割れる文が混ざっていたら書き直させます。

**判定2: 観点が抜けていないか**

次の4つを、自分の目で当てます。

| 観点 | 見るところ |
|:--|:--|
| 決めたとおりでない使われ方 | 空のまま送る、上限を超える、順番を飛ばす（13-8-1） |
| 権限の否定形 | 他人のものを操作しようとしたとき、メンバーでない人が開いたとき |
| 横断の交差 | 検索と公開APIに「プライベートチャンネルの内容が漏れない」の行があるか |
| スコープ外 | 作らないと決めたものが、条件の中に紛れ込んでいないか |

3つ目は、権限マトリクスを1行ずつ潰しても出てきません。16-1-5で書いたとおり、この2つは表の形に入らないからです。無ければ足させてください。

**判定3: 多すぎるものを刈る**

条件が細かく分かれすぎていたら、まとめさせるか落とします。その物差しになるのが、次の行数の線です。

---

## 受け入れ条件の行数

受け入れ条件は、**1つの実装単位につき2〜4行**に保ちます。この行は、あとで人が手で1行ずつ試して潰す約束だからです。機能一覧の `F-xx` の1本ずつに書き出すと70行を超える量になり、人が全行を通し切れません。実際、Chapter 4で全部を通すときには、この量が効いてきます。

網羅は、テスト観点のほうに置きます。そのテスト観点も、書くのは「何を見るか」までです。入力の組み合わせや境界の値を全部書き出すと数百行になり、人が読み通せる量を超えます。組み合わせを潰すのはテストコードの仕事で、そちらはAIに任せます。判定は `failed` が0であることです。

---

## 🏃 受け入れ条件を起こして、設計を締める

思いどおりに直らない・壊れたと感じたら、14-5-1（直らないときの型）へ。応急は `git restore .` です。

### Step 1: 2つを起こさせる

```text
最後に受け入れ条件とテスト観点。docs/design/ にあるものを全部読んでから書いて。

- 根拠は docs/design/ の一式ぜんぶと docs/spec.md、mockup/
- ファイル名と置き場は docs/design/README.md のとおり
- 受け入れ条件は、実装単位ごとに2〜4行。実装単位は 認証／チャンネル／メンバー管理／メッセージ／スレッド／検索／公開API の7つ
- 受け入れ条件には `AC-<単位の番号>-<連番>` の番号を振る。単位の番号は上の並びの順（認証が1、公開APIが7）
- 「〜すると、〜になる」の形で、ブラウザで操作すれば合否が決まる文にする
- テスト観点は、ID・何を確かめるか・区分（正常系／異常系／境界値）・元になった設計書 の4列

線を1本引いておく。受け入れ条件は、人が手で全部試して1行ずつ潰すためのものだから、2〜4行に保って。
網羅はテスト観点のほうに置いて、そちらは観点までにする。組み合わせを全部書き出さなくていい。
```

> 💡 **進行例について**: AIとの開発は毎回違う流れになります。ここに示すのは一つの進行例です。あなたの画面と違っていても、チェックリストを満たしていれば正解です。

受け入れ条件は7つの単位で23行になりました。依頼に書いていないのに入っていて、いちばん効いたのが、条件の手前に置かれた**試す前の準備**です。初期データの3人を、役として固定してありました。

| 使う人 | このアプリでの立場 |
|:--|:--|
| 佐藤 太郎 | 「開発」と「採用プロジェクト」を作った人 |
| 鈴木 花子 | 「採用プロジェクト」のメンバー |
| 高橋 健 | 「採用プロジェクト」のメンバーではない人 |

この表があると、全23行が「誰でログインして、何をするか」まで書ける形になります。「高橋でログインすると、採用プロジェクトが一覧に出ない」のように、読んだ人がそのまま手を動かせます。仕様書に初期データが固定で指定されていたことが、そのまま受け入れ条件の道具になりました。

この節は、あとで名前で呼びます。16-2-2では `/uat` に「試す前の準備も読んで」と書き込み、Chapter 4の全数の受け入れでも読み直します。**自分のファイルに同じ節が無ければ、ここで足させてください。** 見出しの名前は「試す前の準備」に揃え、受け入れ条件より前、ファイルの先頭の節に置いておくと、あとで指すときに迷いません。

### Step 2: 3つの判定を当てる

上の判定1から3を、返ってきた23行に当てます。ここは渡せません。

横断の交差だけは、当て方を具体的に書いておきます。検索の行と公開APIの行を見て、「メンバーでない人が探しても出てこない」「作った本人が呼んでも公開チャンネルしか返らない」に当たる行があるかを確かめてください。無ければ足させます。人が手で漏れを確かめる窓口は、**この2行だけ**です（残りはテスト観点の側で見ます）。

### Step 3: 設計の穴を、質問の形で出させる

一式が揃った状態で、最後にもう1本投げます。ここがこの節でいちばん効きます。

```text
これで一式がそろった。最後に、一式を通しでレビューしてほしい。
ただし「よくできています」のような講評は要らない。

実装に入るとして、答えに詰まる質問を挙げて。設計書を読んでも決まっていなくて、
コードを書き始めたら手が止まるところ。答えられない質問が出てきたら、それが設計の穴だから。

- 根拠は docs/design/ の一式と docs/spec.md、mockup/
- 質問の形で挙げて。「〜が書かれていません」ではなく「〜のとき、どうしますか」
- 重い順に。思いつきの粗探しではなく、本当に手が止まるものだけ
- 設計書どうしが食い違っているところがあれば、それも一緒に

ファイルはまだ直さなくていい。挙げるだけ。
```

「一式をレビューして」と頼むと講評が返ってきます。**答えに詰まる質問を挙げて**、という聞き方に変えると、出てくるものが変わります。このとき出た中から4つ、質問の形に起こして挙げます。

| 出てきた穴 | なぜ手が止まるか |
|:--|:--|
| 時刻の基準と表示の言語をどうしますか | Laravelの既定は協定世界時と英語です。そのままだと、デザイン指定書が固定した日時の表記が9時間ずれ、日付の区切りの曜日が英語で出ます |
| パスワードの上限をどうしますか | 仕様書は「上限は決めなくて構いません」としています。Laravelの既定のハッシュは72バイトより先を捨てるので、上限を置かないと、極端に長い入力を黙って切り落としたまま受け付けます |
| 検索のキーワードに `%` や `_` が入ったらどうしますか | どちらもデータベースの検索で「何でも当てはまる」記号として扱われます。そのまま渡すと、`%` ひとつで全件が一致します |
| 文字数をどう数えますか | 改行を1文字と数えるか、Windowsから貼り付けた改行をどう扱うかで、同じ本文の判定が入力元によって変わります |

どれも、**実装に入れば必ず踏むのに、設計書を眺めていても気づかない**種類です。設計書は個別にはどれも整合していて、読んでも矛盾は見つかりません。それでも決まっていないことが残ります。

なお、「挙げるだけ」と書いても、そのままファイルを直しに入ることがあります。出てきた内容が本物なら受け取って構いませんが、**依頼していない差分が混ざります**。受け取る前に `git diff` で範囲を確かめます。

### Step 4: 直したら、下流も直す

設計を1か所直すと、そこを根拠にしていた受け入れ条件とテスト観点が、黙って古くなります。実装が正しくても落ちるテストになり、しかも設計書どうしは矛盾しないので、突き合わせでは見つかりません。

ここで効くのが、テスト観点の表の「元になった設計書」の列です。直した設計書の名前で引けば、直しそこねた観点が出てきます。穴を潰して設計を動かしたら、必ずこの列で引き直してください。

引くところはAIに回せます。直した設計書の名前を渡すだけです。

```text
穴出しの結果で docs/design/data.md を直した。
テスト観点の「元になった設計書」の列が data.md になっている行を全部出して。
そのうち、いまの data.md と食い違っている行があれば、どこがどう古いのかも一緒に。
```

出てきた行を読んで、直すかどうかは自分が決めます。設計を動かしたぶんだけ古くなっているので、たいていは直します。

### Step 5: 完成条件を確かめて、コミットする

`docs/design/README.md` を開いて、そこに書かれているファイルが全部揃っているかを突き合わせます。書く量の決まりも、この README に書いてあります。揃っていたら `main` にコミットします。

**この一式は、ここで終わりではありません。** 実装中に設計とのズレが見つかったら、先に直すのは設計書のほうです。提出物の中心なので、実物と食い違ったまま終えません。

もう1つ、この節で済んだことがあります。14-3-1で、計画を「なし」「planモード」「設計書」のどれで持つかを変更ごとに選びました。設計書を選ぶ条件として挙がっていたのは、受け入れ条件を実装のあとで何度も突き合わせる・作業が複数に分かれて1回のやり取りでは終わらない・新しいセッションを起動して実行する、の3つです。今回はChapter 4で全体と突き合わせ、作業は7つの実装単位に分かれ、その1本ずつを、前のやり取りを持ち越さずに回します（16-3-2）。3つとも当たるので、この7本ぶんの計画は **`docs/design/` の一式として持ちます**。アプリ全体ぶんの計画の持ち方は、ここで選んだことになります。

Chapter 1はここまでです。足場を組みに入る前に、`/usage` で枠の残りを見ておいてください（14-1-6）。Chapter 2から先は、実装とテストが加わるぶん、消費が一段増えます。

これで図面はそろいました。Chapter 2では、この図面を読ませて作るための足場を組みます。

- [ ] 受け入れ条件が、実装単位ごとに2〜4行になっている
- [ ] 受け入れ条件の1行ずつに `AC-<単位の番号>-<連番>` の番号が付いている
- [ ] 受け入れ条件の手前に「試す前の準備」の節があり、初期データの3人の立場が書いてある
- [ ] すべての行が、ブラウザの操作で合否が決まる文になっている
- [ ] 検索と公開APIに、プライベートチャンネルの内容が漏れないことを確かめる行がある
- [ ] テスト観点が、組み合わせの書き出しではなく観点で書かれている
- [ ] 穴出しで出てきた質問に、決めと理由が付いている
- [ ] `docs/design/README.md` の構成と突き合わせて、揃っている
- [ ] `docs/design/` の変更が `main` にコミットされている

## ✨ まとめ

- 受け入れ条件とテスト観点はAIに起こさせる。人がやるのは、型・観点・取捨の判定。
- 受け入れ条件は実装単位ごとに2〜4行。人が手で全行潰す約束なので、増やしすぎると通し切れない。
- 網羅はテスト観点からテストコードへ。観点は「何を見るか」までにする。
- 検索と公開APIの漏れは、権限マトリクスを潰しても出てこない。受け入れ条件に独立した行として置く。
- 「答えに詰まる質問を挙げて」と聞くと、講評では出ない穴が出る。聞き方が変わると、出るものが変わる。
- 設計を直したら、それを根拠にしている受け入れ条件とテスト観点も引き直す。
- 14-3-1で設計書を選ぶ条件が3つとも当たるので、この一式が計画そのものになる。アプリ全体ぶんの計画の持ち方は、ここで選び終えている。
