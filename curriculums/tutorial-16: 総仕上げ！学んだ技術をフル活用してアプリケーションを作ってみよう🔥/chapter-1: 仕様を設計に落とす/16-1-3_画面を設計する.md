# 16-1-3: 画面を設計する

## 🎯 このセクションで学ぶこと

- モックアップを根拠に、画面一覧・画面遷移図・画面項目定義・入力チェックをAIと確定できるようになる。
- 見本が動きを示唆している表示を、自分の設計の判断として受け取れるようになる。
- 画面設計をどこまで書くかを、自分で決められるようになる。

## 導入

13-3-3ではワイヤーフレームを描きました。今回は描きません。画面の見た目は、モックアップという完成した形でもう手元にあるからです。デザインが支給される現場では、画面設計は描く仕事から**読む仕事**に変わり、決めることの中身も入れ替わります。

この節は、新しいセッションで始めます。1つの節を書き終えたところが、作業の切れ目です（14-5-2）。前の節を閉じる前に `/context` を1回見ておくと、1節ぶんでどれくらい積もるのかが分かります。前の節で決めたことは `docs/design/` に置いてあるので、切っても口で言い直さずに読ませられます。起動したら `/model` で `opus` を選び直し（`s` で選ぶとそのセッション限りなので、開き直すたびに選びます）、`/rename` で名前を付けてください。Chapter 1の残りの節も、同じ構えで始めます。

## モックアップがあっても決まらないもの

モックアップは静的なHTMLです。画面から画面へのリンクは動くので見て回れますが、中のボタンや入力欄は押しても何も起きません。そこから読み取れないものが、この節で決めることです。

| 決めること | なぜモックアップから読み取れないか |
|:--|:--|
| 画面の名前と番号（`SC-01` から。13-3-1） | ファイル名しか付いていないので、設計書で呼ぶ名前を決めます |
| どこから、何を押すと、どこへ移るか（13-3-2） | 静的なHTMLなので、送信に成功したあとの着地先が描けません |
| 項目の型と必須（13-3-3） | 見た目からは、表示なのか入力なのか、必須なのかが決まりません |
| 入力チェックとエラーメッセージ（13-3-4） | 上限を超えたときや空のときの見え方が、見本に描かれていません |

このうち、着地先は特に落ちやすいところです。「キャンセル」の戻り先は絵に描いてありますが、「作成する」に成功したあとどこへ行くかは、どこにも書いてありません。

## 使う道具を決める

もう1つ、モックアップを読む前に決めておくことがあります。この画面をどの道具で組むかです。

モックアップにJavaScriptは使われていません。ただしそれは、ファイルをブラウザにドラッグするだけで開けるようにするための、見本側の作りです。アプリで使うかどうかは、設計の判断として自分が決めます。モックアップの `README.md` にも、その旨が書いてあります。

この教材では、**JavaScriptを扱っていません**。Tutorial 1からTutorial 12までに、JavaScriptを学ぶ章はありません。ですから、このアプリはBladeとCSSとフォームの送信だけで組める形に設計します。禁止ではありませんが、必須にもしません。

### 動いて見える表示を、どう受け取るか

この決めが最初に効くのが、メッセージの投稿欄です。モックアップには `0 / 1,000 文字` と出ています。

**投稿欄の文字数表示**

<img alt="16-1-3_1.png" src="">

数字が `0` から始まっているので、打つたびに数が動く表示に見えます。それを実現するには、入力を見張り続ける仕掛けが要ります。デザイン指定書はここを言い切っておらず、入力に追随させるなら `248 / 1,000 文字`、追随させないなら `1,000文字まで` の目安表示にする、とどちらも許しています。今回は追随させない側を選び、上限を超えたことは送信したときのエラー文で伝えます。仕様書は「並び・項目・言葉づかい・状態の見せ方」が合っていればよいとしているので、この形で満たせます。

同じ読み替えが、ほかにも3か所あります。

| 見本の見え方 | 置き換えた形 |
|:--|:--|
| メッセージのその場編集 | 編集用のURLでその画面を開き直し、その1件だけを入力欄にする |
| 削除の確認が同じページの中で開く | 別のURLで確認の画面を出す |
| 検索結果から、そのメッセージの場所へ移る | リンク先にアンカーを付けて、ブラウザに運ばせる |

**見本が動いて見えるところは、読み違えの種です。** 絵のとおりに作らなければいけないと読むと、作れない機能が出てきて、機能そのものを落とす判断につながります。決めたことは、確認事項の「自分で決めたこと」に理由ごと残してください。この決めは、これから書く画面項目定義と入力チェックの全部に効きます。

## 書く量を決める

画面項目定義は、主要な画面だけ書きます。全部の画面ぶんを書くと、同じ行が何度も並びます。スレッドの返信1件は、チャンネルのメッセージ1件と同じ項目を持つので、「メッセージと同じ」と書けば足ります。

**どこまで書くかを決めるのも設計です。** 多く書いた設計書が良い設計書ではありません。あとから読む人が判断に使う分だけを書きます。この線は `docs/design/README.md` にも「書く量の決まり」として書いてあります。

## 🏃 画面まわりを起こして、突き合わせる

思いどおりに直らない・壊れたと感じたら、14-5-1（直らないときの型）へ。応急は `git restore .` です。

### Step 1: 4つをまとめて起こさせる

```text
次は画面の設計。docs/design/ にある機能一覧と確認事項を先に読んで。確認事項には、クライアントの回答と、
回答が無くて自分で決めたことが両方書いてある。

モックアップが最初からあるので、ワイヤーフレームは描かない。モックアップを根拠に、画面一覧・画面遷移図・
画面項目定義・入力チェックとエラーメッセージを作ってほしい。置き場とファイル名は docs/design/README.md の
とおりで、図はMermaidでMarkdownの中に。画像ファイルは置かないで。画面一覧は SC-01 から連番。文字数の上限は
spec.md の値を使って、エラー文の言い回しはモックアップに合わせて。

根拠は mockup/（9枚の画面と design-guide.md）・spec.md・docs/design/ にあるものだけ。無いことを想像で
足さないで、迷ったら聞いて。spec.md と mockup/ は変えないで。

全画面ぶんの画面項目定義は要らない。どこまで書くかはそちらで決めて、選んだ理由も教えて。
```

> 💡 **進行例について**: AIとの開発は毎回違う流れになります。ここに示すのは一つの進行例です。あなたの画面と違っていても、チェックリストを満たしていれば正解です。

1往復で、`SC-01` から `SC-09` までの9画面が返ってきました。依頼に書いていないのに決めていたことが、3つあります。

- **画面として数えないもの**を切り分けた。`mockup/index.html` は見本を配るためのカタログでアプリの画面ではない、公開APIは画面を持たない
- **上部バーとサイドバーを、画面から外して共通の部品にした**。付いている画面すべてに矢印を引く代わりに、遷移図では1つにまとめた
- **画面項目定義をどこまで書くかの基準を、自分の言葉で書いた**。「その画面でしか決まらない項目があるか」。省いた画面と、省いた理由も表にしてあった

エラーメッセージについては、モックアップにそのまま書かれている文言は3つだけで、残りは書き起こしたもの、と分けて報告してきました。どこまでが見本の言葉で、どこからが自分たちの言葉かが分かる形になっています。

### Step 2: 削除の確認を、画面として数え直す

進行例では、チャンネル削除の確認はチャンネル編集画面の中の表示として扱われていました。見本が同じページに並べて描いているためです。ただし、その並べ方は見本の都合です。モックアップの `README.md` に、切り替えて見せる状態（エラー・確認・0件・ホバー中の操作）は静的に開いた状態で描くか同じページに並べている、と書いてあります。

ここで、使う道具の決めが効きます。同じページの中で確認を開くにはJavaScriptが要るので、別のURLで確認の画面を出す形にします。すると削除の確認は独立した1画面になるので、`SC-10` として画面一覧と遷移図に足します。

### Step 3: 表を1行ずつ潰す

入力チェックの表は、機能ごとに上から潰して読みます。ここで抜けが見つかりました。

メッセージと返信の「新しく書く」の行はあるのに、**「その場で書き換える」の行がありません。** 確認事項でその場編集をすると決めているのに、編集したときの空・上限超過のチェックが落ちていました。画面項目定義には編集ボタンの説明があったので、AIの中でも編集は存在しています。それでも入力の表には現れませんでした。作る・読むは書けていて、直すが抜ける形です。エラーメッセージの側にも同じだけ足します。

ほかに、この回では次の2か所を直しました。

- **空白だけの入力の扱い**を明記した。「前後の空白と改行を取り除いてから、空かどうかを見る」。スペースだけのメッセージが通ってしまう定番の穴です
- **自分で引いた線を、自分で破っていた1行を落とした**。入力チェックの表の下に「入力の中身ではなく、誰が操作したかで断るものは扱わない」と書いてあるのに、作成者を外せないという行が表に入っていました。この行は権限の話なので、16-1-5で扱います

見つけた3つは、まとめて直させます。抜けているものと、線からはみ出しているものなので、こちらの言い分がそのまま通ります。**言い切って構いません**。

```text
入力チェックとエラーメッセージの表を3か所直して。

- メッセージと返信の「その場で書き換える」の行が無い。確認事項でその場編集にすると決めているので、
  空と上限超過のチェックを、新しく書くほうと同じだけ足して
- 空白だけの入力の扱いが書いていない。前後の空白と改行を取り除いてから、空かどうかを見る形にして
- 「作成者を外せない」の行は、入力の中身ではなく誰が操作したかの話なので、この表から落として。
  権限はあとで別に決める
```

直し終えたら、`main` にコミットします。

- [ ] 画面一覧の各行が、モックアップのどの見本に当たるかを指している（13-3-1）
- [ ] 遷移図に、送信に成功したあとの着地先が入っている（13-3-2）
- [ ] 画面項目定義を書いた画面と、省いた画面の理由が書かれている（13-3-3）
- [ ] 入力チェックの表に、新しく書く行と書き換える行の両方がある（13-3-4）
- [ ] JavaScriptを使わない決めと、その置き換え方が設計書に残っている

## ✨ まとめ

- デザインが支給されると、画面設計は描く仕事から読む仕事に変わる。決めるのは、名前・遷移・項目の型・エラーの出し方。
- 見本が動いて見えるところは、そのまま作れる保証がない。使う道具を先に決めて、置き換えた形を設計書に残す。
- このアプリはBladeとCSSとフォーム送信で組む。JavaScriptは学んでいないので、必要になる作りは置き換える。
- 画面項目定義は、その画面でしか決まらない項目があるかで選ぶ。繰り返しになる画面は書かない。
- 入力チェックの表は、機能ごとに1行ずつ潰して読む。作る・読むは書けていても、直すが抜ける。
