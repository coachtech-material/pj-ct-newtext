## 📚 テストの基礎知識

### AAAパターン（Arrange-Act-Assert）

テストコードは、**AAAパターン**と呼ばれる3つのステップで構成するのが一般的です。

| ステップ | 意味 | 内容 |
|:---|:---|:---|
| **Arrange** | 準備 | テストに必要なデータや状態を準備する |
| **Act** | 実行 | テスト対象のコードを実行する |
| **Assert** | 検証 | 実行結果が期待通りかを検証する |

**コード例**:

```php
/** @test */
public function ユーザーはタスク一覧を取得できる(): void
{
    // Arrange（準備）
    $user = User::factory()->create();
    Task::factory()->count(3)->create(['user_id' => $user->id]);

    // Act（実行）
    $response = $this->actingAs($user)->get(route('tasks.index'));

    // Assert（検証）
    $response->assertStatus(200);
    $response->assertViewHas('tasks');
}
```

#### コードリーディング

| コード | 説明 |
|:---|:---|
| `/** @test */` | このメソッドがテストであることを示すアノテーション |
| `User::factory()->create()` | テスト用のユーザーを作成 |
| `Task::factory()->count(3)->create()` | テスト用のタスクを3件作成 |
| `$this->actingAs($user)` | 指定したユーザーとしてログインした状態でリクエスト |
| `->get(route('tasks.index'))` | GETリクエストを送信 |
| `assertStatus(200)` | HTTPステータスコードが200であることを確認 |
| `assertViewHas('tasks')` | ビューに `tasks` 変数が渡されていることを確認 |

> **💡 ポイント**: AAAパターンに従うことで、テストコードが読みやすくなり、何をテストしているのかが明確になります。

### テストの観点

テストを書く際は、以下の3つの観点を意識します。

**1. 正常系テスト**

期待通りの入力で、期待通りの結果が返ることを確認します。

```php
/** @test */
public function 正しい認証情報でログインできる(): void
{
    $user = User::factory()->create(['password' => bcrypt('password')]);

    $response = $this->post(route('login'), [
        'email' => $user->email,
        'password' => 'password',
    ]);

    $response->assertRedirect(route('tasks.index'));
    $this->assertAuthenticatedAs($user);
}
```

**2. 異常系テスト**

エラーが発生するケースで、適切にエラーハンドリングされることを確認します。

```php
/** @test */
public function 間違ったパスワードではログインできない(): void
{
    $user = User::factory()->create(['password' => bcrypt('password')]);

    $response = $this->post(route('login'), [
        'email' => $user->email,
        'password' => 'wrong-password',
    ]);

    $response->assertSessionHasErrors('email');
    $this->assertGuest();
}
```

**3. 境界値テスト**

入力値の境界（上限・下限）で正しく動作することを確認します。

```php
/** @test */
public function タイトルは255文字まで入力できる(): void
{
    $user = User::factory()->create();
    $category = Category::factory()->create();

    $response = $this->actingAs($user)->post(route('tasks.store'), [
        'title' => str_repeat('あ', 255), // 255文字
        'category_id' => $category->id,
        'priority' => 2,
    ]);

    $response->assertRedirect(route('tasks.index'));
}

/** @test */
public function タイトルが256文字以上だとバリデーションエラーになる(): void
{
    $user = User::factory()->create();
    $category = Category::factory()->create();

    $response = $this->actingAs($user)->post(route('tasks.store'), [
        'title' => str_repeat('あ', 256), // 256文字
        'category_id' => $category->id,
        'priority' => 2,
    ]);

    $response->assertSessionHasErrors('title');
}
```

## 🧠 先輩エンジニアの思考プロセス

テストを書く際、経験豊富なエンジニアはどのように考えているのでしょうか。

### テストケースを考える順序

1. **まず正常系を書く**
   - 「このメソッドは何をするものか？」を明確にする
   - 期待通りの入力で期待通りの結果が返ることを確認

2. **次に異常系を考える**
   - 「何が失敗する可能性があるか？」を洗い出す
   - バリデーションエラー、認可エラー、存在しないリソースへのアクセス等

3. **境界値を確認する**
   - 「ギリギリのケースはどうか？」を検証
   - 文字数制限の上限・下限、日付の境界等

### 「何をテストすべきか」の判断基準

| 優先度 | テスト対象 | 理由 |
|:---|:---|:---|
| 高 | ビジネスロジック | バグがあると業務に直接影響 |
| 高 | 認証・認可 | セキュリティに関わる |
| 中 | バリデーション | 不正データの混入を防ぐ |
| 中 | エラーハンドリング | ユーザー体験に影響 |
| 低 | 単純なCRUD | フレームワークが保証している部分が多い |

### テストを書くタイミング

- **機能実装後すぐに書く**: 実装内容が頭に残っているうちに書くのが効率的
- **バグ修正時に書く**: 同じバグを再発させないためのリグレッションテスト
- **リファクタリング前に書く**: 既存の動作を保証してから安全にリファクタリング

> **💡 実務でのポイント**: 「テストを書く時間がない」と感じることもありますが、テストがないコードは後から修正するのが怖くなります。最低限、認証・認可とビジネスロジックのテストは書く習慣をつけましょう。

## ⚙️ テスト環境のセットアップ

### phpunit.xml の設定

Laravelプロジェクトには、テスト設定ファイル `phpunit.xml` が含まれています。テスト用のデータベース設定を行います。

**ファイル**: `phpunit.xml`

#### 修正箇所

`<php>` セクション内で以下の2点を修正します。

**1. `DB_CONNECTION` 行を追加**（デフォルトでは存在しません）

**2. `DB_DATABASE` の値を変更**

```xml
<!-- 変更前 -->
<env name="DB_DATABASE" value="testing"/>

<!-- 変更後 -->
<env name="DB_CONNECTION" value="sqlite"/>   <!-- ← この行を追加 -->
<env name="DB_DATABASE" value=":memory:"/>   <!-- ← 値を変更 -->
```

#### 修正後の `<php>` セクション全体

```xml
<php>
    <env name="APP_ENV" value="testing"/>
    <env name="BCRYPT_ROUNDS" value="4"/>
    <env name="CACHE_DRIVER" value="array"/>
    <env name="DB_CONNECTION" value="sqlite"/>   <!-- ← 追加 -->
    <env name="DB_DATABASE" value=":memory:"/>   <!-- ← 値を変更 -->
    <env name="MAIL_MAILER" value="array"/>
    <env name="PULSE_ENABLED" value="false"/>
    <env name="QUEUE_CONNECTION" value="sync"/>
    <env name="SESSION_DRIVER" value="array"/>
    <env name="TELESCOPE_ENABLED" value="false"/>
</php>
```

#### 設定内容の解説

| 設定 | 値 | 説明 |
|:---|:---|:---|
| `APP_ENV` | testing | テスト環境であることを示す |
| `BCRYPT_ROUNDS` | 4 | パスワードハッシュの計算回数を減らしてテストを高速化 |
| `CACHE_DRIVER` | array | キャッシュをメモリ上に保持（テスト間で影響しない） |
| `DB_CONNECTION` | sqlite | テスト用にSQLiteを使用 |
| `DB_DATABASE` | :memory: | メモリ上にデータベースを作成（高速） |
| `SESSION_DRIVER` | array | セッションをメモリ上に保持 |

> **💡 ポイント**: `DB_DATABASE` を `:memory:` に設定することで、テストごとにデータベースがリセットされ、テスト間の影響を防げます。
>
> **📌 なぜSQLiteを使うのか？**: 本番環境ではMySQLを使用していますが、テストではSQLiteのインメモリデータベースを使用します。これにより、テストが高速に実行され、本番データベースに影響を与えません。

### ファクトリの作成

テストデータを効率的に作成するために、ファクトリを使用します。

**CategoryFactory の作成**

```bash
sail artisan make:factory CategoryFactory --model=Category
```

**ファイル**: `database/factories/CategoryFactory.php`

```php
<?php

namespace Database\Factories;

use App\Models\Category;
use Illuminate\Database\Eloquent\Factories\Factory;

/**
 * @extends \Illuminate\Database\Eloquent\Factories\Factory<\App\Models\Category>
 */
class CategoryFactory extends Factory
{
    /**
     * Define the model's default state.
     *
     * @return array<string, mixed>
     */
    public function definition(): array
    {
        return [
            'name' => fake()->word(),
        ];
    }
}
```

**TaskFactory の作成**

```bash
sail artisan make:factory TaskFactory --model=Task
```

**ファイル**: `database/factories/TaskFactory.php`

```php
<?php

namespace Database\Factories;

use App\Models\Category;
use App\Models\Task;
use App\Models\User;
use Illuminate\Database\Eloquent\Factories\Factory;

/**
 * @extends \Illuminate\Database\Eloquent\Factories\Factory<\App\Models\Task>
 */
class TaskFactory extends Factory
{
    /**
     * Define the model's default state.
     *
     * @return array<string, mixed>
     */
    public function definition(): array
    {
        return [
            'title' => fake()->sentence(),
            'description' => fake()->paragraph(),
            'priority' => fake()->randomElement([1, 2, 3]),
            'user_id' => User::factory(),
            'category_id' => Category::factory(),
        ];
    }

    /**
     * 優先度を高にする
     */
    public function highPriority(): static
    {
        return $this->state(fn (array $attributes) => [
            'priority' => 3,
        ]);
    }

    /**
     * 優先度を低にする
     */
    public function lowPriority(): static
    {
        return $this->state(fn (array $attributes) => [
            'priority' => 1,
        ]);
    }
}
```

#### ファクトリの使い方

```php
// 基本的な使い方
$task = Task::factory()->create();

// 複数件作成
$tasks = Task::factory()->count(5)->create();

// 属性を指定して作成
$task = Task::factory()->create([
    'title' => 'テストタスク',
    'priority' => 3,
]);

// ステートを使用
$highPriorityTask = Task::factory()->highPriority()->create();

// リレーションを指定
$user = User::factory()->create();
$task = Task::factory()->create(['user_id' => $user->id]);
```

## 🚀 テスト実行コマンド

> **📌 参考情報**: このセクションでは、テスト実行コマンドの使い方を紹介します。実際にテストを実行するのは、次のセクション（16-8-2）以降でテストファイルを作成した後になります。

### 基本的なテスト実行

```bash
# 全てのテストを実行
sail test

# 特定のテストファイルを実行
sail test tests/Feature/TaskControllerTest.php

# 特定のテストメソッドを実行
sail test --filter=ユーザーはタスク一覧を取得できる
```

> ⚠️ **PHP 8.5以降の場合**: `DEPR`と表示されることがありますが、テストは正常に通っています。これはLaravelの設定ファイルで使用している定数がPHP 8.5で非推奨になったためで、ハンズオンの内容には影響しません。

#### コマンドのコードリーディング

| コマンド | 説明 |
|:---|:---|
| `sail test` | PHPUnitを使って全テストを実行 |
| `--filter=テスト名` | 指定した名前を含むテストのみ実行 |

### テスト結果の見方

```
   PASS  Tests\Feature\TaskControllerTest
  ✓ ユーザーはタスク一覧を取得できる                                    0.15s
  ✓ ユーザーはタスクを作成できる                                        0.08s
  ✓ 未認証ユーザーはタスク一覧にアクセスできない                        0.05s

  Tests:    3 passed (8 assertions)
  Duration: 0.45s
```

| 表示 | 意味 |
|:---|:---|
| `PASS` | テストが成功 |
| `FAIL` | テストが失敗 |
| `✓` | 個別のテストが成功 |
| `×` | 個別のテストが失敗 |
| `Tests: 3 passed` | 3件のテストが成功 |
| `8 assertions` | 8件のアサーション（検証）が実行された |

### カバレッジレポートの確認

テストがコードのどの部分をカバーしているかを確認できます。

**Xdebugのセットアップ**

カバレッジレポートを生成するには、Xdebugが必要です。Laravel Sailでは `.env` ファイルに設定を追加するだけでセットアップできます。

**ステップ1**: `.env` ファイルに以下の行を追加します。

```
XDEBUG_MODE=coverage
```

**ステップ2**: コンテナを再起動して設定を反映します。

```bash
sail down
sail up -d
```

**ステップ3**: Vite開発サーバーを起動します（別のターミナルタブで実行）。

```bash
sail npm run dev
```

> **📌 補足**: `sail down` を実行すると、起動していたVite開発サーバー（`sail npm run dev`）も停止します。`sail npm run dev` はターミナルを占有するため、別のタブで起動してください。

> **💡 ポイント**: `XDEBUG_MODE` には他にも `debug`（デバッグ用）や `off`（無効化）などの値を設定できます。カバレッジレポートが不要になったら `off` に変更することで、テストの実行速度が向上します。

**カバレッジレポートの生成**

```bash
# HTMLレポートを生成
sail test --coverage-html=coverage

# ターミナルに概要を表示
sail test --coverage
```

**ターミナル出力例**:

```
  App\Http\Controllers\TaskController .............. 85.7%
  App\Http\Controllers\CategoryController .......... 78.3%
  App\Models\Task .................................. 100.0%
  App\Models\Category .............................. 100.0%
  App\Policies\TaskPolicy .......................... 66.7%

  Total: 82.4%
```

HTMLレポートは `coverage/index.html` に生成されます。ブラウザで開くと、ファイルごとのカバレッジ率や、テストされていない行を視覚的に確認できます。

> **💡 カバレッジの目安**: 100%を目指す必要はありませんが、重要なビジネスロジックや認証・認可の部分は高いカバレッジを維持しましょう。一般的に70〜80%程度が目安とされています。

## ❌ よくある間違い

### 1. テストデータベースの設定を忘れる

```php
// ❌ NG: 本番データベースでテストを実行してしまう
// phpunit.xmlにDB_CONNECTION, DB_DATABASEの設定がない
```

**対処法**: `phpunit.xml` に `DB_CONNECTION=sqlite` と `DB_DATABASE=:memory:` を設定する。

### 2. RefreshDatabaseトレイトを忘れる

```php
// ❌ NG: データベースがリセットされない
class TaskControllerTest extends TestCase
{
    // use RefreshDatabase; が抜けている

    /** @test */
    public function テスト(): void
    {
        // 前のテストのデータが残っている可能性がある
    }
}
```

**対処法**: テストクラスに `use RefreshDatabase;` を追加する。

### 3. ファクトリでリレーションを考慮しない

```php
// ❌ NG: user_idが設定されていない
public function definition(): array
{
    return [
        'title' => fake()->sentence(),
        // 'user_id' => User::factory(), が抜けている
    ];
}
```

**対処法**: ファクトリの `definition()` で外部キーを設定する。

## 📌 Git操作について

このセクションで作成・編集したファイル（phpunit.xml、CategoryFactory、TaskFactory）は、**まだコミットしません**。

次のセクション（16-8-2 CRUD機能のテスト）で、テストファイルと一緒にコミットします。

> **💡 なぜ？**: Gitでは、ブランチを作成するときに未コミットの変更がある場合、その変更は新しいブランチに引き継がれます。次のセクションでブランチを作成した後、このセクションで行った変更とテストファイルをまとめてコミットします。
