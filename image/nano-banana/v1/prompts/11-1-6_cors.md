## c1: CORSの基本概念（異なるオリジン間のリソース共有）

### プロンプト本文

```
CORSの基本概念を、「異なるオリジン間のリソース共有」として図解してください。

## 内容
教材では以下のように説明している:
- CORSは「Cross-Origin Resource Sharing」の略
- オリジン = プロトコル + ドメイン + ポート の組み合わせ
- ブラウザには「同一オリジンポリシー」というセキュリティ機能がある
- 同じオリジンからのリクエストは許可、異なるオリジンはブロックされる
- CORSを設定することで、許可されたオリジンからのアクセスを受け入れる

## 描いてほしいもの
左側にフロントエンド、右側にバックエンドを配置し、その間にブラウザのセキュリティ（門番）を描く:

【左側 — フロントエンド（緑系）】
- http://localhost:3000 のキャラクター（開発者、アプリ）
- 「APIにデータちょうだい！」というセリフの吹き出し

【中央 — ブラウザのセキュリティ（門番キャラクター）】
- 門番が「オリジンが違う！」と手を広げてブロックしている場面（上段）
- 門番が「CORSヘッダーがあるから通してよし！」と道を開けている場面（下段）
- 上段に大きく「同一オリジンポリシー」、下段に大きく「CORS（許可）」とラベル

【右側 — バックエンド（青系）】
- http://localhost:8000 のキャラクター（サーバー）
- 「Access-Control-Allow-Origin ヘッダーを付けて返すよ！」というセリフ

流れ:
上段（ブロック）:
① フロントエンド（:3000）がリクエスト送信
② ブラウザの門番が「オリジンが違う！ブロック！」
③ 赤い×印で通信失敗

下段（許可）:
① フロントエンド（:3000）がリクエスト送信
② サーバーがCORSヘッダー付きでレスポンス
③ ブラウザの門番が「許可されたオリジンだ！通過OK！」
④ データが無事に届く

タイトル: 「CORS 〜異なるオリジン間のリソース共有〜」

## 概念の強調
- 「同一オリジンポリシー」「CORS」を最も大きく太い文字で描く
- 「オリジン = プロトコル + ドメイン + ポート」を分かりやすく図示する
- ブロックと許可の対比が一目で伝わるように上下で色分けする（上:赤系、下:緑系）
- この図で伝えたいのは「ブラウザがセキュリティのために異なるオリジンへの通信を制限しており、CORSはそれを許可する仕組み」ということ
```

## c2: プリフライトリクエスト（OPTIONSメソッド）の流れ

### プロンプト本文

```
CORSのプリフライトリクエストの流れを、フローチャートで図解してください。

## 内容
教材では以下のように説明している:
- ブラウザは異なるオリジンへのリクエストを送信する前に、プリフライトリクエストを送信する
- プリフライトリクエストのHTTPメソッドは OPTIONS
- サーバーが許可している場合、ブラウザは本来のリクエストを送信する

## 描いてほしいもの
左にブラウザ、右にサーバーを配置し、時系列（上から下）で通信の流れを描く:

【登場キャラクター】
- ブラウザ（慎重な性格のキャラクター）: 「いきなり本番リクエストは送らないよ。まず確認！」
- サーバー（受付係のキャラクター）: 「CORSヘッダーで許可を返すよ」

【ステップ（時系列フロー）】
① ブラウザ: 「まずOPTIONSで確認するよ！」
   → OPTIONSリクエスト（プリフライト）をサーバーに送信
   → 送信内容: Origin, Access-Control-Request-Method, Access-Control-Request-Headers

② サーバー: 「このオリジンはOKだよ！」
   → プリフライトレスポンスを返す
   → 返却内容: Access-Control-Allow-Origin, Access-Control-Allow-Methods, Access-Control-Allow-Headers

③ ブラウザ: 「許可が出た！本番リクエストを送るよ！」
   → 本来のリクエスト（GET, POST等）をサーバーに送信

④ サーバー: 「はい、データをどうぞ！」
   → 本来のレスポンスを返す（CORSヘッダー付き）

タイトル: 「プリフライトリクエストの流れ」

## 概念の強調
- 「プリフライト（事前確認）」と「本番リクエスト」の2段階であることを大きく強調する
- OPTIONSメソッドを最も目立つラベルで描く
- 「2段階通信」であることが図の骨格。①②が事前確認、③④が本番として色分けする（事前確認:オレンジ系、本番:青系）
- この図で伝えたいのは「ブラウザは安全のために、まず事前確認（OPTIONS）を送り、許可が出てから本番リクエストを送る」という2段階の仕組み
```
