# 13-3-3: Issue駆動開発の全体ワークフロー（B1: 技術フロー）

**Gem**: v4.1 | **テンプレート**: B1 | **ステータス**: ドラフト

## プロンプト本文

```
Issue駆動開発の全体ワークフローを図解してください。Tutorial 13の文脈で、個人開発でもIssue駆動を実践する流れを描きます。

## 内容
教材では以下のように説明している:
- 開発前にやるべきことをIssueとして登録しておく
- メリット: 「何をやるか」が明確になる、コミットとIssueが紐づく、進捗が可視化される
- ワークフロー: Issue確認 → ブランチ作成 → 実装 → コミット（#N付き）→ push → PR作成（close #N付き）→ マージ → Issue自動クローズ

## 描いてほしいもの
左から右への横フローで、一連のワークフローをステップバイステップで描く:

【登場キャラクター】
- 開発者（1人、個人開発を想定）: 全ステップを自分で進める

【ステップ（番号付きフロー）】
① Issueを確認（紫系）
   - GitHubのIssueリスト画面を描く
   - 10個のIssueが並んでいるイメージ（#1〜#10）
   - 開発者「まずIssue #1から片付けよう！」

② ブランチ作成（緑系）
   - `git switch -c feature/issue-1-migrations`
   - mainから分岐する枝を描く
   - 開発者「Issue番号をブランチ名に入れるのがコツ！」

③ 実装（青系）
   - コードエディタでコードを書いている様子
   - 開発者「よし、マイグレーション書けた！」

④ コミット（オレンジ系）
   - `git commit -m "マイグレーション作成 #1"`
   - Issue番号「#1」を赤く大きく強調
   - 開発者「コミットメッセージにIssue番号を入れると紐づくよ！」

⑤ push（青系）
   - `git push origin feature/issue-1-migrations`
   - ローカルからリモートへの矢印
   - 開発者「GitHubにpush！」

⑥ PR作成（オレンジ系）
   - PRフォームの画面を描く
   - タイトル: 「feat: マイグレーション作成」
   - 説明欄に大きく「close #1」
   - 開発者「PRの説明にclose #1を書くのがポイント！」

⑦ マージ & 自動クローズ（赤系→緑系）
   - 「Merge pull request」ボタン
   - Issue #1に✅がつき、自動クローズされる
   - 開発者「マージしたらIssueが自動で閉じた！次はIssue #2だ！」

⑦から①に戻る矢印を描き、次のIssueに進むサイクルを示す。

タイトル: 「Issue駆動開発ワークフロー」

## 概念の強調
- 「#1」のIssue番号が全ステップに登場し、赤い線や印で目立たせる
- コミットメッセージの「#1」（紐付け）とPR説明欄の「close #1」（自動クローズ）の使い分けを大きく強調する
- 個人開発でもIssue駆動を使うことのメリット（迷わない、進捗が見える）を伝える
- この図で伝えたいのは「Issue → ブランチ → 実装 → コミット → push → PR → マージ の一連の流れがサイクルとして回る」ということ
```
