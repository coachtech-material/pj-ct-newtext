# 10-6-4: セッション/Cookieによる状態管理のシーケンス（B1: シーケンス図）

**Gem**: v4.1 | **テンプレート**: B1 | **ステータス**: ドラフト

## プロンプト本文

```
HTTPのステートレス性を克服する、セッションとCookieによる状態管理の仕組みをシーケンス図で図解してください。

## 内容
教材では以下を解説している:

HTTPはステートレス（状態を持たない）:
- 各リクエストは独立しており、前のリクエストの情報を覚えていない
- ログインしても、次のリクエストでは「誰だっけ？」となる

セッションとCookieで解決:
- Cookie: ブラウザに保存される小さなデータ。サーバーが発行し、次回以降のリクエストで自動送信
- Session: サーバー側に保存されるユーザーの状態。セッションIDをCookieに保存してブラウザとサーバーを紐付ける

教材の比喩: 映画館のチケット
- チケット（セッションID）を持っていれば映画館（サーバー）に入場できる
- チケットを失くすと入場できない

セッションハイジャック対策:
- セッションIDの再生成（$request->session()->regenerate()）
- HttpOnlyフラグ（JavaScriptからアクセス不可）
- Secureフラグ（HTTPS通信のみ）
- SameSite属性（クロスサイトリクエスト制限）

## 描いてほしいもの
3つのフェーズに分けたシーケンス図:

登場キャラクター（横一列に配置）:
- Browser（ブラウザ）: 映画館に来た観客
- Server（サーバー）: 映画館の受付
- Session Store（セッション保管庫）: チケットの記録棚

【フェーズ1: ステートレスの問題】（グレー系）
① Browser → Server: 「ログインします！」（POST /login）
② Server: 「認証OK！」
③ Browser → Server: 「ダッシュボード見せて！」（GET /dashboard）
④ Server: 「...誰？」😟（HTTPはステートレス、前のことを覚えていない）
セリフ: 「毎回忘れちゃう...どうしよう？」

【フェーズ2: セッション＆Cookieで解決】（青系）
⑤ Browser → Server: 「ログインします！」
⑥ Server → Session Store: セッション作成（ユーザーID等を保存）
⑦ Server → Browser: Cookie発行（Set-Cookie: session_id=abc123; HttpOnly; Secure）
⑧ Browser → Server: 「ダッシュボード見せて！」+ Cookie自動送信
⑨ Server → Session Store: セッションIDで照合 → ユーザー情報を復元
⑩ Server → Browser: 「山田さんのダッシュボードです！」
セリフ: 「チケット（Cookie）を見ればわかる！」

【フェーズ3: セキュリティ対策（右下に小さく）】
- HttpOnly: JSからアクセスNG（XSS対策）
- Secure: HTTPSのみ（盗聴対策）
- SameSite: クロスサイト制限（CSRF対策）
- regenerate(): セッションID再生成（ハイジャック対策）

タイトル: 「セッションとCookie 〜ステートレスを克服する〜」

## 概念の強調
- 「Session」「Cookie」「ステートレス」を最も大きく太い文字で描く
- フェーズ1の「誰？」問題を強調し、なぜセッション/Cookieが必要かを伝える
- Cookie内のセッションIDが「ブラウザとサーバーの紐付け」の鍵であることを視覚的に示す
- Set-Cookie ヘッダーの属性（HttpOnly, Secure）がセキュリティに重要であることを示す
- 映画館のチケットの比喩はイラストの補助として小さく添える
```
