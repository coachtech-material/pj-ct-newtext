# ハンズオンSection構成ガイド

> **目的**: ハンズオンSectionの構成を統一し、「要件（WHAT）」と「実装タスク（HOW）」を分離する

---

## 標準構成

```
ハンズオンSection
│
├── 📌 このハンズオンについて
│   └── セクションの目的
│
├── 📁 ディレクトリ構成（※「📌 このハンズオンについて」のサブ見出しとして記載）
│   └── practice / sample の説明
│
├── 🎯 演習課題
│   ├── この演習で作るもの（説明文）
│   ├── 🖼️ 完成イメージ（画像）
│   ├── 📋 要件（箇条書き）
│   ├── ✅ 完成チェックリスト
│   └── ✏️ 実装タスク（番号リスト）
│
├── ⚙️ 環境準備（自分で作成する用）
│   ├── ハンズオンディレクトリ作成
│   ├── プロジェクト作成・Sail起動
│   └── 📄 提供ファイル（Blade等）
│       └── ファイルパス + コードのみ（操作指示なし）
│
│   ※ code . は9-1-7で最初に実行済み（laravel-practiceディレクトリ全体を開く）
│
│   > 🚀 **ここから先は、自分の力で実装してみましょう！**
│
├── 💡 ヒント
│
├── 🏃 実践セクション（一緒に作成する用）
│   ├── ⚙️ 環境準備（実践用プロジェクト）
│   ├── 🧠 先輩エンジニアの思考プロセス
│   ├── 📝 ステップバイステップで実装
│   └── ✨ 完成！
│
├── 📖 模範解答
│
└── 🚀 まとめ
```

## 画像の挿入

### ファイル命名規則

```
{Tutorial}-{Chapter}-{Section}_{連番}.png
```

例: `9-1-8_1.png`, `9-1-8_2.png`

### imgタグの形式

```html
**画像の説明**

<img alt="9-1-8_1.png" src="">
```

- `alt`属性にファイル名を記載
- `src`属性は空（後でS3アップロード時に設定）
- 画像の前に説明テキストを記載

### 完成イメージのトグル表示

**画像が1枚の場合**: トグル不要、直接表示

```markdown
### 🖼️ 完成イメージ

**投稿一覧ページ**

<img alt="9-4-9_1.png" src="">
```

**画像が2枚以上の場合**: トグルで展開

```markdown
### 🖼️ 完成イメージ

<details>
<summary>📸 完成画面を確認する（クリックで展開）</summary>

**投稿一覧ページ**

<img alt="9-5-5_1.png" src="">

**投稿詳細ページ**

<img alt="9-5-5_2.png" src="">

</details>
```

### 必要な画像の種類

| 画像 | 配置場所 | 説明 |
|:-----|:---------|:-----|
| 完成イメージ | 🎯 演習課題 > 🖼️ 完成イメージ | 完成画面のスクリーンショット（必須） |
| 環境確認 | ⚙️ 環境準備 | Laravelウェルカムページ等（※9-1-7のみ） |
| 途中経過 | 📝 ステップバイステップ | 必要に応じて途中の画面 |
| 動作確認 | ✨ 完成！ | 実践セクションでの完成画面（任意） |

> 💡 **ポイント**: 画像は「受講生が正しく進められているか確認できる」ポイントに配置する

### 画像挿入の運用

各セクション修正時に、必要な画像を提案・相談してから挿入する。

```
1. セクションを読む
2. 「このセクションでは〇〇の画像が必要では？」と提案
3. ユーザー承認後に画像挿入ポイントを追加
4. 必要な画像をメモしておく
```

> ⚠️ **重要**: 画像ファイルは `image/` ディレクトリに配置する。`Glob image/*.png` でファイルの存在を確認できる。

### 画像ファイルの管理

画像ファイルは `image/` ディレクトリで管理する。

```
image/
├── 9-1-7_1.png
├── 9-1-7_2.png
└── ...
```

- 全セクション修正完了後にまとめて撮影
- 撮影後は `image/` ディレクトリに配置する

## 各セクションの詳細

### 📋 要件

機能要件を箇条書きで記述。**ユーザー視点**で「何ができるか」を書く。

> ⚠️ **注意**: 技術的な実装内容（テーブル作成、モデル定義、クエリビルダ等）は要件に含めない。それらは「✏️ 実装タスク」や「テーブル構成」として別途記載する。

**良い例**:
```markdown
- タスクの一覧が表示できる
- 新しいタスクを作成できる
```

**悪い例**:
```markdown
- tasksテーブルを作成できる        ← 技術的
- Eloquentモデルを定義できる       ← 技術的
- クエリビルダでデータを取得できる  ← 技術的
```

---

### ✅ 完成チェックリスト

要件を確認可能な形に具体化したチェックリスト。動作確認方法を引用で補足。

**例（ブラウザ確認）**:
```markdown
### ✅ 完成チェックリスト

- [ ] `/tasks`にアクセスするとタスク一覧が表示される
- [ ] 「新規作成」からタスクを追加できる
- [ ] 「編集」からタスクを更新できる
- [ ] 「削除」でタスクが削除される

> 💡 **動作確認**: `http://localhost/tasks` にアクセス
```

**例（テスト実行）**:
```markdown
### ✅ 完成チェックリスト

- [ ] テストが全てパスする

> 💡 **動作確認**: `sail artisan test --filter UserTest` を実行
```

---

### ✏️ 実装タスク

具体的な実装ステップを**番号リスト**で記述。

**Bladeの扱い**:
- 実装タスクに「Bladeファイルを配置する」を含めるかは柔軟に判断
- Blade提供がある場合は補足文で案内してもよい

**例（CRUD）**:
```markdown
### ✏️ 実装タスク

1. Taskモデルとマイグレーションを作成
2. TaskControllerを作成
3. ルーティングを設定
4. 各メソッドを実装（index, create, store, edit, update, destroy）
5. Bladeファイルを配置する

> 💡 Bladeファイルは「⚙️ 環境準備」セクションで提供します。
```

---

### 📄 提供ファイル（Blade等）

⚙️ 環境準備で提供するBladeファイルについて。

**書き方のルール**:
- 「コピペしてください」「以下を作成してください」等の**操作指示は書かない**
- 単にファイルパスとコードを提示するだけ
- コードリーディングは**📝 ステップバイステップ**の「Bladeを配置する」ステップで行う

**例**:
```markdown
### 📄 提供ファイル

`resources/views/posts/index.blade.php`

```blade
@extends('layouts.app')

@section('content')
    <h1>投稿一覧</h1>
    @foreach ($posts as $post)
        <div class="post">
            <h2>{{ $post->title }}</h2>
            <p>コメント数: {{ $post->comments_count }}</p>
        </div>
    @endforeach
@endsection
```
```

### 🧠 先輩エンジニアの思考プロセス

要件を構造化し、実装タスクに落とし込む過程を表で示す。表のStep番号は「📝 ステップバイステップで実装」のStep番号と対応させる。

**注意**: 環境構築や動作確認は含めない。これらは別セクション（⚙️ 環境準備、✨ 完成！）で扱う。

**例（CRUD）**:
```markdown
### 🧠 先輩エンジニアの思考プロセス

先輩エンジニアは要件を以下のように構造化し、実装タスクに落とし込みます：

| Step | やること | 説明 |
|:-----|:---------|:-----|
| 1 | モデル・マイグレーション・コントローラー作成 | `-mcr`オプションで一度に生成 |
| 2 | マイグレーションでテーブル定義 | 必要なカラムを設定 |
| 3 | Tinkerでデータ確認 | コントローラー実装前にデータ取得を確認 |
| 4 | リソースルート定義 | 7つのルートを一度に設定 |
| 5 | コントローラー実装 | CRUD各メソッドを実装 |
| 6 | ビュー作成 | 一覧・作成・編集画面 |
```

**ポイント**:
- 表の左列（Step）と「📝 ステップバイステップで実装」のStep番号を一致させる
- 「説明」列で「なぜこの順番か」「何がポイントか」を簡潔に記載

## 紐づきの関係

「✏️ 実装タスク」「🧠 思考プロセス」「📝 ステップバイステップ」は同じステップを指す。**実装に関するステップのみ**を対象とし、環境構築・動作確認は含めない。

```
🎯 演習課題 > ✏️ 実装タスク（番号リスト）
    ↓ 同じステップを指す（実装のみ）
🏃 実践 > 🧠 先輩エンジニアの思考プロセス（表形式）
    ↓ 同じステップを指す（実装のみ）
🏃 実践 > 📝 ステップバイステップで実装（詳細手順）
```

| セクション | 形式 | 目的 |
|:-----------|:-----|:-----|
| ✏️ 実装タスク | 番号リスト | 自分でやる人向けのゴール確認 |
| 🧠 思考プロセス | 表 | 一緒にやる人向けの概要・順番の説明 |
| 📝 ステップバイステップ | 詳細な手順 | 実際のコマンド・コード例 |

**除外するもの**:
- 環境構築 → ⚙️ 環境準備（実践用プロジェクト）で扱う
- 動作確認 → ✨ 完成！で扱う

### ⚠️ 文言の統一

3つのセクションで**同じステップの文言を統一する**こと。

**良い例**:
```
実装タスク: 1. マイグレーションを作成・実行する
思考プロセス: Step 1 | マイグレーションを作成・実行
ステップ: #### ステップ1: マイグレーションを作成・実行する
```

**悪い例**:
```
実装タスク: 1. マイグレーションファイルを作成する  ← 「実行」がない
思考プロセス: Step 1 | マイグレーションを作成      ← 「実行」がない
ステップ: #### ステップ1: マイグレーションを作成・実行する
```

**チェックポイント**:
- 各ステップの動詞・内容が一致しているか
- 「作成」と「配置」、「Controller」と「コントローラー」などの表記揺れがないか
- 複合タスク（〜して、〜する）が同じ粒度で記載されているか

## 修正前チェックリスト

ハンズオンSection修正時は、以下を**必ず確認してからユーザーに報告**する。

### 1. 学習内容の確認

- [ ] Chapterの通常Section（10-2-1, 10-2-2等）を読んだ
- [ ] 学習内容を表形式で整理した
- [ ] ハンズオンがChapterで学んだ内容の復習になっているか確認した
- [ ] Chapterで習っていない内容が含まれていないか確認した

### 2. 技術的な実行可能性

- [ ] 環境構築手順でエラーが起きないか確認した
- [ ] 必要なカラム・テーブルが存在するか確認した
- [ ] 必要な機能（認証等）が利用可能か確認した
- [ ] テストデータ作成手順があるか確認した

### 3. 構成面の確認

- [ ] 標準構成（見出し形式）に準拠しているか確認した
- [ ] 要件がユーザー視点で書かれているか確認した
- [ ] 実装タスク・完成チェックリストがあるか確認した
- [ ] Bladeファイルが環境準備セクションにあるか確認した
- [ ] コードの一貫性（ステップ・模範解答・Blade）を確認した

### 4. 報告時のフォーマット

```markdown
## Chapter X 学習内容の整理

| Section | 学習内容 |
|:--------|:---------|
| X-X-1 | ... |
| X-X-2 | ... |

## ハンズオンの評価

### ✅ 学習内容との整合性
- ...

### ⚠️ 問題点
- ...

## 修正方針
- ...
```

## 確認・修正の観点

1. **構成の柔軟性**: 標準構成が合わない場合は臨機応変に提案
2. **学習内容との整合性**: そのTutorial/Chapterで学んだ内容を演習できること
3. **最重要 - 実行可能性**: 受講生が問題なく進められること
   - 環境構築が正しく動作する
   - 実践セクションの手順でエラーなく実装できる
   - テストデータ作成手順があること
   - **修正後にユーザーに動作確認を依頼する**
4. **既存コードの維持**: 既存の内容（特にコード例）を**できれば**崩さない
   - ただし、既存コードに問題があれば臨機応変に修正する
5. **問題の発見**: GitHub Issuesに記載がなくても、問題がないか検証する
   - 問題を発見したらGitHub Issueとして報告する
6. **コードの一貫性**: 以下のコードを揃える
   - 📝 ステップバイステップで解説されるコード例
   - 📖 模範解答のコード
   - ⚙️ 環境準備で提供するBladeファイル
   - ルーティングとControllerメソッドの対応
7. **Bladeの見栄え**: 提供BladeにはCSSを当てる（模範解答と同じスタイル）

## スターターキット活用について

### 方針

既存のプロジェクト（モデル、マイグレーション、認証等）が前提となるセクションは、新規スターターキットを作成してclone方式にすることを検討する。

### 作成予定のスターターキット

| セクション | リポジトリ名 | 含めるもの | 演習対象（含めない） |
|:-----------|:-------------|:-----------|:---------------------|
| 10-2-4（ミドルウェア） | `laravel-middleware-starter` | Userモデル（is_adminカラム）、マイグレーション、シーダー（管理者・一般ユーザー）、AdminController、Blade、動作確認用ログインルート | CheckAdminミドルウェア、Kernel.php登録、ルートへのミドルウェア適用 |
| 10-3-5（認可） | `laravel-authorization-starter` | Postモデル（user_idカラム、リレーション）、マイグレーション、シーダー（2ユーザー・2投稿）、PostController（index, edit, update, destroy）、Blade（index, edit）、ルーティング、動作確認用ログインルート | PostPolicy、$this->authorize()の実装、@canディレクティブの実装 |
| 10-4-6（デバッグ） | `laravel-debugging-starter` | Userモデル（$fillable未設定=バグ）、UserController（バグ入りstore()）、Bladeファイル（create, index）、ルーティング、マイグレーション | dd()でデバッグ、Log::info()でログ出力、$fillableを設定して修正 |
| 10-4-7（HTTPライフサイクル） | `laravel-http-lifecycle-starter` | Postモデル（viewsカラム、incrementViews()）、マイグレーション、シーダー（3件）、PostController（index, show）、Blade（index, show）、ルーティング（ミドルウェア未適用） | LogHttpLifecycleミドルウェア、CountPostViewsミドルウェア、Kernel.php登録、ルートへのミドルウェア適用 |

※各セクション修正時に個別に判断し、必要であればスターターキット作成を提案する
