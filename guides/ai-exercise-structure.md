# AI演習Section構成ガイド

> **目的**: T14「AIを率いて開発しよう」・T15「AI開発を仕組み化しよう」・T16「総仕上げ」の執筆で機械的に守る規則と書式を定める。あわせて、教材全体で使うフェーズ別AIスタンス定型文の正本とする。
>
> ⚠️ **思想・構成・題材の正本はこのガイドではない**。スタンス（役割分担・検証の輪・2軸の背骨）、章構成、演習のスケール設計、題材の扱いは **「AIパート再設計方針」Artifact**（マイルストーン #9 `stage1-design-ai` の Description からリンク）が正本。このガイドには思想の再説明・例文の雛形・分量の数値目安を書かない（過去に雛形と数値目安が量産時の定型量産の源になったため）。執筆サブエージェントへは、章ブリーフに方針Artifactの該当箇所を転記して渡す。

---

## 対象と前提

- **対象**: T14〜T16の全Section、および全Tutorialのハンズオンに入るフェーズ別定型文
- **土台**: 文体・マークダウン要素は `guides/writing-rules.md`。設計成果物の扱いは `guides/design-section-structure.md` と接続する
- **確定事実**: 受講生のAIツールは **Claude Code Proプラン** を標準とする／作図はT14以降Mermaid（8-1-5・8-3-1で既出）／GitHub操作は **`gh` コマンドでAIにやらせる**／権限モードは **auto を標準** として書く

---

## 用語の規則

- 依頼で固める要素は標準用語で呼ぶ: **目的・制約・スコープ外（変えないもの）・参照・受け入れ条件・検証手段**。独自の口語フレームを発明しない
- 計画の持ち方は **なし／planモード／設計書** の3つから1つ。**併用させる手順を書かない**（設計書を作った機能にplanモードを通す記述は禁止）
- **X・Slackは名指しで参照してよい**（「Xのような」）。ポスト・リプライ・タイムライン・ハッシュタグ・チャンネル・スレッド等の用語もUI・設計書・演習の語彙として使う。ただし題材アプリの名称・ロゴは独自のものにし、実在サービスを名乗らない
- 独自の造語・凝った概念名を作らない（例: ×「コンテキストの経済」→ ○「コンテキスト管理」）。迷ったら公式ドキュメントの語彙に合わせる

---

## プロンプト例の規則

- **トーンの基準は公式ドキュメントの例文**（Common workflows等）。端的で要素が詰まった生の形を日本語に置き換える。丁寧語の完全文でなくてよく、箇条書き・短い指示形を使ってよい
- **固める要素は内容であって書式ではない**。毎回すべての要素を書く形式にしない。文脈に既にあるもの（直前に渡したファイル・Issueに書いたこと）は依頼文で繰り返さない
- **依頼は視界に収まる長さ**（目安10行）。超える内容は設計書・Issueに置いて参照で指す
- **解説は非自明な1点だけ**。読めば分かる行には触れない。「ポイントは◯つです」の個数宣言をしない
- 「この通り送ってください」は演習の再現性が要る箇所に限定し、他は「自分の言葉で」と書く
- **整理をAIに任せる例・探索の例**（未整理のまま投げる・案を並べさせる・壁打ち）を各章に必ず混ぜ、「常に構造化された依頼を書く」という誤学習を防ぐ

---

## 文体の規則（AI感の禁止事項）

| やめる | 代わり |
|:-------|:-------|
| 全節の「導入：警句」定型 | 導入は前節からの接続を1〜2文。警句は効く節だけ |
| 短文の連打・体言止めの連続 | 文長を混ぜる。1段落に主張は1つ |
| 同じ主張の節内再演・まとめでの全文再掲 | 本説明は1箇所。まとめは行動と判断基準だけ |
| プロンプト直後の全行解説 | 非自明な1点のみ |
| 比喩の重ね掛け | 1節1比喩まで。既出の比喩は再利用する |

原則は1行: **必要な情報を省略しない前提で、最短の表現**。

## 削る記述

次のものは書かない。見つけたら削除する。

- 「任せる」と「丸投げ」は違う／品質の責任はあなたが握る、といった精神論
- AIの報告を疑うよう求める記述
- 「最後の1回は自分で打つ」「自分の目で見る」式の作業の引き留め
- **「先に全部を自分で決めてから渡す」式の記述**。整理・言語化はAIとの対話でやる（決めるのは人）。AIに整理を投げることを妨げる書き方をしない
- 「分かったことをメモに残しましょう」式の優等生ムーブ
- 承認を全部飛ばす方法への警告。auto モードを標準として扱う
- 各Section冒頭で同じ主張を繰り返す定型ブロック

機構の事実・機能的指示（deny設定の効き方・承認の永続範囲・演習の合否条件・部品の動作指示など）は説教に見えても残す。ただし短く書く。

## 「AI出力は毎回変わる」前提の書式

- 判定は出力の一致ではなく**検証手段**（テスト・受け入れ条件・動作確認）で書く。「〜という出力になります」ではなく「〜を満たしていることを確認します」
- AI対話のやり取りは**テキストブロック**で示す。スクリーンショットを使うのは「状態が一目で伝わる初出UI」のみ（枚数・候補は方針Artifact 07）
- 変動する値（コマンド・料金・UI・同梱Skillの挙動）には「**2026年◯月時点**」を付け、「表示が違うときは `/help` と公式ドキュメント」への誘導を添える。バージョン番号・モデル名は原則書かない
- 出力例・進行例の冒頭に置く注記の正本:

```markdown
> 💡 **出力例について**: AIの応答は毎回変わります。以下はあくまで一例です。文言が違っても、チェックリストの項目を満たしていれば問題ありません。
```

```markdown
> 💡 **進行例について**: AIとの開発は毎回違う流れになります。ここに示すのは一つの進行例です。あなたの画面と違っていても、チェックリストを満たしていれば正解です。
```

## AI演習Sectionの標準構成

構成は**必要なものだけ使う部品**として扱う。中身の無い部品は置かない。

```
AI演習Section
│
├── 📌 この演習について（演習の目的。定型文は置かない）
│
├── 🎯 演習課題
│   ├── 📋 課題（目的・スコープ外・受け入れ条件）
│   ├── ✏️ 進め方タスク（番号リスト。各タスクに【自分】【AI】【自分⇄AI】の担当ラベル）
│   └── ✅ 完成チェックリスト（検証手段で書く）
│
├── 🏃 実践（一緒に進める用）
│   └── 📝 ステップバイステップ
│
├── 📖 進行例（模範解答の代わり。上の注記正本を冒頭に）
│
└── 🚀 まとめ
```

任意の部品: `💡 ヒント`／`🧠 先輩エンジニアの思考プロセス`。`💡 ヒント` が本文の再掲になる・`📖 進行例` が `📝` の逐語なぞりになる重複が起きやすい。**本説明は1箇所**。

### 検証の型（3点セット）

| 検証 | 方法 |
|:-----|:-----|
| テスト | 実装と同じ依頼に含め、AIに回させて直させる。人は証拠（実行結果）を読む |
| 受け入れ条件 | 人がブラウザで潰す＋Playwright MCPでAIにも回させる（T14 Ch4以降） |
| 設計の穴 | AIからの質問に設計書・Issueで答えられたかを振り返る |

---

## 手元の外へ出ていくもの（線引きの物差し）

物差しは1つ: **その作業の結果が、自分の手元の中で終わるか**。終わるなら任せてよい。

- よく挙げる例は3つ: 本番で動いているデータ／秘密の値（コミットしてGitHubへ送った時点で外に出る、と書く）／外部への公開。**この3つで全部とは書かない**（列挙で線を引かない）
- 「戻せるか」を物差しにしない。取り消せるかどうかは理由として使ってよいが、物差しにはしない

## フェーズ別AIスタンス定型文（T1〜T12のみ）

学習の前半では、AIとの距離感を定型文で示す。**T13以降では定型文を使わない**（P3・P4は廃止済み。T13の手描き方針は13-1-1に、T14の立場は14-1-1に、それぞれ1回だけ書く）。

| フェーズ | 対象 | AIの位置づけ | 定型文 |
|:---------|:-----|:-------------|:-------|
| Phase 1 | T1〜T10 | 先生（質問・解説） | 下記P1 |
| Phase 2 | T11〜T12 | 相棒（レビュー・壁打ち） | 下記P2 |

### P1（T1〜T10: AI=先生）

```markdown
> 🔥 分からないことがあったら、すぐに答えを見るのではなく、過去の教材を見返したり、AIに「質問」したりして、自分の力で実装してみましょう。この段階では、コードそのものをAIに書かせるのはぐっと我慢です。1-1-6でお話しした通り、設計ができる人は「自分の手でコードを書いたことがある人」だからです。
```

### P2（T11〜T12: AI=相棒）

```markdown
> 🔥 実装は引き続き自分の手で行いましょう。ただし、この段階からは書き終えたコードをAIにレビューしてもらったり、実装方針の相談相手（壁打ち）として使ったりするのはおすすめです。人のコードやAIの意見を読んで判断する力は、この後AIを率いるための土台になります。
```

> ⚠️ **運用ルール**: 定型文の本文はこのガイドを正本とし、各Sectionへはコピーして使う。文言を変更する場合はこのガイドを先に更新し、全Sectionへ一括反映する（lintが正本一致を検査する）。

## Claude Code の表記規約

- ツール名は「**Claude Code**」で統一。プラン名は「**Proプラン**」。料金・利用枠など変動する値は本文に固定で書かず、書く場合は「2026年◯月時点」を付ける
- **権限モードは `auto` を標準**として書く。auto は 2026年8月14日から Pro・Max・Team の新規セッションの既定（公式アナウンス）。ただし自分で既定を設定している人は変わらない旨を添える
- **`defaultMode: "auto"` はプロジェクトの `.claude/settings.json` では効かない**（ユーザー設定 `~/.claude/settings.json` に書く）。**`deny` ルールはプロジェクト側で効く**。この2つを混同しない
- **`Read()` の deny は Bash の `cat`・`head`・`tail`・`sed` も止める**が、スクリプトがファイルを開く経路は止まらない。「機械が止めるので安全」と言い切らない
- 公式・同梱の機能（`/code-review`・`/security-review`・skill-creator 等）は正式名で書き、「公式が出しているものを第一選択にする」の線で扱う
- セットアップ手順・UI記述は執筆時に実機確認し、確認日を明記する
