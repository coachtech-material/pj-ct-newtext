## AIとの距離感（教材全体の正本）

### 立場

**人がやるのは、ゴールを決めることと、できたものを検証することの2つだけ。** その間の作業はAIに渡す。

**AIに任せる範囲を狭めても、品質は上がらない。** 上がるのは、渡す情報が良いときと、確かめ方が決まっているときの2つ。T14・T15が扱うのはこの2つで、「AIをどこまで信じるか」という話はしない。

| 書かない | 書く |
|:---------|:-----|
| 疑う | **確かめる**（AIだからではなく、受け取る前だから。人が書いたコードでも同じ） |
| 自分の手でやる | **ゴールを決めて、検証する**（作業は渡す。人が持つのはこの2つだけ） |
| 慎重に進める | **速く、たくさん出す**（1回の指示で出てくる成果物の大きさが、AIを使う価値そのもの） |

慎重になるのは、**取り返しがつかないもの**に触るとき。見分ける物差しは「失敗したときに自分の手で元へ戻せるか」で、戻せるなら任せてよい。

### 削る記述

次のものは書かない。教材全体で削除する。

- 「任せる」と「丸投げ」は違う／品質の責任はあなたが握る、といった精神論
- AIの報告を疑うよう求める記述（「AIの『完了しました』は合格の証拠ではありません」）
- 「最後の1回は自分で打つ」「自分の目で見る」「自分の手で開く」式の作業の引き留め
- 「分かったことをメモに残しましょう」式の優等生ムーブ
- 承認を全部飛ばす方法への警告（「やってはいけない近道」）。auto モードを標準として扱う
- 各Section冒頭で同じ主張を繰り返す定型ブロック

### 残す記述（機構の事実・機能的指示）

説教に見えても、次は事実か機能なので残す。ただし短く書く。

- Claude Code は起動フォルダ配下を読める（`.env` も読める）。これは deny 設定で解決する話に接続する
- 承認の効き方（コマンドはリポジトリ単位で永続、編集はセッション限り。保存先は `.claude/settings.local.json`）
- `auto` モードは背景の安全性チェックを通したうえで自動承認する
- コンテキストの限界と `/context`
- 学習者が作る部品（Skill・サブエージェント）の本文に書かせる動作指示（「ファイルを書き換えません」等）。消すと部品の挙動が変わる
- 演習の合否に直結する条件（「落ちたテストを消して通すのは禁じ手」等）

### 「量を出す」を本文に効かせる2つの形

標語で終わらせないため、次の形で本文に落とす。

- **量が出せると、選べるようになる**。1案しか作れないときは最初の案を採るしかないが、3案作れるなら比べて選べる。AIに複数案を出させて選ぶ場面を演習に入れる
- **量が増えると、設計の質が効いてくる**。何を作るかが決まっていないまま量を出すと、違うものが大量にできる。T13で設計をやる理由をここに置く

## フェーズ別AIスタンス定型文（T1〜T12のみ）

学習の前半では、AIとの距離感を定型文で示す。**T13以降では定型文を使わない**。

| フェーズ | 対象 | AIの位置づけ | 定型文 |
|:---------|:-----|:-------------|:-------|
| Phase 1 | T1〜T10 | 先生（質問・解説） | 下記P1 |
| Phase 2 | T11〜T12 | 相棒（レビュー・壁打ち） | 下記P2 |

### P1（T1〜T10: AI=先生）

```markdown
> 🔥 分からないことがあったら、すぐに答えを見るのではなく、過去の教材を見返したり、AIに「質問」したりして、自分の力で実装してみましょう。この段階では、コードそのものをAIに書かせるのはぐっと我慢です。1-1-6でお話しした通り、設計ができる人は「自分の手でコードを書いたことがある人」だからです。
```

### P2（T11〜T12: AI=相棒）

```markdown
> 🔥 実装は引き続き自分の手で行いましょう。ただし、この段階からは書き終えたコードをAIにレビューしてもらったり、実装方針の相談相手（壁打ち）として使ったりするのはおすすめです。人のコードやAIの意見を読んで判断する力は、この後AIを率いるための土台になります。
```

> ⚠️ **運用ルール**: 定型文の本文はこのガイドを正本とし、各Sectionへはコピーして使う。文言を変更する場合はこのガイドを先に更新し、全Sectionへ一括反映する（lintが正本一致を検査する）。

## 大原則: 「AI出力は毎回変わる」前提で書く

AI演習は、実行するたびに出力（生成コード・応答文・かかる時間）が変わる。従来ハンズオンの「この通りに打てばこの画面になる」という決定的再現の書き方は成立しない。次の3原則で書く。

### 原則1: 判定は出力の一致ではなく、検証手段で行う

- 「〜という出力になります」ではなく「**〜を満たしていることを確認します**」と書く
- 完成チェックリストは必ず**検証手段**（テスト実行・受け入れ条件との突合・動作確認）で書く
- 出力例には必ず注記を付ける:

```markdown
> 💡 **出力例について**: AIの応答は毎回変わります。以下はあくまで一例です。文言が違っても、チェックリストの項目を満たしていれば問題ありません。
```

### 原則2: 操作手順は最小限、原則を中心に教える

- ツールのUI・コマンド体系は変わる。ボタン名や画面配置の詳細な列挙は避け、「**何を伝えるか・どこで承認するか・何で検証するか**」という原則を本文の主役にする
- どうしても必要な具体的コマンド・画面は、執筆時に実機確認し「**2026年◯月時点**」を明記する
- AI対話のやり取りはスクリーンショットではなく**テキストブロック**で示す（UIが変わっても価値が残り、修正も容易）:

```markdown
​```text
あなた: docs/design.md を読んで、タスク一覧に「完了」ボタンを追加する実装計画を立ててください。
Claude Code: （計画が提示される。ファイル変更の一覧と手順を確認し、問題なければ承認します）
​```
```

### 原則3: プロンプト例は「意図」とセットで示す

- 良いプロンプト例を示すときは、丸写しを防ぐため**なぜその書き方なのか**を併記する

```markdown
> 💡 このプロンプトのポイントは、①対象ファイルを名指ししている ②完成条件（テストが通る）を含めている、の2点です。文言をそのまま覚える必要はありません。
```

## AI演習Sectionの標準構成

`guides/handson-structure.md` のAI版。

構成は**必要なものだけ使う部品**として扱う。中身の無い部品は置かない。

```
AI演習Section
│
├── 📌 この演習について（演習の目的。定型文は置かない）
│
├── 🎯 演習課題
│   ├── 📋 課題（何を実現したいか・何は変えたくないか・どうなったら完成か）
│   ├── ✏️ 進め方タスク（番号リスト。各タスクに【自分】【AI】の担当ラベルを付ける）
│   └── ✅ 完成チェックリスト（検証手段で書く: テスト・受け入れ条件・動作確認）
│
├── 🏃 実践（一緒に進める用）
│   └── 📝 ステップバイステップ（プロンプト例＋承認・検証ポイント）
│
├── 📖 進行例（模範解答の代わり。下記参照）
│
└── 🚀 まとめ
```

任意の部品: `💡 ヒント`（詰まった時の型）／`🧠 先輩エンジニアの思考プロセス`。

> ⚠️ **重複しやすい箇所**: `💡 ヒント` が本文の再掲になる、`📖 進行例` が `📝 ステップバイステップ` の逐語なぞりになる、`💡 よくある間違い` が既出の言い直しになる、の3つが実測で最も多い。**本説明は1箇所**にする。

## 演習の作り方

演習の価値は難しさではなく、**成果物の大きさと指示の抽象度**で決まる。手で書いても終わる量を、超具体的な指示で作らせると、AIを使う価値が出ず実務とも乖離する。

| | やらない | やる |
|:--|:---------|:-----|
| **成果物の単位** | 1ファイルの変更、1メソッドの説明、返答の見比べ | **1機能まるごと**。Issueの作成からブランチ・実装・テスト・PRまで通す |
| **指示の粒度** | どのファイルに何を書くかを渡す | 何を実現したいか・何は変えたくないか・どうなったら完成か。**やり方は渡さない** |
| **人が手を出す場所** | 各ステップ（承認・確認・メモ） | planを読んで承認するところと、受け入れ条件と突き合わせるところの**2箇所だけ** |
| **AIの使い方** | 1案を出させて直す | **複数案を出させて選ぶ**場面を入れる |

「道具の挙動を観察する」課題（同じことを2通りで頼んで返答を比べる等）は作らない。観察が目的だと、AIに長い仕事をさせる場面が出てこない。

> ⚠️ **概念Sectionの 🏃 も同じ**。演習だけを大きくしても、概念Sectionが小さな問答の繰り返しだと、そちらが受講生の基準になる。実測では14-1-2が「4つの問いを1つずつ投げる」形で、直前の14-1-1が「速さと量」を掲げているのと食い違っていた。**概念Sectionでも、依頼は1つにまとめて大きく投げる**。1回の指示でテーブルから画面までまとめて出てくることを、早い段階で一度見せる。
>
> `/context` の読み取りのように、道具の状態を見せることが節の目的である場合だけは、観察の形でよい（14-2-2）。

### ✏️ 進め方タスクの担当ラベル

人とAIの役割分担を常に意識させるため、タスクごとに担当を明記する。

```markdown
### ✏️ 進め方タスク

1. 【自分】機能Issueを立て、docs/に設計書を用意する
2. 【自分⇄AI】設計書からタスク一覧を作り、Issueに起票する
3. 【AI】タスク1を実装させる（テスト作成を含めて指示する）
4. 【自分】差分をレビューし、テストを回して検証する
5. 【自分】受け入れ条件と突き合わせて動作確認する
```

### 📖 進行例の書き方 — 模範解答ではなく「一つの進行」

- コードの唯一解を示すのではなく、**承認ポイント・検証結果を含む一連の流れの実例**を示す
- 最終成果物のコードは「参考実装」として提示してよい（受講生のAIが生成するコードとは異なることを明記）
- 冒頭の定型文:

```markdown
> 💡 **進行例について**: AIとの開発は毎回違う流れになります。ここに示すのは一つの進行例です。あなたの画面と違っていても、チェックリストを満たしていれば正解です。
```

### 検証の型（3点セット）

演習の検証は次の3つを基本形とし、課題の性質に応じて取捨する。

| 検証 | 方法 | 学ばせること |
|:-----|:-----|:-------------|
| テスト | 実装時に先に書かせたテストを回す | まず機械に聞く |
| 受け入れ条件 | ユースケース記述（T13-Ch2）と突き合わせて動作確認 | 検収の目線 |
| 設計の穴 | AIからの質問に設計書で答えられたかを振り返る | 質問=穴の検出器 |

## 取り返しがつかないもの（全AI演習共通）

線を引く物差しは1つ。**失敗したときに、自分の手で元へ戻せるか**。恐怖ではなく、取り消せるかどうかで説明する。戻せるなら任せてよい。

教材でよく挙げる例は次の3つ。

- **本番で動いているデータ**
- **秘密の値**（パスワード・APIキー・個人情報）。演習で扱うのはダミー値だけで、ダミーであることを明記する
- **外部への公開**（一度出したものは取り消せない）

> ⚠️ **この3つは例であって、全部ではない**。「この3つ以外は任せて構いません」と書かない。挙げていない取り返しのつかない操作（外部サービスへの課金、他人が使っているものの削除など）はいくらでもある。列挙で線を引かず、**戻せるかどうかの物差しを渡す**。

承認を1件ずつ読ませる誘導や、承認疲れへの説教は書かない。権限は `.claude/settings.json` の設定で解決する話として扱う。

## Claude Code の表記規約

- ツール名は「**Claude Code**」で統一（クロードコード等の表記揺れ禁止）
- プラン名は「**Proプラン**」。料金・利用枠など変動する値は本文に固定で書かず、書く場合は「2026年◯月時点」を付ける
- モデル名・バージョン番号は原則書かない（すぐ古びるため）。「最新のモデル」等の相対表現にする
- **権限モードは `auto` を標準**として書く。`--permission-mode` は `manual`（＝従来の `default`）／`acceptEdits`／`plan`／`auto`／`dontAsk`／`bypassPermissions`（2026年8月・v2.1.228 で確認）。`auto` は、別の分類モデルが実行前に行動を検査し、依頼の範囲を超えるもの・見覚えのない基盤を対象にするもの・読み込んだ内容に誘導されたものを止めたうえで自動承認するモード
- **auto は 2026年8月14日から Pro・Max・Team の新規セッションの既定になる**（公式アナウンス）。教材では「既定は auto です（2026年8月時点）」と書いてよい。ただし自分で既定を設定している人は変わらない旨を添える
- **`defaultMode: "auto"` はプロジェクトの `.claude/settings.json` では効かない**（リポジトリが自分に auto を与えられないよう、v2.1.142 以降は無視される）。ユーザー設定の `~/.claude/settings.json` に書く。**`deny` ルールはプロジェクト側で効く**ので、この2つを混同して書かない
- **`Read()` の deny は、Claude の読み書きツールに加えて Bash の `cat`・`head`・`tail`・`sed` も止める**。ただしスクリプト（Python や Node）がファイルを開く経路は止まらない。「機械が止めるので安全」と言い切らず、この範囲まで書く
- セットアップ手順は執筆時に実機確認し、確認日を明記する
