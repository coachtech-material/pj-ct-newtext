# AI演習Section構成ガイド

> **目的**: T14「AIを率いて開発しよう」・T15「AI開発を仕組み化しよう」のAI演習Sectionの構成を統一し、「AI出力は毎回変わる」前提でも品質がぶれない教材の書き方を定義する。あわせて、教材全体で使うフェーズ別AIスタンス定型文の正本とする

---

## 対象と前提

- **対象**: T14・T15の全Section（AI協働の概念Sectionと演習Section）、および全Tutorialのハンズオンに入るフェーズ別定型文
- **土台**: 文体・分量・マークダウン要素は `guides/writing-rules.md` に従う。設計成果物の扱いは `guides/design-section-structure.md` と接続する
- **確定事項**（構成確定版Artifactより）:
  - 受講生のAIツールは **Claude Code Proプラン** を標準とする
  - 作図はT14以降Mermaidに移行（AIに起こさせ、人が読んで検証する）
  - 検証の合言葉は「**設計書で答えられない質問が来たら、それが設計の穴**」

## フェーズ別AIスタンス定型文（教材全体の正本）

学習フェーズによってAIとの距離感を変える。ハンズオン・演習の冒頭に、該当フェーズの定型文を置く。

| フェーズ | 対象 | AIの位置づけ | 定型文 |
|:---------|:-----|:-------------|:-------|
| Phase 1 | T1〜T10 | 先生（質問・解説） | 下記P1 |
| Phase 2 | T11〜T12 | 相棒（レビュー・壁打ち） | 下記P2 |
| Phase 3 | T13 | 質問は可・作図は手で | 下記P3 |
| Phase 4 | T14〜T15・T16 | 部下（実装させ、検証する） | 下記P4 |

### P1（T1〜T10: AI=先生）

```markdown
> 🔥 分からないことがあったら、すぐに答えを見るのではなく、過去の教材を見返したり、AIに「質問」したりして、自分の力で実装してみましょう。この段階では、コードそのものをAIに書かせるのはぐっと我慢です。1-1-6でお話しした通り、設計ができる人は「自分の手でコードを書いたことがある人」だからです。
```

### P2（T11〜T12: AI=相棒）

```markdown
> 🔥 実装は引き続き自分の手で行いましょう。ただし、この段階からは書き終えたコードをAIにレビューしてもらったり、実装方針の相談相手（壁打ち）として使ったりするのはおすすめです。人のコードやAIの意見を読んで判断する力は、この後AIを率いるための土台になります。
```

### P3（T13: 設計は手で描く）

```markdown
> 🔥 この演習では、設計書をAIに作らせずに、自分の手で書きましょう。記法や考え方についてAIに質問するのは構いませんが、成果物を生成させるのはTutorial 14までお預けです。まず自分の手と頭で書けるようになった人だけが、AIの作った設計を正しく評価できるようになります。
```

### P4（T14〜T15・T16: AI=部下）

```markdown
> 🔥 ここからは、AIに実装を任せて構いません。ただし「任せる」と「丸投げ」は違います。何を作るかは設計書で自分が決め、出てきたものはテスト・動作確認・コードレビューで自分が検証します。品質の責任は、AIではなくあなたが握ります。
```

> ⚠️ **運用ルール**: 定型文の本文はこのガイドを正本とし、各Sectionへはコピーして使う。文言を変更する場合はこのガイドを先に更新し、全Sectionへ一括反映する。

**置き場所**（T14の20Sectionで確立した運用）:

| Section種別 | 置き場所 |
|:------------|:---------|
| AI演習Section | 「📌 この演習について」の中（下記の標準構成のとおり） |
| 概念Section（🏃 実践パートを持つもの） | 「## 🏃」見出しの直後 |
| 概念Section（実践パートを持たないもの） | 置かない |

同じ章の中で何度も繰り返すことになるが、Sectionは単独で読まれるため各Sectionに置く。

## 大原則: 「AI出力は毎回変わる」前提で書く

AI演習は、実行するたびに出力（生成コード・応答文・かかる時間）が変わる。従来ハンズオンの「この通りに打てばこの画面になる」という決定的再現の書き方は成立しない。次の3原則で書く。

### 原則1: 判定は出力の一致ではなく、検証手段で行う

- 「〜という出力になります」ではなく「**〜を満たしていることを確認します**」と書く
- 完成チェックリストは必ず**検証手段**（テスト実行・受け入れ条件との突合・動作確認）で書く
- 出力例には必ず注記を付ける:

```markdown
> 💡 **出力例について**: AIの応答は毎回変わります。以下はあくまで一例です。文言が違っても、チェックリストの項目を満たしていれば問題ありません。
```

### 原則2: 操作手順は最小限、原則を中心に教える

- ツールのUI・コマンド体系は変わる。ボタン名や画面配置の詳細な列挙は避け、「**何を伝えるか・どこで承認するか・何で検証するか**」という原則を本文の主役にする
- どうしても必要な具体的コマンド・画面は、執筆時に実機確認し「**2026年◯月時点**」を明記する
- AI対話のやり取りはスクリーンショットではなく**テキストブロック**で示す（UIが変わっても価値が残り、修正も容易）:

```markdown
​```text
あなた: docs/design.md を読んで、タスク一覧に「完了」ボタンを追加する実装計画を立ててください。
Claude Code: （計画が提示される。ファイル変更の一覧と手順を確認し、問題なければ承認します）
​```
```

### 原則3: プロンプト例は「意図」とセットで示す

- 良いプロンプト例を示すときは、丸写しを防ぐため**なぜその書き方なのか**を併記する

```markdown
> 💡 このプロンプトのポイントは、①対象ファイルを名指ししている ②完成条件（テストが通る）を含めている、の2点です。文言をそのまま覚える必要はありません。
```

## AI演習Sectionの標準構成

`guides/handson-structure.md` のAI版。

```
AI演習Section
│
├── 📌 この演習について
│   └── 演習の目的＋フェーズ定型文（P4）
│
├── 🎯 演習課題
│   ├── 📋 課題（何を作るか。設計書・Issueなど入力になるものを明記）
│   ├── ✏️ 進め方タスク（番号リスト。各タスクに【自分】【AI】【自分⇄AI】の担当ラベルを付ける）
│   └── ✅ 完成チェックリスト（検証手段で書く: テスト・受け入れ条件・動作確認）
│
├── 💡 ヒント（詰まった時の型: 巻き戻す・小さく分ける・2回直らなければ仕切り直す）
│
├── 🏃 実践（一緒に進める用）
│   ├── 🧠 先輩エンジニアの思考プロセス（何を渡し、どこで承認し、何で検証するかの表）
│   └── 📝 ステップバイステップ（プロンプト例＋期待される流れ＋承認・検証ポイント）
│
├── 📖 進行例（模範解答の代わり。下記参照）
│
└── 🚀 まとめ
```

### ✏️ 進め方タスクの担当ラベル

人とAIの役割分担を常に意識させるため、タスクごとに担当を明記する。

```markdown
### ✏️ 進め方タスク

1. 【自分】機能Issueを立て、docs/に設計書を用意する
2. 【自分⇄AI】設計書からタスク一覧を作り、Issueに起票する
3. 【AI】タスク1を実装させる（テスト作成を含めて指示する）
4. 【自分】差分をレビューし、テストを回して検証する
5. 【自分】受け入れ条件と突き合わせて動作確認する
```

### 📖 進行例の書き方 — 模範解答ではなく「一つの進行」

- コードの唯一解を示すのではなく、**承認ポイント・検証結果を含む一連の流れの実例**を示す
- 最終成果物のコードは「参考実装」として提示してよい（受講生のAIが生成するコードとは異なることを明記）
- 冒頭の定型文:

```markdown
> 💡 **進行例について**: AIとの開発は毎回違う流れになります。ここに示すのは一つの進行例です。あなたの画面と違っていても、チェックリストを満たしていれば正解です。
```

### 検証の型（3点セット）

演習の検証は次の3つを基本形とし、課題の性質に応じて取捨する。

| 検証 | 方法 | 学ばせること |
|:-----|:-----|:-------------|
| テスト | 実装時に先に書かせたテストを回す | まず機械に聞く |
| 受け入れ条件 | ユースケース記述（T13-Ch2）と突き合わせて動作確認 | 検収の目線 |
| 設計の穴 | AIからの質問に設計書で答えられたかを振り返る | 質問=穴の検出器 |

## ガードレール（全AI演習共通の注意）

- **機密情報**: `.env`・パスワード・個人情報をAIに貼らない。演習内で扱う場合はダミー値であることを明記する
- **権限の承認**: ファイル変更・コマンド実行の承認を求められたら、内容を読んでから許可する習慣を付けさせる（「読まずに全部許可」を明示的に注意）
- **鵜呑みの禁止**: AIの説明にも誤りはあり得る。検証手段を通ったものだけを信じる、を全編で一貫させる

---

## Claude Code の表記規約

- ツール名は「**Claude Code**」で統一（クロードコード等の表記揺れ禁止）
- プラン名は「**Proプラン**」。料金・利用枠など変動する値は本文に固定で書かず、書く場合は「2026年◯月時点」を付ける
- モデル名・バージョン番号は原則書かない（すぐ古びるため）。「最新のモデル」等の相対表現にする
- セットアップ手順（14-1-2）は執筆時に実機確認し、確認日を明記する

## 執筆時のチェックリスト

- [ ] フェーズ定型文（P4）が演習冒頭にある
- [ ] 完成チェックリストが検証手段（テスト・受け入れ条件・動作確認）で書かれている
- [ ] 出力例・進行例に「毎回変わる」注記がある
- [ ] 進め方タスクに【自分】【AI】の担当ラベルがある
- [ ] プロンプト例に意図の解説が付いている
- [ ] AI対話はスクリーンショットでなくテキストブロックで示している
- [ ] 変動する値（コマンド・料金・UI）に「◯◯時点」が付いている
- [ ] ガードレール（機密・承認・鵜呑み）に反する誘導がない

> ⚠️ **quizについて**: `quiz/` の確認問題はアイデア段階の試行（既存Sectionのみ）のため、**新規Sectionでは作成しない**。方針確定後に一括追加する。
